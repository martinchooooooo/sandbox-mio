# Paseo Plugins E2E

This document is the test plan for the delivery and registration pipeline built in `docs/features/paseo-plugins/02_dev.md` (Phases A to C). It plans one `standard` spec against a real Podman sandbox. The app-side half of the proof, the deterministic archive and the Paseo version coupling, already lives in `cargo test` (`src-tauri/src/runtime/paseo_plugins.rs`). The spec is written and passes (`## De-risking spike results`). The delivery spike (`docs/features/paseo-plugins/spike/spike.md`) and the manual probe check in `02_dev.md` Phase D cleared the in-sandbox mechanics.

## Goal

Prove the real code path: an Agents-pane open (`open_agent_web`, then `prepare_agent_web()` in `src-tauri/src/runtime/mod.rs`) builds the plugin bundle, `paseo-up.sh` (`src-tauri/resources/agent-web/paseo-up.sh`) answers exit 12, the delivery script (`src-tauri/resources/agent-web/paseo-plugins-deliver.sh`) receives the archive over a real `podman exec` stdin pipe, and the next `paseo-up.sh` run merges `~/.paseo/config.json` and starts the real Paseo daemon with `mio-probe` running. The same spec exercises the three re-open outcomes: nothing changed (no restart, no reload), contents changed (in-place `paseo plugin reload`), and plugin set changed (daemon restart).

A weaker test would fail to cover:

- **A `light` spec proves nothing here.** `MockRuntime::prepare_agent_web()` is deliberately unchanged (`02_dev.md`, Resolved Decision 6), so under `MIO_MOCK_BACKEND=1` no archive is delivered and no daemon runs.
- **A Rust unit test of the archive** cannot show that `tar --no-same-owner` extracts the host-built archive inside the container, that the swap leaves a matching `.bundle-hash`, or that Paseo accepts the merged `config.json` and compiles the plugin.
- **Reading `paseo plugin ls` once** would not show the restart rule. The pid in `~/.paseo/paseo.pid` is the evidence: unchanged for reload-only re-opens, changed when the plugin set changes.

Deliberate boundary: the spec asserts that Paseo reports the plugin `running` and that the delivered files equal the repository's files. It does not render the probe panel in the Agents webview, because that needs a conversation and Paseo's minified SPA; the panel and its RPC were checked by hand on Podman (`02_dev.md`, Phase D).

## Existing test styles

- `e2e/test/specs/standard/agent-web.spec.ts` is the closest relative. It drives a real sandbox through `useSandboxWorkspace()` and the `openAgentWeb()`/`closePane()` helpers in `e2e/lib/workspace.ts`, reads daemon state back with `podman exec`, and asserts the daemon pid is unchanged across a re-open. The new spec copies its shape.
- `e2e/test/specs/standard/base-image-recipe.spec.ts` reads repository files relative to the spec file; the new spec reads `paseo-plugins/` the same way.

## Chosen approach

**Tier: `standard`**, spec `e2e/test/specs/standard/agent-web-plugins.spec.ts`, topology: one local sandbox on the `mio-tests` machine, no remote machine. The first Agents open installs Node and the Paseo CLI through mise, the same order of cost as `agent-web.spec.ts`; no large asset or remote deploy is involved, so `heavy` is not warranted. The run takes the host lock and serialises against other real-infrastructure runs; that is the intended cost.

Decisions:

- **Open through the command, not the launcher.** The spec calls `openAgentWeb()` after `row.openWorkspace()`. It skips the Pi install that `agent-web.spec.ts` needs to unlock the Manage launcher, because the delivery path is identical and the install adds minutes.
- **Edit the sandbox, not the repository.** Reload, redelivery and restart are provoked by changing files and markers inside the container. A spec that edited `paseo-plugins/` would modify the worktree during the run and race a neighbouring edit.
- **No new host paths.** The spec reads only the repository's `paseo-plugins/mio-probe/` (read-only, located from the spec file) and the container. Host app data and workspaces come from `useSandboxWorkspace()` and `e2e/lib/run-identity.ts`.
- **No harness change.** `e2e/package.json` gains a `test:agentweb-plugins` script beside `test:agentweb`.

Not covered by this plan:

- **Microsandbox sandboxes.** The delivery goes through the microsandbox provider's `exec_piped()` instead of Podman's. It needs a base-image build and `msb` VM boot, so it stays a manual check (`02_dev.md`, Phase D).
- **Deployed sandboxes.** Delivery reaches a deployed sandbox through the same `prepare_agent_web()` on the remote provider. Chaining a deploy and an Agents open would be a `heavy` spec; it stays a manual check for now.

## Spec scenario

1. **Create and start a sandbox.** Create through `ProjectsPage.createProject()`, `row.start()`, `row.waitForRunning()`. Open the workspace with `row.openWorkspace()`.
2. **First open delivers and registers.** `openAgentWeb()`, then wait for the `agentweb` pane in `workspaceState()`. Assert:
   - `/usr/local/lib/mio/paseo-plugins/.bundle-hash` holds a 64-character hex digest, and `~/.paseo/mio-plugins-loaded` holds the same value.
   - Every file under the repository's `paseo-plugins/mio-probe/` has the same SHA-256 inside the container, and the container directory holds no `node_modules` and no dotfile besides the marker.
   - `~/.paseo/config.json` has `pluginsEnabled: true` and a `mio-probe` entry with `source: "directory"` and the delivered path.
   - `paseo plugin ls` lists `mio-probe` as `running`, polled for up to `AGENT_SETTLE` because Paseo compiles it after startup.
   - `/root/work` contains no `mio-probe` directory, so the plugins stay outside the workspace.
3. **Unchanged re-open does nothing.** Record the daemon pid and the number of `paseo plugin logs mio-probe` lines. `closePane()`, `openAgentWeb()`. The pid and the log line count are unchanged.
4. **Contents-only change reloads in place.** Write a different value into `~/.paseo/mio-plugins-loaded` (the state after the app ships new plugin contents). Re-open. The marker equals `.bundle-hash` again, the pid is unchanged, the plugin log shows new lines, and `mio-probe` is `running`.
5. **A stale delivery is redelivered.** Append junk to the delivered `index.client.tsx` and delete `.bundle-hash`. Re-open. The delivered file equals the repository file again and `.bundle-hash` is restored, with the pid unchanged because the plugin set is the same.
6. **A changed plugin set restarts the daemon and prunes.** Stop the daemon with `paseo daemon stop`, then edit `config.json` to add a `mio-ghost` entry with no folder and a non-`mio` `user-plugin` entry, and delete `~/.paseo/mio-launch`. Re-open. The pid differs, `mio-probe` is `running`, `mio-ghost` is gone, `user-plugin` is still present, and `pluginsEnabled` is `true`.
7. **Destroy removes the container.** `row.destroy()`, then assert `podman inspect` fails. The plugin directory and `~/.paseo` die with the container filesystem, so nothing is left to clean on the host.

Every step uses named budgets from `e2e/lib/timeouts.ts`, and the spec calls `captureDiagOnFailure()`.

## De-risking spike results

No separate spike was run; the first run of the spec on 2026-11-20 doubled as one and cleared both open risks. Command: `./build e2e agentweb-plugins` (`pnpm run test:agentweb-plugins` in `e2e/`), 7 passing in about 2 minutes against the `mio-tests` machine.

| Risk | Result |
|---|---|
| `paseo plugin ls` output cannot be matched by a plain line check | Cleared. A line containing the plugin id and `running` is enough |
| Paseo rewrites `config.json` between the step 6 edit and the re-open and drops the `user-plugin` entry | Cleared. The daemon was stopped first, and the entry survived the merge and the restart |

## Common Gotchas

| Gotcha | Cause | Fix |
|---|---|---|
| The spec sees a restart in step 3 or 4 although nothing changed | A tool install changed `mise.toml` between the two pid reads, and `mise.toml` is part of the restart key in `src-tauri/resources/agent-web/paseo-up.sh` | Read the pid only after the first open settled, and install nothing between reads |
| `paseo plugin ls` shows `mio-probe` as `starting` or absent right after the pane appears | Paseo compiles plugins in the background after the daemon answers `/api/status` | Poll for `running` with the `AGENT_SETTLE` budget instead of reading once |
| A host-side edit of `paseo-plugins/` changes the expected hashes mid-run | A debug build rebuilds the bundle from the worktree on every `prepare_agent_web()` call | The spec compares delivered files with the repository files at the time of each re-open and never edits the repository |
| `podman exec` output of `sha256sum` has CRLF or extra columns on Windows | The command output passes through the Windows podman client | Split on whitespace and take the first column, as the host digests are computed with `node:crypto` |

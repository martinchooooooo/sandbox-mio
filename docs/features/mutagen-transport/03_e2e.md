# Mutagen-Based Transport: E2E Test Plan

This is the test plan for `docs/features/mutagen-transport/02_dev.md`'s **Phase A** (`PortTransport`/`PodmanPortTransport` extraction) — the only phase in that plan with an observable, real-backend code path to prove. No spike has been run; this feature has not been implemented yet. Phase B (`SshAlias` split) and Phase C (`SyncStrategy::Volume`) are pure type-shape refactors with no new runtime behaviour — `02_dev.md` already scopes their verification to `cargo check` (Phase C) and a check that existing `light` specs touching `write_alias` still pass (Phase B), and neither needs a new spec here. If Phase B or C is later found to need real-backend coverage of its own, that belongs in an update to this document, not a silent gap.

## Goal

Prove that after `prepare_terminal`, `prepare_agent_web` (`src-tauri/src/runtime/mod.rs`), and `expose_port` (`src-tauri/src/network/mod.rs`) are rewritten to call `PortTransport::resolve_remote_port` instead of inlining `podman port <name> <port>/tcp` + `parse_host_port`, all three still resolve the real Podman-published loopback port and the resulting Mutagen forward still reaches the real service behind it — i.e., the extraction changed *where* the lookup code lives, not what it does. A weaker test — one that calls `resolve_remote_port` directly with a fabricated `sandbox`/`connection`/`container_port` and asserts on its return value — would prove the function parses `podman port` output correctly but would not prove any of the three real call sites actually invoke it, or that the resulting forward chain (Mutagen SSH tunnel → Podman-machine loopback → container loopback) still connects end-to-end; a wiring mistake in `prepare_terminal`/`prepare_agent_web`/`expose_port` (e.g., still calling the old inline code, or passing the wrong `container_port`) would go undetected.

A secondary, narrower goal: prove `PodmanPortTransport`'s `podman port` call goes through `crate::backends::podman_command()` (the bundled-`podman.exe`-resolving constructor) rather than reproducing `network/mod.rs`'s old bare `Command::new("podman")`, since `02_dev.md`'s Resolved Decisions calls this out as a real bug fix riding along with the extraction. This part is **not** provable at the e2e level — a dev machine's `PATH` `podman` and the bundled sidecar `podman.exe` are typically the same install, so a spec cannot observe a difference between "used the bundled resolver" and "used whatever's on PATH." See Common Gotchas.

## Chosen Approach

**Standard tier, reusing three existing specs rather than writing a new one.** All three of `PortTransport`'s real call sites already have full real-backend coverage from features built before this refactor:

- `e2e/test/specs/standard/embedded-workspace.spec.ts` drives `prepare_terminal_webview` (`src-tauri/src/lib.rs`) → `RuntimeManager::prepare_terminal` and asserts the resulting URL is `http://127.0.0.1:<port>/<sandbox-name>` (line ~148) and that `zellij web --status` reports `online` against the real container (line ~205) — this is the `ZELLIJ_WEB_PORT` lookup Phase A moves into `PortTransport`.
- `e2e/test/specs/standard/agent-web.spec.ts` drives `prepare_agent_web` → the `PASEO_WEB_PORT` lookup, the other `RuntimeManager` call site Phase A touches.
- `e2e/test/specs/standard/expose-port.spec.ts` drives `NetworkManager::expose_port`'s relay-pool path end-to-end: it starts a real `socat` fake service inside the container (`startFakeService`), exposes it via the UI, and dials the resulting Windows-host loopback port with a raw TCP socket (`readOnce`) to confirm the byte-for-byte round trip through the real relay and the real Mutagen forward (lines 82–114). This is the specific scenario `02_dev.md`'s Phase A note flags as needing the `podman_command()` fix, since it's the one call site that previously used the bare-`Command::new("podman")` free function.

No fourth spec is added. Running these three unmodified after Phase A lands is the actual regression signal — if any of the three still-inline `podman port`/`parse_host_port` call sites is missed, or is wired to the new `PortTransport` call incorrectly (wrong `container_port` argument, wrong `connection`), the corresponding spec's TCP-dial or URL-shape assertion fails exactly the way it would have caught a hand-written bug in the pre-refactor code. This matches `01_ideas.md`'s framing of this extraction as "verifiable by the existing `standard` tier alone" and follows Decision rule 4 (`e2e/AGENTS.md`): the real spec is the source of truth, and there is no edge case here awkward enough to justify a paired `light` spec — `PortTransport`'s only implementation this feature adds is Podman's, has no new gating/UI logic, and the light tier does not exercise any of these three call sites today (`network/mock.rs`'s doc comment: "the light tier never opens a terminal/agent-web pane or exposes a port today").

**Prerequisite:** none beyond what these three specs already require — a real `mio-tests` Podman machine (`e2e/AGENTS.md`), no new provisioning, no new `wdio.conf.ts` wiring, no new host port or app-data path (Phase A introduces no new host-global state per `02_dev.md`'s Parallel-worktree constraints section).

## Spec Scenario

Run the three specs unmodified against the Phase A build, in this order (fastest-to-fail first so a wiring mistake surfaces before burning the full `expose-port.spec.ts` budget):

1. **`agent-web.spec.ts`** — creates a sandbox, opens the Agents web pane, and asserts the resulting connection reaches the real `paseo` daemon. Failure here means `prepare_agent_web`'s new `self.port_transport.resolve_remote_port(name, connection, PASEO_WEB_PORT)` call is missing, mis-wired, or `PodmanPortTransport` doesn't parse `podman port`'s output the same way `parse_host_port` did.
2. **`embedded-workspace.spec.ts`** — creates two sandboxes, opens each one's Terminal pane, and asserts the URL shape and that `zellij web --status` reports `online` for the real container behind the resolved port. Same failure mode as above, for the `ZELLIJ_WEB_PORT` call site.
3. **`expose-port.spec.ts`** — the highest-value spec for this phase: exposes a real `socat`-backed fake service via the relay pool, and dials the resolved host port with a raw socket to read back a literal token (`MANUAL_TOKEN`/`FILE_TOKEN`). This is the spec most likely to catch the `podman_command()`-vs-bare-`Command::new` mismatch indirectly — if `PodmanPortTransport` resolved a different `podman` binary than the one that actually built the container and started the relay, the port lookup could point at a stale or nonexistent mapping and the TCP dial would time out (`readOnce`'s 10s timeout) rather than returning the expected token. It also exercises `watch_ports_file`'s auto-expose/auto-unexpose path (steps 3–4 in the spec), which calls `expose_port`/`unexpose_port` the same way the manual UI path does, so both call shapes into the relay-pool `PortTransport` usage get covered.

All three should be run via `./build e2e` (`standard`) rather than individually where practical, since a merge-time `standard` run is already required by `02_dev.md`'s Phase D and this is the same run.

## De-Risking Spike Results

No spike run. `01_ideas.md`'s Validation section notes this extraction rests on evidence already gathered by other features (`host-tool-ssh-access`'s confirmation that `open_forward` is connection-agnostic, `remote-sync`'s two-machine validation of `MutagenCli`) rather than needing its own; the same reasoning extends to this phase's e2e coverage — the three specs above already proved the *behaviour* this phase must preserve, so no exploratory spike is needed before writing (there is nothing here that wasn't already working end-to-end pre-refactor).

## Common Gotchas

| Gotcha | Cause | Fix |
|---|---|---|
| `expose-port.spec.ts`'s `readOnce()` times out after Phase A lands, but only intermittently or only on a specific machine | `PodmanPortTransport` resolved the wrong `podman` binary (e.g. the extraction accidentally kept `network/mod.rs`'s old bare `Command::new("podman")` shape instead of switching to `crate::backends::podman_command()`) and that machine's `PATH` `podman` is a different install/version than the bundled sidecar the container was actually built and started with | Confirm `PodmanPortTransport::resolve_remote_port` (`src-tauri/src/transport/mod.rs`) calls `crate::backends::podman_command()`, not a fresh `Command::new("podman")`, per `02_dev.md`'s Resolved Decisions |
| `embedded-workspace.spec.ts` or `agent-web.spec.ts` fails with a URL/status assertion but `expose-port.spec.ts` passes | The `RuntimeManager` call sites (`prepare_terminal`/`prepare_agent_web`) were not actually switched to `PortTransport`, or were switched with the wrong `container_port` constant (`ZELLIJ_WEB_PORT`/`PASEO_WEB_PORT` swapped or reused), while `NetworkManager::expose_port`'s separate call site was updated correctly | Check both `runtime/mod.rs` call sites individually — Phase A touches three call sites across two files, and a partial migration passes some specs while failing others |
| A spec-level assertion is added to try to directly prove the `podman_command()` vs bare-`Command::new` distinction | The two resolve to the same binary on any machine where `PATH` `podman` and the bundled sidecar happen to match, which is true for every CI/dev machine this suite runs on today | Don't try to prove this at the e2e level (see Goal); if it needs a direct assertion, add a narrow `cargo test` on `PodmanPortTransport`'s constructed `Command`'s program path with `PODMAN_RESOURCE_DIR` set, not a new spec |
| Running only `expose-port.spec.ts` after a Phase A change and calling it sufficient | `expose-port.spec.ts` covers the `NetworkManager::expose_port` call site but not either `RuntimeManager` call site (`prepare_terminal`/`prepare_agent_web`), which have their own separate `PortTransport` wiring | Run all three specs listed in Spec Scenario — a `standard`-tier merge run already does this by default, so this only matters when running specs individually during development |

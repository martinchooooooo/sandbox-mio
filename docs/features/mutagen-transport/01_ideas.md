# Mutagen-Based Transport: Decoupling Ports and Workspaces from Podman

This document covers generalising port forwarding and workspace file transport away from Podman-specific mechanisms — `podman port`, the `pasta:--host-lo-to-ns-lo` network flag, `--volume` bind mounts, and the relay-pool `socat` trick tied to `podman exec` — onto a provider-neutral transport built on the Mutagen sidecar this project already bundles. It is a refactor, not a new user-facing capability: nothing here changes what a Podman sandbox does today. The trigger is `docs/features/microsandbox-provider/01_ideas.md`, which needs both ports and the workspace reachable from a second provider (`msb`) that has no bind-mount story on Windows and no `podman port`-shaped "what did you publish" query. That document currently designs microsandbox-specific answers for both problems (a `--kind disk` volume synced by `MutagenCli`, and explicit `msb create -p` host-port allocation plus forcing services onto `0.0.0.0`). This feature extracts the general shape those answers are instances of, so `MachineProvider` (the seam `microsandbox-provider/01_ideas.md` proposes at `src-tauri/src/provider/types.rs`) has one transport story to implement instead of two providers each inventing their own. Relevant files: `src-tauri/src/network/mod.rs` and `types.rs` (`NetworkManager`, `MutagenNetworkManager`), `src-tauri/src/sync/mod.rs` and `types.rs` (`MutagenCli`, `forward_create`), `src-tauri/src/ssh/mod.rs` and `types.rs` (`SshAlias`, `write_alias`), `src-tauri/src/runtime/mod.rs` (`PodmanMiseRuntime::podman_on`, `prepare_terminal`, `prepare_agent_web`), and `src-tauri/src/backends/mod.rs` (`create`, `deploy`, `resolve_workspace`, `ensure_connection_alias`).

## Current State

**Port forwarding is already connection-agnostic at the `NetworkManager` layer, but not below it.** `NetworkManager::open_forward` (`src-tauri/src/network/types.rs`) takes a bare `connection: &str` and a `remote_port: u16`, and its implementation (`MutagenNetworkManager::open_forward`, `src-tauri/src/network/mod.rs:135`) does nothing Podman-specific: it allocates a Windows-host loopback port and calls `crate::sync::forward_create(&self.app, &name, host_port, connection, remote_port)`. `docs/features/host-tool-ssh-access/01_ideas.md` already documents that this same path works identically for local and remote Podman targets today, because `crate::sync::forward_create` (`src-tauri/src/sync/mod.rs:80`) only ever needs an SSH `Host` alias (`connection`) and a numeric remote port — it has no notion of "Podman" at all.

What *is* Podman-specific is how `remote_port` gets produced and what it means once dialled:

- `RuntimeManager::prepare_terminal`/`prepare_agent_web` (`src-tauri/src/runtime/mod.rs:245`, `:292`) each end by running `podman port <name> <port>/tcp` and parsing the `127.0.0.1:<N>` line out of its output (`parse_host_port`, line 73). That `N` — a port on the Podman *machine's* own loopback, not the container's — is what gets handed to `open_forward` as `remote_port`.
- `MutagenNetworkManager::expose_port` (`src-tauri/src/network/mod.rs:206`) does the same lookup (line 238) after starting a `socat` relay inside the container (lines 229–235) that bridges a fixed relay-pool slot (`RELAY_PORT_POOL_START`/`RELAY_POOL_SIZE`, lines 21–23) to the user's actual `target_port`. The relay exists only because Podman cannot publish a *new* container port without recreating the container (`create`, `src-tauri/src/backends/mod.rs:402`, which hard-codes the zellij, paseo, and eight relay-pool ports into the `podman create` argv at lines 422–431), so every port that might ever need forwarding has to be pre-published at create time, and `expose_port` picks a free pre-published slot and points a fresh `socat` at whatever port the user actually wants.
- Both lookups depend on `SshAlias` (`src-tauri/src/ssh/mod.rs`, `types.rs`) resolving to **the Podman host/machine**, not the container: `ensure_connection_alias` (`src-tauri/src/backends/mod.rs:729`) reads `podman system connection list` for `host`/`port`/`user`/`identity` and writes those into the managed `~/.ssh/sandbox-mio/config` block. `forward_create`'s destination string, `{remote_alias}:tcp:127.0.0.1:{remote_port}`, therefore means "SSH to the Podman machine, then dial its own loopback" — which is exactly the loopback Podman's `--publish 127.0.0.1::<port>` plus the `pasta:--host-lo-to-ns-lo` network flag (`src-tauri/src/backends/mod.rs:411–428`) arranges to be reachable at all. Without that flag, pasta forwards published ports to the container's `eth0`, not its loopback, and zellij/paseo bind loopback only (comment at backends/mod.rs:411–422).

**Workspace transport already has two branches, both still Podman-shaped.** `resolve_workspace` (`src-tauri/src/backends/mod.rs:351`, documented in `docs/features/remote-sync/01_ideas.md`) returns a `WorkspacePlan { bind_mount_source, laptop_dir, strategy }`. For `SyncStrategy::Local` the two paths are equal and nothing syncs — a direct Podman bind mount (`--volume <path>:/root/work` in `create`). For `SyncStrategy::Remote(info)`, `MutagenCli` (`src-tauri/src/sync/mod.rs`) syncs the laptop directory against a *remote directory Podman then bind-mounts* (`deploy`, `backends/mod.rs:550`, `volume = format!("{}:{WORKSPACE_MOUNT}", plan.bind_mount_source)`). Mutagen is already load-bearing for one of the two branches; the branch that isn't Mutagen-backed (`Local`) is the one that breaks for microsandbox, because a bind mount is what fails on Windows (see `microsandbox-provider/01_ideas.md`, Validation).

**`RuntimeManager`'s Podman coupling is deeper than the port lookups above.** Every method in `PodmanMiseRuntime` (`src-tauri/src/runtime/mod.rs`) reaches Podman through `podman_on` (line 87), which builds `--connection <name> …` argv directly against `crate::backends::podman_command()` — not through `ProcessRunner`, not through any transport seam. `seed_paseo_projects` (line 105) additionally uses `podman cp` (line 134) to place a JSON file inside the container, and `reproduce_remote` (line 207) uses `podman cp` twice (lines 219–232) to copy `mise.toml`/`mise.lock` ahead of a remote `mise install`, explicitly to avoid racing the workspace sync (comment at line 217, citing `docs/features/sandbox-runtime-management/02_dev.md`).

## Proposed Model

### `PortTransport`: the seam that replaces per-provider port-publish logic (new, `src-tauri/src/network/types.rs` or a sibling `transport` module)

A trait with one method — `resolve_remote_port(&self, sandbox: &str, connection: &str, container_port: u16) -> Result<u16, NetworkError>` — called wherever `podman port` is called today: `prepare_terminal`, `prepare_agent_web` (`src-tauri/src/runtime/mod.rs`), and `expose_port` (`src-tauri/src/network/mod.rs:206`). A `PodmanPortTransport` implementation runs `podman port <name> <port>/tcp` exactly as today. This is the exact shape of `published_host_port` already sketched on the `MachineProvider` trait in `microsandbox-provider/01_ideas.md` (Proposed Model, first section) — this feature is where that primitive actually gets designed and given a Podman implementation, so `microsandbox-provider/02_dev.md` has a real trait to implement `MsbProvider` against instead of inventing one mid-phase.

The point of pulling this out on its own is what a *microsandbox* implementation of it looks like: identity. If the SSH alias a microsandbox sandbox's `connection` resolves to targets the guest microVM directly (via the `ProxyCommand` variant below), then `resolve_remote_port` for microsandbox is `Ok(container_port)` — no `msb create -p`, no host-port pre-allocation, no lookup at all, because dialling `{alias}:tcp:127.0.0.1:{container_port}` already reaches the guest's own loopback where the service is bound. This is the load-bearing difference between the two providers' network topology (see Technology Choices), and it is why `resolve_remote_port` needs to exist as a seam rather than staying inline in `prepare_terminal`/`expose_port`: the two providers don't just implement the same operation differently, one of them has nothing to do.

### `SshAlias` grows a target kind, not just a `ProxyCommand` field (`src-tauri/src/ssh/types.rs`)

`microsandbox-provider/01_ideas.md` proposes adding a `ProxyCommand` variant to `SshAlias` for `msb ssh serve --stdio`. This feature widens that into the general shape `SshAlias` needs once two providers write it: an enum (`Direct { host, port, user, identity }` for Podman's today-shape, `Proxied { command }` for microsandbox) rather than one struct with an optional field, because `render_block` (`src-tauri/src/ssh/mod.rs:74`) emits mutually exclusive OpenSSH stanzas — `HostName`/`Port`/`User`/`IdentityFile` for one, `ProxyCommand` for the other — and a struct with both risks a caller populating both and OpenSSH silently preferring one. `ensure_connection_alias` (`src-tauri/src/backends/mod.rs:729`) becomes the `Direct` constructor; a new sibling for microsandbox is the `Proxied` constructor, called with the sandbox's own identity rather than a shared per-connection one (each `msb` sandbox is its own SSH endpoint, unlike Podman where many containers share one machine connection).

### Workspace transport: `SyncStrategy` grows a third case instead of `resolve_workspace` staying Podman/remote-only (`src-tauri/src/backends/mod.rs`, `src-tauri/src/sync/types.rs`)

`SyncStrategy::Local` and `::Remote(info)` (`src-tauri/src/sync/types.rs`, referenced at `backends/mod.rs:351`) both currently assume the destination is *something Podman will bind-mount*. `microsandbox-provider/01_ideas.md`'s disk-volume design needs a third case — call it `SyncStrategy::Volume(info)` — where the "remote" side is not a directory a container mount will attach to, but a `--kind disk` volume reached the same way `Remote` reaches a directory: over `MutagenCli` through an `SshAlias`. The mechanism is identical to `Remote`; the only difference is what's on the other end (a bind-mountable directory vs. a Mutagen-managed disk volume the provider itself owns), so `MutagenCli` (`src-tauri/src/sync/mod.rs`) needs no change — only `resolve_workspace`'s Podman-vs-microsandbox branch and whatever `MachineProvider::create_instance` does with `WorkspacePlan` differ.

This also opens the option, not required by this feature but worth stating because it falls out for free: a **local** Podman sandbox could move from `SyncStrategy::Local`'s direct bind mount onto `SyncStrategy::Volume`, unifying all three cases (local Podman, remote Podman, microsandbox) onto one Mutagen-backed transport and retiring the bind-mount path entirely. See Technology Choices for why this is scoped out of v1 despite the symmetry appeal.

### `RuntimeManager`'s transport calls move behind the same seam `MachineProvider` will own (`src-tauri/src/runtime/mod.rs`)

`podman_on`, the two `podman cp` call sites, and the `podman port` calls all currently build Podman argv directly. `microsandbox-provider/01_ideas.md` already commits to renaming `PodmanMiseRuntime` to `MiseRuntime` holding `Arc<dyn MachineProvider>` instead — this feature's job is narrower and precedes that rename: make sure the primitives `MachineProvider` needs (`exec`, `exec_piped`, `copy_in`, and the `resolve_remote_port` seam above) are proven out against a **second real caller** before the rename happens, so the rename is a mechanical swap rather than a design exercise done twice. Concretely: extract `podman_on`'s argv-building into something `PortTransport`/copy-in call sites share, without yet adding a microsandbox implementation — that's `microsandbox-provider`'s job once this lands.

## Technology Choices with Tradeoffs

### Port reachability for microsandbox: dial the guest directly via SSH (chosen) vs. keep the publish-then-forward model microsandbox-provider/01_ideas.md currently proposes

Chosen: give microsandbox sandboxes an `SshAlias::Proxied` alias targeting `msb ssh serve --stdio` for the *specific sandbox*, and let `resolve_remote_port` be a no-op passthrough, so Mutagen dials straight into the guest's own loopback for any port a guest process happens to bind.

- **`msb create -p <host>:<guest>` explicit host-port allocation plus forcing zellij/paseo onto `0.0.0.0`** (the plan `microsandbox-provider/01_ideas.md` currently records) — superseded, not merely rejected: that plan exists to solve "how does the Windows host reach a port on a network interface it can't otherwise see," which is exactly the problem SSH forwarding already solves for Podman's *remote* deploys. It costs real design surface `microsandbox-provider/01_ideas.md` currently pays for nothing: the `loopback_publish`/`publish_after_create` capability distinction, the relay-pool carve-out for microsandbox, and the requirement that in-guest services bind `0.0.0.0` instead of matching Podman's `127.0.0.1` convention. Once ports are reached by dialling directly into the guest over its own SSH session, "publish" stops being a concept microsandbox needs at all — there is nothing to pre-allocate and nothing that goes stale if a service starts after the sandbox is created, which is the exact problem the relay pool exists to work around for Podman.
- **Keep it exactly as `microsandbox-provider/01_ideas.md` describes today and treat this feature as pure Podman-side cleanup** — rejected: it would ship a microsandbox implementation more complex than Podman's (explicit allocation *and* a capability-flag maze) for a provider whose actual network topology (SSH straight to the guest) makes the *simpler* thing possible. Building the harder version first and simplifying later means throwing away `-p`-argv plumbing, the `0.0.0.0`-bind change to `prepare_terminal`/`prepare_agent_web`, and the capability flags, all of which `microsandbox-provider/02_dev.md` would otherwise have already turned into phases.

The cost of the chosen path: it makes microsandbox's reachability model depend on `msb ssh serve --stdio` staying healthy per-connection (a new failure mode — see `microsandbox-provider/01_ideas.md`'s gotcha about `msb ssh serve` owning sandbox lifecycle and crashing it if force-killed), where the rejected path's failure mode (a stale published-port lookup) is one this codebase already knows how to debug. `02_dev.md` should treat "does a second concurrent `msb ssh serve --stdio` ProxyCommand session per forward (terminal, agent-web, each exposed port) work, or does it serialise/conflict" as a gating spike, since `forward_create`'s current Podman usage never opens more than one SSH session per container's *machine* connection concurrently in a way that matters — every forward for one sandbox shares one machine-level alias — whereas this design opens one raw SSH-to-guest session per forward.

### Whether Podman also moves off bind mounts onto Mutagen-synced disk volumes: not in this feature's scope (deferred)

The symmetry is real — `SyncStrategy::Volume` (Proposed Model) could serve local Podman too, and it would mean `MachineProvider`'s two implementations share one workspace strategy instead of Podman keeping a bind mount as a third, load-bearing special case. Deferred anyway: Podman's bind mount has no equivalent to the Windows virtiofs bugs motivating microsandbox's disk-volume design (`microsandbox-provider/01_ideas.md`, Validation) — it works today, is the fastest of the three transports (no sync latency, no conflict semantics), and every other subsystem (`RuntimeManager::init`, `list` in `src-tauri/src/runtime/mod.rs:168,194`, which read/write `mise.toml` directly against `workspace_host_path`) is written assuming host and container see literally the same files. Moving it onto sync would be a second, larger refactor with its own risk (see `docs/features/remote-sync/01_ideas.md`'s Destroy Guard section for the unsynced-changes-on-destroy problem, which local bind-mount sandboxes don't have today and would newly acquire). Recorded here rather than attempted; `04_improvements.md` is where it belongs if picked up later.

### Extracting `PortTransport`/`SshAlias` widening now, ahead of `microsandbox-provider`, vs. doing it inline inside that feature's own phase plan

Chosen: land this as its own feature first.

- **Do it inline as an early phase of `microsandbox-provider/02_dev.md`** — rejected: `microsandbox-provider/01_ideas.md`'s own Open Questions already flags "how much of the refactor lands before the first microsandbox code" as unresolved and names the `MachineProvider` extraction specifically as verifiable by the existing Podman-only `standard` e2e tier alone. The port-transport and workspace-transport pieces have that same property — `PortTransport`'s `PodmanPortTransport` impl, the `SshAlias` enum split, and `SyncStrategy::Volume`'s plumbing (with no microsandbox consumer yet) are all exercisable against Podman alone, with zero behaviour change, before any `msb`-specific code exists. Keeping it a separate feature means it gets its own `02_dev.md` phase plan, its own `03_e2e.md` regression coverage proving Podman is unaffected, and a clean point where `microsandbox-provider/02_dev.md` can simply state "depends on `mutagen-transport` landing" instead of interleaving two designs in one phase list.
- **Skip the extraction and let `MsbProvider` grow its own parallel port/workspace logic, unify later** — rejected on the same grounds `microsandbox-provider/01_ideas.md` already rejected a translating `ProcessRunner`: it would leave two independently-evolving implementations of "how do I reach a service inside this thing" that happen to both use Mutagen, rather than one seam two providers implement.

## Validation

No spike has been run for this feature specifically. It rests on evidence already gathered by two other features: `docs/features/host-tool-ssh-access/01_ideas.md`'s Current State confirms `open_forward`/`forward_create` already work identically for local and remote Podman connections with no code branching on which; `docs/features/remote-sync/01_ideas.md`'s two-Podman-machine validation confirms `MutagenCli` syncs correctly over an `SshAlias`-resolved connection whose SSH port is read fresh rather than cached. What remains genuinely unvalidated is specific to the microsandbox side of this design (concurrent `msb ssh serve --stdio` sessions per forward, and dialling a guest loopback port with no prior `msb create -p`) and is called out as a gating spike above and in `microsandbox-provider/01_ideas.md`'s own "Not yet run" section — this feature's `02_dev.md` should decide whether that spike runs here or is inherited by `microsandbox-provider`.

## Open Questions

- **Where `resolve_remote_port`/`PortTransport` physically lives.** Candidates: a new field on `NetworkManager`'s implementation, a method on `MachineProvider` itself (as `microsandbox-provider/01_ideas.md` currently sketches via `published_host_port`), or a free-standing trait `network`/`runtime` both depend on. The right owner affects whether `RuntimeManager::prepare_terminal` and `NetworkManager::expose_port` — which both need it — share one `Arc<dyn MachineProvider>` or need a second injected dependency.
- **Whether `SyncStrategy::Volume` is introduced now (unused by Podman, awaiting microsandbox) or held until `microsandbox-provider` actually needs it.** Introducing an enum variant nothing constructs yet is a minor smell but avoids `microsandbox-provider/02_dev.md` needing a "widen `SyncStrategy`" phase of its own.
- **Whether the `SshAlias` enum split is a breaking rename or an additive variant.** `ensure_connection_alias`'s existing callers and `write_alias`'s block-rendering (`src-tauri/src/ssh/mod.rs:74`) would need updating either way; whether existing Podman aliases already on disk (`~/.ssh/sandbox-mio/config`) need a migration step or are simply overwritten on next call is undecided.
- **The concurrent-SSH-session spike's outcome shapes whether `resolve_remote_port`'s passthrough for microsandbox is viable as designed**, or whether a single long-lived `msb ssh serve` (not `--stdio` per-connection) needs to be supervised instead — which would reintroduce a lifecycle-ownership problem this design specifically avoided (see Technology Choices and the `msb ssh serve` gotcha in `microsandbox-provider/01_ideas.md`). Not resolvable without running the spike.

## Common Gotchas

| Gotcha | Cause | Fix |
|---|---|---|
| A microsandbox port forward opens but nothing answers, even though the in-guest service is confirmed running | `resolve_remote_port`'s passthrough assumes the alias resolves to the guest's own network namespace; if the alias was accidentally built as a `Direct` (Podman-shaped) alias instead of `Proxied`, Mutagen dials the wrong host entirely | Confirm the sandbox's `SshAlias` is the `Proxied` variant targeting `msb ssh serve --stdio` for that specific sandbox, not a `Direct` alias |
| Podman port forwarding regresses after this refactor even though no Podman behaviour was meant to change | `PortTransport`'s `PodmanPortTransport` impl must reproduce `podman port <name> <port>/tcp` parsing (`parse_host_port`, `src-tauri/src/runtime/mod.rs:73`) exactly, including the `127.0.0.1:` prefix filter | Keep `parse_host_port` and its call sites unchanged in behaviour; move them, don't rewrite them, when extracting `PodmanPortTransport` |
| Two forwards for the same microsandbox sandbox (e.g. terminal and an exposed dev-server port) interfere with each other | Each forward now opens its own `msb ssh serve --stdio` process via `ProxyCommand`, unlike Podman where every forward for a sandbox shares one machine-level SSH session | Verify concurrent `--stdio` sessions to the same sandbox don't serialise or crash it (gating spike, Validation section) before relying on this for more than one simultaneous forward |
| `write_alias` silently emits an OpenSSH block with both `HostName`/`Port` and `ProxyCommand` set | `SshAlias` was left as a single struct with an optional `ProxyCommand` field instead of split into `Direct`/`Proxied` variants, and a caller populated both | Split `SshAlias` into an enum (Proposed Model) so `render_block` can only ever emit one shape |
| A local Podman sandbox's workspace stops seeing host edits after `SyncStrategy` gains a `Volume` case | `Volume` was accidentally selected for a local Podman sandbox that should stay on the zero-latency `Local` bind-mount path | `resolve_workspace` must keep `Local` as the default for a local Podman connection; `Volume` is opt-in per provider capability, not a blanket replacement (see Technology Choices, "not in scope") |

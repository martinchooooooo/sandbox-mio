# Embedded Windows (Multi-Webview Workspace) Ideas

This document is the ideation for hosting a sandbox's tool surfaces — the Zellij terminal today, and separate apps such as OpenCode next — **inside the main application window** instead of in separate operating-system windows. The target interaction: opening a sandbox minimises the current projects view and reveals a per-sandbox *workspace* filling the window; inside that workspace, one or more app surfaces (Zellij terminal, OpenCode, other web apps) open as embedded panes that can be tiled or switched between. None of this embedding exists yet: every secondary surface in the app is its own top-level OS window today. The feature builds on three existing seams — the terminal launcher `open_terminal` (`src-tauri/src/lib.rs:100`), which currently opens a standalone `WebviewWindow`; the Mutagen loopback-port bridge `sync::forward_create` (`src-tauri/src/lib.rs:148`), which makes a container-served web app reachable at `http://127.0.0.1:<port>`; and the main SvelteKit single-page app that renders the projects list and per-sandbox action row (`src/routes/projects/+page.svelte`, `src/routes/projects/SandboxItem.svelte:130`). The chosen shell model is a **collapsible chrome panel with a sandbox-side app switcher**: the SvelteKit UI stays on screen as a global navigation panel that collapses to a thin rail with a single button (enlarging the sandbox area), and the sandbox panel carries its own chrome — a tab/switcher bar for moving between the multiple apps (Zellij, OpenCode, …) it hosts, each app being a child webview shown or hidden on switch. The user's sizing control is deliberately limited to that one collapse toggle; there are no draggable splits. A feasibility spike on 2026-07-01 proved the enabling Tauri API works on this machine (see Validation).

## Current State

The app is a single Tauri window running one SvelteKit single-page app. `tauri.conf.json` (`app.windows`) declares exactly one window, `main`, 800×600, loading the SvelteKit frontend (`src/routes/`). All in-app navigation (projects, models, settings, intro, admin) is client-side routing *inside that one webview*; there is no concept of a second webview sharing the window.

Every secondary surface is a separate top-level OS window, each with its own single webview:

- **The Zellij terminal.** `open_terminal` (`src-tauri/src/lib.rs:100`) prepares the terminal, mints a token, creates a Mutagen forward to a Windows-host loopback port, then builds a dedicated `tauri::WebviewWindowBuilder` (`src-tauri/src/lib.rs:191`) pointed at `http://127.0.0.1:<port>/` with an `initialization_script` that auto-logs in. The window label is `terminal-<name>`; a second click focuses the existing window (`src-tauri/src/lib.rs:112`). This is a whole OS window, not a pane inside the app.
- **Agent authentication.** `AgentManager.svelte:138` opens a `new WebviewWindow` labelled `agent-auth-<sandbox>-<agent>` loading the internal `/agent-auth` route — again a separate OS window, created from the JS side.

Two distinct window-creation paths therefore already exist: from Rust via `WebviewWindowBuilder` (the terminal, because it needs `initialization_script`, which the JS `WindowConfig` forbids — see `src-tauri/src/lib.rs:169`), and from JS via `new WebviewWindow` (agent-auth). Both produce `WebviewWindow`, Tauri's combined one-window-one-webview type.

Capabilities gate what each window may do. `src-tauri/capabilities/default.json` scopes its permissions to `windows: ["main"]` and grants `core:webview:allow-create-webview-window` and `core:window:allow-set-focus`. `src-tauri/capabilities/agent-auth.json` is a second capability file scoped to `windows: ["agent-auth-*"]` — the existing precedent that a new class of window/webview label needs its own capability entry to call IPC commands.

App surfaces that a sandbox exposes are container-served web apps reached over a loopback port. The terminal is the built example: Zellij serves HTTP inside the container, `sync::forward_create` (`src-tauri/src/lib.rs:148`) bridges a Windows-host loopback port to the container's published port, and the webview loads `http://127.0.0.1:<port>/`. Any additional app surface (OpenCode, etc.) that speaks HTTP would reuse this same forward-then-load shape. The per-sandbox forward ports are tracked host-side in `ForwardPortMap` (`src-tauri/src/lib.rs:27`), a `Arc<Mutex<HashMap<String, u16>>>` held in Tauri state so teardown can reclaim them.

The installable agents (`src/lib/agents/catalogue.ts`) — Claude Code, OpenCode, pi — are all *terminal* agents today: the user runs them by typing inside the Zellij terminal. "OpenCode as a separate app webview" is a future surface, not a current one; whether OpenCode exposes an embeddable web UI is an open question below.

## Proposed Model

### The workspace container window (`Window` + child webviews)

The enabling primitive is Tauri's multi-webview support: a bare `tauri::window::Window` (a native window with **no** webview of its own) that hosts multiple child `Webview`s, each positioned by a pixel rectangle. This is distinct from today's `WebviewWindow` (one window bonded to one webview). The seam is a new Rust path that parallels `open_terminal` (`src-tauri/src/lib.rs:100`): instead of `WebviewWindowBuilder`, it uses `tauri::window::WindowBuilder::new(app, "workspace-<name>")` to create the container, then `window.add_child(webview_builder, position, size)` to place each surface. `add_child`, `Window::builder`, and the `Webview` geometry methods (`set_position`, `set_size`, `set_focus`, `bounds`, `close`, `reparent`) are all gated behind the `unstable` Cargo feature on the `tauri` crate, which the build must enable (`src-tauri/Cargo.toml`).

Whether the *main* app window is itself converted into a container that gains child webviews, or whether the workspace is a distinct container window that opens when a sandbox is entered, is an open question below; the spike used a distinct container window and both are viable with the same API.

### Two chromes and content webviews (the chosen shell model)

The workspace has two chrome regions and a content area, all realised as sibling child webviews of the container:

- **Global chrome (collapsible app panel).** The existing SvelteKit UI — global navigation, sandbox list, the theme/locale toggles (`src/routes/+layout.svelte`), the activity center — persists as a panel occupying one side of the container. A single button collapses it to a thin rail (see "Collapsing the global panel"), enlarging the sandbox area. This directly realises "the current view minimises and a new view opens with the sandbox inside."
- **Sandbox chrome (app switcher).** The sandbox panel is not a single app; it hosts several (Zellij, OpenCode, …) and the user switches between them. That requires its own chrome: a tab/switcher bar, rendered by a chrome webview, listing the apps open for the sandbox and marking the active one. Clicking a tab is an in-DOM click that drives Rust to show the chosen app's webview and hide the others (see "Switching between apps").
- **Content area (app webviews).** Each app surface (Zellij, OpenCode) is a child webview loading an external loopback URL. Exactly one is shown at a time in the content rectangle; the rest are hidden but alive.

Both chrome regions load internal `WebviewUrl::App` routes (new `/workspace`-style routes, or the existing SvelteKit app scoped to a sandbox); the content webviews load external loopback URLs. Whether the two chromes are one L-shaped webview or two separate webviews is an open question below. The chrome owns *intent* (which apps are open, which is active, whether the global panel is collapsed) and drives Rust over IPC to add, show, hide, position, and close webviews; Rust owns the *native geometry*. The seam for the chrome is a new SvelteKit route under `src/routes/`; the seam for the commands it calls is a family of new `#[tauri::command]` functions beside `open_terminal` in `src-tauri/src/lib.rs`.

### Collapsing the global panel (discrete states, not draggable)

Sizing is limited to a single collapse toggle rather than draggable splits. Collapsing is two discrete layouts: *expanded* (global panel at its normal width, sandbox area taking the rest) and *collapsed* (global panel shrunk to a thin rail, sandbox area grown to fill). The toggle button lives in the global chrome webview's own DOM, so pressing it is an ordinary in-page click — no cross-webview pointer capture is involved. On toggle, the chrome issues IPC that recomputes the two rectangles and calls `Webview::set_bounds` on the global-panel and sandbox webviews. The global panel collapses to a **thin rail** rather than vanishing, so the expand button remains inside the chrome in both states (a fully hidden panel would leave nothing to click to bring it back). Transitions **snap** by default: a smooth slide would require issuing many `set_bounds` calls per frame against native webviews, which is a polish item, not core.

### Switching between apps (hide/show live webviews)

The sandbox hosts multiple app webviews and shows one at a time. Switching uses `Webview::hide()` / `Webview::show()` (both present under the `unstable` feature at `tauri-2.11.2/src/webview/mod.rs:1541`/`:1546`): the newly selected app is shown in the content rectangle and the previously active one is hidden. A hidden webview keeps running — its Zellij or OpenCode session stays connected — so switching away and back does not restart the app or drop scrollback. Because only one app webview is visible in the content rectangle at a time, no child-webview z-ordering is needed (there is no z-order API for child webviews anyway). The seam is the app-switcher chrome's tab handlers calling new show/hide/focus IPC commands; the active app per sandbox is tracked in the webview registry below.

### App surfaces are external-URL child webviews

Each embedded app is a child webview whose URL is a forwarded loopback address, exactly the shape `open_terminal` already produces. Opening the terminal pane becomes: run the existing `prepare_terminal` + `sync::forward_create` steps (unchanged), then `window.add_child(WebviewBuilder::new("<name>-terminal", WebviewUrl::External(loopback_url)), position, size)` against the workspace container instead of building a standalone `WebviewWindow`. A second app (e.g. OpenCode over HTTP) follows the identical pattern with its own forward and its own child label. The terminal's `initialization_script` auto-login (`src-tauri/src/lib.rs:176`) carries over: `WebviewBuilder` exposes `initialization_script` just as `WebviewWindowBuilder` does, so the Rust-side creation path is retained for exactly the reason it exists today.

### Webview registry and lifecycle

The container plus its child webviews need host-side bookkeeping so apps can be shown, hidden, moved, closed, and torn down with the sandbox — mirroring how `ForwardPortMap` (`src-tauri/src/lib.rs:27`) already tracks per-sandbox forward ports. A parallel registry (the workspace label, its chrome and app-webview labels, and which app is currently active, keyed by sandbox name) held in Tauri state lets the app-switcher show/hide the right webview and lets `undeploy_sandbox`/`destroy_sandbox` (`src-tauri/src/lib.rs:254`, `:286`) close the workspace and its children alongside the forward teardown they already do. Child webviews are addressed by label (`app.get_webview(label)` / `window.webviews()`), the same label-based identity `open_terminal` uses to focus-or-create.

### Positioning is native and manual, not CSS

Child webviews are native surfaces that float **above** the container's DOM; they are not laid out by HTML/CSS and do not clip to DOM elements. Their rectangles are set explicitly in logical units (`LogicalPosition`/`LogicalSize`), and the runtime scales them to physical pixels per the monitor DPI (the spike confirmed a 600×700 logical child became 1200×1400 physical at 200% scaling). Consequently the layout the chrome webviews *draw* in their DOM has no automatic effect on where the app webviews sit: every layout change must be translated by the chrome/Rust into explicit geometry or visibility calls on the affected child webviews. The layout changes are deliberately few and discrete — collapse/expand the global panel (`set_bounds` on two webviews) and switch the active app (`hide`/`show`) — not a continuous draggable layout. The one continuous case that remains is the OS window itself resizing, so a window-resize listener that re-lays-out every visible child is a first-class concern, not an afterthought.

### Capability scoping for the new webview labels

The workspace container and its content webviews are new window/webview labels absent from `capabilities/default.json` (scoped to `windows: ["main"]`). Following the `agent-auth` precedent (`src-tauri/capabilities/agent-auth.json`), the chrome webview that must call `invoke` needs a capability entry covering its label; external-URL content webviews that only render a remote page need no IPC permissions (the spike's external children rendered with none).

## Technology Choices With Tradeoffs

### Embedding mechanism: Tauri unstable multi-webview

A single `Window` hosting multiple child `Webview`s (via `add_child`, behind the `unstable` feature) is the chosen mechanism. It is the only approach that puts genuinely independent web apps — including ones that refuse to be iframed — side by side inside one OS window with native rendering and per-pane process isolation. Alternatives evaluated:

- **`<iframe>` elements inside the SvelteKit page.** Rejected: the web-terminal spike (`docs/features/web-terminal/01_ideas.md`) established that the Zellij web client sends `X-Frame-Options: DENY` on every response, which blocks embedding it in an iframe. Any future app surface with the same header (common for security-sensitive apps) would be equally un-iframable. Child webviews are top-level documents to which `X-Frame-Options` does not apply — the 2026-07-01 spike confirmed a loopback HTTP page renders in a child webview — so this is the decisive reason to prefer native webviews over iframes.
- **Keep separate OS windows (the status quo).** Rejected against the feature's explicit "inside the main app window" requirement. It is the zero-effort path and remains the fallback if the `unstable` API proves too unstable across Tauri upgrades, but it does not deliver the inside-one-window workspace the feature asks for.
- **A DOM terminal (xterm.js) plus in-page renders for other apps.** Rejected for the same reasons the web-terminal ideas doc rejected it: it forces the app to own PTY streaming, resize, and session lifecycle, does not survive the host process, and still cannot render an arbitrary third-party web app (OpenCode's own UI) that expects to be a full document. It is strictly more code than embedding a webview that already renders these apps.

### Sizing control: discrete collapse states, not draggable splits

The user's control over sizing is a single collapse toggle producing two discrete layouts, not a continuously draggable split. Chosen because it delivers the "make the sandbox bigger" intent with almost no cost — a button press maps to two `set_bounds` calls — and because it sidesteps the hard part of draggable panes entirely. Alternatives evaluated:

- **Draggable split(s) between the panels.** Rejected: a native child webview captures every pointer event over its rectangle, so a drag that starts on a gutter breaks the moment the cursor crosses into a webview, and `set_ignore_cursor_events` is window-wide (not per-webview) so a pane cannot be made click-through cheaply. Making dragging work needs a transparent full-window capture overlay (or a ghost-divider deferred-apply scheme) — real complexity for a degree of control the user explicitly does not want.
- **CSS grid/flex placing the panes as DOM elements.** Rejected as impossible for native child webviews: they float above the DOM and are not laid out by HTML flow (this only works for iframes, already rejected for `X-Frame-Options`). Geometry must be applied via `set_bounds`.

### App switching: hide/show live webviews, not close-and-recreate

Switching the active app in the sandbox panel hides the current app webview and shows the next (`Webview::hide`/`show`), keeping every app webview alive in the background. Chosen because Zellij and OpenCode are stateful sessions: keeping the webview alive preserves the connected session and scrollback, and switching is instant. The rejected alternative is **closing the inactive app's webview and recreating it on return** (`close` + a fresh `add_child`); rejected because it drops the session, re-runs the token login and forward setup, and shows a reload flash on every switch. The cost accepted is several live webviews (each a WebView2 process) held per sandbox; acceptable because the number of apps per sandbox is small and bounded by what the user opens.

### Shell model: collapsible chrome panel plus content webviews

The SvelteKit UI stays resident as a collapsible global panel, with a second sandbox-side chrome for the app switcher, while apps run in sibling content webviews (the model the user selected). Chosen because it keeps all navigation, activity, and app-switching UI in the framework the app already uses, and confines the bespoke native-window work to positioning and show/hide. The rejected alternative is a **full-swap workspace** where entering a sandbox replaces the entire window content with app webviews and all chrome (global nav *and* the app switcher) is drawn by native code or a single overlay; rejected because it either duplicates chrome inside a web app or pushes window-management concerns (tab bar, collapse button, focus ring) into native code, both more work than SvelteKit chrome that simply drives Rust.

### Window-creation path: retain Rust-side builder for app surfaces

App-surface webviews are created from Rust via `WebviewBuilder` rather than from JS, preserving the reason `open_terminal` already lives in Rust: the auto-login `initialization_script` cannot be passed through the JS `WindowConfig` (`deny_unknown_fields`, noted at `src-tauri/src/lib.rs:169`). The rejected alternative — **create every child webview from JS** — would reintroduce that exact limitation for the terminal and any future surface needing script injection. The chrome webview still *requests* creation over IPC; Rust performs it.

## Validation

A feasibility spike was run by hand on 2026-07-01 on the target machine (Windows 11, WebView2), against this repository at Tauri `2.11.2` / wry `0.55.1`. The spike temporarily enabled the `unstable` feature on the `tauri` dependency and added an env-guarded (`MIO_SPIKE_MULTIWEBVIEW`) setup hook that built a bare container `Window` and added two child webviews to it — one internal (`WebviewUrl::App("projects")`) and two throwaway loopback HTTP servers standing in for container-served apps. All spike code and the feature flag were reverted after the run; the working tree carries none of it.

Cleared risks:

- **The multi-webview API exists and compiles under `unstable`.** `cargo check --lib` succeeded with only pre-existing dead-code warnings. The needed surface is present and gated exactly as expected: `tauri::window::WindowBuilder::new` (bare container window), `Window::add_child(WebviewBuilder, position, size)`, and `Webview::{set_position, set_size, set_bounds, set_focus, bounds, hide, show, close, reparent}`, all under `#[cfg(feature = "unstable")]` in `tauri-2.11.2/src/window/mod.rs` and `src/webview/mod.rs`. Without the feature these methods do not exist, so the build must set `tauri = { features = ["unstable"] }` in `src-tauri/Cargo.toml`.
- **Two child webviews coexist in one window.** After two `add_child` calls, `window.webviews().len()` reported `2`, and a launched app process showed a single OS window titled "multi-webview spike" hosting both.
- **Geometry is applied precisely, non-overlapping, and DPI-scaled.** Positions given as `LogicalPosition (0,0)` and `(600,0)` with `LogicalSize (600,700)` produced measured child bounds of physical `(0,0) 1200×1400` and `(1200,0) 1200×1400` on a 200%-scaled display — side by side, no overlap, with the runtime performing the logical-to-physical scaling. Positioning is therefore specified in logical units and is deterministic.
- **An internal `WebviewUrl::App` child renders the live app.** The left child loaded the real `/projects` route (the "Sandpits" projects list with its action row), confirming the SvelteKit chrome can be one of the child webviews.
- **External loopback HTTP children render distinct pages.** Two children pointed at `http://127.0.0.1:<ephemeral>/` rendered their two distinct pages (a solid-red "LEFT" page and a solid-green "RIGHT" page) simultaneously in the one window — the exact shape the Zellij terminal and a future OpenCode surface use. This also re-confirms the web-terminal finding that `X-Frame-Options` does not obstruct a top-level webview.
- **Per-child focus works.** `Webview::set_focus()` on a child returned `Ok`.

Not yet validated (deferred to the build):

- **Collapse re-layout, app switching, and window-resize re-layout.** The spike used a single fixed-size window and hard-coded rectangles. It did **not** exercise the collapse toggle (`set_bounds` on two webviews), app switching (`hide`/`show`, and that a hidden app webview keeps its session alive), or re-laying-out on OS-window resize. The float-above-DOM behaviour is documented, and `set_bounds`/`hide`/`show` are confirmed present, but the concrete collapse, switch, and resize loops are unbuilt and unproven here.
- **The auto-login `initialization_script` on a child webview.** `WebviewBuilder` exposes `initialization_script`, but the spike did not drive the real Zellij token-login script through an embedded child (it used throwaway pages). The terminal's existing script is expected to port unchanged; that expectation is untested in the embedded configuration.
- **IPC from a child webview under a new capability.** The spike's children either rendered a remote page (no IPC needed) or loaded `/projects` without a capability scoped to the `spike-*` label; a chrome child that must `invoke` under a properly scoped capability entry was not exercised.
- **`unstable` API durability across Tauri upgrades.** The feature is explicitly outside Tauri's semver stability guarantee; the spike proves 2.11.2 but not that the API shape survives a future bump.

## Open Questions

- **Main window converted versus a separate container window.** Whether the existing `main` window is turned into a bare `Window` that gains child webviews (the chrome moving into a child), or the workspace is a *new* container window opened when a sandbox is entered while `main` stays a plain `WebviewWindow`, is undecided. The spike used a separate container; both compile against the same API. `02_dev.md` resolves this against how navigation between the projects list and a workspace should feel and whether multiple sandboxes' workspaces coexist.
- **Multiple concurrent sandbox workspaces versus one at a time.** Whether the user can have several sandboxes' workspaces open at once (several container windows, or several tab groups in one) or the app shows one workspace at a time is undecided and shapes the registry keyed off sandbox name.
- **One L-shaped chrome webview versus two.** The global-nav chrome and the sandbox app-switcher chrome could be a single L-shaped `WebviewUrl::App` webview drawing both regions, or two separate chrome webviews (one collapsing, one persistent). A single webview is fewer moving parts but couples the collapse geometry to the app-switcher; two webviews decouple them at the cost of a second chrome surface and capability entry. Undecided; `02_dev.md` picks against how the collapse animation and the app-switcher bar should relate visually.
- **Collapsed target and transition.** The global panel collapses to a thin rail (default, so the expand button stays reachable) versus fully hidden with the expand affordance drawn elsewhere; and the transition snaps (default) versus animates. Both defaults are stated in "Collapsing the global panel"; `02_dev.md` confirms them or overrides with a specific rail width and any animation budget.
- **Bound on concurrently open apps per sandbox.** App switching keeps every opened app webview alive (each a WebView2 process). Whether to cap how many apps a sandbox may have open at once, or evict least-recently-used ones back to close-and-recreate, is undecided and matters only if per-sandbox app counts grow beyond a handful.
- **What "OpenCode as an app webview" actually is.** OpenCode is a terminal agent today (`src/lib/agents/catalogue.ts`). Whether it is surfaced as its own embedded app webview (requiring an OpenCode web/HTTP UI served from the container and forwarded like Zellij), or simply continues to run inside the Zellij terminal pane, is undecided and determines whether a second forward + child webview is even needed for it.
- **Fallback to separate OS windows.** Whether to keep the current standalone-`WebviewWindow` terminal path as a runtime fallback if the `unstable` embedding misbehaves after a Tauri upgrade, or to commit fully to embedding, is undecided.
- **Remote-deployed sandboxes.** As with the web terminal, a remote-deployed sandbox's app surfaces are served on the remote host. Whether embedded app webviews work for remote sandboxes (over the same forward mechanism) or are scoped out of the first iteration is undecided and likely inherits the web-terminal feature's answer.

## Common Gotchas

| Gotcha | Cause | Fix |
|---|---|---|
| `add_child` / `WindowBuilder` / webview geometry methods do not exist | These APIs are gated behind the `unstable` Cargo feature on the `tauri` crate, which is off by default | Set `tauri = { version = "2", features = ["unstable"] }` in `src-tauri/Cargo.toml`; the spike confirmed the whole surface appears only with the feature enabled |
| Embedded app webviews ignore the CSS layout the chrome draws | Child webviews are native surfaces that float above the DOM and are not laid out or clipped by HTML/CSS | Position every child explicitly with `set_bounds` in logical units; treat the chrome's DOM (collapse button, app-switcher tabs) as intent only, and translate it into geometry/visibility commands |
| App webviews end up the wrong size on a high-DPI monitor | Rectangles interpreted in the wrong unit space | Specify positions/sizes in `LogicalPosition`/`LogicalSize`; the runtime scales to physical pixels per monitor DPI (spike: 600×700 logical → 1200×1400 physical at 200%) |
| App webviews overlap or vanish after the user resizes the OS window | Child bounds are absolute and do not reflow with the container | Add a window-resize listener that re-lays-out every visible child webview; this loop is unbuilt as of the spike and must be authored |
| Collapsing the global panel leaves no way to expand it again | The panel was collapsed to zero width, hiding its own expand button | Collapse to a thin rail that still holds the expand button (stated default), not to nothing; keep the toggle inside the chrome webview in both states |
| Switching apps restarts Zellij/OpenCode or drops scrollback | The inactive app's webview was closed and recreated on return | Switch with `Webview::hide`/`show` (present under `unstable`), keeping every app webview alive so its session and scrollback persist; only `close` on sandbox teardown |
| A "hidden" app still shows through or steals clicks | The webview was moved off-screen or 0-sized instead of actually hidden | Use `Webview::hide()` (not an off-screen `set_bounds`) so the inactive app is truly non-rendering and non-interactive |

| The chrome webview's `invoke` calls are denied | The new workspace/chrome webview label is not covered by any capability (`default.json` is scoped to `windows: ["main"]`) | Add a capability entry scoped to the new label, following `src-tauri/capabilities/agent-auth.json`; external-URL content webviews that only render need no IPC capability |
| Terminal auto-login breaks when moved into a pane | The login `initialization_script` was assumed to survive the port from `WebviewWindowBuilder` to `WebviewBuilder` untested | `WebviewBuilder` exposes `initialization_script`; keep creating app-surface webviews from Rust (as `open_terminal` does at `src-tauri/src/lib.rs:191`) and verify the script runs in the embedded configuration |

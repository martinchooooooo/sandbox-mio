# Embedded Windows (Multi-Webview Workspace) Build Plan

This document is the build plan for hosting a sandbox's tool surfaces — the Zellij terminal today, and separate apps such as OpenCode later — inside an in-app *workspace* rather than in separate top-level operating-system windows. It continues `01_ideas.md` and supersedes its option space: the ideation weighed alternatives and left seven open questions; this plan fixes the concrete model and answers every one of those questions in the "Resolved Decisions" section. **Status: Phases A–E are implemented (2026-07-02); Phase F remains deferred.** The `unstable` feature is enabled, `src-tauri/src/workspace/` holds the registry, layout, and window plumbing, the `open_workspace`/`set_panel_collapsed`/`close_workspace` commands are registered, and the `workspace_state` read command was pulled forward from Phase F into Phase B per the e2e plan (`03_e2e.md`, "The read-back seam"). Implementation deviations from the letter of this plan: teardown also hooks `WindowEvent::Destroyed`, so closing the container with the OS X button reclaims the registry entry and forwards (the plan only named the close button and undeploy/destroy paths); and the pre-existing `openWorkspace()` folder-reveal helper in `SandboxItem.svelte` was renamed `openFolder()` to free the name for the workspace action. The e2e spec of `03_e2e.md` is not yet written (its de-risking spike is a prerequisite).

> **Redesign (2026-07-02, user direction — supersedes Resolved Decisions 1 and 2 below):** the Workspace now **is** the AppContainer's content area. There is a single bare container window labelled `main`, created in Rust setup (the `windows` entry was removed from `tauri.conf.json`); the entire pre-existing app UI (projects, models, settings) is the **left collapsible NavigationPanel** (`main-navigation-panel` child webview), and the switcher bar (`main-switcher`) plus content panes per sandbox (`workspace-<name>-terminal/dashboard/agentweb`) fill the rest. Consequences: `open_workspace` embeds a tab (or switches to it) instead of creating a window; `switch_app` was pulled forward from Phase F to switch between sandboxes' tabs; `set_panel_collapsed` and `workspace_state` lost their `name` parameter (there is one AppContainer); the registry is a single `WorkspaceState` instead of a per-sandbox map; every mutation broadcasts a `workspace://state` event that the two chrome webviews mirror. With **no embedded tab the NavigationPanel fills the whole window** (the app looks unchanged at startup); once a tab exists the panel shrinks to `NAVIGATION_PANEL_EXPANDED_W` (now 380 logical px) or the 48 px rail. The `/workspace/global` route and the separate `workspace.json` capability were removed (`default.json` covers `main-navigation-panel`/`main-switcher`); the wdio config gained a `before` hook that pins the WebDriver session to the app webview handle, since the main window now exposes several.

## The concrete model

A sandbox workspace is a **separate bare container window** — a `tauri::window::Window` with no webview of its own — created per sandbox and labelled `workspace-<name>`. The existing `main` window stays a plain `WebviewWindow` showing the projects list; entering a sandbox opens its container window beside `main`, and **several sandboxes' workspaces coexist**, one container window each. Each container hosts three sibling child webviews, added with `Window::add_child(WebviewBuilder, LogicalPosition, LogicalSize)` under the `unstable` feature:

- **Global chrome** (`workspace-<name>-global`) — a SvelteKit internal route (`WebviewUrl::App`) pinned to the left edge. It carries global navigation and the single collapse toggle. It collapses between two discrete widths: expanded (`GLOBAL_EXPANDED_W`, 260 logical px) and a thin rail (`GLOBAL_RAIL_W`, 48 logical px) that still holds the expand button.
- **Switcher chrome** (`workspace-<name>-switcher`) — a second SvelteKit internal route drawn as a horizontal bar (`SWITCHER_H`, 40 logical px) across the top of the sandbox area, right of the global panel. It lists the apps open in this sandbox and marks the active one. In v1 it renders a single tab (the terminal); the multi-tab wiring is built structurally but only exercised once a second app exists.
- **Content area** (`workspace-<name>-terminal`, and later `workspace-<name>-<app>`) — one external-URL child webview per app, filling the sandbox area below the switcher bar. Exactly one is shown at a time via `Webview::show`/`hide`; the rest stay alive.

The two chromes own *intent* (which apps are open, which is active, whether the global panel is collapsed) and drive Rust over IPC; Rust owns *native geometry*. Child webviews float above the DOM and are not laid out by CSS, so every layout change is translated into explicit `set_bounds`/`show`/`hide` calls (see "Positioning" in `01_ideas.md`). The layout is recomputed by one pure Rust function, `workspace_layout(container_size, collapsed) -> Rects`, called from three triggers: workspace open, collapse toggle, and OS-window resize.

Host-side bookkeeping mirrors `ForwardPortMap` (`src-tauri/src/lib.rs:27`): a new `WorkspaceRegistry` in Tauri state, keyed by sandbox name, records each container's label, its two chrome labels, its app panes (label + forward name + kind), the active app, and the collapsed flag. The registry lets the switcher show/hide the right webview and lets `undeploy_sandbox`/`destroy_sandbox` (`src-tauri/src/lib.rs:254`, `:286`) close the container and its children alongside the forward teardown they already perform.

## Resolved Decisions

Each Open Question from `01_ideas.md` is restated with its resolution.

1. **Main window converted versus a separate container window.** Resolved: a **separate container window** `workspace-<name>` opens per sandbox; `main` stays a plain `WebviewWindow` showing the projects list. Chosen because it matches the spike's proven shape, isolates workspace teardown to closing one window, and composes naturally with the multiple-concurrent decision below.
2. **Multiple concurrent sandbox workspaces versus one at a time.** Resolved: **multiple concurrent** workspaces, one container window per sandbox. The `WorkspaceRegistry` is keyed by sandbox name so any number of entries coexist; there is no single-active-workspace slot.
3. **One L-shaped chrome webview versus two.** Resolved: **two** separate chrome webviews (NavigationPanel + switcher). Chosen because the NavigationPanel collapses and the switcher bar does not; two webviews decouple the collapse geometry from the switcher bar, at the cost of a second chrome label and capability coverage.
4. **Collapsed target and transition.** Resolved: the NavigationPanel collapses to a **thin rail** of `NAVIGATION_PANEL_RAIL_W` = 48 logical px (keeping the expand button reachable), never to zero. The transition **snaps** — a single `set_bounds` pair per toggle. No animation budget in v1; a slide is an explicit later polish item.
5. **Bound on concurrently open apps per sandbox.** Resolved: **no cap and no LRU eviction in v1**, because v1 embeds a single app (the terminal). The registry stores a `Vec` of app panes so more than one is representable; a cap is revisited only if per-sandbox app counts grow beyond a handful.
6. **What "OpenCode as an app webview" actually is.** Resolved: **deferred out of v1.** OpenCode and pi remain terminal agents run inside the Zellij pane (`src/lib/agents/catalogue.ts` unchanged). v1 embeds only the terminal; a dedicated OpenCode app webview (needing an in-container OpenCode HTTP UI plus a second forward) is Phase F, gated on that UI existing.
7. **Fallback to separate OS windows.** Resolved: **no runtime fallback flag.** v1 commits to embedding for the workspace path. Recoverability is preserved at the *code* level, not at runtime: the terminal-preparation steps are factored into a shared helper so the standalone `WebviewWindowBuilder` path remains reconstructable from one call site if a future Tauri upgrade breaks `unstable`.
8. **Remote-deployed sandboxes.** Resolved: **in scope.** An embedded app webview loads a `http://127.0.0.1:<port>/` loopback URL whose shape is identical for local and remote sandboxes; the connection resolution already in `open_terminal` (`src-tauri/src/lib.rs:121`–`127`) distinguishes deployed from local and picks the right host, so the embedded path inherits remote support for free.

## Implemented: Phase A — enable the API and scope capabilities

- **`src-tauri/Cargo.toml`** — change `tauri = { version = "2", features = [] }` (line 21) to `features = ["unstable"]`. Without it, `WindowBuilder::new`, `Window::add_child`, and the `Webview` geometry/visibility methods do not exist (spike finding; `01_ideas.md` Validation).
- **`src-tauri/capabilities/workspace.json`** (new) — a capability following the `agent-auth.json` precedent (`src-tauri/capabilities/agent-auth.json`), granting the chrome webviews the IPC they need (`core:default`, `opener:default`, and — because the switcher may focus/close panes — `core:window:allow-set-focus`). Scope it to the chrome **webview** labels, not just window labels: use `"webviews": ["workspace-*-global", "workspace-*-switcher"]`. The spike deferred "IPC from a child webview under a new capability" as unproven; verifying an `invoke` from a chrome child succeeds under this file is a Phase-A exit criterion. The content webviews (`workspace-*-terminal`) render a remote page only and need no capability entry.

## Implemented: Phase B — Rust container, registry, and terminal embedding

- **`WorkspaceRegistry`** — new type `Arc<Mutex<HashMap<String, WorkspaceEntry>>>` beside `ForwardPortMap` (`src-tauri/src/lib.rs:27`). `WorkspaceEntry` holds `container_label: String`, `global_label: String`, `switcher_label: String`, `apps: Vec<AppPane>`, `active_app: Option<String>`, `collapsed: bool`. `AppPane` holds `label: String`, `forward_name: String`, `kind: AppKind` (v1: only `AppKind::Terminal`). Register it in `setup` alongside the other `app.manage(...)` calls (`src-tauri/src/lib.rs:895`). Given the scale, place the registry and its types in a new module `src-tauri/src/workspace/mod.rs` with `types.rs`, mirroring the existing module layout; re-export the state type into `lib.rs`.
- **`workspace_layout(container: LogicalSize, collapsed: bool) -> WorkspaceRects`** — pure function in `workspace/mod.rs` computing four rectangles (global, switcher, content, and the collapsed-rail width) from the container size and collapse flag, using `GLOBAL_EXPANDED_W`, `GLOBAL_RAIL_W`, `SWITCHER_H` constants. Pure and side-effect-free so it is unit-testable without a window.
- **`open_workspace(name, workspace_path, ...) -> Result<(), AppError>`** — new `#[tauri::command]` beside `open_terminal`. If the sandbox already has a registry entry, focus its container and return (the focus-or-create idiom `open_terminal` uses at `src-tauri/src/lib.rs:112`). Otherwise: build the container with `tauri::window::WindowBuilder::new(&app, format!("workspace-{name}"))`; add the two chrome children with `WebviewUrl::App` (routes below), passing the sandbox name as a query param; call the shared terminal helper to get the terminal child's URL and init-script; add the terminal child with `WebviewUrl::External`; apply `workspace_layout` via `set_bounds` on all three; insert the `WorkspaceEntry`.
- **Factor the terminal preparation.** Extract lines `src-tauri/src/lib.rs:119`–`195` of `open_terminal` — connection resolution, `ensure_connection_alias`, `prepare_terminal`, ephemeral-port allocation, `forward_create`, `forward_ports` insert, `zellij.json` write, and `init_script` construction — into a helper `prepare_terminal_webview(name, workspace_path, ...) -> Result<TerminalWebview, AppError>` returning the child label, parsed URL, and init-script. Both the existing standalone `open_terminal` (which still calls `WebviewWindowBuilder`) and the new `open_workspace` (which calls `Window::add_child(WebviewBuilder::new(...).initialization_script(...))`) call this helper, so the auto-login script (`src-tauri/src/lib.rs:176`) is authored once. The spike deferred "the auto-login `initialization_script` on a child webview" as unproven; confirming the script runs in the embedded child is a Phase-B exit criterion.
- **`set_panel_collapsed(name, collapsed) -> Result<(), AppError>`** — new command: flip the entry's `collapsed`, recompute `workspace_layout`, `set_bounds` on the global and switcher/content webviews, snap (no animation).
- **`close_workspace(name) -> Result<(), AppError>`** — new command and internal helper: close the container window (children close with it), terminate each app pane's forward via `sync::forward_terminate`, drop the registry entry and the `ForwardPortMap` entry. Used by the workspace's own close button and by teardown (Phase E).
- Register `open_workspace`, `set_panel_collapsed`, and `close_workspace` in the `generate_handler!` list (`src-tauri/src/lib.rs:901`).

## Implemented: Phase C — SvelteKit chrome routes and IPC wiring

- **`src/routes/workspace/global/+page.svelte`** (new) — the global chrome. Reuses the existing global navigation and reads the sandbox name from the query param. Holds the single collapse toggle; the button's click handler `invoke("set_panel_collapsed", { name, collapsed })` and updates local state. Because this is a distinct webview loaded into the container, factor any shared nav out of `src/routes/+layout.svelte` into a component both can mount.
- **`src/routes/workspace/switcher/+page.svelte`** (new) — the app-switcher bar. In v1 it renders one tab (the terminal) and marks it active. Tab click handlers call the switch/show-hide IPC (Phase F); v1 wires the handler shape against a single tab so the multi-app path is structurally present.
- **`openWorkspace()` in `src/routes/projects/SandboxItem.svelte`** — add beside `openTerminal()` (`src/routes/projects/SandboxItem.svelte:130`), invoking `open_workspace` with `{ name, workspacePath }`. Decide per the product intent whether the sandbox action row's primary button becomes "Open workspace" (embedded) and the standalone terminal stays as a secondary action, or the embedded path replaces the terminal button outright. Recommended: make "Open workspace" the primary action and keep `openTerminal()` reachable as the code-level fallback (Resolved Decision 7).
- **`messages/en.json`** plus the other locale files (`messages/de.json`, `messages/ru.json`) — add keys for the workspace button, the collapse toggle labels, and the switcher tab, mirroring every locale per the i18n convention in `AGENTS.md`.

## Implemented: Phase D — layout on OS-window resize

- **Window-resize re-layout.** The one continuous layout trigger is the container window resizing. In `open_workspace`, after creating the container, attach a resize listener (`Window::on_window_event`, matching `WindowEvent::Resized`) that reads the new size, recomputes `workspace_layout` with the entry's current `collapsed` flag, and `set_bounds` every visible child. This loop was explicitly *not* exercised by the spike (`01_ideas.md` Validation, "Not yet validated") and must be authored and tested here. Guard against re-entrancy and coalesce bursts of resize events so the app does not issue a `set_bounds` storm.

## Remaining: Phase F — multi-app switching and OpenCode (deferred)

Deferred past v1 (Resolved Decisions 5 and 6), but the seams exist so the work is additive:

- **`switch_app(name, app_label) -> Result<(), AppError>`** — `Webview::show` the target pane, `hide` the rest, update `active_app` in the entry. Keeps every pane's session alive (the rejected close-and-recreate alternative in `01_ideas.md`).
- **`embed_app(name, kind, ...)`** — generalises `open_workspace`'s terminal-embedding step to add a second content child (its own forward, its own label) for an app that serves HTTP in-container. The first consumer is an OpenCode web UI, which does not exist yet; this phase is gated on that UI being served and forwardable like Zellij.
- The switcher route (Phase C) gains real multi-tab rendering and calls `switch_app`/`embed_app`.

## Lifecycle and cross-cutting concerns

- **Teardown wiring.** `undeploy_sandbox` (`src-tauri/src/lib.rs:254`) and `destroy_sandbox` (`src-tauri/src/lib.rs:286`) already call `sync::forward_terminate(&app, &format!("terminal-{name}"))` and remove the `ForwardPortMap` entry. Extend both to call `close_workspace(name)` (or its internal helper) first, so a torn-down sandbox never leaves an orphaned container window or its child webviews and forwards. This mirrors the existing forward-teardown discipline and is the direct fix for the "orphaned panes or forwards" gotcha in `01_ideas.md`.
- **App-exit cleanup.** The `RunEvent::Exit` handler (`src-tauri/src/lib.rs` near line 950) already stops the inference server and the Mutagen daemon best-effort. Container windows close with the process, but their forwards are Mutagen sessions; if any workspace forwards are still live at exit they are reclaimed by the existing daemon stop, so no extra exit handling is required beyond what `close_workspace` does during normal teardown.
- **State derivation for the switcher.** The switcher chrome cannot see the registry directly. Either it is seeded with the initial app list via query param / an `invoke` on mount, or a lightweight `workspace_state(name)` read command is added when Phase F needs live multi-app state. v1's single tab can be static, so this command is deferred with Phase F.
- **DPI and units.** All geometry passed to `add_child`/`set_bounds` is `LogicalPosition`/`LogicalSize`; the runtime scales to physical pixels per monitor DPI (spike: 600×700 logical → 1200×1400 at 200%). Never compute physical pixels by hand.
- **`unstable` durability.** The whole feature sits outside Tauri's semver stability guarantee. Pin the `tauri` version, re-run the spike after any Tauri bump, and keep the factored `prepare_terminal_webview` helper so reverting to the standalone-window path is a one-call-site change.

## Common Gotchas

| Gotcha | Cause | Fix |
|---|---|---|
| `add_child` / `WindowBuilder` / geometry methods do not compile | The `unstable` Cargo feature is off (`src-tauri/Cargo.toml:21`) | Set `tauri = { version = "2", features = ["unstable"] }` (Phase A) |
| Chrome webview's `invoke` calls are denied | New `workspace-*-global` / `workspace-*-switcher` labels are covered by no capability (`default.json` is scoped to `windows: ["main"]`) | Add `capabilities/workspace.json` scoped by `"webviews"` to the chrome labels (Phase A); verify against the spike's deferred IPC-under-capability risk |
| Terminal auto-login breaks in the embedded pane | The login `initialization_script` (`src-tauri/src/lib.rs:176`) was ported from `WebviewWindowBuilder` to `WebviewBuilder` untested | Reuse it via the shared `prepare_terminal_webview` helper and confirm it runs in the child (Phase-B exit criterion) |
| App panes overlap or vanish after the user resizes the window | Child bounds are absolute and do not reflow | Author the `WindowEvent::Resized` listener that recomputes `workspace_layout` and `set_bounds` every visible child (Phase D) — this loop was never exercised by the spike |
| Collapsing hides the expand button | The NavigationPanel was collapsed to zero width | Collapse to `NAVIGATION_PANEL_RAIL_W` = 48 logical px, never zero; keep the toggle in the NavigationPanel chrome in both states |
| Layout ignores what the chrome draws in CSS | Child webviews float above the DOM and are not laid out by HTML/CSS | Treat chrome DOM as intent only; apply all geometry via `set_bounds` in logical units |
| App panes wrong size on a high-DPI monitor | Rectangles specified in physical pixels | Always pass `LogicalPosition`/`LogicalSize`; let the runtime scale to DPI |
| Switching apps restarts Zellij or drops scrollback | The inactive pane was closed and recreated | Switch with `Webview::hide`/`show` (Phase F), keeping panes alive; only `close` on workspace teardown |
| Orphaned container windows or forwards after teardown | `undeploy_sandbox`/`destroy_sandbox` do not close the workspace | Call `close_workspace(name)` from both before the existing forward teardown (Lifecycle) |
| Embedding API breaks after a Tauri upgrade | `unstable` is outside the semver guarantee | Pin `tauri`, re-run the spike after any bump, keep `prepare_terminal_webview` so the standalone-window fallback is one code change away |

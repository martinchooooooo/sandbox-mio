# Embedded Windows (Multi-Webview Workspace) E2E Test Plan

This document is the end-to-end test plan for the embedded-windows workspace described in `02_dev.md`. It covers only the build that plan describes: a per-sandbox bare container window (`workspace-<name>`) hosting a global-chrome child webview, a switcher-chrome child webview, and one content child webview embedding the Zellij terminal (v1 is terminal-only per Resolved Decision 6). It depends on the Phase A–E seams in `02_dev.md` — the `open_workspace`, `set_panel_collapsed`, and `close_workspace` commands, the `WorkspaceRegistry` state, and the teardown wiring into `undeploy_sandbox`/`destroy_sandbox`. **No e2e spike has been run yet.** A code-level multi-webview spike ran on 2026-07-01 (recorded in `01_ideas.md`) and cleared the Tauri `unstable` API, but nothing has yet proven the WebdriverIO/tauri-driver session survives creating and closing a bare container window; the "De-risking spike results" and "Sequencing" sections below make that spike a prerequisite of writing the full spec.

## Goal

Prove, through the real application, that entering a sandbox creates a real container window with the terminal embedded as a native child webview, that the single collapse toggle recomputes native geometry, that several sandboxes' workspaces coexist, and that tearing a sandbox down closes its container and reclaims its forward. The exact real code path the spec must exercise:

- `open_workspace` (Phase B) — builds the `workspace-<name>` container via `tauri::window::WindowBuilder`, adds the two chrome children and the terminal content child via `Window::add_child`, and reuses the factored `prepare_terminal_webview` helper (the same `runtime.prepare_terminal` zellij daemonize + token mint, the same `sync::forward_create` Mutagen forward, the same host-side `zellij.json` write) that `open_terminal` uses today.
- `set_panel_collapsed` (Phase B) — recomputes `workspace_layout` and applies `set_bounds` to the global and content webviews.
- `close_workspace` invoked from `destroy_sandbox`/`undeploy_sandbox` (Phase E) — closes the container window and calls `sync::forward_terminate`.
- The bundled components under test: Podman (the `mio-tests` machine), the Zellij web server baked into the mise base image, and the Mutagen sidecar performing the loopback forward.

What a weaker test would fail to cover: the existing `web-terminal.spec.ts` already proves the token file, `zellij web --status online`, a live forward, and HTTP 200 on the loopback URL. A spec that asserted only those side effects would **not distinguish `open_workspace` from `open_terminal`** — it would not prove a container window was created, that the terminal was embedded as a *child* webview rather than a standalone `WebviewWindow`, that collapse recomputed geometry, that two workspaces coexist, or that teardown closed the container. Those four facts are the feature, so the spec must read them back explicitly (see "Chosen approach").

## Existing test styles

Two styles exist in `e2e/`:

- **App-driven WebdriverIO specs** under `e2e/test/specs/standard/**` and `e2e/test/specs/heavy/**`. They launch the built Tauri app, drive the real UI through page objects (`e2e/test/pageobjects/projects.page.ts`, `e2e/test/pageobjects/project-row.component.ts`), and assert side effects by reading state back through the Podman/Mutagen CLIs (`e2e/lib/podman-connection.ts`, `e2e/lib/mutagen.ts`) and the filesystem. `web-terminal.spec.ts` is the direct precedent for this feature.
- **Light mock-backend specs** under `e2e/test/specs/light/**`. They run against `MIO_MOCK_BACKEND=1` and drive Tauri commands directly through `browser.execute(() => window.__TAURI_INTERNALS__.invoke(...))` without podman (see `e2e/AGENTS.md`).

The new test belongs to the **app-driven standard** style, following `web-terminal.spec.ts`. It borrows one technique from the light style — a direct `invoke` through `window.__TAURI_INTERNALS__` — for the read-back command, because container-window and child-webview state has no CLI equivalent (the Podman/Mutagen CLIs cannot observe a Tauri native window).

## Chosen approach

**Tier: `standard`.** The happy path creates a real local sandbox, runs the real Zellij web server, and opens a real Mutagen forward; that is the tier that proves the feature. It is not `heavy` — it downloads no large asset and loads no model (the one-time base-image build is amortised and covered by a wide timeout, exactly as `web-terminal.spec.ts` does). It is not `light` — the whole point is to prove the real embedding and forward, which the mock backend cannot produce.

**Spec to add:** `e2e/test/specs/standard/embedded-workspace.spec.ts`, discovered by the default `specs: ["./test/specs/standard/*.ts"]` glob in `e2e/wdio.conf.ts`.

**Topology:** local only — the `mio-tests` machine (`LOCAL_CONNECTION`), no remote host. Two local sandboxes are created in one spec to prove concurrent workspaces (Resolved Decision 2); neither needs a deploy target. A remote-workspace scenario (Resolved Decision 8) is deferred to a future `heavy` spec mirroring `remote-terminal.spec.ts`/`deploy-remote.spec.ts`, because it would chain a real deploy.

**The read-back seam.** Because the container window and its child webviews are separate native windows that tauri-driver cannot attach to — the same limitation `project-row.component.ts:101` records for the standalone terminal `WebviewWindow` — the spec cannot drive the embedded panes. It instead reads workspace state back through a **`workspace_state(name)` introspection command**. `02_dev.md` floats this command under "State derivation for the switcher" and defers it to Phase F; **this test plan requires pulling it forward into Phase B** so the standard spec has teeth. `workspace_state` returns, per sandbox: the container label, the `collapsed` flag, the app-pane list (each pane's label, kind, and loopback URL), the active app, and the **last-applied logical rectangles** the layout computed for the global/switcher/content webviews (stored in the `WorkspaceEntry` when `set_bounds` is applied). Returning the applied *logical* rects — not live physical `bounds()` — keeps the collapse assertion deterministic and DPI-independent. The spec invokes `workspace_state` from the `main` webview via `browser.execute(() => window.__TAURI_INTERNALS__.invoke("workspace_state", { name }))`; `main` already holds `core:default`, so no capability change is needed, but the command must be added to the `generate_handler!` list (`src-tauri/src/lib.rs:901`).

**Optional light companion (debug loop only, not primary coverage):** a later `e2e/test/specs/light/embedded-workspace-ui.spec.ts` could exercise the switcher/collapse chrome routes' intent logic (the SvelteKit state in `src/routes/workspace/global` and `/switcher`) against the mock backend for fast iteration. It is not written first and is not the source of truth; the `standard` spec is.

## Harness changes

The standard tier already provisions everything this spec needs, so harness edits are small:

- **No new provisioning.** `e2e/wdio.conf.ts` `onPrepare` already calls `provisionMachine(LOCAL_CONNECTION)` and `ensureMiseBaseImage(LOCAL_CONNECTION, ...)`, and `beforeSession` spawns the app with `PODMAN_CONNECTION=LOCAL_CONNECTION`. The Zellij web server and the Mutagen sidecar are already staged by the `pnpm tauri build --debug` step and the base image. The new spec runs under the default glob with no `onPrepare`/`beforeSession` change.
- **Page-object method.** Add `openWorkspace()` to `e2e/test/pageobjects/project-row.component.ts`, clicking the new workspace button that Phase C adds to `src/routes/projects/SandboxItem.svelte` (button label to match whatever Phase C ships, e.g. `button=workspace`). Mirror the existing `openTerminal()` at `project-row.component.ts:104`, including its comment that the opened surface is a window tauri-driver cannot drive.
- **Read-back helper.** Add a small helper (inline in the spec, or `e2e/lib/workspace.ts`) wrapping `browser.execute(() => window.__TAURI_INTERNALS__.invoke("workspace_state", { name }))` and returning the parsed entry, plus a `workspaceExists(name)` that resolves the command's absence/`null` to `false` for the teardown assertion.
- **Cleanup honouring existing flags.** In the spec's `after`, best-effort `podman(LOCAL_CONNECTION, ["rm", "-f", name], { check: false })` for **both** sandboxes, mirroring `web-terminal.spec.ts:42`. No new env flag is needed; the spec creates and destroys its own sandboxes within the run.
- **Failure diagnostics.** Reuse the `afterEach` diag dump from `web-terminal.spec.ts:49` (URL + page source + screenshot to `e2e/.diag`) so a failure captures the `main` webview state.

## Spec scenario

Numbered steps for `embedded-workspace.spec.ts`. Sandbox names are timestamped (`e2e-workspace-a-${Date.now()}`, `e2e-workspace-b-${Date.now()}`). The suite uses `function ()` with `this.timeout(600000)` so the first create can absorb the one-time base-image build, exactly as `web-terminal.spec.ts:27` does.

1. **Create and start sandbox A.** Drive `ProjectsPage.open()` → `ensurePodmanReady()` → `createProject(nameA, { timeout: 600000 })`, then `row.start()` and `row.waitForRunning()`. Assert the row shows `running`. This reuses the proven create/start path; it is setup, not the feature.
2. **Open sandbox A's workspace.** Call the new `row.openWorkspace()`. Poll for the host-side token file `<<workspace>>/.mio/zellij.json` (as `web-terminal.spec.ts:107` does) to confirm the embedded terminal ran the real `prepare_terminal_webview` path. Then read `workspace_state(nameA)` and assert: an entry exists; its container label is `workspace-<nameA>`; the app-pane list has exactly one pane of kind terminal whose URL starts with `http://127.0.0.1:`; the applied logical rects for the global, switcher, and content webviews are present and non-overlapping. This is the proof that a container window with an embedded child webview was created — the fact `web-terminal.spec.ts` cannot assert.
3. **Prove the embedded terminal actually serves.** Assert `zellij web --status` inside the container contains `online` (via `podman exec`, `check: false`), that `forwardList("terminal-<nameA>")` shows `Connected`, and that a `fetch(session.url)` on the persisted loopback URL returns HTTP 200 (poll, as `web-terminal.spec.ts:151`). This confirms the embedded child renders a live surface, not a dead rectangle.
4. **Collapse and expand the global panel.** Invoke `set_panel_collapsed(nameA, true)`, re-read `workspace_state`, and assert `collapsed` is true, the global rect width equals `GLOBAL_RAIL_W` (48), and the content rect x-offset and width grew relative to step 2. Invoke `set_panel_collapsed(nameA, false)` and assert the global rect width is back to `GLOBAL_EXPANDED_W` (260) and the content rect returned to its step-2 value. This gives teeth to the collapse loop the 2026-07-01 spike explicitly left unexercised.
5. **Re-open is idempotent.** Call `row.openWorkspace()` a second time and assert `workspace_state(nameA)`'s pane list is unchanged (still one terminal pane) and no second forward appeared (`forwardList` still shows a single `terminal-<nameA>` session). Mirrors the idempotency step in `web-terminal.spec.ts:171` and proves the focus-or-create guard in `open_workspace`.
6. **Two workspaces coexist.** Create and start sandbox B, open its workspace, then assert `workspace_state(nameA)` and `workspace_state(nameB)` both return live entries with distinct container labels and distinct forwards (`terminal-<nameA>` and `terminal-<nameB>` both `Connected`). This proves the registry is keyed per sandbox and multiple container windows coexist (Resolved Decision 2).
7. **Teardown closes only the torn-down workspace.** Destroy sandbox A via `row.destroy()`. Assert: the local container A is gone (`!podmanOk(inspect nameA)`); `workspace_state(nameA)` no longer returns an entry (`workspaceExists(nameA)` is false), proving `destroy_sandbox` called `close_workspace`; `forwardList("terminal-<nameA>")` no longer shows `Connected`, proving `sync::forward_terminate` ran; and sandbox B's workspace is **untouched** — `workspace_state(nameB)` still returns its entry and `terminal-<nameB>` is still `Connected`. This proves Phase E teardown wiring and workspace isolation. Finally destroy sandbox B and assert its entry and forward are gone too.

## De-risking spike results

No e2e spike has been run for this feature. The relevant prior evidence and the outstanding e2e risk:

- **Cleared (2026-07-01, code-level, from `01_ideas.md`):** the `unstable` multi-webview API compiles and renders — `tauri::window::WindowBuilder::new`, `Window::add_child`, and `Webview::{set_bounds, hide, show, bounds, close}` are present under the feature; two children coexist in one window; an internal `WebviewUrl::App` child renders a live route; external loopback children render distinct pages. This clears the mechanics the spec depends on.
- **Not yet cleared (blocking the spec being worth writing):** whether the WebdriverIO/tauri-driver session, attached to the `main` webview, **survives `open_workspace` creating a bare container `Window` with child webviews and `close_workspace` closing it**. `web-terminal.spec.ts` already opens an extra standalone `WebviewWindow` without breaking the session, which makes the risk low, but a bare `Window` with children is a different object than a `WebviewWindow`, so this is unproven. Classification: **test concern**, not a feature fix — if the session drops, the fix is harness handling of the extra window, not a product change. A spec written before this is confirmed could go red for a reason unrelated to the feature, so confirm it first.

Recommended minimal spike before the full spec: with Phase A/B implemented (including `workspace_state` pulled forward), write a throwaway spec that opens one workspace, reads `workspace_state` back through `window.__TAURI_INTERNALS__.invoke`, closes it, and asserts the `main` session is still responsive. Record the date and result here.

## Sequencing

1. Implement Phase A (enable `unstable`, add `capabilities/workspace.json`) and Phase B (`WorkspaceRegistry`, `workspace_layout`, `open_workspace`, `set_panel_collapsed`, `close_workspace`, the factored `prepare_terminal_webview`), and **pull `workspace_state` forward from Phase F into Phase B** — the spec cannot assert anything without it.
2. Run the minimal de-risking spike above; confirm the tauri-driver session survives the container window's lifecycle. Do not write the full spec until this is green.
3. Implement Phase C's `openWorkspace()` button in `SandboxItem.svelte` and the matching `ProjectRow.openWorkspace()` page-object method.
4. Wire Phase E teardown (`close_workspace` from `destroy_sandbox`/`undeploy_sandbox`) — step 7 of the spec asserts it directly.
5. Write `embedded-workspace.spec.ts`. The collapse assertion (step 4) depends on `set_panel_collapsed` storing the applied logical rects into the `WorkspaceEntry` so `workspace_state` can report them; land that storage in Phase B, not as an afterthought.

## Environment notes

A future session needs: the `mio-tests` Podman machine provisioned and running (done by `wdio.conf.ts` `onPrepare` → `provisionMachine(LOCAL_CONNECTION)`); the mise base image staged with the Zellij web server on the global PATH (`ensureMiseBaseImage`, gated on `BASE_IMAGE_VERSION`); `SANDBOX_WORKSPACE_ROOT` set so the spec can resolve `<<workspace>>/.mio/zellij.json`; the app spawned with `PODMAN_CONNECTION=mio-tests` (done by `beforeSession`); and the Mutagen sidecar bundled by the debug build. The `workspace_state` command is reached from the `main` webview via `window.__TAURI_INTERNALS__.invoke` and needs no capability beyond `main`'s existing `core:default`, but it must be registered in `generate_handler!` (`src-tauri/src/lib.rs:901`). No remote machine is required for this spec; a remote-workspace scenario is a separate future `heavy` spec.

## Common Gotchas

| Gotcha | Cause | Fix |
|---|---|---|
| Spec cannot click the terminal/collapse/switcher inside the workspace | The container window and its child webviews are separate native surfaces tauri-driver never attaches to (same limit as the standalone terminal `WebviewWindow`, `project-row.component.ts:101`) | Assert side effects and read state back with `workspace_state` through `window.__TAURI_INTERNALS__.invoke`; do not try to drive the embedded panes |
| `workspace_state` invoke rejects with an unknown-command error | The command was left deferred to Phase F or never added to `generate_handler!` (`src-tauri/src/lib.rs:901`) | Pull `workspace_state` forward into Phase B and register it in the handler list |
| Collapse step reads wildly different rect widths across machines | The command returned live physical `bounds()`, which are DPI-scaled (spike: 260 logical → 520 physical at 200%) | Have `workspace_state` report the last-applied **logical** rects stored in the `WorkspaceEntry`, not physical `bounds()`; assert against `GLOBAL_EXPANDED_W`/`GLOBAL_RAIL_W` |
| WebdriverIO session dies or hangs when the workspace opens/closes | Creating or closing a bare container `Window` with children disturbed the tauri-driver session attached to `main` (unproven; classified a test concern) | Run the minimal de-risking spike before writing the full spec; if it reproduces, add harness handling for the extra window rather than changing the feature |
| `token file <<workspace>>/.mio/zellij.json did not appear` after `openWorkspace()` | `open_workspace` did not route through the factored `prepare_terminal_webview` helper, so the host-side token write (`src-tauri/src/lib.rs:156`) never ran | Ensure `open_workspace` calls `prepare_terminal_webview` for the terminal pane, not a divergent inline path |
| `forwardList("terminal-<name>")` shows nothing after opening the workspace | The embedded terminal pane skipped `sync::forward_create`, or used a different forward name than `terminal-<name>` | Keep the `terminal-<name>` forward-name convention in `prepare_terminal_webview` so both the standalone and embedded paths, and the teardown in `undeploy`/`destroy`, agree |
| Destroying one sandbox leaves the other's workspace broken or its forward orphaned | `close_workspace` closed the wrong container, or teardown was not keyed by sandbox name | Key `close_workspace` and the `WorkspaceRegistry` strictly by sandbox name; step 7 asserts sandbox B is untouched after A is destroyed |
| Sandbox B's create times out on a fresh machine | The base-image build only amortises after the first create; a slow machine can still exceed a narrow per-step wait | Keep `this.timeout(600000)` on the suite and pass a wide `timeout` to `createProject`, mirroring `web-terminal.spec.ts:69` |
| Orphaned containers after a failed run | An assertion threw before teardown | Best-effort `podman rm -f` **both** sandbox names in `after` with `{ check: false }`, mirroring `web-terminal.spec.ts:42` |

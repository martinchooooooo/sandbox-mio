# Host-Tool SSH Access Dev

This is the build plan for `docs/features/host-tool-ssh-access/01_ideas.md`: letting a host-machine SSH client — the Claude Code desktop app's "Add SSH connection" feature foremost, and any other `~/.ssh/config`-aware tool after it — attach to a sandbox over the SSH transport the app already maintains for Mutagen. **Status: Phases A, B, C, and E are implemented; every other phase below is `Remaining`.** The transport it builds on is complete (`docs/features/podman-exec-transport/02_dev.md`, extended to `msb` sandboxes by `docs/features/microsandbox-provider/02_dev.md`), which is why this plan is far smaller than the revision it replaces: the container-side server, the per-sandbox keypair, the authorized-keys install, and the per-sandbox `Host` alias all ship today.

Reviewed against the tree on 2026-08-17. Most of the earlier plan's phases described a second, independent SSH path that the exec transport superseded; "Superseded plan" below records each dropped item and why, so a future session does not rebuild it.

## The concrete model

Every exec-capable sandbox already has everything a host tool needs: an `sshd` in the base image reached through `podman exec`/`msb exec` by `/usr/local/bin/mio-sshd`, an ed25519 keypair under `crate::paths::app_data_root(app)/ssh-keys/<name>/`, its public half in the container's `/etc/ssh/authorized_keys.container`, and a `Host <sandbox name>` block in `~/.ssh/sandbox-mio/config` carrying `ProxyCommand`, `User root`, `IdentityFile`, `UserKnownHostsFile`, `IdentitiesOnly yes`, and `StrictHostKeyChecking accept-new` — included from `~/.ssh/config`. This feature adds no transport, no port, no daemon, and no second identity. It adds four things:

1. A command that guarantees the block is current and reports the handoff values (`sandbox_ssh_access`), because the block's `ProxyCommand` encodes the machine the sandbox currently runs on and the app rewrites it only on paths that open a forward.
2. A `PATH` fix in the base image, so a non-interactive SSH session sees the sandbox's mise-managed toolchain.
3. Keepalives and quoted paths in the rendered alias block.
4. A panel that shows the user the alias, plus alias/key teardown at destroy so a dead sandbox stops leaving a resolvable handle behind.

There is no enabled state, no `.mio` record, and no startup restore: nothing is provisioned per sandbox at enable time, so there is nothing to persist or restore. The one hard precondition is that the container must be running, since the `ProxyCommand` is an `exec` into it.

## Superseded plan (do not reintroduce)

The earlier revision of this document specified a parallel SSH path. Each item below was dropped because the exec transport already covers it or made it counterproductive:

- **`SSH_PORT = 22`, a third `--publish 127.0.0.1::22` in `create`/`deploy`, and the matching constant in `runtime/mod.rs`.** An exec-capable sandbox publishes nothing at all (`PublishModel::ExecTunnelled`, `src-tauri/src/provider/types.rs`); reintroducing a publish would resurrect the model the project deliberately left behind.
- **`ServiceKind::Ssh` plus `forward_name`, `open_forward`, and frontend-union work.** No forward is involved: the client's own SSH connection *is* the transport. `ServiceKind` keeps `Terminal`, `AgentWeb`, and `Exposed(port)`.
- **The relay-scanner exclusion of `ZELLIJ_WEB_PORT`/`PASEO_WEB_PORT`/`SSH_PORT` by literal value.** `poll_ports_file` (`src-tauri/src/network/mod.rs`) never sees a container-side 22, because no `sshd` listens on a port — `sshd -i` speaks over the exec pipe's stdio. The relay pool itself was removed with the publish model (image 7).
- **An `ssh-` prefix arm in `sweep_stale_forwards` (`src-tauri/src/sync/mod.rs`).** No Mutagen session named `ssh-<sandbox>` exists to sweep.
- **`RuntimeManager::prepare_ssh`** with its `/run/sshd` creation, `PermitRootLogin yes` drop-in, `ssh-keygen -A`, `authorized_keys` injection, and idempotent daemon start. `mio-sshd` creates `/run/sshd` on every connection, host keys are baked, `install_sandbox_key` installs the key at create/deploy, and `sshd_config.container` sets `UsePAM no` with pubkey auth — root login already works, as every Mutagen session against a sandbox proves. No runtime trait method, no `RuntimeError` variant, no mock addition.
- **An app-scoped keypair generated in-process, and the `MIO_SSH_KEY_DIR` override for it.** `ensure_sandbox_identity` (`src-tauri/src/backends/mod.rs`) generates a *per-sandbox* key by shelling out to the host's `ssh-keygen`, under `crate::paths::app_data_root`, which already honours the per-worktree `MIO_APP_DATA_DIR` the e2e harness sets. The in-process-generation argument lost to shipped code; the host `ssh-keygen` dependency is now a pre-existing fact of `create`, not something this feature introduces.
- **`HostKeyAlias` and a `scrub_known_hosts` helper running `ssh-keygen -R`.** The alias pins its own `UserKnownHostsFile` beside the sandbox's identity, and `forget_sandbox_host_key` deletes it whenever a fresh container takes a reused name. The user's own `known_hosts` is never touched, so nothing needs scrubbing there and no e2e harness change against it is needed. **Partly reversed (2026-11-18):** pinning the host keys proactively is now justified, see "Host keys are pinned from the container" under Resolved Decisions. `HostKeyAlias` itself stays out, because the pinned lines' host pattern already covers every port.
- **`.mio/ssh.json`, the startup restore, and the running-only guard on it.** There is no per-sandbox state to persist.
- **Extending `CONFIG_LOCK` over `write_alias`/`remove_alias`.** Done since, and more thoroughly: `with_config_lock` (`src-tauri/src/ssh/mod.rs`) holds both the in-process mutex and a cross-process file lock for the whole read-modify-write.
- **A `sandbox-mio-ssh-<name>` alias class.** The alias is the sandbox name (`alias_name`, `src-tauri/src/services/routing.rs`). Its namespace cost is recorded in `01_ideas.md` and `04_improvements.md`.

Two items from the earlier plan survive, because they are still true of `render_block` today: the unquoted `IdentityFile` value, and the absent keepalives. Both are Phase C.

## Resolved Decisions

Restating every Open Question from `01_ideas.md`:

- **Does a third-party client resolve an `Include`d `ProxyCommand` alias, and what is the fallback?** Yes: spike S1 (Phase 0) passed on 2026-11-18, so none of the fallbacks below was needed. They stay recorded as the decision S1 would have forced: if S1 fails on `Include` only, the fallback is to write the managed block into `~/.ssh/config` itself for exec-capable sandboxes; if it fails on `ProxyCommand` support, no fallback exists inside this model and the feature stops at "the panel shows the block for the user to paste into their own client's config", with the publish-plus-forward model reconsidered as a separate feature.
- **Toggle or read-only panel?** Read-only panel with a refresh action. Nothing is started, provisioned, or torn down per sandbox, so a toggle would persist state that has no referent — the failure mode the earlier plan's `.mio/ssh.json` existed to work around, and which disappears entirely here. The panel's one piece of live state is whether the container is running.
- **Where does the panel live?** A section in `src/lib/workspace/WorkspaceDashboard.svelte`, sibling to `PortsManager`, rendered from a new `src/routes/projects/SshAccessCard.svelte`. The dashboard is the per-sandbox detail surface (`PackageManager`, `AgentManager`, `PortsManager` all live there); `SandboxItem.svelte` is a compact lifecycle row whose actions all fit one line, and copyable connection details do not.
- **How is a value copied?** Add `@tauri-apps/plugin-clipboard-manager` (plus the Rust crate and a `clipboard-manager:allow-write-text` entry in `src-tauri/capabilities/default.json`). No clipboard mechanism exists in `src/` today, so either route is new work; the plugin is chosen because it goes through the capability model every other privileged call in this app uses, rather than depending on the webview's own permission behaviour. `navigator.clipboard` may well work — the app's origin ends in `localhost`, which Chromium treats as a secure context — but nothing in the codebase exercises it, so it is the fallback to try only if the plugin is rejected in review, alongside a selectable read-only input.
- **Is the user's own public key authorized too?** No for v1. `install_sandbox_key` writes `/etc/ssh/authorized_keys.container` by `podman cp`, replacing it wholesale, and every target client accepts an explicit identity file. Recorded in `04_improvements.md`.
- **Alias and key teardown on destroy?** Yes — Phase E, which gives `remove_alias` its first caller.
- **Which host tools are validated?** Claude Desktop is the one exercised by hand (spike S1) and the one the panel's copy names. VS Code Remote-SSH and JetBrains Gateway need no project-side code, so they ship as "should work" and are spiked opportunistically in S3.
- **Credential handoff to a client's auto-installed agent?** Deferred, unchanged: it depends on `docs/features/shared-agent-auth/01_ideas.md` shipping and on confirming where that copy stores credentials.

Decisions forced by the current tree rather than restated from `01_ideas.md`:

- **The command refreshes the alias; it does not start the container.** `SandboxRouter::resolve` (`src-tauri/src/services/routing.rs`) rewrites the managed block, which is required because the `ProxyCommand` embeds `--connection <machine>` and a deploy or undeploy moves the sandbox. Starting the container is deliberately *not* part of the command: the panel reports the stopped state and points at the existing start control, so opening a panel never boots a sandbox the user left stopped.
- **~~A non-exec-capable sandbox returns a payload, not an error.~~ Obsolete (2026-11-18).** The techdebt sweep removed the publish+relay model, `Sandbox::supports_exec_transport` and `EXEC_TRANSPORT_MIN_IMAGE_VERSION` (`docs/features/techdebt-sweep/02_dev.md`, Phases D and E): every sandbox is now reached through its own alias, so the payload carries no `execCapable` field and the command always refreshes the block.
- **`PATH` is fixed in the image, not per session, with `SetEnv` in the baked `sshd_config.container`.** The client's remote agent spawns its own subprocesses, so nothing host-side can wrap them. Spike S2 ([spike/s2-path.md](spike/s2-path.md)) found that `/root/.bashrc` *is* read for a remote command under `sshd -i` (sshd exports `SSH_CLIENT=UNKNOWN 65535 65535` over the pipe), so a non-interactive shims branch there would also work; `SetEnv` won because it does not depend on shell startup files or on Debian building bash with `SSH_SOURCE_BASHRC`, adds no process per command, and leaves Herdr panes untouched. The `BASE_IMAGE_VERSION` bump is 8 to 9.
- **~~`EXEC_TRANSPORT_MIN_IMAGE_VERSION` does not move.~~ Obsolete (2026-11-18).** The constant was removed with the publish+relay model (see the obsolete decision above), so Phase B bumps only `BASE_IMAGE_VERSION` (`src-tauri/src/backends/mod.rs`). A sandbox on an earlier image keeps its transport and only misses the `PATH` fix.
- **Host keys are pinned from the container, not learned on first contact.** Claude Desktop checks a first connection strictly whenever the alias sets its own `UserKnownHostsFile` (its log says it cannot redirect `accept-new` to its own file for such a configuration), and the pinned file was empty until some other client connected first. `seed_sandbox_host_keys` (`src-tauri/src/backends/mod.rs`) now execs `cat /etc/ssh/ssh_host_*_key.pub` through the sandbox's provider, which is authoritative because `ssh-keygen -A` bakes the keys into the image, and writes every key type to the pinned file as `<alias>,[<alias>]:* <type> <base64>`. Seeding runs at microsandbox create (running by then), at deploy, after every `start_sandbox` (`services::ssh_access::spawn_pin_host_keys`, in the background; a Podman `create` leaves the container stopped, so its first start is the first chance), and in `services::ssh_access::access` whenever the sandbox is running, which also pins existing sandboxes when their panel loads. It is best effort and warn-logged: empty or garbage output writes nothing, a failure never fails a create, deploy or panel fetch, and the file is rewritten wholesale only when its content differs, which also heals a recreate. `forget_sandbox_host_key` still runs first at create and deploy. The `[alias]:*` pattern is needed because a client that carries a non-22 port looks up `[alias]:<port>`; verified with OpenSSH 10.2 on Windows that `ssh-keygen -F [alias]:61548` matches it, and that `ssh -o StrictHostKeyChecking=yes` connects with and without `-p`. That `ssh` itself already looks up the plain alias when a `ProxyCommand` is set, so `HostKeyAlias` adds nothing and is not emitted (this reverses the "Superseded plan" item only for the pinning, not for `HostKeyAlias`). The terminal's russh client matches the plain `<alias>` entry on port 22 and shares the file.
- **Keepalives apply to every `Proxied` block, with no opt-in field.** The earlier plan made them optional to keep Mutagen's aliases unchanged; that distinction no longer exists, since every `Proxied` alias is a per-sandbox exec-transport alias and Mutagen's own long-lived forwards benefit from the same directives. One fewer field on `SshAlias`.
- **The light e2e tier really does write `~/.ssh` and a real keypair.** `default_backend` returns `CliBackend` regardless of `MIO_MOCK_BACKEND`, so a light-tier `create` runs `ensure_sandbox_identity` (real `ssh-keygen`) and `ensure_sandbox_alias` (real managed config) against a scripted `podman`, whose unknown-key default (`default_output`, `src-tauri/src/mockctl/mod.rs`) makes `podman cp` succeed silently. A light spec for the panel is therefore feasible, and the stale comment in `e2e/wdio.conf.ts`'s `onComplete` claiming a light run writes no SSH alias is recorded in `04_improvements.md`.

## Parallel-worktree constraints

- **New path the app reads or writes:** none. The keypair and pinned `known_hosts` already live under `crate::paths::app_data_root`, which honours `MIO_APP_DATA_DIR`.
- **New host port:** none — the whole point of the exec transport.
- **New host-global external resource:** none *new*, but the feature's value depends on one that already exists: the managed `~/.ssh/sandbox-mio/config` and the `Include` line in `~/.ssh/config`. `03_e2e.md`'s spec therefore stays in the host-locked `standard` tier, and any teardown touching `~/.ssh` stays inside the existing `!IS_LIGHT_RUN` gate in `e2e/wdio.conf.ts`.
- **New bundled binary:** none. The clipboard plugin is a crate and an npm package, not a `src-tauri/binaries/` asset.
- **New environment variable:** none.

## Phase 0 — gating spikes

S1 can invalidate the flagship use case; S2 decides Phase B's mechanism. Run both before Phase A. Record scripts and captured output under `docs/features/host-tool-ssh-access/spike/` and update this section's status line.

Status: S2 `Done` and S4's headless half `Done` ([spike/s2-path.md](spike/s2-path.md)); S1 `Done` (below); S3 and S4's client-side half `Remaining`. S2 picks `SetEnv PATH` in `sshd_config.container` for Phase B. S4: killing `ssh.exe` ends the in-container `sshd` at once (Windows OpenSSH takes its `ProxyCommand` child down), a hung client is reaped by ClientAlive in about two minutes, and in both cases the session's own command is left running under PID 1. The transport spikes this feature relies on are recorded in `docs/features/podman-exec-transport/02_dev.md`, Phases A and F.

- **S1 — does a third-party client resolve an `Include`d alias and honour its `ProxyCommand`?** Create a sandbox, start it, and confirm the baseline first: `ssh <sandbox name> whoami` from `cmd.exe` or PowerShell — **not** Git Bash, whose `PATH` and path conversion mask the failure modes a real client hits — must print `root`. That single command proves the `Include`, the `ProxyCommand`, the identity, and root login in one step, and it is also the exact path any client that shells out to the system client takes. Then add the same alias name in Claude Desktop's "+ Add SSH connection" and open a session. Record which of the three outcomes holds: the alias resolves; the alias is invisible (an `Include` gap — fallback is writing the block into `~/.ssh/config`); or the alias resolves but `ProxyCommand` is refused or unsupported (no fallback inside this model — see Resolved Decisions). **Done (2026-11-18, Claude Desktop on Windows):** "Add SSH connection" spawns the system OpenSSH, resolves the `Include`d `Host <sandbox>` alias in `~/.ssh/sandbox-mio/config` and runs the alias's `ProxyCommand`, so the alias resolves and no fallback is needed. The first attempt failed with `Host key verification failed`: because the block sets its own `UserKnownHostsFile`, Claude Desktop cannot redirect its first-contact pin to its own file and verifies strictly, while the pinned file was empty. The form had also prefilled a stale port (61548) from an old connection, so the lookup key was `[alias]:61548`; a port means nothing over a `ProxyCommand`. After a manual `ssh <alias> whoami` populated the file and the port was cleared, Claude Desktop connected. The fixes are host-key pinning (Resolved Decisions) and the panel's instruction to leave the port and key empty.
- **S2 — do mise-managed tools appear on `PATH` in a non-interactive session, and which mechanism fixes it?** With the same alias: `ssh <name> "which node; mise --version; echo $PATH"` after installing a tool through the app's package manager. Then determine whether `~/.bashrc` is read at all under `sshd -i` over a pipe (echo a marker from it), since that decides between the two candidate fixes: `SetEnv PATH=…` in the baked `sshd_config.container`, which is independent of shell startup files, or a shims branch in `/root/.bashrc`. Confirm the chosen fix with a rebuilt image before Phase B commits to it. **Done ([spike/s2-path.md](spike/s2-path.md)):** without a fix, `which node` finds nothing, because sshd starts the session in `/root`, outside the workspace, and `mise activate`'s hook re-runs only on a shell `cd`. `~/.bashrc` *is* read under `sshd -i`, since sshd exports `SSH_CLIENT=UNKNOWN 65535 65535` over the pipe. Both candidates work. Phase B ships `SetEnv PATH=/root/.local/share/mise/shims:/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin` in `sshd_config.container`: it does not depend on shell startup files, it adds no process per command, it leaves Herdr panes and interactive logins as they are, and it was confirmed on a rebuilt image. The shims resolve versions from the directory a tool runs in, so a client must work in `/root/work`: from `$HOME` a shim reports `No version is set`.
- **S3 — does a client's own remote bootstrap complete inside the container?** Claude Desktop installs its own Claude Code copy on first connect; VS Code Remote-SSH and JetBrains Gateway install their own server components. Each downloads a runtime over the sandbox's egress and writes under `/root`. Nothing in the project exercises that path. Capture what gets installed and where, since it also decides whether the deferred credential handoff has a target.
- **S4 — session durability.** Leave a session idle past any keepalive interval Phase C would set and confirm whether it survives; stop the sandbox mid-session and record what the client reports; kill the client abruptly and check for a lingering in-container `sshd` (`podman exec <name> pgrep -a sshd`), refining the finding already recorded in `docs/features/podman-exec-transport/02_dev.md`, Phase F.

## Implementation phases

### Implemented: Phase A — the handoff command

- `SshAccess` payload in `src-tauri/src/ssh/types.rs`: `Serialize`, `rename_all = "camelCase"`, carrying the alias name, the identity path, the pinned `known_hosts` path, the literal `ProxyCommand` string, and `running`. Kept in the `ssh` module rather than in a command file, so the alias's shape and the payload describing it stay in one place.
- `src-tauri/src/services/ssh_access.rs` (peer of `services::panes` and `services::routing`): `access(name, router, app)` validates the name before any key exists, calls `SandboxRouter::resolve` — which rewrites the managed block — and assembles the payload. The identity path comes from `ensure_sandbox_identity` and the `known_hosts` path from `sandbox_known_hosts_path`, the same functions the alias write uses. The `ProxyCommand` comes from `sandbox_proxy_command(name, machine)` (`src-tauri/src/backends/mod.rs`), extracted from `ensure_sandbox_alias` and dispatching to the Podman or `msb_proxy_command` form; `ensure_sandbox_alias` now formats through the same Podman helper, so the panel can never display a command that differs from the one in the file. Unit tests in `backends/mod.rs` pin the Podman form to the route's `--connection` and the microsandbox form to `msb_proxy_command`.
- `src-tauri/src/commands/ssh.rs` holds one thin `#[tauri::command] sandbox_ssh_access(name, router, app)`, registered as `ssh::sandbox_ssh_access` in `tauri::generate_handler![]` (`src-tauri/src/commands/mod.rs`).
- `src/lib/ssh.ts`: the `SshAccess` interface plus a typed `sandboxSshAccess(name)` wrapper around `invoke`, mirroring how `src/lib/network/state.svelte.ts` wraps its commands (without a store — this payload is fetched per panel, not pushed).
- Deviations from the plan as reviewed on 2026-08-17:
  - **No `execCapable` field and no `locate` branch.** The exec-capability predicate was removed by the techdebt sweep (see the obsolete Resolved Decision above), so every sandbox takes the `resolve` path.
  - **No `store` parameter.** `running` is `SandboxRoute::running`, which `resolve` already derives from `SandboxBackend::list` in the same pass (listed `running` and on its provider's local machine); a second `list` would cost another podman call for the same answer. The command therefore takes only the `SandboxRouter` handle, per the state narrowing rule. A deployed sandbox always reports `running: false` (`docs/features/native-terminal/02_dev.md`, Resolved Decision 11), recorded in `04_improvements.md`.
  - **Built before S1.** Nothing in Phase A depends on S1's outcome: S1 decides which of the payload's values Phase D shows, not what the command returns.

### Implemented: Phase B — non-interactive `PATH` in the base image

- `src-tauri/resources/Containerfile`: the `sshd_config.container` `printf` gains `SetEnv PATH=/root/.local/share/mise/shims:/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin` after the `Subsystem sftp` line, the mechanism spike S2 confirmed ([spike/s2-path.md](spike/s2-path.md)). The shims directory is a literal, because that `RUN` precedes `ENV MISE_DATA_DIR`; both lines carry a comment naming the other, per the paired-values rule. The tail is Debian's root path, which `/etc/profile` also sets. `/root/.bashrc` is unchanged, so Herdr panes and interactive logins keep `mise activate bash`.
- The comment states the constraint, not the mechanism: a client's remote agent runs commands non-interactively and must still see the toolchain.
- `BASE_IMAGE_VERSION` (`src-tauri/src/backends/mod.rs`) 8 to 9; no other file hardcodes the version (`e2e/lib/podman-machine.ts` regex-parses the constant). A sandbox created on an earlier image keeps working over SSH and only misses the `PATH` fix.
- Limitation: the shims resolve a version only where a mise config applies, and the only one is `/root/work/mise.toml`, so a client must work in `/root/work`; from `$HOME` a shim prints `No version is set`. Phase D's panel must say so; the rejected global-config fallback is in `04_improvements.md`.
- Verified on 2026-11-18 against `sandbox-mio/base:9`, built the way `ensure_image` (`src-tauri/src/provider/mod.rs`) builds it, on `podman-machine-default`: a throwaway container with `mise use node@24.19.0` in `/root/work`, reached by `ssh.exe` from PowerShell through the alias-shaped `ProxyCommand` with a throwaway key. `cd /root/work && which node` and `exec env -C /root/work node -v` (a non-shell child) both found node 24.19.0, the spike's `s2-probe.sh` resolved it in `/root/work` and below but not in `/root`, and the `sftp` subsystem still listed `/root/work`. Not yet verified through the app's own create and package-install path, which Phase F's `standard` run covers.

### Implemented: Phase C — alias block hardening (`src-tauri/src/ssh/mod.rs`)

- `render_block`'s `Proxied` arm emits `ServerAliveInterval 15` and `ServerAliveCountMax 3`, matching the image's `ClientAliveInterval 15`/`ClientAliveCountMax 3` in `src-tauri/resources/Containerfile`, so both ends give up on a dead exec pipe after about 45 seconds. No new field on `SshAlias`: every `Proxied` alias is a per-sandbox exec-transport alias, and Mutagen's own long-lived forwards over the same block benefit identically. The `Direct` arm gets no keepalives.
- `IdentityFile` and `UserKnownHostsFile` in `Proxied`, and `IdentityFile` in `Direct`, are wrapped in double quotes by a `quoted` helper, so a home directory containing a space (`C:\Users\John Smith\…`) stays one argument. The helper deliberately escapes nothing: the Windows 10 inbox OpenSSH (8.1) parser has no backslash escapes, and a Windows path cannot contain `"`. `ProxyCommand` is left verbatim, since OpenSSH passes the rest of that line unparsed and its executable path is already quoted where it is built (`podman_literal_path`, `msb_literal_path` in `src-tauri/src/backends/mod.rs`).
- No Rust code parses a value back out of the managed config: `strip_block` matches only the marker lines, and `probe_alias` hands the file to `ssh -F`. No e2e helper reads a value back yet either — `agent-web.spec.ts` asserts on keywords only — so the quote-stripping requirement lands with `e2e/lib/ssh-client.ts` (`03_e2e.md`, harness change 2).
- Unit tests in `src-tauri/src/ssh/mod.rs` cover the keepalives, quoting of space-bearing paths in both arms, the verbatim `ProxyCommand`, and `strip_block` removing a quoted block.

### Implemented: Phase D — the "Connect from desktop apps" panel

- `src/routes/projects/SshAccessCard.svelte`, rendered by `src/lib/workspace/WorkspaceDashboard.svelte` directly after `PortsManager` inside the dashboard's Ports section, taking the same `sandboxName`/`workspacePath`/`action` props. It is a plain labelled block like its siblings, not a `card` component. It fetches `sandboxSshAccess` through its own `createActionRunner` (`src/lib/actions.svelte.ts`), whose `run` routes failures through `parseError`, and shows the error inline. A request counter drops a response that a newer request has overtaken.
- Order on screen: one neutral sentence naming Claude Desktop and VS Code Remote-SSH, then the alias as "SSH host" with a copy button, then the state line, then a sentence telling the user to open `/root/work` in their client (Phase B's limitation, with its own copy button), then a collapsed "Details" disclosure (`src/lib/components/AdvancedSection.svelte`) holding the identity path, the pinned `known_hosts` path and the `ProxyCommand`, each with a copy button, plus a note that a copied `ProxyCommand` goes stale on deploy or undeploy while the alias does not.
- Copy uses `writeText` from `@tauri-apps/plugin-clipboard-manager`. The crate is registered in `src-tauri/src/lib.rs` beside the other plugins, and `clipboard-manager:allow-write-text` is in `src-tauri/capabilities/default.json`. A copied value swaps its icon for a tick for 1.5 seconds; a failure raises a `svelte-sonner` error toast.
- State line, from `data-ssh-state`: `deployed` whenever `deploymentFor` (`src/lib/sandbox/state.svelte.ts`) returns a deployment, before the payload is consulted, since `running` is false for every deployed sandbox. That line names the deploy host and says the sandbox must be running there. Otherwise `running` or `stopped` follow the payload's `running` flag, and the stopped line points at the header's existing start button.

## Lifecycle / cross-cutting concerns

- **The container must be running.** The `ProxyCommand` is an `exec` into the instance; a stopped sandbox fails at the transport, before SSH. Nothing in the connection path can start it — there is no host-side listener in this model, only the client's own process — so auto-start stays out of scope (`04_improvements.md`).
- **The alias is rewritten, never accumulated.** `write_alias` replaces the block keyed by the sandbox name under a cross-process lock, so repeated panel refreshes, forward opens, and app restarts all converge on one block.
- **A deploy or undeploy moves the sandbox** and changes the `ProxyCommand`'s `--connection` value. Any client holding the alias keeps working after the next refresh; a client holding a *copy* of the `ProxyCommand` string does not, which is why the panel's copyable command is a diagnostic aid rather than the recommended handoff.
- **Authorized keys survive stop/start, not destroy.** `/etc/ssh/authorized_keys.container` lives in the instance's writable layer, installed once at create/deploy. A recreate re-runs the install and `forget_sandbox_host_key`, so a reused name does not trip a host-key mismatch.
- **One key per sandbox, host-side only.** The private half never leaves `app_data_root`; the app hands its path to the client rather than the key material.
- **A dead client leaves its remote command running, not its `sshd`.** Killing the Windows OpenSSH client also kills its `podman` `ProxyCommand` child, so the in-container `sshd` exits within a second; a hung client is reaped by `sshd_config.container`'s `ClientAlive*` after roughly two minutes. In both cases the session's own remote processes are re-parented to PID 1 and keep running until the container stops (spike S4, `docs/features/host-tool-ssh-access/spike/s2-path.md`).

## Common Gotchas

| Gotcha | Cause | Fix |
|---|---|---|
| `sandbox_ssh_access` succeeds but the client cannot connect | The container is stopped: the `ProxyCommand` execs into it, so the failure is in the transport, not in SSH | Start the sandbox; the payload's `running` flag is what the panel must surface for exactly this case |
| The alias worked yesterday and fails after a deploy | The `ProxyCommand` embeds `--connection <machine>`; a deploy or undeploy moves the sandbox and the stale block execs against the wrong machine | Re-fetch the handoff (the command refreshes the block through `SandboxRouter::resolve`); never cache the command string |
| A client's remote agent starts but cannot find node or any installed tool | The sandbox predates image 9: `/root/.bashrc`'s `mise activate` hook resolves tools only on a shell `cd` or prompt, and sshd starts every session in `/root` | Recreate the sandbox on image 9 or later, whose `SetEnv PATH` in `sshd_config.container` puts mise's shims first (Phase B) |
| `which node` finds the shim, but running it prints `mise ERROR No version is set for shim: node` | The shims resolve a version from the directory the tool runs in, and the only mise config is `/root/work/mise.toml`; the client is working in `$HOME` | Point the client at `/root/work` as its remote folder; a global-config fallback is recorded in `04_improvements.md` |
| Tools vanish from SSH sessions after `MISE_DATA_DIR` moves | `SetEnv PATH` in `sshd_config.container` repeats the shims directory literally, since its `RUN` precedes `ENV MISE_DATA_DIR` in `src-tauri/resources/Containerfile` | Change both lines together and bump `BASE_IMAGE_VERSION` |
| Authentication fails only for one developer | `render_block` emits `IdentityFile`/`UserKnownHostsFile` unquoted, and their `app_data_root`-derived paths contain a space under a home directory like `C:\Users\John Smith` | Quote both values (Phase C), and strip the quotes in any helper that reads a value back |
| A long-idle desktop session drops silently | No `ServerAliveInterval` in the rendered block, over a path that ends in a `podman exec` pipe (nested inside an SSH connection for a deployed sandbox) | Add the keepalive directives to the `Proxied` arm (Phase C) |
| A destroyed sandbox's alias still resolves, and its key directory grows collateral | A destroy path that skips `cleanup_host_state` (`src-tauri/src/services/sandbox.rs`) leaves the block and `app_data_root/ssh-keys/<name>/` behind | Call `cleanup_host_state` from any new destroy or rollback path (Phase E) |
| The panel tells the user a deployed sandbox is stopped | `running` is `SandboxRoute::running`, which is false for any sandbox not on its provider's local machine | `SshAccessCard.svelte` checks `deploymentFor` before the payload's `running` flag; keep that order. See `04_improvements.md` |
| The panel still says "stopped" after the header's Start button | The payload is fetched, not pushed, so it stays as it was when it was fetched | The card re-fetches when the sandbox's live status or deployment host changes; keep both in the effect's dependencies |
| Adding the clipboard call throws at runtime with a permission error | Tauri 2 gates plugin commands per capability; the plugin crate and npm package alone are not enough | Add `clipboard-manager:allow-write-text` to `src-tauri/capabilities/default.json`, whose `webviews` list already covers `main-navigation-panel` |
| `tauri build` refuses to run after bumping the clipboard npm package | The Tauri CLI requires each plugin's crate and npm package to share a major/minor, and the crate's 2.4+ needs a newer `tauri` than the lockfile | Move `@tauri-apps/plugin-clipboard-manager` (pinned `~2.3.3`) and the crate together, with a `tauri` bump |
| A `light` e2e run leaves an alias block and a keypair behind | `default_backend` returns `CliBackend` under `MIO_MOCK_BACKEND=1`, so `create` writes a real alias and a real key against a scripted `podman`; `onComplete`'s `~/.ssh` cleanup runs only outside the light tier, by design | Key light-tier assertions on a run-unique alias, never on the absence of blocks; see `04_improvements.md` for the stale harness comment |
| A new sandbox shadows one of the user's own SSH hosts | The managed `Include` is prepended to `~/.ssh/config` and OpenSSH takes the first matching keyword | Avoid naming a sandbox after a real host; a namespaced alias is a recorded improvement, not a v1 change (it would move every shipped Mutagen path) |
| `Host key verification failed` on a client's first connect | The alias sets its own `UserKnownHostsFile`, so Claude Desktop verifies strictly instead of pinning on first contact, and the file was empty until another client connected | `seed_sandbox_host_keys` pins every host key read from the running container (create on microsandbox, deploy, and each panel fetch of a running sandbox); open the panel once with the sandbox running |
| `No ED25519 host key is known for [alias]:<port>` | The client's form carries a stale non-22 port, so the lookup key becomes `[alias]:<port>`, which a plain `<alias>` entry does not match | Pinned lines use `<alias>,[<alias>]:*`, which matches any port; the panel tells the user to leave the port empty, since it means nothing over a `ProxyCommand` |

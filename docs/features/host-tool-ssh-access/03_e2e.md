# Host-Tool SSH Access — E2E Test Plan

This is the end-to-end test plan for the feature specified in `docs/features/host-tool-ssh-access/02_dev.md`: the `sandbox_ssh_access` handoff command (Phase A), the non-interactive `PATH` fix in the base image (Phase B), the hardened alias block (Phase C), the "Connect from desktop apps" panel (Phase D), and alias/identity teardown at destroy (Phase E). **Every phase in `02_dev.md` is `Remaining`**, and none of Phase 0's spikes (S1–S4) has been run, so the spec below would fail at its first UI step today — see "Sequencing". Reviewed against the tree on 2026-08-17.

Unlike the revision this replaces, the spec is small: the transport it exercises already has standing coverage in `e2e/test/specs/standard/agent-web.spec.ts`, which asserts that a fresh sandbox publishes nothing, that its `Proxied` alias block carries `ProxyCommand`/`User root`/`IdentityFile`/`UserKnownHostsFile`, and that `/etc/ssh/authorized_keys.container` holds the sandbox's public key. What has never been proven is that an **off-the-shelf SSH client on the host** can use that alias.

## Goal

The test must prove the path a Claude Desktop (or VS Code Remote-SSH, or JetBrains Gateway) user actually takes:

- The panel in `src/lib/workspace/WorkspaceDashboard.svelte` (Phase D), which invokes `sandbox_ssh_access` (`src-tauri/src/commands/ssh.rs`) and displays the alias the user hands to their tool.
- `sandbox_ssh_access` resolving the route through `SandboxRouter::resolve` (`src-tauri/src/services/routing.rs`), which rewrites the managed `Host` block in `~/.ssh/sandbox-mio/config`.
- The **bundled component**: the base image's `openssh-server`, its baked `/etc/ssh/sshd_config.container`, and `/usr/local/bin/mio-sshd` (`src-tauri/resources/Containerfile`), reached with no published port and no daemon running.
- The **decisive proof**: the host's own `ssh.exe` completing a full key-based login against the alias name — alias resolution through the `Include` line in `~/.ssh/config`, the `ProxyCommand`'s `podman exec` pipe, pubkey authentication against the installed `authorized_keys.container`, and a remote command's output. Nothing weaker demonstrates the feature, because the feature *is* "an off-the-shelf SSH client reaches the sandbox".
- The **toolchain assertion**: a mise-managed tool resolvable in that non-interactive session (Phase B). A login that works into a sandbox whose toolchain is invisible is a working connection to a useless remote, and the login assertion passes either way.
- **Teardown**: the alias block and the sandbox's key directory are gone after destroy (Phase E).

A weaker test would fail to cover the parts most likely to break:

- Asserting only that `sandbox_ssh_access` returns an alias string would prove nothing about resolution, authentication, or the exec pipe.
- Asserting the block exists in `~/.ssh/sandbox-mio/config` duplicates what `agent-web.spec.ts` already asserts, and a well-formed block with an unquoted space-bearing `IdentityFile` (Phase C) still looks correct while failing to authenticate.
- Driving `podman exec <name> …` from the spec would exercise the app's own transport, not a client's: it skips the `Include`, the client's config parsing, and OpenSSH's identity handling entirely.

## Existing test styles

Two categories exist (`e2e/AGENTS.md`):

- **App-driven WebdriverIO/Mocha specs** under `e2e/test/specs/standard/`, driven through `tauri-driver`, using the `useSandboxWorkspace` fixture (`e2e/lib/sandbox-suite.ts`), page objects (`e2e/test/pageobjects/project-row.component.ts`, `workspace-dashboard.page.ts`), and out-of-band ground truth via `podman(LOCAL_CONNECTION, …)` (`e2e/lib/podman-connection.ts`), `sshAliasBlock` (`e2e/lib/ssh.ts`), and the filesystem. The preferred style.
- **Standalone spike scripts** under `docs/features/<feature>/spike/`. None exist for this feature; `02_dev.md`'s Phase 0 defines four.

The closest existing model is `agent-web.spec.ts`: it creates a sandbox with the `useSandboxWorkspace` fixture, asserts the alias block, starts the container, and then proves a real end-to-end round trip over that alias.

## Chosen approach

**Tier: standard.** A real container, the real base image, and the host's real `ssh.exe` are all required; nothing downloads a large asset or loads a model, so `heavy` is unwarranted, and the `light` tier — whose scripted `podman` cannot execute an `sshd` — could not prove the one thing the feature is for. Choosing `standard` means the run takes the host lock and serialises against every other real-infra run on the machine, which is the intended cost here: the feature's value depends on host-global `~/.ssh` state that cannot be slug-isolated per worktree.

Add **`e2e/test/specs/standard/host-tool-ssh-access.spec.ts`**. Topology: the local Podman machine only (`LOCAL_CONNECTION`, `mio-tests`), matching `agent-web.spec.ts`. The remote-deployed variant is in scope of the feature but recorded as a follow-up in `04_improvements.md`.

A **`light`-tier companion spec is worth adding** for the panel's own rendering, and it is feasible where the earlier revision assumed it was not: `default_backend` returns `CliBackend` under `MIO_MOCK_BACKEND=1`, so a light-tier `create` writes a real alias and generates a real keypair against a scripted `podman` (`02_dev.md`, Resolved Decisions). Keep that spec to the panel's own behaviour — that it renders the alias, identity path, and running-state wording the command returned — and keep it off host-global assertions, since a light run must neither depend on nor clean `~/.ssh`.

## Harness changes

1. **Page-object additions** in `e2e/test/pageobjects/workspace-dashboard.page.ts`: getters for the panel's alias and identity-path values and its refresh control, plus `async sshAlias(): Promise<string>` reading the displayed alias text (mirroring the `installedPackages`/`#portLabelSpan` text-read patterns already in the file). Exact selectors cannot be fixed until Phase D lands, which is why the spec is written last.
2. **New helper `e2e/lib/ssh-client.ts`**: `sshExec(alias, command, { identityPath })`, spawning `ssh -o BatchMode=yes -o ConnectTimeout=15 <alias> <command>` via `child_process.spawnSync` with `shell: false`, mirroring `podman()`'s shape in `e2e/lib/podman-connection.ts`, and returning `{ status, stdout, stderr }`. Three details are load-bearing: `BatchMode=yes` keeps a failed authentication from blocking the run on a prompt; **no `-F` argument**, so the invocation depends on the `Include` line in `~/.ssh/config` exactly as a third-party client that shells out to the system client does; and `identityPath` is resolved by reading the `IdentityFile` line back out of the alias block via `sshAliasBlock`, **stripping the surrounding quotes** Phase C adds, rather than reconstructing an app-data path — reading it back also asserts the block carries a usable path. Do not pass `-i` at all when the goal is to prove the alias supplies the identity; keep the option for the diagnostic case.
3. **No `known_hosts` change, and no new environment variable.** The alias pins its own `UserKnownHostsFile` under the sandbox's key directory (`app_data_root/ssh-keys/<name>/known_hosts`), which `MIO_APP_DATA_DIR` already isolates per worktree and `forget_sandbox_host_key` resets on recreate. The user's `~/.ssh/known_hosts` is never written, so `onComplete` needs no cleanup for it. `onComplete`'s existing managed-config cleanup already covers this feature's alias block, and it must stay inside the `!IS_LIGHT_RUN` gate.
4. **Confirm `ssh -V` succeeds** before trusting the login assertions. Windows 10/11 ships OpenSSH on `PATH`, but a locked-down image can have it removed; the app itself needs the host's `ssh-keygen` for `ensure_sandbox_identity` regardless, so a missing OpenSSH breaks sandbox creation long before this spec.

## Spec scenario

`host-tool-ssh-access.spec.ts`, using `useSandboxWorkspace("e2e-hostssh")` for naming and container teardown, plus `captureDiagOnFailure()` (`e2e/lib/diag.ts`).

1. **Create and start a local sandbox.** UI: `ProjectsPage.createProject(projectName)`, `row.start()`, `row.waitForRunning()`. Necessary but not sufficient — the later steps carry the proof.
2. **Open the workspace dashboard and read the handoff.** UI: `row.openWorkspace()`, `workspaceDashboard.waitForRendered(projectName)`, then `workspaceDashboard.sshAlias()`. Assertion: the displayed alias equals `projectName`, proving `sandbox_ssh_access` completed its chain and the panel rendered what it returned.
3. **Assert the managed block is well-formed and quoted.** `sshAliasBlock(projectName)` contains `ProxyCommand`, `User root`, `ServerAliveInterval`, and an `IdentityFile` whose value is double-quoted (Phase C). The quoting assertion is the only guard against a defect that reproduces solely on a host whose home directory contains a space.
4. **The decisive assertion: a real SSH login.** `sshExec(projectName, "whoami")` exits 0 with `root` on stdout. This proves alias resolution through the `Include`, the `ProxyCommand`'s exec pipe, the identity the block names, and root pubkey auth against the installed `authorized_keys.container` — the whole chain a third-party client walks.
5. **Assert the sandbox's toolchain is visible over SSH.** Install one tool through the dashboard's package manager (`workspaceDashboard.installPackage(...)`, the existing helper), then `sshExec(projectName, "node --version")` (or the installed tool's own version flag) exits 0. Standing regression for Phase B and for spike S2's risk; step 4 passes with or without it.
6. **Assert `mise` itself resolves**, `sshExec(projectName, "mise --version")` exiting 0, so a failure in step 5 can be attributed to the tool rather than to the activation mechanism.
7. **Assert the transport leaves no daemon behind.** After steps 4–6, `podman(LOCAL_CONNECTION, ["exec", projectName, "pgrep", "-a", "sshd"])` reports no *running* `sshd`: each connection's `sshd -i` exits with its session. Guards the graceful-teardown property recorded in `docs/features/podman-exec-transport/02_dev.md`, Phase F, against a regression that would accumulate one process per connection.
8. **Assert a stopped sandbox fails fast rather than hanging.** UI: `row.stop()`, `row.waitForStopped()`. Then `sshExec(projectName, "whoami")` exits non-zero within the helper's timeout. Proves the documented precondition behaves as a clean failure — the case a user hits most often, and the one `BatchMode`/`ConnectTimeout` exist to keep from hanging the suite.
9. **Restart and reconnect.** `row.start()`, `row.waitForRunning()`, then `sshExec(projectName, "whoami")` succeeds again — the container's host key is baked and unchanged, so no host-key churn should appear across a stop/start.
10. **Destroy and assert teardown.** UI: `row.destroy()`. Assertions: `sshAliasBlock(projectName)` is `undefined`, and `app_data_root/ssh-keys/<projectName>/` no longer exists (derive the root from `APP_DATA_ROOT` in `e2e/lib/run-identity.ts`, never from `%APPDATA%`). Both prove Phase E, and both are worded as "removed during this run" — the sandbox name is timestamped by `useSandboxWorkspace`, so the block and directory provably belonged to this run.

## De-risking spike results

No spike has been run for this feature. Transport-level risks were already cleared by `docs/features/podman-exec-transport/02_dev.md` (Phases A and F, 2026-08-10): the pubkey handshake through `podman exec`, `scp`/sftp over the same pipe, three concurrent sessions, and zero running `sshd` after a graceful close. Their bearing on this spec:

- **S1 (a third-party client resolving an `Include`d `ProxyCommand` alias)** — *cannot be fully covered by this spec*. Step 4 drives the system `ssh` client, which definitively supports both `Include` and `ProxyCommand`, so it proves the alias is well-formed and usable and covers every client that shells out to the system client. A client with its own config parser is a different implementation; only a manual session against the actual desktop app closes that, and it should happen before Phase D's copy commits to presenting the alias as the primary handoff.
- **S2 (mise tools on `PATH` non-interactively)** — *feature concern*. Steps 5 and 6 are its standing regression. If S2 is unresolved, those two steps fail while step 4 passes, which is the correct signal rather than a blocker for the rest of the spec.
- **S3 (a client's own remote bootstrap inside the container)** — *out of this spec's reach*: it installs a third-party agent over the sandbox's egress. Manual verification only.
- **S4 (session durability)** — partially covered: step 7 covers process hygiene on graceful close, step 8 covers a stopped container. Idle-timeout survival and abrupt-client-death orphans stay manual, since both need wall-clock waits or a killed client the suite has no reason to model.

**Dominant blocker: the feature is unimplemented.** There is no panel and no `sandbox_ssh_access` command, so the spec fails at step 2. A spec that goes red at a known blocker is not worth writing yet.

## Sequencing

1. Run Phase 0's spikes by hand against `mio-tests` — S1 first, since its outcome decides what Phase D presents and whether the alias-handoff model holds at all. Record scripts and output under `docs/features/host-tool-ssh-access/spike/`.
2. Implement `02_dev.md` Phases A–C. After Phase A there is a command to drive, but no UI surface.
3. Implement Phase D (the panel) and Phase E (teardown), then the page-object additions (harness change 1) and `e2e/lib/ssh-client.ts` (harness change 2).
4. Write `host-tool-ssh-access.spec.ts` last, and the `light` companion spec alongside it. This matches `agent-web.spec.ts`'s precedent: the spec is the final artifact, written once the path it drives exists.

## Environment notes

State a future session needs:

- **Machine.** `mio-tests` (`LOCAL_CONNECTION`) only; no remote machine for this spec's scope.
- **Base image.** Must be rebuilt under Phase B's bumped `BASE_IMAGE_VERSION` for steps 5 and 6; steps 1–4 and 7–10 pass on image 6 as well, since the transport is unchanged.
- **Ports.** None. An exec-capable sandbox publishes nothing and no forward is involved — the spec must never look for a host port.
- **Keys.** The per-sandbox keypair lives at `app_data_root/ssh-keys/<name>/id_ed25519`, isolated per worktree by `MIO_APP_DATA_DIR` (`APP_DATA_ROOT`, `e2e/lib/run-identity.ts`). Resolve the path from the alias block's quote-stripped `IdentityFile` line, not from an assumed location.
- **`known_hosts`.** Per sandbox, beside the identity; the user's own file is untouched. No cleanup needed.
- **Managed SSH config.** `~/.ssh/sandbox-mio/config` plus the `Include` line, both host-global, both cleaned by `onComplete` inside the `!IS_LIGHT_RUN` gate. Every assertion keys on the timestamped sandbox name.
- **Workspace path.** `SANDBOX_WORKSPACE_ROOT/<projectName>`, unchanged from every other standard-tier spec.
- **System `ssh` client on `PATH`.** Required by the spec; `ssh-keygen` is already required by the app's own `create`.

## Common Gotchas

| Gotcha | Cause | Fix |
|---|---|---|
| Step 4 hangs instead of failing | `BatchMode=yes` was omitted, so a failed key auth fell back to an interactive prompt and blocked the WebdriverIO run | Always pass `-o BatchMode=yes -o ConnectTimeout=15` in `e2e/lib/ssh-client.ts` |
| Step 4 fails with the connection closed by a remote port that does not exist | The `ProxyCommand` failed, not SSH: the container is stopped, or an argument was rewritten by an MSYS-derived shell | Confirm the container is running; run the block's `ProxyCommand` by hand from `cmd.exe`, and see `docs/features/podman-exec-transport/02_dev.md`, Resolved Decision 5 |
| Step 4 passes locally but fails on another developer's machine | `IdentityFile`'s value is unquoted and that home directory contains a space | Phase C quotes the value; step 3 asserts it, and the helper must strip the quotes when reading it back |
| The helper works only when run from Git Bash | Git Bash's `PATH` and path conversion mask exactly the failures a real desktop client hits | Spawn with `shell: false` from the Node process, and run any manual reproduction from `cmd.exe` or PowerShell |
| Step 5 fails while step 4 passes | Expected before Phase B: the session is non-interactive and mise's activation hook needs a prompt | Implement Phase B and rebuild the base image; step 6 separates an activation failure from a per-tool one |
| Step 7 finds a running `sshd` | Either a client session was killed abruptly rather than closed, or the transport regressed to a long-lived daemon | Compare against `docs/features/podman-exec-transport/02_dev.md`, Phase F; a bounded count of *defunct* entries is expected and not a failure |
| Step 10's alias assertion fails intermittently | The spec asserted on the absence of *any* managed block, and a concurrent worktree's light run had written one | Assert only that the block for this run's timestamped sandbox name is gone |
| A light-tier companion spec fails after a standard run | The light spec asserted on `~/.ssh` state, which `onComplete` cleans outside the light tier only | Keep the light spec to the panel's rendering of the command payload; host-global assertions belong to `standard` |
| Every standard spec starts failing after Phase B | The `BASE_IMAGE_VERSION` bump makes existing sandboxes and the cached image stale for the whole suite | Expected: the harness rebuilds the image in `onPrepare`; re-run the full `standard` tier after the bump, per `02_dev.md`, Phase F |

# Host-Tool SSH Access to Sandboxes

This document is the ideation for letting host-machine tools that speak SSH attach to a sandbox as if it were an ordinary remote Linux box, while all execution and state stay inside the container. The flagship case is the Claude Code desktop app's built-in "Add SSH connection" remote-session feature; the same mechanism generalises to any `~/.ssh/config`-aware tool (VS Code Remote-SSH, JetBrains Gateway). Nothing of this feature is implemented, but the transport it needs already ships: `docs/features/podman-exec-transport/02_dev.md` (complete) put an OpenSSH server inside the base image, gave every sandbox its own keypair and its own `Host` alias in the app-managed OpenSSH config, and proved a full pubkey handshake through `podman exec`; `docs/features/microsandbox-provider/02_dev.md` extended the identical alias shape to `msb`-backed sandboxes. What is missing is entirely on top of that: no surface tells a user the alias exists, nothing has verified that a third-party SSH client can resolve it, and a non-interactive SSH session cannot see the sandbox's mise-managed toolchain. Relevant files: `src-tauri/resources/Containerfile`, `src-tauri/src/ssh/mod.rs` and `types.rs`, `src-tauri/src/backends/mod.rs`, `src-tauri/src/services/routing.rs`, `src/lib/workspace/WorkspaceDashboard.svelte`.

Earlier revisions of this document (and of `02_dev.md`) designed a *second*, independent SSH path: `--publish 127.0.0.1::22`, a `ServiceKind::Ssh` Mutagen forward, an app-scoped keypair, and a `sandbox-mio-ssh-<name>` alias. The exec transport superseded all of it. `02_dev.md`'s "Superseded plan" section records what was dropped and why, so a future session does not rebuild it.

## Current State

An in-container SSH server, a per-sandbox identity, and a per-sandbox `Host` alias all exist today — built for Mutagen, not for the user:

- `src-tauri/resources/Containerfile` installs `openssh-server`, bakes `/etc/ssh/sshd_config.container` (`AuthorizedKeysFile /etc/ssh/authorized_keys.container`, `PasswordAuthentication no`, `PubkeyAuthentication yes`, `StrictModes no`, `UsePAM no`, `Subsystem sftp`), generates host keys at build time, and bakes `/usr/local/bin/mio-sshd` — a launcher that creates `/run/sshd` (lost on every container start, since `/run` is tmpfs) and then executes `sshd -i` against that config. Nothing runs as a daemon: one `sshd` process is spawned per inbound connection by the exec pipe, inetd-style.
- `CliBackend::create`/`deploy` (`src-tauri/src/backends/mod.rs`) call `ensure_sandbox_identity` (an ed25519 keypair under `crate::paths::app_data_root(app)/ssh-keys/<name>/`, generated by shelling out to the host's `ssh-keygen`), `forget_sandbox_host_key`, `install_sandbox_key` (the public half `podman cp`'d to `/etc/ssh/authorized_keys.container`), and then `ensure_sandbox_alias` or `ensure_msb_sandbox_alias`.
- `SshAlias::Proxied` (`src-tauri/src/ssh/types.rs`) renders, via `render_block` (`src-tauri/src/ssh/mod.rs`), a `Host <sandbox name>` block carrying `ProxyCommand`, `User root`, `IdentityFile`, `UserKnownHostsFile`, `IdentitiesOnly yes`, and `StrictHostKeyChecking accept-new`. The `ProxyCommand` is `<quoted bundled podman.exe> --connection <c> exec -i <name> mio-sshd` for Podman and `msb exec --stream <name> -- mio-sshd` for microsandbox; both reference `mio-sshd` by bare name so no argument has a POSIX-path shape for an MSYS-derived shell to rewrite (`docs/features/podman-exec-transport/02_dev.md`, Resolved Decision 5).
- `write_alias` and `remove_alias` (`src-tauri/src/ssh/mod.rs`) run their read-modify-write under both an in-process mutex and a cross-process file lock, and `write_alias` prepends `Include sandbox-mio/config` to `~/.ssh/config` exactly once. `remove_alias` still has no caller and carries `#[allow(dead_code)]`.
- `SandboxRouter` (`src-tauri/src/services/routing.rs`) is the one seam that answers "which alias reaches this sandbox": `locate` reports the machine, the `exec_capable` flag (`Sandbox::supports_exec_transport`, true for every microsandbox sandbox and for any Podman sandbox whose `image_version` is at least `EXEC_TRANSPORT_MIN_IMAGE_VERSION = 6`), and the `forward_alias`; `resolve` additionally rewrites the managed block, because that file is not guaranteed to survive between app runs while the container is.
- An exec-capable sandbox publishes **no** container ports at all, and `ServiceKind` (`src-tauri/src/network/types.rs`) still has only `Terminal`, `AgentWeb`, and `Exposed(port)`. Terminal, agent-web, and user-exposed ports are all Mutagen forwards *over* the alias.
- Nothing in `src/` displays the alias, the identity path, or the `ProxyCommand`. The per-sandbox surface is `src/lib/workspace/WorkspaceDashboard.svelte`, which renders `PackageManager`, `AgentManager`, and `PortsManager` (`src/routes/projects/`); `SandboxItem.svelte` is a compact row with lifecycle buttons only and no longer carries a Terminal button. No copy-to-clipboard helper exists anywhere in the frontend, and no clipboard plugin is declared in `package.json`, `src-tauri/Cargo.toml`, or `src-tauri/capabilities/default.json`.
- mise is activated only for interactive shells: the image writes a single `eval "$(mise activate bash)"` into `/root/.bashrc`, and `mise activate` installs a `PROMPT_COMMAND` hook that a prompt-less session never runs. `zellij` is on the system `PATH` only because the image symlinks it into `/usr/local/bin`.
- `e2e/test/specs/standard/agent-web.spec.ts` already asserts, as a standing regression, that a fresh sandbox publishes nothing, that its `Proxied` block carries all four load-bearing keywords, and that `/etc/ssh/authorized_keys.container` holds the sandbox's public key. `e2e/lib/ssh.ts` exposes `sshAliasBlock(alias)` for reading the managed block back.
- Desk research (2026-07-14) on the Claude Code desktop app: its environment picker offers "+ Add SSH connection", accepting an `SSH Host` (a bare `user@host` **or** a `Host` alias defined in `~/.ssh/config`, resolved the way `ssh -G <alias>` would), an optional port, and an optional identity file; on first connect it installs its own Claude Code copy on the remote, with no manual server bootstrap; Linux/macOS remotes only, which the Debian-based sandbox satisfies. Managed settings carry `sshHostAllowlist`/`sshConfigs` keys, relevant only to a future enterprise rollout.

## Proposed model

### Hand the user the alias the exec transport already writes (`src-tauri/src/services/routing.rs`)

No new transport, no new alias class, no new keypair. The alias a host tool should use is exactly the one Mutagen already uses: `Host <sandbox name>` in `~/.ssh/sandbox-mio/config`, included from `~/.ssh/config`. `SandboxRouter::resolve` is the call that guarantees the block is present and current, and it is already the call every forward-opening command makes.

### A read-and-refresh command, not an enable/disable toggle (new `src-tauri/src/commands/ssh.rs`)

Because nothing has to be started, provisioned, or torn down per sandbox, "SSH access" has no on/off state to persist. One command — `sandbox_ssh_access(name)` — calls `SandboxRouter::resolve` (refreshing the managed block, whose `ProxyCommand` encodes the machine the sandbox currently runs on and therefore changes across deploy/undeploy), reads the sandbox's status through `SandboxBackend::list`, and returns the handoff payload: alias name, identity path, pinned `known_hosts` path, the literal `ProxyCommand`, the `exec_capable` flag, and whether the container is running. No `.mio` record, no startup restore.

### Non-interactive `PATH` for the mise toolchain (`src-tauri/resources/Containerfile`)

A host tool's remote agent runs as `ssh <alias> <command>` — non-interactive, so mise's prompt-driven hook never fires and the sandbox's node/python/etc. are invisible. The fix belongs in the image's `/root/.bashrc`, which bash *does* read for a remote command: activate with mise's shims mechanism for a non-interactive shell and keep today's `mise activate bash` for interactive panes. Requires a `BASE_IMAGE_VERSION` bump, and only for sandboxes created after it.

### Keepalives on the `Proxied` block (`src-tauri/src/ssh/mod.rs`)

A desktop-app session is long-lived and mostly idle, and it traverses a `podman exec` pipe (for a deployed sandbox, one nested inside an SSH connection to the remote machine). `render_block` sets no `ServerAliveInterval` today.

### A "Connect from desktop apps" panel (`src/lib/workspace/WorkspaceDashboard.svelte`)

A new section, sibling to `PortsManager`, showing the alias name plus the individual values a client may need, each copyable, with an explicit note that the container must be running. For a sandbox that is not exec-capable the section explains that recreating the sandbox on the current base image is the prerequisite, rather than offering a handoff that would silently land on the Podman machine instead of the container.

### Alias and identity teardown at destroy (`src-tauri/src/services/sandbox.rs`)

Once the alias is a documented user-facing handle, a destroyed sandbox leaving a resolvable-but-dead alias behind stops being harmless bookkeeping. `destroy` gains `crate::ssh::remove_alias(name)` — its first caller — and removal of `app_data_root(app)/ssh-keys/<name>/`.

## Technology choices with tradeoffs

### Transport: the shipped `ProxyCommand` alias (chosen) vs publishing container port 22 vs Tailscale

Chosen: reuse `SshAlias::Proxied`. It needs no host port (so it stays per-worktree isolatable, `e2e/AGENTS.md`), works unchanged for a locally-created sandbox, a remote-deployed one, and a microsandbox one, and is already proven end to end by Mutagen's own sync and forward sessions plus `agent-web.spec.ts`.

- **Publish `127.0.0.1::22` and tunnel it with a Mutagen forward** — the model earlier revisions of this document proposed. Rejected because it is now strictly worse in every dimension: exec-capable sandboxes publish nothing, so it would reintroduce the publish path this project deliberately left behind, claim a host port that moves on every allocation, and add a second authentication and host-key story alongside the one that already works. Its only advantage is that `HostName`/`Port` are expressible in a client's form fields, which matters solely if a client cannot resolve an alias at all — see the cost below.
- **Route through Tailscale** (`docs/features/tailscale-access/01_ideas.md`) — rejected as the default: it needs a tailnet credential and a node-join step to reach an endpoint that terminates on the same laptop. Tailscale remains the right mechanism for reaching a sandbox from a *second* device.

The real cost of the chosen option: `ProxyCommand` is expressible only in an SSH config file, never in a client's `HostName`/`Port`/`User`/`IdentityFile` form. If a client parses SSH config with its own parser (where `Include` support is commonly absent) or refuses `ProxyCommand`, there is **no fallback within this model** — which is why the client-resolution question below is the feature's one gating unknown rather than a detail.

### Alias identity: reuse the sandbox-named alias (chosen) vs a second, namespaced alias class

Chosen: the user pastes the sandbox name. One block per sandbox, one identity, one pinned `known_hosts`, and every existing consumer (Mutagen sync, forwards, `agent-web.spec.ts`) keeps working untouched.

- **A separate `sandbox-mio-ssh-<name>` block for host tools** — rejected: two blocks pointing at the same container would drift (the `ProxyCommand`'s `--connection` value changes on deploy), and the second would need its own refresh path for no functional gain.

The cost is a namespace collision: because `write_alias` prepends its `Include` at the top of `~/.ssh/config` and OpenSSH takes the first matching keyword, a sandbox named after a host the user already has an entry for shadows that entry for every SSH client on the machine. `validate_name` (`src-tauri/src/backends/mod.rs`) does not reserve names, and renaming the alias would break the shipped Mutagen paths, so this stays a documented gotcha with a namespaced-alias migration recorded in `04_improvements.md`.

### Container-side host key: keep the image-baked key (chosen) vs per-instance generation

Chosen: leave `docs/features/podman-exec-transport/02_dev.md`'s decision alone. Every container from one image presents the same host key, and the alias pins its own `UserKnownHostsFile` under the sandbox's key directory, dropped by `forget_sandbox_host_key` whenever a fresh container takes a reused name.

- **Per-instance `ssh-keygen -A` at first connect** (an earlier revision's plan) — rejected: it re-adds a runtime provisioning step to a path that currently has none, and the threat it defends against does not exist here. There is no network path to intercept — the transport is a `podman exec`/`msb exec` pipe on the same machine, or one nested inside an already-authenticated SSH connection to the deploy host — so a shared host key cannot be used to impersonate a sandbox to a client that reaches it only through that pipe.

### Authorized key: the app-managed per-sandbox identity (chosen) vs authorizing the user's own key

Chosen: hand the tool the identity the app already generated. Claude Desktop, VS Code Remote-SSH, and JetBrains Gateway all accept an explicit identity file, and the alias supplies one, so nothing needs to change.

- **Append the user's own public key to `/etc/ssh/authorized_keys.container`** — rejected for v1: `install_sandbox_key` writes that file by `podman cp`, which replaces it wholesale, so supporting a second key means an append-and-dedup step and a new "which key" setting for a case no reported workflow needs yet. Recorded in `04_improvements.md`.

### Non-interactive toolchain: shims in `/root/.bashrc` (chosen) vs a profile drop-in vs per-call `mise exec`

Chosen: branch in `/root/.bashrc` on shell interactivity and use mise's shims mechanism for the non-interactive case. Bash reads `~/.bashrc` for `ssh host command` through its remote-shell special case, and the image already replaces Debian's stock file (including its non-interactive early return), so the file is the one hook that a remote command reliably reaches.

- **A `/etc/profile.d` entry** — rejected outright: a non-interactive, non-login shell reads neither profile nor login files.
- **Leaving it to the client** (each tool prefixing `mise exec`) — rejected: the tools this feature exists to host spawn their own subprocesses and cannot be told to wrap them.
- **Symlinking each shim into `/usr/local/bin`**, the way the image handles `zellij` — rejected as the primary mechanism: shims are created per tool at install time, so a build-time symlink pass cannot cover tools the user installs later.

## Validation

The transport half is validated; the host-tool half is not. Evidence already recorded in `docs/features/podman-exec-transport/02_dev.md` (Phases A and F, spiked 2026-08-10 against real Podman):

- A full pubkey-authenticated OpenSSH handshake completes through `podman exec` and runs remote commands; `scp` works too, once the transport tunnels to the image's own `sshd` with its `Subsystem sftp` line (the microsandbox path proves the negative case: `msb ssh serve` drops the sftp subsystem and breaks `scp`).
- Three simultaneous sessions against one container are independent, with no serialization or instability.
- A graceful client disconnect leaves zero running `sshd` in the container; the defunct count stays bounded. An **abrupt** client kill of a bare forwarding session does leave one in-container `sshd` alive until the container stops, because `sshd_config.container` sets no `ClientAliveInterval`.
- Outbound egress (DNS, HTTPS, a real `mise install`) works with no published ports and plain `--network pasta`.

Unconfirmed, carried into `02_dev.md` as gating spikes:

- Whether a third-party client resolves a `Host` alias that lives in an `Include`d file **and** honours its `ProxyCommand`. This is the single assumption the flagship use case rests on, and the chosen model has no field-based fallback if it fails.
- Whether mise-managed tools appear on `PATH` in a non-interactive SSH session, and whether the shims fix carries into whatever shell a client's remote agent uses.
- Whether a client's own remote bootstrap (Claude Desktop's auto-installed CLI, VS Code Server, JetBrains' backend) completes inside the container — it downloads its own runtime over the sandbox's egress and writes under `/root`, neither of which any existing path exercises.
- Whether a long-idle third-party session survives without keepalives, and what a container stopped mid-session does to the client.

## Open Questions

Each question below is resolved in `02_dev.md`'s "Resolved Decisions"; that document, not this one, is the record of what was settled.

- **Does a third-party client resolve an `Include`d `ProxyCommand` alias, and what is the fallback if not?** Candidate fallbacks all cost something: writing the block into `~/.ssh/config` directly (touches a file the app currently only appends one line to), asking the user to paste a block into their own config (manual, but honest), or reviving the publish-plus-forward model for host tools only (a second transport to maintain).
- **Is the surface a toggle or a read-only panel?** Nothing needs starting per sandbox, so a toggle would be decorative state; but users may expect an explicit "enable" step for something described as remote access.
- **Where does the panel live** — a section in `WorkspaceDashboard.svelte` beside `PortsManager`, or a row in the compact `SandboxItem.svelte` list?
- **How is a value copied to the clipboard**, given no clipboard mechanism exists in the frontend today: add `@tauri-apps/plugin-clipboard-manager` (a new plugin plus a capability entry in `src-tauri/capabilities/default.json`), call `navigator.clipboard` directly (untried anywhere in this app), or settle for a selectable read-only field?
- **Is the user's own public key authorized alongside the app's?**
- **Do alias and key material get cleaned up on destroy**, and does `remove_alias` finally get a caller?
- **Which host tools are explicitly validated and documented** — only Claude Desktop, or VS Code Remote-SSH and JetBrains Gateway too?
- **Credential handoff to a client's auto-installed agent**: whether the host credential store (`docs/features/shared-agent-auth/01_ideas.md`) should inject into wherever that copy keeps its credentials, so the user is not asked to log in a second time inside the SSH session.

## Common Gotchas

| Gotcha | Cause | Fix |
|---|---|---|
| A client cannot see the alias at all | The alias lives in `~/.ssh/sandbox-mio/config`, reachable only through the `Include` line `write_alias` prepends; a client parsing SSH config with its own parser commonly omits `Include` | Run `02_dev.md`'s spike S1 before building on alias handoff; the fallbacks it decides between are listed under Open Questions |
| The alias resolves but the client reports the connection closed immediately | The `ProxyCommand` is failing, not the SSH protocol: the container is stopped, or the client's shell rewrote an argument. `mio-sshd` is referenced by bare name for exactly that reason (`docs/features/podman-exec-transport/02_dev.md`, Resolved Decision 5) | Start the sandbox, then run the alias's `ProxyCommand` by hand from `cmd.exe`; `podman exec <name> /usr/sbin/sshd -t -f /etc/ssh/sshd_config.container` names a config fault that the client's error never does |
| A sandbox created before base image 6 cannot be reached this way | `Sandbox::supports_exec_transport` is false for it, so its alias is the shared Podman *connection* alias and a login lands on the Podman machine, not the container | Recreate the sandbox on the current base image; the panel must state the prerequisite rather than offer a handoff that silently reaches the wrong host |
| A remote agent inside the SSH session cannot find node, python, or any installed tool | mise is activated only for interactive shells in `/root/.bashrc`, and its `PROMPT_COMMAND` hook never fires without a prompt | Activate with mise's shims mechanism for non-interactive shells (`02_dev.md`, Phase B); a `/etc/profile.d` entry cannot work here |
| The alias stops working after a deploy or undeploy | The `ProxyCommand` embeds `--connection <machine>`, which changes when the sandbox moves | Re-read the handoff (the command refreshes the block on every call via `SandboxRouter::resolve`) rather than caching what the panel showed earlier |
| An SSH client on the machine suddenly resolves a well-known host to a sandbox | The managed `Include` sits at the top of `~/.ssh/config` and OpenSSH takes the first matching keyword, so a sandbox named after one of the user's own hosts shadows it | Do not name a sandbox after a real SSH host; a namespaced alias is recorded in `04_improvements.md` |
| An in-container `sshd` lingers after the desktop app is killed | An abrupt client death is not propagated through the exec pipe, and `sshd_config.container` sets no `ClientAliveInterval` (`docs/features/podman-exec-transport/02_dev.md`, Phase F) | Harmless until the container stops; stop/start the sandbox to clear it, and see `04_improvements.md` for the supervision option |
| A destroyed sandbox's alias still resolves | `remove_alias` has no caller and `destroy` leaves `app_data_root/ssh-keys/<name>/` in place | Wire teardown into `services::sandbox::destroy` (`02_dev.md`, Phase E) |

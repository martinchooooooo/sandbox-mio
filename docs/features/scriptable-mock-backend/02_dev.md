# Scriptable Mock Backend Build Plan

This document is the build plan for the scriptable-mock-backend feature, continuing `docs/features/scriptable-mock-backend/01_ideas.md`. **This revision supersedes the previous one.** The previous revision scripted behaviour at the subsystem-trait level (`MockDirector` overrides consulted inside hand-written `MockBackend`/`MockSync`/`MockMachineManager` structs that never ran the real `PodmanCliBackend`/`MutagenCli`/`PodmanMachineManager` orchestration code). That design was partially implemented (its Phase B) and is now judged the wrong seam: it structurally cannot exercise the real Rust logic — workspace resolution, image-exists-then-build branching, deploy's stop/create/start sequencing, JSON parsing — because the mock is a parallel reimplementation, not the real code under test. See "Superseded: the trait-level design" below for exactly what that entails discarding.

The new seam is one level down: script the external **process** each subsystem shells out to (`podman`, the bundled Mutagen sidecar), and let the real subsystem structs run unmodified against a scripted process layer. **Verification for this feature is end-to-end only** — every phase below is proven through `pnpm run test:light` webview specs driving the real Tauri commands, never through standalone Rust `#[test]` fns. This was a deliberate correction during Phase B of this revision: an earlier draft of this plan included a pure-function unit-test tier and per-phase Rust-level integration tests; both were cut before implementation, because unit tests were explicitly out of scope for this feature — the point of moving the seam is to make the *real* orchestration logic observable end-to-end, not to add another layer of Rust-only test surface. `cargo check`/`cargo test` still gate compilation as usual (root `AGENTS.md` Verification Commands), but no new `#[test]` fns are written as part of this feature.

Status: all phases (A–E) are implemented. Each phase section below records what shipped, including where implementation diverged from what this document originally specified.

## The Concrete Model

### One seam, one verification surface

Two things exist, not three: the `ProcessRunner` seam beneath each subsystem's real struct, and the e2e `light` tier as the sole place that exercises it. There is no separate Rust-level test tier — a scenario worth proving is a scenario worth writing as a light spec, which has the added benefit of proving the IPC round-trip and (where relevant) the frontend rendering in the same assertion, not just the Rust logic in isolation.

### `ProcessRunner`: the seam

```rust
#[async_trait::async_trait]
pub trait ProcessRunner: Send + Sync {
    /// Runs one external-tool invocation and returns its raw output. `args` excludes the binary
    /// name; args[0] is the CLI subcommand (`"create"`, `"machine"`, `"sync"`, ...).
    async fn run(&self, args: &[&str]) -> std::io::Result<std::process::Output>;
}
```

One runner per external tool, not one generic program-agnostic runner:

- **`PodmanProcessRunner`** — backs every `podman` invocation. `podman` is shelled out to by four of the five subsystems (`backends`, `machine`, `runtime`, `network`) through the shared `podman_command()` helper in `src-tauri/src/backends/mod.rs` (network's `podman()` helper bypasses `podman_command()` today and calls `Command::new("podman")` directly — pre-existing inconsistency, not introduced by this feature, noted in Phase B). One shared runner instance means a single scripted `podman.*` override affects every subsystem that shells to `podman`, matching production reality (one binary, one failure surface) — see the trade-off called out under "Decision: shared runner, CLI-shaped keys" below.
- **`MutagenProcessRunner`** — backs the bundled Mutagen sidecar, invoked through `tauri_plugin_shell`'s `Command` (a different type from `tokio::process::Command`; see Phase C) in `src-tauri/src/sync/mod.rs`. Kept separate from `PodmanProcessRunner` because the real implementation's plumbing (`command()`/`data_dir()` in `sync/mod.rs`) is structurally different, not because the abstraction couldn't unify them.

Real implementations (`SystemPodmanRunner`, `SystemMutagenRunner`) wrap the existing `podman_command()`/sidecar-`command()` construction and call `.output().await`, preserving today's env vars (`CONTAINERS_HELPER_BINARY_DIR`, `MUTAGEN_DATA_DIRECTORY`) and `no_window()` behaviour byte-for-byte. Mock implementations (`ScriptedPodmanRunner`, `ScriptedMutagenRunner`) consult the `MockDirector` (kept, redesigned — see below) and return a canned `Output` instead of spawning anything.

**Scope limit**: `ProcessRunner::run` returns one `Output` for one completed invocation. It does not cover `spawn()`-and-stream calls (`listen_events`'s piped `podman events` child, `activate_podman_socket`'s backgrounded-and-killed child) or synchronous/`spawn_blocking` calls to a different binary (`ssh-keygen`, `wsl`). Those stay unscripted in this feature and are recorded in `04_improvements.md`.

### Key matching strategy: CLI-shaped, not method-shaped

Override keys move from `<subsystem>.<method>` (e.g. `sync.status`) to `<binary>.<subcommand>` (e.g. `podman.create`, `podman.machine-start`, `mutagen.sync-list`), because the seam is now "which CLI call happened," not "which trait method was invoked." Matching strips a leading `--connection <name>` pair (present on most `backends`/`runtime` calls, absent on `machine`'s calls), then joins the remaining leading non-flag tokens with `-` up to the point subcommands stop nesting: `["ps", "--all", "--format", "json"]` → `podman.ps`; `["machine", "list", "--format", "json"]` → `podman.machine-list`; `["system", "connection", "list", "--format", "json"]` → `podman.system-connection-list`; `["image", "exists", image]` → `podman.image-exists`. A `KNOWN_CALLS` table (replacing the old `KNOWN_KEYS`) in `src-tauri/src/mockctl/mod.rs` lists every scriptable key; `mock_configure` rejects a key absent from that table, same as before. Its well-formedness (every key has a `.`, every subsystem prefix is recognized) is proven by a light spec that scripts each `KNOWN_CALLS` entry once and asserts `mock_configure` accepts it — not a Rust unit test (see "One seam, one verification surface" above).

**Known imprecision, documented not solved**: `SyncEngine::status(name)` and `SyncEngine::sessions()` both shell out to `sync list --template={{json .}}` — `status` appends a trailing `name` positional, `sessions` does not. Both collapse to the same key `mutagen.sync-list`; a script installed against that key answers both calls identically regardless of the trailing filter. A spec that needs `status` and `sessions` to disagree cannot express that in v1 — recorded as a Phase C limitation, not blocking.

### Behaviour: same shape, different payload

The `Behaviour` enum keeps its four variants and their semantics from the previous revision — fail-once, fail-always, return-value, return-sequence — because that vocabulary was never the problem, only its payload type was. The payload for a return-value/return-sequence behaviour is now the process's raw text output (`{ stdout: String, exit_code: i32 }`, `stderr` defaulted empty since every scriptable call here reads stdout on success) rather than a typed Rust value deserialized via `serde`. This is strictly simpler than before: `KNOWN_CALLS` validators no longer need a per-key `Deserialize` target, since the payload is just text the real subsystem code will parse itself (or not, for calls that don't return JSON). A fail-once/fail-always behaviour supplies `{ exit_code: i32 (non-zero), stderr: String }`, since every `check()` function across the five subsystems reads stderr on non-zero exit.

### Decision: the light tier runs the real structs

The previous revision's Phase C/D (e2e helper + first scripted specs) is rewritten, not just carried forward, because of an open question that must be settled now rather than deferred: does the e2e `light` tier run against the real `PodmanCliBackend`/`MutagenCli`/`PodmanMachineManager` with a scripted `ProcessRunner`, or does it keep a separate, cheaper UI-shortcut mock for scenarios that only care about rendering?

**Decision: the light tier runs the real structs, full stop — no parallel shortcut layer, and no parallel Rust-test layer either.** Reasons:

- A second mock layer (or a second *test* layer) recreates exactly the maintenance problem this rewrite exists to fix: two systems to keep in sync drift from each other the same way `MockBackend` drifted from `PodmanCliBackend`.
- The real structs are cheap to run — they are Rust function calls plus a scripted process response, not an actual `podman` invocation. There is no latency or flakiness reason to bypass them for "just UI" scenarios, and no reason to duplicate coverage in a Rust-only test when the same scenario is provable end-to-end for roughly the same cost.
- Stateful scenarios ("a sandbox already exists and is deployed") fall out for free: `MockBackend`'s hand-maintained `Vec<Sandbox>` is gone; state is now whatever `PodmanCliBackend::create`/`list`/`start` naturally produce when their scripted `podman.create`/`podman.ps` calls report it. Seeding a scenario means scripting the process response that would make the real code believe that state exists (e.g. script `podman.ps` to return a fabricated container line), not writing to a separate in-memory store.

This does introduce two real side effects the old design never had, both already handled by existing infrastructure and called out explicitly so a future agent does not "fix" them as bugs:

- `PodmanCliBackend::create` really writes a directory via `std::fs::create_dir_all` under `workspace_root()` (`src-tauri/src/backends/mod.rs`). `e2e/wdio.conf.ts` already sets `SANDBOX_WORKSPACE_ROOT` to a scratch directory unconditionally (line 25), so this lands in a disposable location today with no change needed — but `mock_reset` does not clean up directories already created by prior calls, and a future spec that asserts on `workspace_root()`'s contents must account for cross-spec accumulation within a session.
- `MutagenCli::command()` really calls `data_dir(app)`, which creates a `mutagen` subdirectory under the app's real data dir (`src-tauri/src/sync/mod.rs`). Harmless (empty directory, no daemon spawned since the sidecar's `.output()` call is what gets scripted, not the directory setup before it), but real disk I/O that the previous revision's `MockSync` never performed.

### The `mockctl` module: redesigned, not renamed

`src-tauri/src/mockctl/mod.rs` keeps its name and its role (runtime control plane for `MIO_MOCK_BACKEND=1`) but its internals change:

- `MockDirector`: same struct shape (mutex-guarded map, `configure`/`consult`/`reset`), now storing `<binary>.<subcommand>` keys instead of `<subsystem>.<method>` keys.
- `Behaviour`: same four variants, text/exit-code payload instead of typed JSON (see above).
- `KNOWN_CALLS` replaces `KNOWN_KEYS`: same validate-at-configure-time role, validators now check "well-formed key + exit-code sign consistency" instead of "deserializes into type T."
- `resolve()` (the previous revision's generic outcome-to-`Result<T, E>` helper) goes away — a `ProcessRunner`'s `consult`-then-return path returns `std::process::Output` directly, and the calling subsystem's own `check()` function (already present in every subsystem module) turns that into the subsystem's real error type exactly as it does for a genuine process failure. This is a second simplification the old design didn't have: scripted failures now flow through the *same* `check()` code path as real failures, rather than needing a `mockctl::backend_error`/`mockctl::sync_error` constructor to fake an "as if IPC-serialized" error.
- **No `#[cfg(test)] mod tests` in this file.** The previous revision's `mockctl` unit tests (key validation, fail-once consumption, reset) are not carried forward as Rust tests — their scenarios are proven by light specs instead (see Phase B).

## Resolved Decisions

Restating `01_ideas.md`'s Open Questions plus the two raised this session, with this revision's answers:

1. **Override key integrity**: resolved (carried over, verification mechanism changed) — `KNOWN_CALLS` in `src-tauri/src/mockctl/mod.rs` validates keys at `mock_configure` time; a light spec (not a Rust unit test) proves every `KNOWN_CALLS` entry is accepted.
2. **Subsystem scope for v1**: re-resolved — scope is now organized by *runner*, not subsystem. `PodmanProcessRunner` ships in Phase B covering the `backends`/`machine` call sites needed for create/list/start/stop/destroy/deploy and machine-readiness paths; `MutagenProcessRunner` ships in Phase C. `runtime` and `network`'s `podman` call sites (both route through the same shared `PodmanProcessRunner`) are deferred to `04_improvements.md` — deferring them no longer means "no scripting at all" the way it did under the old per-subsystem design, since any spec can already script `podman.start`/`podman.exec` etc. the moment `PodmanProcessRunner` exists; what's deferred is only the `KNOWN_CALLS` entries for `runtime`/`network`-specific subcommands (`mise`, `socat`, `curl`) nobody has needed yet.
3. **Reset policy**: unchanged from the previous revision — `useMockControl()` in `e2e/lib/mock.ts` (Phase D) registers `mock_reset` hooks at `describe` scope: `before`/`after`, plus `beforeEach` so an override cannot leak between `it` blocks. The `beforeEach` reset obliges a spec to install its overrides inside the `it` block that consumes them — see the Mock control plane section of `e2e/AGENTS.md`.
4. **Event scripting**: unchanged — out of scope, `listen_events` is a spawn/stream call outside `ProcessRunner`'s scope (see above); the frontend `plugin:event|emit` bridge remains the mechanism.
5. **Latency simulation**: unchanged — deferred to `04_improvements.md`.
6. **Release-build posture**: unchanged — runtime-gated on `mock_backend_enabled()` only.
7. **Cadence codification**: unchanged — Phase E.
8. **New this session — mocking granularity (trait-level vs. process-level)**: resolved — process-level, per the whole of this document. The rejected-alternatives framing in `01_ideas.md`'s Technology Choices ("Override addressing") is updated to reflect this (see that document).
9. **New this session — verification style (Rust unit/integration tests vs. e2e)**: resolved — e2e only. No standalone `#[test]` fns are written for this feature; every scenario (including `mockctl`'s own control-plane correctness) is proven through `pnpm run test:light` specs. See "One seam, one verification surface" above.

## Superseded: the trait-level design (previous revision's Phase B)

The previous revision implemented (uncommitted, on the current branch) a `MockDirector` consulted inside three hand-written mock structs. This is discarded:

- **Deleted**: `src-tauri/src/backends/mock.rs` (`MockBackend`), `src-tauri/src/sync/mock.rs` (`MockSync`), `src-tauri/src/machine/mock.rs` (`MockMachineManager`) — entire files. Their state machines and constant-responder behaviour are replaced by the real `PodmanCliBackend`/`MutagenCli`/`PodmanMachineManager` running against a scripted `ProcessRunner`.
- **Deleted**: the old `KNOWN_KEYS` table, the typed `Behaviour::{FailOnce,FailAlways,ReturnValue,ReturnSequence}` payload validators (`validate_as::<T>`, `backend_error_ctor`/`sync_error_ctor`), `mockctl::resolve()`'s typed-outcome path, and the old `#[cfg(test)] mod tests` block, all in `src-tauri/src/mockctl/mod.rs`.
- **Deleted**: `default_backend()`/`default_sync_engine()`/`default_machine_manager()`'s branch between two different struct types (`MockX::new(director)` vs. the real struct). Replaced by constructing the one real struct always, parameterized by which `ProcessRunner` it holds (see Phase B).
- **Kept conceptually, rebuilt in new shape**: the `MockDirector` struct pattern (mutex-guarded override map, `configure`/`reset`, consumed-once semantics for fail-once/return-sequence), the `mock_configure`/`mock_reset` Tauri commands and their runtime gate on `mock_backend_enabled()`, the `AppError::MockControl` variant, and the requirement (Phase D) that light specs call a reset hook.
- **Do not reintroduce** a per-subsystem-method override key, a typed-JSON return-value payload, or a `#[cfg(test)] mod tests` block for this feature's own control-plane logic — all three were deliberate simplifications/scope cuts this revision removes, not oversights.

## Implemented: Phase B — `ProcessRunner` seam + `PodmanProcessRunner`

- `ProcessRunner` trait (shape above), `SystemPodmanRunner`, `ScriptedPodmanRunner`, `MockDirector`, `Behaviour`, `ReturnPayload`, and `KNOWN_CALLS` all live in `src-tauri/src/mockctl/mod.rs`. `SystemPodmanRunner` wraps `podman_command().args(args).output().await` verbatim.
- `PodmanCliBackend` (`src-tauri/src/backends/types.rs`/`mod.rs`) and `PodmanMachineManager` (`src-tauri/src/machine/types.rs`/`mod.rs`) each gained a `runner: Arc<dyn ProcessRunner>` field; every call site routes through it (`self.podman(...)`/`PodmanMachineManager::podman(...)`). Free functions with no `&self` (`ensure_connection_alias`, `Self::podman_global`/`podman_on` internals) go through a module-level `PODMAN_RUNNER: OnceLock<Arc<dyn ProcessRunner>>` in `backends/mod.rs`, set once via `set_podman_runner()` from the same `Arc` handed to both structs — the doc's "one shared runner instance" holds across both the struct-field and free-function call sites, not just within one struct.
- `default_backend()`/`default_machine_manager()` now take the runner as a parameter (constructed once in `run()`, `src-tauri/src/lib.rs`, as `Arc::new(SystemPodmanRunner)` or `Arc::new(ScriptedPodmanRunner::new(director))` depending on `mock_backend_enabled()`) instead of branching internally. `src-tauri/src/backends/mock.rs` and `src-tauri/src/machine/mock.rs` (the superseded trait-level `MockBackend`/`MockMachineManager`) are deleted, matching "Superseded" above.
- `KNOWN_CALLS` v1 entries match the doc's list exactly: `podman.create`, `podman.ps`, `podman.start`, `podman.stop`, `podman.rm`, `podman.machine-list`, `podman.machine-start`, `podman.system-connection-list`, `podman.image-exists`, `podman.build`, `podman.info`.
- Key derivation (`derive_podman_key`) strips a leading `--connection <name>` pair, then joins a per-root nesting depth (`machine <x>` → 2, `system connection <x>` → 3, `image <x>` → 2, everything else → 1) — implements the doc's "Key matching strategy" exactly for the four worked examples there.
- **Discovered during implementation, not anticipated by the doc's abstract "no-override invariant" language**: a single stateless empty-`Output` default does not hold end-to-end. Two concrete gaps, both fixed inside `ScriptedPodmanRunner` rather than by asking every light spec to script around them:
  1. `podman ps`/`system connection list --format json` parse stdout as a JSON array — a bare `""` fails to parse at all, not "naturally yields an empty list" as the doc assumed. Fixed via `default_output()`, which answers `"[]"` for `podman.system-connection-list` (and, before the fix below, would have for `podman.ps`).
  2. `check_podman_ready` needs `podman.machine-list` to report a running default machine on every call with no override, or every light spec hits the Podman-startup-recovery gate before reaching its own scenario (the old `MockMachineManager` always reported ready; nothing preserved that once it was deleted). `default_output()` answers `podman.machine-list` with a fixed `[{"Name":"podman-machine-default","Running":true}]` fixture.
  3. Bigger gap: with the real `PodmanCliBackend::create`/`list` running against a *stateless* scripted runner, `create()` then `list()` no longer round-trip — nothing remembers a container across two separate `run()` calls, so every light spec that calls `createProject(name)` and expects the row to render would break (previously `MockBackend`'s own `Vec<Sandbox>` did this). Resolved with the user's direction to keep a small amount of state: `ScriptedPodmanRunner` now tracks `Mutex<Vec<TrackedContainer>>`, updated by `podman.create`/`start`/`stop`/`rm` when no override is installed, and `podman.ps`'s no-override default reports it back (`track_create`/`set_running`/`track_remove`/`tracked_ps` in `mockctl/mod.rs`). A spec that overrides `podman.ps` directly still takes precedence over this tracked state.
- **Second discovered gap, in `RuntimeManager`'s existing mock, not this feature's new code**: `MockRuntime::install`/`list` (`src-tauri/src/runtime/mock.rs`, untouched by this feature otherwise) used to key packages by a hard-coded `/mock/workspace/{name}` string that only matched because the old `MockBackend` fabricated that exact fake path. The real `PodmanCliBackend::create` writes a genuine directory under `SANDBOX_WORKSPACE_ROOT`, so that hard-coded convention silently broke `workspace-dashboard-switch-ui.spec.ts` (install succeeded, but `list(workspace_host_path)` could never find it). Fixed by keying `install`/`uninstall` on the sandbox name directly and having `list` derive the name from `workspace_host_path`'s final path segment — true for any workspace-root layout, not just the deleted mock's fake one.
- Note the pre-existing inconsistency surfaced while wiring this: `network/mod.rs`'s `podman()` helper calls `Command::new("podman")` directly, bypassing `podman_command()`'s resource-dir/env setup. Out of scope to fix here (network stays on the old direct-`Command` path until `04_improvements.md`'s NetworkManager item); noted so the same runner isn't silently assumed to cover it.
- Exit criterion verified: `cargo check`/`cargo test` clean (no new `#[test]` fns); `e2e/test/specs/light/sandbox-list-ui.spec.ts` scripts `podman.ps` directly with a fabricated container JSON line and asserts the real `PodmanCliBackend::list()` parsing/mapping produced the rendered row; `e2e/test/specs/light/sandbox-start-failure-ui.spec.ts` scripts `podman.start` to a non-zero exit and asserts the row's error line renders `BackendError::CommandFailed`'s message via the real `check()` path, then a retry succeeds once the fail-once override is consumed. Both pass under `pnpm run test:light`, along with the rest of the pre-existing light suite (`workspace-dashboard-switch-ui.spec.ts` required the `MockRuntime` fix above to keep passing).

## Implemented: Phase C — `MutagenProcessRunner`

- **The output-type spike resolved in favour of keeping `std::process::Output`** — no `ProcRunOutput` fallback was needed. `std::process::Output`'s fields are public and `ExitStatusExt::from_raw` builds the status on both platforms (`exit_status()`/`to_output()` in `src-tauri/src/mockctl/mod.rs` already did exactly this for the podman runner). `tauri_plugin_shell::process::Output` exposes public `stdout`/`stderr: Vec<u8>` and a `status.code() -> Option<i32>`, so `SystemMutagenRunner::run` re-wraps it field-for-field. One fidelity loss, commented at the call site: `sync::command()`'s `SyncError::DataDir`/`Sidecar` distinction collapses into a single `io::Error` and re-emerges as `SyncError::Sidecar`.
- `SystemMutagenRunner` holds the `AppHandle` (the sidecar is resolved through it) — the reason it cannot share `SystemPodmanRunner`'s shape. `ScriptedMutagenRunner` is stateless, unlike `ScriptedPodmanRunner`: no light-tier flow creates a session and lists it back, since deployment needs a real remote host the tier never has.
- **Scope narrowed to `MutagenCli`'s own `sync` subcommands**, against the doc's earlier "`run()` routes through it" wording. `run()` is shared by `MutagenCli` *and* the `forward`/`version` free functions, which are `NetworkManager`'s calls — explicitly deferred in `04_improvements.md`. Routing them too would have meant threading the runner through nine call sites in `network/mod.rs` for no light-tier gain, since `MockNetworkManager` keeps them off that path entirely. `run_via()` (`sync/mod.rs`) is `run()`'s contract over a `ProcessRunner`; `run()` stays for the free functions.
- `MutagenCli` holds `runner: Arc<dyn ProcessRunner>` and no longer holds an `AppHandle` (the runner owns it), so `default_sync_engine()` takes only the runner. `src-tauri/src/sync/mock.rs` (`MockSync`) is deleted.
- `KNOWN_CALLS` gained the six `mutagen.sync-*` entries exactly as listed. `derive_mutagen_key` needs no `--connection` strip and only a two-level/one-level depth rule (`sync`/`forward`/`daemon` nest once; `version` does not).
- No-override defaults got their own pass, as the doc required rather than inheriting podman's: `mutagen.sync-list` answers `"[]"`. `sessions()` tolerates `""` but `status()` parses it and would raise `SyncError::ParseError`. This drops the deleted `MockSync`'s always-`UpToDate` `status()`, which is safe because `destroy_sandbox`/`undeploy_sandbox` only reach `status()` after finding a session in `sessions()`, and the default reports none (`src-tauri/src/lib.rs`).
- **Discovered while finishing this phase, and the most consequential finding of the feature**: with the real `PodmanMachineManager` running in the light tier, `settings-debugging-ui.spec.ts` was really executing `wsl --unregister podman-machine-default` on the developer's host, deleting the machine's WSL distro on every light run. `wsl` is outside the `ProcessRunner` seam by design ("Scope limit"), so nothing scripted it away. Fixed by `run_host_wsl()` (`src-tauri/src/machine/mod.rs`), which no-ops under `MIO_MOCK_BACKEND=1` and now guards all three host-mutating `wsl` calls. See `04_improvements.md`, "Host commands outside the `ProcessRunner` seam" — the general lesson is that deleting a mock struct hands the light tier every unscripted side effect the real struct has, not only the ones the seam covers.
- Exit criterion verified: `e2e/test/specs/light/sync-status-ui.spec.ts` scripts `mutagen.sync-list` with a conflicted-session fixture and asserts the real `MutagenCli::sessions()` → `SyncEngine::sessions` → frontend badge chain renders `conflict`. `cargo check`/`cargo test` clean (no new `#[test]` fns), `pnpm check` clean, and all 10 light spec files pass.

## Lifecycle and Cross-Cutting Concerns

- **Override lifetime**: unchanged — process memory only, `mock_reset`/app exit are the only clears.
- **No-override invariant**: restated per Phase B's findings — this document's original assumption ("empty stdout naturally yields an empty sandbox list") turned out false for two call sites and was corrected during implementation, not just verified: `podman.ps`/`podman.system-connection-list` need `"[]"`, not `""`, to parse at all, and `podman.machine-list` needs a fixed "default machine is running" fixture or `check_podman_ready` fails by default (see Phase B above, "Discovered during implementation"). A third gap — `create()`/`list()` no longer round-tripping against a stateless runner — was resolved by giving `ScriptedPodmanRunner` a small `Mutex<Vec<TrackedContainer>>` that `create`/`start`/`stop`/`rm` update and `ps` reports back when no override is installed; an explicit override on any of those keys always takes precedence over the tracked state. `ScriptedMutagenRunner` (Phase C, not yet built) will need its own pass through this same question rather than assuming the podman runner's answers transfer.
- **Filesystem side effects**: real now (see "Decision: the light tier runs the real structs" above) — `workspace_root()` writes and Mutagen's `data_dir()` writes are genuine disk I/O under `MIO_MOCK_BACKEND=1`, bounded by `SANDBOX_WORKSPACE_ROOT` already pointing at a scratch directory.
- **Error-kind fidelity**: strengthened, not just carried over — since scripted failures now flow through the same `check()` function real failures do, there is no separate "does the scripted error map to the right `AppError` kind" risk to track; it's the same code path, provable with the same light-spec assertions used for a real failure.

## Common Gotchas

| Gotcha | Cause | Fix |
|---|---|---|
| `mock_configure` rejects a key that looks like it should match a real `podman`/`mutagen` call | The key is missing from `KNOWN_CALLS` in `src-tauri/src/mockctl/mod.rs`, or the derived key doesn't match the matching strategy's leading-args-join rule for that call shape | Add the key to `KNOWN_CALLS`; if the derived key looks wrong, check whether the call passes `--connection` (stripped) or a multi-word subcommand (joined with `-`) |
| Scripting `podman.start` also affects an unrelated subsystem's `start` call | `PodmanProcessRunner` is shared across `backends`/`machine` (and, once wired, `runtime`/`network`) — this is intentional (see "shared runner, CLI-shaped keys"), not a bug | Scope the scenario's assertions to expect the shared effect, or use a fail-once behaviour if only one call in the flow should fail |
| Scripting `mutagen.sync-list` makes both `status()` and `sessions()` see the same fixture | The key does not discriminate on the trailing name-filter positional (documented limitation, Phase C) | Don't script a scenario that needs `status(name)` and `sessions()` to disagree in v1; extending the key to include the filter is a `04_improvements.md` candidate if a spec needs it |
| A light spec passes alone but fails after another scripting spec in the same file | Overrides persist across `it` blocks within a spec file's app session (unchanged from the previous revision) | Call `useMockControl()` (`e2e/lib/mock.ts`) at `describe` scope |
| A scripted `create`/`start`/`stop` behaviour is accepted by `mock_configure` but the real subsystem code never sees it fail | The scripted `Output` has `exit_code: 0` — `check()` only treats non-zero exit as failure, so a `FailOnce`/`FailAlways` behaviour must always set a non-zero exit code, not just a populated `stderr` | `KNOWN_CALLS`' validator for fail behaviours rejects `exit_code: 0`; if it doesn't yet, that's the bug, not the spec |
| `cargo check` fails after Phase B/C with errors about `PodmanCliBackend`/`MutagenCli`'s constructor signature | Every call site that builds these structs directly (not through `default_backend()`/`default_sync_engine()`) needs the new `runner` field | Search for direct struct-literal construction outside the `default_*()` functions before considering Phase B/C done |
| The temptation to add a Rust `#[test]` "just to check this one function" during Phase B/C | Habit from the previous revision's mock-level design, or from `mockctl`'s old unit tests | Don't — write or extend a light spec instead (Resolved Decision 9); if the function genuinely can't be reached from a light spec, that's a sign the `ProcessRunner` wiring for that call site is incomplete, not a reason to unit-test around it |
| A light spec mutates the developer's real host (deletes a WSL distro, stops WSL, installs something) | The real subsystem struct also calls host binaries the `ProcessRunner` seam does not cover (`wsl`, `ssh-keygen`, `ssh`) — deleting a mock struct hands the light tier *every* side effect the real struct has, not only the scripted ones | Gate the call on `mock_backend_enabled()` (pattern: `run_host_wsl()` in `src-tauri/src/machine/mod.rs`); audit any new host-binary call reachable from a light spec the same way |
| A light spec asserts on `err.kind` and always sees `undefined` | A promise rejected inside `browser.execute` reaches the spec as a WebdriverIO error, not the `AppError` object | Catch inside the webview and return the error as a value (pattern: `configureMockExpectingError()` in `e2e/lib/mock.ts`) |

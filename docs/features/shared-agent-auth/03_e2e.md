# Shared Agent Auth E2E Test Plan

Test plan for the feature built in `docs/features/shared-agent-auth/02_dev.md` (Phases A–E: the
`src-tauri/src/credentials/` store, the auth-container capture flow, the `credentials::inject`
tar-based transport, and the `src/routes/credentials/` UI). No spec has been written yet, despite
Phases A–E of `02_dev.md` being implemented. A manual spike already ran on 2026-07-02 and is
recorded in `01_ideas.md`'s Validation section; it proved credential portability and refresh-token
rotation semantics by hand against real containers (`gg`, throwaway `spikeb`/`spikec`) — that spike
is the proof for the one step this plan explicitly does not automate (the real OAuth code exchange,
same exclusion `agent-setup`'s `03_e2e.md` makes for `start_agent_auth`). The spike's original
`.claude.json` merge strategy was superseded 2026-07-03 by whole-directory replacement — see
`02_dev.md`'s Resolved Decisions.

## Goal

The spec must prove, against the real backend:

1. `capture_agent_credentials` (`src-tauri/src/lib.rs`, wrapping `credentials::capture` in
   `src-tauri/src/credentials/mod.rs`) reads `/root/.claude/.credentials.json` and
   `/root/.claude.json` out of a real, already-authenticated sandbox container via
   `RuntimeManager::exec_in_container` (for `manifest.json`'s email/expiry only), tars
   `/root/.claude` plus `/root/.claude.json` via `tar_capture`, and writes `home.tar.gz` and
   `manifest.json` to `%APPDATA%/com.tincho.sandbox-mio/credentials/anthropic/` on the real host
   filesystem.
2. `inject_agent_credentials` (wrapping `credentials::inject`) extracts `home.tar.gz` into a
   **different** real container via `tar_inject` (`podman exec -i ... tar -C / -xzpf -`) — never
   `podman cp`, never a bare `cat >` — landing a working `/root/.claude/.credentials.json` and a
   fully onboarded `/root/.claude.json` (both files replaced verbatim from the source container,
   not merged; see `02_dev.md`'s Resolved Decisions for why whole-directory replacement superseded
   the original `oauthAccount`-only merge).
3. `install_agent` (`src-tauri/src/lib.rs`) auto-injects when a host bundle already exists for the
   agent's `credentialService`: a **freshly installed** agent in a **freshly created** container
   reports `authenticated: true` via `get_agent_auth_status` without any explicit auth click.
4. The `/credentials` route reads `list_credential_bundles` and renders real per-service status
   (connected email, expiry) sourced from the host `manifest.json`, and "Log out" removes the host
   directory via `delete_credential_bundle` (`credentials::delete`) while leaving injected container
   copies untouched.

A weaker test that only checks `manifest.json` exists after capture, without extracting
`home.tar.gz` and checking both `.credentials.json` and `.claude.json` landed with mode `0600` in
the target container, would fail to catch a regression to `podman cp`-style injection (wrong
permissions) or a capture that silently drops one of the two paths. A test that skips the
auto-inject-at-install assertion (item 3) would fail to catch `install_agent` never calling
`credentials::inject` at all, silently leaving the "inject automatically... the user never sees a
login step" promise in `01_ideas.md`'s Proposed Model unimplemented. A test that only checks the
injected token is valid (e.g. a non-interactive `claude -p` call succeeds) without also asserting
onboarding state landed would fail to catch a regression back to merge-only injection — the
non-interactive check alone would pass even with the original bug where the interactive UI still
re-ran its first-run wizard on a freshly injected target (see `02_dev.md`'s gotcha table entry
dated 2026-07-03).

## Existing Test Styles

All `standard`-tier specs (see `e2e/AGENTS.md`) drive a real compiled Tauri app via WebdriverIO
against real Podman containers on the `mio-tests` connection (`LOCAL_CONNECTION`,
`e2e/lib/podman-connection.ts`), and read back state with `podman exec` and direct filesystem
reads — never through mocked Tauri commands. The closest existing spec is
`e2e/test/specs/standard/agent-setup.spec.ts` (test plan: `docs/features/agent-setup/03_e2e.md`):
it pre-seeds fake credential files into a container via `podman exec ... bash -c` rather than
completing a real OAuth flow, and asserts on `get_agent_auth_status`'s resulting UI state — this
spec reuses that exact pre-seeding technique as its starting point, then adds the host-side bundle
directory and a second/third container to prove capture and injection.

Relevant existing pieces:

| Piece | Path | Reused for |
|---|---|---|
| `ProjectRow` page object | `e2e/test/pageobjects/project-row.component.ts` | `startAgentInstall`, `waitForAgentRow`, `waitForAgentStatus`, `agentAuthButton` |
| `ProjectsPage` page object | `e2e/test/pageobjects/projects.page.ts` | `createProject`, `row(name)` |
| `SettingsPage` page object | `e2e/test/pageobjects/settings.page.ts` | Pattern for a new global (non-project) route page object — `/credentials` is structurally the same shape as `/settings` |
| `podman`/`podmanOk`/`LOCAL_CONNECTION` | `e2e/lib/podman-connection.ts` | Seeding fake credentials, reading container state, cleanup |
| `APP_DATA_MODELS` pattern | `e2e/test/specs/heavy/local-llm.spec.ts:31` | Pattern for resolving `%APPDATA%/com.tincho.sandbox-mio/credentials/` on Windows |

## Chosen Approach

Tier: **standard**. No large asset download beyond what `agent-setup.spec.ts` already pays for
(`node@lts` + `npm:@anthropic-ai/claude-code` + native postinstall binary, ~70 MB, one-time per
container). No real Anthropic OAuth call is made — every credential file in this spec is
synthetic, seeded the same way `agent-setup.spec.ts` seeds them, so refresh-token rotation (the
real-world risk `01_ideas.md`'s spike 2 found) never triggers a genuine Anthropic API call and
cannot invalidate a real login.

Spec file: `e2e/test/specs/standard/shared-agent-auth.spec.ts`.

Topology: single Podman machine (`mio-tests`, `LOCAL_CONNECTION`), three sandbox containers created
in sequence within the suite:

- **`source`** — has Claude Code installed and fake credential files seeded directly (mirrors
  `agent-setup.spec.ts`'s pre-seed step). Used only as the input to `capture_agent_credentials`.
- **`target-manual`** — has Claude Code installed but no credentials, used to prove the
  `/credentials` "Log in" → capture happened once, then per-sandbox manual injection (the
  `AgentManager.svelte` "use saved login" path from `02_dev.md` Phase E).
- **`target-auto`** — created and has Claude Code installed only **after** the host bundle exists,
  to isolate `install_agent`'s auto-inject branch from the manual one.

Three containers (not one reused) because the three assertions are about three different trigger
points (explicit capture, explicit inject, implicit inject-on-install) that would otherwise mask
each other if sequenced on shared container state — e.g. reusing `target-manual` for the
auto-inject check could not tell whether authentication came from the manual click or the install
hook.

No `light` spec is added for this feature. The gating logic ("use saved login" vs. "Authenticate"
button, connected/not-connected status rendering) is thin enough to be covered by the `standard`
spec's UI assertions directly; a separate mock-backend spec would only duplicate the real one
without adding an edge case that is awkward to provoke for real (unlike, say,
`light/local-llm-ui.spec.ts`'s catalogue-gating edge cases, which have no download-free real
equivalent).

## Harness Changes

No `wdio.conf.ts` changes and no new Podman machine. `%APPDATA%/com.tincho.sandbox-mio/credentials/`
is not cleaned up by any existing hook — the spec's own `after` must delete
`credentials/anthropic/` on the host after the run, the same way the existing `after` hooks
`podman rm -f` their containers, so a failed run does not leave a stale "connected" bundle that
makes the next run's Step 1 (no bundle exists) assertion fail.


### New: `e2e/test/pageobjects/credentials.page.ts`

Modelled on `e2e/test/pageobjects/settings.page.ts`. Phase E's `src/routes/credentials/+page.svelte`
must expose the same kind of data-attribute selectors `SettingsPage` relies on
(`[data-active-engine]`, `[data-save]`) rather than CSS classes, so this page object — and Phase
E's implementation — should use:

```
import AppPage, { type Element } from "./app.page.js";

class CredentialsPage extends AppPage {
  get navLink(): Element {
    return $("a[href='/credentials']");
  }

  // One row per service in the catalogue (src/lib/agents/catalogue.ts's distinct credentialService
  // values), keyed by data-service (e.g. "anthropic").
  serviceRow(serviceId: string): Element {
    return $(`[data-service='${serviceId}']`);
  }

  serviceStatusText(serviceId: string): Element {
    return this.serviceRow(serviceId).$("[data-status]");
  }

  logInButton(serviceId: string): Element {
    return this.serviceRow(serviceId).$("button=Log in");
  }

  logOutButton(serviceId: string): Element {
    return this.serviceRow(serviceId).$("button=Log out");
  }

  async open(timeout = 10000): Promise<void> {
    const url = await browser.getUrl();
    if (!url.includes("/credentials")) {
      const link = await this.navLink;
      await link.waitForDisplayed({ timeout });
      await link.click();
    }
  }

  async waitForStatus(serviceId: string, text: string, timeoutMs = 10000): Promise<void> {
    await browser.waitUntil(
      async () => (await this.serviceStatusText(serviceId).getText()) === text,
      { timeout: timeoutMs, interval: 500, timeoutMsg: `credential status for "${serviceId}" did not become "${text}"` }
    );
  }
}

export default new CredentialsPage();
```

This is new surface Phase E must build to this contract; the spec below depends on
`[data-service]`/`[data-status]` existing verbatim in `src/routes/credentials/+page.svelte`.

## Spec Scenario — `e2e/test/specs/standard/shared-agent-auth.spec.ts`

```ts
describe("Shared agent auth — credential store", function () {
  this.timeout(1800000); // three cold containers, each paying the ~70 MB claude-code install
  // ...
});
```

`APP_DATA_CREDENTIALS` resolved the same way `local-llm.spec.ts` resolves `APP_DATA_MODELS`:
`%APPDATA%/com.tincho.sandbox-mio/credentials/anthropic`.

---

**Step 1 — Suite setup**

`before`: assert `SANDBOX_WORKSPACE_ROOT` is set. Compute container names
(`e2e-cred-source-<timestamp>`, `e2e-cred-manual-<timestamp>`, `e2e-cred-auto-<timestamp>`).

`after`: `podman(LOCAL_CONNECTION, ["rm", "-f", ...allThreeNames], { check: false })`, then
`fs.rmSync(APP_DATA_CREDENTIALS, { recursive: true, force: true })` — cleans the host bundle so a
failed run does not poison the next.

`afterEach`: capture `.diag` on failure, identical to `agent-setup.spec.ts`'s pattern.

---

**Step 2 — Source sandbox: install Claude Code and seed fake credentials**

Action: `ProjectsPage.createProject("source")`, `row.startAgentInstall("Claude Code")`,
`row.waitForAgentRow("Claude Code", 900000)` — same install path `agent-setup.spec.ts` Step 2
exercises (proves nothing new by itself, but the `source` container needs a real installed agent
before it has meaningful credential files to capture).

Seed fake credentials via `podman exec` (same shape as `agent-setup.spec.ts`'s seed, with a
distinct `machineID`/`userID` recorded for later comparison):

```ts
const sourceExpiresAt = Date.now() + 365 * 24 * 60 * 60 * 1000;
podman(LOCAL_CONNECTION, [
  "exec", "source", "bash", "-c",
  `mkdir -p /root/.claude && ` +
  `printf '%s' '{"claudeAiOauth":{"accessToken":"fake-access","refreshToken":"fake-refresh","expiresAt":${sourceExpiresAt}}}' ` +
  `> /root/.claude/.credentials.json && ` +
  `printf '%s' '{"machineID":"source-machine","userID":"source-user","oauthAccount":{"emailAddress":"e2e-shared-auth@example.com"}}' ` +
  `> /root/.claude.json`,
]);
```

Assertion: `get_agent_auth_status`-driven UI already shows `e2e-shared-auth@example.com` next to
"Claude Code" in `source`'s row (`row.waitForAgentStatus`), confirming the seed took before capture
is attempted — a capture bug and a seed bug must not be confused.

---

**Step 3 — Capture from the source sandbox**

Action: invoke `capture_agent_credentials` directly (not yet wired to a dedicated
`AgentManager.svelte` button per `02_dev.md`'s Phase E, which only names the auth-container path
explicitly) via `browser.execute()` against `window.__TAURI_INTERNALS__.invoke`, the same technique
`light` specs use for direct command calls:

```ts
await browser.execute((sourceName: string) => {
  // @ts-expect-error Tauri internals global, no type package
  return window.__TAURI_INTERNALS__.invoke("capture_agent_credentials", {
    name: sourceName,
    serviceId: "anthropic",
    credentialPath: "/root/.claude/.credentials.json",
    expiresAtJsonKey: "claudeAiOauth.expiresAt",
    accountSourcePath: "/root/.claude.json",
    accountEmailJsonKey: "oauthAccount.emailAddress",
  });
}, sourceName);
```

Assertions, all against the real host filesystem at `APP_DATA_CREDENTIALS`:

3a. `manifest.json` exists and parses with `accountEmail === "e2e-shared-auth@example.com"` and a
future `expiresAtMs`.

3b. `home.tar.gz` exists; extracting it (e.g. via Node's `zlib`+`tar` or a shelled-out `tar -tzf`)
lists members for both `root/.claude/.credentials.json` and `root/.claude.json` — proves the
archive captured the credential directory *and* the account-source file, not just one.

3c. Extracting `home.tar.gz`'s `root/.claude.json` member and parsing as JSON has
`machineID === "source-machine"` and `oauthAccount.emailAddress === "e2e-shared-auth@example.com"`
— the whole seeded file round-tripped verbatim (no merge/subtree extraction). This is the decisive
assertion distinguishing whole-directory capture from the superseded merge-only design.

---

**Step 4 — Inject into a different, unauthenticated sandbox (manual path)**

Action: `ProjectsPage.createProject("target-manual")`, install Claude Code (unauthenticated, no
seed this time), record the container's own pre-injection `machineID` via
`podman exec target-manual bash -c "cat /root/.claude.json"` parsed for `machineID` (this container
got its own `machineID` from its own first unauthenticated `claude -p` invocation the postinstall
step or `get_agent_auth_status`'s `cat` may have already triggered — if not yet present, the spec
runs `mise exec -- claude -p "x"` once inside `target-manual` to force its creation before
recording it, matching how the 2026-07-02 spike produced `spikec`'s default file).

Then drive the UI: `row.agentUseSavedLoginButton("Claude Code")` should already be showing instead
of "Authenticate" (proves `AgentManager.svelte`'s Phase E branch on `list_credential_bundles`
having an `anthropic` entry). Click it.

Assertions:

4a. `row.waitForAgentStatus("Claude Code", "e2e-shared-auth@example.com")` — the injected email
appears through the same `get_agent_auth_status` read path Step 3 of `agent-setup.spec.ts` uses.

4b. `podman exec target-manual bash -c "cat /root/.claude.json"`, parsed as JSON: `machineID` equals
`"source-machine"` (**not** the value recorded before injection) — proves whole-directory
replacement landed the source's onboarding state, the fix for the bug that motivated this design
(interactive UI re-running its first-run wizard when only the OAuth subtree was merged in).

4c. `podman exec target-manual bash -c "stat -c '%a' /root/.claude/.credentials.json"` prints `600`
— proves `tar_inject`'s `-p` flag preserved the credential file's mode, not `podman cp`'s `0666`.

4d. `podman exec target-manual bash -c "cat /root/.claude/.credentials.json"`, parsed as JSON:
`claudeAiOauth.accessToken === "fake-access"` — proves the credential file itself was injected
correctly.

---

**Step 5 — Auto-inject at install time**

Action: `ProjectsPage.createProject("target-auto")` — created **after** Step 3's capture, with no
Claude Code installed yet. `row.startAgentInstall("Claude Code")`,
`row.waitForAgentRow("Claude Code", 900000)`. No auth button is clicked at all.

Assertion: `row.waitForAgentStatus("Claude Code", "e2e-shared-auth@example.com", 15000)` — proves
`install_agent` (`src-tauri/src/lib.rs`) itself calls `credentials::inject` when a bundle exists,
with no user action beyond installing the agent. This is the assertion a weaker test (checking only
that manual injection via Step 4's button works) would miss.

---

**Step 6 — `/credentials` page reflects host state and Log out leaves containers untouched**

Action: `CredentialsPage.open()`.

Assertions:

6a. `CredentialsPage.waitForStatus("anthropic", "e2e-shared-auth@example.com")` — the page reads
`list_credential_bundles` and renders the same manifest Step 3 wrote.

6b. Click `CredentialsPage.logOutButton("anthropic")`. `fs.existsSync(APP_DATA_CREDENTIALS)` is now
`false` (or the directory is empty) — `delete_credential_bundle` removed the host bundle.

6c. `target-manual`'s Claude Code status is **still** `e2e-shared-auth@example.com` after log-out —
navigate to `target-manual`'s row (`navigateHome` + `ProjectsPage.open()`,
`row.waitForAgentStatus`) and confirm the email is unchanged. Proves log-out deletes only the host
copy, matching the gotcha table row in `01_ideas.md` ("Log out ... does not de-authenticate existing
sandboxes").

---

**Step 7 — Cleanup**

`after` hook runs (Step 1); no explicit `it()` needed.

## De-risking Spike Results

Spike run 2026-07-02, recorded in full in `01_ideas.md`'s Validation section. Results directly
relevant to this spec:

| Risk | Result | Command |
|---|---|---|
| Credentials portable across containers (no machine/container binding) | Cleared — `spikeb` ran `claude -p` successfully immediately after receiving `gg`'s copied files | `mise exec -- claude -p "reply with exactly the word PORTABILITY_OK"` in `spikeb` |
| Refresh-token rotation invalidates sibling copies | **Blocker found, classified as a real product constraint, not a test concern** — confirmed `gg`'s original session died the moment `spikeb` refreshed from the same snapshot. Not a blocker for this spec because the spec never performs a real refresh (all seeded credentials are synthetic and never exercised against the real Anthropic API); it is a blocker for the feature's UX, tracked in `02_dev.md`'s Resolved Decisions | `claude -p "reply OK"` in `gg` after `spikeb` refreshed → `Not logged in · Please run /login` |
| `.claude.json` merge-only strategy preserves `machineID`/`userID` | Cleared — merging only `oauthAccount` into `spikec`'s own file left `machineID`/`userID` unchanged | Node `JSON.parse`/merge/`JSON.stringify` script run inside `spikec`, comparing before/after `machineID` |
| Injection transport permissions | Cleared — `podman exec -i ... cat > file && chmod 600` produces mode `0600`; `podman cp` produces mode `0666` | `podman exec -i spikeb sh -c 'mkdir -p /root/.claude && cat > ... && chmod 600 ...'` |
| Real OAuth PKCE flow via FIFO stdin | Cleared (reconfirms the 2026-06-28 `agent-setup` spike) — `claude auth login` accepted a code delivered through a FIFO with a persistent writer holding it open | `mkfifo /tmp/auth_fifo; nohup sh -c "sleep 600 > /tmp/auth_fifo" &; nohup sh -c "mise exec -- claude auth login < /tmp/auth_fifo > /tmp/auth_output.log" &` in `gg` |

No blocker in the list above blocks writing this spec — all of it is de-risked, and the one live-API
risk (refresh-token rotation) is sidestepped entirely by using synthetic credentials, exactly as
`agent-setup.spec.ts` sidesteps needing a real Claude account.

## Sequencing

1. Implement `02_dev.md` Phases A–E, in order (the store must exist before capture, capture before
   injection, injection before the auto-inject hook and the UI).
2. Add the `agentUseSavedLoginButton` selector to `project-row.component.ts` and the new
   `credentials.page.ts`, matching the `data-service`/`data-status` contract Phase E's
   `+page.svelte` must implement.
3. Write `shared-agent-auth.spec.ts` Steps 1–3 (source seed + capture) first and get them green —
   this validates the store module (Phase A) and capture (Phase C) in isolation before injection
   (Phase D) exists.
4. Add Steps 4–5 once `credentials::inject` and the `install_agent` auto-inject hook are wired.
5. Add Step 6 once `src/routes/credentials/` (Phase E) exists.
6. Run the full spec against a cold `mio-tests` machine once to validate the 1800000 ms ceiling;
   adjust per-step timeouts (not the suite ceiling) if any individual `waitForAgentRow` proves too
   tight, following `agent-setup.spec.ts`'s precedent of 900000 ms per cold install.

## Environment Notes

- `mio-tests` Podman machine must be provisioned; `mio-tests-remote` is **not needed** — this spec
  is entirely local-connection, matching `agent-setup.spec.ts`.
- `SANDBOX_WORKSPACE_ROOT` is set by `wdio.conf.ts`; the spec does not read `mise.toml` directly
  (unlike `agent-setup.spec.ts`) since its assertions are about credential files, not package
  manifests, but the three containers still need this env var set for `ProjectsPage.createProject`
  to succeed.
- `%APPDATA%/com.tincho.sandbox-mio/credentials/` is created fresh by Step 3 and removed by the
  `after` hook; a prior failed run leaving this directory populated will make Step 6a's "no bundle"
  precondition (implicit in the `/credentials` page showing "not connected" before Step 3, if that
  assertion is added) fail — always confirm the directory is absent before a manual re-run.
- No real Claude/Anthropic account or internet access beyond the containers' outbound HTTPS for
  `mise use` downloads is required; the spec never completes a real OAuth exchange.

## Common Gotchas

| Gotcha | Cause | Fix |
|---|---|---|
| Step 3b/3c's `home.tar.gz` is missing the `root/.claude.json` member | `credentials::capture`'s `tar_capture` call only passed the credential directory, not `account_source_path`, to `tar` | Confirm `capture` builds its `paths` vec from both `credential_dir(credential_path)` and `account_source_path` before calling `tar_capture` |
| Step 4b shows `machineID` still equal to the value recorded before injection (injection had no effect) | `credentials::inject`/`tar_inject` failed silently, or extracted to the wrong location | Confirm `tar_inject` pipes the archive to `podman exec -i <name> tar -C / -xzpf -` and checks the child's exit status; a non-zero exit must surface as `CredentialError::ExecFailed`, not be swallowed |
| Step 5 times out — `target-auto` never shows the seeded email after install | `install_agent` (`src-tauri/src/lib.rs`) does not call `credentials::inject` after `run_postinstall_npm`, or checks the wrong `credentialService` | Add/verify the auto-inject check runs after `AgentInstallEvent::Done` is queued but the credential inject happens before the frontend's `loadAgentStatuses` polls; confirm the descriptor's `credentialService` matches the bundle's directory name (`"anthropic"`) exactly |
| `agentUseSavedLoginButton` never appears in Step 4, "Authenticate" shows instead | `AgentManager.svelte`'s Phase E branch checks `list_credential_bundles` before it resolves (a race), or checks the wrong field name | Ensure the branch awaits `list_credential_bundles` in `onMount` before rendering the auth button, mirroring how `loadAgentStatuses` is already awaited before the Agents section renders |
| `capture_agent_credentials` invoked via `browser.execute` throws `command not found` | The Tauri command was not added to `tauri::generate_handler![]` in `src-tauri/src/lib.rs` | Add `capture_agent_credentials` to the handler list alongside `install_agent`/`start_agent_auth` |
| Step 6b's `fs.existsSync` still returns `true` after clicking Log out | `delete_credential_bundle` removed only `manifest.json`, not the whole `credentials/anthropic/` directory | Confirm `credentials::delete` calls `std::fs::remove_dir_all` on the service directory, not per-file removal |
| Suite runs past 1800000 ms on a cold machine | Three containers each cold-install `node@lts` + `npm:@anthropic-ai/claude-code` (~70 MB each) with no shared cache between containers on `mio-tests` | Raise `this.timeout` further, or pre-warm `mio-tests` by running `agent-setup.spec.ts` first in CI so the base image layer is cached (containers still redownload the mise-managed tools per container, but network/image-pull cost is amortized) |

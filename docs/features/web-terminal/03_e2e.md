# In-App Web Terminal (Zellij) — E2E Test Plan

This document is the end-to-end test plan for the in-app web terminal whose build
is specified in `docs/features/web-terminal/02_dev.md`. It depends on that build
plan and tests only the build it describes (Phases A–D: Zellij baked into the
base image, the web port published at container create, the `open_terminal`
runtime operation plus its Tauri command, and the frontend "Terminal" button that
opens a `WebviewWindow`). **No test-specific spike has been run in this session.**
The only spike to date is the 2026-06-27 feasibility spike recorded in
`01_ideas.md` and reproduced by `docs/features/web-terminal/spike/reproduce.sh`;
that spike ran by hand on the developer machine's default Podman against the flox
base image using `flox activate`, not on the WebdriverIO test machine and not
through the app, so the risks it leaves open for the automated harness are listed
in section "De-risking spike results" below. **The feature is entirely
unimplemented** (every phase in `02_dev.md` is Remaining), so the spec described
here would go red on the missing "Terminal" button today; section "Sequencing"
states it is written only after Phases A–D land.

## Goal

The test must prove the **real application code path**, not the spike shell
script. Concretely it must drive, end to end:

- The frontend "Terminal" button in `src/routes/projects/+page.svelte`, which
  invokes the `open_terminal` Tauri command (`src-tauri/src/lib.rs`).
- `RuntimeManager::open_terminal` in `src-tauri/src/runtime/mod.rs`, which over
  `podman exec` runs `zellij web --status` / `zellij web --daemonize` (idempotent
  start), `zellij web --create-token` (token mint and stdout parse), reads the
  host port with `podman --connection <c> port <name> 8082/tcp`, and writes the
  token host-side to `<workspace>/.mio/zellij.json`.
- The **bundled component**: the `zellij` binary baked into the base image's root
  Nix profile by `src-tauri/resources/Containerfile` (Phase A), reachable on the
  global container `PATH` without `flox activate`.
- The **published-port chain**: the `--network pasta:--host-lo-to-ns-lo` and
  `--publish 127.0.0.1::8082` flags added to `podman create` (Phase B), proven by
  an HTTP 200 fetched from the Windows host loopback at the port `open_terminal`
  returns.

A weaker test would **fail to cover** the parts most likely to break:

- Running `spike/reproduce.sh` (or any standalone `podman` script) would prove the
  network topology but **not** that the Tauri command exists, that its token-line
  and `podman port` parsers are correct, that the token is written to the exact
  host path the frontend passes, or that the frontend button is wired to the
  command. It exercises a side-channel, not the app.
- Asserting only that `open_terminal` returns a `{ url, token }` shape (e.g. a
  Rust unit test) would **not** prove the zellij server actually bound, that the
  published port reaches the host, or that the image ships zellij at all (Phase A
  regressions are invisible to a shape check because a stale base image still
  satisfies the type).
- Reading the token only from the command result would **not** prove the
  `.mio/zellij.json` host-side write (the `docs/techdebt.md` workaround) actually
  landed where the deferred auto-login follow-up will read it.

## Existing test styles

Two styles exist in the repo:

- **App-driven WebdriverIO/Mocha specs** under `e2e/test/specs/*.spec.ts`, driven
  through `tauri-driver` against the built debug binary, using the page-object
  model in `e2e/test/pageobjects/` and asserting out-of-band on container state
  via the `podman --connection <name>` CLI (`e2e/lib/podman-connection.ts`) and on
  the filesystem. Examples: `runtime-management.spec.ts` (drives install/deploy
  through the UI, reads `manifest.toml` back from the host filesystem and runs the
  package via `podman exec`), `project-start-stop.spec.ts`, `deploy-remote.spec.ts`,
  `base-image-build.spec.ts`. These are the project's preferred tests
  (`e2e/README.md`: "These tests are preferred above all others").
- **Standalone POC shell scripts** under `docs/features/<feature>/spike/`, run by
  hand to de-risk feasibility. Example: `docs/features/web-terminal/spike/reproduce.sh`.
  These are not part of the WebdriverIO suite and prove topology, not the app.

The new test belongs to the **app-driven WebdriverIO** style, mirroring
`runtime-management.spec.ts` most closely (UI action → read state back through the
CLI and filesystem).

## Chosen approach

Add a single app-driven spec: **`e2e/test/specs/web-terminal.spec.ts`**.

Topology: **a single local Podman machine** (`mio-tests`, the `LOCAL_CONNECTION`
the app talks to). No remote machine and no external host are involved — the
terminal feature is local-only per the `02_dev.md` "Remote-deployed sandboxes →
out of scope" decision, and the published port is on the Windows host loopback
(`127.0.0.1`), reached by the spec process itself with a Node `fetch`. This is the
right topology because the decisive end-to-end assertion (HTTP 200 from the host
loopback) is exactly what the host running the WebdriverIO suite can observe
directly, and adding the remote machine would test a path the feature explicitly
does not implement.

The spec exercises the real chain but **does not attempt to drive the second
`WebviewWindow`** that the frontend opens: `tauri-driver` automates the main
application webview only, and multi-window control is a known limitation (see
"Common Gotchas"). The spec instead asserts the window's *precondition* (the
command returned a reachable URL serving HTTP 200) and the *side effects*
(`.mio/zellij.json` written, server online), which together prove the window
would load a working terminal. Driving the terminal window's contents is left to
manual verification (`/verify`).

## Harness changes

Edits to `e2e/` so the spec can assume a zellij-capable base image and a clean
machine:

1. **Base-image tag bump in the harness.** `02_dev.md` Phase A bumps
   `BASE_IMAGE_VERSION` from `"flox"` to a new tag (e.g. `"zellij"`).
   `e2e/lib/podman-machine.ts` hardcodes `FLOX_BASE_IMAGE = "sandbox-mio/base:flox"`
   and `ensureFloxBaseImage` builds it from the **sandbox-runtime-management**
   spike Containerfile (`docs/features/sandbox-runtime-management/spike/Containerfile`),
   which has no zellij. Update the harness to match the new tag and a recipe that
   bakes zellij:
   - Either point `ensureFloxBaseImage` at a Containerfile that includes the
     zellij step (the cleanest source of truth is `src-tauri/resources/Containerfile`
     itself, the recipe the app actually bakes), and rename the constant/tag to the
     new `BASE_IMAGE_VERSION`; **or**
   - Drop the pre-stage entirely for the local connection and let the app build the
     image on first `create` (the path `base-image-build.spec.ts` already exercises
     since commit 017759d "build flox base image reliably on first create"). The
     `web-terminal.spec.ts` `createProject` wait must then carry the wide
     (~900 s) timeout that covers the one-time build, as `base-image-build.spec.ts`
     does.
   The constant name `FLOX_BASE_IMAGE` is referenced by `base-image-build.spec.ts`
   and `base-image-recipe.spec.ts`; keep one exported constant and update both
   call sites in lockstep.

2. **Extend the recipe regression guard.** `base-image-recipe.spec.ts` asserts the
   flox `nix profile add` is pinned to a 40-hex rev in both Containerfiles. Phase A
   adds `nix profile add nixpkgs#zellij` which `02_dev.md` requires be pinned to a
   full commit rev (`github:NixOS/nixpkgs/<rev>#zellij`) for the same GitHub-API
   rate-limit reason. Add a `PINNED_ZELLIJ` pattern
   (`/nix profile add\s+github:NixOS\/nixpkgs\/[0-9a-f]{40}#zellij\b/`) and a
   `FLOATING_ZELLIJ` negative pattern (`/nix profile add\s+nixpkgs#zellij/`) to that
   spec so an unpinned zellij flakeref fails the cheap static guard before it costs
   a 60-req/h-limited image build.

3. **No `wdio.conf.ts` provisioning change** beyond the constant rename: the local
   machine is already provisioned in `onPrepare`, the app build step
   (`pnpm tauri build --debug --no-bundle`) already runs, and
   `SANDBOX_WORKSPACE_ROOT` already points the app's workspace at
   `~/.sandbox-mio-e2e` where the spec reads `.mio/zellij.json` back. No new
   environment flag is needed because the spec creates and destroys its own
   container and writes no host-global state (contrast the SSH-config cleanup the
   deploy path needs).

4. **Page-object additions** in `e2e/test/pageobjects/project-row.component.ts`:
   a `terminalButton` getter (`this.root.$("button=" + <terminal label text>)`,
   matching the rendered `m.projects_terminal()` text) and an
   `async openTerminal()` method that scroll-clicks it, mirroring `start()`/`stop()`.
   The token banner that Phase D surfaces can get a getter too if the spec asserts
   the token is shown in the app window.

## Spec scenario

`web-terminal.spec.ts`, modelled on `runtime-management.spec.ts` (same `before`
to compute `workspaceDir`, same `after` best-effort `podman rm -f`, same
`afterEach` `.diag` dump on failure). Use a wide `this.timeout` (e.g. 600000) for
the create step's possible one-time image build.

1. **Create a local sandbox.** UI action: `ProjectsPage.createProject(name)` on a
   freshly named project. Assertion: the row appears (proving the zellij-tagged
   base image built/exists and the container was created with the publish/pasta
   flags from Phase B — a create that rejected the new flags would never show a
   row).
2. **Start the sandbox.** UI action: `row.start()` then `row.waitForRunning()`.
   Assertion: the running indicator appears (the container must be running before
   `open_terminal` can `podman exec` into it).
3. **Open the terminal.** UI action: `row.openTerminal()` (clicks the "Terminal"
   button, invoking the `open_terminal` command). Assertion: no error banner
   appears and the token banner (Phase D) becomes visible, if surfaced.
4. **Assert the server is online inside the container** (read back through the
   CLI). `podman(LOCAL_CONNECTION, ["exec", name, "zellij", "web", "--status"])`
   contains the spike-observed string `"online"`. This proves the idempotent
   `--daemonize` start ran and zellij is on the global `PATH` (Phase A) without
   `flox activate`.
5. **Assert the token file was written host-side** (read back through the
   filesystem). `fs.readFileSync(path.join(workspaceDir, ".mio", "zellij.json"))`
   parses as JSON containing a non-empty `token` and a `url`. This proves the
   `.mio/zellij.json` workaround landed at the path the frontend passed.
6. **Assert the published port reaches the host** (the decisive end-to-end proof).
   Read the host port with
   `podman(LOCAL_CONNECTION, ["port", name, "8082/tcp"])`, parse the
   `127.0.0.1:<hostport>` line, then `await fetch("http://127.0.0.1:<hostport>/")`
   from the spec process and assert `res.status === 200` and the body looks like
   the web client (e.g. contains an HTML `<title>` or a zellij asset reference).
   Cross-check that the `url` read from `zellij.json` (step 5) points at the same
   host port the fetch succeeded against, proving the command reported the port it
   actually published.
7. **Idempotency.** UI action: `row.openTerminal()` a second time. Assertion: it
   still returns 200 (step 6 repeated) and the container has not spawned a second
   web server (status still `"online"`, a single process) — proving the
   `--status`-before-`--daemonize` guard.
8. **Destroy.** UI action: `row.destroy()`. Assertion: the local container no
   longer exists (`!podmanOk(LOCAL_CONNECTION, ["inspect", name])`), matching the
   cleanup style of the other specs.

The `WebviewWindow` itself is intentionally not asserted in WebdriverIO — see
"Chosen approach" and "Common Gotchas".

## De-risking spike results

**2026-06-27 feasibility spike** (recorded in `01_ideas.md`; script
`docs/features/web-terminal/spike/reproduce.sh`). Run by hand on the developer
machine's default Podman against `sandbox-mio/base:flox`, installing zellij via
`flox install` and launching via `flox activate -- zellij web`. Relevant to the
test, the following risks **cleared**:

- *Published port reaches the Windows host.* With
  `--network pasta:--host-lo-to-ns-lo --publish 127.0.0.1::8082`,
  `Invoke-WebRequest http://127.0.0.1:<hostport>/` returned `STATUS: 200`,
  `Content-Type: text/html`. This is the chain the spec's step 6 asserts.
- *The web server binds only with a config file present.* `zellij web` aborts with
  `Failed to find default config file path` unless `~/.config/zellij/config.kdl`
  exists; the spike created it with `zellij setup --dump-config`. Phase A bakes
  this into the image, so the spec needs no per-run setup — but a missing config is
  a known way the server silently never binds.
- *The token is displayed only once.* `zellij web --create-token` emits the
  plaintext once on stdout and never again, confirming the command must capture it
  at mint time (the spec reads it back from `.mio/zellij.json`, not from zellij).
- *`zellij web --status` reports `"online"`/`"offline"`*, the strings the spec's
  step 4 keys on.

Risks the feasibility spike did **not** clear, and that remain open for the
automated harness (no blocker has a verbatim error yet because none was run):

- **Pasta `--host-lo-to-ns-lo` on the `mio-tests` WSL machine.** *Test concern.*
  The spike used the developer machine's default Podman, not the WebdriverIO
  `mio-tests` machine. Whether that machine's pasta build accepts
  `--host-lo-to-ns-lo` is unconfirmed. A future session should run, against
  `mio-tests`, a one-off `podman --connection mio-tests run -d --network
  pasta:--host-lo-to-ns-lo --publish 127.0.0.1::8082 ...` and `fetch` the port
  before trusting step 6. Does not block writing the spec, but a red step 6 on
  first run points here first.
- **Baked-PATH zellij vs `flox activate`.** *Feature concern.* The spike reached
  zellij through `flox activate`; the feature (Phase A) bakes zellij into the image
  root profile and `open_terminal` runs plain `podman exec ... zellij ...`. That
  exact invocation has not been exercised. The spec's step 4 is the first place it
  is proven.
- **Token line format from `--create-token`.** *Feature concern.* The parser in
  `open_terminal` keys on a `token_<n>: <value>` line (`02_dev.md` Phase C step 3).
  The spike printed the token but the exact stdout format the parser must match was
  not pinned down; a parser mismatch surfaces as an empty `token` in step 5.
- **Loading the URL in a real `WebviewWindow`.** *Test concern, deliberately out
  of scope.* `01_ideas.md` notes launching an actual `WebviewWindow` against the
  loopback URL was never exercised; `tauri-driver` cannot drive it either, so the
  spec asserts the URL serves 200 rather than the window's contents. Manual
  `/verify` covers the window.

**Dominant blocker (feature fix): the feature is unimplemented.** There is no
"Terminal" button and no `open_terminal` command today, so the spec would fail at
step 3 immediately. A spec that goes red at a known blocker is not worth writing
yet — see "Sequencing".

## Sequencing

1. Implement `02_dev.md` Phases A–D (base image bakes zellij; create publishes the
   port; `open_terminal` runtime op + Tauri command; frontend button + webview).
   The spec has nothing real to drive until at least Phase C (the command) and
   Phase D (the button) land.
2. Land the cheap, app-independent harness guards first: extend
   `base-image-recipe.spec.ts` with the pinned-zellij assertion (harness change 2)
   and the `FLOX_BASE_IMAGE` tag/recipe update (harness change 1). The recipe guard
   needs no Podman machine and catches an unpinned zellij flakeref before it costs a
   rate-limited image build.
3. Before writing the full spec, run the one-off pasta/publish check against
   `mio-tests` (the first open test-concern risk above). If it fails, the fix is a
   harness or feature-network concern, not a spec bug; resolve it first so step 6
   is trustworthy.
4. Add the page-object methods (harness change 4) and then `web-terminal.spec.ts`.
   Note this ordering differs from a naive "write the test first" plan: the
   feasibility spike inverted nothing about the topology, but it also did not
   exercise the app path, so the spec is the last thing written, after the feature
   and after the network risk is cleared on the actual test machine.

## Environment notes

State a future session needs:

- **Machines.** Only `mio-tests` (the `LOCAL_CONNECTION`) is required; the
  `mio-tests-remote` machine the deploy specs use is irrelevant here and need not
  be running. `wdio.conf.ts` `onPrepare` provisions `mio-tests` and activates its
  rootless API socket (`/run/user/1000/podman/podman.sock`); if a session runs the
  spec alone, ensure that socket is live (re-run `provisionMachine(LOCAL_CONNECTION)`
  or the full `onPrepare`).
- **Base image.** A zellij-baked base image must exist on `mio-tests` under the new
  `BASE_IMAGE_VERSION` tag, either pre-staged by the updated `ensureFloxBaseImage`
  or built by the app on first `create` (budget ~900 s the first time, ~1.27 GB+).
- **Ports.** The container binds zellij on `127.0.0.1:8082`; Podman publishes it to
  an **ephemeral** host port on `127.0.0.1` (read fresh each run with
  `podman port <name> 8082/tcp` — never hardcode it).
- **Workspace path.** The token file is at
  `~/.sandbox-mio-e2e/<projectName>/.mio/zellij.json`
  (`SANDBOX_WORKSPACE_ROOT` set in `wdio.conf.ts`). `onPrepare`/`onComplete` wipe
  `WORKSPACE_ROOT`, so the file is gone between runs by design.
- **Node fetch.** Step 6 uses the global `fetch` (Node 18+); no extra dependency.

## Common Gotchas

| Gotcha | Cause | Fix |
|---|---|---|
| Row never appears at `createProject`, create rejected | The `mio-tests` machine's pasta build does not accept `--network pasta:--host-lo-to-ns-lo`, so `podman create` (Phase B) errors | Run the one-off pasta/publish check against `mio-tests` (see Sequencing step 3); if pasta rejects the flag, fix the network flag in `src-tauri/src/backends/mod.rs` `create` or the machine's pasta version before relying on `web-terminal.spec.ts` |
| `zellij web --status` does not contain `"online"` after `openTerminal` | zellij is not on the container's global `PATH` because Phase A did not bake it (stale base image under the old `flox` tag, or `BASE_IMAGE_VERSION` not bumped) | Bump `BASE_IMAGE_VERSION` in `src-tauri/src/backends/mod.rs` and rebuild; recreate the sandbox (existing containers do not gain zellij — see `02_dev.md` Lifecycle) |
| `"Failed to find default config file path"` in zellij logs; server never binds | `~/.config/zellij/config.kdl` is absent in the container | Ensure Phase A bakes `zellij setup --dump-config > /root/.config/zellij/config.kdl` into `src-tauri/resources/Containerfile` |
| `.mio/zellij.json` has an empty `token` | The `token_<n>: <value>` stdout parser in `open_terminal` did not match `zellij web --create-token` output | Verify the actual stdout format with `podman exec <name> zellij web --create-token` and align the parser in `src-tauri/src/runtime/mod.rs` (Phase C step 3) |
| `.mio/zellij.json` missing entirely though the terminal opened | `open_terminal` wrote the token to the wrong host path, or the frontend passed a `workspacePath` differing from `SANDBOX_WORKSPACE_ROOT/<name>` | Confirm the frontend passes `project.workspace_path` and the runtime writes to `<workspace_host_path>/.mio/` host-side, not via `podman exec` into the container |
| `fetch("http://127.0.0.1:<hostport>/")` hangs or refuses connection | The host port was read from the wrong source (e.g. hardcoded 8082 instead of the ephemeral published port) or pasta does not forward host-loopback to container-loopback | Read the port with `podman port <name> 8082/tcp` and parse `127.0.0.1:<hostport>`; confirm `--network pasta:--host-lo-to-ns-lo` is on the create command |
| `"API rate limit exceeded for <ip>"` (HTTP 403) during base-image build | The zellij flakeref `nixpkgs#zellij` is unpinned and resolves through the rate-limited GitHub commits API (60 req/h unauthenticated) | Pin to `github:NixOS/nixpkgs/<rev>#zellij` in `src-tauri/resources/Containerfile`; the `PINNED_ZELLIJ` guard in `base-image-recipe.spec.ts` catches a regression cheaply |
| Spec cannot click into or read the terminal contents | `tauri-driver` automates only the main application webview; the terminal's separate top-level `WebviewWindow` is not controllable | Assert the window's precondition (URL serves HTTP 200, token file written) in the spec; cover the live terminal window with manual `/verify`, not WebdriverIO |
| `NIX_REMOTE=daemon` / nix errors when execing into the container | `open_terminal` used a login shell, and `/etc/profile` sets `NIX_REMOTE=daemon` with no nix daemon present | Run `podman exec` without a login shell, matching `flox_exec` in `src-tauri/src/runtime/mod.rs` |
| Git Bash mangles container paths (e.g. `/bin/sh` → `C:/Program Files/Git/usr/bin/sh`) when reproducing by hand | MSYS path conversion in Git Bash on Windows | Prefix manual `podman` reproductions with `MSYS_NO_PATHCONV=1`, as `spike/reproduce.sh` does (the spec itself spawns `podman` with `shell:false`, which is unaffected) |

# Cloud Sandboxes

This document covers the design for a new top-level nav panel, "Cloud Sandboxes," that administers the list of remote Podman hosts a sandbox can be deployed to. The panel is almost entirely a frontend feature: the backend host-management API it drives — `list_hosts`, `add_host`, `prepare_host`, `provision_host` on the `SandboxBackend` trait in `src-tauri/src/backends/types.rs`, wrapped by the Tauri commands `list_sandbox_hosts`, `add_sandbox_host`, `prepare_sandbox_host`, `provision_sandbox_host` in `src-tauri/src/lib.rs:754-788` — already exists and is already implemented by both `PodmanCliBackend` (`src-tauri/src/backends/mod.rs`) and the in-memory mock (`src-tauri/src/backends/mock.rs:92-115`). Only `list_sandbox_hosts` has a frontend caller today (`src/routes/projects/+page.svelte:63`); `add_sandbox_host`, `prepare_sandbox_host`, and `provision_sandbox_host` have zero callers anywhere in `src/`. This document also records desk research into two candidate cloud providers with perpetual free tiers — Oracle Cloud and Google Cloud — for validating a real (non-mocked) remote deploy once the panel exists. Beyond administering already-existing remotes, the panel also gives each provider vendor-specific onboarding: a link to that provider's sign-up/setup guidance, a form to paste the API credentials the app needs to act on the user's behalf, and (once credentials are stored) a "provision a new remote on `<Provider>`" action that creates the cloud VM itself via that provider's API rather than requiring the user to have already created one and authorized SSH access by hand. The companion documents `docs/features/remote-deploys/01_ideas.md` (base-image provisioning on an already-connected remote) and `docs/features/tailscale-access/01_ideas.md` (reaching a deployed sandbox from other devices) cover adjacent, already-scoped concerns that this panel does not re-litigate.

## Current State

**Backend host registry.** There is no app-owned persistence for the list of remotes; `podman system connection list` is the sole source of truth. `PodmanCliBackend::list_hosts()` (`src-tauri/src/backends/mod.rs:637`) runs `podman system connection list --format json` and returns connection names as `Vec<String>`. `PodmanCliBackend::add_host(name, ssh_url, identity)` (`mod.rs:648`) runs `podman system connection add`. `PodmanCliBackend::prepare_host(ssh_url, identity_path)` (`mod.rs:664`) SSHes into an already-reachable host to enable user lingering and start the rootless `podman.socket`. `PodmanCliBackend::provision_host(name, ssh_url, identity_path, on_progress)` (`mod.rs:692`) is the guided end-to-end flow: generate an SSH key if absent, `prepare_host`, `add_host`, then verify, streaming step progress over a Tauri `Channel<serde_json::Value>` — the same progress-channel idiom `install_agent` uses for the credentials page. `ConnectionInfo { host, port, user, identity }` (`backends/types.rs:103`) is the parsed SSH endpoint of one connection, produced by `parse_connection_entry` (`mod.rs:182`) and `remote_connection_info(name)` (`mod.rs:286`), both re-reading `podman system connection list` fresh on every call rather than caching, because a Podman machine's SSH port is reassigned on every boot.

**SSH alias bookkeeping.** `SshAlias { alias, host, port, user, identity }` (`src-tauri/src/ssh/types.rs:17`) is keyed to a Podman connection. `write_alias()` (`src-tauri/src/ssh/mod.rs:124`) renders a marker-delimited `Host` block into the app-owned `~/.ssh/sandbox-mio/config`; `ensure_connection_alias(connection)` (`backends/mod.rs:726`) calls it after re-deriving `ConnectionInfo` fresh each time. `remove_alias()` (`ssh/mod.rs:144`) exists but is marked `#[allow(dead_code)]` with no caller anywhere in the codebase — there is no host-removal flow wired up yet in either direction (Podman connection or SSH alias).

**Frontend deploy picker.** `src/routes/projects/+page.svelte` polls `hosts = await invoke<string[]>("list_sandbox_hosts")` (line 63) and `deployments` via `sandbox_deployments` (line 54), passing both down to `SandboxItem.svelte` as props. `SandboxItem.svelte` renders a per-sandbox inline `<select>` of `hosts` (lines 272-278) backing `chosenHost` state (lines 55-65) and calls `deploy_sandbox` (line 68-73) with the chosen host string. When `hosts` is empty the picker shows `m.projects_no_hosts()` with no way to add one from the UI. `Deployment` (`src/lib/sandbox.ts:14`) is `{ name: string; host: string; status: SyncStatus }` — `host` is a bare connection-name string, mirroring the Rust side's lack of a richer remote model.

**Nav and routing.** `src/routes/+layout.svelte` renders `NavigationColumn` (`src/lib/workspace/NavigationColumn.svelte`), which renders `GlobalNav.svelte`. `GlobalNav.svelte:7-13` is a shadcn `Tabs.Root`/`Tabs.List` driven by a plain `items` array of `{ href, label }`, each `label` a Paraglide message getter; the active tab is derived from `page.url.pathname` (line 15-17). Adding a nav entry is one array entry plus a matching route directory.

**Credential-store precedent for metadata persistence.** `src-tauri/src/credentials/mod.rs` persists per-service bundles at `app_data_dir()/credentials/<service_id>/`, each with a `manifest.json` (`CredentialManifest { captured_at_ms, account_email, expires_at_ms }`, `credentials/types.rs:33`) written via `save_manifest`/`load_manifest` (`credentials/mod.rs:44-58`) using `serde_json::to_string_pretty`. This is the template for any small manifest this feature needs, since `podman system connection list` carries no user-facing label, provider name, or added-at timestamp. The store's manifests are plain, unencrypted JSON on disk — there is no keychain or `tauri-plugin-stronghold` integration anywhere in the codebase — which sets the existing security posture any new secret store in this feature should match rather than silently exceed.

**Static catalogue precedent.** `src/AGENTS.md` documents `src/lib/agents/` and `src/lib/models/` as "static catalogues plus per-agent provisioning descriptors; extend the catalogue file rather than branching on names in components" — the credentials page (`src/routes/credentials/+page.svelte:41-48`) derives its list of services directly from the `AGENTS` catalogue instead of hardcoding service names in the component. A per-provider catalogue is the same pattern applied to cloud vendors.

**HTTP client already available.** `reqwest` is already a dependency of `src-tauri` (`src-tauri/Cargo.toml:43`, `features = ["stream", "json", "native-tls"]`), currently used for model downloads. This resolves, for this feature's Oracle Cloud path (see below), the "new HTTP dependency in `src-tauri`" concern the tailscale-access document (`docs/features/tailscale-access/01_ideas.md`) raised as an open question for its own Tailscale-API key-minting call — no new bare HTTP crate is needed there. For Google Cloud, this feature instead pulls in the official `google-cloud-compute-v1` and `google-cloud-auth` crates from the `googleapis/google-cloud-rust` project (crates.io: `google-cloud-compute-v1`, currently `2.2.0`) rather than hand-rolling Compute Engine REST calls over `reqwest` — see Technology Choices.

## Proposed Model

### Nav entry and route (`GlobalNav.svelte`, new `src/routes/cloud-sandboxes/+page.svelte`)

A new `{ href: "/cloud-sandboxes", label: m.nav_cloud_sandboxes }` entry in the `items` array in `GlobalNav.svelte:7-13`, plus a new locale key mirrored across every file in `messages/` per the root `AGENTS.md` i18n rule. The route is a standalone page under `src/routes/cloud-sandboxes/`, not a workspace pane — it manages state independent of any single sandbox, the same shape as `src/routes/credentials/`.

### Remote list (existing `list_sandbox_hosts`, needs a detail-bearing sibling command)

The panel calls `list_sandbox_hosts` on mount, exactly as `+page.svelte:63` does today, but a bare name list is not enough to render a useful admin panel — the panel needs the host/port/user behind each connection too. `remote_connection_info(name)` (`backends/mod.rs:286`) already computes this but is `pub(super)`, scoped to the `backends` module. Exposing it needs either a new Tauri command (e.g. `sandbox_host_details`, returning `Vec<{ name, host, port, user }>`) or broadening `list_hosts` on the trait to return structured entries instead of bare strings. Widening the existing trait method risks a larger diff across `PodmanCliBackend`, the mock, and `SandboxItem.svelte`'s existing `hosts: string[]` prop; a new additive command is the smaller change and keeps `list_sandbox_hosts` as-is for the deploy picker.

### Add-remote flow (existing `provision_sandbox_host`, currently orphaned)

The panel's "Add Remote" action drives `provision_sandbox_host` — already implemented, already streaming progress over a `Channel<serde_json::Value>` — through a form collecting a display name, the `ssh_url` (`ssh://user@host[:port]/run/user/<uid>/podman/podman.sock`), and an optional identity path. The progress UI follows the collapsible-card pattern already built for `src/routes/credentials/+page.svelte` (`Collapsible.Root`/`Collapsible.Content` per entry, a live step log during the async action, `createActionRunner` from `src/lib/actions.svelte` for busy/error state). `provision_host`'s doc comment on the trait (`backends/types.rs:181-187`) states the hard prerequisite: the public key must already be authorized on the remote, because `ssh` reads passwords from the TTY and not stdin, so `ssh-copy-id` cannot be driven from inside the app. The panel must surface this as an explicit manual step — showing the public key to copy and the exact `ssh-copy-id` invocation — rather than silently failing partway through `provision_host`'s `verify_host` step.

### Remove-remote flow (net new: no backend method exists)

Neither `SandboxBackend` nor the Tauri command layer has a way to remove a registered connection today; `ssh::remove_alias` (`ssh/mod.rs:144`) is unreferenced dead code, confirming nothing currently drives removal. This feature adds a `remove_host(name)` method to `SandboxBackend` (mirroring `add_host`'s shape) that runs `podman system connection remove <name>` and then calls `remove_alias` to clean the corresponding `~/.ssh/sandbox-mio/config` block, plus a wrapping `remove_sandbox_host` Tauri command. Removal must cross-check the current `sandbox_deployments` list (already loaded by `+page.svelte`) for any `Deployment.host` matching the target connection, since removing a connection a sandbox is actively deployed to would orphan that sandbox's remote container with no reachable connection to undeploy or reconnect it through.

### Remote metadata beyond the Podman connection registry (net new: small JSON manifest)

A user managing several remotes needs a memorable label ("Oracle free-tier box") and, optionally, a provider tag, neither of which `podman system connection add` can store — the CLI's connection entries carry only name, destination, and identity. Following the `credentials/mod.rs` precedent, this feature adds a small manifest at `app_data_dir()/remotes/manifest.json`, keyed by connection name, holding additive display metadata (label, provider, added-at timestamp, and — for provider-managed remotes only — the provider-side instance ID needed by the teardown flow below). Podman's own connection registry remains the sole source of truth for reachability and SSH parameters; the manifest is decorative for BYO-host entries and never consulted for their connectivity, so a manifest entry orphaned by an out-of-band `podman system connection remove` (run from a terminal, bypassing this app) is a display-only inconsistency, not a functional break. For provider-managed entries the manifest is load-bearing in one respect: it is the only record linking a Podman connection back to the cloud instance that must be terminated to stop it from consuming free-tier quota or billing.

### Provider catalogue and sign-up guidance (net new: `src/lib/providers/catalogue.ts`)

A static catalogue, one entry per vendor, following the `src/lib/agents/` precedent: `{ id: "gcp" | "oracle", label, signupUrl, setupGuideUrl, freeTierSummary, credentialFields: [...] }`. `signupUrl` links to the provider's account sign-up page; `setupGuideUrl` links to (or the panel renders inline) step-by-step guidance for the one-time console steps a user must complete before pasting credentials — for Google Cloud, creating a project, enabling the Compute Engine API, creating a service account with a scoped role, and downloading its JSON key; for Oracle Cloud, generating an API signing key pair, uploading the public key in the console, and reading off the tenancy OCID, user OCID, and key fingerprint the console displays. `credentialFields` drives a generic form renderer per vendor, since the two providers' credential shapes are structurally different (one JSON blob for Google vs. four discrete fields plus a PEM key for Oracle) rather than a single generic "API key" text box.

### Provider credential capture (net new: `src-tauri/src/providers/credentials.rs`)

A new store, separate from `src-tauri/src/credentials/`, persists each vendor's pasted API credential as `app_data_dir()/providers/<provider_id>/credentials.json`: for Google Cloud, the service-account JSON key content verbatim; for Oracle Cloud, `{ tenancy_ocid, user_ocid, fingerprint, private_key_pem, region }`. This is deliberately a separate module from `src-tauri/src/credentials/` because that store's shape (a `home.tar.gz` directory snapshot captured out of a running container) is built for agent CLI login artifacts, not for a small vendor API secret pasted directly into a form — reusing it would mean inventing a fake "container capture" for data that never touched a container. The new store follows the same plain-JSON-on-disk posture as `credentials/mod.rs` (see Current State) rather than introducing new encryption machinery.

### Provider-managed VM provisioning (net new: `src-tauri/src/providers/` trait + `provision_cloud_remote` command)

A `CloudProvider` trait (one method set, two implementations: `GcpProvider`, `OracleProvider`) wraps each vendor's instance-creation call using the credential stored by the module above for request auth. The two implementations use different transports (see Technology Choices): `GcpProvider` calls the official `google-cloud-compute-v1` crate's `Instances` client; `OracleProvider` hand-signs REST requests over `reqwest`, since Oracle publishes no official Rust SDK. `create_instance(name, ...)` creates a free-tier-shaped VM (Google: `e2-micro` in `us-west1`/`us-east1`/`us-central1`; Oracle: `VM.Standard.A1.Flex` sized to the Always Free 2 OCPU/12 GB ceiling) and polls until the instance reports a running state with a public IP. Critically, both providers accept an SSH public key as instance metadata at creation time (the `Instance.metadata` `ssh-keys` entry in the Google Compute API's request schema, `ssh_authorized_keys` in Oracle's) — so `create_instance` passes the app's own key (the same key `provision_host`'s internal `ensure_key` step already generates or reuses) at creation, and the resulting VM is SSH-reachable under that key immediately, with no manual `ssh-copy-id` step. A new `provision_cloud_remote(provider_id, name)` Tauri command chains: `create_instance` → build the `ssh://` URL from the returned public IP and the provider's default image user (`ubuntu` for both providers' default Ubuntu images) → call the existing `provision_host` (`backends/mod.rs:692`) exactly as the bring-your-own-host flow does, reusing `prepare_host`/`add_host`/verify unchanged. Provider-managed provisioning is additive to, not a replacement for, the existing BYO-host add-remote flow described above — the panel offers both as sibling actions ("I already have a server" vs. "Create one on Google Cloud").

### Provider-side teardown (net new: paired with the remove-remote flow)

Removing a provider-managed remote must offer to terminate the underlying cloud instance through the same `CloudProvider` trait (`delete_instance(instance_id)`), not just run `podman system connection remove` — a connection removed without terminating the VM leaves a running, billable (or free-tier-consuming) instance the user cannot see anywhere in the app again. The proposed `remotes/manifest.json` (see below) is the natural place to record which connections are provider-managed and their provider-side instance ID, since a BYO-host connection has no instance to terminate and a provider-managed one does.

## Technology Choices with Tradeoffs

### Add-remote flow: reuse `provision_sandbox_host`'s guided flow (chosen) vs. automate `ssh-copy-id` vs. a raw "paste an existing connection name" field

Chosen: the panel's add-remote form drives the already-implemented `provision_sandbox_host` (key generation + `prepare_host` + `add_host` + verify, streamed progress).

- **Automating `ssh-copy-id` from the app** — rejected: `ssh` reads the remote account's password from the controlling TTY, not stdin, so no subprocess wrapper can supply it programmatically; the trait doc comment on `provision_host` (`backends/types.rs:185-187`) already states this as a hard constraint the design must respect, not something to work around.
- **A minimal V1 that just lets the user paste the name of a connection they registered themselves via `podman system connection add` in a terminal** — rejected: it would leave `add_sandbox_host` and `provision_sandbox_host` permanently unused, defeats the purpose of building an admin panel (the user would still need a terminal for the one step that matters), and provides nothing beyond what `list_sandbox_hosts` already exposes today.

### Remote metadata persistence: small JSON manifest mirroring the credential store (chosen) vs. Podman connection labels vs. no metadata

Chosen: `app_data_dir()/remotes/manifest.json`, following `credentials/mod.rs`'s `manifest.json`-per-entity pattern.

- **Storing a label/provider tag on the Podman connection itself** — rejected: `podman system connection add` has no field for arbitrary metadata beyond the destination URL, identity path, and an optional default-connection flag; there is nowhere in Podman's own connection model to put a display label.
- **No metadata at all — show the raw connection name and SSH host string** — rejected: the panel's purpose is to let a user distinguish several remotes at a glance ("Oracle free-tier box" vs. "GCP free-tier box" vs. a personal server); a bare hostname or user-chosen connection-name slug is not sufficient for that once more than one or two remotes are registered.

### Free-tier provider candidates for validating the pipeline: Oracle Cloud (chosen candidate 1) and Google Cloud (chosen candidate 2), vs. AWS, DigitalOcean/Hetzner, and Fly.io

Both chosen as the two candidates to spike against, since the deploy pipeline (`deploy` in `backends/mod.rs`, per `docs/features/remote-deploys/01_ideas.md`) only needs a bare Linux host reachable over SSH with a user able to run rootless Podman — any VPS qualifies, so the deciding factor is which providers offer that indefinitely, not just during a trial window.

- **Oracle Cloud Infrastructure "Always Free" tier** — an Ampere `VM.Standard.A1.Flex` (ARM/aarch64) instance, Ubuntu image, SSH-key auth to an `ubuntu` user with `sudo`. As of a tier reduction effective June 15, 2026, Always Free A1 capacity is 2 OCPU / 12 GB RAM total (down from a prior, larger allotment) — still ample for one sandbox's rootless Podman plus the mise base image. No time limit; the allotment does not expire.
- **Google Cloud Platform "Always Free" tier** — one `e2-micro` (x86_64) instance per month, restricted to `us-west1`, `us-east1`, or `us-central1`, with 30 GB of Standard persistent disk. No time limit, but the instance is small (shared vCPU, ~1 GB RAM) and only one is free simultaneously — running a second free instance bills immediately.
- **AWS free tier** — rejected as a candidate: AWS's EC2 free allotment is not indefinite the way Oracle's and Google's are; it is scoped to an account's first 12 months (or, under AWS's newer credit-based free-tier structure, a fixed dollar credit that is consumed and gone), so it does not fit a "spike and revisit anytime" workflow without eventually hitting a hard cutoff or a bill.
- **DigitalOcean / Hetzner** — rejected: neither offers a perpetual free tier, only a one-time trial credit (DigitalOcean) or no free tier at all (Hetzner), which would force repeated new signups to keep testing for free.
- **Fly.io** — rejected: its free allowance is scoped to its own Firecracker-based app-deployment platform, not a general SSH-reachable Linux host; it does not expose the kind of bare VM `podman system connection add` needs.

### Google Cloud credential: pasted service-account JSON key (chosen) vs. OAuth installed-app consent flow vs. `gcloud` CLI delegation

Chosen: the user creates a service account scoped to Compute Engine instance management, downloads its JSON key from the console, and pastes the key content into the app, which authenticates as that service account via `google-cloud-auth` and calls the Compute Engine API through the official `google-cloud-compute-v1` client (see the VM-creation orchestration tradeoff below).

- **OAuth installed-app (loopback redirect) consent flow** — rejected for v1: it requires this project to register and maintain its own OAuth client with Google (client ID shipped in the app, subject to Google's verification process for the scopes requested), and a consent screen adds a browser round-trip the paste flow avoids entirely. It is a plausible v2 upgrade for a less error-prone, individually-revocable credential, mirroring the OAuth-vs-raw-key tradeoff already argued in `docs/features/tailscale-access/01_ideas.md`, but is more engineering than a first cut needs.
- **Shelling out to the `gcloud` CLI with the user's own `gcloud auth login` session** — rejected: it requires the user to have `gcloud` installed and authenticated outside the app, which reintroduces exactly the "needs a terminal" problem the BYO-host paste-a-connection-name alternative was rejected for above, and ties provisioning to a binary this app does not bundle or control the version of.

### Oracle Cloud credential: pasted API signing key set (chosen; no viable single-secret alternative)

Chosen: the user generates an RSA API signing key pair, uploads the public half in the OCI console, and pastes four fields plus the private key PEM into the app — tenancy OCID, user OCID, key fingerprint, region, and the private key content — mirroring the `~/.oci/config` shape OCI's own SDKs expect.

- **A single pasted "API key" string, analogous to a simpler vendor's API token** — not viable: OCI's request-signing scheme is not a single bearer token; every API call is signed with the RSA private key and must be accompanied by the tenancy/user OCIDs and key fingerprint to be verifiable, so the credential form necessarily has more fields than Google's single JSON-blob paste. This asymmetry between the two providers' credential shapes is the reason the catalogue entry (`src/lib/providers/catalogue.ts`) carries a per-vendor `credentialFields` list rather than one shared credential shape.

### Secret storage for provider credentials: plain JSON under `app_data_dir()` (chosen) vs. OS keychain / `tauri-plugin-stronghold`

Chosen: `app_data_dir()/providers/<provider_id>/credentials.json`, unencrypted, matching `src-tauri/src/credentials/mod.rs`'s existing posture (see Current State).

- **OS-native keychain (Windows Credential Manager) or `tauri-plugin-stronghold`** — rejected for this feature specifically: introducing encrypted storage here while every other secret in the app (agent OAuth tokens, Tailscale's OAuth client secret per `docs/features/tailscale-access/01_ideas.md`) stays in plain JSON would make this one class of credential inconsistently harder to back up, migrate, or debug than the rest of the app's secrets, without a stated broader decision to encrypt everything. Revisiting the whole app's secret-storage posture is out of scope for this document; flagged as a candidate follow-up in Open Questions rather than solved unilaterally here, since a cloud provider credential is more damaging if leaked (it can spend money) than a captured agent session token.

### VM-creation orchestration: official `google-cloud-rust` crates for Google (chosen), hand-signed `reqwest` calls for Oracle (chosen, no alternative) vs. bundling each provider's CLI vs. a hosted broker service vs. hand-rolled REST for Google too

Chosen, split by provider because their Rust tooling ecosystems differ:

- **Google Cloud**: `src-tauri/src/providers/gcp.rs` depends on `google-cloud-compute-v1` (crates.io, from the `googleapis/google-cloud-rust` project) for the typed `Instances` client and `google-cloud-auth` for turning the pasted service-account JSON key into credentials the client accepts. Chosen over hand-rolling the Compute Engine REST calls with `reqwest` directly: the official crate is generated from and kept in sync with Google's API definitions, so request/response shapes (including the `Instance.metadata` field carrying the `ssh-keys` entry) are typed and version-checked at compile time instead of hand-built JSON payloads this project would have to keep matching against Google's REST reference by hand as the API evolves.
- **Oracle Cloud**: `src-tauri/src/providers/oracle.rs` hand-signs REST requests over `reqwest` (already a dependency, see Current State), because Oracle publishes no official Rust SDK — the OCI SDKs Oracle maintains directly cover Python, Java, Go, .NET, TypeScript, and Ruby, not Rust. This is a chosen path, not a rejected alternative, but it does mean Oracle's request-signing scheme (an RSA-signed `Authorization` header built from the pasted tenancy/user OCIDs, fingerprint, and private key) has to be implemented and maintained by this project, unlike Google's crate-backed path.
- **Bundling `gcloud`/`oci` CLI binaries with the app** — rejected: it would add external binaries the app downloads, updates, and invokes as a subprocess, on top of the Podman and Mutagen binaries the app already bundles per the root `AGENTS.md`; the API surface this feature needs (create/list/delete one Compute instance) is small enough that a CLI's much larger feature set is unneeded weight, and it reintroduces the "needs an external tool installed/authenticated outside the app" problem the `gcloud`-delegation alternative was rejected for above.
- **A hosted broker service this project operates, holding provider credentials server-side on the user's behalf** — rejected: the product is a local-first desktop app with no backend service today; introducing one solely to proxy cloud-provider API calls would be new infrastructure this project has to run and secure, for a call pattern (a Rust client running on the user's own machine, using the user's own credential) that has no technical need for a middleman.

**Architecture note carried into the remote-deploys design:** Oracle's A1 instance is ARM (aarch64), not x86_64. This is not a blocker for the base image itself — `ensure_image_on` (`backends/mod.rs`, per `docs/features/remote-deploys/01_ideas.md`) builds `sandbox-mio/base:mise` natively on whichever connection it targets from the bundled Containerfile, so it builds an aarch64 image on an aarch64 remote with no cross-compilation involved. It is a residual risk for `reproduce_remote` (`src-tauri/src/runtime/mod.rs`), which reinstalls mise-managed tools from `mise.lock` on the remote: any tool a sandbox has installed must have an aarch64 build available from its upstream release host, or `mise install` fails on that remote specifically. This is a per-tool risk to check during validation, not a pipeline-level blocker.

## Validation

Desk research only, performed 2026-07-06; no in-container or on-VM spike has been run yet.

- Confirmed Oracle Cloud's Always Free Ampere A1 allotment was reduced to 2 OCPU / 12 GB total effective June 15, 2026 (previously larger), and that the default SSH user for an Ubuntu A1 instance is `ubuntu`, not `opc` (which is Oracle Linux's default user) — relevant to what `ssh_url`/user string the add-remote form should default to.
- Confirmed Google Cloud's `e2-micro` Always Free allotment is capped at one instance, restricted to three specific regions, requires the Standard (not Premium) network tier and Standard (not Balanced/SSD) persistent disk to stay free, and includes only 1 GB of free egress per month — all relevant constraints for a spike script or for any onboarding copy the panel shows.
- Not yet confirmed: whether `provision_sandbox_host`'s `prepare_host` step (enabling `systemctl --user enable --now podman.socket` plus lingering) succeeds unmodified on Oracle's Ubuntu A1 image and on GCP's default Debian/Ubuntu `e2-micro` image — both should have rootless Podman installable via each distro's package manager, but neither has been tried end-to-end against this codebase's `provision_host` implementation.

Proposed next spike (not yet run), in two stages:

1. **Manual VM, existing flow.** Stand up a Google Cloud `e2-micro` free-tier VM by hand through the console, authorize the app's SSH key manually (per the `ssh-copy-id` prerequisite above), and drive the already-implemented `provision_sandbox_host` → `deploy_sandbox` pipeline against it (a temporary `invoke()` call from devtools works before this feature's UI exists). Risks this stage must clear: (1) `prepare_host`'s `podman.socket` + lingering steps succeed on GCP's default Debian/Ubuntu image without extra package installs baked in beforehand; (2) `ensure_image_on`'s Containerfile build and the resulting ~324 MB base-image container fit in `e2-micro`'s ~1 GB RAM without OOM; (3) `reproduce_remote` completes `mise install` for at least one representative tool (e.g. `mise use node@lts`) inside that memory budget; (4) the Standard-tier networking and persistent-disk constraints noted above hold in practice (no surprise egress or disk-class billing).
2. **API-driven creation.** Once stage 1 clears, create a service account with a Compute-Engine-scoped role, download its JSON key, and call `google-cloud-compute-v1`'s `Instances::insert` (a throwaway Rust binary is enough before `src-tauri/src/providers/` exists) with the app's public key embedded in the `ssh-keys` instance metadata entry, to confirm the metadata-key injection is sufficient for immediate SSH access with no manual `ssh-copy-id` step — this is the load-bearing assumption behind the "no manual authorization needed for provider-managed remotes" claim in Proposed Model above. This stage also confirms `google-cloud-auth` correctly turns a pasted service-account JSON key into a working credential for the typed client, since the crate's authentication path has not been exercised against this project's paste-flow shape yet.

Oracle Cloud's A1 remains a documented second candidate (see Open Questions) for both stages but is not part of this spike.

## Open Questions

- **Removal safety.** Should `remove_sandbox_host` refuse to remove a connection any `Deployment.host` currently references, or should it force an undeploy first? Undecided — states the risk (orphaning a deployed sandbox's only reachable connection) without picking the guard behavior.
- **Remote metadata manifest shape.** The exact fields of the proposed `app_data_dir()/remotes/manifest.json` entries (a free-text label vs. a fixed provider enum, whether `added_at_ms` is tracked, whether region is recorded) are undecided.
- **Which provider to spike first.** Resolved 2026-07-07: Google Cloud's `e2-micro` is the first validation target (see Validation). Oracle's A1 remains a candidate for a later spike if `e2-micro`'s ~1 GB RAM proves too tight for the base image plus `mise install`, since A1's 12 GB would remove that ceiling at the cost of the ARM risk noted above.
- **Key-generation UX in the add-remote form.** `provision_host`'s internal `ensure_key` step (per its trait doc comment, `backends/types.rs:181-187`) already generates an SSH key if absent — whether the panel exposes "generate a new key for me" as an explicit form choice, shows the resulting public key with copy-to-clipboard for the manual `ssh-copy-id` step, or assumes the user already has a key and has already authorized it, is undecided.
- **Mock backend statefulness for testing.** `PodmanCliBackend`'s mock counterpart (`src-tauri/src/backends/mock.rs:92-115`) has `list_hosts` always return an empty `Vec` and `add_host` is a no-op that mutates nothing, so the light e2e tier cannot currently observe an add-then-list round trip. Whether the mock needs in-memory state to support meaningful light-tier coverage of this panel is undecided and feeds into `03_e2e.md`.
- **Relationship to the per-sandbox deploy picker.** Whether the flat `hosts: string[]` prop `SandboxItem.svelte` renders as a `<select>` (lines 272-278) keeps reading `list_sandbox_hosts` independently, or is refactored to read from whatever store this new panel introduces to back its list, is undecided.
- **Provider-managed provisioning scope for v1.** Whether both Google Cloud and Oracle Cloud ship provider-managed VM creation (`provision_cloud_remote`) at once, or Google Cloud ships first (matching the SSH-spike provider order resolved 2026-07-07) with Oracle's OCI-signing-key flow following once its four-field credential form and request-signing code are validated, is undecided.
- **Instance shape and region: hardcoded free-tier defaults vs. user choice.** Whether `create_instance` always requests the exact free-tier shape/region (`e2-micro` in one of three fixed regions for Google; a capped `VM.Standard.A1.Flex` for Oracle) with no user override, or exposes shape/region as form fields the user can change (risking an accidental non-free, billable choice), is undecided.
- **Provider-side teardown guarantee.** Whether removing a provider-managed remote is allowed to leave the cloud instance running (e.g., the user wants to keep it but disconnect Podman from it) or must always offer/force `delete_instance`, is undecided — this interacts with the runaway-billing risk noted in Common Gotchas below.
- **Provider credential secret-storage posture.** The plain-JSON `app_data_dir()/providers/<provider_id>/credentials.json` approach was chosen to match the rest of the app's existing (unencrypted) secret storage, but whether a cloud credential capable of spending real money warrants OS-keychain-backed storage even though nothing else in the app has that yet is an open, unresolved tension — see the Technology Choices tradeoff above.
- **`google-cloud-compute-v1` maturity and dependency footprint.** The crate (currently `2.2.0` on crates.io) is part of the `googleapis/google-cloud-rust` project; whether its release history is stable enough for a shipped feature to depend on, and how much its transitive dependency tree (likely including `tonic`/`prost` or an internal HTTP transport) adds to `src-tauri`'s build time and binary size, has not been checked against this project's existing `Cargo.toml` — needs a `cargo add google-cloud-compute-v1 --dry-run` (or equivalent) pass before Stage 2 of the Validation spike.
- **Minimal IAM role / OCI policy documented in the setup guide.** The exact least-privilege role set the sign-up guidance instructs the user to grant (Google: a custom role scoped to `compute.instances.*` rather than the broader `roles/compute.instanceAdmin.v1`; Oracle: an IAM policy statement scoped to the free-tier compartment) is undecided and needs to be pinned down before the guidance page copy is written.

## Common Gotchas

| Gotcha | Cause | Fix |
|---|---|---|
| Add-remote form calls `provision_sandbox_host` and it hangs or fails at the verify step | The public SSH key must be authorized on the remote host *before* calling `provision_host`; `ssh` reads passwords from the TTY, not stdin, so the app cannot drive an interactive `ssh-copy-id` | Show the public key and the exact `ssh-copy-id` command in the add-remote form as a manual pre-step, per the constraint documented on `provision_host` in `backends/types.rs:181-187` |
| New remote shows in the panel but never shows in the per-sandbox deploy `<select>`, or vice versa | Two independent call sites read `list_sandbox_hosts` (`+page.svelte:63` and this panel); nothing keeps them in sync beyond both re-invoking the same command | Re-run `list_sandbox_hosts` in both places after any add/remove, or route both through one shared store per `src/AGENTS.md`'s module-scoped `.svelte.ts` pattern |
| Removing a remote in the new panel silently strands a deployed sandbox | No cross-check exists yet between `remove_sandbox_host` and `sandbox_deployments`; a sandbox whose `Deployment.host` points at a removed connection can no longer be undeployed or reconnected through Podman | Check `sandbox_deployments` for a matching `host` before calling the new `remove_host` backend method; block or warn before removing |
| Light e2e spec adds a host through the panel, then asserts it appears in the list, and the assertion fails | The mock backend's `list_hosts` (`backends/mock.rs:92`) always returns an empty `Vec` regardless of prior `add_host` calls | Give the mock an in-memory `Vec<String>` (or equivalent) that `add_host`/`list_hosts` share, resolved as part of `03_e2e.md` |
| `podman system connection add` succeeds but the panel's remote list still shows a stale label after a manual `podman system connection remove` run from a terminal | The proposed `remotes/manifest.json` is decorative metadata never consulted for connectivity, so it does not react to out-of-band changes to Podman's own connection registry | Reconcile the manifest against `list_sandbox_hosts`' current output on load, dropping entries with no matching live connection |
| Deploy to an Oracle Cloud A1 remote fails during `reproduce_remote` on a tool install | Oracle's Always Free A1 instance is ARM (aarch64); a mise-managed tool pinned in `mise.lock` may have no aarch64 build from its upstream release host | Confirm aarch64 availability for each tool before relying on an ARM remote, or prefer the GCP `e2-micro` (x86_64) remote for tools without ARM builds |
| Google Cloud API call returns 403 `Compute Engine API has not been used in project ... before or it is disabled` | The pasted service account belongs to a project where the Compute Engine API was never enabled — a one-time per-project console step separate from creating the service account itself | Add "enable the Compute Engine API" as an explicit step in the sign-up guidance page, before the "create a service account" step |
| Oracle Cloud API call returns `NotAuthenticated` or a signature-verification error | The pasted fingerprint does not match the uploaded public key, or the private key PEM was pasted with mismatched line endings/truncated by a form field | Regenerate the key pair and re-paste all four fields together (tenancy OCID, user OCID, fingerprint, private key) rather than editing one field in isolation |
| A freshly created cloud VM is briefly unreachable over SSH right after `create_instance` reports it as running | Cloud-init/metadata-key propagation on the guest lags a few seconds behind the API reporting the instance as running | Retry `prepare_host`'s initial SSH connection with backoff for the first 30-60 seconds after instance creation, rather than treating the first failed connection as terminal |
| A provider-managed remote is removed from the panel but a bill or free-tier-quota warning shows up later anyway | `podman system connection remove` only deregisters the local Podman connection; it never calls the provider's API to terminate the cloud instance | Always route provider-managed removal through the paired `delete_instance` call (`src-tauri/src/providers/`), using the instance ID recorded in `remotes/manifest.json`, not just `remove_host` |

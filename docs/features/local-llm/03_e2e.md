# Local LLM Models E2E Test Plan

Test plan for the local-LLM feature built in `docs/features/local-llm/02_dev.md`. Phases A–F are now implemented, the bring-up spike cleared (recorded below and in `01_ideas.md` Validation), and the host-only spec plus its page object exist on disk: `e2e/test/specs/local-llm.spec.ts` and `e2e/test/pageobjects/models.page.ts`. The `/models` UI has since evolved past the first cut, and this revision records the current `src/routes/models/+page.svelte` surface so future tests target the real selectors and behaviours. The feature differs from every existing spec in one structural way: the Phase A–F core runs on the Windows **host** and touches no Podman, so the spec reads state from the host filesystem and a real HTTP call to the inference endpoint rather than from `podman exec`. Only the Phase G sandbox-wiring spec uses the container harness, and it is gated on the Phase G spike from `02_dev.md`.

### UI surface changes since first implementation

Four UI changes landed after the original plan; the spec selectors and scenario steps below reflect them:

1. **Per-row runtime-setup checklist scoping (bug fix).** The checklist previously rendered under every catalogue row once any model was running, because its visibility condition tested only global state (`status.running && setupEvents.length > 0`). It is now scoped to the one row whose start produced the events: visibility is `startingModel === descriptor.id || (setupModel === descriptor.id && setupEvents.length > 0)`. `setupModel` records the catalogue id that owns `setupEvents` and outlives `startingModel` (which clears when `start_inference` resolves), so the finished checklist stays pinned to its row.
2. **Downloaded-models-first ordering.** The catalogue is rendered from a `displayModels` derived view that floats downloaded models to the top with a stable sort, preserving the recommend-first / descending-params order from `recommendModels` within each group.
3. **Running endpoint merged into the model row.** The separate status panel is gone. The running model's `<li>` now carries the `data-running` attribute, shows **Running · Endpoint: `<base_url>`** under the model label (`code[data-base-url]`), and swaps its **Start** button (`[data-start]`) for a **Stop** button. Exactly one row can be running at a time (`InferenceStatus` is a single record). The chat test surface moved to its own `section[data-chat]` below the list, still gated on `status.running`.
4. **Auto-collapsing checklist with a View/Hide toggle.** After a start completes, the checklist stays visible for 2 seconds, then a timer sets `stepsCollapsed = true` and `collapsedOnce = true`; the checklist slides closed (`transition:slide`, 300 ms) and a small toggle button appears reading **View details** / **Hide details** (`m.models_view_details` / `m.models_hide_details`). The toggle button only renders after `collapsedOnce` is set — never during the initial 2-second window — and thereafter expands/collapses the checklist in both directions.

## Goal

The spec must prove the real host-side inference path end to end with the llama engine:

1. `detect_machine_specs` (Phase B) returns real host specs — nonzero CPU cores and total RAM read via `sysinfo` — driven by opening the `/models` route.
2. `download_model` (Phase D) streams a real GGUF from Hugging Face to the app data dir, emits progress, computes sha256, and verifies it — proven by the final file existing on the host filesystem at `app_data_dir()/models/<model_id>/` with the expected size.
3. `start_inference` with `engine: "llama"` (Phase B) spawns the **real bundled `llama-server` sidecar** (Phase A), passes the downloaded GGUF, and reports a live `base_url`.
4. A real HTTP `POST <base_url>/chat/completions` returns a non-empty assistant message — the decisive proof that the bundled binary actually loaded the model and is serving the OpenAI-compatible API.
5. `stop_inference` (Phase B) terminates the sidecar — proven by the endpoint no longer accepting connections and no orphaned `llama-server` process.

Beyond the host path, the spec should also lock in the four UI behaviours that changed after first implementation, because each guards a real regression: the checklist must render under **only** the running row (the original bug rendered it under all rows), downloaded models must sort above non-downloaded ones, the running row must show its own `base_url` and a Stop button (no separate status panel), and the checklist must auto-collapse behind a View/Hide toggle.

A weaker test would fail to have teeth in three specific ways: (a) asserting only that the GGUF file appeared on disk would not prove the sidecar can load and serve it (a corrupt-but-correctly-sized file, or a sidecar/model architecture mismatch, would pass); (b) mocking the HTTP endpoint or asserting only `inference_status.running == true` would not prove the model produces tokens; (c) asserting `stepTitles()` is non-empty without scoping the query to the running row would not catch the checklist-leaks-to-all-rows bug — the spec must count checklist blocks and assert exactly one. Step 4's real completion call is the assertion with teeth for the host path.

## Existing Test Styles

Two styles exist, per `docs/e2e-testing.md` (removed 2026-11-05; current harness: `docs/architecture/testing.md`):

- **App-driven WebdriverIO specs** (`e2e/test/specs/*.spec.ts`) drive the compiled Tauri app via `tauri-driver` and exercise real Tauri commands. All existing feature coverage (`runtime-management.spec.ts`, `web-terminal.spec.ts`, `deploy-remote.spec.ts`, `agent-setup.spec.ts`) is here. They read state via `podman exec` (`podman`/`podmanOk` in `e2e/lib/podman-connection.ts`) and the host filesystem.
- **Standalone transport tests** (`e2e/test/remote-workspace-sync.test.js` style) drive a vendored binary directly without the app. Smoke-only, not feature coverage.

The new local-LLM spec belongs to the app-driven style, but is the first such spec whose core assertions read an **HTTP endpoint on host loopback** and the **host app-data filesystem** instead of `podman exec`. It needs no Podman connection for Steps 1–5; only the deferred Phase G spec uses `LOCAL_CONNECTION` (`mio-tests`).

## Chosen Approach

Spec file: `e2e/test/specs/local-llm.spec.ts`. New page object: `e2e/test/pageobjects/models.page.ts` (`ModelsPage`: navigate to `/models`, trigger download, start/stop inference, read status).

Topology: **host-only, no Podman machine**. The Tauri app and the spec run on the same host, so the spec hits the inference `base_url` directly with `fetch`. The llama engine is the only engine exercised automatically; the Foundry engine and the Phase G in-sandbox path are covered by manual spike + conditional specs (below) because Foundry Local is a winget-installed system component that cannot be assumed in CI.

Test model: a **dedicated tiny GGUF**, not a catalogue model. The smallest catalogue model (Qwen2.5-1.5B, ~1.1 GB) is too heavy to download and load per CI run. The spec uses a test-only model (e.g. `SmolLM2-135M-Instruct` GGUF, ~100 MB, or `Qwen2.5-0.5B-Instruct` Q4, ~400 MB) injected via a `MIO_TEST_MODEL` env var that the `/models` route honours in test builds, so the real `download_model` → `start_inference` → completion path is exercised on a model small enough to finish in a couple of minutes. The completion assertion checks only that a non-empty string returns, never specific text — a 135M model's output is not deterministic enough to assert content.

`this.timeout(600000)` (10 minutes): a cold run downloads the test GGUF and loads it into the sidecar; the ceiling must cover a slow network plus first-load.

## Harness Changes

Edits to `e2e/wdio.conf.ts`:

1. **Stage the llama-server sidecar** before the debug build, mirroring the Mutagen sidecar gotcha in `docs/e2e-testing.md` (removed 2026-11-05; current harness: `docs/architecture/testing.md`): place `llama-server-x86_64-pc-windows-msvc.exe` (plus its Vulkan runtime DLLs) at `src-tauri/binaries/` so `pnpm tauri build --debug --no-bundle` bundles it. Without this, `start_inference` fails at sidecar resolution exactly as deploy fails without the staged Mutagen binary.
2. **Set `MIO_TEST_MODEL`** in the spec environment to the tiny test GGUF's `{repo, file, sha256, sizeBytes}` so the `/models` route offers it. Keeping it in env (not the shipped catalogue) prevents a 100 MB test model leaking into the product catalogue.
3. **Cleanup the app-data model store** in `onComplete`: remove the debug build's `app_data_dir()/models/` directory so a downloaded test GGUF does not persist across runs. The debug build's app-data path derives from its bundle identifier in `src-tauri/tauri.conf.json`.
4. No new Podman machine. `onPrepare` still provisions `mio-tests` for the other specs; the local-LLM core spec simply does not use it.

The `before` hook needs no sandbox. The `after` hook calls `stop_inference` (best-effort) so a failed run leaves no orphaned sidecar, and deletes the test model file.

## Page Object — `e2e/test/pageobjects/models.page.ts`

`ModelsPage` (implemented) uses `data-*` attribute selectors, never CSS classes or copy, so the page object survives styling and i18n changes. The rows are keyed by the stable catalogue id (`data-model-id`), not the label. Implemented members:

- `open()` — navigate to `/models` (via the home-page nav link) and wait for `[data-specs]`.
- `specsText()` — read `[data-specs]` text (asserts the probe ran).
- `row(modelId)` — the `<li data-model-id='<id>'>` for one catalogue/test model.
- `startDownload(modelId)` — click `button=Download` inside the row.
- `waitForDownloaded(modelId, timeoutMs)` — poll until the row shows `[data-downloaded]`.
- `startInference(modelId)` — click `[data-start]` inside the row.
- `waitForRunning(timeoutMs)` — poll until `[data-running]` exists (now the running **row**, not a separate panel).
- `baseUrl()` — read `[data-base-url]` (now lives inside the running row).
- `stepTitles()` — collect every `[data-step-id] [data-step-title]` title (used by the checklist assertion).
- `stopInference()` — click `button=Stop` inside `[data-running]`, then wait for `[data-running]` to disappear.

Because the running status merged into the row, `runningPanel`/`baseUrlEl`/`stopInference` resolve against the running `<li>` rather than a standalone section, but their selectors (`[data-running]`, `[data-base-url]`, `button=Stop`) are unchanged, so the existing Steps 1–5 keep working without page-object edits.

New helpers to add for the UI-behaviour steps below (Steps 7–9):

- `modelOrder()` — return the rendered `data-model-id`s top-to-bottom (`$$("[data-model-id]")` mapped to the attribute), to assert downloaded-first ordering.
- `checklistRowCount()` — count rows that render a checklist, e.g. distinct `[data-model-id]` ancestors of `[data-step-id]`, to assert the checklist appears under exactly one row.
- `detailsToggle(modelId)` — the toggle `button` inside the row (matched by `m.models_view_details` / `m.models_hide_details` text), plus `waitForCollapsed(modelId, timeoutMs)` that polls until `[data-step-id]` is absent from the row.

## Spec Scenario — `e2e/test/specs/local-llm.spec.ts`

```ts
describe("Local LLM — llama engine", function () {
  this.timeout(600000);
  // ...
});
```

---

**Step 1 — Suite setup**

`before`: assert `MIO_TEST_MODEL` is set; parse it for the expected `sizeBytes` and on-disk path under the app-data model store. `after`: call `stop_inference` (best-effort) and delete the test model file. `afterEach`: capture `.diag` (URL + page source + screenshot) on failure, identical to `runtime-management.spec.ts` lines 51–65.

---

**Step 2 — Specs probe renders**

Action: `ModelsPage.open()`.

Assertion: the specs block shows a nonzero RAM figure and at least one CPU core. Proves `detect_machine_specs` (Phase B) ran through the real command and returned host (not container-VM) numbers. A value matching the 2 GiB Podman-VM cap would indicate the probe wrongly targeted the container.

---

**Step 3 — Download the test model**

Action: `ModelsPage.startDownload(testModelLabel)`, then `ModelsPage.waitForDownloaded(testModelLabel, 480000)`.

Assertions (host filesystem, not `podman exec`):

```ts
const modelPath = path.join(appDataModelsDir, testModelId, testModelFile);
assert(fs.existsSync(modelPath),
  `Test GGUF ${modelPath} missing after download. This can happen when download_model failed `
  + "the sha256 verify and deleted the .part file, or wrote to a different app-data path.");
const size = fs.statSync(modelPath).size;
assert(size === expectedSizeBytes,
  `Downloaded GGUF is ${size} bytes, expected ${expectedSizeBytes}. A size mismatch means a `
  + "truncated download passed the presence check; download_model must verify sha256 before rename.");
```

Proves `download_model` (Phase D) streamed a real file and the atomic-rename-after-verify path completed.

---

**Step 4 — Start inference and get a completion**

Action: `ModelsPage.startInference(testModelLabel)` with the engine setting at its default (`llama`), then `ModelsPage.waitForRunning(180000)`.

Assertions:

4z. The runtime-setup checklist (Phase F2) renders and completes: the llama steps `detect-device` and `launch-server` appear, reach a done state before `running`, and each carries **non-empty title text**. Proves two things — `start_inference` streamed `RuntimeSetupEvent`s the informative UI consumed (a weaker test that only waited for `running` would miss a broken step stream), and the Paraglide `runtime_step_<id>_*` keys resolve (a blank row would mean a step id was added without its message key).


4a. The running **row** shows a `base_url` of the form `http://127.0.0.1:<port>/v1` (read from `[data-base-url]`, which now lives inside the `data-running` row, not a separate panel). The same row's action button reads **Stop**, not **Start**:

```ts
const baseUrl = await ModelsPage.baseUrl();
assert(/^http:\/\/127\.0\.0\.1:\d+\/v1$/.test(baseUrl),
  `base_url "${baseUrl}" is not a loopback /v1 endpoint. start_inference must report the live `
  + "sidecar port.");
```

4b. A real chat completion returns non-empty content — the assertion with teeth:

```ts
const res = await fetch(`${baseUrl}/chat/completions`, {
  method: "POST",
  headers: { "Content-Type": "application/json" },
  body: JSON.stringify({
    model: testModelId,
    messages: [{ role: "user", content: "Say hello in one word." }],
    max_tokens: 16,
  }),
});
assert(res.ok, `chat/completions returned HTTP ${res.status}. The bundled llama-server sidecar `
  + "did not serve the request — model load may have failed.");
const body = await res.json();
const content = body?.choices?.[0]?.message?.content ?? "";
assert(content.trim().length > 0,
  `chat/completions returned empty content. The sidecar accepted the connection but produced no `
  + "tokens — the GGUF may be corrupt or architecture-mismatched with the bundled llama-server.");
```

Proves Steps in Phase A (sidecar spawn + health) and the OpenAI-compatible serving path. Content is never asserted for exact text — a tiny model is non-deterministic.

---

**Step 5 — Stop inference**

Action: `ModelsPage.stopInference()`.

Assertions:

5a. The running row drops its `data-running` attribute (`[data-running]` no longer exists) and the row's button reverts to **Start**. The row itself stays in the list — only its running state clears.

5b. The endpoint no longer answers:

```ts
let reachable = true;
try { await fetch(`${baseUrl}/models`, { signal: AbortSignal.timeout(2000) }); }
catch { reachable = false; }
assert(!reachable, `Endpoint ${baseUrl} still answered after stop_inference. The sidecar was not `
  + "terminated — it would orphan and hold RAM after the app exits.");
```

Proves `stop_inference` and the single-active-server lifecycle from `02_dev.md` Cross-Cutting Concerns.

---

**Conditional Step 6 — Foundry engine (skipped when absent)**

Guard: read `detect_machine_specs.foundryInstalled`; `this.skip()` when false. When Foundry Local is present, set the engine setting to `foundry`, start the smallest Foundry alias, and repeat the Step 4b completion call against the Foundry-reported endpoint. This step is opportunistic: CI machines without Foundry skip it, and the manual spike (below) is the standing proof for the Foundry path.

---

**Step 7 — Checklist renders under exactly one row (scoping regression)**

Context: this step guards the per-row scoping fix. Before the fix the checklist rendered under every catalogue row once any model was running.

Action: while the model started in Step 4 is running (before stop), call `ModelsPage.checklistRowCount()`.

Assertion: exactly one row contains a `[data-step-id]` checklist, and it is the row whose `data-model-id` equals the started model's id. A count greater than one means the visibility condition regressed to global state (`status.running && setupEvents.length > 0`) instead of the per-row `setupModel === descriptor.id` guard. This step must run before Step 5 (stop clears `setupEvents`/`setupModel` and removes the checklist).

---

**Step 8 — Downloaded models sort first**

Context: catalogue rows are rendered from the `displayModels` derived view, which floats downloaded models above non-downloaded ones with a stable sort.

Action: after Step 3 downloads the test model, call `ModelsPage.modelOrder()`.

Assertion: the downloaded test model's id appears before any non-downloaded model's id in the returned order. With the `MIO_TEST_MODEL` row prepended and then downloaded, it should sit at the top. A failure means the `displayModels` sort was dropped or made unstable (which would also scramble the recommend-first order within each group).

---

**Step 9 — Checklist auto-collapses behind a View/Hide toggle**

Context: after a start completes, the checklist lingers 2 seconds, then slides closed and exposes a **View details** / **Hide details** toggle; the toggle button only appears after the initial auto-collapse.

Actions and assertions, in order:

9a. Immediately after `waitForRunning` (within the 2-second window), the checklist is still visible (`[data-step-id]` present in the running row) and **no toggle button** is rendered yet — `collapsedOnce` is still false. This is why Step 4z's `stepTitles()` assertion is safe: it runs inside this window.

9b. `ModelsPage.waitForCollapsed(modelId, 4000)` — poll until `[data-step-id]` disappears from the row. Proves the 2-second timer fired and the slide-collapse ran. The poll ceiling exceeds the 2 s timer plus the 300 ms slide with margin.

9c. After collapse, a toggle button reading **View details** exists in the row. Click it: the checklist reappears (`[data-step-id]` present) and the button text flips to **Hide details**. Click again: the checklist collapses and the text returns to **View details**. Proves the toggle drives both directions and that the button is gated on `collapsedOnce` (it was absent in 9a).

Note: Steps 7 and 9 share the single running model from Step 4, so order them 4 → 7 → 9 → 5 (stop). Step 8 only needs the post-download state and can run between Step 3 and Step 4.

## Sequencing

1. Implement Phases A–F (`02_dev.md`).
2. Run the **bring-up spike** (stage sidecar, download tiny GGUF, manual completion call); record results in the table above.
3. Stage the `llama-server` sidecar in `e2e/wdio.conf.ts` and wire `MIO_TEST_MODEL` + app-data cleanup.
4. Write `models.page.ts`, then `local-llm.spec.ts` Steps 1–5. (Both files now exist for Steps 1–5; the UI-behaviour steps below are still to be added.)
5. Add the UI-behaviour steps against the implemented selectors: the `modelOrder`/`checklistRowCount`/`detailsToggle`/`waitForCollapsed` page-object helpers, then Steps 7 (scoping), 8 (ordering), and 9 (auto-collapse toggle).
7. Add conditional Step 6 once a Foundry-equipped machine is available.
8. Defer the Phase G in-sandbox spec until the Phase G gating spike clears; it is podman-style (`LOCAL_CONNECTION`) and asserts an in-container `curl` reaches the forwarded host endpoint.

The host-only spec (Steps 1–5) has no dependency on Podman or Phase G, so it can land as soon as the bring-up spike passes.

## Environment Notes

- No Podman machine is required for Steps 1–5; `mio-tests` is provisioned by `onPrepare` only for other specs.
- The `llama-server` sidecar (+ Vulkan DLLs) must be staged at `src-tauri/binaries/` before `pnpm tauri build --debug --no-bundle`, the same staging requirement as the Mutagen sidecar.
- `MIO_TEST_MODEL` must name a small, stable GGUF with a known sha256; the spec asserts that exact size.
- The debug build writes models under its own `app_data_dir()/models/` (derived from the bundle identifier in `src-tauri/tauri.conf.json`); `onComplete` must delete it to avoid cross-run residue.
- The spec hits `http://127.0.0.1:<port>` directly because it runs on the same host as the app; no Mutagen forward is involved (forwarding is only for the in-sandbox Phase G path).
- A network connection is required for the model download; the OpenAI completion call in Step 4 is fully local (no internet).
- Foundry Local (Step 6) requires the `Microsoft.FoundryLocal` winget package; absent it, Step 6 self-skips.

## Common Gotchas

| Gotcha | Cause | Fix |
|---|---|---|
| `start_inference` fails at sidecar resolution in the e2e build | `pnpm tauri build --debug --no-bundle` did not bundle `llama-server` because the binary was not staged | Stage `llama-server-x86_64-pc-windows-msvc.exe` (+ Vulkan DLLs) at `src-tauri/binaries/` before the build, mirroring the Mutagen sidecar staging in `docs/e2e-testing.md` (removed 2026-11-05; current harness: `docs/architecture/testing.md`) |
| Step 4b returns HTTP 503 / connection refused despite `running: true` | The health poll passed before the model finished loading, or the sidecar reported ready prematurely | Poll `GET /health` with a size-proportional timeout in `LlamaServerEngine::start`; in the spec, wrap the completion call in a short retry loop |
| Step 3 size assertion fails with a slightly different byte count | `MIO_TEST_MODEL` `sizeBytes` was copied from a different quantization of the same model | Re-derive `sizeBytes` and `sha256` from the exact file URL during the bring-up spike and update the env value |
| Downloaded GGUF persists and grows the disk across runs | `onComplete` did not delete the debug build's `app_data_dir()/models/` directory | Add the app-data models cleanup to `onComplete` in `e2e/wdio.conf.ts`; the path derives from the bundle identifier in `src-tauri/tauri.conf.json` |
| Step 5 endpoint still answers after stop | `stop_inference` dropped the `ServerHandle` without killing the `llama-server` child process | `LlamaServerEngine::stop` must kill the `CommandChild`; confirm the `RunEvent::Exit` hook in `src-tauri/src/lib.rs` also stops the active server |

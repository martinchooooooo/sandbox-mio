# Parallel Worktree E2E Runs — E2E Test Plan

This document is the test plan for the feature specified in
`docs/features/parallel-worktree-e2e/02_dev.md`: the run identity and the two run locks (Phase A),
worktree-scoped process killing (Phase B), app-data isolation in Rust (Phase C), the slug-keyed
workspace root and tier-gated `~/.ssh` teardown (Phase D), port pair allocation (Phase E), and
worktree asset staging plus the per-run staging cost (Phase F). **Every phase is `Remaining`**, so
nothing described here can be written yet; see Sequencing.

A 3-step spike was run on 2026-08-02 (`01_ideas.md`, Validation) — sequential then concurrent light
runs across two worktrees with hand-set, uncommitted overrides standing in for the not-yet-built
`e2e/lib/run-identity.ts`. It confirmed the mechanism (ports, workspace root, settings/credentials
redirection, a worktree-scoped process filter) end to end, including under genuine concurrent overlap,
and surfaced one open item folded into "De-risking spike results" below. The facts the plan otherwise
rests on were established by reading code and running read-only commands (`02_dev.md`, The concrete
model); of the two riskiest of them, the spike could not directly exercise "the WebDriver config
module is re-evaluated per worker process" (no `run-identity.ts` existed to probe), so the automated
spec below is still what's shaped to catch that one if it turns out to be wrong. The other — that
`app_log_dir()` resolves to Local rather than Roaming AppData — is a `dirs`/Tauri source-reading claim
the spike had no reason to re-check.

## Goal

The feature under test is the test harness itself, which makes the usual framing inapplicable: there
is no user-facing behaviour to drive through the UI, and the thing that would break is the machinery
every other spec runs on. The test plan therefore has to prove three different kinds of claim, and
only the first is a spec.

**The app honours the isolation the launcher set up.** After a run, the settings file, the credential
store, the model store, and `mio.log` must all sit under the slug-keyed app-data root, and the fixed
pre-feature paths must be empty. This is a real assertion about Rust behaviour — `paths.rs`'s
override precedence, and the deliberate asymmetry that leaves `app_log_dir()` alone when
`MIO_APP_DATA_DIR` is unset — and it is what a light spec can prove.

**Nothing regressed for a single-worktree run.** Every existing spec in every tier runs on the
harness this feature rewrites. The plan's largest risk is not that concurrency fails but that the
ordinary case breaks: an over-narrowed process filter leaves a stale `sandbox-mio.exe` locking its
own `.exe` and the build dies on LNK1104, a mis-set `config.port` fails every session, a skipped
asset copy leaves `local-llm.spec.ts` with no sidecar.

**Two worktrees genuinely ran at the same time without touching each other.** Two green runs are not
evidence of this on their own — two runs that never overlapped on a shared resource are also green.
The pass criterion has to be positive evidence of isolation, not the absence of a failure.

A weaker plan — "run it twice and see if it passes" — would miss all three of the failure modes that
matter. It would not notice that the second run was serialised behind the first by an unrelated
lock, that the isolation came from luck rather than the slug, or that the shipped app's log directory
moved as a side effect.

## What cannot be an automated spec, and why

WebdriverIO cannot orchestrate two of itself: the launcher owns `onPrepare`/`onComplete`, the locks,
the port allocation, and the process killer, and none of those is observable from inside a spec that
the same launcher started. A spec also cannot observe `onComplete`, which is where the `~/.ssh`
teardown and the model cleanup live, because the worker is gone by then.

Everything in those two categories is a documented manual procedure below rather than an
unwritten aspiration. They are short, and each has an explicit pass criterion.

## Existing test styles

Specs are WebdriverIO/mocha files under `e2e/test/specs/<tier>/`, driven through `tauri-driver`
against a real debug build. Light specs reach the app through `invokeCmd()` in `e2e/lib/mock.ts`
(`window.__TAURI_INTERNALS__.invoke` from inside the webview) and script the process layer with
`configureMock()`; `useMockControl()` is mandatory at `describe` scope for any spec that scripts.
Assertions use `assert` from `node:assert` for plain values and `browser.waitUntil` with a
`timeoutMsg` for convergence, with every wait budget taken from a named constant in
`e2e/lib/timeouts.ts`. `captureDiagOnFailure()` from `e2e/lib/diag.ts` provides the failure dump.

Two existing specs establish the shape this plan needs: `standard/base-image-recipe.spec.ts` parses
repository files and never opens a page, and `standard/forward-sweep.spec.ts` uses `browser` only to
poll out-of-band state. Both are accepted specs that assert on the filesystem rather than the DOM,
which is precisely what a harness-isolation spec does. Neither calls `captureDiagOnFailure()`,
because a page dump would be noise rather than evidence — the new spec follows them in that.

## Chosen approach

Three layers, in the order they give signal.

### Layer 1 — `light/run-identity.spec.ts`, the automated isolation spec

A light spec that imports `e2e/lib/run-identity.ts` directly and asserts against the filesystem the
running app actually wrote to. It belongs in `light/` because it needs a running app but no real
infrastructure, and it runs in seconds, which means it runs on every iteration of the loop this
feature exists to serve.

The spec depends on one design property from Phase A: importing `e2e/lib/run-identity.ts` must be
free of side effects in a worker, because a spec runs in the worker process. `IS_LAUNCHER` gating
already exists for correctness reasons (`02_dev.md`, Resolved Decision 8); this spec is the second
consumer of it, and would acquire or release the run lock from inside a test without it.

Care is needed to keep the assertions from being tautologies. Recomputing a path from the same module
that produced it and comparing the two proves nothing. Each assertion below either compares the
module's output against the filesystem the *app* wrote, or checks a property the module could
plausibly lose in a future edit.

### Layer 2 — the existing suites, single worktree

`./build e2e light` and `./build e2e` from one worktree, with no second worktree running. This is the
regression gate for the harness rewrite and it gates the concurrency work: a phase that breaks the
ordinary run is not ready to be tested for concurrency.

### Layer 3 — the manual procedures

Five short procedures covering the launcher behaviour no spec can see: the concurrency proof, the two
locks, the process filter, and the tier-gated teardown.

## Spec scenario

**File**: `e2e/test/specs/light/run-identity.spec.ts`. No `useMockControl()` — the spec installs no
overrides. No `captureDiagOnFailure()`, following `base-image-recipe.spec.ts`.

**Step 1 — the slug is deterministic, path-derived, and discriminating.** Computing the slug twice
from the same worktree root yields the same value; computing it from a synthetic different root
yields a different one; both are non-empty and contain only characters legal in a Windows path
segment and a filename. This is the property every other guarantee rests on — a slug that varies
between two runs in one worktree turns `onPrepare`'s self-healing delete into an unbounded directory
leak, and one that collides between worktrees silently restores every collision the feature removes.

**Step 2 — the four roots are distinct, and each carries the slug.** `APP_DATA_ROOT`,
`WORKSPACE_ROOT`, and the settings and credentials subdirectories are pairwise distinct and each
contains `RUN_SLUG`. This is the assertion that catches a partial revert: a future edit that re-roots
one of them at a fixed path passes every other check in this file.

**Step 3 — the pre-feature fixed paths are unused.** `~/.sandbox-mio-e2e-appdata` (no slug) does not
exist. The whole point of Phase C is that no worktree writes there any more, and its continued
absence is a cheap, decisive check that the app is reading the environment the launcher set rather
than falling through to a compiled-in default.

**Step 4 — the app wrote its settings under the slug-keyed root.** Round-trip `set_settings` then
`get_settings` through `invokeCmd()` with a non-default value, then assert from the spec process that
`settings.json` exists under `<APP_DATA_ROOT>/settings` and contains that value. `local-llm-ui.spec.ts`
already round-trips these commands to prove engine persistence; this step adds the *location* claim
the existing spec does not make. The value chosen must not be the one `local-llm-ui.spec.ts` asserts
on, and the spec restores the default afterwards, since `onPrepare`'s wipe is per run and both specs
share one app-data root within a run.

**Step 5 — the app wrote its log under the slug-keyed root.** A file whose name begins with `mio.log`
exists under `<APP_DATA_ROOT>/logs` and is non-empty. The name is a prefix match, not an equality
check: `tracing_appender::rolling::daily` in `init_logging()` suffixes the base name with the date,
so the file on disk is `mio.log.<YYYY-MM-DD>`. This step is the only automated proof of the
`MIO_APP_DATA_DIR` override branch in `paths.rs`, since settings and credentials are covered by their
own higher-precedence variables and would pass whether the root works or not. Given the spike's
finding (De-risking spike results, above) that the log did not visibly flush even by the end of a
short spec, assert this with `browser.waitUntil` against a real timeout rather than a single
point-in-time check, and confirm separately — before relying on the step — that `init_logging()`'s
`WorkerGuard` is actually held/flushed before the process exits.

**Step 6 — the port pair the launcher chose is the pair in force.** `MIO_DRIVER_PORT` is set in the
worker's environment, equals the port the session is connected on, and sits inside the window
`e2e/lib/run-identity.ts` derives from the slug. This is the assertion that fails if the port ever
goes back to being probed at module scope, where the launcher's log line and the worker's actual port
can diverge (`02_dev.md`, Resolved Decision 7).

**Step 7 — the workspace root the app uses carries the slug.** `SANDBOX_WORKSPACE_ROOT` in the
worker's environment equals `WORKSPACE_ROOT`. Whether the light create flow actually materialises a
directory there under `MIO_MOCK_BACKEND=1` is unverified — check it while writing the spec, and if it
does, assert the created sandbox's directory lands under the slug-keyed root. If it does not, leave
the on-disk claim to the standard tier rather than asserting something the mock path never exercises.

## Harness changes

`e2e/lib/run-identity.ts` must export what the spec asserts on — `RUN_SLUG`, `WORKTREE_ROOT`,
`APP_DATA_ROOT`, `WORKSPACE_ROOT`, the port window bounds, and the slug derivation as a callable
function so Step 1 can apply it to a synthetic root. Exporting the derivation function rather than
only its result is a test requirement, not an implementation preference, and Phase A should land it
that way.

No changes to `onPrepare` or `onComplete` are needed for the spec. Nothing in it provisions
infrastructure, and it adds no new wait budget to `e2e/lib/timeouts.ts` — every step is a filesystem
or environment assertion plus one command round-trip, which reuses the budget
`local-llm-ui.spec.ts` already uses for `set_settings`.

## Manual procedures

**P1 — concurrency with isolation evidence.** Start `./build e2e light` in two worktrees close enough
together that both are in their spec phase at the same time; confirm the overlap from the timestamps
in each run's output rather than assuming it. Both runs pass, and afterwards each worktree's
`APP_DATA_ROOT` holds its own `mio.log.<date>` whose contents cover only that run's session. Two
distinct app-data roots exist, each containing the other worktree's slug nowhere. The overlap
confirmation is the part that makes this a proof rather than a coincidence.

**P2 — the worktree lock refuses a second light run in one worktree.** Start `./build e2e light`,
and while it runs start it again from the same worktree. The second exits non-zero, before any
deletion, naming the holding process id. The first run completes normally and its workspace and
app-data directories are intact — the failure mode this lock exists to prevent is the second run's
`onPrepare` wiping the first run's directories, so "the first run still passed" is part of the pass
criterion.

**P3 — the host lock refuses a second standard run, and does not refuse a light one.** With
`./build e2e` running in one worktree, `./build e2e` in another exits non-zero naming the holder and
its worktree, while `./build e2e light` in a third proceeds normally. The second half matters as much
as the first: a host lock that a light run takes would serialise the whole development loop and
defeat the feature.

**P4 — the process filter kills its own worktree's strays and nothing else.** Leave a stale
`sandbox-mio.exe` running from worktree A's `target/debug`, and another from worktree B's, then run
in A. A's stray is gone and the build succeeds; B's stray survives. Both halves are load-bearing: an
over-narrowed filter leaves the stale exe holding a file lock and the build fails with LNK1104, which
is the original bug the killer was written for, and an under-narrowed one kills B's run. Repeat once
with worktree B nested under A (`.claude/worktrees/`), which is the case a root-prefix filter gets
wrong.

**P5 — a light run leaves `~/.ssh` alone.** Seed `~/.ssh/sandbox-mio/config` and the
`Include sandbox-mio/config` line in `~/.ssh/config`, run `./build e2e light` to completion, and
confirm both survive. Then run `./build e2e` and confirm both are cleaned up as before — the gate
must be tier-scoped, not a removal of the cleanup.

## Phase-to-check map

Phase A is covered by Steps 1 and 2 for the identity, and by P2 and P3 for the locks. Phase B is
covered by P4 only. Phase C is covered by Steps 3, 4, and 5, plus one check no spec can make: with
`MIO_APP_DATA_DIR` unset, a plain `./build dev` must still write its log under Local AppData, which
is the regression that would otherwise ship silently to users. Phase D is covered by Step 7 and P5.
Phase E is covered by Step 6 and by P1. Phase F is covered by a one-off procedure — create a genuinely
fresh worktree, stage it with `build dev --setup-worktree <path>` from an existing one, and run
`./build e2e light` in it — and, for the staging-cost half, by comparing the wall-clock time of two
consecutive light runs in one worktree, where the second must not re-copy the ~180 MB of assets.

Phase B is the phase with the thinnest automated coverage and the sharpest failure mode, which is why
P4 is written as two positive assertions rather than one.

## De-risking spike results

Both questions were checked by the `01_ideas.md` spike; one is settled, one is not.

**`set_settings` under `MIO_MOCK_BACKEND=1` reaches the real `settings::save`.** Settled, yes. The
spike's two worktrees each wrote a real `settings.json` with real content (`{"inferenceEngine":...}`)
under their hand-set, worktree-specific settings directory. Step 4 can be written as planned.

**Whether the light tier's app writes a `mio.log` at all within a run short enough for Step 5 to see
it.** Still open, and reading `init_logging()` (`src-tauri/src/lib.rs:1275`) against the vendored
`tracing-appender-0.2.5` source narrows it to two separate facts, only one of which is fixed by intent
today.

`init_logging()` calls `Box::leak(Box::new(guard))`, permanently leaking the `WorkerGuard`. That
guard's `Drop` impl (`non_blocking.rs`) is the *only* code path that signals the worker thread to
shut down and blocks (up to 1s) waiting for it to drain whatever is still queued — leaking it opts out
of that guarantee for the process's entire lifetime, not just at startup. Concretely: anything enqueued
but not yet drained by the worker at the moment `closeTauriDriver()`'s `tauriDriver?.kill()` forcibly
ends the process is lost, since nothing waits for the worker to catch up. This is a real gap and
independent of Phase C — see Harness changes / Phase C note below.

That said, the leaked guard does not explain a file staying at *0 bytes for its entire, much
earlier-timestamped lifetime*, which is what the spike observed — the worker thread does not batch on
a timer, it blocks on `recv()`, drains and `write_all`s each message straight to the underlying `File`
(no Rust-side buffering) as soon as it's scheduled, then flushes, so under an ordinarily-running
process log lines should land within about one scheduler tick of being emitted, well inside a 5–9
second spec — the leaked guard only threatens the last few lines right at a forceful kill, not the
whole file. The spike could not distinguish "genuinely never gets scheduled in time" from "wrong
`log_dir` resolved for a debug build" or "level filter suppressing it" from the evidence gathered.
**Before Phase A/C land, run the debug app normally (no immediate kill, e.g. `pnpm tauri dev` or a
manual `--no-bundle` launch) and confirm `mio.log.<date>` receives *any* content at all** — that
isolates the mystery from the flush-on-kill gap above. If it does receive content under a clean exit,
Step 5 only needs to guard against the kill-timing gap (`browser.waitUntil` with a real timeout, run
late in the spec); if it does not, something upstream of flush timing is wrong and needs its own
investigation before the spec is written.

## Sequencing

1. Land Phase A. Write Steps 1 and 2 against it and run them; they need no other phase.
2. Land Phases B, C, and D. Add Steps 3, 4, 5, and 7. Run P4 and P5, and the `./build dev` log-location
   check from the phase map. At this point cross-worktree work is safe sequentially, and Layer 2 —
   both suites green from one worktree — is the gate before going further.
3. Land Phase E. Add Step 6. Run P1, P2, and P3; concurrency is only meaningful from here.
4. Land Phase F. Run the fresh-worktree procedure and the consecutive-run timing check.
5. Land Phase G, and fold P1–P5 into `e2e/AGENTS.md` in whatever abbreviated form survives as a
   habit — a manual procedure nobody re-runs is a procedure that stops being true.

## Environment notes

The spec assumes the run was started through `./build e2e light` or `pnpm run test:light`, so
`IS_LIGHT_RUN` resolved true and `MIO_MOCK_BACKEND=1` reached the app. An ad-hoc single-file
invocation still gets the mock, because `beforeSession` decides from the resolved spec paths, but
`onPrepare`'s launcher-side view can differ — the `argValues()` flag-spelling gotcha in
`e2e/AGENTS.md` applies to every step here that reads a launcher-set variable.

P1 needs two worktrees that are both staged (Phase F) and both on a commit where the phase under test
has landed. A worktree on an older commit is a valid test subject for the process filter in P4, since
that only concerns paths, but not for anything that depends on `run-identity.ts` existing on both
sides.

P3 needs the standard tier's machines, so it costs minutes and belongs to the once-per-feature
cadence rather than the loop. P2 and P4 are seconds and can run whenever.

The concurrency procedures load the machine with two debug builds at once. Cargo's global package
cache lock will serialise the two builds' registry access — the "Blocking waiting for file lock on
package cache" line is expected contention, not the failure P1 is looking for.

## Common Gotchas

| Gotcha | Cause | Fix |
|---|---|---|
| Step 5 fails because no `mio.log` exists under the app-data root | `tracing_appender::rolling::daily` writes `mio.log.<YYYY-MM-DD>`, not `mio.log` | Assert on a directory entry whose name starts with `mio.log`, never on the exact name |
| Step 5 fails intermittently, even at the end of the spec | The non-blocking writer's buffer may not flush before `closeTauriDriver()` kills the process (spike finding, `01_ideas.md` Validation) — not just an ordering issue within the spec | Use `browser.waitUntil` with a real timeout rather than a point-in-time check; confirm `init_logging()`'s `WorkerGuard` is held/flushed before process exit |
| Step 4 passes whether or not `MIO_APP_DATA_DIR` works | `settings_path()` checks `MIO_SETTINGS_DIR` first by design, and the launcher sets it | Treat Step 5 (the log) as the only automated proof of the root override; Step 4 proves the slug-keying, not the fallback |
| Every assertion passes but proves nothing | The spec recomputed a value from the same module that produced it and compared the two | Assert against the filesystem the app wrote, against the worker's inherited environment, or against a property a future edit could lose — never module output against itself |
| The spec acquires or releases the run lock while running | `e2e/lib/run-identity.ts` is imported by the spec, which runs in a worker, and the config module's side effects are gated on being the launcher | Keep every side effect in that module behind `IS_LAUNCHER`; a spec importing it must be inert |
| Both worktrees pass P1 but nothing was actually concurrent | The second run started after the first finished, or was serialised behind a lock | Confirm the overlap from timestamps in both runs' output before reading the result as a pass |
| P4 passes on sibling worktrees and fails on the nested one | A filter built from the worktree root rather than its full `src-tauri\target\debug\` path matches the nested worktree's paths too | Run P4 once with the second worktree nested under `.claude/worktrees/`, which is the only arrangement that catches it |
| A stale `sandbox-mio.exe` survives and the build fails with LNK1104 | The process filter was narrowed past the invoking worktree's own strays | P4's first assertion is that A's own stray dies; an over-narrowed filter restores the original bug the killer exists for |
| The shipped app's log location changes and no test notices | Every automated step runs with `MIO_APP_DATA_DIR` set, which is exactly the branch that is supposed to differ | Run the `./build dev` log-location check from the phase map by hand after Phase C; it is the only coverage of the unset branch |

# Sandbox Runtime Management Build Plan

This document is the build plan for managing the software installed inside a sandbox: installing packages, recording what is installed, and reproducing that software on a remote host at deploy time. It continues `docs/features/sandbox-runtime-management/01_ideas.md` and **supersedes the engine decision recorded in an earlier revision of this plan**: the engine was flox (built on Nix), and flox is what currently ships in the codebase, but a 2026-06-27 spike replaced flox with [mise](https://mise.jdx.dev) to shrink the sandbox base image from 1.84 GB to 324 MB. Status: the mise migration is implemented in the Rust backend and the base-image recipe (Phases A, B, C, and the reproduce engine of D); what remains is the deeper e2e spec rewrite (`runtime-management.spec.ts`), a deploy verification run, and a `GITHUB_TOKEN` pass-through. The former flox engine has been replaced in code. Relevant files: container lifecycle in `src-tauri/src/backends/mod.rs`, backend contracts in `src-tauri/src/backends/types.rs`, the runtime engine in `src-tauri/src/runtime/mod.rs` and `src-tauri/src/runtime/types.rs`, command wiring in `src-tauri/src/lib.rs`, and the workspace-sync lifecycle in `docs/features/remote-sync/02_dev.md` that this feature plugs into.

## The Concrete Model

A sandbox carries a mise tool environment whose `mise.toml` (human-readable intent) and `mise.lock` (pinned, checksum-verified lockfile) are the single source of truth for the sandbox's software. Both files live in the sandbox workspace at `/root/work`, which `workspace_path` in `src-tauri/src/backends/mod.rs` (line 52) computes and `create` bind-mounts at `WORKSPACE_MOUNT` (`/root/work`, line 36). Because both files sit in the workspace, the Mutagen sync session from the remote-sync feature (`docs/features/remote-sync/02_dev.md`) carries `mise.toml` and `mise.lock` to the laptop and to the remote host with no separate transfer.

The container runs a single static `mise` binary. There is no Nix store, no daemon, and no per-package glibc closure: mise downloads prebuilt upstream release binaries (GitHub releases via the aqua and ubi backends, plus language-runtime backends) and verifies them against the lockfile checksums. mise and the in-app terminal engine zellij are baked into the sandbox base image so sandbox creation pays no download. A user installs software through a backend command that runs `mise use <tool>@<version>` inside the container over `podman exec`; mise rewrites `mise.toml` and `mise.lock`, so every install writes the record as a side effect. Listing installed software reads the `[tools]` table of `mise.toml` rather than inspecting the container filesystem.

The sandbox base image is **debian:12-slim (glibc)**, not Alpine. The 01_ideas decision to keep Alpine rested entirely on Nix packages carrying their own glibc closure; removing Nix removes that rationale. mise installs prebuilt upstream binaries, and many language runtimes (Node.js from nodejs.org, for example) are published only against glibc, so they fail on musl. A slim glibc base (measured 324 MB with mise and zellij baked) unlocks the full mise catalog while remaining 5.7× smaller than the 1.84 GB flox image.

Deploy stops shipping the committed image for software, exactly as the flox plan intended. After the remote container is created from the same mise-baked base image and the workspace sync has seeded `mise.toml` and `mise.lock` onto the remote, deploy runs `mise install` on the remote container, which reads the lockfile and downloads the identical checksum-pinned binaries from the upstream release hosts. The transfer is the size of the manifest plus lockfile (measured 3 KB in the spike), not the size of a committed image.

## Spike Validation (2026-06-27)

A hands-on spike on the local `podman-machine-default` connection cleared the two risks the engine switch introduced. Artifacts live in `docs/features/sandbox-runtime-management/spike/mise/` (`Containerfile.glibc`, `Containerfile.musl`).

- **mise runs on the sandbox base.** The pinned `mise v2026.6.14` musl static binary ran on `alpine:3.24`; the glibc build ran on `debian:12-slim`. The mise binary itself is ~97 MB and dominates the base-image size.
- **zellij installs through mise with the `web` subcommand.** `mise install zellij@0.44.3` resolved to the `aqua:zellij-org/zellij` backend, downloaded the `zellij-x86_64-unknown-linux-musl` asset, and the binary reported `zellij 0.44.3` with a working `zellij web` subcommand (the terminal requires zellij ≥ 0.43.0). Symlinking the installed binary onto `/usr/local/bin/zellij` made it run standalone, off any per-sandbox env — the same global-PATH model the flox base used.
- **The lockfile is stronger than flox's.** `mise.toml` recorded intent (`jq = "latest"`); `mise.lock` recorded the resolved version (`1.8.2`) with per-platform SHA256 checksums, download URLs, and `github-attestations` provenance. Reproducing from a 3 KB `mise.toml` + `mise.lock` transfer on a fresh container installed byte-identical `jq 1.8.2`.
- **The musl gotcha is real and is why the base is glibc.** `mise use node@22` failed on `alpine:3.24` with exit code 127 (the core `node` backend downloads glibc-linked binaries from nodejs.org that do not run on musl) and succeeded on `debian:12-slim` (`node v22.23.1`). Static-linked CLI tools (jq, zellij) ran on both bases; glibc-only language runtimes need the glibc base.
- **mise's documented musl-node path does not rescue the musl base, despite the binaries existing.** Prebuilt musl Node binaries do exist on the unofficial-builds mirror (`https://unofficial-builds.nodejs.org/download/release/v22.9.0/node-v22.9.0-linux-x64-musl.tar.gz` is present); the blocker is mise's resolver, not a missing asset. Both musl levers the docs (`https://mise.jdx.dev/lang/node.html`) describe — `node.flavor=musl` and `libc=musl` — were tested on `alpine:3.24` with mise `v2026.6.14` and both hit the same code path: the verbose log prints `NodePlugin: we will fetch the source and compile`. The `core:node` backend decides to compile from source on musl *before* honoring the flavor/libc setting; the setting is read (`mise settings` reports it) and feeds only the error hint, never the binary URL. With the default mirror that means a compile-from-source that needs a full C++ toolchain (gcc/g++/make/python3) baked into the base image — erasing the musl size advantage — and a multi-minute build on every install. With the unofficial-builds mirror mise still builds the source-tarball name (no `-linux-x64-musl` segment) and 404s. The prebuilt-musl path is therefore unreachable through mise's `core:node` backend in this version; the glibc base needs none of these settings. The glibc base needs none of these settings.
- **GitHub rate limiting is a reproducibility risk.** Unauthenticated installs hit `HTTP 403` on the GitHub version-listing API (the same 60-req/h limit that broke flox's HEAD resolution). Installs of exactly-pinned versions still proceeded, but the build and runtime should pass a `GITHUB_TOKEN`/`MISE_GITHUB_TOKEN` and pin exact versions to avoid the version-listing call.

Image sizes measured during the spike: `base:zellij` (current shipped flox+Nix+zellij) **1.84 GB**; `base:flox` (flox without zellij) 1.27 GB; `base:mise-glibc` **324 MB**; `base:mise-musl` 172 MB.

## Resolved Decisions

The 01_ideas Open Questions are resolved as follows.

- **Engine: mise replaces flox.** The provisioning engine is mise, not flox or plain Nix. mise gives a human-readable `mise.toml` intent file, a checksum-and-provenance `mise.lock` lockfile, and an `install`/`use`/`ls`/`rm` CLI surface that maps onto the existing `RuntimeManager` trait, while collapsing the base image from 1.84 GB to 324 MB by dropping the Nix store. The aqua and pixi candidates from the engine investigation are rejected: aqua is subsumed (mise drives the aqua registry as a backend, confirmed by the `aqua:zellij-org/zellij` resolution in the spike), and pixi targets the conda-forge ecosystem, which is glibc-centric and a poorer fit than mise's GitHub-release catalog for a CLI-tool sandbox. flox remains in the codebase only until the Phase A–D migration lands.
- **Base image: switch from Alpine to debian:12-slim (glibc).** The base changes from `alpine:3.24` to `debian:12-slim` because mise installs prebuilt upstream binaries and glibc-only language runtimes fail on musl (the spike's `node@22` failure). mise's documented musl-node workarounds were tested and do not rescue the musl base: the prebuilt musl binaries exist on the unofficial-builds mirror, but mise `v2026.6.14`'s `core:node` backend ignores both `node.flavor=musl` and `libc=musl` and compiles from source on musl (verbose log: `we will fetch the source and compile`), which needs a C++ toolchain baked in (erasing the size win) and is slow per install. The glibc base costs ~150 MB more than the musl base (324 MB vs 172 MB) but unlocks the full mise catalog with zero per-tool settings and is still 5.7× smaller than the flox image. The musl base (`spike/mise/Containerfile.musl`) remains a valid choice only for a sandbox whose tools are all static CLIs (Go/Rust binaries, jq, zellij) with no glibc-only language runtimes.
- **Where the manifest lives and how it reaches the remote.** Resolved: `mise.toml` and `mise.lock` live at the workspace root `/root/work`, so the existing Mutagen workspace sync (`docs/features/remote-sync/02_dev.md`) carries them with no dedicated transfer. Unlike flox's hidden `.flox/` directory, `mise.toml`/`mise.lock` are visible files at the workspace root; Phase B configures mise to use the hidden `.config/mise/config.toml` location inside the workspace if the visible files are judged to pollute the user's view (see Lifecycle).
- **Reconciling pre-existing system-package installs.** Resolved: software installs are supported only through the mise-backed install command. Raw `apt-get` remains usable for ad-hoc system libraries but is neither recorded in `mise.toml` nor reproduced on deploy; loss of `apt-get`-installed software across a deploy is a documented limitation, not a reconciled case.
- **Bootstrap location.** Resolved: mise and zellij are baked into the prebuilt base image, and `BASE_IMAGE`/`BASE_IMAGE_VERSION` in `src-tauri/src/backends/mod.rs` (lines 16 and 20) point at the prebuilt image. Installing mise at each `create` call was rejected because the mise binary is ~97 MB and would make sandbox creation slow.
- **Cross-machine reproduction dependency.** Resolved: reproduction stays self-contained. The remote resolves from `mise.lock` against the upstream release hosts named in the lockfile URLs; mise has no FloxHub-style hub dependency.
- **Manifest in the destroy guard.** Resolved: because `mise.toml` and `mise.lock` live under `/root/work`, the remote-sync destroy guard (`docs/features/remote-sync/02_dev.md`) that checks for unsynced workspace changes before destroying a remote sandbox already protects them; no separate guard is added.

## Superseded: the former flox engine (removed)

The runtime engine was flox until the mise migration below replaced it in code. A future agent must not reintroduce the flox path. The replaced code was:

- The flox-baked base image recipe in `src-tauri/resources/Containerfile` (`alpine:3.24` + `apk add nix git`, an `/etc/nix/nix.conf` with the flox binary cache, and `nix profile add github:flox/flox`), tagged `sandbox-mio/base:zellij`.
- The `PodmanFloxRuntime` implementation driving `flox init`/`install`/`uninstall`, reading `.flox/env/manifest.toml`, and reproducing on the remote with `flox activate`.

The flox path was removed because the Nix store made the base image 1.84 GB; the manifest-driven deploy model it established is kept unchanged in shape. The `RuntimeManager` trait surface in `src-tauri/src/runtime/types.rs` survived the swap essentially intact (only `init` dropped its now-unused `image` parameter), so the Tauri command wiring in `src-tauri/src/lib.rs` was unchanged apart from that one call site.

## Implemented (mise) — Phase A: mise-baked glibc base image

`src-tauri/resources/Containerfile` is the mise recipe (matching `docs/features/sandbox-runtime-management/spike/mise/Containerfile.glibc`): `debian:12-slim`, `apt-get install` of `curl git ca-certificates xz-utils`, a baked `mise` binary pinned via `ARG MISE_VERSION`, the `MISE_DATA_DIR`/`MISE_LOCKFILE`/`MISE_YES` environment, a `mise install zellij@${ZELLIJ_VERSION}` symlinked to `/usr/local/bin/zellij`, and a dumped zellij config at `/root/.config/zellij/config.kdl`. Both versions are pinned by `ARG` so the build skips the rate-limited GitHub version-listing API. `BASE_IMAGE_VERSION` in `src-tauri/src/backends/mod.rs` is `"mise"`, consumed by `image()` in the same file. The image is staged onto every connection with a `podman save | podman load` pipe, not `podman image scp` (see Lifecycle). `git` is included because some mise backends clone tool repositories. Remaining: the image has not yet been built into the shipped binary on developer/CI machines (the next `create_sandbox` builds it on first use).

## Implemented (mise) — Phase B: workspace-embedded mise environment

The `init` method of `PodmanMiseRuntime` (`src-tauri/src/runtime/mod.rs`) ensures the workspace holds a `mise.toml` (written `[tools]\n`) and an empty `mise.lock`, writing both host-side because the workspace is bind-mounted (mise has no `init` subcommand, and the empty lockfile must pre-exist for `MISE_LOCKFILE=1` installs to maintain it). `init` is idempotent: it returns early when `mise.toml` already exists. The config lives at the visible workspace-root path `/root/work/mise.toml`; relocating it to a hidden `/root/work/.config/mise/config.toml` is deferred and noted under Lifecycle ("Manifest visibility"). `init` no longer takes the `image` parameter the flox throwaway-container init needed; the `src-tauri/src/lib.rs` `create_sandbox` call site was updated accordingly.

## Implemented (mise) — Phase C: install / uninstall / list / reproduce engine

`PodmanMiseRuntime` in `src-tauri/src/runtime/mod.rs` implements the `RuntimeManager` trait (`src-tauri/src/runtime/types.rs`); the trait surface is engine-agnostic, so `src-tauri/src/lib.rs` command wiring is unchanged apart from `init`'s dropped argument. `install` runs `mise use <pkg>` over `podman exec`; `uninstall` runs `mise rm <pkg>`; `list` parses the `[tools]` table of `mise.toml` on the host filesystem (the `parse_installed` helper); `reproduce_remote` `podman cp`s `mise.toml` and `mise.lock` to the remote workspace and runs `mise install`. `MANIFEST_REL` is `mise.toml` and `LOCKFILE_REL` is `mise.lock`; the `RuntimeError::ManifestRead`/`ManifestParse` messages name "mise". `open_terminal` is unchanged — zellij is baked on the global PATH by Phase A, and `container_exec` runs it without any per-sandbox env. The `validate_package` allowlist already accepts the `@`, `:`, and `#` characters mise tool specs use; its error message lists them.

## Implemented (mise) — Phase D: manifest-driven deploy (reproduce engine done; verification remaining)

`deploy` in `src-tauri/src/backends/mod.rs` already delegates software reproduction to `reproduce_remote` rather than `podman commit`, and the mise engine inside `reproduce_remote` (Phase C) `podman cp`s `mise.toml`/`mise.lock` to the remote and runs `mise install`, which resolves the lock-pinned builds. The copy-then-install order is deterministic and does not race the Mutagen workspace sync. Remaining: (1) a two-machine deploy verification run (the e2e `runtime-management.spec.ts` still asserts the flox `.flox/env/manifest.toml` path and must be rewritten to assert `mise.toml` and the install/reproduce flow); (2) passing a `GITHUB_TOKEN`/`MISE_GITHUB_TOKEN` into the remote exec environment, because a cold remote `mise install` may hit the GitHub version-listing rate limit (pinned versions in `mise.lock` avoid most calls). The `RemoteDeployment` endpoints (`src-tauri/src/backends/types.rs` line 55) and the `deploy_sandbox` command keep orchestrating the workspace sync unchanged.

## Lifecycle and Cross-Cutting Concerns

**Base image presence on every connection.** Phase D creates remote containers from the mise-baked base image, so the 324 MB image must exist on each connection. Stage it with a `podman --connection <src> save … | podman --connection <dst> load` pipe; `podman image scp` between two Podman-machine connections is broken on Windows (the connection name is resolved as a DNS host, the same defect `docs/features/remote-sync/03_e2e.md` records).

**Remote install needs network and a checksum match.** The remote `mise install` downloads binaries from the upstream release hosts named in `mise.lock` and verifies them against the recorded SHA256 checksums, so the remote container needs outbound network. A checksum mismatch (an upstream re-tagged a release) fails the install loudly rather than silently installing a different build.

**GitHub rate limit.** Unauthenticated GitHub API calls are limited to 60 requests/hour per IP and return HTTP 403 when exhausted, breaking version resolution (the same limit that broke flox's HEAD resolution). Pin exact tool versions and pass a `GITHUB_TOKEN` to both the base-image build and the runtime exec environment to avoid the version-listing API.

**Tool store growth.** Each container has its own `MISE_DATA_DIR` (`/root/.local/share/mise`); installing many tool versions grows it. mise has `mise prune` to remove versions no longer referenced by any config; treat store growth as expected and document pruning as a manual operation for now.

**Manifest visibility.** Unlike flox's hidden `.flox/` directory, mise's default `mise.toml`/`mise.lock` are visible files at the workspace root. Phase B decides whether to relocate the config to a hidden `.config/mise/config.toml` inside the workspace to keep the user's file view clean; the lockfile and config must remain inside `/root/work` either way so the workspace sync carries them.

**The removed flox/Nix substrate.** The Nix store, the `/etc/nix/nix.conf` cache configuration, and the `flox` binary are intentionally gone from the base image after Phase A. They must not be reintroduced for software management: the Nix store is what made the base image 1.84 GB, and mise reproduces the same manifest-driven model at 324 MB.

## Common Gotchas

| Gotcha | Cause | Fix |
|---|---|---|
| A language runtime installs but fails to run with exit code 127 | The base image is musl (Alpine) and the runtime (e.g. Node.js from nodejs.org) is a glibc-only prebuilt binary | Build the base from `debian:12-slim` (glibc), per Phase A; the spike confirmed `node@22` fails on Alpine and succeeds on debian-slim |
| `node.flavor=musl` / `libc=musl` makes node compile from source or 404 instead of fetching the musl binary | The musl binaries exist on the unofficial-builds mirror, but mise `v2026.6.14`'s `core:node` backend ignores the flavor/libc setting and compiles from source on musl (verbose: `we will fetch the source and compile`); on the unofficial mirror it builds the source-tarball URL and 404s | Use the glibc base (Phase A) where node needs no flavor settings; do not rely on mise's musl-node guidance for this project unless a newer mise version wires the flavor into binary selection |
| `mise install` or `mise use` fails with HTTP 403 from the GitHub API | Unauthenticated GitHub version-listing calls hit the 60-req/h rate limit | Pin exact tool versions (so the lockfile drives the install) and pass `GITHUB_TOKEN`/`MISE_GITHUB_TOKEN` to the build and runtime exec environment |
| `mise.lock` is never written even though installs succeed | mise only maintains the lockfile when `MISE_LOCKFILE` is set and the lockfile already exists | Bake `MISE_LOCKFILE=1` into the base (Phase A) and create an empty `mise.lock` in the workspace on first use (Phase B) |
| `zellij web` aborts with "Failed to find default config file path" | zellij's web server needs a config file present at startup | Dump the default config to `/root/.config/zellij/config.kdl` in the base image (Phase A), as the prior flox base did |
| The in-app terminal cannot find zellij | zellij was installed into the per-tool mise store but not placed on the global PATH | Symlink the mise-installed zellij binary onto `/usr/local/bin/zellij` in the base image (Phase A); `open_terminal` runs plain `zellij` off the global PATH, not through mise |
| Remote reproduces a different build than the laptop | Deploy resolved from tool names instead of the lockfile | Seed `mise.lock` onto the remote and run `mise install` so it installs the checksum-pinned builds recorded in the lockfile (Phase D) |
| Software installed with `apt-get` disappears after deploy | Only the mise manifest is reproduced on the remote; `apt-get` packages are not recorded in `mise.toml` | Install software through the mise-backed install command (Phase C); treat `apt-get` installs as non-reproducible |
| Deploy fails creating the remote container | The mise-baked base image does not exist on the target connection | Stage the base image onto the target connection once with a `podman save \| podman load` pipe before creating the remote container |
| The base image is far larger than expected for "just a CLI manager" | The `mise` binary is ~97 MB and dominates the 324 MB base | Expected; the base is still 5.7× smaller than the 1.84 GB flox image, and the mise binary is the floor |
| Reintroducing Nix or `podman commit` for software | A future change re-adds the removed Nix substrate or the snapshot-and-push deploy path | Keep software reproduction on the mise manifest; the Nix store was removed because it made the image 1.84 GB |

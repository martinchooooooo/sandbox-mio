# Sandbox Runtime Management Build Plan

This document is the build plan for managing the software installed inside a sandbox: installing packages, recording what is installed, and reproducing that software on a remote host at deploy time. It continues `docs/features/sandbox-runtime-management/01_ideas.md` and supersedes its central open question — the engine is now flox (built on Nix), proven end-to-end by a spike on 2026-06-23. Status: no production code for runtime management exists yet; every phase below is Remaining. The existing image-snapshot deploy in `src-tauri/src/backends/mod.rs` (`deploy`, line 319) is the only related code that is Already Implemented, and Phase D replaces its software-transfer path. Relevant files: container lifecycle in `src-tauri/src/backends/mod.rs`, backend contracts in `src-tauri/src/backends/types.rs`, command wiring in `src-tauri/src/lib.rs`, and the workspace-sync lifecycle in `docs/features/remote-sync/02_dev.md` that this feature plugs into.

## The Concrete Model

A sandbox carries a flox environment whose `manifest.toml` (human-readable intent) and `manifest.lock` (pinned closure) are the single source of truth for the sandbox's software. The flox environment lives inside the sandbox workspace as a `.flox/` directory at `/root/work/.flox`, so the workspace path computed by `workspace_path` in `src-tauri/src/backends/mod.rs` (line 52) and bind-mounted at `/root/work` already contains it. Because the flox environment sits in the workspace, the Mutagen sync session from the remote-sync feature (`docs/features/remote-sync/02_dev.md`) carries `manifest.toml` and `manifest.lock` to the laptop and to the remote host with no separate transfer.

The container runs flox, which runs on Nix. flox and Nix are baked into the sandbox base image (measured at 1.27 GB; see "The flox/Nix Substrate") so sandbox creation does not pay that download. A user installs software through a backend command that runs `flox install` inside the container over `podman exec`; flox rewrites `manifest.toml` and `manifest.lock`, so every install writes the record as a side effect. Listing installed software reads the manifest rather than inspecting the container filesystem.

Deploy stops shipping the committed image for software. After the remote container is created from the same flox-baked base image and the workspace sync has seeded `.flox/` onto the remote, deploy runs `flox activate` on the remote container, which reads `manifest.lock` and substitutes the identical locked closure from the Nix binary caches. The transfer is the size of the manifest, not the size of a committed image.

## The flox/Nix Substrate (validated)

Nix is installed from Alpine's `apk` repository as `nix-2.31.5-r0`; it is musl-native and needs no daemon. The Nix configuration at `/etc/nix/nix.conf` inside the container must set `experimental-features = nix-command flakes`, `sandbox = false` (the rootless container cannot create the nested user namespaces Nix's build sandbox needs), and must list `https://cache.flox.dev` as a substituter with the flox cache public key `flox-cache-public-1:7F4OyH7ZCnFhcze3fJdfyXYLQw/aV7GEed86nQ7IsOs=` in `trusted-public-keys`. flox itself is installed with `nix profile add github:flox/flox`. The 2026-06-23 spike confirmed this end to end: flox `1.13.0` installed, and `flox init` then `flox install hello` then `flox activate -- hello` printed `Hello, world!` inside an `alpine:latest` container. Nix packages carry their own glibc in the `/nix/store` closure, so glibc-linked binaries run on the musl host. Building the base image from `docs/features/sandbox-runtime-management/spike/Containerfile` produced a 1.27 GB image (`sandbox-mio/base:flox`); the bake cost is material, which is why deploy moves only the manifest and not this image (see "Manifest-driven deploy" and Lifecycle).

## Resolved Decisions

- **flox versus plain Nix as the shipped engine.** Resolved to flox. The 2026-06-23 spike installed flox `1.13.0` via `nix profile add github:flox/flox` and ran the full `flox init` / `flox install` / `flox activate` workflow inside the Alpine sandbox once the correct cache key was set. The earlier multi-attempt "stall" was a stale `trusted-public-keys` value (`...aV7GEml05smvKuLg=`) that caused Nix to reject every `cache.flox.dev` substitute and silently compile flox from source; the correct key (`...aV7GEed86nQ7IsOs=`) reduced rejected-substitute warnings to zero. Plain Nix remains the substrate flox runs on and is the fallback only if flox is later dropped.
- **Where the manifest lives and how it reaches the remote.** Resolved: the flox environment lives in the workspace at `/root/work/.flox`, so `manifest.toml` and `manifest.lock` are carried by the existing Mutagen workspace sync (`docs/features/remote-sync/02_dev.md`) rather than by a dedicated transfer step. The `.flox/` directory is a self-contained hidden directory with its own `.gitignore`/`.gitattributes`, so it does not pollute the user's visible files.
- **Reconciling pre-existing `apk` installs.** Resolved: software installs are supported only through the flox-backed install command. Raw `apk` remains usable for ad-hoc system libraries but is neither recorded in the manifest nor reproduced on deploy; loss of `apk`-installed software across a deploy is a documented limitation, not a reconciled case.
- **Bootstrap location.** Resolved: Nix and flox are baked into a prebuilt base image layered on `alpine:latest`, and `BASE_IMAGE`/`BASE_IMAGE_VERSION` in `src-tauri/src/backends/mod.rs` (lines 14–15) point at the prebuilt image. Installing flox at each `create` call was rejected because the first flox install pulls a large closure and would make sandbox creation slow.
- **FloxHub dependency.** Resolved: reproduction stays self-contained. The remote resolves from `manifest.lock` against the Nix binary caches (`cache.nixos.org` and `cache.flox.dev`); `flox push`/`flox pull` against FloxHub is deferred as an optional later enhancement and is not a dependency.
- **Manifest in the destroy guard.** Resolved: because `manifest.toml` and `manifest.lock` live under `/root/work/.flox`, the remote-sync destroy guard (`docs/features/remote-sync/02_dev.md`) that checks for unsynced workspace changes before destroying a remote sandbox already protects them; no separate guard is added.

## Remaining: Phase A — flox-baked base image

Build a sandbox base image layered on `alpine:3.24` that `apk add`s `nix` and `git`, writes `/etc/nix/nix.conf` with the substituter, key, `sandbox = false`, and `experimental-features` settings named in "The flox/Nix Substrate" section, and runs `nix profile add github:flox/flox`. The proven recipe is `docs/features/sandbox-runtime-management/spike/Containerfile`, validated on 2026-06-23; it produces `sandbox-mio/base:flox` at 1.27 GB. Point `BASE_IMAGE` and `BASE_IMAGE_VERSION` in `src-tauri/src/backends/mod.rs` (lines 14–15), consumed by `image()` in the same file (line 127), at the built image. The image must be available on every connection the app uses, not only the local one, because Phase D creates remote containers from it; stage it across connections with `podman save | podman load`, not `podman image scp` (see Lifecycle). `git` is required because flox manages the `.flox/` environment with Git internally.

## Remaining: Phase B — workspace-embedded flox environment

Extend `create` in `src-tauri/src/backends/mod.rs` (line 248) so that after the container is created it initializes a flox environment in the workspace by running `flox init` in `/root/work` over `podman exec` when no `.flox/` directory is present. The workspace directory is the one `create` already prepares through `workspace_path`/`resolve_workspace` (`src-tauri/src/backends/mod.rs`, lines 52 and 213); the flox environment is created inside it, not at a separate path. Set `FLOX_DISABLE_METRICS` in the exec environment so flox does not emit telemetry.

## Remaining: Phase C — install / uninstall / list commands

Add three methods to the `SandboxBackend` trait in `src-tauri/src/backends/types.rs` (line 110) and implement them on `PodmanCliBackend` in `src-tauri/src/backends/mod.rs`: an install operation that runs `flox install <pkg>` over `podman exec`, an uninstall operation that runs `flox uninstall <pkg>`, and a list operation that reads the installed set from `manifest.toml`/`manifest.lock`. Wire one Tauri command per method in `src-tauri/src/lib.rs` alongside the existing sandbox lifecycle commands. Surface the installed-software list to the frontend either by adding a field to the `Sandbox` struct in `src-tauri/src/backends/types.rs` (line 41) or by a dedicated list command; the list operation is the authoritative reader because the manifest, not the container filesystem, is the source of truth. Methods added before their Tauri commands are wired should carry `#[allow(dead_code)]`, removed as each command lands.

## Remaining: Phase D — manifest-driven deploy

Refactor `deploy` in `src-tauri/src/backends/mod.rs` (line 319) to reproduce software from the manifest instead of shipping a committed image. Remove the software-transfer path that today stops the container, runs `podman commit`, and streams the image with `podman save` piped into `podman load` (`src-tauri/src/backends/mod.rs`, lines 344–388). The replacement: create the remote container from the flox-baked base image (Phase A), let the workspace sync seed `/root/work/.flox` onto the remote (the manifest is small and deterministic), then run `flox activate` on the remote container over `podman exec` so it substitutes the locked closure from `manifest.lock`. The `RemoteDeployment` endpoints in `src-tauri/src/backends/types.rs` (line 55) and the `deploy_sandbox` command in `src-tauri/src/lib.rs` keep orchestrating the workspace sync; only the software-transfer mechanism changes. Record in the code comment that the removed `podman commit` path is intentionally gone and must not be reintroduced for software, because it ships an opaque, drift-prone image instead of the reproducible manifest. Resolving from `manifest.lock` (not package names) is mandatory so the remote reproduces the identical builds the laptop locked.

## Lifecycle and Cross-Cutting Concerns

**Base image presence on every connection.** Phase D creates remote containers from the flox-baked base image, so the 1.27 GB image must exist on each connection. The 2026-06-23 spike staged it with a `podman --connection <src> save … | podman --connection <dst> load` pipe; `podman image scp` was deliberately not used because, between two Podman-machine connections on Windows, it resolves the connection name as a DNS host and fails (the same defect `docs/features/remote-sync/03_e2e.md` records). The build must therefore stage the base image with `save | load` or pull it from a container registry on the remote, not with `image scp`. A missing base image on the remote is the most likely Phase D failure.

**Remote closure realization needs network and the cache key.** `flox activate` on the remote substitutes the locked closure from `cache.nixos.org` and `cache.flox.dev`, so the remote container needs outbound network and the same `/etc/nix/nix.conf` cache key as the local one. The flox-baked base image (Phase A) carries that configuration, which is why the same image must be used on both ends.

**Nix store growth and garbage collection.** Each container has its own `/nix/store`; installing packages and activating environments grows it. The build plan does not add automatic GC, but a sandbox that installs and uninstalls many packages accumulates store paths until a `nix-collect-garbage` is run; treat store growth as expected and document GC as a manual operation for now.

**`sandbox = false` security note.** Disabling Nix's build sandbox inside the container is acceptable because the Podman container is itself the isolation boundary; the setting only affects Nix's own nested-namespace build isolation, which the rootless container cannot provide.

**Manifest timing on deploy.** Phase D depends on `/root/work/.flox/manifest.lock` being present on the remote before `flox activate` runs. The deploy flow must order the workspace-sync seed before the remote activation, or copy `manifest.toml`/`manifest.lock` directly to the remote workspace as a deterministic pre-step rather than racing the sync.

## Common Gotchas

| Gotcha | Cause | Fix |
|---|---|---|
| flox install hangs for many minutes and the `/nix/store` grows with `cargo-package-*` paths | The flox cache public key in `trusted-public-keys` is wrong, so Nix rejects every `cache.flox.dev` substitute and silently compiles flox from source | Set `trusted-public-keys` in `/etc/nix/nix.conf` to `flox-cache-public-1:7F4OyH7ZCnFhcze3fJdfyXYLQw/aV7GEed86nQ7IsOs=` (the stale `...aV7GEml05smvKuLg=` value causes the source compile) |
| `warning: ignoring substitute ... not signed by any of the keys in 'trusted-public-keys'` during flox install | The `cache.flox.dev` signing key is absent from `trusted-public-keys`, so prebuilt paths are discarded | Add the flox cache public key to `trusted-public-keys` in `/etc/nix/nix.conf`; a count of zero such warnings confirms substitution is working |
| `nix` build fails with a namespace/sandbox error inside the sandbox | The rootless Podman container cannot create the nested user namespaces Nix's build sandbox requires | Set `sandbox = false` in `/etc/nix/nix.conf` inside the container |
| Software installed with `apk` disappears after deploy | Only the flox manifest is reproduced on the remote; `apk`-installed packages are not recorded in `manifest.toml` and are not reproduced | Install software through the flox-backed install command (Phase C) so it is recorded and reproduced; treat `apk` installs as non-reproducible |
| Deploy fails creating the remote container | The flox-baked base image (Phase A) does not exist on the target connection | Stage the base image onto the target connection once with `podman --connection <src> save … \| podman --connection <dst> load`, or pull it from a registry, before creating the remote container |
| Staging the base image to the remote fails with "lookup &lt;name&gt;: Temporary failure in name resolution" | `podman image scp` between two Podman-machine connections resolves the connection name as a DNS host on Windows | Move the image with a `podman save \| podman load` pipe between the two connections, not `podman image scp` |
| `flox activate` on the remote fails to fetch packages | The remote container lacks outbound network or the `cache.flox.dev` key in `/etc/nix/nix.conf` | Ensure the remote uses the flox-baked base image (which carries the cache config) and has outbound network to `cache.nixos.org` and `cache.flox.dev` |
| Remote reproduces different package versions than the laptop | Deploy resolved from package names instead of the lockfile | Run the remote `flox activate` against the synced `manifest.lock` so it substitutes the identical locked closure |
| Reintroducing `podman commit` for software in `deploy` | A future change re-adds the removed snapshot-and-push path (`src-tauri/src/backends/mod.rs` lines 344–388) | Keep software reproduction on the manifest; the committed-image path was removed in Phase D because it ships an opaque, drift-prone image |
| flox manages a Git repo error during `flox init`/`flox install` | `git` is absent from the base image and flox manages `.flox/` with Git internally | Include `git` in the flox-baked base image (Phase A) |

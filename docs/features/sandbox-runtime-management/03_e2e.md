# E2E Test Plan: Sandbox Runtime Management

This document is the end-to-end test plan for the sandbox-runtime-management feature whose build is described in `docs/features/sandbox-runtime-management/02_dev.md`. Read `docs/features/sandbox-runtime-management/02_dev.md` first for the four build phases (A: flox-baked base image; B: workspace-embedded flox env on create; C: install/uninstall/list commands; D: manifest-driven deploy); the present file covers only how to prove that build through the real application. Two spikes were run by hand and are recorded under "De-Risking Spike Results": a flox/Nix substrate spike on 2026-06-22 and 2026-06-23, and a two-machine manifest-reproduction spike on 2026-06-23 that cleared the core of Phase D (a package installed via a flox manifest on `mio-tests` reproduced byte-for-byte on `mio-tests-remote` from a 7,295-byte manifest transfer). Spike artifacts are kept in `docs/features/sandbox-runtime-management/spike/`. No production code for the feature exists yet, so the spec described here is to be written after the phases it exercises land, not now.

## Goal

Prove the real software-management code path through the actual Tauri application: the Phase C `install_package`, `uninstall_package`, and `list_package` commands (wired in `src-tauri/src/lib.rs`, implemented on `PodmanCliBackend` in `src-tauri/src/backends/mod.rs`), and the Phase D manifest-driven `deploy_sandbox` command that reproduces software on a remote host from `manifest.lock` instead of from a committed image. The bundled component the test depends on is the flox-baked base image (Phase A) that carries Nix, flox, and the `/etc/nix/nix.conf` cache key; it is the runtime-management equivalent of the Mutagen sidecar that `docs/features/remote-sync/03_e2e.md` stages.

A weaker test would drive flox directly with `podman exec` against a container (exactly what the feasibility spike did) — that proves the flox substrate works but exercises none of the application's command code, the same gap `docs/features/remote-sync/03_e2e.md` calls out about the standalone Mutagen POC. The test must therefore drive the UI controls that invoke the Tauri commands and read state back through the Podman CLI and the workspace filesystem.

## Existing Test Styles

The repository has two end-to-end styles, and the new test belongs to the first:

- **App-driven WebdriverIO specs** (`e2e/test/specs/*.spec.ts`) drive the real Tauri application through `tauri-driver`, invoking the actual Tauri commands; assertions read state back through the Podman CLI (`podman`/`podmanOk` in `e2e/lib/podman-connection.ts`) and the laptop filesystem. `e2e/test/specs/workspace-mount.spec.ts` is the template for a single-machine filesystem assertion, and `e2e/test/specs/deploy-remote.spec.ts` is the template for the two-machine deploy lifecycle.
- **Standalone POC** (the Mutagen transport POC referenced in `docs/features/remote-sync/03_e2e.md`) exercises a transport in isolation and tests no application code.

## Chosen Approach

Add an app-driven WebdriverIO spec `e2e/test/specs/runtime-management.spec.ts` that uses the same two-machine topology as `e2e/test/specs/deploy-remote.spec.ts`: the local connection `mio-tests` (`LOCAL_CONNECTION` in `e2e/lib/podman-connection.ts`, pinned through `PODMAN_CONNECTION`) and the deploy target `mio-tests-remote` (`REMOTE_CONNECTION`). No external host is needed. The spec drives package installation on the local sandbox, then a deploy, and asserts the package is reproduced on the remote from the manifest. New UI controls from Phase C (a package-install input/button and an installed-package list in the project row) require new methods on the `ProjectRow` component (`e2e/test/pageobjects/project-row.component.ts`), mirroring how `deployTo` and `waitForSyncStatus` were added there.

## Harness Changes (`e2e/wdio.conf.ts`)

- **Stage the flox-baked base image on both connections.** `provisionMachine` in `e2e/lib/podman-machine.ts` currently pre-pulls `alpine`; the runtime feature replaces `BASE_IMAGE` (`src-tauri/src/backends/mod.rs` lines 14–15) with the Phase A flox image, which both `create` (local) and the Phase D remote-create use. Add an `onPrepare` step that builds the flox base image once and loads it onto both `mio-tests` and `mio-tests-remote` (build once, then `podman save` piped to `podman --connection <name> load`, or push through a registry), so neither connection silently falls back to plain `alpine`.
- **Pre-warm the remote `/nix/store` for the test package.** The first `flox activate` on the remote substitutes the package closure from `cache.nixos.org`/`cache.flox.dev` over the internet, which is slow and network-dependent. Realize the spec's test package (for example `hello`) into the remote machine's `/nix/store` during `onPrepare` so the Phase D reproduction step is fast and not at the mercy of cache latency, the same idea as the Alpine pre-pull.
- **Raise the Mocha timeout.** `mochaOpts.timeout` is 180000 ms; a cold remote closure realization plus the deploy can exceed it. Raise it for this spec or rely on the pre-warm above.
- **Cleanup honouring env flags.** Reuse `MIO_REMOTE_KEEP`/`MIO_REMOTE_REMOVE`. Remove the sandbox container on both connections in an `after` hook (as `deploy-remote.spec.ts` does). The flox environment lives under `/root/work/.flox` inside the per-sandbox workspace directory, so the existing `onComplete` removal of `WORKSPACE_ROOT` already deletes the manifest with the workspace; no extra cleanup is needed for it.

## Spec Scenario

Mirror `e2e/test/specs/deploy-remote.spec.ts` — drive UI controls for actions, assert through `podman --connection` and `fs`:

1. **Create a project on `mio-tests`.** Assert (fs) that `<workspace>/.flox/env/manifest.toml` exists, proving Phase B's `flox init` ran during `create_sandbox`.
2. **Install a package through the UI** (drive the Phase C install control with `hello`), invoking `install_package`. Assert (fs) that `<workspace>/.flox/env/manifest.toml` now contains `hello.pkg-path = "hello"`, and assert the installed-package list in the row shows `hello` (proving `list_package` reads the manifest).
3. **Assert the package runs in the local container.** Run `podman --connection mio-tests exec <name>` to activate the flox environment and execute the installed binary; assert its expected output, proving the install realized the closure inside the container, not merely edited the manifest.
4. **Deploy to `mio-tests-remote`** with `deployTo(REMOTE_CONNECTION)`, invoking the Phase D `deploy_sandbox`. Assert the remote container is `running` (`podman --connection mio-tests-remote inspect`).
5. **Assert the package is reproduced on the remote from the manifest.** Run the installed binary via `podman --connection mio-tests-remote exec <name>` and assert its output. Additionally assert that no `sandbox-mio/<name>:deployed` image exists on the remote (`podmanOk(REMOTE_CONNECTION, ["image","exists",...])` is false), proving the reproduction came from `manifest.lock` and not from the removed `podman commit` path.
6. **Assert the manifest reached the remote workspace** (`podman --connection mio-tests-remote exec <name> cat /root/work/.flox/env/manifest.toml` contains `hello`), confirming the workspace sync carried it.
7. **Destroy** the sandbox; assert the local container is gone (`podmanOk(LOCAL_CONNECTION, ["inspect", name])` false) and the workspace directory plus `.flox/env/manifest.toml` are left intact (fs), matching the destroy-guard rule that the workspace is never deleted.

## De-Risking Spike Results

A feasibility spike of the flox/Nix substrate was run by hand inside a rootless `alpine:latest` Podman container on `podman-machine-default`, driven over `podman exec`. The spike answered whether the substrate the whole feature rests on runs inside the actual sandbox base image. The spike containers (`flox-spike`, `flox-spike2`) were removed afterward.

### Cleared (2026-06-22 / 2026-06-23)

- **Nix installs in a rootless Alpine container.** `apk add nix` installed `nix-2.31.5-r0`; `nix --version` reported `nix (Nix) 2.31.5`.
- **glibc binaries run on musl.** `nix profile add nixpkgs#hello` fetched `glibc-2.42` into `/nix/store` and the binary printed `Hello, world!`, so the musl base needs no glibc.
- **flox installs and the full workflow runs.** With the correct cache key configured, `nix profile add github:flox/flox` installed flox `1.13.0`, and `flox init` then `flox install hello` then `flox activate -- hello` printed `Hello, world!` inside the container.
- **The manifest artifacts exist.** `flox install` produced `.flox/env/manifest.toml` (with `[install] hello.pkg-path = "hello"`) and `.flox/env/manifest.lock` (a locked derivation path plus the nixpkgs `rev`), the record and reproducibility inputs the feature depends on.

### Blocker found and resolved: wrong flox cache key

The first flox install attempts stalled for many minutes with `/nix/store` growing through `cargo-package-*` paths. The cause was a wrong `trusted-public-keys` value (`flox-cache-public-1:7F4OyH7ZCnFhcze3fJdfyXYLQw/aV7GEml05smvKuLg=`): Nix rejected every prebuilt path from `cache.flox.dev` with `warning: ignoring substitute ... not signed by any of the keys in 'trusted-public-keys'` and silently fell back to compiling flox from source. Setting the correct key (`flox-cache-public-1:7F4OyH7ZCnFhcze3fJdfyXYLQw/aV7GEed86nQ7IsOs=`) reduced rejected-substitute warnings to zero and flox substituted in seconds. This is a **feature requirement, not a test concern**: the Phase A base image must bake the correct key. With the correct key baked, the spec is unaffected.

### Cleared: two-machine manifest reproduction (2026-06-23)

The central Phase D claim — that a package installed via the manifest on `mio-tests` reproduces on `mio-tests-remote` from `manifest.lock` without the committed image — was run by hand and cleared. The exact steps are scripted in `docs/features/sandbox-runtime-management/spike/two-machine-repro.sh`.

- **Base image built and staged on both connections.** `podman --connection mio-tests build` from `docs/features/sandbox-runtime-management/spike/Containerfile` produced `sandbox-mio/base:flox`, substituting flox `1.13.0` from `cache.flox.dev` with zero rejected-substitute warnings. The image is **1.27 GB** (larger than an early "few hundred MB" estimate — the bake cost is material and is the reason Phase D must move only the manifest, not this image, per deploy).
- **Image transfer between two machine connections needs `save | load`.** `podman --connection mio-tests save sandbox-mio/base:flox | podman --connection mio-tests-remote load` placed the image on the remote. `podman image scp` was not used, matching the `docs/features/remote-sync/03_e2e.md` finding that machine-to-machine `image scp` resolves the connection name as a DNS host and fails on Windows.
- **Manifest-only transfer reproduces the package.** On `mio-tests` a flox env was created in `/root/work` and `hello` installed; only the `.flox/env/` directory (`manifest.toml` + `manifest.lock`, **7,295 bytes total**, no `/nix/store` paths) was transferred to `mio-tests-remote`, whose `/nix/store` held zero `hello` paths beforehand. Running `flox activate -- hello` on the remote fetched the closure from the binary cache and printed `Hello, world!`.
- **Reproduction is deterministic across machines.** Both machines ended with the byte-identical store path `/nix/store/zi2bj2hlavv8q743li2s9diqbcpmrf9b-hello-2.12.3` and the same nixpkgs rev `567a49d1913ce81ac6e9582e3553dd90a955875f`, confirming the lockfile reproduces the same build, not merely the same package name.

The reproduction spike de-risks spec steps 4–6 ahead of writing them. It also confirms the harness must pre-warm the remote `/nix/store` (the cold remote fetch over the internet is the slow, network-dependent step) and stage the 1.27 GB base image onto both connections.

## Sequencing

The spec is not worth writing until the commands it drives exist; implement in this order:

1. **Phase A (flox base image), baking the correct cache key.** Prerequisite for every later step and for the harness staging. The `docs/features/sandbox-runtime-management/spike/Containerfile` is the proven recipe.
2. **Phases B and C (flox env on create; install/uninstall/list commands).** Enough to write and run steps 1–3 of the spec on a single machine.
3. **Phase D (manifest-driven deploy).** Enables steps 4–7 of the spec. The two-machine reproduction this phase implements is already hand-proven (see De-Risking Spike Results), so Phase D wires the proven mechanism into `deploy_sandbox` rather than discovering it.
4. **Write `runtime-management.spec.ts` and the harness changes.** By then the happy path is hand-proven and the spec guards against regression.

## Environment Notes for the Next Session

- Both Podman machines exist: `mio-tests` (`LOCAL_CONNECTION`, source, pinned via `PODMAN_CONNECTION`) and `mio-tests-remote` (`REMOTE_CONNECTION`, deploy target), each a registered system connection.
- The flox-baked base image `sandbox-mio/base:flox` (1.27 GB) is already built and staged on **both** `mio-tests` and `mio-tests-remote` from the 2026-06-23 reproduction spike; a fresh build is only needed if the `Containerfile` changes.
- `mio-tests-remote` was stopped before the spike and restarted; its rootless Podman socket must be re-activated after any restart (the `startPodmanSocket` launcher in `e2e/lib/podman-machine.ts`) before `podman --connection mio-tests-remote …` works. Its SSH port stayed `58307` across the restart, but a future restart may move it.
- Both machines need outbound internet to substitute closures from `cache.nixos.org` and `cache.flox.dev`, unless the remote `/nix/store` is pre-warmed for the test package.
- The spike's throwaway `flox-repro` containers on both connections were removed; the base images and the feasibility-spike `/nix/store` contents remain.
- Per-sandbox workspaces live under `~/.sandbox-mio-e2e` (`SANDBOX_WORKSPACE_ROOT` set in `e2e/wdio.conf.ts`); the flox environment is the `.flox/` directory inside each.

## Common Gotchas

| Gotcha | Cause | Fix |
|---|---|---|
| Spec's install/deploy steps go red because the Tauri command does not exist | The spec was written before Phases A–D landed; `install_package`/`list_package`/manifest-driven `deploy_sandbox` are not implemented | Implement the phases in the Sequencing order; write `e2e/test/specs/runtime-management.spec.ts` only after the commands it drives exist |
| Sandbox is created from plain `alpine` and `flox` is absent | The harness pre-pulled `alpine` but never staged the Phase A flox-baked base image onto the connection | Build the flox base image and load it onto both `mio-tests` and `mio-tests-remote` in `onPrepare`; point `BASE_IMAGE` (`src-tauri/src/backends/mod.rs` lines 14–15) at it |
| `flox` install during base-image build stalls and `/nix/store` fills with `cargo-package-*` paths | The base image's `/etc/nix/nix.conf` has the wrong `cache.flox.dev` key, so Nix rejects prebuilt flox and compiles from source | Bake `trusted-public-keys = flox-cache-public-1:7F4OyH7ZCnFhcze3fJdfyXYLQw/aV7GEed86nQ7IsOs=` (the stale `...ml05smvKuLg=` value causes the source compile) |
| Deploy step times out on the first remote activation | `flox activate` on the remote substitutes the package closure from the internet on a cold `/nix/store`, exceeding `mochaOpts.timeout` (180000 ms) | Pre-warm the remote `/nix/store` for the test package in `onPrepare`, and/or raise the Mocha timeout for the spec |
| Deploy step fails creating the remote container | The flox-baked base image is missing on `mio-tests-remote` | Load the flox base image onto `mio-tests-remote` before the spec, the same staging the harness does for `mio-tests` |
| Test passes even though deploy still ships a committed image | The spec asserted only that the binary runs on the remote, which a committed-image deploy would also satisfy | Also assert no `sandbox-mio/<name>:deployed` image exists on the remote (`podmanOk(REMOTE_CONNECTION, ["image","exists",...])` false), proving reproduction came from `manifest.lock` |
| `manifest.toml` not found on the remote in step 6 | The remote `flox activate` ran before the workspace sync seeded `/root/work/.flox` onto the remote | Order the workspace-sync seed before remote activation in Phase D, or assert after `waitForSyncStatus("up-to-date")` as `deploy-remote.spec.ts` does |
| Remote machine answers no `podman` commands right after start | The rootless `podman system service` socket is not auto-started on the WSL image | Run `provisionMachine(REMOTE_CONNECTION)` (the `startPodmanSocket` launcher in `e2e/lib/podman-machine.ts`) before using the connection |
| Staging the base image onto the remote fails with "lookup &lt;name&gt;: Temporary failure in name resolution" | `podman image scp` between two Podman-machine connections resolves the connection name as a DNS host on Windows | Stage the image with a `podman --connection <src> save … \| podman --connection <dst> load` pipe instead of `image scp` |
| Spike `tar -C /root/work` fails with "can't change directory to 'C:/Program Files/Git/root/work'" | Git Bash (MSYS) rewrites a leading-slash argument into a Windows path before it reaches `podman exec` | Prefix the command with `MSYS_NO_PATHCONV=1` when running the by-hand spike on Git Bash; the WebdriverIO harness uses `spawnSync` with `shell: false` and is unaffected |

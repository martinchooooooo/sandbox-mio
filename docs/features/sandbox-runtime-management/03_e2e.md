# E2E Test Plan: Sandbox Runtime Management (mise)

This document is the test plan for proving the mise-based runtime management built in `docs/features/sandbox-runtime-management/02_dev.md` works through the real application. Read `02_dev.md` first: it describes the engine (mise on a `debian:12-slim` glibc base), the `mise.toml`/`mise.lock` model, and the manifest-driven deploy that this plan exercises. **History:** an earlier revision of this plan tested the former flox engine and asserted `.flox/env/manifest.toml`; the 2026-06-27 mise migration replaced that, and this revision supersedes it. The mise spike recorded in `02_dev.md` already proved the mechanism by hand (`jq` reproduced byte-identically from a 3 KB `mise.toml`+`mise.lock` transfer); this plan turns that into an app-driven regression spec at `e2e/test/specs/runtime-management.spec.ts`. The harness required no new changes because the mise base image is already staged by `ensureMiseBaseImage` in `e2e/wdio.conf.ts`.

## Goal

Prove the real software-management code path through the actual Tauri application:

- `create_sandbox` calls `RuntimeManager::init` (`src-tauri/src/runtime/mod.rs`), which writes `mise.toml` and an empty `mise.lock` host-side into the sandbox workspace.
- The install UI calls `install_package` → `RuntimeManager::install`, which runs `mise use <pkg>` over `podman exec` inside the container, so mise rewrites `mise.toml` and maintains `mise.lock`.
- `list_packages` → `RuntimeManager::list` parses the `[tools]` table of `mise.toml`.
- `deploy_sandbox` → `SandboxBackend::deploy` + `RuntimeManager::reproduce_remote`, which `podman cp`s `mise.toml`/`mise.lock` to the remote and runs `mise install`, resolving the lock-pinned binary from the upstream release host.

The runtime operations live in their own module `src-tauri/src/runtime/` (the `RuntimeManager` trait in `runtime/types.rs`, `PodmanMiseRuntime` in `runtime/mod.rs`), kept out of the container-lifecycle backend; the flox-init-at-create and reproduce-at-deploy steps are orchestrated at the command layer in `src-tauri/src/lib.rs`. A weaker test would drive mise directly with `podman exec` (what the spike did) and exercise none of the application's command code — the same gap `docs/features/remote-sync/03_e2e.md` calls out about the standalone Mutagen POC. The spec must therefore drive the UI controls that invoke the Tauri commands and read state back through the Podman CLI and the workspace filesystem. It also asserts the decisive properties a manifest-name-only check would miss: that the installed tool is actually *runnable* inside the container, that `mise.lock` gains the resolved version (proving the baked `MISE_LOCKFILE=1` is in effect), and that the remote tool comes from the **lockfile**, not a committed image (asserted by the absence of `sandbox-mio/<name>:deployed`).

## Existing Test Styles

The repository has two end-to-end styles; this spec belongs to the first:

- **App-driven WebdriverIO specs** (`e2e/test/specs/*.spec.ts`) drive the real Tauri app through `tauri-driver`, invoking the actual Tauri commands, and read state back through `podman --connection` (`podman`/`podmanOk` in `e2e/lib/podman-connection.ts`) and the laptop filesystem. `deploy-remote.spec.ts` is the template for the two-machine deploy lifecycle and `web-terminal.spec.ts` for the single-machine assertions; `runtime-management.spec.ts` mirrors their structure (a `function ()` describe with a raised `this.timeout`, a per-test `afterEach` failure-diagnostics dump to `e2e/.diag`, and `node:assert` with diagnostic second arguments).
- **Standalone POCs** exercise a transport in isolation and test no application code. Not used here.

## Chosen Approach

The spec is `e2e/test/specs/runtime-management.spec.ts`, a single `describe("Sandbox runtime management (mise)")` block that runs the full lifecycle on one project. The topology is the same two-local-machine setup the deploy spec uses: `mio-tests` (`LOCAL_CONNECTION`, the source, pinned via `PODMAN_CONNECTION`) and `mio-tests-remote` (`REMOTE_CONNECTION`, the deploy target). No external host is needed; the deploy target is just a second registered Podman system connection that appears in the host picker automatically.

The test tool is **`jq`** (`PKG = "jq"`): a tiny static single-binary CLI that runs on the glibc base with no runtime dependencies, resolves through mise's aqua backend, and prints a stable `jq-<semver>` line from `jq --version` (asserted via the `jq-` prefix). It is the tool the spike reproduced byte-identically, so its install and cross-machine reproduction are hand-proven. A language runtime (e.g. Node) was deliberately *not* chosen: it is large and slow to install per run, while `jq` keeps the spec fast and exercises the same `mise use`/`mise install` code path. `jq` being a static CLI would also pass on a musl base, but the feature ships the glibc base so runtime installs work too.

## Harness

No harness changes were required. `e2e/wdio.conf.ts` already:

- provisions both `mio-tests` and `mio-tests-remote` in `onPrepare` (`provisionMachine`),
- stages the mise base image on both connections with `ensureMiseBaseImage(LOCAL_CONNECTION, [REMOTE_CONNECTION])` (a `podman save | podman load` pipe, not `image scp`),
- builds the debug app with the Mutagen sidecar staged,
- cleans the workspace root and the app-written SSH config in `onComplete`, honouring `MIO_REMOTE_KEEP` / `MIO_REMOTE_REMOVE`.

The base image staged is built from the real recipe the binary bakes (`src-tauri/resources/Containerfile`), so the spec exercises the same image the app would build on first `create_sandbox`. No remote pre-warm step is needed: unlike the former flox `/nix/store`, each container has its own `MISE_DATA_DIR`, so the remote `mise install` always fetches into the fresh deploy container regardless of any machine-level cache. The spec raises the per-suite Mocha timeout to 600000 ms to cover the cold remote install instead. The `base-image-build.spec.ts` spec separately proves the on-first-create build path by removing and rebuilding the image; `base-image-recipe.spec.ts` statically guards that the recipe keeps mise and zellij pinned to exact versions (no rate-limited `@latest`/`releases/latest`/`mise.run`).

## Spec Scenario

Each step drives a UI action through the app and asserts by reading state back through `podman --connection` and `fs`:

1. **Create** the project (`ProjectsPage.createProject`). Assert `mise.toml` appears in the laptop workspace directory (`<WORKSPACE_ROOT>/<name>/mise.toml`) and that an empty `mise.lock` exists beside it — without a pre-existing lockfile, `MISE_LOCKFILE=1` installs cannot record resolved versions.
2. **Install** `jq` through the row's package input (`row.installPackage`). Assert `mise.toml` lists `jq`, `mise.lock` mentions `jq` (proving lockfile maintenance), and the row's installed-package chips show `jq` (proving `list_packages` re-read the manifest).
3. **Run locally**: `podman exec --workdir /root/work <name> mise exec -- jq --version` contains `jq-`, proving the binary was installed into `MISE_DATA_DIR`, not merely recorded in the manifest.
4. **Deploy** to `mio-tests-remote` (`row.deployTo`, 300 s timeout for the cold remote `mise install`). Assert the remote container state is `running`.
5. **Reproduce on remote**: the same `mise exec -- jq --version` on `REMOTE_CONNECTION` contains `jq-`, and `sandbox-mio/<name>:deployed` does **not** exist on the remote — proving the tool came from `mise.lock`, never a committed image.
6. **Manifest carried by sync**: after `row.waitForSyncStatus("up-to-date")`, `cat /root/work/mise.toml` on the remote mentions `jq`. (Reproduction itself uses `podman cp`, not the sync, so step 5 can pass before this is ready.)
7. **Destroy** (`row.destroy`). Assert the local container is gone but `mise.toml` survives on the laptop (the workspace, and its manifest, must outlive destroy).

## De-Risking Spike Results (2026-06-27)

The spike is recorded in full under "Spike Validation (2026-06-27)" in `02_dev.md`. Summary as it bears on this spec:

- **Cleared — mise runs on the base and installs zellij with `web`.** `mise v2026.6.14` ran on `debian:12-slim`; `mise install zellij@0.44.3` resolved through the aqua backend and produced a working `zellij web`. This underwrites both this spec and `web-terminal.spec.ts`.
- **Cleared — lockfile-driven reproduction.** `mise.toml` (`jq = "latest"`) + `mise.lock` (resolved `1.8.2`, SHA256, provenance) reproduced byte-identical `jq` on a fresh container from a 3 KB transfer. This is exactly the deploy path step 5 asserts.
- **Cleared — glibc base is the right call.** `node@22` failed on Alpine/musl (exit 127) and succeeded on `debian:12-slim`; static CLIs like `jq` ran on both. The spec uses `jq`, so it would pass on either base, but the feature ships the glibc base for runtime coverage.
- **Known risk, not a blocker — GitHub rate limit.** Unauthenticated installs can hit HTTP 403 on the GitHub version-listing API (60 req/h). This is a **test concern** that can make step 2 (install of `jq` at `latest`) flaky on a hot egress IP, and step 4's cold remote `mise install` similarly. It does not block writing the spec — the lockfile drives the remote install, so only the initial local resolve makes a listing call. The durable fix is the `GITHUB_TOKEN`/`MISE_GITHUB_TOKEN` pass-through still outstanding in `02_dev.md` Phase D; until then, re-run on a 403 rather than treating it as a real failure.

No blocker classified as a feature fix was found for this spec — unlike the remote-sync spike (`docs/features/remote-sync/03_e2e.md`), whose `image scp` blocker had to be fixed first. The mise migration reuses the already-fixed `save | load` staging and `accept-new` host-key handling, so the deploy path is sound.

## Sequencing

The spike did not invert the plan, so the ordering is straightforward:

1. **Spec is written** (`runtime-management.spec.ts`, done) — replaces the former flox spec that asserted `.flox/env/manifest.toml`.
2. **Run the two-machine verification** end to end (still outstanding per `02_dev.md` Phase D): `pnpm wdio` with both machines provisioned. This is the deploy verification run the dev plan flags as remaining.
3. **Wire the `GITHUB_TOKEN` pass-through** (`02_dev.md` Phase D) if step 2 shows rate-limit flakiness; the spec already documents the 403 as a re-run-worthy transient.

## Environment Notes for the Next Session

- Both machines are provisioned by `onPrepare`: `mio-tests` (source, `PODMAN_CONNECTION`) and `mio-tests-remote` (deploy target). After any machine restart, its rootless `podman system service` socket must be re-activated (`provisionMachine` / `startPodmanSocket` in `e2e/lib/podman-machine.ts`) before `podman --connection …` works.
- The mise base image `sandbox-mio/base:mise` (~324 MB) is staged on both connections by `ensureMiseBaseImage`; the first run builds it from `src-tauri/resources/Containerfile` (one-time, can be slow — the bootstrap spec allows 900 s).
- `SANDBOX_WORKSPACE_ROOT` is set to `~/.sandbox-mio-e2e`; the spec reads `mise.toml`/`mise.lock` from `<root>/<project>/`.
- The bundled Mutagen sidecar must be staged at `src-tauri/binaries/mutagen-<triple>` for `deploy_sandbox`; the debug build step in `onPrepare` assumes it is present (see `docs/features/remote-sync/03_e2e.md`).
- Both machines need outbound internet for the `mise install` downloads from the upstream release hosts named in `mise.lock`.
- Use `MIO_REMOTE_KEEP=1` for fast iteration (leaves the remote machine running between runs). Prior failed runs leave `e2e-runtime-*` containers on `mio-tests`; the spec's `after` only removes the current run's container — clear stale ones with a `podman ... rm -f` filtered on the `e2e-runtime` name prefix when the list gets cluttered.

## Common Gotchas

| Gotcha | Cause | Fix |
|---|---|---|
| Step 2 (`installPackage`) intermittently fails with an HTTP 403 from GitHub | `mise use jq` at `latest` makes an unauthenticated GitHub version-listing call, rate-limited to 60 req/h per IP | Re-run; for a durable fix pass `GITHUB_TOKEN`/`MISE_GITHUB_TOKEN` into the runtime exec environment (`02_dev.md` Phase D) |
| `mise exec -- jq --version` prints nothing or errors after install | `mise use` recorded the tool in `mise.toml` but the binary was not realized into `MISE_DATA_DIR`, or the exec did not run in `/root/work` so mise read no config | Run the exec with `--workdir /root/work` (as the spec does) so mise reads the workspace `mise.toml`; confirm the install step itself succeeded |
| `mise.lock` is empty after install even though `mise.toml` lists the tool | `MISE_LOCKFILE=1` was not baked into the base image, or `mise.lock` did not exist before the install (mise only maintains an already-present lockfile) | Confirm Phase A bakes `MISE_LOCKFILE=1` and Phase B's `init` writes an empty `mise.lock`; the create step asserts the empty lockfile exists |
| Step 4 deploy fails creating the remote container | The mise base image is not staged on `mio-tests-remote` | `ensureMiseBaseImage(LOCAL_CONNECTION, [REMOTE_CONNECTION])` in `onPrepare` stages it via `save \| load`; never `podman image scp` |
| Staging the base image onto the remote fails with "lookup &lt;name&gt;: Temporary failure in name resolution" | `podman image scp` between two Podman-machine connections resolves the connection name as a DNS host on Windows | Stage with a `podman --connection <src> save … \| podman --connection <dst> load` pipe instead of `image scp` (what `ensureMiseBaseImage` already does) |
| Step 5 finds a `sandbox-mio/<name>:deployed` image on the remote | A regression reintroduced the committed-image deploy path instead of manifest reproduction | Keep `deploy` delegating to `reproduce_remote` (`mise.toml`/`mise.lock` `podman cp` + `mise install`); never `podman commit` for software |
| Remote `cat /root/work/mise.toml` (step 6) lacks `jq` even though deploy succeeded | The workspace Mutagen sync had not yet seeded the manifest onto the remote when read | Wait for `row.waitForSyncStatus("up-to-date")` before the read, as the spec does; reproduction itself uses `podman cp`, not the sync, so step 5 can pass before step 6 is ready |
| Cold remote `mise install` (step 4) exceeds the default 180 s mocha timeout | The first remote install downloads the lock-pinned binary over the network on a fresh container | The `describe` raises `this.timeout(600000)` and `deployTo` is given a 300 s timeout; keep both |
| Remote machine answers no `podman` commands right after start | The rootless `podman system service` socket is not auto-started on the WSL image | Run `provisionMachine(REMOTE_CONNECTION)` (the `startPodmanSocket` launcher in `e2e/lib/podman-machine.ts`) before using the connection |
| Every `li*=<name>` row lookup returns "element wasn't found" although a failure-time page-source dump shows the row present | A row-internal list rendered as `<li>` nested inside the project's own `<li>`; WebView2's live WebDriver XPath cannot resolve a project `<li>` that contains a nested `<li>` (lenient parsers still find it) | Render row-internal lists with non-`<li>` elements (`<div>`/`<span>`); keep the project row the only `<li>`. The installed-package chips were already moved to `<span class="font-mono">` for this reason — preserve that class, which `ProjectRow.installedPackages` selects |
| `runtime-management.spec.ts` shows fewer/more failures than the step count implies | Mocha failure numbers are sequential across the run, not per spec; an early crash cascades into later row-lookup failures | Read the per-test pass/fail list, not the failure ordinals; capture the failure-time page source (the spec's `afterEach`) to tell an app crash from a stale-element race |
| By-hand spike `podman exec … --workdir /root/work` fails with "can't change directory to 'C:/Program Files/Git/...'" | Git Bash (MSYS) rewrites a leading-slash argument into a Windows path before it reaches `podman exec` | Prefix the by-hand command with `MSYS_NO_PATHCONV=1`; the WebdriverIO harness uses `spawnSync` with `shell: false` and is unaffected |

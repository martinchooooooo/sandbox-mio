# Activity Center E2E Test Plan

Test plan for the global activity-and-notification subsystem built in `docs/features/activity-center/02_dev.md`. No spike of the real feature code path has been run because no phase is implemented yet; the only evidence so far is the standalone race model recorded in `01_ideas.md` Validation (2026-06-29), which proved the hydration-vs-stream fold logic in the abstract but exercised no Tauri command. This document defines the app-driven spec to add and the one timing risk that must be de-risked before the spec is worth running. The feature has a defining property no existing spec covers: progress must survive a **route change** and a **webview reload**, because the source of truth is the Rust `TaskRegistry`, not any route component. The spec therefore drives a real enrolled command (`download_model`) from one route, then asserts the task is visible from a *different* route and *after a reload* — the two assertions with teeth that the existing `local-llm.spec.ts` deliberately does not make.

## Goal

The spec must prove the real activity pipeline end to end, reusing the already-staged host-side inference path as the work that produces tasks:

1. A real `download_model` (Phase D enrollment, `src-tauri/src/lib.rs` line 487 → `inference::download_gguf`) calls `activity::open`/`progress`/`succeed`, which mutate the Rust `TaskRegistry` (Phase A) and broadcast `activity://task-updated` via `app.emit`.
2. The frontend store `src/lib/activity/activity.svelte.ts` (Phase B), subscribed once from the root layout, folds those events by version and renders them in `ActivityCenter.svelte` (Phase C) — proven by the task row appearing in the activity panel **while a route other than `/models` is mounted**.
3. After a webview reload, the same task reappears via the `list_tasks` snapshot (Phase A command) — proving the registry, not the frontend store, is authoritative (the store was wiped by the reload and rehydrated).
4. A terminal transition (`succeeded`) appends a synthetic line to the Event scrollback and raises a `sonner` toast — proving the store's `onTransition` subscriber fired.
5. A real `start_inference` (Phase E enrollment) produces an `inference-setup` task that reaches `succeeded` — proving the second enrolled flow drives the registry through the same path.

A weaker test would fail to have teeth in three specific ways, each of which the existing `local-llm.spec.ts` already exhibits and must not be mistaken for activity-center coverage: (a) asserting the `/models` in-context progress bar (the per-invoke `Channel` path) proves nothing about the global store, because the `Channel` and the `activity://task-updated` emit are independent code paths — the `Channel` UI would still work with the entire activity subsystem deleted; (b) reading `list_tasks` directly via `invoke` without navigating would not prove the store's subscribe-before-snapshot fold or the survives-navigation property; (c) asserting a task only on the route that started it would not distinguish a working global store from a component-local one. The cross-route assertion (Step 4) and the reload-hydration assertion (Step 5) are the assertions with teeth.

## Existing Test Styles

Two styles exist, per `docs/e2e-testing.md` (removed 2026-11-05; current harness: `docs/architecture/testing.md`):

- **App-driven WebdriverIO specs** (`e2e/test/specs/*.spec.ts`) drive the compiled Tauri app via `tauri-driver` and exercise real Tauri commands. The closest sibling is `e2e/test/specs/local-llm.spec.ts`, which already drives the real `download_model` → `start_inference` → completion path host-side and reads state from the host filesystem and a real HTTP call rather than `podman exec`. Container-touching specs (`runtime-management.spec.ts`, `deploy-remote.spec.ts`, `agent-setup.spec.ts`) read state via `podman exec`.
- **Standalone transport tests** drive a vendored binary directly without the app — smoke-only, not feature coverage.

The new activity-center spec belongs to the app-driven style and is a near-twin of `local-llm.spec.ts`: it reuses the same staged `llama-server` sidecar and the same `MIO_TEST_MODEL` tiny GGUF as the work that produces tasks, but its assertions read the **activity panel from a foreign route** and **after a reload**, not the `/models` route that started the work.

## Chosen Approach

Spec file: `e2e/test/specs/activity-center.spec.ts`. New page object: `e2e/test/pageobjects/activity.page.ts` (`ActivityCenter`: toggle the panel from any route, read the badge count, read a task row's status by task id, read the event scrollback, read the toast). The existing `e2e/test/pageobjects/models.page.ts` is reused to *start* the work (download/start inference); the new page object *observes* it globally.

Topology: **host-only, no Podman machine** for the core scenario, identical to `local-llm.spec.ts` Steps 1–5. The enrolled flows chosen for the spec — `download_model` and `start_inference` — run entirely on the Windows host, so no container is needed to produce tasks. This reuses the staging the local-LLM harness already added (the `llama-server` sidecar at `src-tauri/binaries/llama`, the `MIO_TEST_MODEL` env injection, and the app-data model cleanup in `onComplete`); the activity spec needs **no new provisioning**.

Test model: the same `MIO_TEST_MODEL` tiny GGUF (`SmolLM2-135M-Instruct`, ~100 MB) the local-LLM spec uses. The model-download task id is `model-download:smollm2-135m`, derived from its stable id, so the spec asserts on that exact id rather than a count (other specs in the same suite may leave tasks in the shared per-process registry — though each app launch starts with an empty registry).

A secondary, **conditional container scenario** (Step 7) covers the Event half: it creates a sandbox via the existing `projects` flow so a real `listen_events` container event flows into the *global* store, and asserts the event scrollback in the activity panel gains a line. It uses `LOCAL_CONNECTION` (`mio-tests`, already provisioned by `onPrepare`) and self-skips if container creation is unavailable.

`this.timeout(600000)` (10 minutes) on the suite, matching `local-llm.spec.ts`: a cold run downloads the test GGUF and loads it into the sidecar.

## Selector Contract (a Phase C prerequisite)

The page object uses data-attribute selectors set in `src/lib/activity/ActivityCenter.svelte`, mirroring the `data-*` convention in `src/routes/models/+page.svelte` (so the page object never depends on CSS classes or translated copy). Phase C **must** add these attributes or the spec cannot be written:

- `[data-activity-toggle]` — the bell button (present on every route).
- `[data-activity-badge]` — the badge element; its text is the count.
- `[data-activity-panel]` — the expandable panel root.
- `[data-activity-task='<task-id>']` — one row per task, with `[data-task-status]` (`running`/`succeeded`/`failed`) and a `[data-task-detail]` child.
- `[data-activity-events]` — the event scrollback container.

The `sonner` toast is read via its own rendered markup (`[data-sonner-toast]`, emitted by the shadcn-svelte `sonner` component); the spec asserts presence and `data-type` (`success`/`error`).

## Harness Changes

Edits to `e2e/wdio.conf.ts` are minimal because the local-LLM staging is reused:

1. **No new staging.** The `llama-server` sidecar staging, `MIO_TEST_MODEL` injection, and `app_data_dir()/models/` cleanup added for `local-llm.spec.ts` already cover the work this spec produces. If the activity spec runs in a suite where `local-llm.spec.ts` is absent, the same three staging steps must be present.
2. **Registry isolation.** The `TaskRegistry` is in-memory per app process and starts empty at each session launch, so no cleanup is required. The spec asserts on the specific task id `model-download:smollm2-135m`, never on a total count, so residue from another spec in the same session cannot make it pass or fail spuriously.
3. **Reload mechanism.** Step 5 reloads the webview with `browser.refresh()`. No harness change is needed, but the spec must re-open the activity panel after reload (the panel's open/closed state is component-local UI, not registry state, and is reset by the reload).

The `before` hook asserts `MIO_TEST_MODEL` is set (same as `local-llm.spec.ts` lines 35–44). The `after` hook calls `stop_inference` best-effort and deletes the test model directory. `afterEach` captures `.diag` (URL + page source + screenshot) on failure, identical to `local-llm.spec.ts` lines 60–74.

## Page Object — `e2e/test/pageobjects/activity.page.ts`

`ActivityCenter extends AppPage` with data-attribute selectors:

- `openPanel()` — click `[data-activity-toggle]`, wait for `[data-activity-panel]` displayed. Works on any route because the toggle lives in the root layout.
- `badgeCount(): Promise<number>` — parse the text of `[data-activity-badge]` (0 when absent).
- `taskRow(id): Element` — `$("[data-activity-task='" + id + "']")`.
- `waitForTask(id, status, timeoutMs)` — poll until `taskRow(id)` exists with `[data-task-status='<status>']`.
- `taskDetail(id): Promise<string>` — text of the row's `[data-task-detail]`.
- `eventsText(): Promise<string>` — text of `[data-activity-events]`.
- `latestToast(): Element` — `$("[data-sonner-toast]")`; `toastType()` reads its `data-type`.

## Spec Scenario — `e2e/test/specs/activity-center.spec.ts`

```ts
describe("Activity Center — global task tracking", function () {
  this.timeout(600000);
  // before/after/afterEach mirror local-llm.spec.ts (MIO_TEST_MODEL parse, stop_inference, .diag)
});
```

---

**Step 1 — Suite setup**

`before`: assert `MIO_TEST_MODEL` is set and parse `{id,file,sizeBytes}`; compute `taskId = "model-download:" + model.id`. `after`: best-effort `stop_inference` and delete the test model dir. `afterEach`: `.diag` capture on failure.

---

**Step 2 — Start a real download from `/models`**

Action: `ModelsPage.open()`, then `ModelsPage.startDownload(model.id)`.

Assertion: none yet — this is the work that produces the task. Driving the real `download_model` command (not a stub) is what gives every later assertion teeth.

---

**Step 3 — The task appears in the activity center on `/models`**

Action: `ActivityCenter.openPanel()`; `ActivityCenter.waitForTask(taskId, "running"|"succeeded", 480000)` (accept either, since a fast download may already be terminal).

Assertion: the row `[data-activity-task='model-download:smollm2-135m']` exists. Proves the Phase D enrollment called `activity::open` and the `activity://task-updated` emit reached the store. A missing row means either the enrollment did not fire or the store never subscribed.

---

**Step 4 — The task survives navigation to a foreign route (teeth)**

Action: navigate to `/projects` via its nav link (`ProjectsPage` / `$("a[href='/projects']")`), **without** returning to `/models`; `ActivityCenter.openPanel()` on `/projects`; `ActivityCenter.waitForTask(taskId, "succeeded", 480000)`.

Assertion: the same task row is present on `/projects` and reaches `succeeded`. This is the assertion the existing `local-llm.spec.ts` cannot make: the `/models` component that started the download is unmounted, so a component-local progress UI would show nothing here. Observing the task reach `succeeded` on a route that never initiated it proves the registry + app-wide event + module-scoped store deliver progress independently of route lifetime — the core feature claim and the GUI check `01_ideas.md`/`02_dev.md` deferred.

---

**Step 5 — The task survives a webview reload via `list_tasks` hydration (teeth)**

Action: `browser.refresh()`; re-`openPanel()`; `ActivityCenter.waitForTask(taskId, "succeeded", 30000)`.

Assertion: after the reload wiped the frontend store, the completed task is present again. Because the only place the task could come from after a reload is the `list_tasks` snapshot, this proves the Rust `TaskRegistry` is authoritative and `ensureActivity()` rehydrated it in Protocol B order (subscribe, then snapshot, fold by version). A frontend-only store would show an empty panel here — the exact failure mode the Rust-registry decision exists to prevent.

---

**Step 6 — Terminal transition raised a toast and an event line**

Action: read `ActivityCenter.eventsText()` and `ActivityCenter.latestToast()` shortly after the `succeeded` transition in Step 4 (capture the toast before its auto-dismiss; assert the event line, which is persistent, as the timing-robust proxy).

Assertions:
- `eventsText()` contains a line referencing the completed model-download task — proving `onTransition` appended a synthetic Event to the ring buffer (the Tasks-vs-Events split: a terminal task also writes one Event line).
- If captured in time, `latestToast()` has `data-type='success'`. The toast is best-effort because success toasts auto-dismiss; the event-line assertion is the one that must pass.

---

**Step 7 — `start_inference` produces a second task**

Action: `ModelsPage.open()`, `ModelsPage.startInference(model.id)`, `ModelsPage.waitForRunning(180000)`; `ActivityCenter.openPanel()`; `ActivityCenter.waitForTask("inference-setup", "succeeded", 180000)`.

Assertion: an `inference-setup` task row reached `succeeded` and its `[data-task-detail]` reports the live `base_url` (the `succeed` detail from Phase E). Proves the second enrolled flow (Phase E) drives the registry through the same `open`/`progress`/`succeed` path, and that a different `TaskKind` renders. `after`/Step 8 stops inference.

---

**Conditional Step 8 — Container event reaches the global event scrollback (Podman, self-skipping)**

Guard: requires `LOCAL_CONNECTION` (`mio-tests`); `this.skip()` if sandbox creation fails. Action: create a sandbox via `ProjectsPage`, then read `ActivityCenter.eventsText()`.

Assertion: the scrollback contains a container lifecycle line (e.g. `create`/`start`) for the new sandbox — proving the `listen_events` channel, now owned by the store (Phase C supersede of `EventLog.svelte`), feeds the global event log rather than a route-local one. This is the only scenario that touches Podman; it self-skips on machines without the connection.

---

**Conditional Step 9 — A failed task increments the badge and raises a sticky error toast (needs a bad descriptor)**

Guard: requires a second injected descriptor `MIO_TEST_MODEL_BAD` (a valid repo/file with a deliberately wrong `sha256`, or a nonexistent repo) so `download_model` reaches `activity::fail`. Action: start the bad download, navigate to `/projects`, open the panel.

Assertions: the task row for the bad id shows `[data-task-status='failed']` with `[data-task-detail]` carrying the verbatim error; `latestToast()` has `data-type='error'` and persists (sticky); `ActivityCenter.badgeCount()` is ≥ 1 before the panel is opened and returns to 0 after (proving `markSeen()` on panel open). Proves the failure-mapping contract (the command's `Err` path calls `activity::fail`) and the badge unread semantics. This step needs the bad descriptor wired into the harness; until then it is documented but not implemented.

## De-risking Spike Results

No spike of the real activity code path has been run — no phase is implemented. The standalone race model (2026-06-29, recorded in `01_ideas.md` Validation) is the only evidence and covers only the fold logic, not any Tauri command, `app.emit`, or webview reload. One genuine risk must be de-risked by hand before the spec is worth writing:

| Risk | Status | How to clear before writing the spec |
|---|---|---|
| **Observable running-window too short.** A ~100 MB download (or a 135M-model inference setup) may finish in under one poll interval, so the "running" state is never seen and Step 3/4's `running` assertion is flaky. | **Open (test concern).** | Make Step 3/4 accept `running` **or** `succeeded` (the spec already does), and rely on the *succeeded-on-foreign-route* and *reload-hydration* assertions for teeth, which are timing-insensitive. If a held running window is wanted, inject a slightly larger `MIO_TEST_MODEL` (e.g. `Qwen2.5-0.5B`, ~400 MB) so a multi-second download holds the running state across the navigation. |
| **Reload during an in-flight task.** `browser.refresh()` mid-download could interrupt the `download_model` command if the command future is tied to the webview. | **Open (must check; feature-relevant).** `02_dev.md` claims the command keeps running because it writes the registry directly, but this is the exact GUI behaviour `01_ideas.md` listed as "not spiked". Run Step 5's reload **after** the task is `succeeded` first (deterministic); then, as a separate manual check, reload **mid-download** and confirm the task still reaches `succeeded` in the registry. | Manual: start a ~400 MB download, `F5` mid-flight, observe the activity panel still completes the task. Record the result here. If the future is cancelled by the reload, that is a **feature fix** (detach the command's work from the webview) before the mid-flight reload assertion is worth adding. |
| **`sonner` success toast auto-dismisses before assertion.** | **Open (test concern).** | Assert the persistent Event scrollback line, not the toast, as the required proof (Step 6); treat the toast assertion as best-effort, and use the **sticky error** toast (Step 9) for the deterministic toast assertion. |

Classify: all three are test concerns except the mid-flight-reload behaviour, which is a potential feature fix. The core spec (Steps 1–7) is worth writing once Phases A–E land, because its teeth (Steps 4 and 5, both post-completion and timing-insensitive) do not depend on any open risk. The mid-flight-reload assertion and Step 9 wait on their respective checks.

## Sequencing

1. Implement Phases A–E (`02_dev.md`): the Rust registry + `list_tasks`, the frontend store, the `ActivityCenter.svelte` surface **with the data-attributes from the Selector Contract**, and the `download_model`/`start_inference` enrollments.
2. Run the **bring-up spike by hand**: start a download on `/models`, navigate to `/projects`, confirm the activity panel shows the task reach `succeeded`; then `F5` and confirm it rehydrates. Record results in the table above. Separately, reload mid-download and record whether the task still completes.
3. Add `activity.page.ts`, then `activity-center.spec.ts` Steps 1–7.
4. Add the conditional container scenario (Step 8) once Step 7 is green.
5. Wire `MIO_TEST_MODEL_BAD` and add the failure scenario (Step 9).
6. Add the mid-flight-reload assertion only if the manual check in Step 2 confirms the command survives the reload; otherwise file the feature fix first.

Steps 1–7 have no dependency on Podman or any unresolved risk, so they land as soon as Phases A–E and the bring-up spike pass.

## Environment Notes

- No Podman machine is required for Steps 1–7; `mio-tests` is provisioned by `onPrepare` only for the conditional Step 8 and other specs.
- The `llama-server` sidecar (+ Vulkan DLLs) must be staged at `src-tauri/binaries/llama` before `pnpm tauri build --debug --no-bundle`, the same requirement `local-llm.spec.ts` documents; the activity spec reuses it to produce real tasks.
- `MIO_TEST_MODEL` must be set (the tiny GGUF); the spec derives the task id `model-download:<MIO_TEST_MODEL.id>` from it.
- The activity panel's open/closed state is component-local and resets on `browser.refresh()`; the spec re-opens the panel after every reload or navigation.
- The `TaskRegistry` is in-memory and empty at each app launch; assert on the specific task id, never a count, to stay robust against other specs in the same session.
- Step 9 requires a `MIO_TEST_MODEL_BAD` descriptor (valid URL, wrong sha256, or nonexistent repo) injected the same way as `MIO_TEST_MODEL`.
- A network connection is required for the model download that produces the tasks; the activity assertions themselves are fully local.

## Common Gotchas

| Gotcha | Cause | Fix |
|---|---|---|
| Spec passes even though the global store is broken | The assertion read the `/models` in-context progress bar (the per-invoke `Channel` path), which is independent of the `activity://task-updated` emit | Assert the task from a foreign route (`/projects`, Step 4) and after `browser.refresh()` (Step 5); never assert activity coverage from the `/models` route that started the work |
| `waitForTask(id, "running", …)` times out on a fast download | The ~100 MB download finished before the first poll, so the `running` state was never observed | Accept `running` **or** `succeeded` in Step 3/4 and rely on the succeeded-on-foreign-route and reload assertions for teeth; or inject a larger `MIO_TEST_MODEL` to hold a running window |
| Activity panel empty after `browser.refresh()` | The frontend store was wiped by the reload and `list_tasks` hydration did not run, or `ensureActivity()` awaited `list_tasks` before registering `listen` and lost the snapshot | Confirm `ensureActivity()` runs at root-layout top level in Protocol B order; the empty panel is the exact failure the Rust-registry + subscribe-first design prevents |
| `[data-activity-task='model-download:...']` selector never matches | `ActivityCenter.svelte` (Phase C) did not add the `data-*` attributes from the Selector Contract | Add `[data-activity-toggle]`, `[data-activity-panel]`, `[data-activity-task]`, `[data-task-status]`, `[data-activity-events]` in `src/lib/activity/ActivityCenter.svelte` before writing the page object |
| Success toast assertion flakes | The `sonner` success toast auto-dismisses before WebdriverIO reads it | Assert the persistent Event scrollback line (Step 6) as the required proof; use the sticky **error** toast (Step 9) for a deterministic toast assertion |
| Task stuck at `running`, never reaches `succeeded` | The enrolled command's error path did not call `activity::fail`, or `succeed` was never called on the success path | Verify the Phase D/E enrollment wraps the command body so both the `Ok` and `Err` arms reach the registry (`02_dev.md` "Failure mapping is the command's job") |
| Mid-download `browser.refresh()` aborts the task | The `download_model` command future may be tied to the webview that initiated it | De-risk by the manual check in Sequencing Step 2; if the task dies, detach the command's work from the webview (feature fix) before adding the mid-flight-reload assertion |
| Step 8 finds no container line in the scrollback | The `listen_events` channel is still owned by a route component (`EventLog.svelte`) instead of the store | Confirm Phase C moved `listen_events` ownership into `activity.svelte.ts` and removed `EventLog.svelte` from `src/routes/projects/+page.svelte` |
| Two activity panels or duplicate toasts appear in the spec DOM | A per-route `EventLog`/`<Toaster />` was reintroduced alongside the global one | The activity center and `<Toaster />` mount exactly once in `src/routes/+layout.svelte`; the spec's `[data-activity-panel]` must resolve to a single element |

# Remote Sandbox Terminal — E2E Test Plan

This document is the test plan for the remote-sandbox terminal feature described in `docs/features/remote-terminal/02_dev.md`. The plan covers the deployed-sandbox terminal path introduced by Phases A–E of that build plan: specifically, the Mutagen forwarding session that bridges a Windows-host loopback port to a Zellij web server running inside a remote Podman container. No spike has been run for the remote path; the risks that need spike confirmation are listed in Section 7.

## Goal

The test must prove that clicking Terminal for a deployed sandbox invokes the real `open_terminal` Tauri command, which calls `RuntimeManager::prepare_terminal` over `REMOTE_CONNECTION`, creates a `mutagen forward` session (`src-tauri/src/sync/mod.rs::forward_create`), and returns a URL on the Windows-host loopback that serves the Zellij web client with HTTP 200. A weaker test that mocks `forward_create`, or one that only checks the persisted token file without fetching the URL, would fail to confirm that the Mutagen daemon reaches `Connected` state and that pasta's `--host-lo-to-ns-lo` flag on the remote container routes the port correctly.

The test also proves the cleanup path: that `undeploy_sandbox` calls `forward_terminate` and removes the Mutagen forwarding session named `terminal-<name>` before tearing down the sync session.

## Existing Test Styles

The repo contains one category of E2E test: app-driven WebdriverIO specs that launch the compiled Tauri binary, drive the UI through page objects, and read ground truth from the CLI (`podman`, Mutagen sidecar) and the filesystem.

- `e2e/test/specs/web-terminal.spec.ts` — local terminal path; creates a local sandbox, clicks Terminal, and asserts (a) the Mutagen forwarding session `terminal-<name>` reaches `Connected`, (b) the forwarded URL serves HTTP 200, and (c) `destroy` terminates the forwarding session. Updated in the remote-terminal feature to cover the unified forward path for local sandboxes.
- `e2e/test/specs/deploy-remote.spec.ts` — deploy and undeploy a sandbox to `REMOTE_CONNECTION`; drives the same page objects the remote terminal spec will use (`row.deployTo`, `row.undeploy`).

The new spec belongs to the same app-driven WebdriverIO category.

## Chosen Approach

Add `e2e/test/specs/remote-terminal.spec.ts` with two `describe` blocks. The first proves the undeploy cleanup path (deploy → open terminal → undeploy → forwarding session gone). The second proves the destroy-while-deployed cleanup path, which follows a separate code branch in `lib.rs::destroy_sandbox`. No external host is needed; the topology is the same two local Podman machines used by `deploy-remote.spec.ts`. This keeps the spec self-contained and lets it run in the same CI environment.

Also add to `e2e/test/specs/web-terminal.spec.ts`: a `forwardList` assertion proving the local path also goes through `forward_create` (the unified path from the remote-terminal feature), and a post-destroy assertion proving `forward_terminate` is called for local sandboxes.

## Harness Changes

### Already applied (unstaged `e2e/wdio.conf.ts`)

`onPrepare` now copies `tools/mutagen-agents.tar.gz` to `src-tauri/target/debug/mutagen-agents.tar.gz` immediately after the Tauri build step. Mutagen resolves the agent bundle relative to its own binary; without this copy, `mutagen forward create` targeting a new SSH endpoint fails with `unable to find agent bundle`. The copy is idempotent and safe to repeat.

### Still needed for the new spec

No additional harness changes are required. `REMOTE_CONNECTION` is provisioned and the mise base image is staged on both machines in the existing `onPrepare`. `SANDBOX_WORKSPACE_ROOT` is already exported as an env var. The `after` hook in the new spec should call `podman(LOCAL_CONNECTION, ["rm", "-f", name])` and `podman(REMOTE_CONNECTION, ["rm", "-f", name])` (mirroring `deploy-remote.spec.ts:27–28`).

### `REMOTE_TERMINAL_KEEP` env flag

The `deploy-remote.spec.ts` precedent uses `MIO_REMOTE_KEEP=1` to skip teardown during fast iteration. The remote terminal spec's `after` hook should honour a `MIO_REMOTE_KEEP` check rather than introducing a new flag so iteration on the two specs is symmetric.

## Spec Scenario

### `e2e/test/specs/remote-terminal.spec.ts` — describe block 1: undeploy path

1. **Create sandbox.** Call `ProjectsPage.createProject(projectName)`. Assert the row appears.

2. **Deploy to `REMOTE_CONNECTION`.** Call `row.deployTo(REMOTE_CONNECTION)`. Assert `podman(REMOTE_CONNECTION, ["inspect", projectName, "--format", "{{.State.Status}}"])` returns `"running"`. Assert `row.isHostShown(REMOTE_CONNECTION)` is true.

3. **Assert remote container has the zellij port published.** Read `podman(REMOTE_CONNECTION, ["inspect", projectName, "--format", '{{json (index .HostConfig.PortBindings "8082/tcp")}}'])`. Parse JSON; assert the array includes an entry with `HostIp === "127.0.0.1"`. This proves Phase A (remote `--publish` flag) is in effect. Mirrors the local check in `web-terminal.spec.ts`.

4. **Wait for sync to settle.** Call `row.waitForSyncStatus("up-to-date")`.

5. **Click Terminal (deployed state).** Call `row.openTerminal()`. This button now appears in the deployed branch of `SandboxItem.svelte` (Phase E).

6. **Wait for the token file.** Poll `fs.existsSync(tokenPath)` (up to 60 s, 1 s interval) where `tokenPath = path.join(workspaceDir, ".mio", "zellij.json")`. Failure here means `open_terminal` did not complete or `prepare_terminal` failed before writing the session file.

7. **Assert Mutagen forwarding session is active.** Call `forwardList("terminal-<projectName>")` from `e2e/lib/mutagen.ts` (which passes `MUTAGEN_DATA_DIRECTORY` pointing at the app's private daemon). Poll for `"Connected"` up to 60 s because first-run agent installation can be slow. This is the hard proof that Mutagen reached the remote host.

8. **Assert the persisted session file is well-formed.** Parse `tokenPath`; assert `session.token` is a non-empty string and `session.url` starts with `"http://127.0.0.1:"`. The URL is the Windows-host loopback port chosen by the Rust `TcpListener::bind("127.0.0.1:0")` step in `lib.rs::open_terminal`.

9. **Assert the forwarded port serves HTTP 200.** Poll `fetch(session.url)` for HTTP 200 (up to 30 s, 1 s interval). Failure here means the Mutagen tunnel is connected but `pasta:--host-lo-to-ns-lo` on the remote container is not routing the container-loopback port to the remote host's loopback.

10. **Re-open terminal (idempotency).** Call `row.openTerminal()` again. Assert `forwardList("terminal-<projectName>")` still contains `"Connected"`. Assert `fetch(session.url)` returns HTTP 200.

11. **Undeploy.** Call `row.undeploy()`. Assert `!podmanOk(REMOTE_CONNECTION, ["inspect", projectName])`. Assert `forwardList("terminal-<projectName>")` does not contain `"Connected"`. This proves `undeploy_sandbox` called `forward_terminate` before tearing down the sync session.

12. **Destroy.** Call `row.destroy()`. Assert `!podmanOk(LOCAL_CONNECTION, ["inspect", projectName])`.

### `e2e/test/specs/remote-terminal.spec.ts` — describe block 2: destroy-while-deployed path

This describe block exercises the separate `destroy_sandbox` code branch that handles a deployed sandbox (`lib.rs::destroy_sandbox` lines that call `forward_terminate` before `engine.terminate` and `remove_remote`). The destroy button in `SandboxItem.svelte` is rendered outside the `{#if deployment}` block, so it is always clickable.

Setup (create → deploy → sync → open terminal → wait for `Connected`) runs in the `before` hook, not an `it`. When setup fails, Mocha skips the `it` with a clear hook-failure message rather than running it against a missing project row, which would produce a misleading "element not found" error.

**`before` hook:** `ProjectsPage.open()` → `createProject(projectName)` → `row.deployTo(REMOTE_CONNECTION)` → `row.waitForSyncStatus("up-to-date")` → `row.openTerminal()` → poll token file (60 s) → poll `forwardList("terminal-<projectName>")` for `"Connected"` (60 s).

**Single `it` — "destroy removes both containers and terminates the forwarding session":** Call `row.destroy()`. Assert `!podmanOk(LOCAL_CONNECTION, ["inspect", projectName])`. Assert `!podmanOk(REMOTE_CONNECTION, ["inspect", projectName])` — `destroy_sandbox` must call `store.remove_remote` for the deployed branch. Assert `forwardList("terminal-<projectName>")` does not contain `"Connected"` — proves `forward_terminate` was called in the deployed branch of `destroy_sandbox`.

### `e2e/test/specs/web-terminal.spec.ts` additions (implemented)

Two assertions added to the existing local-terminal spec to close the gap introduced by the unified forward path:

- In "opens the terminal": after the URL assertion, call `forwardList("terminal-<projectName>")` and assert `"Connected"`. Proves `open_terminal` calls `forward_create` even for local sandboxes.
- In "destroy removes the container": call `forwardList("terminal-<projectName>")` and assert it does not contain `"Connected"`. Proves `destroy_sandbox` calls `forward_terminate` for the local (non-deployed) branch.

## De-risking Spike Results

No spike has been run. The following risks from `01_ideas.md` remain unconfirmed and must be cleared by a manual spike before the spec is worth writing (a spec that would always go red at a known blocker is not worth writing yet).

**Risk 1 — `mutagen forward create` reaches `Connected` with a sandbox-mio SSH alias (feature-fix concern).**
Mutagen sync uses the alias successfully, but `forward` has not been exercised. Spike: after deploying a sandbox and confirming its alias is in `~/.ssh/sandbox-mio/config`, run `mutagen forward create --name=spike-fwd tcp:127.0.0.1:19998 <alias>:tcp:127.0.0.1:<remote_zellij_port>` and poll `mutagen forward list spike-fwd` for `Connected` status. Fetch `http://127.0.0.1:19998/`. If this fails, the feature itself cannot work and the spec must wait on the fix.

**Risk 2 — `pasta:--host-lo-to-ns-lo` on the remote Podman routes container-loopback correctly (feature-fix concern).**
Confirmed on the local machine by the web-terminal spike; not confirmed on the remote Podman machine. The remote Podman may run a different pasta version. Spike: after deploying a container with the new `--network pasta:--host-lo-to-ns-lo --publish 127.0.0.1::8082` flags, run `podman --connection <alias> exec <name> zellij web --daemonize` and confirm `podman --connection <alias> port <name> 8082/tcp` returns `127.0.0.1:<port>`. Then confirm the Mutagen forward session (Risk 1 spike) reaches `Connected`. If `podman port` returns nothing, the pasta flag is not routing the port and Phase A or the `sshd` configuration needs investigation.

**Risk 3 — `mutagen forward list` sidecar invocation in-spec (test-concern). RESOLVED.**
`e2e/lib/mutagen.ts` already defines `MUTAGEN_BIN = tools/mutagen.exe` (the same binary used by `syncCreate`/`syncFlush`). The new `forwardList(name)` function in that file passes `MUTAGEN_DATA_DIRECTORY=%APPDATA%\com.tincho.sandbox-mio\mutagen` so it queries the app's private daemon rather than a user-installed Mutagen. The path is confirmed; no spike needed.

## Sequencing

1. Run Risk 1 spike (Mutagen forward with the sandbox-mio alias). If it fails, open a feature fix before the spec.
2. Run Risk 2 spike (pasta on remote Podman). If `podman port` returns nothing, fix the network flag or investigate remote Podman version before the spec.
3. Resolve Risk 3 (sidecar path for `mutagen forward list` in-spec). This is a test-concern; it does not block the feature.
4. Write the spec once Risks 1 and 2 are cleared. The spec scenario in Section 6 is the implementation target.

The `web-terminal.spec.ts` changes in the current diff (removing the exact-port assertion and replacing it with a `startsWith("http://127.0.0.1:")` check) are already correct and do not need a spike — the local path now also goes through Mutagen and the URL is the Windows-side forwarded port.

## Environment Notes

A future session writing this spec needs:

- `REMOTE_CONNECTION` machine provisioned and running — `provisionMachine(REMOTE_CONNECTION)` is in `onPrepare` and already handles this.
- Mise base image present on `REMOTE_CONNECTION` — `ensureMiseBaseImage(LOCAL_CONNECTION, [REMOTE_CONNECTION])` in `onPrepare` handles this.
- `tools/mutagen-agents.tar.gz` copied to `src-tauri/target/debug/` — handled by the `onPrepare` `fs.copyFileSync` added in the current diff.
- `~/.ssh/sandbox-mio/config` written at deploy time — the deploy flow calls `ensure_connection_alias` before `forward_create` (visible in `lib.rs::open_terminal`), so the file is ready when the spec reaches step 7.
- `SANDBOX_WORKSPACE_ROOT` set to `~/.sandbox-mio-e2e` — set in `wdio.conf.ts` and read by the spec to locate `tokenPath`.
- The compiled Tauri binary must include all five phases of the remote terminal feature — run `pnpm tauri build --debug --no-bundle` before the suite.

## Common Gotchas

| Gotcha | Cause | Fix |
|---|---|---|
| `podman --connection REMOTE port <name> 8082/tcp` returns nothing | Remote `create` call omits `--publish 127.0.0.1::8082` or `--network pasta:--host-lo-to-ns-lo`, so pasta does not materialise the loopback mapping | Confirm `src-tauri/src/backends/mod.rs` remote `create` call includes both flags (Phase A); inspect the running container with `podman --connection REMOTE inspect <name> --format '{{json .HostConfig.PortBindings}}'` |
| `mutagen forward list terminal-<name>` shows `Connecting` indefinitely | Mutagen agent bundle missing on the remote host, or `AllowTcpForwarding` disabled in remote `sshd_config`, or Zellij not yet started before `forward_create` | Confirm `mutagen-agents.tar.gz` is copied to `target/debug/` (the `wdio.conf.ts` `onPrepare` step); check remote `/etc/ssh/sshd_config` for `AllowTcpForwarding`; confirm `prepare_terminal` starts Zellij before returning `container_port` |
| `fetch(session.url)` times out even though the forwarding session shows `Connected` | `pasta:--host-lo-to-ns-lo` not routing the remote container loopback to the remote host loopback, so Mutagen's TCP connect to `127.0.0.1:<remote_port>` on the remote host reaches nothing | Confirm the flag is present in the remote container's network config; run Risk 2 spike manually |
| Token file never appears | `open_terminal` failed before writing `<workspace>/.mio/zellij.json`, likely because `forward_create` returned an error that was mapped to `RuntimeError::TerminalUnavailable` | Check the app's stderr for the `TerminalUnavailable` message; the `wdio.conf.ts` `tauriDriver` is spawned with `stdio: [null, process.stdout, process.stderr]` so Rust panics and errors appear in the test runner output |
| Forwarding session not removed after undeploy | `forward_terminate` call in `undeploy_sandbox` silently failed, or the `ForwardPortMap` remove did not match the session name | Confirm `sync::forward_terminate` is called before `engine.terminate` in `src-tauri/src/lib.rs::undeploy_sandbox`; run `mutagen forward list` directly after undeploy to inspect live state |
| Terminal button not visible in deployed state | `SandboxItem.svelte` Phase E change missing or the button is inside the wrong `{#if}` branch | Confirm the `<button onclick={openTerminal}>` line is inside the `{#if deployment}` block, not the `{:else}` block (see `src/routes/projects/SandboxItem.svelte`) |
| `mutagen forward create` races with Mutagen agent installation on a fresh remote machine | First `forward create` to a new SSH endpoint triggers agent installation, which takes several seconds; `forward_create` in Rust does not wait for `Connected` before returning | Add a poll for `Connected` state after `forward_create` returns, or increase the `browser.waitUntil` timeout in step 9 to 60 s for first-run coverage |
| Windows-side port already in use when Mutagen binds | Race between `TcpListener` drop and Mutagen bind won by another process on `127.0.0.1:<port>` | Retry `open_terminal` from the UI; `forward_create` calls `forward_terminate` first, so a retry allocates a fresh port |
| `forwardList` always returns empty even when the app created a session | `MUTAGEN_DATA_DIRECTORY` in `forwardList` does not match the directory the app used; the two daemon instances are separate | Confirm the identifier in `src-tauri/tauri.conf.json` is still `com.tincho.sandbox-mio`; update `APP_MUTAGEN_DIR` in `e2e/lib/mutagen.ts` if the identifier changed |
| Destroy of a deployed sandbox leaves the remote container behind | `destroy_sandbox` in `lib.rs` reached `store.destroy` before `store.remove_remote` due to an early error return | Check the app's stderr for the error; the sequence in `destroy_sandbox` is `forward_terminate` → `engine.terminate` → `remove_remote` → `destroy` and any `?` propagation skips subsequent steps |

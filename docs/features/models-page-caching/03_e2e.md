# Models Page Caching E2E Plan

This document is the test plan for `docs/features/models-page-caching/02_dev.md` (Phases A–E: `MachineSpecsCache`, the split `detect_specs`/`redetect_specs`, the `redetect_machine_specs` command, and the `/models` spinner/re-detect-button UI). None of `02_dev.md` is implemented yet, so this spec cannot be written and run until at least Phases A–D (the Rust cache + commands) land; Phase E's `data-redetect` UI hook is a hard prerequisite for the UI-level assertions below. A manual timing spike was run on the developer's machine to ground the spec's assertion thresholds in real numbers (see De-risking Spike Results); no spike was needed for the caching mechanism itself, since it is a straightforward in-process memoization with no novel risk.

## Goal

The spec must prove the real, shipped code path: a real `detect_machine_specs` / `redetect_machine_specs` Tauri command round trip (`src-tauri/src/lib.rs`), backed by the real `MachineSpecsCache` state and the real `inference::detect_specs`/`redetect_specs` functions (`src-tauri/src/inference/mod.rs`) — which on Windows really shell out to `powershell`/`foundry`/`winget` on a cache miss. It must **not** substitute a Rust unit test of `MachineSpecsCache` in isolation, because a unit test cannot prove the two things a user actually experiences: that the real webview `onMount` round trip in `src/routes/models/+page.svelte` gets measurably faster on a repeat visit, and that the Tauri command registration/state wiring (`.manage(MachineSpecsCache::default())`, the `State<'_, MachineSpecsCache>` parameter, the `spawn_blocking` `Arc` clone) actually connects end to end without a wiring mistake silently no-op'ing the cache. A weaker test that only asserted `detect_machine_specs` returns valid-looking data (as the existing light spec already does) would not catch a regression where the cache is wired but never actually hit — the command would still "work," just always slow.

## Existing Test Styles

Two styles already exist in `e2e/test/specs/`:

- **App-driven WebdriverIO specs** (`e2e/test/specs/{standard,light,heavy}/*.spec.ts`) — drive the real, built Tauri app through `wdio`, using page objects (`e2e/test/pageobjects/*.page.ts`) for UI-level assertions and, in `light`/`heavy` specs, direct `browser.execute(() => window.__TAURI_INTERNALS__.invoke(...))` calls for command-level assertions that don't need a UI round trip. This is the only test style relevant here.
- No standalone-POC style is used for this kind of Tauri-command/UI feature in this repo (that style, if it exists elsewhere, is not applicable to a `/models` page feature).

`e2e/test/specs/light/local-llm-ui.spec.ts` is the direct precedent: it already exercises `detect_machine_specs` for real (not mocked — `MIO_MOCK_BACKEND=1` only swaps `SandboxBackend`/`RuntimeManager`/`SyncEngine`, none of which `detect_machine_specs` touches) under the `light` suite, asserting the specs panel renders real numbers (`local-llm-ui.spec.ts:22-31`). This feature's new spec belongs to the same family.

## Chosen Approach

**Tier: `light`.** This feature has zero interaction with `SandboxBackend`, `RuntimeManager`, or `SyncEngine` — it never touches podman, mise, or Mutagen, and it downloads nothing. Per `e2e/AGENTS.md`'s decision rules, `standard` is proven by testing against real podman/mutagen infrastructure; provisioning the `mio-tests` machine for this feature would add real cost (minutes of machine startup) while exercising zero code path this feature actually changes. The same reasoning already governs the existing local-llm coverage split: `local-llm-ui.spec.ts` classifies the cheap, non-download, non-podman `detect_machine_specs` round trip as `light` even though it calls the exact same real command this feature modifies, and only promotes to `heavy` for the GGUF-download-and-load path (`heavy/local-llm.spec.ts`). This feature never downloads or loads a model, so it never crosses that `heavy` threshold either. `light` still exercises real, unmocked production code — the PowerShell/winget subprocess spawns inside `inference::detect_specs`/`probe_static` run for real under the `light` suite, so the spec has teeth on the actual caching behavior, not a simulated one.

**New spec file**: `e2e/test/specs/light/models-page-caching.spec.ts`, feature-scoped and separate from `local-llm-ui.spec.ts` (mirroring how `activity-center-ui.spec.ts` and `local-llm-ui.spec.ts` are separate light specs rather than one shared file). Topology: single local app instance under `wdio`, `MIO_MOCK_BACKEND=1`, no podman machine, no `MIO_TEST_MODEL` needed (this feature never touches the model catalogue/download path).

No paired `heavy` or `standard` spec is planned. There is no download/load/deploy path in this feature to justify `heavy`, and no podman/mutagen/SSH path to justify `standard` — `light` is not a fallback here, it is the correct and sufficient tier for the feature's entire surface area.

## Harness Changes

None beyond what `local-llm-ui.spec.ts` already proved works: the `light` suite already boots the app with `MIO_MOCK_BACKEND=1` and successfully round-trips `detect_machine_specs` (`e2e/wdio.conf.ts`'s existing `onPrepare`/`beforeSession` wiring for the `light` suite, `e2e/AGENTS.md:73-79`). The only new requirement is a build/staging dependency, not a harness dependency: `02_dev.md` Phase E must add a `data-redetect` attribute to the re-detect button in `src/routes/models/+page.svelte` before `ModelsPage` gains a `redetectButton`/`redetect()` accessor — this spec cannot assert the manual re-detect UI path until that data attribute exists. No new env var, no new suite, no `wdio.conf.ts` edit.

**Page object addition** (not a harness change, a test-code addition): `e2e/test/pageobjects/models.page.ts` gains:

```ts
get redetectButton(): Element {
  return $("[data-redetect]");
}
async redetect(): Promise<void> {
  const btn = await this.redetectButton;
  await btn.waitForClickable({ timeout: 10000 });
  await btn.click();
}
```

## Spec Scenario

All steps run inside one `describe` block against one running app instance, matching `local-llm-ui.spec.ts`'s structure (no `MIO_TEST_MODEL` dependency, no podman).

1. **Baseline: force a full re-probe and time it.** Call `redetect_machine_specs` directly via `browser.execute(() => window.__TAURI_INTERNALS__.invoke("redetect_machine_specs"))`, timed with `Date.now()` immediately before and after the `browser.execute` call resolves. This exercises `inference::redetect_specs` (`inference/mod.rs`, Phase B), which clears `MachineSpecsCache` and re-runs the full `probe_static()` — the real PowerShell/winget spawns. Assert the returned `MachineSpecs` has `cpuCores > 0` and `totalRamBytes > 0` (same shape assertion as the existing light spec), and record the elapsed time as `baselineMs`.
2. **Cache hit: call `detect_machine_specs` again and time it.** Immediately after step 1, call `detect_machine_specs` the same way and time it as `cachedMs`. Assert `cachedMs` is dramatically smaller than `baselineMs` — a relative assertion (e.g. `cachedMs < baselineMs / 3`), not a fixed millisecond threshold, so the spec is robust to slower CI hardware (see De-risking Spike Results for why a relative bound is chosen over an absolute one).
3. **Cache-hit values match the just-probed baseline.** Assert every static field from step 2's response (`cpuCores`, `gpuNames`, `hasNpu`, `arch`, `foundryInstalled`, `foundryInstallable`) deep-equals the corresponding field from step 1's response. This is the assertion with teeth that distinguishes "the cache actually served stored values" from "the probe just happened to return the same numbers twice" — a coincidence that would otherwise mask a cache that's wired but silently bypassed.
4. **Volatile fields are still live.** Assert `totalRamBytes`/`freeRamBytes` are present and `> 0` on both responses (already covered by the shape assertion), documenting — via a comment, not a hard equality assertion — that these are expected to be re-read every call rather than cached, per the resolved decision in `02_dev.md`. (Free RAM may or may not have changed between the two calls on a quiet CI box; the spec must not assert it differs, only that it was read.)
5. **UI round trip: a second page visit resolves fast.** `ModelsPage.open()` once (first visit this test — cache is already warm from steps 1–2, so this does not test a cold UI mount; that is intentional, see the note below), then navigate home and call `ModelsPage.open()` again, timing the second call with `Date.now()` around it. Assert the second `open()` (which internally waits for `[data-specs-ready]`, `models.page.ts:69-78`) resolves within a small absolute bound (e.g. under 1000ms) — this is the user-facing symptom from the original bug report, proven at the UI layer, not just the command layer.
6. **Manual re-detect button drives a real re-probe from the UI.** Call `ModelsPage.redetect()` (the new page-object method) and assert the button enters a busy state (`aria-busy="true"` or `isEnabled() === false` while in flight, matching the `Button` component's existing `loading`/`disabled` contract, `src/lib/components/ui/button/button.svelte:41-42,60`), then assert `[data-specs-ready]` is present again once the click settles (specs re-rendered, not stuck on a stale/blank panel).

Step 5's note: this spec intentionally does not attempt to prove "the very first `/models` visit after a fresh app launch is slow" (Phase B's cache miss on cold start), because forcing a truly cold app launch inside one `wdio` session is either impossible (the app is already running from earlier specs / earlier steps in this same file) or requires an app restart the `light` suite's topology doesn't support today. Steps 1–2 already prove the underlying mechanism (cache miss vs. cache hit timing) at the command level with a guaranteed-cold baseline (via the explicit `redetect_machine_specs` clear); step 5 proves the mechanism also pays off through the real UI `onMount` path once warm. This combination is judged to cover the reported symptom without needing a genuinely cold app boot inside the spec.

## De-risking Spike Results

Spike run on 2026-07-02 on the developer's Windows machine, timing the four subprocess calls `detect_specs`/`probe_static` will shell out to, to ground the spec's timing assertions in real numbers rather than a guessed threshold:

- `Get-CimInstance Win32_VideoController | Select-Object -ExpandProperty Name` (GPU probe): **122ms**.
- `Get-PnpDevice -Status OK ... | Where-Object {...} | Measure-Object` (NPU probe): **638ms**.
- `foundry --version` (Foundry-installed probe): **156ms**.
- `winget show Microsoft.FoundryLocal` (Foundry-installable probe): **393ms**.

Sequential total: **~1.3 seconds**. This confirms two things for the spec design: (1) the baseline (cache-miss) call in step 1 is expected to take on the order of a second or more, comfortably distinguishable from a cache hit, which is a single in-process `sysinfo` memory read expected to complete in low single-digit milliseconds; and (2) a fixed-millisecond assertion (e.g. "cache hit must be under 50ms") is risky across machines with slower PowerShell startup or antivirus-hooked process creation, which is why step 2 uses a relative bound (`cachedMs < baselineMs / 3`) instead. No blocker found — this was a pure timing-characterization spike, not a risk-clearing one, since the caching mechanism itself (an `Arc<Mutex<Option<T>>>` memoization) carries no architectural risk.

## Sequencing

1. Implement `02_dev.md` Phases A–D (the Rust cache, the split probe functions, the `redetect_machine_specs` command) first. Steps 1–4 of the spec scenario can be written and run against this alone, using direct `invoke()` calls with no UI dependency.
2. Implement `02_dev.md` Phase E (the spinner and the `data-redetect` button, including the new `data-redetect` attribute). Steps 5–6 of the spec scenario, and the `ModelsPage.redetectButton`/`redetect()` page-object addition, depend on this phase.
3. Write and land the spec (`e2e/test/specs/light/models-page-caching.spec.ts`) only once both phases are in — a spec written against Phase A–D alone and merged before Phase E would need a follow-up edit to add steps 5–6 rather than being written once.

## Environment Notes

No standing infrastructure is required between sessions — no machine needs to stay provisioned, no sidecar needs to stay staged, no port or socket needs to be reactivated. The spec runs under the existing `light` suite (`pnpm run test:light`), which needs only a built debug app (`pnpm tauri build --debug`, already part of `wdio.conf.ts`'s `onPrepare`) and no podman machine. A future session picking this up needs nothing beyond a normal `pnpm install` + build.

## Common Gotchas

| Gotcha | Cause | Fix |
|---|---|---|
| Step 2's relative timing assertion (`cachedMs < baselineMs / 3`) flakes on a slow CI runner | `baselineMs` itself can be small on a fast machine with a warm PowerShell host process, shrinking the margin between cache-hit and cache-miss timings | Widen the divisor (e.g. `/ 2` instead of `/ 3`) or add an absolute floor (e.g. `baselineMs > 200`) before applying the relative check, so the assertion only fires when there was a meaningful gap to measure |
| Step 3's deep-equal assertion fails even though caching works correctly | `gpuNames` order or exact string formatting from `Get-CimInstance` is not guaranteed stable if Windows re-enumerates GPU devices between the two calls (rare, e.g. a driver reset) | Compare the cached and re-probed values by sorted-array/set equality for `gpuNames` rather than strict array equality, if this proves flaky in practice |
| `[data-redetect]` selector not found | The spec was written or run before `02_dev.md` Phase E landed the button and its data attribute | Confirm Phase E is implemented (`src/routes/models/+page.svelte` has a `data-redetect` element) before running steps 5–6; do not run this spec against a Phase A–D-only build |
| `redetect_machine_specs` invoke rejects with a command-not-found-style error | The command was not registered in the `invoke_handler` list in `src-tauri/src/lib.rs` (`02_dev.md` Phase D) even though `inference::redetect_specs` exists | Check the `tauri::generate_handler!` macro invocation includes `redetect_machine_specs` alongside `detect_machine_specs` |
| Step 5's UI timing assertion is flaky immediately after app launch, before any spec has warmed the cache | If this spec is the very first one to open `/models` in a given app session (spec execution order not guaranteed across the full suite), step 5's "second visit" is still cache-warm from steps 1–2 of this same spec, but a differently-ordered suite run could change which spec pays the first-ever cold cost | Steps 1–2 explicitly force-warm the cache via `redetect_machine_specs` before step 5 runs, so step 5 does not depend on suite ordering — do not remove steps 1–2 or reorder them after step 5 |

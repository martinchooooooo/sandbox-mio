# Network Proxy: Traffic Inspection and Secret Injection

This document covers running a [mitmproxy](https://github.com/mitmproxy/mitmproxy) instance in its own per-sandbox container so every HTTP(S) request a sandbox makes flows through it, giving the app a point to inspect outbound traffic and to inject real credentials into requests that never need the credential material inside the sandbox itself — the model [microsandbox](https://github.com/superradcompany/microsandbox) documents as a host-side network stack gating egress and secret release on verified domain/TLS identity. Nothing of this feature is implemented. It is the first feature in this codebase to intercept a sandbox's *outbound* traffic; everything shipped so far (`docs/features/remote-terminal/01_ideas.md`, `docs/features/host-tool-ssh-access/01_ideas.md`, `docs/features/tailscale-access/01_ideas.md`) tunnels *inbound* connections into a sandbox. The reachability design deliberately avoids the one already-working "container reaches a process outside itself" primitive this codebase has (`forward_create_reverse` in `src-tauri/src/sync/mod.rs`), because that primitive's precondition — a listener bound `0.0.0.0` inside the Podman machine, reachable from every container on it, not just the sandbox it's meant for — is a wider exposure than a security-focused default should accept; see Technology Choices. Relevant existing files: `src-tauri/src/backends/mod.rs` (`create`, `CliBackend`), `src-tauri/src/provider/mod.rs` and `types.rs` (`PodmanProvider::create_instance`, `InstanceSpec`), `src-tauri/src/network/mod.rs` and `types.rs` (`NetworkManager`), `src-tauri/src/sync/mod.rs` (`forward_create_reverse`), `src-tauri/src/credentials/mod.rs` (host-side secret store), and `src-tauri/resources/Containerfile` (the sandbox base image).

## Current State

**Sandboxes reach the open internet unmediated today.** `PodmanProvider::create_instance` (`src-tauri/src/provider/mod.rs`) creates every sandbox with `--network pasta` (plus `--host-lo-to-ns-lo` and `--publish` for a sandbox on the older `PublishModel::PublishRelay` model; the current `ExecTunnelled` model publishes nothing at all — `docs/features/podman-exec-transport/02_dev.md`). Pasta gives each container an isolated, per-container user-mode network stack with outbound NAT to the host's real interface; nothing in the crate configures a proxy, filters egress, or logs any request a sandbox makes. `mise install`, `apt-get`, `git clone`, and any command an agent runs all dial out directly.

**No shared network namespace between containers.** `docs/features/tailscale-access/01_ideas.md`'s Technology Choices already established, when rejecting a Tailscale sidecar, that "pasta networking is per-container user-mode networking, not a shareable namespace in the rootless setup used here." Two sandbox-mio containers cannot reach each other by attaching to one netns; any inter-container path has to go through a real network hop.

**A working "container reaches something outside itself" primitive already exists, in the opposite direction.** `docs/features/local-llm/02_dev.md` (Phase G) needed a sandbox to reach a llama.cpp server bound to the Windows host's own loopback. The solution, `forward_create_reverse` (`src-tauri/src/sync/mod.rs`, line 149), creates a Mutagen forward that listens inside the Podman machine and dials the host. Its doc comment records the load-bearing, spiked (2026-06-29) fact this feature depends on: **a listener bound to the Podman machine's own `127.0.0.1` is unreachable from a container's netns via `host.containers.internal`; only a `0.0.0.0` bind is reachable that way.** `wire_sandbox_to_inference` (also Phase G) is the caller: it creates the reverse forward, then writes `OPENAI_BASE_URL` pointed at `host.containers.internal:<port>` into the sandbox so an agent picks it up. That is close to the exact shape this feature needs, aimed at a different final target (a sibling container's published port instead of a Windows-host process).

**No `env` field exists on the provider-neutral create path.** `InstanceSpec` (`src-tauri/src/provider/types.rs`) carries `name`, `image`, `workspace_source`, `labels`, and `publish_model` — no per-instance environment variables. `--env` flags do not appear anywhere in `PodmanProvider::create_instance`'s argv construction. Every environment value a sandbox process currently sees comes either from the Containerfile's `ENV` directives (`MISE_DATA_DIR`, `MISE_LOCKFILE`, `MISE_YES`, `SHELL`) or from `RuntimeManager::install` writing into `mise.toml`.

**Credential injection today means copying real secret material into the sandbox.** `src-tauri/src/credentials/mod.rs` captures and injects credentials as a `home.tar.gz` snapshot piped into the container over `podman exec -i ... tar`. The real token, cookie, or config file lands on the sandbox's own filesystem, readable by anything running inside it (including the agent being sandboxed against). `docs/features/shared-agent-auth/01_ideas.md` is the design record for that flow.

**No CA trust or TLS interception exists anywhere in the crate.** `src-tauri/resources/Containerfile` installs `ca-certificates` for validating outbound TLS as a normal client, never for trusting a locally generated interception CA.

## Proposed Model

### One mitmproxy container per sandbox, created and destroyed alongside it (new `proxy` subsystem, sibling to `credentials/`)

A sandbox that opts into traffic inspection gets a second container, `<sandbox-name>-proxy`, created immediately after the sandbox container and destroyed alongside it. One proxy per sandbox — not one shared proxy for the whole app — so a compromised sandbox's traffic and a compromised sandbox's proxy-side secrets stay confined to that sandbox's own blast radius (expanded on under Technology Choices). The lifecycle hooks are the same ones `credentials::ensure_auth_container` already establishes as a pattern: create-if-absent, tie removal to the owning sandbox's `destroy`/`undeploy`.

### Base image: the official `mitmproxy/mitmproxy` image plus a mounted addon script, not a custom Containerfile

The proxy container runs the upstream `docker.io/mitmproxy/mitmproxy` image unmodified, started with `mitmdump` (the headless, scriptable variant — no interactive console needed inside a container the user never attaches to) and a `-s <path>` addon script. The addon script — the piece this project owns — is bind-mounted in from a location under `app_data_dir()`, the same way the sandbox workspace itself is bind-mounted, so iterating on injection/logging logic needs no image rebuild.

### Reachability: sandbox dials the proxy over a private, per-sandbox bridge network

The proxy container joins a fresh, per-sandbox rootless bridge network created alongside it (`mio-proxy-<sandbox-name>`, Podman's ordinary `podman network create`, no special privileges needed on either container — network setup happens on the host/rootless-netns side, not inside the container). The sandbox container gets a second `--network` attachment to that same bridge, added alongside its existing `pasta` attachment (Podman's documented mechanism is repeated `--network` flags, one per attachment — see Technology Choices for the comma-separated form's limitation). The sandbox reaches the proxy by its bridge-scoped container name, resolved through Podman's built-in `aardvark-dns`, with no published port, no `host.containers.internal`, and nothing bound to any interface the Podman machine's own loopback or host-facing side ever sees. The proxy's own onward connections (the real request it forwards after inspecting/rewriting) go out through the bridge network's own default outbound NAT — the same mechanism that gives any rootless bridge-networked container internet access — so the proxy container needs no `pasta` attachment of its own. The sandbox's `pasta` attachment is untouched and keeps working exactly as it does today for everything the proxy is not involved in (the exec-transport `podman exec`-tunnelled `sshd`, which does not use the network stack at all).

### Explicit proxy configuration via `InstanceSpec.env`, not shell activation

`InstanceSpec` (`src-tauri/src/provider/types.rs`) gains an `env: Vec<(String, String)>` field, threaded into `PodmanProvider::create_instance`'s argv as `--env` flags, one pair per entry. A proxy-enabled sandbox's `create` call populates `http_proxy`, `https_proxy`, `HTTP_PROXY`, `HTTPS_PROXY` (both cases, since tool proxy-env-var conventions are inconsistent) with the proxy's bridge-network container name and port, and `NO_PROXY`/`no_proxy` covering the sandbox's own loopback. `--env` at `podman create` time is a container-wide setting every process tree sees — interactive shells, `podman exec` sessions, and daemons started with `podman exec -d` alike — unlike the `.bashrc`-only `mise activate` pattern the Containerfile already documents as invisible to non-interactive sessions (the same trap `docs/features/tailscale-access/01_ideas.md`'s Common Gotchas records for mise-managed binaries).

### TLS interception: per-sandbox CA cert generated by the proxy, injected into the sandbox's trust store

`mitmdump` generates its own CA keypair on first run into a state directory (bind-mounted from `app_data_dir()/proxy/<sandbox-name>/`, kept distinct per sandbox for the reason under Technology Choices below). Once the proxy container has started and written its CA cert, the app copies `mitmproxy-ca-cert.pem` into the sandbox with the same `podman exec -i ... tar`-piping transport `credentials::capture`/`tar_inject` already use, running `update-ca-certificates` inside the sandbox afterward so the OS trust store picks it up. This covers curl, git (which consults the system store by default), and any tool that defers to OpenSSL's default trust path; it does **not** cover language runtimes that ship their own bundled trust store (Node.js, Python's `certifi`) — flagged explicitly as an open question rather than silently assumed to work.

### Secret injection: a mitmproxy addon substitutes real values into matched outbound requests

The addon script matches outbound requests by host (and optionally path) against a per-sandbox rule list — e.g., `api.openai.com` → replace the `Authorization` header with a real value — and only then substitutes the credential the sandbox itself never holds. The sandbox is given a placeholder value (or no value at all, if the tool tolerates a missing header until the proxy adds one) instead of the real secret from `src-tauri/src/credentials/`; the real value is written only into the proxy container's own filesystem (e.g., a rules file the app generates at proxy-create time from the host-side credential store), which the sandbox container has no path to read even though both run on the same Podman machine — containers do not share filesystem namespaces by default, and nothing in this design bind-mounts the proxy's rules file into the sandbox. This is additive to, not a replacement for, `credentials/mod.rs`'s existing tar-inject flow: some credentials (an agent's full OAuth-derived config directory, as `shared-agent-auth` captures) are not shaped as a single bearer header, and stay on the injection path that already exists. The proxy-injection path is for the narrower, common shape of "one API token in one header for one host."

## Technology Choices with Tradeoffs

### Interception mechanism: explicit `http_proxy`/`https_proxy` env vars (chosen) vs. transparent `iptables` redirect vs. a proxy process inside the sandbox itself

Chosen: configure the proxy explicitly via environment variables honoured by well-behaved HTTP clients (curl, git, npm, pip, mise's own downloader, most agent CLIs).

- **Transparent interception via `iptables`/`nftables` `OUTPUT` redirection** — rejected: it needs `NET_ADMIN` inside the sandbox to install redirect rules, and `docs/features/tailscale-access/01_ideas.md`'s Technology Choices already rejected granting `NET_ADMIN` to a sandbox on exactly this isolation-weakening ground, for a different feature. Podman also cannot add capabilities to an existing container, so every already-created sandbox would need recreation the day this capability was introduced. The cost of the chosen path is real and stated plainly: any tool that ignores proxy env vars (a raw `TcpStream`/socket client, some Go binaries with custom transports) is invisible to the proxy and bypasses inspection silently.
- **Run mitmproxy as a process inside the sandbox's own container instead of a sidecar** — rejected as the default, though it is the simplest network-wise (no cross-container reachability problem at all, since it is just `localhost`). It fails the isolation goal the separate-container request is explicitly for: a compromised sandbox process can see, kill, or reconfigure a proxy running in its own container, and any credential the addon injects would sit in the same filesystem the compromised process already controls — defeating the entire point of moving secrets out of the sandbox. It also bloats every sandbox image with a Python interpreter and mitmproxy's dependency set, including sandboxes that never enable inspection.

### Proxy placement: one container per sandbox (chosen) vs. one shared proxy container for every sandbox

Chosen: one `<sandbox-name>-proxy` container per sandbox, matching the per-sandbox lifecycle every other resource in this project already follows.

- **A single shared proxy container for the whole app** — rejected: it is a shared trust boundary across sandboxes, which contradicts the product's whole premise. A shared proxy holding every sandbox's secret-injection rules means a bug in the addon's host-matching logic could leak one sandbox's credential into another sandbox's request. It also has no clean way to know *which* sandbox a given inbound connection came from — every sandbox would dial the same `host.containers.internal:<port>`, and mitmproxy sees only the connecting socket, not a sandbox identity — so a shared proxy would need a second disambiguation mechanism (per-sandbox ports on one container, defeating the "shared" premise; or a client-identifying header the sandbox itself would have to add, which a compromised sandbox could forge to impersonate another). Per-sandbox containers make disambiguation free: the container *is* the sandbox's rule set.

### Reachability: a private per-sandbox bridge network (chosen) vs. `0.0.0.0` publish plus `host.containers.internal` vs. reusing `forward_create_reverse` verbatim

Chosen: a fresh bridge network per sandbox, joined only by that sandbox and its own proxy container, as described in Proposed Model. It is the only option of the three that never binds a proxy port to any interface reachable beyond the two containers meant to talk to each other — the sane-default requirement this feature is held to.

- **Publish the proxy's port with a `0.0.0.0` host bind, dialled from the sandbox via `host.containers.internal`** — rejected: it necessarily exposes the proxy's port to every process on the Podman machine, not just the one sandbox that should reach it, because a `0.0.0.0` bind is what `forward_create_reverse`'s doc comment (spiked 2026-06-29) establishes as the *only* bind address `host.containers.internal` can reach — the safer `127.0.0.1` bind this project uses everywhere else (zellij, paseo, the relay pool) is specifically the one that does not work here. For a feature whose entire purpose is tightening what a sandbox can do on the network, widening the proxy's own exposure to buy that is the wrong trade.
- **Reuse `forward_create_reverse` (`src-tauri/src/sync/mod.rs`) unmodified**, relaying through an SSH-tunnelled Mutagen session instead of dialling the proxy directly — rejected on the same exposure ground as the option above, not a lesser version of it: the mechanism's remote-side listener still has to bind `0.0.0.0` inside the Podman machine to be reachable via `host.containers.internal` at all (that is the fact the spike established), so relaying through Mutagen changes *how* the sandbox reaches the exposed port, not *whether* one exists. It would also add an SSH round trip for a hop that never needs to leave the Podman machine.

The cost of the chosen option: a second Podman network resource to create and tear down per proxy-enabled sandbox, and an unconfirmed assumption — that a `pasta`-networked container accepts a second `--network` bridge attachment without disturbing the `--host-lo-to-ns-lo` pasta option zellij/paseo depend on — that needs its own spike before `02_dev.md` commits to it (see Validation and Open Questions). Podman's own documentation confirms repeated `--network` flags are the supported way to attach multiple networks to one container (the comma-separated single-flag form is called out as a backwards-compatibility path that forecloses per-network options), but does not speak to combining `pasta` specifically with a second bridge.

Whichever reachability mechanism is chosen, remote-deployed sandboxes need the proxy container and its bridge network created on the *same* Podman connection the sandbox deploys to — a proxy left on the local machine is on a different bridge network entirely from a sandbox deployed remotely.

### Base image: official `mitmproxy/mitmproxy` plus a mounted addon (chosen) vs. a custom Containerfile built with `pip install mitmproxy` vs. baking mitmproxy into the sandbox's own base image

Chosen: the upstream image, unmodified, with the addon script and CA state directory bind-mounted in.

- **A custom Containerfile, `podman build`-based like `src-tauri/resources/Containerfile`** — rejected: it means tracking mitmproxy's own dependency chain and rebuild cadence for no gain over an image the mitmproxy project already builds, tests, and publishes; the only project-owned logic (the addon script) does not need to live inside the image at all, since mitmdump loads it from a mounted path at every start.
- **Bake mitmproxy into the sandbox's own base image and run it as a background process there** — rejected: this is the "process inside the sandbox" option already rejected above under Interception Mechanism, restated at the image layer; it fails the same isolation goal and would add mitmproxy's footprint to every sandbox, proxy-enabled or not.

### Secret handling: proxy-side injection addon (chosen, additive) vs. continuing the existing tar-inject-into-sandbox model exclusively

Chosen: add proxy-side injection as a second mechanism for the specific shape of "one bearer token/header for one host," leaving `credentials/mod.rs`'s existing capture/inject flow in place for credentials that are not that shape.

- **Replace `credentials/mod.rs` outright** — rejected: `shared-agent-auth`'s captured bundles are full account-state directories (OAuth tokens, onboarding markers, project-trust files an agent CLI reads from disk at multiple points, not just one HTTP header), which a request-rewriting proxy addon cannot reconstruct. The two mechanisms solve different-shaped problems; the proxy path is strictly additive.

### CA trust scope: a CA cert generated per sandbox's own proxy instance (chosen) vs. one CA reused across every sandbox

Chosen: let each proxy container generate (or receive, via its own bind-mounted state directory) its own CA keypair, distinct per sandbox.

- **One app-wide CA cert, reused across every sandbox's proxy** — rejected on the same reasoning `docs/features/host-tool-ssh-access/01_ideas.md` used to reject a single host key baked into the base image: it does concentrate risk (any process able to read one proxy container's CA private key could, in principle, forge certificates trusted by every sandbox that installed the shared CA), for a savings — skipping one `update-ca-certificates` run per sandbox — that is not worth paying for. Per-sandbox CA material also means revoking trust for one sandbox (destroy it) never requires touching any other sandbox's trust store.

## Validation

No spike has been run for this feature specifically. Two pieces of desk research and one reused prior spike inform the design above:

- **microsandbox's own network security model** (`docs/security/network.mdx` in the microsandbox repository, fetched 2026-08-17): confirms the reference architecture is a host-side network stack — not a sidecar container the sandboxed process talks to over a wire — that terminates every packet, enforces deny-by-default egress (public internet plus DNS only; private ranges, loopback, link-local, and the cloud metadata endpoint blocked), and gates both DNS-rebinding protection and *credential release* on the same DNS/SNI verification. This project's design differs deliberately: mitmproxy-in-a-sidecar is a userspace HTTP(S) proxy the sandbox is explicitly configured to use, not a packet-level stack the sandbox cannot observe or opt out of — a smaller, more implementable slice of the same idea, with domain-level allow/deny policy left out of this feature's scope (`04_improvements.md`).
- **mitmproxy's own capabilities** (github.com/mitmproxy/mitmproxy, fetched 2026-08-17): confirmed the project ships `mitmdump` as a headless, scriptable variant suited to unattended container use, and that its addon/scripting API is the documented extension point — consistent with the addon-script design above. The fetch did not surface mode-specific configuration detail (transparent vs. regular vs. upstream mode); this document does not depend on any mode beyond mitmproxy's default explicit/regular proxy mode, which is what `http_proxy`/`https_proxy` env vars drive.
- **Reused from `docs/features/local-llm/02_dev.md` (Phase G), spiked 2026-06-29**: a listener bound `0.0.0.0` inside the Podman machine is reachable from a container's netns via `host.containers.internal`; a `127.0.0.1`-bound listener is not. This is why `host.containers.internal`-based reachability was rejected above rather than adopted — the fact that made it work for the local-llm feature is exactly the fact that makes it too exposed here.
- **Podman's multi-network documentation** (`docs.podman.io`, `podman-run` reference, fetched 2026-08-17): confirms repeated `--network` flags are the supported way to attach a container to more than one network, and that the single-flag comma-separated form is a backwards-compatibility path with reduced per-network options. It does not confirm or deny combining the `pasta` mode specifically with a second bridge network on one container — the gating spike below.

A gating spike this feature needs before `02_dev.md` commits to a phase plan: create a container with both a `pasta` network attachment and a second bridge-network attachment, confirm the `--host-lo-to-ns-lo` pasta option and the exec-transport model still behave unchanged, and confirm two containers on a shared bridge network resolve and reach each other by name with no port published to the Podman machine's own interfaces.

## Open Questions

- **Pasta-plus-bridge coexistence.** Does a `pasta`-networked sandbox accept a second `--network` bridge attachment cleanly, with no regression to the `--host-lo-to-ns-lo` behaviour zellij/paseo depend on or to the exec-transport model? This is the single assumption the chosen reachability design rests on and is unconfirmed — see the gating spike above.
- **Opt-in default.** Is traffic inspection a per-sandbox toggle a user enables explicitly (matching `host-tool-ssh-access`'s leaning toward opt-in for a feature that changes the container's trust/attack surface), or on by default for every sandbox? Opt-in avoids surprising a user with a second container and an installed CA cert they didn't ask for; default-on maximises the secrets-never-touch-the-sandbox benefit but means every sandbox pays the proxy container's overhead.
- **Where secret-injection rules are configured and stored.** A rule binds a credential (from the app-global `src-tauri/src/credentials/` store) to a target host/path and a header. Whether that mapping lives per-workspace (a new `.mio/proxy-rules.json`, mirroring `.mio/ports.json`) or app-globally (alongside `AppSettings`) is undecided, and affects whether rules are portable across a workspace's local/remote lifecycle or tied to one Podman connection.
- **Remote deploy scope.** Does a proxy-enabled sandbox's proxy container and bridge network get created on the same remote Podman connection at `deploy` time, mirroring how `reproduce_remote` chains post-create provisioning today? Left open pending the pasta-plus-bridge spike, since rootless bridge-network behaviour on a non-WSL remote Podman host is a separate, unconfirmed assumption from the local WSL case.
- **Non-HTTP(S) traffic.** Git-over-SSH, raw TCP connections, and any tool that ignores `http_proxy`/`https_proxy` bypass the proxy entirely and go out over pasta's normal NAT path unmediated and uninspected. Is that an acceptable, documented gap for v1 (tools keep working, just unobserved), or does it need to be surfaced to the user as "traffic X was not inspected"?
- **Per-runtime CA trust beyond the OS store.** Node.js and Python's `certifi`-based `requests`/`pip` do not consult the OS trust store by default (`NODE_EXTRA_CA_CERTS`, `REQUESTS_CA_BUNDLE`/`PIP_CERT`, `SSL_CERT_FILE` are the respective escape hatches). Whether this feature configures those env vars for every mise-installed runtime it can detect, or ships with TLS interception working for OS-trust-store-respecting tools only and documents the gap, is undecided.
- **Microsandbox provider support.** This document scopes to the Podman provider only; whether and how a proxy sidecar attaches to a microsandbox sandbox (which has no confirmed bridge-network or `pasta`-equivalent story at all, per `docs/features/microsandbox-provider/01_ideas.md`) is out of scope until that provider's own networking model is further along.

## Common Gotchas

| Gotcha | Cause | Fix |
|---|---|---|
| A sandbox's outbound HTTPS requests fail with a certificate-trust error after inspection is enabled | The proxy's CA cert was injected into the sandbox's OS trust store, but the failing tool (Node.js, Python's `requests`/`pip`) ships its own bundled trust store and never consults the OS one | Set the tool-specific override (`NODE_EXTRA_CA_CERTS`, `REQUESTS_CA_BUNDLE`/`PIP_CERT`, `SSL_CERT_FILE`) alongside `update-ca-certificates`; see Open Questions |
| `http_proxy`/`https_proxy` have no effect inside a `podman exec` session even though they were set for the container | The env vars were set via `.bashrc`/shell activation, which non-interactive `podman exec` sessions never read — the same trap that hit mise-activated tools and is documented in `docs/features/tailscale-access/01_ideas.md`'s Common Gotchas | Set proxy env vars via `--env` on `podman create` (through `InstanceSpec.env`), not shell activation — they then apply container-wide regardless of session type |
| The sandbox cannot reach the proxy container at all (connection refused/timeout, or the proxy's container name does not resolve) | The sandbox was created without its second `--network` attachment to the per-sandbox bridge, or the bridge network was never created before the sandbox, so no shared network segment or `aardvark-dns` entry exists between the two containers | Confirm the proxy's bridge network is created before the sandbox, and that the sandbox's `create`/`create_instance` call includes a second `--network <mio-proxy-net>` attachment alongside `pasta` |
| A sandbox created with a second bridge-network attachment loses reachability on its terminal/agent-web/exec-transport paths | Combining `pasta` with a second `--network` attachment on one container is unconfirmed to work cleanly (Open Questions, gating spike) and may disturb the `--host-lo-to-ns-lo` pasta option or the exec-transport model | Run the gating spike (Validation) before shipping; if the combination proves unsafe, the reachability design needs revisiting rather than falling back to a wider-exposure publish |
| A tool's traffic never shows up in the proxy's log even though the sandbox is proxy-enabled | The tool ignores `http_proxy`/`https_proxy` (a raw socket client, some Go binaries) or uses a non-HTTP(S) protocol (git-over-SSH) | Expected and documented, not a bug — see Open Questions, "Non-HTTP(S) traffic"; transparent interception was deliberately rejected (Technology Choices) because it requires `NET_ADMIN` |
| A secret meant to be injected by the proxy appears verbatim inside the sandbox's own environment or files anyway | The credential is still also flowing through `credentials/mod.rs`'s tar-inject path (e.g., an agent's captured OAuth bundle) because it is not the "one header for one host" shape the proxy addon substitutes | Confirm which mechanism owns a given credential; proxy injection is additive, not a replacement, for credentials shaped as multi-file account state (Technology Choices) |
| A destroyed sandbox leaves an orphaned `<sandbox-name>-proxy` container behind | Proxy container teardown was not chained into the sandbox's `destroy`/`undeploy` path | Tie proxy-container removal to the same command that removes the sandbox, mirroring how `credentials::ensure_auth_container`'s throwaway container is scoped to one capture operation |

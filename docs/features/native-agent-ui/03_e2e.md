# Native Agent UI E2E

This document is the end-to-end test plan for the native agent chat built in `docs/features/native-agent-ui/02_dev.md` (Phases A to F implemented, Phase G translations pending). The plan covers one `light` spec and one `standard` spec that are written and passing (`e2e/test/specs/light/agent-chat-ui.spec.ts`, `e2e/test/specs/standard/agent-chat.spec.ts`), one optional `standard` spec and one `heavy` spec that are planned but not written, four manual procedures for the Phase B writer-lock checks, and the Rust unit tests that already exist. S1 automates the Phase B hand verification on Podman since 2026-11-13; microsandbox remains unverified (De-risking Spike Results).

## Goal

The real code path the tests must prove, from the Manage dashboard's Chat launcher to pi and back:

- **Opening the pane:** the launcher button `data-app="agentchat"` in `src/lib/workspace/DashboardOverview.svelte` (offered only when pi is installed, `LAUNCHABLE_APPS` in `src/lib/workspace/apps.ts`) → the `open_agent_chat` command (`src-tauri/src/commands/panes.rs`) → `open_native_pane` (`src-tauri/src/workspace/mod.rs`) → `ChatView` rendered in the main webview by `src/lib/workspace/WorkspaceContent.svelte`.
- **Attaching:** the chat store (`src/lib/agent-chat/chat.svelte.ts`) → `agent_chat_attach` (`src-tauri/src/commands/agent_chat.rs`) → `SandboxRouter::locate` and `SandboxRouter::is_local` (`src-tauri/src/services/routing.rs`) → `ExecAgentHost::ensure` (`src-tauri/src/agent_host/mod.rs`), which installs the embedded `pi-host.sh` and `pi-attach.sh` (`src-tauri/resources/agent-host/`) into `/usr/local/lib/mio/` through `MachineProvider::exec_piped` and starts `pi --mode rpc` under the supervisor → `ExecAgentHost::attach`, one `podman exec -i` or `msb exec --stream` child through `MachineProvider::exec_command` (`src-tauri/src/provider/types.rs`) → the reader task's framed records on the Tauri `Channel` → `applyPiRecord` in `src/lib/agent-chat/pi-events.ts`.
- **Writing:** `agent_chat_send` → the attach child's stdin → `pi-attach.sh` (`tee -a input.jsonl` into the named pipe) → pi, with responses correlated by `id` in the store.
- **Control:** `agent_chat_takeover` (`pi-host.sh takeover`), `agent_chat_stop` (`pi-host.sh stop`), `agent_chat_sessions` (`list_sessions` in `src-tauri/src/agent_host/sessions.rs`, reading the host workspace) and `agent_chat_detach` through `teardown_forwards` on tab close.
- **Bundled components exercised:** the pinned pi (`pi@1.5.0`, `PI_PINNED_VERSION` in `src/lib/agents/pi.ts`) installed through the existing agent install, the base image's `flock`, `setsid` and `procps`, and for the heavy spec the bundled `llama-server` reached through the inference forward.

A weaker test fails to cover the following:

- **The `light` tier proves no sandbox behaviour.** Under `MIO_MOCK_BACKEND=1`, `default_agent_host()` builds `MockAgentHost` (`src-tauri/src/agent_host/mock.rs`), which replays recorded traces in-process. No script is installed, no supervisor starts, no `flock` is taken, no exec child is spawned, and `attach` always reports `writer: true`. The light spec proves the commands' IPC shapes, the router's deployed check, the store, the adapter and the rendering only.
- **The Rust unit tests prove parsing only.** `cargo test agent_host` (12 tests in `src-tauri/src/agent_host/framing.rs`, `dialogs.rs`, `sessions.rs` and the `SCRIPT_VERSION` check) covers byte-exact framing and reattach contiguity over the spike's `02a`/`02b` traces, pending-dialog derivation over the `04b`–`04f` traces and session-file parsing. The unit tests never run a shell script or a pi process; the e2e plan references the unit tests and does not duplicate them.
- **The spike traces predate the productionised scripts.** Spike 01 drove the hand-written spike scripts over an SSH alias; the shipped scripts use the engine exec, a writer lock, a start lock, an input log and an install step that only S1 executes against a real sandbox.

## Chosen Approach

| Id | Tier | Spec path | Status | Topology | Proves |
|---|---|---|---|---|---|
| L1 | `light` | `e2e/test/specs/light/agent-chat-ui.spec.ts` | Written, passing | Mock backend, `MockAgentHost` replay | Store, adapter, rendering, dialogs, sessions UI, stop/start, reload re-seeding, deployed state |
| S1 | `standard` | `e2e/test/specs/standard/agent-chat.spec.ts` | Written, passing | One Podman sandbox on `mio-tests`, pi installed, no model | Script install, supervisor, attach, writer lock, takeover, dialogs, stop, sessions on disk, inference-down state |
| S2 | `standard` | `e2e/test/specs/standard/agent-chat-msb.spec.ts` | Planned, optional | One microsandbox sandbox (`MIO_MACHINE_PROVIDER=msb`), pi installed, no model | The same supervisor and lock over `msb exec --stream` |
| H1 | `heavy` | `e2e/test/specs/heavy/agent-chat-model.spec.ts` | Planned | One Podman sandbox plus the `MIO_TEST_MODEL` GGUF served by `llama-server` | A real prompt round trip, usage and the context meter |
| U | Rust unit | `src-tauri/src/agent_host/*.rs` | Existing (12 tests) | None | Framing offsets, pending dialogs, session parsing |
| M1–M4 | Manual | Manual Procedures below | M1–M3 covered by S1 on Podman; microsandbox and M4 not executed | Real sandboxes on both engines | Phase B hand verification |

- **Why S1 is the primary spec and needs no model.** The supervisor, the writer lock and the dialog flow do not depend on inference: a pi extension command raises a dialog without calling the model, as Spike 01's `spikeconfirm` did. Keeping the model out of S1 keeps S1 at the `standard` tier (decision rule 2 in `e2e/AGENTS.md` sends any real model load to `heavy`). The chat adds no host-global resource (`02_dev.md`, Parallel-worktree constraints), but S1 still takes the host lock because the `standard` tier provisions `mio-tests`; that serialisation is the intended cost of real coverage.
- **Why L1 exists.** L1 is the fast debug loop for the store and adapter, and it reaches the deployed state, which needs a Mutagen session on a remote host that S1 does not create.
- **Why H1 is separate.** A real prompt loads a model into `llama-server`, which is `heavy` by decision rule 2. H1 reuses the download and start path of `e2e/test/specs/heavy/opencode-forward.spec.ts`.

### Harness and environment prerequisites

- `e2e/test/pageobjects/agent-chat.page.ts` (written with L1) holds every chat selector; S1, S2 and H1 reuse it.
- `e2e/lib/workspace.ts` already carries `"agentchat"` in `AppKind` and nullable `AppPane.forward_name` and `AppPane.url` (Resolved Decision 14), so S1 can use `workspaceState()` and `paneFor()` directly. L1 calls `invokeCmd` and does not use them.
- `e2e/test/pageobjects/workspace-dashboard.page.ts`: `launcherButton` and `launchApp` accept `"agentchat"`, and `launcherButton` is scoped under the dashboard's `[data-dashboard]` root.
- A pi extension fixture, `e2e/fixtures/pi-extensions/spikeconfirm.ts`, copied from `docs/features/native-agent-ui/spike/spike-confirm.ts`. S1 writes the fixture into `<workspace>/.mio/pi-agent/extensions/` before the first attach; Spike 01 showed pi loads extensions from `PI_CODING_AGENT_DIR/extensions/` without a trust prompt.
- A spec-side second client: S1 spawns `podman --connection mio-tests exec -i <name> sh /usr/local/lib/mio/pi-attach.sh - end` with Node's `spawn`, keeps its stdin open, and reads its first stdout line as the `mio_attach` header. S2 spawns `MSB_PATH exec --stream <name> -- sh /usr/local/lib/mio/pi-attach.sh - end` (`e2e/lib/run-identity.ts`). The spec kills the child in `after()`, because `killStaleDevProcesses` in `e2e/wdio.conf.ts` matches only processes under the worktree's `target\debug\` directory.
- `AGENT_SETTLE` in `e2e/lib/timeouts.ts` budgets pi settling a run whose model request fails, which takes three automatic retries.
- Run S1 alone with `cd e2e && pnpm exec wdio run wdio.conf.ts --spec ./test/specs/standard/agent-chat.spec.ts`; one run takes about two minutes after the build.
- Host paths: every workspace path comes from `SANDBOX_WORKSPACE_ROOT` or `WORKSPACE_ROOT` (`e2e/lib/run-identity.ts`). The chat writes no host path outside the workspace, so no absence assertion is needed.
- No `e2e/wdio.conf.ts` change: `msb` was already added to `killStaleDevProcesses` in Phase C, and `MIO_TEST_MODEL` is already exported.

## Spec Scenario: L1 `agent-chat-ui.spec.ts` (light, written)

One sandbox name per run, `e2e-chat-<timestamp>`, whose workspace path is `WORKSPACE_ROOT/<name>`. `SandboxRouter::locate` treats a sandbox the backend does not list as a local Podman one, so no sandbox row is created. `useMockControl()` and `captureDiagOnFailure()` are registered at `describe` scope.

1. **Attach.** `invokeCmd("open_agent_chat", { name, workspacePath })`; wait for `[data-agent-chat=<name>]` with `data-connection="attached"`. Assert `data-writer="true"`, `data-run="idle"`, `[data-chat-empty]` displayed, `[data-chat-model]` equal to `qwen3.5-2b` (from the mock's `get_state`) and `[data-chat-thinking]` equal to `off` (the mock's models are reasoning models).
2. **Round trip.** Type into `[data-chat-input]`, click `[data-chat-send]`; wait for `[data-role=user]`, then `[data-role=assistant]`, then `data-run="idle"`. Assert the last assistant text contains "named pipe" (fixture `01-roundtrip`, not a UI string), a `[data-part=reasoning]` exists and `[data-chat-context]` equals `5` (usage 1,599 of the 32,768 window).
3. **Dialog.** Send `/spikeconfirm`; wait for `[data-dialog=confirm]` carrying a `data-dialog-id`; click its `[data-dialog-yes]`; wait until no `[data-dialog]` remains and a `[data-sonner-toast]` is displayed (the `notify` from fixture `04d-answer`).
4. **Reload re-seeding.** Send `/spikeconfirm` again, wait for the dialog, then `browser.refresh()`. The reload drops the module-scoped store, so the dialog that reappears after `data-connection="attached"` can only come from `HostStatus.pendingDialogs` (Resolved Decision 3). Assert at least one `[data-role=assistant]` (history rebuilt from `get_messages`), answer the dialog, and wait until no `[data-dialog]` remains.
5. **Model switch.** Open `[data-chat-model]`, click `[data-model-option=qwen3.5-4b]`; wait for `[data-chat-model=qwen3.5-4b]` (`set_model` then `get_state`).
6. **Sessions.** Write a session file with a `session` header and one user and one assistant message to `WORKSPACE_ROOT/<name>/.mio/pi-agent/chat-sessions/--root-work--/<id>.jsonl`; open `[data-chat-sessions]` and wait for `[data-session-id=<id>]` (the real `list_sessions` reading the host workspace). Click `[data-chat-new-session]`; wait for `[data-chat-empty]` and assert no `[data-role=assistant]`.
7. **Stop and start.** Open `[data-chat-menu]`, click `[data-chat-stop-agent]`; wait for `data-connection="stopped"` and `[data-chat-stopped]`. Click `[data-chat-start-agent]`; wait for `data-connection="attached"` and `[data-chat-empty]` (the mock's next `ensure` is a new generation, so the store rebuilds from an empty history).
8. **Deployed.** For a second name, script `mutagen.sync-list` with a session named after the sandbox whose `beta.host` is `remote-box`; `open_agent_chat`; wait for `data-connection="deployed"` and `[data-chat-deployed]`. The real `resolve_machine` in `src-tauri/src/services/routing.rs` maps the scripted session to a non-local `MachineRef`, `agent_chat_attach` returns kind `AgentChatDeployed`, and no mock extension is needed. Close the pane with `close_pane`.

`after()` closes the first pane with `close_pane` and kind `agentchat`.

## Spec Scenario: S1 `agent-chat.spec.ts` (standard, written)

Mirrors `e2e/test/specs/standard/agent-web.spec.ts`: `useSandboxWorkspace("e2e-agentchat")`, `captureDiagOnFailure()`, `this.timeout(900000)`. Every `it` builds on the previous one, so a failure stops the chain. No model is started.

1. **Create, start, install pi.** `ProjectsPage.createProject`, `row.start()`, `row.openWorkspace()`; assert the Chat launcher is absent; `workspaceDashboard.startAgentInstall("Pi")`, `waitForAgentRow("Pi", AGENT_INSTALL)`. Assert `podman exec -w /root/work <name> mise exec -- pi --version` prints `1.5.0`, which proves the catalogue pin from Phase A. Wait until `models.json` exists and `mise.toml` names `PI_CODING_AGENT_DIR`, because provisioning finishes after the agent row appears.
2. **Seed the dialog extension.** Write `e2e/fixtures/pi-extensions/spikeconfirm.ts` to `<workspaceDir>/.mio/pi-agent/extensions/spikeconfirm.ts`.
3. **Launcher gating.** Assert `button[data-app=agentchat]` is displayed in Manage now that pi is installed; click it through `workspaceDashboard.launchApp("agentchat")`. Assert `workspaceState()` holds an `agentchat` pane for the sandbox with null `forward_name` and `url`, and that the pane is active.
4. **Script install and supervisor start.** Wait for `data-connection="attached"` (budget `SUBPROCESS`) and `data-writer="true"`. Read back through `podman exec`: `/usr/local/lib/mio/pi-host.sh` and `pi-attach.sh` exist with LF line endings; `/run/mio/pi-host/` holds `in.fifo`, `journal.jsonl`, `input.jsonl`, `generation`, `pi.pid` and `keeper.pid`; `/proc/<pi.pid>/cmdline` contains `--mode rpc` and `--session-dir`. Assert `[data-chat-model]` is non-empty (provisioned `models.json`).
5. **Second client is a reader.** Spawn the spec-side attach (Harness prerequisites); assert its header reports `"writer":false`, because the app holds the lock.
6. **Dialog through the real pipe.** Send `/spikeconfirm`; wait for `[data-dialog=confirm]`; read `/run/mio/pi-host/journal.jsonl` and assert it holds an `extension_ui_request` with the same `data-dialog-id`, and that the spec-side reader received the request too. Click `[data-dialog-no]`; wait until no `[data-dialog]` remains and a toast appears; assert `input.jsonl` holds the matching `extension_ui_response` with `confirmed: false`, and that the journal holds the extension's `notify` request carrying the answer, which proves the answer reached pi.
7. **Close the tab detaches without stopping pi.** Kill the spec-side reader first, so the reader cannot hold an attach open. Click `[data-close-tab=agentchat]`; wait until no `pi-attach.sh` process remains in `ps`; assert `flock -n writer.lock true` succeeds inside the sandbox, and that pi's pid is unchanged and alive.
8. **Reader-first ordering and Take control.** Spawn the spec-side attach again before reopening the chat; assert its header reports `"writer":true`. Reopen the chat through the Manage launcher; wait for `data-connection="attached"`, `data-writer="false"` and `[data-chat-readonly]`; assert `[data-chat-input]` is disabled. Click `[data-chat-take-control]`; wait for `data-writer="true"` and no `[data-chat-readonly]`; assert the spec-side child's stdout ended, which proves `pi-host.sh takeover` killed the live writer.
9. **Inference not running.** Send a plain prompt with no model served; wait for `[data-chat-inference-down]` (budget `AGENT_SETTLE`, since pi retries three times), then `data-run="idle"`; assert an `[data-notice=error]` part exists and the journal holds an assistant `message_end` with `stopReason: "error"`. pi 1.5.0 answers the `prompt` itself with `success: true`, so no toast is involved (De-risking Spike Results).
10. **Sessions on disk.** Assert a `*.jsonl` file exists under `<workspaceDir>/.mio/pi-agent/chat-sessions/`; open `[data-chat-sessions]` and assert a listed `[data-session-id]` matches the id in a file's `session` header. Assert no file under `<workspaceDir>/.mio/pi-agent/sessions/` was modified during the run (Resolved Decision 8; a modified-during-run assertion, not an absence assertion).
11. **Stop agent.** `[data-chat-menu]` then `[data-chat-stop-agent]`; wait for `[data-chat-stopped]`; assert no `--mode rpc` process and no `pi-attach.sh` remain in `ps`, and the pid in `keeper.pid` is dead. Click `[data-chat-start-agent]`; wait for `attached`; assert `/run/mio/pi-host/generation` changed.
12. **Sandbox restart.** Stop the sandbox through the row; the open chat reaches `data-connection="disconnected"` with `[data-chat-disconnected]`, because a sandbox stop keeps the pane. Start the sandbox; assert the old `pi.pid` file survived in `/run`; click `[data-chat-reconnect]`; wait for `attached` as the writer and assert a new generation whose `pi.pid` runs `--mode rpc`, which proves the `/proc/<pid>/cmdline` liveness check rejected the stale pid.

## Spec Scenario: S2 `agent-chat-msb.spec.ts` (standard, planned, optional)

## Spec Scenario: H1 `agent-chat-model.spec.ts` (heavy, planned)

1. Download and start the `MIO_TEST_MODEL` GGUF through the Models page (`e2e/test/pageobjects/models.page.ts`), as `e2e/test/specs/heavy/opencode-forward.spec.ts` does.

## Manual Procedures (Phase B hand verification)

Run each procedure on one Podman sandbox and one microsandbox sandbox, each with pi installed and the chat opened once (so the scripts are installed). `<exec>` is `podman --connection <connection> exec -i <name>` or `msb exec --stream <name> --`. Record the date, engine and outcome in this section when run.

| Id | Procedure | Expected |
|---|---|---|
| M1 | Open two terminals; in each run `<exec> sh /usr/local/lib/mio/pi-attach.sh - end` | The first header reports `"writer":true`, the second `"writer":false`; `/run/mio/pi-host/writer.pid` holds the first shell's pid |
| M2 | With M1 running, kill the first terminal's host-side exec client (close the terminal or `Stop-Process`); then run a third attach | The third header reports `"writer":true` within a few seconds; no `tail`, `tee` or `cat` of the first attach remains in `ps` |
| M3 | With a live writer attach, run `<exec> sh /usr/local/lib/mio/pi-host.sh takeover`, then a new attach | `takeover` returns only once the lock is free; the writer's stream ends; the new attach reports `"writer":true` |
| M4 | In the app, close the chat tab and reopen it within one second, ten times | Every reopen reports `data-writer="true"`; a `false` means the replaced attach's shell held the lock longer than the two-second `flock -w 2` in `pi-attach.sh` |

M1 to M3 are the Phase B checks in `02_dev.md`. S1 steps 5, 7 and 8 automate M1 and M3 on Podman, and step 7 also covers M2's lock release after a killed exec client, with no stray `pi-attach.sh` left in `ps`.

- **2026-11-13, Podman (`mio-tests`):** M1–M3 passed through S1. Equivalent outcomes: a second attach reported `"writer":false` while the app held the lock (M1). After the host-side reader was killed and the tab closed, no `pi-attach.sh` process remained, the lock was free, and the next attach reported `"writer":true` (M2). Take control ended the spec-side writer's stream and made the app the writer (M3).
- **Microsandbox:** not executed; S2 is not written.
- **M4:** not executed on either engine and has no automated equivalent.

## Proposed Mock Seams (not built)

Recorded in `docs/features/native-agent-ui/04_improvements.md` under "Mock agent host knobs". None is needed for L1 as written.

- **Writer and takeover knob.** A mock-only command, guarded like `mock_configure` in `src-tauri/src/mockctl/mod.rs`, that makes `MockAgentHost::attach` report `writer: false` until `takeover` runs. Lets a light spec cover `[data-chat-readonly]`, the disabled composer and Take control.
- **pi version knob.** The same command sets the `pi_version` `ensure` reports, so a light spec reaches `[data-chat-outdated]`. Update pi itself calls `install_agent`, which the mock runtime answers.
- **Error and rich-event fixtures.** A second trigger word (alongside `/spikeconfirm`) that replays a run ending in `stopReason: "error"` (for `[data-chat-inference-down]`, with `inference_status` reporting no server), and a recorded trace with tool calls, `queue_update`, `compaction_*` and `auto_retry_*` records (for `[data-tool]`, `[data-chat-queue]` and `[data-notice]`). The rich trace must be recorded from real pi 1.5.0 with a tool-capable model; H1's infrastructure can capture the trace.
- **Mid-stream detach.** A knob that sends `mio_detached` during a replay, so a light spec sees the reconnect path. Of limited value while `ChatView` reattaches on its own (Implementation Observations).

## Implementation Observations

Points where the implementation reads differently from `02_dev.md` or the selector contract. None blocks L1.

- **Resolved after review: the Reconnect banner now persists.** `ChatView.svelte` attaches once per mount, so `[data-chat-disconnected]` and Reconnect stay up after a stream ends while the chat is open; a remount (reopening the tab, a reload) still attaches on its own.
- **Resolved after review: the writer-lock race on a replaced attach.** `pi-attach.sh` (script version 2) waits up to two seconds for the lock instead of trying once, which covers the old shell exiting a moment after its client is killed; a genuine second reader now takes two seconds longer to attach. M4 confirms it on real engines.
- **Mock dialog answers ignore the answer value.** `MockAgentHost` replays `04d-answer` (notify "spikeconfirm answered: true") for Yes, No and Dismiss alike, and every `/spikeconfirm` reuses the fixture's dialog id. A light spec must not assert the answer text, and must answer one dialog before raising the next.
- **Mock `detach` sends `mio_detached` explicitly,** while `ExecAgentHost::detach` relies on the reader task noticing the stream end. Both reach the store as `mio_detached`.
- **Resolved after review: selector gaps.** The six unattributed actions now carry data attributes (Selector Contract).
- **Resolved after review: `e2e/lib/workspace.ts`** now types `AppPane.forward_name` and `url` as nullable and includes `agentchat` in `AppKind` (Resolved Decision 14).

## Common Gotchas

| Gotcha | Cause | Fix |
|---|---|---|
| A light spec fails before any test with "Origin header is not a valid URL" or "[e2e] no loaded app webview found among the window handles" | A pre-existing WebDriver/WebView2 harness flake that reproduces on a clean worktree at HEAD, unrelated to the chat | Rerun the spec; do not add waits or retries to `e2e/test/specs/light/agent-chat-ui.spec.ts` for the flake |
| Clicking `[data-chat-send]` hits the activity bell instead | The activity-center toggle `[data-activity-toggle]` is fixed in the window's bottom-right corner and overlapped the Send button | Keep the composer's right gutter in `src/lib/agent-chat/ChatView.svelte`; wait for `waitForClickable` on `[data-chat-send]` as `e2e/test/pageobjects/agent-chat.page.ts` does |
| A spec selecting chat elements by visible text breaks after Phase G | The chat's strings are `TODO(i18n)` literals that Phase G moves into Paraglide, and German and Russian runs render other text | Select only by the `data-*` attributes in the Selector Contract section of `docs/features/native-agent-ui/03_e2e.md` |
| A spec waits for `[data-chat-disconnected]` after closing and reopening the chat tab, and times out | Reopening remounts `ChatView.svelte`, which attaches on mount, so the banner shows only for a stream that ends while the chat stays open | Assert the reattached outcome (`data-connection="attached"`, `data-writer`) after a remount; expect the banner only when the stream ends under an open chat |
| A light spec asserting "answered: false" after clicking No fails | `MockAgentHost` in `src-tauri/src/agent_host/mock.rs` replays the same `04d-answer` fixture for every answer | Assert only that the dialog disappears and a `[data-sonner-toast]` appears; assert the answer value in the standard spec through `input.jsonl` |
| A second `/spikeconfirm` in a light spec shows two dialogs or none | Every `/spikeconfirm` replays the same `04b-dialog` record, so both dialogs share one id | Answer one dialog before sending the next `/spikeconfirm` |
| `button[data-app="agentchat"]` clicks the switcher tab instead of the Manage launcher | The Manage launcher (`DashboardOverview.svelte`) and the switcher tab (`SandboxSwitcherGroup.svelte`) share the `data-app` value | Use `workspaceDashboard.launcherButton("agentchat")`, which is scoped under `[data-dashboard]`, and `chat.closeTabButton(sandbox)`, which is scoped under the switcher's `div[data-sandbox]` |
| The Chat launcher never appears in Manage | `LAUNCHABLE_APPS` in `src/lib/workspace/apps.ts` offers `agentchat` only when the installed agents include pi | Install pi through `workspaceDashboard.startAgentInstall("Pi")` before looking for the launcher; L1 bypasses the launcher with `invokeCmd("open_agent_chat")` |
| The standard spec's `/spikeconfirm` is answered by pi as an unknown command | The `spikeconfirm` extension is not in the workspace's `.mio/pi-agent/extensions/`, or was written after pi started | Write `e2e/fixtures/pi-extensions/spikeconfirm.ts` into `<workspaceDir>/.mio/pi-agent/extensions/` before the first attach, or use Stop agent and Start agent to reload pi |
| A spec-spawned `podman exec` or `msb exec` attach outlives the run | `killStaleDevProcesses` in `e2e/wdio.conf.ts` kills only processes under the worktree's `target\debug\` directory, and the spec's child runs from `PATH` or `src-tauri/binaries/msb/` | Kill the spawned child in the spec's `after()` hook |
| The spec-side attach reports `"writer":true` when the app was expected to hold the lock | The app's chat was not attached yet, or a close-and-reopen released the app's lock | Wait for `data-connection="attached"` with `data-writer="true"` before spawning the spec-side attach |
| `[data-chat-thinking]` is missing in the standard or heavy spec | The thinking control renders only when the current model has `reasoning: true`, which comes from the catalogue entry in `src/lib/models/catalogue.ts` | Assert `[data-chat-thinking]` only for a catalogue model with `reasoning`; the `MIO_TEST_MODEL` GGUF is not one |
| A wait for `[data-chat-inference-down]` times out at `SUBPROCESS`, or a wait for `data-run="idle"` passes before the run has even started | pi 1.5.0 retries a refused model connection three times (2, 4 and 8 s) before `agent_settled`, and `data-run` is still idle right after Send | Wait for the banner itself with `AGENT_SETTLE` (`e2e/lib/timeouts.ts`), then for idle |
| The standard spec's chat shows no model, or `/spikeconfirm` is unknown, though pi installed | The agent row appears before provisioning writes `models.json` and the `PI_CODING_AGENT_DIR` entry in `mise.toml`, and pi reads both only at start | Wait for both files before the first attach, as S1 step 1 does |
| After a sandbox stop the spec waits for the chat pane to close, or reopens the chat through the launcher | Stopping a sandbox keeps its panes; only the chat's stream ends | Expect `data-connection="disconnected"` and click `[data-chat-reconnect]` after the start, as S1 step 12 does |
| A light spec's session file never shows in `[data-chat-sessions]` | `list_sessions` (`src-tauri/src/agent_host/sessions.rs`) skips a file whose first line is not a `session` header with an `id`, and reads only under `.mio/pi-agent/chat-sessions/` | Write the header first and place the file under `WORKSPACE_ROOT/<name>/.mio/pi-agent/chat-sessions/` |

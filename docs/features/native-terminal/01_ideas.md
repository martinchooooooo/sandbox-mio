# Native Terminal Ideas

This document is the ideation for making a sandbox's Terminal tab open faster by replacing the `zellij web` child webview with a terminal rendered inside the app's main webview, fed by an SSH session the Rust backend owns and attached to the sandbox's existing zellij session. The terminal today is the web-terminal feature (`docs/features/web-terminal/`): a separate WebView2 child webview loading the zellij web client through a Mutagen forward, authenticated by a one-time token. Nothing in this document is built. The relevant code lives in `src-tauri/src/services/panes.rs` (pane preparation), `src-tauri/src/runtime/mod.rs` (`prepare_terminal`), `src-tauri/src/commands/panes.rs` (`open_terminal_pane`), `src-tauri/src/workspace/` (the pane registry), `src-tauri/src/provider/` (the engines' `exec`), `src-tauri/src/backends/mod.rs` (the SSH alias transport) and `src/lib/workspace/apps.ts` (the launchable-app catalogue).

## Current State

Opening a Terminal tab runs the following steps in sequence, every time a Terminal pane is first opened for a sandbox:

1. `open_terminal_pane` in `src-tauri/src/commands/panes.rs` calls `prepare_terminal_webview` in `src-tauri/src/services/panes.rs`.
2. `SandboxRouter::resolve` in `src-tauri/src/services/routing.rs` resolves the sandbox and rewrites its SSH alias under the cross-process lock in `src-tauri/src/ssh/mod.rs`.
3. `RuntimeManager::prepare_terminal` in `src-tauri/src/runtime/mod.rs` runs `provider.start`, then `zellij web --status`, then `zellij web --daemonize` when the server is offline, then `zellij web --create-token`. Each step is a separate engine `exec`; on Windows a `podman exec` crosses the remote client into the WSL machine.
4. `NetworkManager::open_forward` (`src-tauri/src/network/`) creates a Mutagen forward from a fresh host loopback port to the in-sandbox web-client port, through the sandbox's alias, whose `ProxyCommand` is one more engine `exec` of `mio-sshd` (`ensure_sandbox_alias` in `src-tauri/src/backends/mod.rs`).
5. `embed_terminal` in `src-tauri/src/workspace/mod.rs` creates a child webview at the loopback URL `http://127.0.0.1:<port>/<sandbox-name>`.
6. The webview loads the zellij web client, then the init script built in `prepare_terminal_webview` posts the token to `/command/login` and calls `location.replace`, which loads the page a second time.
7. The zellij web client (xterm.js) opens its websocket and attaches to the zellij session named after the sandbox.

No timing of the chain exists yet; the stage that dominates is unmeasured (see Validation).

Seams the feature builds on:

- **A pane rendered by the main webview already exists.** `AppKind::AgentChat` in `src-tauri/src/workspace/types.rs` is a registry pane with no child webview and no forward, introduced by the in-progress native-agent-ui feature (`docs/features/native-agent-ui/01_ideas.md`).
- **Streaming a long-lived child to the frontend has a precedent.** `CliBackend::listen_events` in `src-tauri/src/backends/mod.rs` streams a child's output over a Tauri `Channel` and gates itself on `mock_backend_enabled()`. The native-agent-ui ideation applies the same shape to an `ssh <alias>` attach.
- **An unspawned engine `exec` command is available for live streaming.** `exec_command` on the provider trait (`src-tauri/src/provider/types.rs`) returns a configured `tokio::process::Command` the caller spawns with its own piped stdio. Podman builds `podman --connection <c> exec -i <name> …` and microsandbox builds `msb exec --stream <name> -- …`.
- **Every sandbox runs the same SSH server.** The base image's `mio-sshd` (`src-tauri/resources/Containerfile`) is the alias transport for both engines and for deployed sandboxes, whose alias names the remote connection. The per-sandbox ed25519 key and known-hosts file are generated by `ensure_sandbox_alias` in `src-tauri/src/backends/mod.rs`.
- **zellij is baked into the base image**, pinned by `ZELLIJ_VERSION` in `src-tauri/resources/Containerfile`, so `zellij attach` is available in every sandbox without the web server.

## Terminal Session Host

A new Rust subsystem, `src-tauri/src/terminal/` (trait in `types.rs`, real implementation in `mod.rs`, mock in `mock.rs`, following `src-tauri/AGENTS.md`), owns one interactive session per open Terminal pane.

- **Attach** resolves the sandbox through `SandboxRouter::resolve`, starts the container through the provider, spawns the provider's `exec_command` for `mio-sshd` with piped stdio, and runs an in-process SSH client over that child's stdin and stdout.
- The SSH client authenticates with the sandbox's existing identity file, verifies the host key against the sandbox's known-hosts file, requests a pseudo-terminal at the pane's size, and execs `zellij attach --create <sandbox-name>`.
- Output bytes are forwarded unparsed to the frontend over a Tauri `Channel`. Input bytes and resizes arrive through Tauri commands; a resize becomes an SSH `window-change` request.
- **Detach** ends the SSH session and the `exec` child only. The zellij session keeps running inside the sandbox, as it does today when a web pane closes.
- The session host replaces steps 3 to 7 of the Current State chain with one engine `exec` and one SSH handshake: no web server, token, forward, child webview or page load.

## Persistence Through zellij attach

zellij stays as the in-sandbox multiplexer; only its web front end goes.

- The session name is the sandbox name, the same name the web client derives from the `/<sandbox-name>` URL path, so an existing session started by the web client is reattached unchanged during migration.
- Closing the pane, quitting the app or losing the SSH connection leaves the shell, its scrollback and its running commands alive in the zellij session.
- The web-terminal ideation rejected xterm.js over a Tauri-managed PTY partly because the session "does not survive the host process" (`docs/features/web-terminal/01_ideas.md`, Technology Choices). Attaching zellij over SSH removes that objection.

## Terminal Pane in the Main Webview

`AppKind::Terminal` (`src-tauri/src/workspace/types.rs`) changes from an overlay child webview to a main-webview pane, shaped like `AppKind::AgentChat`.

- The pane registry stays the source of truth for which panes exist and which is active. The terminal pane carries no URL, forward name or init script.
- A Svelte terminal component under `src/lib/terminal/` mounts when the sandbox's Terminal tab is active, subscribes to the session's `Channel`, and sends input and resize events back.
- The component talks to the renderer through a small interface (write bytes, receive input, resize, focus, dispose), so the renderer library can be swapped without touching the session host. The renderer choice is open (see Technology Choices).
- `ServiceKind::Terminal` forwards (`src-tauri/src/network/types.rs`) and the terminal's init-script login in `src-tauri/src/services/panes.rs` are removed once the native terminal replaces the web pane.

## Light-Tier Mock

The session spawns a streaming child, which the scripted `ProcessRunner` (`src-tauri/src/process/types.rs`) cannot model. The terminal subsystem's mock (`src-tauri/src/terminal/mock.rs`) is selected under `MIO_MOCK_BACKEND=1` and echoes input bytes back as output, plus a fixed banner on attach, so `light` specs can type into the terminal and assert on rendered text without Podman.

## Technology Choices With Tradeoffs

### Where the terminal is rendered: the main webview (chosen)

- **Chosen: a terminal component in the main SvelteKit webview.** No second webview to create, no page load, one UI toolkit, and WebdriverIO can drive and read the terminal like any other component.
- **Rejected: a native GPUI surface hosting Ghostty, as the Herd app does.** Ghostty has no Windows build and the app is Windows-first. GPUI owns its own windows and event loop, as does Tauri's `tao`, so embedding GPUI means two event loops or a separate process whose window is re-parented into the Tauri window, with focus, IME, DPI and z-order handled across the boundary. WebdriverIO cannot see a native surface, so `e2e/test/specs/standard/embedded-workspace.spec.ts` and every terminal spec would lose their assertions.
- **Rejected: a native surface built on `alacritty_terminal` or `wezterm-term`** (the crates behind Zed's and WezTerm's terminals). Both run on Windows, but rendering them still needs a native surface beside WebView2, with the same embedding and test-visibility costs as GPUI. Native GPU rendering speeds heavy output, not startup, so the startup goal does not need it.
- **Rejected: keep a child webview but serve the terminal page from the app instead of the sandbox.** Removes the token and the in-sandbox web server, but keeps webview creation and a page load per pane, and keeps the overlay positioning special case.

### Renderer library: wterm or xterm.js (undecided, spike)

Both are web terminal emulators that accept bytes and emit input, so either fits the renderer interface in Terminal Pane in the Main Webview.

- **wterm** (`https://wterm.dev`, `vercel-labs/wterm`, Apache-2.0): renders rows as DOM text with an optional WebGL2 renderer, ships a Svelte component (`@wterm/svelte`), and offers a libghostty-based VT core compiled to WASM (`@wterm/ghostty`, about 580 KB). DOM text gives native selection, browser find, screen-reader access and text WebdriverIO can read directly. Costs, as read from its site and README on 2026-11-15: badged a Vercel Labs experiment with no release history found, no addon ecosystem, ligatures not mentioned, 1,000-line default scrollback, and DOM rendering untested under zellij's full-screen redraws. Not tried in WebView2.
- **xterm.js** with its WebGL addon: the renderer VS Code ships and the one the zellij web client already uses, so its behaviour with zellij is known. Costs: canvas or WebGL output is not DOM text, so e2e specs need its buffer API or the serialize addon to read the screen.
- **Lean:** wterm with the Ghostty core if it passes the renderer spike, for the DOM-text testability; xterm.js otherwise. The renderer interface keeps the choice reversible.

### SSH client: in-process `russh` over the engine `exec` child (chosen)

- **Chosen: the `russh` crate, with the SSH byte stream carried on the stdio of the provider's `exec_command` for `mio-sshd`.** An in-process client sends `pty-req` and `window-change` directly over a plain pipe. Spawning through the provider instead of reading the alias file keeps the session off the host-global `~/.ssh` config, so the session host does not depend on the app-managed alias and the `light` mock stays per-worktree. The cost is a new dependency and owning host-key and key-file handling that OpenSSH does today.
- **Rejected: OpenSSH `ssh -tt <alias>` on plain pipes.** The remote side gets a pseudo-terminal, but OpenSSH sends `window-change` only when its own local terminal resizes, and a piped `ssh` has no local terminal, so pane resizes never reach zellij.
- **Rejected: OpenSSH under a Windows pseudo-console (ConPTY, via the `portable-pty` crate).** Resizing the pseudo-console does resize the remote side, but ConPTY re-renders the VT stream instead of passing it through, which rewrites escape sequences zellij relies on, and the session gains a third process per pane.
- **Rejected: `podman exec -it` or `msb exec` with a terminal, without SSH.** Resize then depends on each engine's remote client seeing a host console, which a piped child does not have, and the two engines differ; SSH gives one engine-neutral in-band resize protocol.

### Session persistence: zellij attach (chosen)

- **Chosen: `zellij attach --create <sandbox-name>`.** zellij is already baked, already holds users' existing sessions, and survives detach.
- **Rejected: tmux, `dtach` or `abduco`.** Each is one more tool in the base image and abandons the sessions users already have in zellij; `dtach` and `abduco` also provide no scrollback.
- **Rejected: a plain login shell with no multiplexer.** Startup is marginally faster, but closing the pane or quitting the app kills running commands, which the current terminal does not do.

## Validation

A gating spike ran on 2026-11-16 on the Windows 11 development host, against throwaway containers built from the base image and a throwaway microsandbox sandbox. The record, scripts, the `russh` probe and raw results are in `docs/features/native-terminal/spike/` ([spike record](spike/README.md)). The spike replicated the current chain from a script rather than instrumenting the app, so webview creation, the web client's JavaScript start-up and its websocket attach are not in the current-chain figures, which are therefore lower bounds.

Cleared risks (medians):

- **The current chain is dominated by serial engine execs and the forward.** On a warm Podman sandbox the chain reaches its first HTTP 200 in 1,767 ms (`podman start` 291, `zellij web --status` 426, `--create-token` 381, Mutagen forward 585), plus about 700 ms of headless page, asset, login and reload fetches. On a freshly started sandbox the chain takes 2,486 ms to the first HTTP 200 and 3,199 ms with the page-load estimate.
- **The proposed path is about three times faster to first frame.** A `russh` session over `podman exec -i <name> mio-sshd` reaches the first complete zellij frame in 636 ms on a warm sandbox and in about 1,108 ms including `podman start` on a stopped one. A plain shell prompt arrives in 440 ms, so `zellij attach` adds about 200 ms.
- **The remaining floor is one Podman exec.** A bare `podman exec <name> true` takes 421 ms, and most of the proposed path's time is that exec plus SSH key exchange; plain OpenSSH `ssh -tt <alias> true` over the same transport takes 546 ms, slower than the in-process client.
- **microsandbox is faster still.** `msb exec` takes 87 ms, and the proposed path reaches the first zellij frame in 403 ms warm and 985 ms after `msb start`.
- **Resize works on both engines.** After a `window-change` from 120×40 to 160×50, zellij redrew to row 50, column 160 in every run (24 Podman, 16 microsandbox), with the first redraw byte about 22 ms after the request.
- **Mutagen's one-off agent install** costs 4 to 9 s on the first forward to a new container; the native terminal does not use a forward, so it never pays the install.

Blocker surfaced and cleared: the default `russh` build fails on the Windows host with "NASM command not found! Build cannot continue." because its default `aws-lc-rs` crypto backend needs NASM. The probe (`docs/features/native-terminal/spike/ssh-probe/Cargo.toml`) builds with default features off and the `ring`, `flate2` and `rsa` features on.

Not yet validated:

- **Renderer fitness in WebView2.** Drive `zellij attach` through wterm (Ghostty core) and xterm.js (WebGL) in the Tauri main webview: time to first frame, smoothness under a flood of output (a verbose build log), IME composition, paste, and zellij's mouse mode.
- **A deployed sandbox** on the remote test machine.
- **`SandboxRouter::resolve`** (`src-tauri/src/services/routing.rs`) and its alias rewrite under the cross-process lock, which both paths still pay and which the spike did not time.

## Open Questions

- **Q1: Renderer library.** wterm (Ghostty core) or xterm.js, decided by the renderer spike in Validation.
- **Q2: Session lifetime while the pane is hidden.** When the user opens a page or the Manage tab, the terminal component unmounts. Either the session host keeps the SSH session open and the remounted component forces a zellij redraw with a resize, or the session host detaches and reattaches on remount at the cost of one engine `exec` and handshake. Recommendation: keep the session open while the pane is registered, since a hidden pane "leaves it running" today (`docs/architecture/workspace-ui.md`).
- **Q3: Retiring `zellij web`.** Whether the zellij web server, its token flow and the terminal forward are removed in the same change, or kept behind a setting as a fallback until the native terminal has run in the `standard` tier. Recommendation: remove them, because keeping both doubles the terminal's e2e surface.
- **Q4: Keyboard ownership.** Which keys the terminal component captures before the main webview's own shortcuts see them, given zellij binds most `Ctrl` chords. The answer depends on which app-wide shortcuts exist when the plan is written.
- **Q5: Pre-warming.** Whether the session host opens the SSH session when a sandbox is selected, before the Terminal tab is clicked. The `embedded-workspace` spec asserts the terminal is not started eagerly (`e2e/test/specs/standard/embedded-workspace.spec.ts`), so pre-warming reverses a tested decision. The spike measured about 640 ms left on a warm Podman sandbox, most of it one Podman exec; recommendation: do not pre-warm in the first build, and revisit only if that delay still feels slow in the app.
- **Q6: `russh` crypto backend.** Whether the build uses `russh` with the `ring` backend, as the spike probe does, or keeps the default `aws-lc-rs` backend and adds NASM to the Windows build prerequisites. Recommendation: `ring`, because it builds with the existing toolchain.

## Common Gotchas

| Gotcha | Cause | Fix |
|---|---|---|
| A `light` e2e run spawns real `podman` or `msb` processes, or hangs opening the terminal | The terminal session is a streaming child, which bypasses the scripted `ProcessRunner` (`src-tauri/src/process/types.rs`), so `MIO_MOCK_BACKEND=1` does not divert it | Select the terminal subsystem's mock (`src-tauri/src/terminal/mock.rs`) under `mock_backend_enabled()`, as `CliBackend::listen_events` in `src-tauri/src/backends/mod.rs` does |
| zellij draws at 80×24 or does not redraw when the pane resizes | The SSH session sent no `pty-req` size or no `window-change` request; OpenSSH on pipes cannot send `window-change` | Send the pane's size in `pty-req` at attach and a `window-change` on every resize from the in-process `russh` client |
| A user's existing terminal session is missing after the switch, and a fresh shell appears | `zellij attach` was given a session name other than the sandbox name the web client used (the `/<sandbox-name>` URL path) | Attach with `zellij attach --create <sandbox-name>` so the session the web client created is reused |
| The `mio-sshd` transport fails with a Windows-style path in the exec argument | Git Bash path conversion rewrites an absolute in-sandbox path passed to `podman` or `msb` | Name `mio-sshd` by bare name, as `ensure_sandbox_alias` in `src-tauri/src/backends/mod.rs` does |
| Host-key verification fails after a base-image rebuild | The `mio-sshd` host key is baked into the base image and changes with each image version, while the per-sandbox known-hosts file keeps the old key | Verify against the per-sandbox known-hosts file (`sandbox_known_hosts_path` in `src-tauri/src/backends/mod.rs`), which `forget_sandbox_host_key` deletes whenever a fresh container is created, and record an unknown key on first connect the way the alias's `StrictHostKeyChecking accept-new` does; never add the key to the user's own known hosts |
| Escape sequences arrive rewritten and zellij renders incorrectly | The session ran OpenSSH under a Windows pseudo-console (ConPTY), which re-renders the VT stream | Carry SSH over the `exec` child's plain stdio with the in-process client; do not put a ConPTY between zellij and the renderer |
| `cargo build` fails with "NASM command not found! Build cannot continue." after adding `russh` | The default `russh` features select the `aws-lc-rs` crypto backend, whose Windows build needs the NASM assembler | Depend on `russh` with default features off and the `ring` backend on, as `docs/features/native-terminal/spike/ssh-probe/Cargo.toml` does, or install NASM |
| A bare `podman` command fails with "connection refused" on a port such as 51105 | The default Podman connection on the development host points at an e2e test machine (`mio-tests-remote`), which is usually stopped | Pass `--connection podman-machine-default` explicitly in manual and spike commands |
| An e2e spec cannot read terminal output | A canvas or WebGL renderer draws pixels, not DOM text | Read text through the renderer's buffer API (xterm.js), or use wterm's DOM renderer, whose rows are DOM text |

# Consolidate AppContainer Webview — E2E Test Plan

This document is the test plan for `docs/features/consolidate-app-container/02_dev.md` (Phases A–C
implemented; Phase D — manual overlay-alignment validation — was performed by hand during
implementation, see "De-risking spike results" below, and is not repeated as an automated check
here). **Status: the rewrite described below is implemented** — `e2e/lib/workspace.ts`, the two
page objects, `e2e/wdio.conf.ts`'s comment, and all seven specs have been rewritten per the Harness
changes/Spec scenario sections, `e2e/lib/dashboard-suite.ts` is deleted, and the whole `e2e/`
package type-checks clean (`npx tsc --noEmit -p tsconfig.json`). **Not yet done:** actually running
the rewritten specs against a real local Podman machine (`pnpm test:standard` or a targeted spec
file) — type-checking proves the mechanical substitution is internally consistent, not that the
real flows still pass.

## Goal

Prove that `main-navigation-panel` is genuinely a single merged webview end-to-end: that a
sandbox's Dashboard (package/agent/ports management), the two-level switcher tab bar, and a
Terminal/AgentWeb pane all coexist as DOM regions of *one* WebDriver window handle, with the
Terminal/AgentWeb pane remaining the one genuine second native surface (a real Mutagen-forwarded
webview). Concretely this means exercising the real Tauri commands `open_workspace`,
`hide_active_pane`, `switch_app`, `switch_pane`, `open_terminal_pane`, `open_agent_web`,
`close_pane`, `close_workspace`, `set_panel_collapsed`, and `workspace_state`, against a real local
Podman sandbox, and reading the resulting DOM back through the same document WebDriver is already
attached to — no `switchToWindow` polling for Dashboard content any more.

A weaker test — e.g. one that only calls `workspace_state()` and asserts on `active_app`/`overlay`
without ever reading the rendered DOM — would miss exactly the class of bug this feature already
produced once (`WorkspaceSwitcher.svelte`'s `h-screen` vs `h-16` regression, see `02_dev.md`'s
Common Gotchas table): the backend can report perfectly correct state while the DOM renders
zero-height. Every spec below must assert on both.

## Existing test styles

- **App-driven WebdriverIO specs**, `e2e/test/specs/{standard,light,heavy}/**` — drive the real
  compiled app through `tauri-driver`, using page objects under `e2e/test/pageobjects/`. This
  feature's specs belong here, tier `standard` (real Podman, real Mutagen).
- **Page objects**, `e2e/test/pageobjects/*.page.ts` — one class per logical UI area, instantiated
  once and exported as a singleton. `workspace-dashboard.page.ts` and `workspace-switcher.page.ts`
  are the two under rewrite here.
- **Shared libs**, `e2e/lib/*.ts` — `workspace.ts` wraps the Tauri commands/types directly (not a
  page object, since it drives via `invoke` not DOM); `dashboard-suite.ts` provides the
  `useDashboardWebview()`/`dashboardIt()` per-test window-handle bookkeeping that this feature makes
  obsolete (see below).

## Chosen approach

Tier: **standard** (default, per `e2e/AGENTS.md` decision rules — this is the happy path, not an
edge case, and provokes nothing large enough for `heavy`). One real local Podman machine
(`mio-tests`, per existing `wdio.conf.ts` provisioning), no second machine or remote deploy needed.

**No new spec file is added.** The seven specs that already exercise a sandbox's Dashboard
(`embedded-workspace.spec.ts`, `agent-web.spec.ts`, `agent-setup.spec.ts`, `expose-port.spec.ts`,
`opencode-agent.spec.ts`, `package-autocomplete.spec.ts`, `runtime-management.spec.ts`) are rewritten
in place — the underlying user flows and assertions they already encode (package install, agent
install/auth, port expose/unexpose, autocomplete, Terminal/AgentWeb pane lifecycle) are still
correct and still the right coverage; only the mechanics of *reaching* the Dashboard's DOM change,
because there is no longer a separate webview to switch WebDriver's session into.

No `light` companion spec is added: there is no new gating/edge-case logic introduced by this
refactor that would be awkward to provoke against real infra — the risk this feature introduces
(CSS-vs-native-geometry drift, see `02_dev.md` Resolved Decision 1) is a rendering/layout concern,
not a store/gating one, and is exactly what the rewritten `embedded-workspace.spec.ts`'s structural
assertions (below) are for.

## Harness changes

1. **`e2e/lib/workspace.ts`** — drop `AppKind`'s `"dashboard"` member (now exactly `"terminal" |
   "agentweb"`, matching `src-tauri/src/workspace/types.rs`). Drop `WorkspaceRects` and its
   `navigation_panel`/`switcher`/`content` fields; `WorkspaceState.rects` becomes
   `WorkspaceState.overlay: Rect` (a single rect), matching `WorkspaceState` in
   `src-tauri/src/workspace/types.rs`. `panesFor`/`paneFor` are unchanged in shape (still filter
   `state.apps`) but can no longer return a `"dashboard"`-kind pane, since none is ever created.
2. **`e2e/test/pageobjects/workspace-dashboard.page.ts`** — delete `switchToDashboard()` and
   `switchToAppWebview()` entirely (no window handle to switch to or from; Dashboard content is a
   DOM subtree of the one window WebDriver is already attached to). Every other getter/action
   (`packageInput`, `installButton`, `launcherButton`, agent/port getters) is kept as-is — those
   selectors are unchanged by this refactor, they just no longer need a preceding window switch.
   Add a `waitForRendered(sandbox)` method replacing the old route/window-poll: wait for
   `packageInput` to exist, exactly as `switchToDashboard` used to do after finding the window,
   since that is still the real signal that `WorkspaceDashboard.svelte`'s `onMount` resolved
   `workspacePath` (`02_dev.md` Phase C).
3. **`e2e/test/pageobjects/workspace-switcher.page.ts`** — delete `switchToSwitcher()`/
   `switchToAppWebview()` (same reasoning). `tab(sandbox, kind)`'s `kind` union drops `"dashboard"`
   as a `data-app` value passed to `switchPane`/`closePane`-style calls, but the home/Manage tab
   itself is unchanged: `SandboxSwitcherGroup.svelte` still renders `button[data-app="dashboard"]`
   for the unconditional home tab (`src/lib/workspace/SandboxSwitcherGroup.svelte:81`), so
   `tab(sandbox, "dashboard")` keeps working as a selector — only its use as an `AppKind` value sent
   to `switch_pane`/`close_pane` is gone.
4. **`e2e/lib/dashboard-suite.ts`** — delete entirely. `useDashboardWebview()`'s `afterEach`
   (`switchToAppWebview().catch(() => {})`) and `dashboardIt()`'s pre-switch
   (`switchToDashboard(sandbox())`) both existed solely to manage the separate-webview handle; with
   Dashboard folded into `main-navigation-panel`, there is nothing to switch to or reset. Every
   caller's `useDashboardWebview()` call is replaced with a direct `captureDiagOnFailure()` call
   (`e2e/lib/diag.ts`) for the same failure-dump behaviour, and every `dashboardIt(title, sandbox,
   fn)` call becomes a plain `it(title, fn)` (the `sandbox` thunk argument is dropped since it only
   existed to drive the pre-switch).
5. **`e2e/wdio.conf.ts`** — the global `before` hook's window-pinning loop
   (`wdio.conf.ts:223-230`) needs no *behavioural* change: `main-navigation-panel`'s pathname was
   never `/workspace/*` (it is the root layout), so the existing `!pagePath.startsWith("/workspace")`
   filter still isolates it correctly now that `/workspace/switcher` and `/workspace/dashboard`
   routes no longer exist at all. Update the stale comment above it (`wdio.conf.ts:218-222`), which
   still describes `main-switcher` and per-sandbox dashboard webviews as if they exist.

## Spec scenario

Each rewritten spec keeps its existing `describe` title and test list; only the following mechanical
substitution is applied throughout, spec by spec:

1. **`embedded-workspace.spec.ts`** — this spec predates even `responsive-panel` (its constants are
   `GLOBAL_EXPANDED_W`/`state.rects.global` where the rest of the codebase has long since renamed
   these `NAVIGATION_PANEL_EXPANDED_W`/`state.overlay`). Rewrite fully against the current model:
   - Drop every assertion on a `"dashboard"`-kind `AppPane` (`paneFor(state, name, "dashboard")`,
     `panesFor` counts that assumed a Dashboard pane exists from `open_workspace` onward) — a
     sandbox with no open Terminal/AgentWeb pane now has zero entries in `state.apps`, full stop.
   - Replace `state.rects.global/switcher/content` assertions with `state.overlay` assertions: the
     overlay rect exists (and is only meaningful) while a Terminal/AgentWeb pane is active; assert
     its `x`/`width` against `NAVIGATION_PANEL_EXPANDED_W`/`RAIL_W`/`SWITCHER_H`
     (`src-tauri/src/workspace/mod.rs`) exactly as the old spec did for the three-way split, but for
     the one remaining rect.
   - Add the DOM-level check this rewrite exists to introduce: after `rowA.openWorkspace()`, assert
     `workspaceDashboard.packageInput` (or another Dashboard element) is actually `isDisplayed()`
     with nonzero height (`getSize()`), not just present in the DOM — this is the structural
     regression check for the `h-screen`/`h-16` class of bug (`02_dev.md` Common Gotchas, last row).
     Repeat this displayed-with-nonzero-height check immediately after closing a Terminal pane and
     returning to the Manage tab, since that is the exact sequence the original bug report described.
   - `switch_pane(name, "dashboard")` call sites become `hide_active_pane()` (the Phase B command
     added specifically for "return to Manage" — see `02_dev.md` Phase B) plus a client-side
     `SandboxSwitcherGroup`'s home-tab click (`workspaceSwitcher.clickTab(name, "dashboard")`) driven
     through the DOM instead of the invoke wrapper, since the real user path is a DOM click, not a
     direct `switch_pane` call with a now-nonexistent `AppKind`.
   - `close_pane(name, "dashboard")` no-op assertion is deleted (there is no such call to make; the
     `AppKind` enum no longer has the variant, so this would be a compile error in `workspace.ts`,
     not a runtime no-op).
   - `sandbox_last_pane` assertions (added post-hoc, see `02_dev.md` Lifecycle section) are kept
     unchanged — that map's contract (Terminal/AgentWeb-only, cleared on destroy regardless of
     whether `apps` is already empty) is orthogonal to this rewrite.
2. **`expose-port.spec.ts`, `agent-setup.spec.ts`, `opencode-agent.spec.ts`,
   `package-autocomplete.spec.ts`, `runtime-management.spec.ts`** — mechanical substitution only:
   - Remove the `useDashboardWebview()`/`dashboardIt` imports and calls; use `captureDiagOnFailure()`
     directly and plain `it(...)`.
   - Replace every `workspaceDashboard.switchToDashboard(projectName)` call with
     `workspaceDashboard.waitForRendered(projectName)` (new name, see Harness changes above) — same
     position in the flow (right after `row.openWorkspace()` or after an action that returns focus
     to Dashboard), same timeout behaviour.
   - Remove every `workspaceDashboard.switchToAppWebview()` call before `row.destroy()` — destroying
     a sandbox no longer requires leaving a separate webview first, since there is only ever the one
     window handle.
   - No other line in these five specs changes: the package/agent/port assertions themselves are
     unaffected by this refactor.
3. **`agent-web.spec.ts`** — same mechanical substitution as above, plus:
   - Line ~103's `["dashboard"]` (an expected initial `AppKind` list, most likely asserting the
     sandbox's pane list right after `open_workspace`) is checked against the actual current source
     before rewriting — read the surrounding assertion first since this file was not read in full
     during planning; if it asserts a Dashboard pane exists post-`open_workspace`, that assertion is
     deleted (Resolved Decision 2: no Dashboard pane is ever created).
   - Line 199's `switchPane(projectName, "dashboard")` becomes `hide_active_pane()` (same reasoning
     as `embedded-workspace.spec.ts` above).

## De-risking spike results

**Date:** during this session's implementation pass (prior to this document being written), not a
separate scheduled spike.

- **Cleared, live, via manual devtools inspection** (screenshot + DOM/console read against a running
  dev instance, see prior session notes): confirmed the Dashboard's markup renders inside
  `main-navigation-panel`'s own document — no separate `workspace-<name>-dashboard` webview is
  created, matching Resolved Decision 2/4.
- **Blocker found and already fixed** (feature fix, not a test concern): `WorkspaceSwitcher.svelte`'s
  tab-bar `<div>` used `h-screen` instead of `h-16`, squeezing the Dashboard's `flex-1` sibling to
  zero height whenever the switcher bar was present. Fixed in `src/lib/workspace/WorkspaceSwitcher.svelte`
  (now `h-16 shrink-0`); recorded in `02_dev.md`'s Common Gotchas table (last row). This is exactly
  the class of bug the new displayed/nonzero-height DOM assertions in `embedded-workspace.spec.ts`
  (see Spec scenario, item 1) are written to catch mechanically instead of by hand next time.
- **Not yet run**: the rewritten specs themselves have not been executed against the real app in
  this pass — the rewrite described above is still to be implemented and then run once.

## Sequencing

1. Rewrite `e2e/lib/workspace.ts` first (type-only change) — every other file below depends on its
   `AppKind`/`WorkspaceState` shape compiling.
2. Rewrite the two page objects (`workspace-dashboard.page.ts`, `workspace-switcher.page.ts`) and
   delete `dashboard-suite.ts` next — these are the shared mechanics every spec calls into.
3. Rewrite `embedded-workspace.spec.ts` third — it is both the most-diverged spec (predates
   `responsive-panel`'s renames as well) and the one that most directly proves the merged-webview
   claim this feature makes, so it should go green (or reveal a real remaining bug) before touching
   the other five, simpler, mechanical-substitution specs.
4. Rewrite the remaining five specs (`expose-port`, `agent-setup`, `opencode-agent`,
   `package-autocomplete`, `runtime-management`) last, since their substitution is identical and
   mechanical once steps 1–3 prove the pattern works.
5. Run `pnpm test:standard` (or the individual rewritten spec files) against a real local Podman
   machine as the final step, not `pnpm check`/`cargo check` alone — this feature's whole risk
   surface (CSS-vs-native geometry, DOM rendering after client-side state changes) is invisible to
   type checking.

## Environment notes

- Needs the `mio-tests` local Podman machine already provisioned (per `e2e/AGENTS.md` `standard` tier
  requirements); no second machine or remote deploy target is needed for any of these seven specs.
- No new ports, sockets, or sidecar binaries beyond what these specs already required before this
  rewrite (Zellij terminal token file, Mutagen forwards, socat fake services in `expose-port.spec.ts`).
- `SANDBOX_WORKSPACE_ROOT` must be set, as `embedded-workspace.spec.ts` already required.

## Common Gotchas

| Gotcha | Cause | Fix |
|---|---|---|
| `tsc`/`eslint` reports `Type '"dashboard"' is not assignable to type 'AppKind'` in a spec that still calls `switchPane`/`closePane` with `"dashboard"` | A leftover call site still sends the deleted `AppKind::Dashboard` variant to a real Tauri command | Delete the call; the client-side path back to Dashboard is `hide_active_pane()` (or a DOM click on the home tab), never `switch_pane`/`close_pane` with kind `"dashboard"` (`02_dev.md` Phase B) |
| A rewritten spec times out inside `waitForRendered`/the old `switchToDashboard`'s replacement, never finding `packageInput` | `main-navigation-panel`'s window handle was never located because `wdio.conf.ts`'s `before` hook comment is stale but its logic already isolates that handle correctly — this points at a real rendering bug (e.g. the `h-screen` class of regression), not a harness problem | Screenshot the current window (`browser.saveScreenshot`, or `e2e/.diag` via `captureDiagOnFailure()`) before assuming the harness is at fault; confirm `workspaceDashboard.packageInput.isDisplayed()` and its size, not just `.isExisting()` |
| `state.rects` is `undefined` / TypeScript error on `.global`/`.switcher`/`.content` in a not-yet-rewritten spec | `WorkspaceState.rects: WorkspaceRects` was replaced by `WorkspaceState.overlay: Rect` in `src-tauri/src/workspace/types.rs`, but `e2e/lib/workspace.ts`'s copy of the type was not updated yet | Apply the Harness changes section's `workspace.ts` rewrite (item 1) before touching any spec that reads `workspace_state()` |
| `dashboardIt`/`useDashboardWebview` import fails to resolve | `e2e/lib/dashboard-suite.ts` was deleted per this plan (Harness changes item 4) but a spec file still imports from it | Replace with `captureDiagOnFailure()` (`e2e/lib/diag.ts`) and plain `it(...)`, per the Spec scenario section |
| A spec passes locally but a reviewer can't tell whether it actually proves the merged-webview claim | An assertion checks only `workspace_state()` (backend truth) and never reads the rendered DOM, so a CSS-only regression (backend state correct, DOM squeezed to zero height) would pass unnoticed — exactly what happened once already, see the Goal section | Every Dashboard-adjacent spec must include at least one `isDisplayed()`/nonzero-size DOM assertion, not backend-state assertions alone |

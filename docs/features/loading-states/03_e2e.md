# Loading States for User Actions — E2E Test Plan

This document is the test plan for the loading-states feature described in `docs/features/loading-states/02_dev.md`. The plan covers the per-row status row (pending message + error), the `loading`/`disabled` button states, and the per-row error scoping that supersedes the old page-level `onError` bubbling. The feature is frontend-only, so the test exercises the real Svelte components (`Button` with `loading`, `StatusRow`, `createActionRunner`) wired over the same unchanged Tauri commands (`create_sandbox`, `install_package`, `deploy_sandbox`, etc.). **No spike has been run.** The central risk — whether WebdriverIO can observe a transient in-flight state before the action completes — is unconfirmed and is the first thing Section 7 says to clear by hand.

## Goal

The test must prove three things through the running app:

1. **A failed action surfaces its error in that row's own status row.** Driving a real action that the backend rejects (e.g. installing a nonexistent package via the real `install_package` command) must render the error text inside the failing row's `[role="status"]` element — and **not** in any other row or in the page-level error line. This is the teeth of the feature: it proves `createActionRunner.run()` caught the rejection, routed it through `parseError` (`src/lib/errors.ts`), and that `StatusRow` is wired per-row, validating the `02_dev.md` decision to remove the `onError` prop from `SandboxItem`.
2. **A slow action shows in-flight feedback while it runs.** During a deliberately slow action (a real package install, which the existing page object already allows up to 180 s), the pressed button must report `aria-busy="true"` / `disabled`, the row's status row must show the pending message ("Installing <name>…"), and the other controls in the same row must be `disabled`. This proves the `loading` prop on `Button` and the `busy`-driven sibling disable.
3. **The button-to-`Button` migration did not break the existing UI contract.** The migrated header controls (`start`, `stop`, `deploy`, `undeploy`, `terminal`, `destroy`) must still be resolvable and clickable by the existing page-object text selectors, proving the Phase D markup change is backward-compatible.

A weaker test would fail to cover the feature: a unit test of `createActionRunner` in isolation proves the runner's state machine but not that `StatusRow` is mounted, that the spinner button renders, or that errors are row-scoped rather than page-scoped. A test that asserts only the page-level error string would actively miss the supersede — it would still pass with the old `onError` bubbling in place.

## Existing Test Styles

The repo has one E2E category: app-driven WebdriverIO specs that launch the compiled Tauri binary, drive the UI through page objects (`e2e/test/pageobjects/`), and read ground truth from the CLI and filesystem.

- `e2e/test/specs/project-start-stop.spec.ts` — the simplest local-only spec: create → start → assert running indicator → stop. It uses only `LOCAL_CONNECTION` and no remote host. The new spec belongs to this lightweight local-only style.
- `e2e/test/pageobjects/project-row.component.ts` — the component object wrapping one `<li>`. It already exposes `startButton`, `stopButton`, `installButton`, `packageInput`, `installPackage(pkg)`, `installedPackages()`, and `statusText`. The new spec extends this page object with status-row and busy-state getters.
- `e2e/test/pageobjects/projects.page.ts` — exposes `createProject(name)` returning a `ProjectRow`.

## Chosen Approach

Add `e2e/test/specs/loading-states.spec.ts` with two `describe` blocks, both local-only (no `REMOTE_CONNECTION`, no second Podman machine), so the spec runs in the lightweight environment of `project-start-stop.spec.ts`:

- **Block 1 — error is surfaced and row-scoped.** Create two projects, trigger a failing `install_package` on the first (a package name guaranteed to not resolve, e.g. `this-package-does-not-exist-<timestamp>`), assert the first row's status row shows non-empty error text, and assert the second row's status row stays empty. This proves both the error rendering and the per-row scoping in one block.
- **Block 2 — in-flight feedback during a slow action.** Create a project, start a real package install of a small valid package, and *before* it completes assert: the install button is `aria-busy`/`disabled`, the package input is `disabled`, and the status row shows the "Installing…" pending message. Then let the install finish and assert the status row clears and the package chip appears.

A real package install is chosen as the slow action rather than `deploy` because install is local-only (no remote host needed) and is reliably slow enough (mise package resolution takes seconds) for the poll in Block 2 to catch the in-flight state. `deploy` would also exhibit the in-flight state but requires the two-machine topology of `deploy-remote.spec.ts`, which is heavier than this feature needs.

The migration regression (Goal 3) is covered for free: `project-start-stop.spec.ts` already drives `start`/`stop` by the `button=start` / `button=stop` text selectors, so if the `Button` migration broke those selectors that existing spec goes red. No new assertion is needed for Goal 3 beyond keeping the existing spec green.

## Harness Changes

### Page object additions (`e2e/test/pageobjects/project-row.component.ts`)

Add getters and helpers; no `wdio.conf.ts` change is required.

- `get statusRow(): Element` → `this.root.$("[role='status']")` — the StatusRow element, present only when busy-with-message or in error.
- `async statusRowText(): Promise<string>` → returns the status row's text, or `""` when the element does not exist (use `isExisting()` first, since StatusRow renders nothing when idle).
- `async hasStatusError(): Promise<boolean>` → true when a `[role='status'].text-destructive` element exists in the row.
- `async isInstallBusy(): Promise<boolean>` → reads `aria-busy` on `installButton` (`(await this.installButton).getAttribute("aria-busy")` === `"true"`).
- `async isPackageInputDisabled(): Promise<boolean>` → `!(await (await this.packageInput).isEnabled())`.
- `async startInstall(pkg): Promise<void>` → a non-waiting variant of `installPackage`: set the input and click install, but **do not** wait for the chip. Block 2 needs to assert the in-flight state, which the existing `installPackage` would race past because it waits for completion.

### Page-level status row getter (`e2e/test/pageobjects/projects.page.ts`)

Add `get pageStatusRow(): Element` → `$("main [role='status']")` scoped to the create field, plus the existing page-level error line, so Block 1 can assert the *page* did not show the row error (proving the error stayed in the row, not bubbled up).

### No build or provisioning change

The spec is local-only and needs only `LOCAL_CONNECTION` and the mise base image already staged by `onPrepare` in `e2e/wdio.conf.ts`. The compiled debug binary must include all five phases of the feature — run `pnpm tauri build --debug --no-bundle` before the suite, as the other specs require. The `after` hook calls `podman(LOCAL_CONNECTION, ["rm", "-f", name])` for each created project, mirroring `project-start-stop.spec.ts` cleanup.

## Spec Scenario

### `e2e/test/specs/loading-states.spec.ts` — Block 1: error is surfaced and row-scoped

1. **Create two projects.** `ProjectsPage.open()`; `const rowA = await ProjectsPage.createProject(nameA)`; `const rowB = await ProjectsPage.createProject(nameB)`. Assert both rows display.
2. **Trigger a failing install on row A.** `await rowA.startInstall("zzz-nonexistent-" + Date.now())`. This invokes the real `install_package` command, which rejects when the package does not resolve.
3. **Assert row A shows the error.** Poll up to 60 s for `rowA.hasStatusError()` to be true and `rowA.statusRowText()` to be non-empty. This proves the rejection reached `createActionRunner.run()`'s catch and `StatusRow` rendered it in `text-destructive`.
4. **Assert the error is row-scoped.** Assert `(await rowB.statusRowText()) === ""` — row B never shows row A's error. Assert `ProjectsPage.pageStatusRow` does not exist / is empty — the page-level line did not receive the error. This is the direct proof that the `onError`-to-page bubbling was removed (the `02_dev.md` supersede).
5. **Assert recovery clears the error.** `await rowA.installPackage("<a-valid-small-package>")` (the waiting variant). Assert `rowA.hasStatusError()` becomes false once the successful action's `run()` cleared `error` at its start. This proves `run()` resets `error` on the next action.
6. **Cleanup.** `after` removes both projects via `podman rm -f`.

### `e2e/test/specs/loading-states.spec.ts` — Block 2: in-flight feedback during a slow action

1. **Create a project.** `const row = await ProjectsPage.createProject(name)`.
2. **Start a real install without waiting.** `await row.startInstall(validPkg)` where `validPkg` is a small real package (the same one `runtime-management.spec.ts` / package specs use).
3. **Assert in-flight state before completion.** Inside a `browser.waitUntil` (short timeout, 10 s) assert all hold simultaneously while the install runs: `await row.isInstallBusy()` is true, `await row.isPackageInputDisabled()` is true, and `(await row.statusRowText())` contains the package name (the "Installing <name>…" message). The `waitUntil` tolerates the small delay before the click's effect renders.
4. **Assert completion clears the in-flight state.** `await row.waitForPackage(validPkg)`. Then assert `row.isInstallBusy()` is false, `row.isPackageInputDisabled()` is false, and `row.statusRowText()` is empty — proving `run()`'s `finally` cleared `busy` and `message`.
5. **Cleanup.** `after` removes the project.

## De-risking Spike Results

No spike has been run. The following risks must be cleared by hand before the spec is worth writing — a spec that races a state that renders and clears faster than WebdriverIO can poll would be flaky, not wrong, which is worse.

**Risk 1 — the in-flight state is observable through WebdriverIO (test-concern).**
The pending message and `aria-busy` exist only while the action is in flight. If a real package install completes in under the WebDriver command round-trip, Block 2 step 3 never sees the busy state. Spike: run the app by hand, click install on a real package, and confirm by eye that the install button greys out, the spinner shows, and the status row reads "Installing…" for at least ~1 s. If install is too fast, switch Block 2 to drive `deploy` (reliably multi-second) instead, accepting the two-machine topology. Record which action proved observable.

**Risk 2 — the failing `install_package` produces a non-empty, parseable error (test-concern).**
Block 1 assumes a nonexistent package name makes `install_package` reject with an `AppError` whose `message` is non-empty after `parseError`. Spike: from the app, install a bogus package name and confirm the row shows a visible red error line (not a silent no-op or an empty string). If the backend treats an unknown package as success, choose a different deterministic failure (e.g. an invalid package-name character) and record it.

**Risk 3 — the `Button` migration preserves the page-object text selectors (feature-fix concern).**
The page objects resolve controls by exact text (`button=start`, `button=install`, `button=Deploy`). After migrating raw `<button>`s to the shadcn `Button` component the rendered element is still a `<button>` with the same text content, so `button=start` should still match — but the inline spinner `<svg>` rendered when `loading` is true must not contribute text or alter the match. Spike: after Phase A and D land, run the existing `project-start-stop.spec.ts`; if `button=start` no longer resolves, the migration changed the element shape and must be fixed (e.g. wrap label text so exact-text selectors still match) before the new spec is written.

## Sequencing

1. Implement Phases A–E from `02_dev.md`.
2. Run Risk 3 check first: keep `project-start-stop.spec.ts` green after the migration. If it breaks, fix the markup before anything else — every other spec depends on those selectors.
3. Run the Risk 1 and Risk 2 manual spikes from the running app. Decide Block 2's slow action (install vs deploy) and Block 1's deterministic-failure input from the results.
4. Add the page-object getters (Section 5), then write `loading-states.spec.ts` per Section 6.

## Common Gotchas

| Gotcha | Cause | Fix |
|---|---|---|
| Block 2 never sees `aria-busy="true"` | The driven action completes faster than one WebDriver command round-trip, so the in-flight state renders and clears between polls | Use a reliably slow action (real package install or `deploy`); wrap the assertion in `browser.waitUntil`; confirm observability in the Risk 1 spike before writing the spec |
| `button=start` no longer resolves after Phase D | The `Button` migration changed the control's text content or nested the label so exact-text matching fails | Keep the label as direct text of the `<button>`; run `project-start-stop.spec.ts` as the regression guard; the spinner `<svg>` must carry no text |
| `rowA.statusRow` is `null` when asserting an error | `StatusRow` renders nothing when idle, so `[role="status"]` does not exist until an action sets `busy`+message or `error` | Guard with `isExisting()` in `statusRowText()`; poll with `browser.waitUntil` rather than reading once |
| Block 1 step 4 fails: page-level line shows the error | A leftover `onError` bubble from `SandboxItem` was not removed in Phase D/E, so the row error still reaches the page | Confirm the `onError` prop is removed from `SandboxItem` and from the `<SandboxItem>` instantiation in `+page.svelte` (Phase E) |
| Installing a bogus package silently succeeds (no error row) | `install_package` does not treat an unknown package name as a failure | Pick a deterministically rejecting input (invalid characters) confirmed in the Risk 2 spike; record the chosen input in the spec comment |
| Error never clears after a successful retry (Block 1 step 5) | `createActionRunner.run()` does not reset `error` at the start of each action | Confirm `run()` sets `error = ""` before awaiting the thunk (`src/lib/actions.svelte.ts`) |
| Spinner persists forever after an action | `run()`'s `finally` did not clear `busy`/`message`, e.g. an exception escaped the try | Confirm the `finally` block in `createActionRunner.run()` always clears `busy` and `message` |
| `waitForSyncStatus` / `statusText` matches the new status row instead of the deployment status | The status row and the deployment status text can both carry `text-muted-foreground text-xs` | Scope status-row assertions to `[role='status']`; keep the deployment status selector distinct from the StatusRow element |
| Disabled button click throws "element not interactable" in a later step | A spec step clicks a control while a prior action's `busy` still disables the whole row | Wait for the prior action to finish (`waitForPackage`, or poll `!isInstallBusy()`) before driving the next control |

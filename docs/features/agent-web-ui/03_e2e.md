# Agent Web UI E2E

Test plan for the agent-web-ui feature as built in `02_dev.md` (Phases A–D, all implemented in the
current working tree). The plan covers two specs: a primary `standard` spec proving the full
open-Agents-pane path against a real sandbox, and a small `standard` spec for the stale-forward
sweep the implementation added to app startup. No e2e-specific de-risking spike has been run yet;
the Phase D implementation spike (recorded in `02_dev.md`) already cleared the auto-login
mechanics, and the remaining e2e-only risks are listed under De-risking.

## Goal

Prove the real code path: the `open_agent_web` Tauri command → `prepare_agent_web_pane`
(`src-tauri/src/lib.rs`) → `PodmanMiseRuntime::prepare_agent_web` (`src-tauri/src/runtime/mod.rs`:
real `mise use node@lts npm:@getpaseo/cli`, real `podman exec -d ... mise exec -- paseo daemon
start`) → `sync::forward_create` (real Mutagen sidecar) → `fetch_paseo_server_info` (real HTTP
`GET /api/status` through the forward) → `workspace::embed_agent_web` (real pane in the Rust
registry). Plus the teardown path: `close_app` terminating the `agentweb-<name>` forward and
`destroy_sandbox`/`undeploy_sandbox` terminating it explicitly.

A weaker test would fail to cover:

- **A mock-backend (`light`) test proves nothing here.** Under `MIO_MOCK_BACKEND=1`,
  `MockRuntime::prepare_agent_web` returns port 0 and `fetch_paseo_server_info` then fails its
  HTTP retries against a dead port, so `open_agent_web` errors before embedding anything. The mock
  seam ends at `prepare_agent_web`; the interesting behaviour (paseo install via mise, daemon
  start under `mise exec`, pasta port publish, Mutagen forward, `serverId` fetch) is all real
  infrastructure by construction.
- **A unit test of `prepare_agent_web_pane` would not prove** that the container image actually
  publishes `PASEO_WEB_PORT` (6767), that `procps` is baked (paseo's `daemon stop` shells out to
  `ps`), that the paseo npm package installs and starts under `podman exec`'s non-interactive
  shell, or that the seeded `@paseo:daemon-registry` `serverId` matches what the live daemon
  reports.

One deliberate boundary: the spec asserts up to and including the daemon serving `/api/status`
with the persisted password through the Mutagen forward, and the pane registering in the workspace
registry with the right URL and `init_script` inputs. It does not screenshot-verify the SPA
rendering its home screen inside the embedded webview — WebDriver can attach to the pane's window
handle, but asserting on paseo's minified SPA internals would couple the suite to a third-party
bundle. The Phase D spike (`02_dev.md`) is the recorded evidence for the SPA-side auto-login, and
the "Direct Connection" welcome-screen gotcha in `02_dev.md` documents the re-verification
technique if the SPA behaviour regresses.

## Existing test styles

- **App-driven WebdriverIO specs** in `e2e/test/specs/{standard,light,heavy}/`, driven through
  page objects (`e2e/test/pageobjects/`) and library helpers (`e2e/lib/`). Tier taxonomy in
  `e2e/AGENTS.md`.
- The closest relatives, both `standard`:
  - `e2e/test/specs/standard/web-terminal.spec.ts` — the Zellij twin: asserts the create-time
    `--publish` binding via `podman inspect .HostConfig.PortBindings`, the persisted
    `.mio/zellij.json`, the `terminal-<name>` Mutagen forward via `forwardList`
    (`e2e/lib/mutagen.ts`), an HTTP 200 from the forwarded Windows port, and forward teardown on
    destroy. The agent-web spec mirrors it seam for seam.
  - `e2e/test/specs/standard/agent-setup.spec.ts` — drives the Dashboard pane's AgentManager UI
    by switching WebDriver window handles (`workspace-dashboard.page.ts`), with a 900000 ms suite
    ceiling for npm downloads.
- **Registry read-back** goes through `e2e/lib/workspace.ts`: Tauri commands invoked from the
  `main-global` webview via `window.__TAURI_INTERNALS__.invoke`, then assertions on the returned
  `workspace_state`.
- **Standalone POCs** (Playwright scripts outside the suite) were used for the Phase D spike only;
  the new tests are app-driven WebdriverIO specs.

## Chosen approach

**Tier: `standard`.** Two specs:

1. `e2e/test/specs/standard/agent-web.spec.ts` — the primary spec, local-only topology (one
   sandbox on the `mio-tests` machine, no remote machine involved). The first "Agents" open
   downloads node@lts plus `@getpaseo/cli` through mise (tens of MB, same order as
   `agent-setup.spec.ts`'s Claude Code install), which stays within `standard` — no model-scale
   asset, no remote deploy, so `heavy` is not warranted.
2. `e2e/test/specs/standard/forward-sweep.spec.ts` — covers `sync::sweep_stale_forwards`
   (`src-tauri/src/sync/mod.rs`), the startup sweep added because the Mutagen daemon outlives the
   app and `terminal-`/`agentweb-` forwards leak on ungraceful exit (a gap this feature's work
   uncovered — the e2e harness itself was a leak source). The sweep only runs at app startup with
   podman ready, so a `light` variant cannot exercise it, and it needs orphan sessions seeded
   *before* the app process spawns — a harness concern, hence its own small spec.

**No `light` spec.** The main path cannot run against the mock backend (see Goal), and the one
pure-UI seam — the switcher's synthetic "Agents" tab — lives in the `main-switcher` child webview,
which is equally reachable (or not) in both tiers, so a `light` spec would add no coverage the
`standard` spec lacks.

**UI drive point.** The synthetic "Agents" tab in the switcher (`src/routes/workspace/switcher/
+page.svelte`) is the feature's unique UI seam: it must render before any AgentWeb pane exists and
its first click must create the pane. The spec drives it by switching to the switcher's WebDriver
window handle (pathname `/workspace/switcher`) and clicking the `<sandbox> — Agents` button —
the switcher webview is never hidden, so the WebView2 `hide()` hang that forced
`workspace-dashboard.page.ts` to call `switch_pane` first does not apply. If the de-risking spike
finds the switcher handle unclickable anyway, the fallback is invoking `open_agent_web` directly
from `main-global` (the exact command the tab's `onclick` calls), accepting the tab's DOM as
untested. The AgentManager "Open Agents UI" button (`src/routes/projects/AgentManager.svelte`) is
*not* driven: it is gated on an installed agent, which would add a multi-minute Claude Code
install to test a button that invokes the identical command; recorded as an accepted gap.

## Harness changes

- `e2e/lib/workspace.ts`: widen the `AppKind` union with `"agentweb"`, add `workspace_path` to
  the `AppPane` interface (the field Phase B added Rust-side), and add an
  `openAgentWeb(name, workspacePath)` helper invoking the `open_agent_web` command (the fallback
  drive point, and the re-open step's drive point). Update the header comment: the claim that
  specs "cannot click into" child webviews is outdated — `workspace-dashboard.page.ts` already
  clicks into the dashboard pane by window handle.
- New page object `e2e/test/pageobjects/workspace-switcher.page.ts`: `switchToSwitcher()` (poll
  window handles for pathname `/workspace/switcher`, mirroring `switchToDashboard`) and
  `agentsTab(sandbox)` / `paneTab(sandbox, title)` getters for the tab buttons.
- `e2e/wdio.conf.ts` `beforeSession` (standard suite only, before `tauri-driver` spawns the app):
  seed two orphan forward sessions in the app's private Mutagen data directory
  (`MUTAGEN_DATA_DIRECTORY` = `%APPDATA%\com.tincho.sandbox-mio\mutagen`, same env
  `forwardList` in `e2e/lib/mutagen.ts` already uses) via the vendored `tools/mutagen.exe`:
  `agentweb-e2e-orphan-sweep` (must be swept) and `mio-e2e-keep-sweep` (prefix outside
  `terminal-`/`agentweb-`, must survive). The forward target alias does not need to resolve —
  a session in "Connecting"/errored state still lists by name, and the sweep terminates by name
  regardless of connection state. Requires a `forwardCreate` helper added to `e2e/lib/mutagen.ts`
  next to `forwardList`.
- Suite timeout: `agent-web.spec.ts` sets `this.timeout(900000)` like `agent-setup.spec.ts`
  (mise downloads node@lts + `@getpaseo/cli` on the first Agents open). No `onPrepare` changes:
  `ensureMiseBaseImage` already stages the base image, and the `BASE_IMAGE_VERSION` 2→3 bump
  (Phase A) makes it rebuild with `procps` and both `--publish` flags automatically.

## Spec scenario: `agent-web.spec.ts`

Constants: `PASEO_WEB_PORT = "6767"`, project name `e2e-agentweb-<timestamp>`, password file
`<WORKSPACE_ROOT>/<project>/.mio/paseo.json`. Diagnostics `afterEach` (URL + page source +
screenshot to `e2e/.diag`) copied from `web-terminal.spec.ts`.

1. **Create a local sandbox with the paseo port published.** UI: `ProjectsPage.createProject`
   (600000 ms window for a first-time base-image build). Assert: `podman inspect <name> --format
   '{{json (index .HostConfig.PortBindings "6767/tcp")}}'` lists a `127.0.0.1` HostIp — read the
   *configured* binding via inspect, not `podman port`, because pasta only materializes the
   forward once the container runs (Phase A/B proof: both `--publish` flags at create time).
2. **Start the sandbox.** UI: `row.start()`. Assert: row status text matches `running`.
3. **Open the workspace; no AgentWeb pane exists yet.** UI: `row.openWorkspace()`. Assert via
   `workspaceState()`: exactly a Terminal and a Dashboard pane for the sandbox, no `agentweb`
   kind, and each pane's `workspace_path` equals the sandbox's workspace directory (the Phase B
   `AppPane` field the switcher depends on).
4. **First click of the synthetic "Agents" tab creates the pane.** UI: switch to the switcher
   window handle, click the `<sandbox> — Agents` button, switch back to `main-global` (fallback:
   `openAgentWeb(name, workspaceDir)`). Assert, polling up to the suite ceiling because the first
   open pays the mise download:
   - `workspaceState()` gains a pane with kind `agentweb`, label `workspace-<name>-agentweb`,
     `forward_name` `agentweb-<name>`, and `active_app` set to that label (lazy embed activates
     immediately — Phase B).
   - `.mio/paseo.json` exists host-side with a non-empty `password` string.
   - `<workspace>/mise.toml` contains `node` and `npm:@getpaseo/cli` — proves the workspace-
     manifest install (the seam that makes `reproduce_remote` reinstall paseo on remote deploys;
     an image-baked paseo would leave the manifest clean and silently break remote).
   - `podman exec <name> ps aux` output contains `paseo` — proves the daemon is running *and*
     that `procps` is baked (`ps` itself is the Phase A dependency).
   - `forwardList("agentweb-<name>")` includes `Connected`.
5. **The forwarded port serves the daemon with the persisted password.** No UI action. Parse the
   Windows port from the `agentweb` pane's `url` in `workspaceState()`. Assert: `fetch` of
   `http://127.0.0.1:<port>/api/status` with header `Authorization: Bearer <password from
   paseo.json>` returns HTTP 200 and a JSON body whose `serverId` is a non-empty string — the
   decisive end-to-end proof (daemon up, listening on `0.0.0.0`, pasta bridged, Mutagen forward
   live, password accepted), and the exact request `fetch_paseo_server_info` must have already
   succeeded at for the pane to exist. Record the `serverId` for step 6.
6. **Re-open is switch-not-duplicate, restarts the daemon, and keeps the password.** UI: invoke
   `switch_pane` to the Terminal pane, capture the paseo daemon PIDs (`podman exec <name> ps -eo
   pid,args`, lines containing `paseo`), then `openAgentWeb(name, workspaceDir)` again. Assert:
   still exactly one `agentweb` pane in `workspaceState()` and `active_app` is back on it (the
   `open_agent_web` exists-guard); `.mio/paseo.json` holds the *same* password (mint-once,
   reuse-on-restart — the Lifecycle resolution); the paseo PID set changed (the environment-
   refresh restart of Phase B step 3 actually ran); `/api/status` on the pane's current URL
   returns 200 again with the same Bearer password. The PID assertion is best-effort — if paseo's
   supervisor/child split makes it flaky in practice, drop it and keep the password-stability and
   200 assertions, which are the user-visible contract.
7. **Closing the workspace tears down the forward but not the daemon.** UI: invoke
   `close_workspace` for the sandbox from `main-global`. Assert: `forwardList("agentweb-<name>")`
   no longer shows `Connected` (the `close_app` `Terminal | AgentWeb` match arm), and `podman
   exec <name> ps aux` still contains `paseo` (the daemon outlives the pane — Lifecycle section:
   re-opening later must be instant).
8. **Destroy removes the container and the forward stays gone.** UI: `row.destroy()`. Assert:
   `podman inspect <name>` fails, and `forwardList("agentweb-<name>")` shows no `Connected`
   session (the explicit `agentweb-` terminate in `destroy_sandbox`).

Suite `after` hook: best-effort `podman rm -f <name>` so a failed run leaves no container.

## Spec scenario: `forward-sweep.spec.ts`

Preconditions created by the harness (`beforeSession`, see Harness changes): sessions
`agentweb-e2e-orphan-sweep` and `mio-e2e-keep-sweep` exist in the app's Mutagen daemon before the
app starts; no sandbox named `e2e-orphan-sweep` exists.

1. **The startup sweep terminates orphaned agentweb/terminal forwards.** No UI action (the sweep
   is spawned in Tauri `setup`, after `SandboxBackend::list` succeeds). Assert:
   `forwardList("agentweb-e2e-orphan-sweep")` becomes empty within 60 s of the session starting
   (poll — the sweep is async and waits on podman readiness).
2. **The sweep never touches sessions outside its prefixes.** Assert:
   `forwardList("mio-e2e-keep-sweep")` still lists the session (any status). Then terminate it
   via the vendored mutagen CLI as cleanup.
3. **A live sandbox's forward survives.** Covered implicitly by `agent-web.spec.ts` running in
   the same session: its forwards are created *after* startup, so the sweep cannot race them, and
   step 5 there asserts `Connected`. No extra step here.

## De-risking spike results

**Feature-side spike (already run, recorded in `02_dev.md` Phase D):** Playwright/Chromium against
a live sandbox's published paseo port (paseo 0.1.103) cleared auto-login end-to-end — seeding
`@paseo:daemon-registry` with the real `serverId` skips the welcome screen; a placeholder
`serverId` fails as "Connection timed out". Also established `GET /api/status` as the public
`serverId` source. Those risks need no re-spiking; the spec's step 5 asserts the same request.

**E2E-side spike (2026-07-03, at implementation time):** two of the three risks are cleared:

- **Mutagen version conflict: cleared.** Both the vendored `tools/mutagen.exe` and the sidecar
  `src-tauri/binaries/mutagen-x86_64-pc-windows-msvc.exe` report 0.18.1, so the harness CLI and
  the app attach to the same daemon in `%APPDATA%\com.tincho.sandbox-mio\mutagen` without a
  mismatch.
- **Seeding mechanics: cleared, with a refinement.** `mutagen forward create` with *local* tcp
  endpoints on both sides (`tcp:127.0.0.1:<port>` → `tcp:127.0.0.1:1`) creates the session
  instantly and non-interactively — no SSH alias needed at all, safer than the planned
  unresolvable-alias approach. Also learned: `forward list <name>` for a missing session echoes
  the name in its error (`did not match any sessions`), so absence must be asserted on that
  phrase, not on the name being absent from the output.
- **Switcher-handle clickability: cleared by the first green run.** `agent-web.spec.ts` step 4
  clicks the synthetic Agents tab through the `main-switcher` window handle with no prior
  `switch_pane` and the pane appears — no `hide()` hang, as predicted. The `openAgentWeb` helper
  in `e2e/lib/workspace.ts` remains available as the fallback drive point.

One deliberate deviation in `agent-web.spec.ts` step 6: the PID-changed assertion is dropped, not
merely "if flaky". The `open_agent_web` exists-guard short-circuits to `switch_pane` while the
pane is alive, so `prepare_agent_web_pane` (and its daemon restart) never runs on re-open — a
PID-set change is impossible by construction. The step keeps the switch-not-duplicate,
password-stability, and authenticated-200 assertions, and additionally asserts the `serverId` is
unchanged across the re-open.

The original risk table, kept for the fallback column:

| Risk | How to clear | Fallback if it fails |
|---|---|---|
| The `main-switcher` webview's window handle accepts clicks (no `hide()` hang — the switcher is never hidden) | Open a workspace in `tauri dev` under wdio, switch to the `/workspace/switcher` handle, click the Agents tab | Drive step 4 via `openAgentWeb` invoke; tab DOM stays untested (test concern, not feature fix) |
| The vendored `tools/mutagen.exe` (v0.18.1) can create sessions in the app daemon's data directory without a version conflict with the app's sidecar mutagen | Run `mutagen forward create` with `MUTAGEN_DATA_DIRECTORY` set, then launch the app and check both see the session | Match the vendored version to the sidecar's, or seed by launching the app once, killing it, and relaunching (slower; test concern) |
| Unauthenticated `GET /api/status` behaviour (public per `02_dev.md`, so no 401 assertion is planned) | curl the published port without a Bearer header | None needed — the spec only asserts the authenticated 200 |

## Sequencing

1. Run the three e2e-side spike checks above by hand; settle the step-4 drive point.
2. Add the `e2e/lib/workspace.ts` and `e2e/lib/mutagen.ts` helper changes and the switcher page
   object.
3. Write and stabilize `agent-web.spec.ts` (the primary regression guard).
4. Add the `beforeSession` seeding and `forward-sweep.spec.ts`.
5. Run the full standard suite once — the seeded orphans must not disturb the other specs, and
   `web-terminal.spec.ts` must still pass with the sweep active (its forwards are created
   post-startup, so no interaction is expected).

## Environment notes

- Machines: only `mio-tests` (local connection) is needed; the remote machine provisioned for
  `deploy-remote.spec.ts` is not used by either spec.
- Base image: `BASE_IMAGE_VERSION` is now 3. `ensureMiseBaseImage` in `onPrepare` rebuilds it;
  any sandbox created from image version 2 lacks `procps` and the 6767 publish and must be
  re-created, never reused, for these specs.
- Network: the first Agents open downloads node@lts (~30 MB) and `@getpaseo/cli` from npm inside
  the container; the suite ceiling of 900000 ms budgets for it. The paseo npm version is not
  pinned by the feature — a paseo release that changes `/api/status` or the localStorage schema
  will surface here first (see Gotchas).
- The app's private Mutagen data directory is
  `%APPDATA%\com.tincho.sandbox-mio\mutagen`; every mutagen CLI call in specs and harness must
  set `MUTAGEN_DATA_DIRECTORY` to it (the `forwardList` helper already does).

## Common Gotchas

| Gotcha | Cause | Fix |
|---|---|---|
| Step 1's port assertion finds no binding even though create succeeded | `podman port <name>` reports nothing for a created-but-not-started container under pasta networking | Read `podman inspect <name> --format '{{json (index .HostConfig.PortBindings "6767/tcp")}}'` instead of `podman port`, exactly as `web-terminal.spec.ts` does for 8082 |
| The Agents pane's `/api/status` fetch returns 200 in the spec, yet a human sees "Connection timed out" in the pane | The seeded `@paseo:daemon-registry` `serverId` mismatches the daemon's real one; the paseo client closes the authenticated connection after connect, which HTTP-level assertions cannot see | Treat the spec's 200 as necessary but not sufficient for the SPA; re-verify with the Playwright seeding technique from docs/features/agent-web-ui/02_dev.md Phase D before blaming the forward |
| `forwardList` returns empty for a session the app definitely created | The mutagen CLI queried the default user daemon, not the app's private one | Set `MUTAGEN_DATA_DIRECTORY` to `%APPDATA%\com.tincho.sandbox-mio\mutagen` on every mutagen invocation (`forwardList` in `e2e/lib/mutagen.ts` already does; new helpers must copy it) |
| `mutagen forward create` in `beforeSession` errors with a daemon version mismatch, or the app later fails to start its Mutagen daemon | The vendored `tools/mutagen.exe` version differs from the app's sidecar mutagen and both target the same data directory | Pin `MUTAGEN_VERSION` in `e2e/lib/mutagen.ts` to the sidecar's version (check `src-tauri` sidecar staging) before adding the seeding step |
| `open_agent_web` fails with `AgentWebUnavailable` mentioning `/api/status` when run with `MIO_MOCK_BACKEND=1` | `MockRuntime::prepare_agent_web` returns port 0 and `fetch_paseo_server_info` performs a real HTTP request, so the mock backend cannot complete the command | Expected — do not write a light-tier spec for the open path; the mock seam ends at `prepare_agent_web` |
| Clicking a button in a sandbox's dashboard/terminal pane hangs until the wdio timeout | The pane's webview is hidden via WebView2 `hide()`, which stops painting, so layout-dependent WebDriver operations stall | Invoke `switch_pane` for the target pane before switching to its window handle (`workspace-dashboard.page.ts` pattern); the `main-switcher` webview is never hidden, so switcher clicks do not need it |
| The first "Agents" open times out at the default 180000 ms mocha timeout | mise downloads node@lts plus `@getpaseo/cli` inside the container on the first open per workspace | Set `this.timeout(900000)` on the suite (a `function ()` describe, not an arrow), matching `agent-setup.spec.ts` |
| `ps aux` inside the container fails with `executable file not found` | The sandbox was created from base image version 2, which lacks `procps` | Destroy and re-create the sandbox on image version 3; `ensureMiseBaseImage` stages the rebuilt image but never migrates existing containers |

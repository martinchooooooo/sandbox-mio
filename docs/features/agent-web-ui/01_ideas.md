# Agent Web UI Ideas

This document covers the ideation for offering a browser-based UI for **OpenCode** and **Pi** (and, as a side effect of the chosen tool, **Claude Code** too) as an alternative to their terminal TUI, aimed at non-technical users who find a Zellij-hosted CLI agent intimidating. The chosen approach is **[Paseo](https://paseo.sh)** (`github.com/getpaseo/paseo`), a single self-hosted, open-source multi-provider agent orchestrator that launches each provider's native CLI as a subprocess and exposes one web UI for all of them — this **supersedes** the document's earlier per-agent plan (a bespoke `opencode web` pane plus a separately-wrapped `jmfederico/pi-web` pane), which is kept below as rejected/fallback material because Paseo was spiked and found to subsume both with one tool, one published port, and one pane, rather than two. **Nothing described here is built yet.** It builds on three already-implemented seams: the static agent catalogue (`src/lib/agents/catalogue.ts`), the on-demand web-server-in-container pattern (`prepare_terminal_webview`, `src-tauri/src/lib.rs:109-194`, and `RuntimeManager::prepare_terminal`, `src-tauri/src/runtime/mod.rs:203-230`), and the `AppKind`-driven pane/switcher machinery (`src-tauri/src/workspace/`).

## Current State

Three agents are catalogued today, all TUI-only (`src/lib/agents/catalogue.ts`): `claude-code` (OAuth `auth`), `opencode` and `pi` (config-only `provision`, pre-wired to the app's local-LLM inference server over a fixed reverse Mutagen forward at `http://host.containers.internal:51199/v1`, per `docs/features/opencode-agent/02_dev.md` and `docs/features/pi-agent/02_dev.md`). Every agent is run today by the user typing its CLI command inside the embedded Zellij terminal pane — there is no non-terminal way to drive any agent.

The embedded workspace (`src-tauri/src/workspace/`) is a bare multi-webview `Window` (label `main`) hosting a collapsible global panel (`main-global`), a switcher tab bar (`main-switcher`), and, per sandbox, up to two content child webviews distinguished by `AppKind` (`src-tauri/src/workspace/types.rs:25-28`): `Terminal` (a `WebviewUrl::External` child pointed at a Mutagen-forwarded loopback URL) and `Dashboard` (an internal `WebviewUrl::App` route, no forward). `AppKind` currently derives `Copy` and has exactly these two **unit** variants.

The Terminal pane's construction is the direct template for any new "external web app in a pane" surface. `prepare_terminal_webview` (`src-tauri/src/lib.rs:109-194`) does, in order: resolve the right Podman connection (local or remote), call `runtime.prepare_terminal` which itself (`src-tauri/src/runtime/mod.rs:203-230`) idempotently checks `zellij web --status` inside the container and only runs `zellij web --daemonize` if it isn't already running, then mints a one-time login token via `zellij web --create-token`; back in `lib.rs`, allocate an ephemeral Windows-loopback port, `sync::forward_create` a Mutagen forward from that port to the container's published Zellij port, and build an `initialization_script` that `POST`s `/command/login` with the token so the embedded webview never shows a manual login screen. This whole sequence runs **on-demand**, the first time a pane is opened — Zellij is baked into the image (`src-tauri/resources/Containerfile`) but is not started at container boot; there is no init system in the image (`CMD ["/bin/bash"]`, no systemd/`tini`).

Container ports are published one at a time today, hardcoded: `ZELLIJ_WEB_PORT = 8082` (`src-tauri/src/backends/mod.rs:48`) is the **only** port `--publish`ed at `podman create` time, for both local (`backends/mod.rs:335-340`) and remote (`:446-452`) container creation. Any second service that needs to be reached from the host needs its own published port, fixed at container-creation time — a sandbox created before this feature ships would not have it published and would need to be recreated.

## Proposed Model

### One pane, one tool, one port: embed Paseo's web UI instead of per-agent panes

Paseo replaces the earlier "one pane per agent" plan with **one pane for all catalogued agents**: a single new `AppKind::AgentWeb` (or similarly named) unit variant, embedded exactly the way `embed_terminal` embeds Zellij (`src-tauri/src/workspace/mod.rs:135-194`) — a content child webview with `WebviewUrl::External(forwarded_loopback_url)`, shown/hidden via `switch_pane` alongside Terminal and Dashboard. Because `AppKind` currently has only unit variants and derives `Copy`, one variant for "the Paseo pane" (not one per agent) keeps that derive intact — this is a direct structural win over the earlier per-agent-pane plan, which needed either N unit variants or a payload that broke `Copy`. The switcher (`src/routes/workspace/switcher/+page.svelte`) grows at most one more tab per sandbox: Terminal / Manage / Agents, where "Agents" is Paseo's own UI — and Paseo's UI has its **own** internal session/tab switching between providers (OpenCode, Pi, Claude Code, …), so this app's switcher does not need to grow further as more providers are added.

### Paseo daemon: started on-demand, self-supervising (mirrors the Zellij pattern, with one improvement)

Paseo is started inside the sandbox container the same way Zellij is — on-demand, the first time the "Agents" tab is opened, via `podman exec -d ... paseo daemon start --foreground --listen 0.0.0.0:<FIXED_PASEO_PORT> --web-ui --hostnames true`, with `PASEO_PASSWORD` set from a per-sandbox-generated secret (mirroring Zellij's per-open token). Unlike Zellij (a single process) or the earlier pi-web plan (two processes, `sessiond` + `server`, requiring manual sequencing), Paseo's `daemon start` itself forks a **supervisor process** that automatically restarts the daemon child if it crashes (confirmed in the spike: `ps` showed `Paseo Supervisor` (PID N) and `Paseo Daemon` (PID N+1) as two separate processes) — so this app's own code does not need to implement crash-restart logic, only the initial idempotent start-if-not-running check `prepare_terminal_webview`'s pattern already establishes for Zellij.

### Catalogue-agnostic: no per-agent `webUi` descriptor needed

Because Paseo auto-discovers every provider CLI already on `PATH` (`paseo provider ls` listed `opencode` and `pi` as `available` immediately after they were `mise use`-installed, no Paseo-side configuration), this feature needs **no** new field on `AgentDescriptor` (`src/lib/agents/types.ts`) analogous to the earlier plan's `webUi?: {...}`. Opening the "Agents" pane is a per-*sandbox* action, not a per-*agent* one — one Paseo pane surfaces whichever agents are installed in that sandbox, automatically, the moment they're `mise install`ed. `AgentManager.svelte`/the dashboard pane needs only a single sandbox-level "Open Agents UI" action, not a per-agent-row action.

### Auth: `PASEO_PASSWORD`, but the browser login flow is not yet scriptable (open risk, carried over)

Paseo requires a password for any non-Basic-Auth network exposure (`authRequired: true` in the daemon's own startup log once `PASEO_PASSWORD` is set) and the web client authenticates over `Authorization: Bearer <token>` (confirmed by grepping the minified web bundle for `Authorization=`Bearer ${t}``), not HTTP Basic Auth and not a session cookie — so Zellij's exact `/command/login` cookie-POST trick does not transfer directly. The spike did not find the password→token exchange endpoint or the client-side storage key the bundle reads on boot (a quick guess — a `?password=` query param or a raw `Authorization: Bearer <password>` header — both returned non-2xx). Until that is reverse-engineered, the embedded pane would show Paseo's own login screen once, which is a materially worse but not disqualifying UX regression relative to Zellij's silent auto-login (see Open Questions).

### Port publishing: one more fixed `--publish`, not one per agent

`ZELLIJ_WEB_PORT` (`src-tauri/src/backends/mod.rs:48`) gains exactly **one** sibling constant, e.g. `PASEO_WEB_PORT`, with its own `--publish 127.0.0.1::<port>` argument at container creation (`backends/mod.rs:335-340`, `:446-452`) — not two or three, because Paseo serves every provider's UI (and its own API/WebSocket) on the single port it binds (`6767` by default, confirmed reachable through the exact `pasta:--host-lo-to-ns-lo` bridge Zellij already uses). As with `ZELLIJ_WEB_PORT`, this only takes effect for sandboxes created (or explicitly re-created) after the feature ships.

## Technology Choices with Tradeoffs

### Web UI tool: Paseo (chosen, spiked 2026-07-02) — supersedes the per-agent plan below

Chosen: [Paseo](https://paseo.sh) (`getpaseo/paseo`, AGPL-3.0, ~9.6k GitHub stars) — a self-hosted daemon that launches installed provider CLIs (Claude Code, Codex, Copilot, OpenCode, Pi, and others) as subprocesses and serves one web UI for all of them, on one port, with password-gated network access built in. It directly supersedes both halves of this document's original plan (an `opencode web` pane plus a separately-wrapped `jmfederico/pi-web` pane, kept below as "Superseded material" because their evidence is still useful if Paseo's remaining risk — see Open Questions — doesn't pan out):

- **One tool covers OpenCode, Pi, and Claude Code at once** — versus maintaining two (or three) separately-integrated web-UI tools, each with its own install quirks, port, and pane. This is a direct simplification of both the Rust pane-embedding surface (`AppKind` needs one new variant, not N) and the container image (one new dependency chain, not two).
- **Auto-discovers already-`mise`-installed provider binaries** — versus the earlier plan's per-agent `webUi` catalogue field, which would have needed a start command, a status-check command, and a container port hand-written per agent.
- **Confirmed to spawn the real provider CLIs, honouring existing provisioning** — `paseo provider ls` listed the `mise`-installed `opencode` and `pi` binaries by resolved path/version with no Paseo-side config, and the local-LLM provider config already written by `provision_pi`/`provision_opencode` (`docs/features/pi-agent/02_dev.md`, `docs/features/opencode-agent/02_dev.md`) is picked up unchanged by the bare CLI in the same environment Paseo spawns from (see Validation) — this is the same property that made `jmfederico/pi-web` attractive, now gained for OpenCode too at no extra integration cost.
- **Self-supervising process, no systemd needed, and a smaller base-image cost than `pi-web`** — the spike found Paseo's bundled `node-pty` ships a working Linux x64 **prebuilt** binary (`prebuilds/linux-x64/pty.node`), so — unlike `jmfederico/pi-web`'s older `node-pty` version — no C/C++ toolchain needs to be added to the base image at all. The only new base-image dependency the spike found was `procps` (for the `ps` binary Paseo's own `daemon status`/`stop` commands shell out to).

Rejected/deferred alternative — **`gh` (GitHub CLI) as a hard prerequisite**: Paseo's docs state a provider needs to be "installed and configured with your credentials" and separately mention `gh` for GitHub-integrated features; the spike found the daemon starts and lists `opencode`/`pi` as available providers with `gh` **absent** from the container, so this is not a blocking dependency for the core "open a web UI and chat with an agent" use case — only PR-related features (untested) may need it later.

### Superseded material: the original per-agent plan (kept for its evidence, not the chosen path)

The original plan before Paseo was evaluated:

- **OpenCode web pane: `opencode web --hostname 0.0.0.0 --port <n>`.** OpenCode's own built-in web server — no alternative was seriously considered here because OpenCode ships and maintains this UI itself. Superseded because Paseo already drives OpenCode with no separate integration work.
- **Pi web pane: `jmfederico/pi-web` (spiked and cleared 2026-07-02, see history below).** Chosen over `Epsilondelta-ai/pi-web` (unconfirmed `pi`-CLI integration, its own generic multi-backend OAuth model) and the official `@mariozechner/pi-web-ui` components (a component library requiring a from-scratch server, and its reference "Direct Mode" example calls provider APIs directly from the browser — incompatible with this app's container-side provisioning model). The spike proved `pi-web-sessiond`/`pi-web-server` run standalone with no systemd, are reachable through the publish/pasta/forward chain, and honour the pre-provisioned `models.json`. Superseded by Paseo, which needed neither a C/C++ toolchain nor a two-process sequencing dance, and additionally covers OpenCode and Claude Code in the same tool.
- **Two published ports (one per agent) and a payload-breaking `AppKind` variant** — both structural costs the per-agent plan required are avoided entirely by Paseo's one-port, one-`AppKind`-variant shape.

This material is retained because if Paseo's remaining login-automation risk (Open Questions) turns out to be a dead end, `jmfederico/pi-web` plus `opencode web` remain a validated fallback — the spikes for both are already run and recorded (see Validation).

### Pane embedding mechanism: reuse the proven external-webview-plus-forward pattern (chosen, unchanged)

Chosen because it is the exact mechanism the Terminal pane already proves end-to-end (spiked 2026-07-01 per `docs/features/embedded-windows/01_ideas.md`), needing no new native-API risk. `<iframe>` was rejected for the same `X-Frame-Options` reasoning already established for Zellij; a new standalone `WebviewWindow` was rejected as contradicting the "workspace is a hub" direction `docs/features/responsive-panel/01_ideas.md` established. Neither reconsideration changes with Paseo as the embedded tool.

### Startup timing: on-demand, mirroring Zellij (chosen, unchanged)

Chosen because it is the existing precedent and keeps sandboxes that never open the Agents pane free of the extra process. Paseo's self-supervising daemon (see Proposed Model) makes this easier than the per-agent plan, not harder: one `podman exec -d` call, not a sequenced pair.

## Validation

Two spikes were run by hand on 2026-07-02 against throwaway containers built from the sandbox base image (`localhost/sandbox-mio/base:2`) on `podman-machine-default`: one for `jmfederico/pi-web` (the superseded per-agent plan) and one for Paseo (the chosen plan). Both cleared their central systemd/reachability risks. **Neither spike attempted the browser login-automation flow** (Zellij's `/command/login`-equivalent) for either OpenCode's `OPENCODE_SERVER_PASSWORD` or Paseo's `PASEO_PASSWORD` — this remains the single largest open risk for either path (see Open Questions).

### Spike: Paseo without systemd, auto-discovering `mise`-installed providers (2026-07-02, cleared)

Each risk and the command/finding that cleared it:

- **`npm install -g @getpaseo/cli` needs no C/C++ toolchain.** Unlike `jmfederico/pi-web`, the install completed cleanly on the bare base image (only `procps` was later found missing, see below) — `node-pty@1.2.0-beta.11`'s Linux x64 **prebuilt** binary (`node_modules/node-pty/prebuilds/linux-x64/pty.node`) is used as-is; `npm`'s `allow-scripts` gate only left `node-pty`'s own install/postinstall scripts pending (irrelevant, since the prebuilt binary needs no build step), and — unlike `pi-web` — Paseo's own `bin` entries (`paseo`) were executable immediately after install with no manual `chmod`.
- **`paseo provider ls` auto-discovers `mise`-installed agents with zero Paseo-side configuration.** After `mise use -g node@lts opencode pi`, `paseo provider ls` listed `opencode` (resolved to `/root/.local/share/mise/installs/opencode/latest/opencode`, version `1.17.12`) and `pi` as `available`/`Enabled` with no config file written.
- **`paseo daemon start` needs explicit flags to bind non-locally and serve the bundled web UI; the defaults are `127.0.0.1`-only and no-UI.** `PASEO_PASSWORD=... paseo daemon start --foreground` alone bound `127.0.0.1:6767` and logged `"Daemon web UI disabled or missing dist directory"`. Adding `--listen 0.0.0.0:6767 --web-ui --hostnames true` produced `"Server listening on http://0.0.0.0:6767"` and `"Daemon web UI mounted"`. `02_dev.md` must use all three flags, not just a port override.
- **`paseo daemon status`/`stop` shell out to the `ps` binary, which the base image lacks.** `paseo daemon stop` crashed with `Error: spawn ps ENOENT`. Installing `procps` via `apt-get` (not currently in `src-tauri/resources/Containerfile`) fixed it — this app's own start/stop logic can avoid the problem by tracking the PID itself (as it already does for other podman-exec'd background processes) rather than shelling out to `paseo daemon stop`, but `procps` should be added regardless since Paseo's own tooling expects it.
- **Paseo self-supervises: a `Paseo Supervisor` process automatically restarts a crashed `Paseo Daemon` child.** Confirmed via `/proc/<pid>/cmdline` inspection showing two distinct processes (`Paseo Supervisor`, `Paseo Daemon`) after a single `paseo daemon start`; killing the daemon child (`kill -9`) resulted in "another Paseo daemon is already running" on a subsequent `start` attempt, i.e. the supervisor had already restarted it. This means this app's own code needs no crash-restart loop for Paseo, only an idempotent "is it already listening" check before starting.
- **Reachable end-to-end through the app's existing publish/pasta/forward chain.** A container was created with the exact flags the app already uses for Zellij (`--network pasta:--host-lo-to-ns-lo --publish 127.0.0.1::6767`), the daemon bound `0.0.0.0:6767` inside it, and `curl http://127.0.0.1:<published-port>/` **from the Windows host** (outside any container) returned `HTTP 200` with the Paseo SPA shell — no new network mechanism needed beyond one more published port.
- **`gh` is not a hard startup requirement.** The daemon started, mounted its web UI, and listed `opencode`/`pi` as available providers with `gh` absent from the container (`which gh` failed) — contradicts an initial documentation-only read that flagged `gh` as required; downgraded to "needed only for GitHub-integrated features, unconfirmed which," not a blocker.
- **The spawned-agent environment honours existing local-LLM provisioning.** A `models.json` and `mise.toml [env] PI_CODING_AGENT_DIR` were written in the exact shape `provision_pi` (`docs/features/pi-agent/02_dev.md` Phase C) produces; `pi --offline --list-models`, run mise-activated in that same workspace directory (the same directory/shell shape Paseo's daemon was started from), printed `local-llm  phi-4-mini-reasoning  128K  16.4K …`. **Caveat, not fully closed**: the daemon in this spike was started *before* the provisioning files were written, so this confirms the *bare CLI* picks up the config in that environment, but does not directly prove a Paseo-spawned agent subprocess (started via `paseo run --provider pi ...` *after* the daemon was already running) inherits the same `mise`-activated environment — whether Paseo's daemon needs to be (re)started *after* `mise.toml [env]` is provisioned, or whether it re-resolves the environment per spawned agent, is an open follow-up (see Open Questions).
- **The login/auth flow is Bearer-token-based, not cookie- or Basic-Auth-based, and the exact exchange was not found.** Grepping the minified web UI bundle (`_expo/static/js/web/index-*.js`) found `Authorization=`Bearer ${t}`` construction, ruling out a Zellij-style cookie POST or a static Basic-Auth header. Guessed shortcuts (`?password=` query param on API calls, `Authorization: Bearer <raw password>`) both failed (`401`/`404`). The real password→token exchange endpoint was not located within the spike's time budget.

Both throwaway containers were removed after the spike.

### Spike: `jmfederico/pi-web` without systemd (2026-07-02, cleared — superseded material, kept for the fallback path)

Each risk and the command that cleared it:

- **The base image lacks a Python/C++ toolchain `node-pty` (a `pi-web` dependency) needs to build.** `npm install -g @jmfederico/pi-web` failed with `node-gyp` unable to find Python; installing `python3 make g++` let the install succeed. Unlike Paseo's newer `node-pty`, `pi-web`'s pinned `node-pty@1.1.0` has no matching prebuilt binary and falls back to compiling.
- **npm's `allow-scripts` gate leaves the package's own bin files non-executable.** `chmod +x` on `dist/cli.js`, `dist/server/index.js`, `dist/server/sessiond.js` (the package's own `bin` entries) fixed `Permission denied` failures.
- **`pi-web`'s own CLI source documents a manual, non-systemd run path** (`manualRunAdvice()` in `dist/cli.js`: `npm run start:sessiond` / `PI_WEB_PORT=8504 npm start`), corresponding to the packaged bin entries `pi-web-sessiond`/`pi-web-server`.
- **`pi-web-sessiond` and `pi-web-server`, started directly via `podman exec -d`, both start and stay up**, reachable end-to-end through the same publish/pasta/forward chain (`curl` from the Windows host → `HTTP 200`), and the wrapped process is confirmed to be the real `earendil-works/pi` agent (bundles `@earendil-works/pi-coding-agent`/`pi-ai` directly), honouring the pre-provisioned `models.json` (`pi --offline --list-models` showed the `local-llm` provider).

Both throwaway containers and the intermediate commit image were removed after the spike.

### Cleared by research (2026-07-02):

- **OpenCode ships a built-in web UI.** `opencode web` starts a local server on `127.0.0.1` with a random port by default; `--hostname 0.0.0.0` and `--port <n>` control binding; `OPENCODE_SERVER_PASSWORD`/`OPENCODE_SERVER_USERNAME` gate network-exposed instances. Source: <https://opencode.ai/docs/web/>. Superseded as the chosen path by Paseo (which drives OpenCode too), but this remains the fallback if Paseo is abandoned.
- **Paseo is open source, self-hostable, and multi-provider.** AGPL-3.0, `github.com/getpaseo/paseo`, ~9.6k stars; supports Claude Code, Codex, Copilot, OpenCode, Pi, and more as "providers," launching each one's native CLI as a subprocess rather than reimplementing agent behavior; ships a CLI (`npm install -g @getpaseo/cli`), a desktop app, and a Docker image (`ghcr.io/getpaseo/paseo`). Sources: <https://paseo.sh>, <https://github.com/getpaseo/paseo>, <https://paseo.sh/docs>. This is the evidence for evaluating and then spiking Paseo as a unifying alternative to per-agent tools.
- **Pi's CLI has no built-in web mode.** No `pi web`/`pi serve` subcommand exists in the `earendil-works/pi` monorepo's documented packages. Source: <https://github.com/earendil-works/pi>.
- **`jmfederico/pi-web` wraps the `pi` CLI as a subprocess in real workspaces; documented deployment is per-user systemd services.** Sources: <https://github.com/jmfederico/pi-web>, <https://github.com/jmfederico/pi-web/blob/main/AGENTS.md>, <https://pi.dev/packages/@jmfederico/pi-web>.
- **The base sandbox image has no init system.** `src-tauri/resources/Containerfile` ends with `CMD ["/bin/bash"]`, no systemd/`tini`; Zellij's own web server is started on-demand via a direct `podman exec ... zellij web --daemonize`. This is the in-repo evidence that motivated both the `pi-web` and Paseo systemd-avoidance spikes.

## Open Questions

- **The Paseo browser login flow is unscripted.** **Resolved 2026-07-03, see `02_dev.md` Phase D.**
  The premise of this question was wrong: there is no password→token exchange endpoint, because the
  client sends the raw password as `Authorization: Bearer <password>` on every request
  (`paseo.sh/docs/security`, not available to the original 2026-07-02 spike). The real mechanism was
  client-side persistence — a `@paseo:daemon-registry` localStorage entry the web bundle reads on
  boot — found by grepping the minified bundle pulled directly off a real running sandbox's
  published port, then confirmed with a throwaway Playwright/Chromium script (no Tauri app needed).
  Seeding that key via `initialization_script` fully auto-logs in; verified screenshot-to-screenshot
  against the same sandbox this question was originally raised against.
- **Whether Paseo's spawned agent subprocesses inherit `mise`-activated environment variables (e.g. `PI_CODING_AGENT_DIR`) written *after* the daemon started.** The spike confirmed the *bare* `pi` CLI honours the provisioned config in the same directory/shell shape Paseo spawns from, but did not confirm this through an actual `paseo run --provider pi ...` call made after `mise.toml [env]` provisioning. If Paseo caches its spawn environment from daemon-start time, `02_dev.md` needs to either (re)start the Paseo daemon after `provision_pi`/`provision_opencode` run, or restart it whenever provisioning changes — mirroring the sequencing constraint already documented for `pi-web`.
- **Fixed port literal and `AppKind` variant name.** Which container port to reserve for Paseo (`6767` by default, avoiding collision with `ZELLIJ_WEB_PORT` 8082), and what to name the new `AppKind` unit variant (`AgentWeb`? `Agents`? `Paseo`, which couples the UI to naming a specific third-party tool?).
- **Local-only or remote too?** The Terminal pane already supports remote-deployed sandboxes; the local-LLM inference server OpenCode/Pi are pre-wired to is explicitly local-only in `docs/features/opencode-agent/02_dev.md`/`pi-agent/02_dev.md` v1. Paseo itself has no such restriction (it just launches whatever provider CLI is installed, with whatever credentials/config that CLI already has), so a remote sandbox's Paseo pane would work for Claude Code (OAuth-authenticated, not local-LLM-dependent) even if OpenCode/Pi's local-LLM backing is unreachable there.
- **Does "Open Agents UI" replace or sit alongside "Open Terminal"?** Whether both access paths remain available per sandbox, or the Paseo pane becomes the primary/only entry point for non-technical users while power users keep using the terminal, is undecided.
- **`procps` and any other Paseo-expected CLI tools as new base-image dependencies.** Beyond `procps` (confirmed needed for `paseo daemon status`/`stop`), whether Paseo's other features (voice/speech background model downloads were observed starting automatically on daemon boot, worktree management, `gh`-dependent features) pull in further base-image dependencies this app doesn't want baked into every sandbox is unconfirmed — worth a flag/config check for disabling speech-model auto-download in a headless sandbox context.
- **Fallback commitment point.** Given both the Paseo spike and the `jmfederico/pi-web`+`opencode web` spike are cleared, `02_dev.md` should decide up front how much effort to spend on the Paseo login-automation open question before falling back to the superseded per-agent plan, rather than discovering the difficulty mid-build.

## Common Gotchas

| Gotcha | Cause | Fix |
|---|---|---|
| A newly created sandbox has no "Open Agents UI" tab even after this feature ships | Container ports are `--publish`ed only at `podman create` time (`src-tauri/src/backends/mod.rs:335-340`); existing containers never gain a newly added published port | Sandboxes created before this feature ships need to be re-created (destroy + recreate) to pick up the new `--publish` argument |
| `paseo daemon start` binds `127.0.0.1` and shows no web UI even though the process started fine | The defaults are loopback-only with the bundled UI disabled; `--listen`/`--web-ui` are opt-in flags (confirmed 2026-07-02) | Always pass `--listen 0.0.0.0:<port> --web-ui --hostnames true` explicitly |
| `paseo daemon stop`/`status` crashes with `spawn ps ENOENT` | The base image has no `procps` package (confirmed 2026-07-02) | Add `procps` to `src-tauri/resources/Containerfile`'s `apt-get install` line, or avoid calling `paseo daemon stop`/`status` and track the PID directly the way other podman-exec'd background processes already are |
| A second `paseo daemon start` fails with "another Paseo daemon is already running" even after `kill -9`-ing the process you saw | Paseo runs a self-restarting supervisor process (`Paseo Supervisor`) in addition to the daemon child (`Paseo Daemon`); killing only the child gets it respawned | Check `paseo daemon status`/kill both the supervisor and daemon PIDs, or (simpler) always do an idempotent status check before attempting a start, mirroring `zellij web --status` |
| The embedded Paseo pane shows a login form instead of auto-logging in | Paseo's web client authenticates over `Authorization: Bearer <token>`, not a cookie set by a scriptable POST like Zellij's `/command/login` | **Resolved, see `02_dev.md` Phase D**: seed the client's own `@paseo:daemon-registry` localStorage entry (host + password) via `initialization_script` before the SPA boots — do not port Zellij's cookie-POST script unchanged, the mechanism is different |

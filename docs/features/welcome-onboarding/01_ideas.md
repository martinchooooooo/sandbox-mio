# Welcome / Onboarding Screen

This document covers replacing the app's current landing content — a leftover Tauri-scaffold "enter a name and greet" form — with a hero-and-onboarding flow modeled on the Dribbble reference [Onboarding flow and loader](https://dribbble.com/shots/25383666-Onboarding-flow-and-loader): a big animated "Sandbox mio" hero (the word "mio" cycling through translations — "Mine", "Meins", "Мой" — per the CSS technique in [this CodePen](https://codepen.io/orchard/pen/LoNdQZ)), followed by a welcome step that tells the user a short setup is coming, then a step with two bare-bones actions — "Create virtual machine" and "Download necessities" — framed as the start of a guided tour. Nothing in this pipeline is implemented yet: the landing route (`src/routes/+page.svelte`) is still the scaffold form, and `src/routes/intro/+page.svelte` is a stub that renders only the existing `Robot.svelte` mascot animation with no onboarding copy, steps, or actions. The relevant frontend files are `src/routes/+page.svelte` (current landing content), `src/routes/intro/+page.svelte` and `src/lib/Robot.svelte` (existing but unused-for-onboarding stub and mascot), `src/lib/components/GlobalNav.svelte` (already has a `/intro` nav entry), and `src/routes/projects/+page.svelte` (the existing, unrelated-but-adjacent Podman machine first-run gate this feature must not collide with). The relevant backend files are `src-tauri/src/lib.rs` (`create_sandbox`, `provision_podman`, `machine_needs_init`, `ensure_base_image` access) and `src-tauri/src/settings/mod.rs` (`AppSettings` persistence, the natural home for any new "onboarding seen" flag).

## Current State

**Landing route is the Tauri scaffold.** `src/routes/+page.svelte` is the literal `create-tauri-app` template: an `<Input>` bound to `name`, a "Greet" button that calls `invoke("greet", { name })` (`src-tauri/src/lib.rs:37-40`), and the result printed below. This is what the user sees first, because the app's single content webview (`main-navigation-panel`, `src-tauri/src/workspace/mod.rs:73-74`) is created with `tauri::WebviewUrl::App(Default::default())`, which resolves to the frontend's root route — `src/routes/+page.svelte` is not a leftover nobody navigates to, it is the actual first screen every launch shows.

**`/intro` exists but is an unwired stub.** `src/routes/intro/+page.svelte` renders only `<Robot bind:this={robot} />` inside a `<main>` with no text, no buttons, and no logic — `robot` is bound but never called. `Robot.svelte` (`src/lib/Robot.svelte`) is a hand-built SVG robot mascot animated with `gsap` (already a project dependency, `package.json:22`, version `3.15.0`): `onMount` starts continuous idle tweens (float, arm swing, screen scanline/bar flicker) on `#robot-full`, `#arm-left`, `#arm-right`, `#screen-scanline`, `#screen-bars`; it exports `stop()` and `startBlinking()` as imperative controls a parent can call via the bound instance. `GlobalNav.svelte:7-13` already lists `{ href: "/intro", label: m.nav_intro }` as the first tab, ahead of Projects/Models/Settings, so `/intro` is reachable today from every route's nav bar, showing only the idle-animated robot with no accompanying screen.

**No first-run or onboarding-completion flag exists anywhere.** `AppSettings` (`src-tauri/src/settings/types.rs:15-21`) — the only app-global persisted state, at `<app_config>/settings.json` via `load`/`save` in `src-tauris/src/settings/mod.rs:21-31` — has fields only for the inference engine and its advanced tuning knobs; nothing tracks whether a user has seen or completed onboarding. A repo-wide search for `first_run`, `onboard`, `has_seen`, and `welcome` (case-insensitive) turns up no code, only feature docs discussing unrelated concerns and locale/translation strings.

**A different, unrelated first-run gate already exists on `/projects`.** `src/routes/projects/+page.svelte:98-120` probes `check_podman_ready` on mount; on a `PodmanUnavailable` error it calls `machine_needs_init` to distinguish "Podman machine never created" from "just stopped," then shows a `podmanNeedsSetup` screen whose button drives `provision_podman` (WSL2 install + `podman machine init` + start, with a `PodmanRebootRequired` branch prompting a Windows restart). This is the app's actual "create the underlying VM" flow already, gated on Podman's own state rather than any app-level "have I onboarded" flag, and it lives entirely inside `/projects`, decoupled from `/` and `/intro`. This feature's proposed "Create virtual machine" button (see Proposed Model) necessarily talks about this same Podman machine, since it is the only "virtual machine" concept in the codebase — there is no second, sandbox-level VM.

**Base image build ("download necessities") is currently a side effect, not a standalone action.** `ensure_base_image` (trait method on `SandboxBackend`, `src-tauri/src/backends/types.rs:128`, implemented at `src-tauri/src/backends/mod.rs:397`) builds `sandbox-mio/base:<BASE_IMAGE_VERSION>` (`mod.rs:20,26`) from the bundled Containerfile, short-circuiting if that exact tagged image already exists. Today it is only invoked from inside `create_sandbox` (`src-tauri/src/lib.rs:67-80`, `store.ensure_base_image().await?` at line 76) — there is no Tauri command that runs it on its own. A "Download necessities" button that builds the base image ahead of creating any sandbox needs either a new thin command wrapping `ensure_base_image` directly, or must silently create a throwaway sandbox to trigger it (rejected in Technology Choices below).

**Locale keys for the current landing page exist and will need replacing.** `messages/en.json` (and mirrored `de.json`, `ru.json`) currently define `home_title`, `greet_label`, `greet_placeholder`, `greet_button` for the scaffold form, and `nav_intro` for the existing nav tab label — all three locale files stay in sync today and must keep doing so per the root `AGENTS.md` i18n rule for every new key this feature adds.

## Proposed Model

### Hero step: cycling "mio" translations (new component, e.g. `src/lib/welcome/MioHero.svelte`)

A large "Sandbox mio" headline where the word "mio" itself cycles through translations of "mine" — Italian "mio", English "Mine", German "Meins", Russian "Мой" are the concrete examples the user gave — using the CSS approach demonstrated in the CodePen reference: a stack of absolutely-positioned words cross-fading/translating in and out on a timed loop, not a JS-driven text-replacement that would flash unstyled content. Given `gsap` is already a dependency and already drives `Robot.svelte`'s idle animation, this hero timeline is a `gsap.timeline({ repeat: -1 })` cycling opacity/translateY across a fixed list of `{ word, lang }` entries, mirroring the existing animation idiom in `Robot.svelte` rather than introducing a second animation library or hand-rolled `@keyframes` for a second, inconsistent technique. The robot mascot (`Robot.svelte`) is a natural companion visual here since it already exists and already has `startBlinking()` as a distinct animation mode — this document treats reusing it in the hero as likely but not decided (see Open Questions).

### Step sequence and container (new component, e.g. `src/routes/+page.svelte` rewritten around `src/lib/welcome/WelcomeFlow.svelte`)

A single local `$state<"hero" | "welcome" | "actions">` (or equivalent step enum) drives which of three panels is visible, matching the Dribbble reference's progression: (1) the hero from above, dismissed by a "Get started" affordance or auto-advancing after its loop plays a fixed number of times; (2) a welcome panel — short copy naming the app and stating that a brief setup follows; (3) an actions panel with the two buttons the user specified. This is component-local `$state`, not a module-scoped store, because per `src/AGENTS.md`'s rune-store convention, module-scoped stores exist specifically for state that must survive navigation across routes — this flow is a single route's internal step machine and does not need to survive being left, so it can reset cleanly if the user navigates away mid-flow. Per-step visuals and copy are still undecided in detail (see Open Questions); this document fixes only the three-step shape and that step 3 is where the two named actions live.

### "Create virtual machine" action (reuses `machine_needs_init` / `provision_podman`, both already implemented, extracted into a shared module)

This button cannot mean anything else in the current codebase but "provision the Podman machine" — the app has exactly one VM concept, the one `/projects`' existing gate already provisions via `provision_podman` (`src-tauri/src/lib.rs`, invoked at `projects/+page.svelte:144`). Resolved 2026-07-08: rather than duplicating `projects/+page.svelte`'s `check_podman_ready` → `machine_needs_init` → `provision_podman` → `PodmanRebootRequired` state machine (lines 98-156) a second time in the welcome flow, that logic is extracted into a shared module — e.g. `src/lib/podman/setup.svelte.ts`, following the module-scoped-store convention in `src/AGENTS.md` — exposing the gate state (`podmanUnavailable`, `podmanNeedsSetup`, `podmanRebootRequired`, `setupBusy`/`setupError`) and the `startPodman`/`setupPodman` actions as accessor functions. Both `/projects` and the welcome flow import this module instead of either screen owning its own copy; `/projects` is refactored to consume it as part of this feature rather than left with a second, drifting implementation.

### "Download necessities" action (needs one new thin command wrapping `ensure_base_image`, auto-chains the VM check)

This button drives a new Tauri command — e.g. `ensure_base_image_standalone` or renaming intent aside, a command that does nothing but call `store.ensure_base_image().await?` (the same call `create_sandbox` already makes at `src-tauri/src/lib.rs:76`) without also creating a sandbox. Resolved 2026-07-08: the button auto-chains rather than requiring the user to click "Create virtual machine" first — its click handler calls the same shared `src/lib/podman/setup.svelte.ts` gate described above to ensure the machine is up (running `provision_podman` transparently if `machine_needs_init` says it has never been created, or `start_podman_machine` if it's just stopped) and only then invokes the base-image command, surfacing whichever step is currently running in one continuous busy state rather than exposing "first do X, then Y" as two user-visible clicks. The command reuses the existing `SandboxBackend::ensure_base_image` trait method and its existing build-lock serialization (`backends/types.rs:209`); the button's busy state follows the same `createActionRunner` (`src/lib/actions.svelte.ts`) pattern used elsewhere in the app (e.g. `CreateSandboxItem.svelte:18,41-51`) for a `<StatusRow>`-style busy/error display across both the (possibly auto-triggered) VM step and the image build itself, not a bare disabled-button spinner.

### Guided-journey framing (copy-only, no new seam)

The user's requirement to "tell the user we're going to go on a guided journey of what this is" is copy on the welcome panel (step 2 above) plus, optionally, copy on the actions panel framing the two buttons as the first two stops of that journey — this document treats it as content for the welcome-panel step rather than a new mechanic, since no further guided-tour steps beyond "create VM" and "download necessities" are in scope yet (see Open Questions on whether more onboarding steps follow later).

### `/intro` repurposed as a post-onboarding "replay the tour" entry (resolved, changes existing route)

Resolved 2026-07-08: `/intro`'s current content (the bare `Robot.svelte` mascot with no copy) is replaced, not deleted — it becomes the route a user lands on if they explicitly replay the welcome flow after onboarding is already complete (see the last Open Question below on whether that replay entry point exists at all in v1). `GlobalNav.svelte:7-13`'s existing `{ href: "/intro", label: m.nav_intro }` entry stays, now pointing at a rerun of the same `WelcomeFlow.svelte` component the first-run experience at `/` uses, rather than two independently-maintained mascot screens.

### Nav chrome hidden during onboarding (resolved, changes `+layout.svelte`)

Resolved 2026-07-08: `src/routes/+layout.svelte` gains a condition — reading the same `onboarding_completed` flag this feature adds — that skips rendering `NavigationColumn`/`GlobalNav` while onboarding is incomplete, so the welcome flow shows full-bleed with no Projects/Models/Settings tabs a user could click away to mid-setup, matching the Dribbble reference's chrome-free presentation. This condition is checked once at layout mount, the same point `isNavigationPanel` is already resolved (`+layout.svelte:87-99`), and does not apply to the `/intro` replay route, which is reached only after onboarding is already complete and chrome is already showing.

### Gating: when the welcome flow shows vs. when the app goes straight to the existing content (needs a new persisted flag)

Since no onboarding-completion state exists anywhere today, this feature adds a field to `AppSettings` (`src-tauri/src/settings/types.rs:15-21`), e.g. `onboarding_completed: bool` (defaulting `false` via the struct's existing `#[serde(default)]`), set `true` once the user completes or explicitly dismisses the flow, and persisted through the existing `settings::save`/`settings::load` (`src-tauri/src/settings/mod.rs:21-31`) — no new persistence mechanism, reusing the one app-global settings file that already exists. `src/routes/+page.svelte` reads this flag on mount (via a new or existing settings-fetching command) and renders the welcome flow when it is `false`; once `true`, `/` shows the post-onboarding home screen described next, not a redirect.

### Post-onboarding home screen at `/` (resolved, new minimal content)

Resolved 2026-07-08: once `onboarding_completed` is `true`, `/` does not redirect to `/projects` — it shows a small, separate "get started with your first sandbox" screen (headline plus a short line of copy) with a link/button to `/projects`. This is deliberately not the `/projects` sandbox list itself; `/` stays a distinct, minimal landing screen whose only job post-onboarding is to point the user at the real work surface. `GlobalNav`/`NavigationColumn` chrome is showing at this point (onboarding is complete, per the nav-chrome resolution above), so the `/projects` tab is also reachable from the nav bar — the `/` link is a redundant, friendlier entry point for someone who lands on `/` directly (e.g. after a relaunch) rather than the only way to reach `/projects`.

### Debug affordance: restart-the-flow button (resolved, new small control)

Resolved 2026-07-08: a small button pinned to the bottom-left corner of `/` (both pre- and post-onboarding) resets `onboarding_completed` to `false` (via a settings-write call) and re-renders the welcome flow from its first step, for manual testing/debugging rather than as a discoverable end-user feature. It is explicitly out of scope for this button to also reset the underlying Podman machine or base image — it only replays the screens; the "Create virtual machine"/"Download necessities" actions inside the replayed flow behave exactly as the `/intro` replay does (see below), showing already-done state rather than re-running provisioning. Being a debug affordance, this control does not need Paraglide translation the way user-facing copy does (see Open Questions on whether it ships in production builds at all).

## Technology Choices with Tradeoffs

### Hero animation: `gsap` timeline (chosen) vs. pure CSS `@keyframes` (per the CodePen reference) vs. a new animation library

Chosen: a `gsap.timeline()` in the new hero component, matching `Robot.svelte`'s existing idiom.

- **Pure CSS `@keyframes`, as the CodePen reference itself uses** — rejected: it would introduce a second, inconsistent animation technique alongside `Robot.svelte`'s existing `gsap`-driven tweens for what is, in the finished screen, one composed animated scene (mascot plus cycling headline); keeping both on `gsap` means one timeline can eventually sequence the mascot and the headline together if a later revision wants them synchronized, which two independent animation systems cannot do as cleanly.
- **A dedicated text-cycling library (e.g. a headline-rotator package)** — rejected: `gsap` already both a dependency and already performs opacity/transform tweening for `Robot.svelte`; a same-shape animation (cross-fading a short list of strings) does not need a second package for what `gsap.timeline({ repeat: -1 })` already does.

### Onboarding-completion flag: new `AppSettings` field (chosen) vs. a per-workspace marker file vs. deriving "onboarded" from "has any sandbox"

Chosen: `onboarding_completed: bool` on `AppSettings`, persisted at the existing `<app_config>/settings.json`.

- **A marker file, mirroring the per-workspace `.mio/dismissed_image_version` pattern (`src-tauri/src/lib.rs:48-59`)** — rejected: that pattern is scoped to a workspace path and exists because different sandboxes can independently dismiss different image-version prompts; onboarding is a single, app-global, one-time event with no per-workspace variation, so it belongs with the other single app-global flag store (`AppSettings`), not duplicated as a bespoke file the settings module does not know about.
- **Deriving "already onboarded" from whether `list_sandboxes` returns anything** — rejected: it conflates two different signals. A user could delete every sandbox they've created (or start on a fresh machine after reinstalling with settings intact) without wanting to see the full hero-and-explanation flow again; an explicit flag says "has this user seen the tour," while sandbox count says "does any sandbox currently exist," and the two can diverge in either direction.

### "Create virtual machine" driving code: extract a shared `src/lib/podman/setup.svelte.ts` module (chosen) vs. a second, independent Podman-setup implementation vs. leaving the logic wherever it lands first with no extraction

Chosen, resolved 2026-07-08: extract `projects/+page.svelte`'s existing Podman first-run/start/provision state machine into a shared module both `/projects` and the welcome flow import, refactoring `/projects` to consume it as part of this feature.

- **A second, welcome-flow-local reimplementation of the Podman first-run check and provisioning call** — rejected outright: `provision_podman`'s WSL2-install-then-restart-required branching (`podmanRebootRequired` in `projects/+page.svelte:139-156`) is exactly the kind of state machine that must not exist in two divergent copies; any bug fix or Windows-version edge case handled in one copy would silently not apply to the other.
- **Duplicate the same `invoke()` calls in the welcome flow for now, unify later** — rejected: it is a smaller diff today but reintroduces the exact two-copies-diverge risk the extraction is meant to prevent, for a codebase that already has one working implementation to lift out rather than write fresh; deferring the unification has no clear trigger to ever come back to it.

### "Download necessities": new standalone command wrapping `ensure_base_image`, auto-chaining the VM check (chosen) vs. silently creating a throwaway sandbox to trigger the existing side-effect path vs. requiring the VM step to be clicked first

Chosen: a new thin Tauri command that calls only `store.ensure_base_image()`.

- **Silently calling `create_sandbox` with a hidden/disposable name just to reach its `ensure_base_image()` call** — rejected: it would create a real sandbox (workspace directory, `runtime.init` call at `src-tauri/src/lib.rs:78`) as a side effect of a button whose entire stated purpose is "prepare the base image, not a project," leaving either a stray sandbox the user never asked for or requiring an immediate follow-up deletion call that has its own failure modes; a direct one-method wrapper command has neither problem and is a smaller diff than either alternative.
- **Require "Create virtual machine" to be clicked and succeed before "Download necessities" is enabled** — rejected in favor of auto-chaining: it is the more literal reading of two separate buttons, but for a "bare bones" first cut it forces an extra click and an extra wait screen for something the download action can trigger transparently itself; auto-chaining keeps the two actions conceptually distinct (two buttons, two things they name) while collapsing the common case (neither has run yet) into one click.

## Validation

No spike has been run. This is a frontend-and-copy-heavy feature composed almost entirely of already-proven pieces — `gsap` timelines already animate `Robot.svelte` in production, `provision_podman`/`machine_needs_init` already run today's real first-run Podman setup on `/projects`, and `ensure_base_image` already runs today inside `create_sandbox` — so the main unvalidated risk is not any single technology but the sequencing/gating logic (Open Questions below), which is cheap to prove by building it directly rather than spiking it first.

## Open Questions

- **Where does the shared "create virtual machine" logic live?** Resolved 2026-07-08: extracted into a shared `src/lib/podman/setup.svelte.ts` module imported by both `/projects` and the welcome flow, with `/projects` refactored onto it as part of this feature — see Proposed Model and Technology Choices above.
- **Does `/` stay the welcome flow's home, or does the flow move to `/intro`?** Resolved 2026-07-08: the first-run flow lives at `/`; `/intro` is repurposed (not deleted) as a post-onboarding "replay the tour" entry reusing the same `WelcomeFlow.svelte` component — see Proposed Model.
- **Does the welcome flow show with or without the persistent nav chrome?** Resolved 2026-07-08: `+layout.svelte` hides `NavigationColumn`/`GlobalNav` while `onboarding_completed` is false, so the first-run flow is full-bleed; the `/intro` replay route is unaffected since it is only reachable once onboarding is already complete and chrome is already showing — see Proposed Model.
- **Re-entry: can a user replay the welcome flow after finishing it?** Resolved 2026-07-08, implied by the `/intro`-as-replay decision above: yes, via the existing `GlobalNav` `/intro` tab, which stays present post-onboarding specifically for this purpose. Resolved 2026-07-08 (second pass): the replay must show each action's *actual current state* (machine already provisioned, image already built) rather than re-presenting "not started" — the "Create virtual machine"/"Download necessities" step components read the same live status each already needs to check before acting (`machine_needs_init`/Podman-ready state, and image-presence — `ensure_base_image`'s own short-circuit-on-existing-tag check per `backends/mod.rs`) and render a completed/disabled state when that check says the work is already done, instead of blindly showing the pre-onboarding "not yet done" button. This avoids a user re-triggering `provision_podman` or a full Podman build from a screen that was only meant to be a walkthrough.
- **What does `/` show once onboarding is complete?** Resolved 2026-07-08: a small "get started with your first sandbox" screen with a link to `/projects`, not a redirect — see Proposed Model.
- **Does the debug restart-the-flow button ship in production builds, or only dev/debug builds?** The button (bottom-left corner of `/`, resets `onboarding_completed` and replays the flow) is explicitly described as a debugging aid, not a discoverable end-user feature; whether it is gated behind a dev-only build flag/env var, hidden behind a settings toggle, or simply always present (small and out of the way, akin to how other debug affordances in the app are or aren't gated) is undecided.
- **Auto-advance vs. explicit dismissal for the hero step.** Whether the cycling-translations hero advances to the welcome panel automatically after a fixed number of loop cycles, or waits for an explicit "Get started"-style click, is undecided.
- **Full translation list for the "mio" word.** The user's examples (Italian "mio", English "Mine", German "Meins", Russian "Мой") happen to match the three locales `messages/` already ships (`en`, `de`, `ru`) plus the base word itself; whether the cycling list is fixed to exactly those, includes additional languages purely for the visual effect (not tied to app locale support), or is dynamically drawn from `messages/`'s supported-locale list, is undecided.
- **Does "Download necessities" show progress detail or just busy/done?** `ensure_base_image` runs a multi-step Podman build, and the auto-chained VM-provisioning step (resolved above) adds a second phase before it; whether the button surfaces step-level detail across both phases (the way `provision_sandbox_host`'s guided flow streams progress over a `Channel`, per `docs/features/cloud-sandboxes/01_ideas.md`) or a single busy spinner via `createActionRunner` covering the whole chain is undecided — the backend command as scoped above returns a bare `Result<(), AppError>` with no progress channel, which would need revisiting if step-level detail is wanted.

## Common Gotchas

| Gotcha | Cause | Fix |
|---|---|---|
| New welcome screen builds fine but the app still shows the old "greet" scaffold on launch | The main webview loads `WebviewUrl::App(Default::default())` (`src-tauri/src/workspace/mod.rs:73-74`), which resolves to `src/routes/+page.svelte` specifically — replacing a different route has no effect on first launch | Confirm the new flow's entry point is `src/routes/+page.svelte` itself (or that `/` redirects there) before assuming a different route change reaches the user |
| `onboarding_completed` flag added to `AppSettings` but old settings files show it as onboarding-incomplete for existing users | `AppSettings` derives `#[serde(default)]` (`src-tauri/src/settings/types.rs:14`), so a field absent from an on-disk `settings.json` written before this feature deserializes to `false` | This is likely the desired behavior for existing users who never saw the new flow, but confirm intent before shipping — an existing user with sandboxes already created re-seeing a "let's set up your VM" flow may be confusing without copy that adapts to that case |
| Hero animation janks or never starts on first mount | `gsap` timelines targeting selector strings (as `Robot.svelte` does, e.g. `gsap.to("#robot-full", ...)`) must run after the target elements exist in the DOM | Start the timeline inside `onMount`, matching `Robot.svelte`'s existing pattern, not at module scope or before the component's markup renders |
| `/projects` and the welcome flow disagree about whether the Podman machine is set up | `src/lib/podman/setup.svelte.ts` was only partially extracted — one of the two screens still holds its own local copy of `podmanUnavailable`/`podmanNeedsSetup` state instead of reading the shared module | Confirm both `/projects` and the welcome flow read the same module-scoped state per the extraction resolved in Proposed Model, not two independent `$state` copies |
| "Download necessities" button never becomes available, or errors with an unrelated sandbox-creation failure | If the "reuse `create_sandbox`" alternative is used instead of the chosen new standalone command, any validation `create_sandbox` performs (name collisions, workspace path handling) can fail unrelated to base-image building | Implement the new thin `ensure_base_image`-only command as scoped in Proposed Model rather than reusing `create_sandbox` for this button |
| "Download necessities" fails immediately with a Podman-unavailable error instead of provisioning the machine first | The auto-chain step (calling into `src/lib/podman/setup.svelte.ts` before `ensure_base_image_standalone`) was skipped, and the button calls the base-image command directly | Wire the button through the shared Podman-setup module first, per the auto-chain decision in Proposed Model, before calling the base-image command |
| Replaying the tour from `/intro` (or via the debug restart button) shows "Create virtual machine"/"Download necessities" as not-yet-done even though both already succeeded | The replay path renders the same initial/unstarted step UI as first-run instead of checking current machine/image state before rendering | Check `machine_needs_init`/Podman-ready state and image presence before rendering each action step, per the resolved replay-state behavior in Open Questions, and show a completed state when the check says the work is already done |
| Debug restart button resets `onboarding_completed` but the Podman machine/base image get re-provisioned anyway | The restart button is only supposed to replay the screens, not touch the underlying machine or image | Confirm the restart button only flips `onboarding_completed` back to `false` and does not call `provision_podman`/`ensure_base_image` itself; the replayed flow's own already-done checks (above) are what prevent redundant work |
| A locale file shows English text on the new welcome screen in `de`/`ru` | A new message key was added to `messages/en.json` only | Mirror every new key into `messages/de.json` and `messages/ru.json` in the same change, per the root `AGENTS.md` i18n rule |

# Microsandbox Provider — E2E Test Plan

Test plan for the microsandbox provider built in `docs/features/microsandbox-provider/02_dev.md`
(Phases E–J). A de-risking spike was run on 2026-08-14 and is recorded below: the spike found and
fixed a transport defect that made the feature completely non-functional, and confirmed one blocker
that must be cleared before the primary spec can be written. Read `e2e/AGENTS.md` for the tier
taxonomy before changing any tier decision recorded here.

## Goal

Prove, through the real application, that creating a sandbox on the microsandbox provider produces a
sandbox whose workspace actually synchronises with the laptop directory. The spec must exercise this
chain end to end:

- The `create_sandbox` Tauri command (`src-tauri/src/lib.rs`) with `provider = Microsandbox`.
- `PodmanCliBackend::create` (`src-tauri/src/backends/mod.rs`) dispatching to `MsbProvider`
  (`src-tauri/src/provider/msb.rs`) against the real `msb` binary.
- `install_sandbox_key` (`src-tauri/src/backends/mod.rs`) writing the sandbox keypair into the guest
  through `MsbProvider::copy_in`, which spawns a real `msb exec` with piped stdin.
- `ensure_msb_sandbox_alias` (`src-tauri/src/backends/mod.rs`) writing the `ProxyCommand` block into
  `~/.ssh/sandbox-mio/config`.
- `MutagenCli::create` (`src-tauri/src/sync/mod.rs`) driving the bundled Mutagen sidecar, which
  installs its remote agent into the guest over a real `ssh`/`scp` connection through the alias.

The last step is the reason the spec must exist. Mutagen's agent installation runs `scp`, which
speaks the SFTP protocol on OpenSSH 9 and later, and is the only consumer in the whole feature that
needs the guest SSH server to answer a `subsystem sftp` request.

**What weaker coverage fails to catch.** `e2e/test/specs/light/microsandbox-provider-ui.spec.ts` runs
under `MIO_MOCK_BACKEND=1`, where every `msb` call lands on `ScriptedMsbRunner`
(`src-tauri/src/mockctl/types.rs`). No guest exists, so there is no SSH server, no sftp subsystem, no
`scp`, and no Mutagen agent. The 2026-08-14 spike found the shipped `ProxyCommand` pointed at a
server that silently drops `subsystem sftp`, which made every microsandbox sandbox creation fail —
while `cargo check`, `cargo test --lib`, and all 12 light specs stayed green. Unit tests on the
`ProxyCommand` string (`msb_proxy_command_tunnels_to_the_image_sshd` in
`src-tauri/src/backends/mod.rs`) pin the transport choice but cannot prove the chosen transport
works. Only a real sync against a real guest has teeth.

## Chosen approach

**Tier: `standard`.** Spec path: `e2e/test/specs/standard/microsandbox-workspace-sync.spec.ts`.
Topology: one microsandbox sandbox created through the projects page on the local host, with no
remote target (microsandbox has no remote-target capability — `ProviderCapabilities.remote_targets`
is false in `src-tauri/src/provider/msb.rs`).

`standard` is correct rather than merely preferred here: the defect class the spec exists to catch
lives entirely in real infrastructure that `light` replaces with a mock. Choosing `standard` means
the run takes the host lock described in `e2e/AGENTS.md` and serialises against every other
real-infra run on the machine, which is the intended cost.

`heavy` is not warranted: no large asset is downloaded, no model or engine is loaded, and no remote
deploy is chained. The base image reaches the microsandbox store through `podman save` piped into
`msb load` (`MsbProvider::ensure_base_image`), which is a local transfer of an image the `standard`
tier already builds.

### Prerequisites a future session must satisfy

- **A real `msb` binary**, resolved through `MSB_PATH`. `e2e/lib/run-identity.ts` already defines
  `MSB_HOME` (slug-keyed, isolating microsandbox's own database, sandboxes, cache and logs per
  worktree) and `MSB_PATH` (the host-wide executable path), and `e2e/wdio.conf.ts` exports both at
  module scope. No harness change is needed for `msb` isolation.
- **The `mio-tests` Podman machine**, because `MsbProvider::ensure_base_image` builds the base image
  with Podman before handing the archive to `msb load`. A microsandbox spec therefore still depends
  on Podman provisioning.
- **Windows Hypervisor Platform**, which microsandbox requires and which no harness code provisions.
- **Cleanup of both halves of a sandbox.** `msb rm --force <name>` leaves the workspace volume
  behind unless `msb volume rm <name>-ws` also runs; `MachineProvider::remove` does both, so
  destroying through the UI is sufficient, but a spec that fails midway leaks a volume that blocks
  the next create of the same name (`MsbProvider::ensure_volume` tolerates the leftover, so the leak
  degrades rather than breaks).

### Step 0 — the job-object blocker (cleared)

`msb create` launches its detached VM supervisor with `CREATE_BREAKAWAY_FROM_JOB`. If any Windows
Job Object above the calling process lacks `JOB_OBJECT_LIMIT_BREAKAWAY_OK`, that launch fails and
`msb create` exits with `error: io error: Access is denied. (os error 5)`.

Two jobs denied breakaway under the e2e harness, each fixed separately:

- **`tauri-driver`'s own job.** `tauri-driver` (2.0.6, unchanged through 3.0.0-alpha.1) puts itself
  and every descendant in a kill-on-close job with no configuration switch. `e2e/wdio.conf.ts`
  therefore spawns `tools/msedgedriver.exe` directly in `spawnDriver`, sends `msedgedriver`'s native
  WebView2 capabilities, sets `TAURI_WEBVIEW_AUTOMATION`, and kills the driver's whole process tree
  at teardown in place of the job's reaping.
- **`build.rs`'s `win_job`.** `./build e2e` runs the harness inside this kill-on-close job.
  `win_job::setup` now also grants `JOB_OBJECT_LIMIT_BREAKAWAY_OK`: explicit, not silent, breakaway,
  so only the microsandbox supervisor leaves the job and a `build.exe` crash still reaps everything
  else.

`tauri dev` remains blocked by `cargo run`'s job; `./build dev` avoids that job through
`run_dev_directly`. `docs/features/microsandbox-provider/spike/job-object-probe.ps1` reproduces the
failure with a bare job object.

## Spec scenario

Each step names the driven action and the assertion. State is read back through the `msb` CLI and
the filesystem, mirroring `e2e/test/specs/standard/workspace-mount.spec.ts`, which proves the Podman
bind mount is live by writing a host file and reading it inside the container.

1. **Open the projects page and select the provider.** `ProjectsPage.open`, then
   `ProjectsPage.chooseProvider("microsandbox")` (`e2e/test/pageobjects/projects.page.ts`). Assert
   the create row offers the microsandbox option, which gates every later step.
2. **Create the sandbox.** `ProjectsPage.createProject(name)`. Assert the row reaches running.
   Derive `name` from `Date.now()` as the existing specs do.
3. **Assert the host workspace directory exists**, resolved from `WORKSPACE_ROOT`
   (`e2e/lib/run-identity.ts`, mirrored to the application as `SANDBOX_WORKSPACE_ROOT` by
   `e2e/wdio.conf.ts`), never from a rebuilt `%APPDATA%` or fixed `$HOME` path.
4. **Assert the SSH alias block is correct.** Read the block with `sshAliasBlock(name)`
   (`e2e/lib/ssh.ts`). Assert the `ProxyCommand` execs `mio-sshd`, and assert it does **not** contain
   `ssh serve` — the exact regression that broke the feature on 2026-08-14.
5. **Assert the Mutagen session reaches a connected state.** Session name is `workspace-<name>`
   (`backends::msb_sync_session` in `src-tauri/src/backends/mod.rs`), deliberately distinct from the
   bare `<name>` a deploy uses. Poll within the `SYNC_CONVERGE` budget (`e2e/lib/timeouts.ts`) until
   status leaves the connecting state; assert the reached status is a watching/connected one. A
   session that exists but never connects is exactly the shipped-broken state, so asserting mere
   existence is insufficient. **A helper must be added**: `e2e/lib/mutagen.ts` exports `syncCreate`,
   `syncFlush` and `syncTerminate` but no status reader, so the spec needs a new session-status
   export there (or a `sync_status` command call through the app).
6. **Prove data crosses the sync.** Write a marker file into the host workspace directory, flush the
   session with `syncFlush` (`e2e/lib/mutagen.ts`), then read the marker back inside the guest with
   `msb exec <name> -- cat /root/work/marker.txt`. Read back through `msb exec`, **not** over SSH, so
   the assertion does not depend on the transport under test.
7. **Assert the Mutagen agent is outside the synced tree.** Assert the guest has `/root/.mutagen`
   and that the guest's `/root/work` contains no `.mutagen-agent*` entry. Absence is a safe
   assertion here specifically because the guest was created by this run — the parallel-worktree
   rule against absence assertions concerns pre-existing host state, not a freshly created guest.
   The old transport logged in at `/root/work` and left a partial agent copy there, which the sync
   then propagated back onto the laptop.
8. **Smoke-test the transport directly.** Assert `ssh <alias> true` and an `scp` of a temporary file
   to `<alias>:/tmp/` both exit 0, both invoked with `-F` against the managed config and
   `-o BatchMode=yes`. The `scp` assertion is the sharpest guard in the spec: it fails with an
   obvious message at the exact operation that broke, rather than as an opaque Mutagen error chain.
9. **Destroy through the UI and assert both halves are gone.** Assert `msb ls` no longer lists the
   sandbox and that the workspace volume `<name>-ws` no longer appears in `msb volume ls`.

### Secondary spec: logging reaches the log file

`e2e/test/specs/light/` should gain an assertion that the app's log file under `APP_DATA_ROOT`
(`e2e/lib/run-identity.ts`) is non-empty after startup. Not microsandbox-specific, but recorded here
because the 2026-08-14 spike lost a full diagnostic cycle to silently dead file logging: the
`tauri-plugin-devtools` plugin claimed the global tracing subscriber, `init_logging`'s own
initialisation failed, and the failure was discarded. `light` is the right tier — the assertion is
about process startup, not infrastructure.

## De-risking spike results — 2026-08-14

Spike artefacts live in `docs/features/microsandbox-provider/spike/`. The spike ran against real
`msb` 0.6.6 on the development host.

### Risks cleared

| Risk | Cleared by | Result |
|---|---|---|
| Guest reachable over the sandbox alias at all | `ssh -F ~/.ssh/sandbox-mio/config <name> "echo; id"` | Exit 0 — reachability was never the problem |
| Mutagen's agent install works over the alias | `scp -F ~/.ssh/sandbox-mio/config <file> <name>:/tmp/x` | **Exit 1** against `msb ssh serve`; exit 0 with `scp -O` (legacy protocol), isolating the failure to the SFTP subsystem |
| Base image carries an sshd with an sftp subsystem | Reading `/etc/ssh/sshd_config.container` in the guest | `Subsystem sftp /usr/lib/openssh/sftp-server` already present, and `mio-sshd` already in the image — microsandbox boots the same base image Podman does |
| `msb exec --stream` can carry an SSH session | `ssh`/`scp` with `ProxyCommand msb exec --stream <name> -- mio-sshd` | Both exit 0 — the fix adopted in `02_dev.md` Resolved Decision 8 |
| A full sync session survives creation | `mutagen sync create` + `sync flush` against the fixed alias | `Copying agent… Installing agent… Created session`, then status `Watching for changes`, and a host file appeared at the guest's `/root/work` |
| Agent lands outside the synced tree | Listing `/root` and `/root/work` in the guest | Agent in `/root/.mutagen`; no `.mutagen-agent*` in `/root/work` |

The `scp` result was the defect: microsandbox's own SSH server answers exec and pty channels but
silently drops `subsystem sftp`, so `ssh` worked while Mutagen's agent install failed. The fix landed
in `ensure_msb_sandbox_alias` (`src-tauri/src/backends/mod.rs`) together with a switch from
`msb ssh authorize` to the provider-neutral `install_sandbox_key`, and is recorded in `02_dev.md`
Resolved Decision 8. Two sandboxes created through the app afterwards both reached
`Watching for changes` with files crossing the sync.

### Blocker: Windows Job Object membership — test concern, cleared by Step 0

Reproduced by `docs/features/microsandbox-provider/spike/job-object-probe.ps1`, which creates a bare
job object (no `JOB_OBJECT_LIMIT_BREAKAWAY_OK`), assigns its own process to the job object, and then
runs `MsbProvider::create_instance`'s exact argv.

- Inside the job object: exit 1, verbatim `error: io error: Access is denied. (os error 5)`.
- Outside any job object, identical argv: exit 0.

Classified as a **test concern**, not a feature fix: no packaged build runs inside a job object, and
`./build dev` already bypasses the problem via `run_dev_directly` (`build.rs`). The blocker affects
only how the e2e harness launches the application. Step 0 records the two jobs responsible and the
fix.

A control run with a bare `msb create <image> --name <n>` — omitting the workspace volume — fails
outside the job object too, with `invalid config: workdir does not exist in guest: /root/work`. Any
future probe must use the full argv including `--mount-named`, or the comparison is meaningless.

## Common Gotchas

| Gotcha | Cause | Fix |
|---|---|---|
| `error: io error: Access is denied. (os error 5)` from `msb create` during an e2e run | A job object above the application denies breakaway, so microsandbox's detached VM supervisor cannot start: `tauri-driver`'s own job, or `win_job`'s job (`build.rs`) without `JOB_OBJECT_LIMIT_BREAKAWAY_OK` | Keep `tauri-driver` out of the chain (`spawnDriver` in `e2e/wdio.conf.ts`) and keep `JOB_OBJECT_LIMIT_BREAKAWAY_OK` in `win_job::setup`; see Step 0 |
| `unable to connect to beta: ... unable to install agent: unable to copy agent binary: unable to run SCP process: exit status 1` while `ssh <alias> <cmd>` works | The sandbox alias tunnels to microsandbox's own `msb ssh serve` server, which drops `subsystem sftp`; Mutagen installs its agent with `scp`, which speaks SFTP on OpenSSH 9+ | Keep `ensure_msb_sandbox_alias` (`src-tauri/src/backends/mod.rs`) pointed at `msb exec --stream <name> -- mio-sshd`; spec step 4 asserts the `ProxyCommand`, step 8 asserts `scp` itself |
| A microsandbox change passes every light spec and unit test while the feature is entirely broken | `ScriptedMsbRunner` (`src-tauri/src/mockctl/types.rs`) has no guest, so no SSH server, sftp subsystem, `scp`, or Mutagen agent is exercised under `MIO_MOCK_BACKEND=1` | Require `standard`-tier coverage for any change to the microsandbox transport, key install, or sync wiring; treat light specs as gating-logic coverage only |
| A microsandbox e2e spec passes under `pnpm exec wdio run` but fails from `./build e2e` | `./build e2e` adds `win_job`'s job object above the harness, while a direct wdio run does not | Confirm `win_job::setup` (`build.rs`) still grants `JOB_OBJECT_LIMIT_BREAKAWAY_OK`; `./build e2e` is the entry point the spec must pass under |
| A microsandbox sandbox created before 2026-08-14 fails SSH authentication after the transport fix | The sandbox was authorised with `msb ssh authorize`, which writes microsandbox's host-wide `authorized_keys`, not the `/etc/ssh/authorized_keys.container` the base image's `sshd_config.container` names | Destroy and recreate the sandbox; no migration path exists in `backends::create` (`src-tauri/src/backends/mod.rs`) |
| `msb create` fails with `invalid config: workdir does not exist in guest: /root/work` when run by hand | The workspace volume was not attached, so the guest has no `/root/work` for the configured working directory | Reproduce `MsbProvider::create_instance`'s full argv: `msb volume create <name>-ws --kind disk --size 20G` followed by `msb create <image> --name <name> --mount-named <name>-ws:/root/work:kind=disk,size=20G` |
| A creating-then-failing microsandbox spec leaves the next run failing on `volume already exists` | `msb rm --force` removes the sandbox record but not the workspace volume, and a spec that aborts midway never reaches the UI destroy step | Remove the leftover with `msb volume rm <name>-ws`; `MsbProvider::ensure_volume` (`src-tauri/src/provider/msb.rs`) tolerates a leftover volume, so the leak degrades rather than breaks |
| The application's log file is empty after an e2e run, hiding every backend event | `tauri-plugin-devtools` claims the global tracing subscriber before `init_logging` (`src-tauri/src/lib.rs`) runs, so the file layer is never installed | Leave `MIO_DEVTOOLS` unset, which keeps file logging active; `init_logging` now writes an explanatory line into the log file when its own initialisation loses the race |

# Microsandbox Provider

This document covers adding [microsandbox](https://github.com/superradcompany/microsandbox) — a libkrun-backed microVM runtime driven by an `msb` CLI — as a second machine provider alongside Podman, which today is the only way a sandbox process runs. The end state is coexistence: Podman remains the default and the only provider supporting remote deploys, while microsandbox becomes a user-selectable local provider needing no Podman machine and no WSL distribution. Reaching coexistence requires a refactor first, because "Podman" is not confined to one trait: `SandboxBackend` (`src-tauri/src/backends/types.rs`) is the only documented seam, but `PodmanMiseRuntime` (`src-tauri/src/runtime/mod.rs`), `MutagenNetworkManager` (`src-tauri/src/network/mod.rs`), `src-tauri/src/credentials/mod.rs`, and `src-tauri/src/agents/mod.rs` each shell out to `podman` directly, and `MachineManager` (`src-tauri/src/machine/types.rs`) is shaped entirely around `podman machine` and WSL.

A three-part spike was run on 2026-08-09 and its artefacts are the evidence base for every decision below: `spike/hands-on-cli.md` (execution against `msb` 0.6.6 installed on the Windows development host), `spike/cli-surface.md` (CLI documentation plus upstream source), and `spike/windows-and-state.md` (Windows host, state layout, networking, and the upstream issue tracker). The spike confirmed the feature is viable and disproved three assumptions in this document's first revision; the Validation section records what changed. Where a documentation-derived claim and an executed result conflict, the executed result is treated as authoritative and the conflict is recorded in the cross-check table in `spike/hands-on-cli.md`.

**Superseded by `docs/features/mutagen-transport/02_dev.md`.** This document's Proposed Model section "Published ports and in-guest services," and its Technology Choices entry of the same name, describe a publish-then-forward model for microsandbox ports (`msb create -p` explicit host-port allocation, forcing zellij/paseo onto `0.0.0.0`, the `loopback_publish`/`publish_after_create` capability flags). `mutagen-transport` implements a simpler alternative discovered after this document was written: since a microsandbox sandbox is reachable directly over its own SSH session (`msb ssh serve --stdio`), Mutagen can dial straight into the guest's loopback for any port with no publish step at all, keeping services on `127.0.0.1` exactly like Podman's convention. `mutagen-transport`'s Phases A–C have landed: `PortTransport`/`PodmanPortTransport` (`src-tauri/src/transport/`), the `SshAlias::Direct`/`Proxied` split (`src-tauri/src/ssh/types.rs`), and the unconstructed `SyncStrategy::Volume` variant (`src-tauri/src/backends/types.rs`) are real types today. `02_dev.md` for this feature should build `MsbProvider` against those concrete shapes rather than the publish-based design below; the sections mentioning the old design are left as-is here as the historical record of the rejected alternative, per this document's Validation/Technology-Choices convention of recording what changed and why.

## Current State

**The documented provider seam.** `SandboxBackend` (`src-tauri/src/backends/types.rs`) declares container lifecycle (`ensure_base_image`, `base_image_ready`, `create`, `list`, `start`, `stop`, `destroy`, `listen_events`), remote deploy (`deploy`, `remove_remote`), and Podman system-connection registry management (`list_hosts`, `add_host`, `prepare_host`, `provision_host`) on one trait. The sole implementation is `PodmanCliBackend`, constructed by `default_backend()` (`src-tauri/src/backends/mod.rs`) with an `Arc<dyn ProcessRunner>`. Three of the eleven methods are Podman-registry operations with no meaning outside Podman.

**Podman call sites that bypass `SandboxBackend`.** Four modules shell out to `podman` without going through any trait:

- `PodmanMiseRuntime` (`src-tauri/src/runtime/mod.rs`) builds `--connection <name> exec …` argv in `podman_on` (line 87) and invokes `crate::backends::podman_command()` (line 90) directly, not the `ProcessRunner`. Every `RuntimeManager` method reaches Podman through `podman_on`, plus `podman cp` in `seed_paseo_projects` (line 134) and `podman port` in `prepare_terminal`/`prepare_agent_web` (lines 278, 363).
- `MutagenNetworkManager` (`src-tauri/src/network/mod.rs`) has a module-private `podman()` free function (line 56) calling `Command::new("podman")` — the bare host binary, not the bundled one `podman_command()` resolves. Call sites: `podman exec … socat` in `expose_port` (line 230), `podman port` (line 238), `pkill` teardown (lines 192, 273), and `scan_listening_ports` (line 326).
- `src-tauri/src/credentials/mod.rs` runs six direct `Command::new("podman")` calls (lines 230, 238, 270, 281, 297, 304) for `tar_capture` and `tar_inject`, two using `podman exec -i` with piped stdin.
- `src-tauri/src/agents/mod.rs` runs two direct `Command::new("podman")` calls (lines 122, 129), the second an interactive `podman exec -i` auth session with piped stdin, stdout, and stderr.

**Machine lifecycle.** `MachineManager` (`src-tauri/src/machine/types.rs`) declares ten methods, of which `run_wsl_shutdown`, `wsl_is_ready`, `install_wsl`, `activate_podman_socket`, `init_machine`, and `reset_stuck_machine` have no microsandbox counterpart. `PodmanMachineManager` (`src-tauri/src/machine/mod.rs`) drives `podman machine list/start/init/rm`, `wsl --install/--shutdown/--unregister/--status`, and `podman machine ssh`. The frontend readiness gate lives in `src/lib/podman/setup.svelte.ts` and the first-run flow in `src/lib/welcome/CreateVmStep.svelte`.

**The `connection` string.** A bare `connection: &str` is the de-facto machine handle throughout the crate: `RuntimeManager::reproduce_remote`/`prepare_terminal`/`prepare_agent_web` (`src-tauri/src/runtime/types.rs`), `NetworkManager::open_forward`/`expose_port`/`watch_ports_file` (`src-tauri/src/network/types.rs`), `ForwardInfo.connection`, and `Deployment.host` on the frontend (`src/lib/sandbox.ts:16`). Nothing in the string identifies which tool interprets it.

**Base image.** `ensure_image_on` (`src-tauri/src/backends/mod.rs`) runs `podman build` against a temp context holding the `include_str!`-embedded `src-tauri/resources/Containerfile`, tagging `sandbox-mio/base:<BASE_IMAGE_VERSION>`. The image is never published to a registry. `parse_image_version` recovers the version from the `:N` tag suffix in `podman ps` output. `e2e/lib/podman-machine.ts` regex-parses `BASE_IMAGE`, `BASE_IMAGE_VERSION`, and `DEFAULT_MACHINE_NAME` out of `src-tauri/src/backends/mod.rs`.

**Port exposure.** `create` (`src-tauri/src/backends/mod.rs`) publishes `127.0.0.1::8082` (zellij), `127.0.0.1::6767` (paseo), and a fixed relay pool (`relay_pool_publish_args()` in `src-tauri/src/network/mod.rs`) at create time, because Podman cannot publish a new port without recreating the container. `NetworkManager::expose_port` bridges a user-chosen sandbox port to a pre-published pool slot with an in-container `socat`. Every published port lands on loopback inside the Podman machine, so a Mutagen forward (`forward_create` in `src-tauri/src/sync/mod.rs`) is required to reach it from Windows. The `--network pasta:--host-lo-to-ns-lo` flag is Podman-specific and load-bearing for loopback-bound in-container servers.

**Process seam and mock tier.** `ProcessRunner` (`src-tauri/src/mockctl/types.rs`) models a one-shot argv-to-`Output` call. `derive_podman_key` (`src-tauri/src/mockctl/mod.rs`) derives `podman.<subcommand>` keys, `KNOWN_CALLS` validates them, and `ScriptedPodmanRunner` keeps an in-memory container list emitting Podman-shaped `ps` JSON.

**E2E isolation.** Per `e2e/AGENTS.md`, `standard`/`heavy` runs take a host-wide lock because the `mio-tests` Podman machine and `~/.ssh` files cannot be split per worktree. Every per-worktree path derives from `RUN_SLUG` (`e2e/lib/run-identity.ts`).

## Proposed Model

### `MachineProvider`: the primitive seam every subsystem shares (new `src-tauri/src/provider/types.rs`)

A new trait declaring only the primitives every subsystem needs from a container or VM engine: `create_instance`, `start`, `stop`, `remove`, `list_instances`, `exec`, `exec_piped` (argv plus a stdin byte stream), `copy_in`, `published_host_port`, and `ensure_base_image`/`base_image_ready`. Two implementations: `PodmanProvider` (the extracted body of today's `PodmanCliBackend` plus the `podman_on` helper from `src-tauri/src/runtime/mod.rs`) and `MsbProvider` (driving `msb`).

`PodmanMiseRuntime` is renamed `MiseRuntime` and rewritten to hold `Arc<dyn MachineProvider>` instead of building `--connection` argv itself; `MutagenNetworkManager`, `src-tauri/src/credentials/mod.rs`, and `src-tauri/src/agents/mod.rs` each drop their direct `Command::new("podman")` calls. `SandboxBackend` keeps its shape as the Tauri-facing orchestration trait and delegates lifecycle to the provider, retaining the deploy and host-registry methods as Podman-only operations gated by capability flags.

### `ProviderCapabilities`: honest feature negotiation instead of runtime errors (`src-tauri/src/provider/types.rs`)

A struct returned by `MachineProvider::capabilities()`. The spike established that five capabilities genuinely differ between the two providers, so each is a field rather than an assumption:

- `remote_targets` — Podman true, microsandbox false.
- `publish_after_create` — false for **both**. `msb modify` has no port flag, so the relay-pool design is required for microsandbox exactly as for Podman.
- `loopback_publish` — Podman true (via `--network pasta:--host-lo-to-ns-lo`), microsandbox false. Microsandbox dials the guest's interface IP, so a guest server bound to `127.0.0.1` is unreachable from the host.
- `event_stream` — Podman true (`podman events`), microsandbox false (no equivalent command exists).
- `host_bind_mount` — Podman true, microsandbox false while upstream issues #1218 and #1219 are open. Implemented as a runtime probe rather than a constant, so the provider adopts bind mounts automatically once a future `msb` release fixes them.

Command handlers in `src-tauri/src/lib.rs` and the frontend consult capabilities to hide the deploy picker in `src/routes/projects/+page.svelte` for a microsandbox sandbox rather than letting `deploy_sandbox` fail at invoke time.

### `MachineRef`: replacing the untyped `connection` string (`src-tauri/src/provider/types.rs`)

A `MachineRef { provider: ProviderId, id: String }` where `ProviderId` is an enum of `Podman` and `Microsandbox`, serialised over IPC as a prefixed string (`podman:mio-tests`, `msb:local`) so `Deployment.host` (`src/lib/sandbox.ts`), `ForwardInfo.connection`, and any persisted `.mio/` state stay plain strings. Every signature currently taking `connection: &str` takes `&MachineRef` instead.

### Workspace transport: a disk-backed volume synced over SSH (`src-tauri/src/sync/mod.rs`)

The spike disproved the assumption that a microsandbox sandbox can bind-mount the host workspace at `/root/work`. Every read on a virtiofs mount returns correct bytes and then exits non-zero, and `statx` fails with `ELOOP` (see Validation). A microsandbox sandbox therefore holds its workspace on a `--kind disk` named volume (ext4 over virtio-blk), which the spike measured as returning exit code 0 for both reads and `stat`.

Host-to-guest file movement reuses the sync engine this project already operates for remote deploys: `MutagenCli` (`src-tauri/src/sync/mod.rs`) syncs the laptop workspace directory against the sandbox's disk volume over SSH, reaching the guest through `msb ssh serve --stdio` as an OpenSSH `ProxyCommand`. The host-side workspace stays exactly where it is today, under `workspace_root()` (`src-tauri/src/backends/mod.rs`), so host editors and the existing workspace-path plumbing are unaffected. `write_alias()` (`src-tauri/src/ssh/mod.rs`) already renders OpenSSH config blocks into `~/.ssh/sandbox-mio/config`; `SshAlias` (`src-tauri/src/ssh/types.rs`) gains a `ProxyCommand` variant alongside its `host`/`port`/`user`/`identity` fields.

### Base image via an imported archive (`src-tauri/resources/Containerfile`)

Podman keeps `podman build`. Microsandbox has no build command and — contrary to this document's first revision — no CLI path that consumes a snapshot at create time. `MsbProvider::ensure_base_image` therefore imports an archive: the recipe in `src-tauri/resources/Containerfile` is built once by Podman, exported with `podman save`, and imported with `msb load --input <tar> --tag sandbox-mio/base:<BASE_IMAGE_VERSION>`. The spike confirmed `msb load --tag` accepts that exact tag form and that `msb list --format json` reports the full tag back, so `parse_image_version` (`src-tauri/src/backends/mod.rs`) maps over unchanged.

The consequence is explicit and unavoidable in v1: producing the microsandbox base image requires a working Podman machine, so a microsandbox-only install cannot build its own base image. Registry publication removes that dependency and is argued under Technology Choices as the path out.

### Provider readiness replacing `MachineManager`'s Podman shape (`src-tauri/src/machine/types.rs`)

`MachineManager` narrows to a provider-neutral readiness contract — a `readiness()` probe, a `setup_steps()` descriptor list, and a `prepare(Channel)` action streaming per-step progress in the idiom `provision_host` already uses. Podman's implementation keeps today's WSL-install, machine-init, machine-start, and socket-activation steps behind the descriptor list. Microsandbox's implementation reports three steps: `msb` binary present, the `HypervisorPlatform` Windows optional feature enabled, and `msb doctor` clean. `src/lib/welcome/CreateVmStep.svelte` and `src/lib/podman/setup.svelte.ts` render the step list from the descriptor rather than hardcoding VM language.

### `msb` as a second scripted process (`src-tauri/src/mockctl/`)

`SystemMsbRunner` and `ScriptedMsbRunner` join the existing runner pairs, keyed `msb.<subcommand>` by a `derive_msb_key` sibling to `derive_podman_key`, with `KNOWN_CALLS` gaining the `msb.*` entries. `ScriptedMsbRunner` needs its own tracked-instance default emitting `msb ls --format json` shapes (four fields: `created_at`, `image`, `name`, `status`), because `ScriptedPodmanRunner::tracked_ps` emits Podman-shaped `ps` JSON. A new `MIO_MACHINE_PROVIDER` environment variable steers which provider an e2e run targets, and `MSB_HOME` plus `MSB_PATH` are set to `RUN_SLUG`-keyed paths for per-worktree isolation.

## Technology Choices with Tradeoffs

### Where the second provider plugs in: a new primitive `MachineProvider` trait (chosen) vs. a second `SandboxBackend` impl vs. an argv-translating `ProcessRunner`

Chosen: extract a primitive `MachineProvider` trait and re-express the five Podman-coupled modules on top of it.

- **A second `SandboxBackend` implementation and nothing else** — rejected: `SandboxBackend` covers container lifecycle only. A sandbox created through a microsandbox `SandboxBackend` would still have its packages installed, terminal started, ports exposed, credentials injected, and agent auth driven by the twelve `podman` call sites listed under Current State, producing a sandbox that exists but is unusable.
- **A translating `ProcessRunner` rewriting `podman` argv into `msb` argv** — rejected: the argv shapes diverge structurally. `--connection <name>` has no microsandbox equivalent, `podman build` has none at all, `podman port` has no counterpart (the spike confirmed microsandbox never reports a resolved ephemeral port), and `--network pasta:--host-lo-to-ns-lo` is meaningless outside Podman. Translation would also make every `podman.<subcommand>` key in `KNOWN_CALLS` a lie about which process ran.

### Driving microsandbox: the `msb` CLI (chosen) vs. the `microsandbox` Rust SDK crate

Chosen: shell out to `msb`, matching how `podman` and the Mutagen sidecar are already driven and reusing the `ProcessRunner` seam the entire `light` e2e tier depends on.

The spike materially changed the reasoning here. This document's first revision rejected the SDK partly because microsandbox's own documentation contradicted itself about whether a daemon exists. That contradiction is resolved: **there is no daemon**. Current documentation states there is no server to connect to, and upstream source confirms it — `BackendKind::Local` is documented as spawning microVMs on the calling host, and the `microsandbox-server` crate last published 0.2.6 in 2025 and no longer exists in the tree. The app supervises no background process under either the CLI or the SDK. The spike also established that the CLI is a thin `clap` front end over the same SDK crate, so the two are the same engine rather than two implementations.

The CLI remains the choice on two grounds that survive:

- **The `ProcessRunner` seam.** An in-process SDK call is invisible to `mock_configure`, so the `light` tier would need a hand-written mock struct — the pattern `docs/features/scriptable-mock-backend/02_dev.md` records as superseded.
- **Dependency footprint.** The `microsandbox` crate (0.6.8) is edition 2024, requiring Rust 1.85 where this crate is on edition 2021; it depends on `reqwest` 0.13 where `src-tauri/Cargo.toml` pins 0.12, forcing two majors side by side; and it pulls `sea-orm` 2.0 with `sqlx`/SQLite for a transitive closure of roughly 687 packages.

The SDK retains one capability the CLI lacks that matters to this design: `Sandbox::builder(...).from_snapshot(...)`. Should the base-image path below ever need snapshots, the SDK becomes the only route, and that is the trigger to revisit the choice.

### Base image for microsandbox: `podman save` piped to `msb load` (chosen) vs. bootstrap-and-snapshot vs. registry publication vs. per-sandbox first-boot install

Chosen: build once with `podman build`, export with `podman save`, import with `msb load --tag sandbox-mio/base:<BASE_IMAGE_VERSION>`.

- **Bootstrap-and-snapshot** (boot `debian:12-slim`, replay the Containerfile's `RUN` steps as `msb exec` calls, snapshot the stopped sandbox) — **rejected on spike evidence**, having been the chosen option in this document's first revision. Snapshot *creation* works and retains labels, but the CLI exposes no way to *consume* a snapshot: `msb create <snapshot-name>` resolves the argument against Docker Hub, and booting the snapshot artifact directly fails every exec with `failed to resolve guest uid 0` because a snapshot captures only the writable upper layer. Retested against a correctly indexed snapshot with identical results (see Validation). Implementable only via the SDK, which is rejected above.
- **Publishing `sandbox-mio/base:<BASE_IMAGE_VERSION>` to a registry such as GHCR so both providers pull the same tag** — rejected for v1, but it is the intended path out of the chosen option's Podman dependency. The repository has no CI pipeline (`docs/features/scriptable-mock-backend/04_improvements.md`), so registry publication is new release infrastructure to build and operate first. It also converts Podman's current offline-capable "absence means build" contract into a network dependency, a regression for the provider that works today. Recorded in `04_improvements.md` rather than attempted here.
- **Skipping a base image and installing mise, zellij, and the apt packages on every sandbox's first boot** — rejected: `src-tauri/resources/Containerfile` exists precisely to move minutes of apt and mise work out of sandbox creation, and paying it per sandbox would make microsandbox sandboxes slower to create than Podman ones despite microsandbox's sub-100ms boot being the headline reason to adopt it.

The chosen option's cost is stated plainly: a microsandbox sandbox cannot be created on a host with no working Podman machine, which removes part of the motivation for the provider until registry publication lands.

### Workspace transport: disk volume plus Mutagen sync (chosen) vs. host bind mount vs. waiting for upstream

Chosen: a `--kind disk` named volume synced from the host workspace over `msb ssh serve --stdio`.

- **A host bind mount, mirroring Podman's local behaviour** — rejected on measured evidence, not preference. Every read on a virtiofs mount exits non-zero and `statx` returns `ELOOP`; the failures are attributable to two open Windows-only upstream bugs, #1219 (`FUSE_STATX` unimplemented, so a host `ENOSYS` surfaces in the guest as `ELOOP`) and #1218 (read-only `close()` returning `EACCES`). Since `check()` in `src-tauri/src/backends/mod.rs`, `src-tauri/src/runtime/mod.rs`, and `src-tauri/src/machine/mod.rs` all treat a non-zero exit as failure, every `mise` and `git` operation against a bind-mounted workspace would report failure while producing correct output. A third issue, #949, reports that virtiofs provides no file locking, desynchronising host and guest views. Inotify propagation from host writes appears absent, which a bind mount would need for dev-server reload to work.
- **Deferring the whole feature until #1218 and #1219 close** — rejected as a plan, though it is the likely long-term resolution. Both are filed, Windows-only, and upstream has fixed three separate boot-failure classes within days each, so a fix is plausible. Blocking on an unscheduled upstream fix stalls the refactor that is valuable on its own, and the `host_bind_mount` capability probe means the provider can adopt bind mounts without a redesign once the fix ships.

The chosen option's cost is that a *local* sandbox acquires sync latency and conflict semantics that the Podman provider's direct bind mount does not have. The mitigation is that the mechanism is not new code: `MutagenCli` already performs exactly this sync for every remote deploy.

### Published ports and in-guest services: explicit host-port allocation plus `0.0.0.0` binds (chosen) vs. ephemeral publishing vs. an in-guest `socat` bridge

**Superseded — see the note at the top of this document.** `docs/features/mutagen-transport/01_ideas.md`'s "Port reachability for microsandbox" Technology Choices entry replaces this whole section with a simpler design (dial the guest directly over SSH, no publish step, keep `127.0.0.1` binds). Left below as the rejected-alternative record.

Chosen: allocate the host port app-side and pass it explicitly to `msb create -p`, and start in-guest services bound to `0.0.0.0`.

- **Ephemeral publishing, mirroring Podman's `127.0.0.1::<port>` form** — not viable. The spike found microsandbox's port parser rejects an empty host segment, and although `-p 127.0.0.1:0:8082` is accepted and genuinely binds a kernel-chosen port, `msb inspect` and `msb status` echo the requested `0` back and no `podman port` equivalent exists. The resolved port is unobservable through `msb`. The app already owns host-port allocation behind `NetworkError::PortAllocation` (`src-tauri/src/network/types.rs`).
- **Bridging loopback-bound services with an in-guest `socat` relay instead of rebinding them** — rejected for the terminal and agent-web services specifically: zellij and paseo are started by this project's own code in `prepare_terminal` and `prepare_agent_web` (`src-tauri/src/runtime/mod.rs`), so changing the bind address is a flag change at the call site, whereas a relay adds a second process per service to supervise. The relay-pool `socat` machinery stays in place for its existing purpose — exposing arbitrary user-started ports — because `msb modify` cannot publish a port after create.

### E2E isolation: `MSB_HOME` and `MSB_PATH` per worktree (chosen) vs. a shared host-global microsandbox state directory

Chosen: point `MSB_HOME` at a `RUN_SLUG`-keyed directory and pin `MSB_PATH` to the host-wide installed executable (`e2e/lib/run-identity.ts`), alongside the existing `MIO_APP_DATA_DIR` and `SANDBOX_WORKSPACE_ROOT` per-worktree roots.

The spike confirmed `MSB_HOME` is read by a single upstream resolver whose documented purpose is CI and test isolation, that every state directory joins it, and that the metrics shared-memory name hashes the home so concurrent isolated environments do not collide. `MSB_PATH` must be pinned alongside it because a freshly created `MSB_HOME` has no `bin/`, so resolution would otherwise depend on `PATH` ordering. Its value is the full path to the `msb` executable, never a directory: `msb` re-reads the inherited variable to spawn its own VM supervisor, so a directory value fails every `msb create` with `Access is denied. (os error 5)` on Windows.

- **Letting microsandbox use its default `%USERPROFILE%\.microsandbox` state directory** — rejected on the cost `e2e/AGENTS.md` names explicitly: host-global state cannot be isolated per worktree, so microsandbox specs would join Podman's `mio-tests` machine under the host-wide lock and serialise against every other real-infra run. Per-worktree isolation is the one axis on which the microsandbox provider is strictly better than Podman, and discarding it by default would waste that advantage.

### Provider choice granularity: per sandbox with an app-wide default (chosen) vs. app-wide only

Chosen: a `default_provider` field on `AppSettings` (`src-tauri/src/settings/types.rs`) with a per-sandbox override at create time, mirroring how `inference_engine` already selects between llama.cpp and Foundry Local.

- **An app-wide switch only** — rejected: switching it would orphan every sandbox created under the previous provider, since `SandboxBackend::list` would stop reporting them while the containers still exist. Per-sandbox selection with a merged `list` makes provider migration a per-sandbox decision instead of a destructive global one. The cost is that sandbox names must be unique across the union of both providers, enforced by extending `validate_name()` (`src-tauri/src/backends/mod.rs`) with a cross-provider existence check, plus one `msb inspect` per sandbox to recover labels because `msb list --format json` omits them.

## Validation

A three-part spike was run on 2026-08-09. `msb` 0.6.6 was already installed on the Windows 11 development host at `C:\Users\krist\.microsandbox\bin\msb.exe`, so the hands-on stage executed against the real binary rather than a fresh install. Full artefacts: `spike/hands-on-cli.md`, `spike/cli-surface.md`, `spike/windows-and-state.md`.

**Cleared — the feature is viable.** The single risk framed as potentially ending the feature is disproved. `msb doctor` reports "Host setup is ready" with the Windows Hypervisor Platform active on the same host that runs Podman on WSL2. `HypervisorPlatform` and `VirtualMachinePlatform` are independent optional features over the same Hyper-V hypervisor; the upstream tracker contains reports of microsandbox, WSL2, and Docker Desktop running concurrently, and no report of WSL2 breaking. Enabling `HypervisorPlatform` requires a reboot, and `msb doctor --fix` enables it with `-NoRestart` without rebooting.

**Cleared — mechanisms this design depends on.** Exit codes propagate faithfully (42 stays 42; a missing command returns 127), so the `check()` idiom works. `msb exec --stream` provides byte-faithful piped stdin, covering `tar_capture`/`tar_inject` (`src-tauri/src/credentials/mod.rs`) and the interactive auth session (`src-tauri/src/agents/mod.rs`). Labels persist and the `sandbox-mio.workspace` key survives the reserved-prefix check. `msb load --tag sandbox-mio/base:4` round-trips and `msb list --format json` reports the full tag. Windows host paths mount with either separator, so `workspace_path()`'s forward-slashing needs no change. SSH works with the Windows OpenSSH client over `ProxyCommand … --stdio`, returning `uid=0(root)` on kernel 6.12.91. No default idle timeout or maximum duration is applied, so a dev sandbox will not self-stop.

**Disproved — three assumptions from this document's first revision.**

1. **Bind mounts are unusable on Windows.** Reads on a virtiofs mount return correct content and exit 1 (`Permission denied` raised by `close()`), and `stat` fails with `ELOOP`. The failure tracks the transport, not file provenance: a guest-written file in the same mount fails identically, a control read outside the mount exits 0, and a `--kind dir` named volume (also virtiofs) reproduces it. All three `stat-virt` values and both `host-perms` values were tested; none help. A `--kind disk` volume (ext4 over virtio-blk) returns exit 0 for both operations. The symptoms match open upstream issues #1219 and #1218.
2. **Snapshots cannot serve as the base image through the CLI.** Creation works and retains labels, but no CLI entry point consumes a snapshot: booting the artifact path fails every exec with `failed to resolve guest uid 0`, and `msb create <indexed-name>` resolves against Docker Hub. Retested against a correctly indexed snapshot whose `msb snapshot inspect` showed the pinned parent image and version label — same failure.
3. **The `-p` flag does not match Podman's ephemeral posture.** An empty host segment is rejected; `-p 127.0.0.1:0:8082` binds a real ephemeral port (confirmed listening on 127.0.0.1:64310) but microsandbox never reports it.

**Also measured.** A guest server bound to `127.0.0.1` is unreachable from Windows through a published port, while the same server bound to `0.0.0.0` returns HTTP 200 — microsandbox dials the guest's interface IP and has no equivalent of `--host-lo-to-ns-lo`. `msb modify` has no port flag. `msb exec` has no detach flag. `msb list --format json` returns four fields and omits labels. Status values are PascalCase across seven states (`Created`, `Starting`, `Running`, `Draining`, `Paused`, `Stopped`, `Crashed`), with no counterpart to Podman's `exited`. `msb ssh serve` auto-starts a stopped sandbox and owns its lifecycle: force-killing the listener left the sandbox `Crashed`.

**Maturity.** Latest release 0.6.8 (2026-07-29); Windows support landed in 0.6.0 (2026-06-27) and bind mounts only in 0.6.1, making the Windows surface roughly six weeks old at spike time. Four open `Windows`-labelled issues, including the two virtiofs bugs above.

**Not yet run.** No spike has driven this project's actual base-image recipe end to end: building `src-tauri/resources/Containerfile` with Podman, exporting it, importing it with `msb load`, and starting zellij inside the resulting sandbox with a `0.0.0.0` bind reachable from a Windows browser. That sequence is the remaining proof that the workspace surface functions under microsandbox, and it should run before `02_dev.md` commits to a phase plan.

## Open Questions

- **Whether the provider ships user-visible in v1.** Microsandbox marks itself beta and its Windows support preview, the Windows surface is roughly six weeks old, and the workspace architecture depends on two open upstream bugs staying worked around. Whether the provider is offered in the welcome flow or hidden behind a settings flag until #1218 and #1219 close is undecided.
- **Whether the base image's Podman dependency is acceptable for v1.** The chosen `podman save` to `msb load` path means a microsandbox sandbox cannot be created without a working Podman machine, which removes much of the provider's appeal on a WSL-free host. Whether v1 ships with that dependency, or waits for registry publication, is undecided and is the single largest open scoping question.
- **How `listen_events` behaves for microsandbox.** No events command exists. The choices are polling `msb list`, deriving events from the per-sandbox `msb logs -f --json` stream (which carries `--- sandbox started/stopped ---` markers under `--source system`), or declaring `event_stream: false` and letting the activity feed stay quieter. Undecided.
- **How the paseo and zellij daemons are started without a detached exec.** `podman exec -d` has no microsandbox equivalent. Candidates are backgrounding inside the guest shell (which the spike observed surviving its exec's exit, though `spike/cli-surface.md` reads the upstream source as signalling the guest process group), registering the command with `msb create --script`, or supervising a long-lived `msb exec --stream` child. Undecided and needs a direct test.
- **Which status vocabulary reaches `translateStatus()`.** Whether `MsbProvider` normalises the seven PascalCase states onto Podman's existing lowercase vocabulary — losing the `Draining`, `Paused`, and `Crashed` distinctions — or introduces `status_<value>` keys in every file under `messages/` for the new states, is undecided.
- **How `Sandbox.image_version` is derived.** `parse_image_version` works for a `msb load`-tagged image because `msb list` reports the full tag. If the base image ever moves to the SDK snapshot path, the version must ride on a sandbox label instead, since a snapshot-booted sandbox reports the pinned parent OCI reference rather than the snapshot name.
- **How much of the refactor lands before the first microsandbox code.** The `MachineProvider` extraction touches five modules and roughly twenty call sites with no user-visible change, and could ship as its own reviewed phase with `PodmanProvider` as the only implementation. `02_dev.md` should resolve the phase boundary, since a Podman-only refactor is verifiable by the existing `standard` tier alone.
- **How Mutagen handles the `ProxyCommand` alias and host-key prompts.** Microsandbox generates a host key per sandbox on first serve, and Mutagen cannot answer an interactive `known_hosts` prompt. Whether `write_alias()` (`src-tauri/src/ssh/mod.rs`) emits `StrictHostKeyChecking=accept-new` for microsandbox aliases, or a per-sandbox `known_hosts` file is managed explicitly, is undecided.

## Common Gotchas

| Gotcha | Cause | Fix |
|---|---|---|
| `msb exec <name> -- cat <file>` prints correct contents but exits 1 with "Permission denied" | Reads on a virtiofs mount in `msb` 0.6.6 on Windows fail on `close()` (upstream issue #1218); no `stat-virt` or `host-perms` option avoids it | Hold the workspace on a `--kind disk` named volume (ext4 over virtio-blk), which returns exit 0 for reads and `stat`, and sync it from the host with `MutagenCli` (`src-tauri/src/sync/mod.rs`) |
| `stat` on a workspace file reports "Too many levels of symbolic links" although no symlink exists | `FUSE_STATX` is unimplemented on the Windows virtiofs backend, so a host `ENOSYS` surfaces in the guest as `ELOOP` (upstream issue #1219) | Keep the workspace off virtiofs; probe the defect at startup behind `ProviderCapabilities.host_bind_mount` so bind mounts are adopted automatically once upstream fixes it |
| A sandbox created through a new microsandbox `SandboxBackend` implementation cannot install packages, open a terminal, or inject credentials | `PodmanMiseRuntime`, `MutagenNetworkManager`, `src-tauri/src/credentials/mod.rs`, and `src-tauri/src/agents/mod.rs` shell out to `podman` directly rather than through `SandboxBackend` | Route every subsystem through the `MachineProvider` trait (`src-tauri/src/provider/types.rs`) before adding a second provider implementation |
| The in-app terminal never loads for a microsandbox sandbox although the sandbox is running | Microsandbox forwards a published port to the guest interface, not the guest loopback, and has no equivalent of Podman's `--network pasta:--host-lo-to-ns-lo`; zellij binds the loopback | Start zellij and paseo with an explicit `0.0.0.0` bind in `prepare_terminal`/`prepare_agent_web` (`src-tauri/src/runtime/mod.rs`); the host side of the publish stays on `127.0.0.1` |
| An ephemeral published port is bound but the app cannot discover which host port it received | `msb inspect` and `msb status` echo the requested `host_port: 0`; microsandbox has no equivalent of `podman port <name> <port>/tcp` | Allocate the host port app-side and pass it explicitly to `msb create -p`, reusing the path behind `NetworkError::PortAllocation` (`src-tauri/src/network/types.rs`) |
| A sandbox created from a snapshot fails every exec with "failed to resolve guest uid 0" | `msb snapshot create` captures only the writable upper layer, and the CLI exposes no create-from-snapshot entry point, so the parent image is absent | Build the base image with Podman and import it with `msb load --input <tar> --tag sandbox-mio/base:<version>`; snapshots are reachable only through the Rust SDK's `from_snapshot` |
| The workspace path label is missing when enumerating sandboxes | `msb list --format json` returns only `created_at`, `image`, `name`, and `status`; labels appear only under `msb inspect --format json` | Call `msb inspect --format json` per sandbox to recover labels, accepting the N+1 cost that `podman ps --format json` avoids |
| A status badge shows a raw `Running` or `Crashed` string in non-English locales | Microsandbox reports seven PascalCase status values, unlike Podman's lowercase vocabulary that `translateStatus()` (`src/lib/sandbox.ts`) maps | Normalise microsandbox status values in the provider implementation, or add a `status_<value>` key for each new value to every file in `messages/` |
| A sandbox is left in `Crashed` state after an `msb ssh serve` process is terminated | `msb ssh serve` auto-starts a stopped sandbox and owns its lifecycle, so force-killing the listener crashes the sandbox it started | Prefer the `--stdio` `ProxyCommand` mode, which OpenSSH spawns and reaps per connection, or call `msb start` first so the listener does not own the sandbox |
| Two worktrees' e2e runs collide on microsandbox state, or a run uses the wrong `msb` binary | Microsandbox state defaults to the host-global `%USERPROFILE%\.microsandbox`, and a slug-keyed `MSB_HOME` has no `bin/`, so binary resolution falls through to `PATH` ordering | Set `MSB_HOME` to a `RUN_SLUG`-keyed path and `MSB_PATH` to the installed `msb.exe` (`e2e/lib/run-identity.ts`), both exported in `e2e/wdio.conf.ts` |
| Every `msb create` fails with `error: io error: Access is denied. (os error 5)` while the app's own `msb` calls succeed | `MSB_PATH` was set to a directory: `msb` inherits the variable and spawns its own VM supervisor from it, and Windows returns ERROR_ACCESS_DENIED for executing a directory | Set `MSB_PATH` to the full path of the `msb` executable at both ends (`msb_command()` in `src-tauri/src/mockctl/mod.rs`, `MSB_PATH` in `e2e/lib/run-identity.ts`) |
| `mock_configure` rejects an `msb.*` key in a light spec | `KNOWN_CALLS` (`src-tauri/src/mockctl/mod.rs`) validates every key and lists only `podman.*` and `mutagen.*` entries | Add the `msb.<subcommand>` key to `KNOWN_CALLS` and confirm `derive_msb_key` produces the same key for the argv the provider builds |
| `deploy_sandbox` fails with an opaque `BackendError::CommandFailed` for a microsandbox sandbox | Remote deploy is Podman-connection-shaped and microsandbox exposes no remote host concept | Gate the deploy picker in `src/routes/projects/+page.svelte` on `ProviderCapabilities.remote_targets` so the action is hidden rather than failing at invoke time |
| `msb` invocations from a Git Bash shell fail with paths like `C:/Program Files/Git/root/work` | MSYS2 path conversion rewrites guest-absolute arguments such as `-w /root/work` into Windows paths | Invoke `msb` from PowerShell, or set `MSYS_NO_PATHCONV=1` for the call |

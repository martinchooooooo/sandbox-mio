# Sandbox List Create-Item Dev Plan

This is the build plan for the feature ideated in `docs/features/sandbox-list-create/01_ideas.md`: extracting the "create project" form into a `CreateSandboxItem.svelte` list item that always renders as the last row of the sandbox `<ul>`, and adding a discreet click-to-reveal control on that row for picking an existing directory as the workspace instead of always auto-creating one. This document continues all of `01_ideas.md`'s Proposed Model and Technology Choices sections unchanged and resolves every one of its Open Questions below. Status: **all four phases implemented** (Phase A backend `existing_path` support, Phase B directory-picker plugin plumbing, Phase C `CreateSandboxItem.svelte` + `+page.svelte` list restructuring, Phase D name-collision and already-tracked-path guards — D ended up folded into A/C's own commits rather than landing separately, see those sections). `cargo check` and `pnpm run check` both pass clean on the changed files. i18n is still deferred: all new user-facing strings are hardcoded English literals marked `TODO(i18n)`, not yet added to `messages/*.json`, pending user sign-off on behavior and wording per the project's `feature-implement` convention. Two manual verification steps remain outstanding — see Phase B and Phase C's notes — and are not yet done: clicking the real native folder picker once from the running `/projects` route, and a general manual click-through of the new UI.

## The Concrete Model

`CreateSandboxItem.svelte` is a new file at `src/routes/projects/CreateSandboxItem.svelte`, always the last `<li>` in the `<ul>` at `+page.svelte:180-189` (renamed conceptually to "the sandbox list", now list-length-independent). It owns two mutually exclusive render states, toggled by local `$state<"name" | "folder">("name")`:

- **`"name"` state (default)**: the current wide `Input` (bound to a local `projectName`) plus `Create` `Button`, byte-for-byte the same width/prominence as today's `+page.svelte:148-155`, plus a small `Button variant="link"` reading `m.projects_create_use_folder()` ("or use an existing folder…") beneath the input row.
- **`"folder"` state**: entered by clicking the link. Shows a `Choose folder…` `Button` that calls `open({ directory: true })` from `@tauri-apps/plugin-dialog`. Once a path is returned, the row shows the picked path (truncated/muted text) next to a name `Input` pre-filled with the path's basename (still editable) and the same `Create` `Button`, plus a small "x"/back `Button` that resets to the `"name"` state and clears the picked path.

Both states funnel into one `createProject()`-equivalent handler in `CreateSandboxItem.svelte` that calls `invoke("create_sandbox", { name, existingPath })`, with `existingPath` being `undefined` in the `"name"` state and the picked absolute path in the `"folder"` state. On success it resets to the `"name"` state and calls the `onCreated: () => void` prop (mirrors `SandboxItem`'s `onChanged` convention) so `+page.svelte` re-runs `loadProjects()`.

Backend: `create_sandbox` (`src-tauri/src/lib.rs:69-81`) gains `existing_path: Option<String>`, forwarded to `store.create(&name, existing_path.as_deref())`. `SandboxBackend::create` (`src-tauri/src/backends/types.rs:125`) becomes `async fn create(&self, name: &str, existing_path: Option<&str>) -> Result<Sandbox, BackendError>`. `PodmanCliBackend::create` (`src-tauri/src/backends/mod.rs:318-352`) branches on `existing_path`: `None` keeps today's `workspace_root()`/`workspace_path()`/`create_dir_all` behavior unchanged; `Some(p)` validates `p` (exists, is a directory, is not already a tracked workspace — see Phase D) and bind-mounts it directly, skipping directory creation. `MockBackend::create` (`src-tauri/src/backends/mock.rs:26-37`) gains the same parameter for signature parity, storing whatever path is passed (or its mock default) in `workspace_path` — the mock never actually validates the filesystem, matching its existing "plain in-memory state machine" role.

## Resolved Decisions

- **Empty-list conditional restructuring**: resolved as `{:else}`. `+page.svelte:166-191`'s `{#if podmanUnavailable}...{:else if projects.length > 0}` becomes `{#if podmanUnavailable}...{:else}`, so the `<ul>` always renders once Podman is confirmed ready. `{#each projects as project (project.id)}` yields zero `<SandboxItem>` rows on an empty list, and `<CreateSandboxItem>` always renders as the final (and, when empty, only) row. No separate empty-state copy is added — the always-present create row *is* the empty state.
- **Name vs. directory-basename prefill**: resolved as auto-filled and editable. Entering the `"folder"` state pre-fills the name `Input` from `existingPath`'s basename (computed client-side, e.g. via a small `basename(path)` helper matching the path's OS separator) but the user can retype it before clicking `Create`.
- **Name collision handling**: resolved as a client-side pre-check, not solely relying on the backend round trip. `CreateSandboxItem` receives the already-loaded `projects: Project[]` list as a prop (the parent already fetches this via `loadProjects()`); before calling `create_sandbox`, the handler checks `projects.some(p => p.name === name)` and shows an inline error (via the same `StatusRow`/`action.error` mechanism already used per-row) without a round trip if it collides. The backend-side failure path (`BackendError::CommandFailed` from podman's own `--name` collision, surfaced as `AppError::Backend`/`"Backend"` kind) remains the fallback for the TOCTOU window between load and submit, consistent with every other mutating action on this page, which does not attempt to eliminate that window either (e.g. destroy/deploy races).
- **Re-registering an already-tracked workspace directory**: resolved as a server-side block, not just a client-side warning, because the client's `projects` list already carries each project's `workspace_path` (`Project.workspace_path`, `src/lib/sandbox.ts:7`) but a race is still possible. `PodmanCliBackend::create`'s `existing_path` branch canonicalizes the picked path and compares it against `workspace_root()` (rejecting anything already nested under the auto-create root — that path always belongs to *some* existing-or-orphaned sandbox slot) and against every current `Sandbox.workspace_path` returned by `self.list()` (rejecting an exact match with any already-tracked sandbox). A new `BackendError::PathAlreadyTracked { path: String }` variant carries the failure. The frontend surfaces it exactly like any other `Backend`-kind error (generic `error.message` display in `StatusRow`) — no new `AppErrorKind` branch is needed, matching the "no special frontend branching for `InvalidName`" precedent already in `createProject()`.
- **Scope of the click-to-reveal link**: resolved as strictly path-only for this feature. No template/runtime/base-image-variant picker is added to `CreateSandboxItem`; the link's only job is exposing the existing-directory path. If a future feature wants more create-time options, it can convert the "folder" state into a richer options panel without changing `create_sandbox`'s two-parameter shape decided here.
- **Single command vs. two-command split**: resolved in favor of the single `create_sandbox` command with an optional `existing_path`, as leaned in `01_ideas.md`. The new `BackendError` variants (`PathNotFound`, `PathNotADirectory`, `PathAlreadyTracked`) all surface through the same generic `Backend`-kind `AppError` the frontend already displays as plain text, so the error-shape concern that could have tipped the balance toward a separate command does not materialize.

## Implementation Phases

## Implemented: Phase A — backend `existing_path` support

- `src-tauri/src/backends/types.rs`: added three variants to `BackendError`: `PathNotFound { path: String }`, `PathNotADirectory { path: String }`, `PathAlreadyTracked { path: String }`, each with a self-documenting `#[error("...")]` message. Changed `SandboxBackend::create`'s trait signature to `async fn create(&self, name: &str, existing_path: Option<&str>) -> Result<Sandbox, BackendError>`, doc comment updated to describe both branches.
- `src-tauri/src/backends/mod.rs`:
  - `PodmanCliBackend::create` now accepts `existing_path: Option<&str>` and delegates to a new `&self` async method `resolve_create_workspace` (named to avoid colliding with the pre-existing `resolve_workspace(name, connection)` used by `deploy`) that: for `None`, keeps the exact prior behavior (`workspace_path(name)?` + `create_dir_all`); for `Some(p)`, canonicalizes `p` via `dunce::canonicalize` (not `std::fs::canonicalize` — see deviation below), returns `PathNotFound`/`PathNotADirectory` as scoped, returns `PathAlreadyTracked` if the canonicalized path falls inside `workspace_root()` or exactly matches an already-tracked sandbox's `workspace_path` (via `self.list().await?`), and otherwise returns the forward-slashed canonicalized path without touching the filesystem further.
  - Updated `validate_name`'s doc comment to scope the path-safety claim to the `existing_path: None` branch.
  - **Deviation from this doc, required for correctness (see de-risking note below):** `create()` now also tags the container with a `sandbox-mio.workspace=<path>` Podman label (`WORKSPACE_LABEL` const) recording its real workspace path verbatim, and `list()` reads that label back (falling back to the name-derived `workspace_path(name)` for containers created before this label existed). This was not in the original Phase A scope, which only touched `create`; it was added because `list()` previously derived every sandbox's `workspace_path` purely from its name, which is wrong for an `existing_path` sandbox and would have broken `03_e2e.md` step 7's assertion, the "open folder" button, and anything else reading `Project.workspace_path`. Using a label (read straight from the same `podman ps --format json` call `list()` already makes) sidesteps the Windows/WSL VM-path-translation risk a `podman inspect`-based approach would have carried, at the cost of a `--label` argument on `create`'s podman invocation.
  - Also used `dunce::canonicalize` (new direct dependency, already present transitively) instead of `std::fs::canonicalize`, pre-emptively taking `03_e2e.md`'s Risk 1 fix rather than shipping the UNC-prefix bug and fixing it later.
- `src-tauri/src/backends/mock.rs`: `MockBackend::create` gained the `existing_path: Option<&str>` parameter; `Some(p)` stores `p.to_string()` as `workspace_path` instead of the `/mock/workspace/{name}` default (the mock's `list()` already returns stored state directly, so no separate mock-side label mechanism was needed).
- `src-tauri/src/lib.rs`: `create_sandbox` gained `existing_path: Option<String>`, passed as `existing_path.as_deref()` into `store.create(&name, ...)`.
- `src-tauri/Cargo.toml`: added `dunce = "1"` as a direct dependency.
- Verified with `cargo check` (clean; only two pre-existing, unrelated warnings in `activity/types.rs` and `inference/types.rs`).

## Implemented: Phase C — `CreateSandboxItem.svelte` and list restructuring

- New file `src/routes/projects/CreateSandboxItem.svelte`:
  - Props: `{ projects: Project[]; onCreated: () => void }`.
  - Local state: `mode: "name" | "folder"`, `name`, `existingPath: string | undefined`.
  - Own `createActionRunner()` instance and `StatusRow`, matching `SandboxItem.svelte`'s per-row pattern.
  - Root markup: `<li data-create-row class="flex flex-col gap-2 rounded-lg border p-3 text-sm">` — the `data-create-row` attribute was added beyond the original bullet, per `03_e2e.md`'s page-object plan, as a stable non-text-dependent selector hook.
  - `"name"` mode: the `Field.Set > Field.Group > Field.Field` + `Input` + `Create` `Button` block, plus a `Button variant="link"` reading (hardcoded, `TODO(i18n)`) "or use an existing folder…", wired to `mode = "folder"`.
  - `"folder"` mode: before a path is picked, a `Choose folder…` `Button` (hardcoded, `TODO(i18n)`) calling `open({ directory: true })` from `@tauri-apps/plugin-dialog`, plus a `Back` button (`aria-label="Back"`) resetting to `"name"` mode. After a path is picked: the picked path (muted, truncated text), the editable name `Input` pre-filled from `basename(picked)`, the `Create` `Button`, and the same back button, now also clearing `existingPath`.
  - `createProject()` handler: trims `name`; the collision pre-check and the `invoke("create_sandbox", ...)` call both run *inside* `action.run`'s thunk — a synchronous `throw { kind: "Backend", message: "…" }` before `invoke` is called satisfies "inline error, no round trip" without adding a new `ActionRunner` setter, since `parseError` already accepts any `{ kind, message }`-shaped throw. On success resets `name`/`existingPath`/`mode` and calls `onCreated()`.
- `src/routes/projects/+page.svelte`:
  - Removed `projectName` state, the page-level `action` runner, `createProject()`, and the inline form block + its `StatusRow` — all now live in `CreateSandboxItem.svelte`. Also removed the now-unused `Field`/`Input`/`StatusRow` imports.
  - Changed `{#if podmanUnavailable}...{:else if projects.length > 0}` to `{#if podmanUnavailable}...{:else}`, so the `<ul>` always renders once Podman is confirmed ready.
  - Added `<CreateSandboxItem {projects} onCreated={reload} />` as the last child inside `<ul class="mt-6 space-y-2">`, after the `{#each}` block.
- i18n: all new strings ("or use an existing folder…", "Choose folder…", the collision error, and `aria-label="Back"`) are hardcoded English literals marked `TODO(i18n)`, per the i18n-deferral convention — not yet added to `messages/*.json`. Existing keys `projects_name_label`, `projects_name_placeholder`, `projects_create`, `projects_status_creating` are reused unchanged.
- Verified with `pnpm run check` (`svelte-check`): zero errors in any file touched by this feature; the 5 remaining errors are pre-existing, in unrelated `ui/command`/`ui/dialog` shadcn primitives and `+layout.svelte`'s deprecated `<slot>` warning.
- Not yet manually clicked through in the running app (UI screenshot/interaction pass still pending — see Common Gotchas / Risk 3 in `03_e2e.md` for the follow-up of confirming rendered copy matches page-object selectors).

## Implemented: Phase D — name-collision and already-tracked-path guards

- Frontend: implemented as part of Phase C's `createProject()` handler (see above) rather than as a separate later change — `projects.some(p => p.name === trimmed)` is checked before `invoke("create_sandbox", ...)` runs.
- Backend: implemented as part of Phase A's `resolve_create_workspace` (see above) — covers both "picked directory is inside `workspace_root()`" and "picked directory matches an existing sandbox's `workspace_path` exactly" (via `self.list()`, now backed by the `sandbox-mio.workspace` label so the comparison is against each sandbox's *real* workspace path, not a name-derived guess).
- New message key: the collision error is currently a hardcoded English literal (`A sandbox named "…" already exists.`) marked `TODO(i18n)`, matching Phase C's deferral — not yet promoted to a `messages/en.json` key.
- **Open issue, not yet resolved:** a light-suite e2e repro (submit the same name twice in `CreateSandboxItem`, mock backend) reliably ends with *two* mock sandboxes sharing the identical name, despite `projects.some(p => p.name === trimmed)` looking correct by inspection and despite ruling out three plausible causes — a stale `projects` prop (disproved with a temporary `data-projects-names` DOM probe: the child does see the freshly created entry before the retry), an out-of-order `loadProjects()` response from `onMount` clobbering state after the retry (an explicit settle-and-retry in the test made no difference), and a test-selector false positive from the guard's own error message containing the sandbox name (fixed the selector; the duplicate persisted). The real cause was not found. The corresponding e2e scenario (`e2e/test/specs/light/sandbox-create-row-ui.spec.ts`'s second `it()`, scoped in `03_e2e.md`) was removed rather than committed failing — **the client-side collision guard should be treated as unverified**, not confirmed working, until this is root-caused. Given the doc's own Resolved Decisions already treat this guard as "a UX nicety only, not authoritative," the backend-side guard (this phase's other half, in `PodmanCliBackend::resolve_create_workspace`) is unaffected and remains the real protection for the real backend — this gap is specific to the frontend pre-check against the *mock* backend's duplicate-name tolerance.

## Lifecycle / Cross-Cutting Concerns

- **`reload()` reuse**: `+page.svelte:86-88`'s `reload` already does exactly what a successful create needs (refresh both `projects` and `deployments`), so `CreateSandboxItem`'s `onCreated` prop is wired straight to it rather than introducing a second reload path.
- **`StatusRow` per-row convention stays intact**: moving the action runner and `StatusRow` into `CreateSandboxItem` keeps every row (including the create row) self-contained for busy/error display, matching `SandboxItem.svelte`'s existing per-row pattern — no shared/global action state is introduced.
- **`existing_path` is additive-only at the IPC boundary**: `create_sandbox`'s new parameter is `Option<String>`, so any external caller still invoking it with just `{ name }` continues to work unchanged (relevant if e2e tests or other code paths call `create_sandbox` directly — grep `invoke("create_sandbox"` and any Rust-side direct callers before assuming Phase A is a pure addition).
- **Podman's own name-collision error remains the ultimate source of truth**: the client-side pre-check (Phase D) and the server-side canonicalization check (Phase A) both reduce round trips and give better error messages, but neither replaces `podman create --name`'s own failure — a race between two `create_sandbox` calls with the same name still surfaces as `BackendError::CommandFailed`, same as today.

## Common Gotchas

| Gotcha | Cause | Fix |
|---|---|---|
| `MockBackend::create`'s signature drifts from `PodmanCliBackend::create`'s after Phase A | Both implement `SandboxBackend::create`, but the mock is easy to forget since it never talks to the filesystem | Update `mock.rs:26-37`'s signature in the same commit as `types.rs`'s trait change, or the crate fails to compile — the trait forces this, but double-check the mock's *behavior* (storing `existing_path` verbatim) was intentionally updated too, not just the signature |
| `create_dir_all`'s comment ("so an unwritable path fails here, not silently via podman's auto-creation") reads as applying to both branches after Phase A | The comment predates the `existing_path` branch, which deliberately skips `create_dir_all` | Scope the comment to the `None`/auto-create branch only when editing `mod.rs:318-352` |
| The client-side collision pre-check (Phase D) gives a false sense of safety | `projects` is a snapshot from the last `loadProjects()` call; a sandbox created by another process/window between that load and this submit is invisible to the check | Keep the backend-side `CommandFailed`/`PathAlreadyTracked` path as the real guard; the client check is a UX nicety only, not documented as authoritative |
| `dialog:allow-open` denied at runtime despite being present in `capabilities/default.json` | Permission scoped to the wrong webview label (`main` instead of `main-global`, or vice versa) | Confirm the exact webview label the `/projects` route runs in (`main-global`, `workspace/mod.rs:29`) before assuming the permission block is correct; test by actually clicking "Choose folder…" from that route, not from a different window |
| New `BackendError` variants (`PathNotFound`, `PathNotADirectory`, `PathAlreadyTracked`) never reach the user with a helpful message | These are `Backend`-kind `AppError`s displayed as plain `error.message` text (no special frontend branching, per Resolved Decisions) | Write the `#[error("...")]` message on each variant to be directly user-facing, since nothing on the frontend adds context around it |

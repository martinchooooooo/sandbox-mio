# Sandbox List Create-Item Ideas

This document covers turning the standalone "create project" form on the projects page (`src/routes/projects/+page.svelte:143-158`) into its own component that renders as a peer of `SandboxItem.svelte` inside the sandbox `<ul>`, positioned at the bottom of the list, plus adding a discreet, click-to-reveal option on that component to pick an existing directory on disk as the sandbox's workspace instead of always auto-creating a new one under `<Documents>/sandbox-mio`. The wide, inviting name-input affordance of the current form is deliberately preserved as the row's primary state; the existing-directory path is a small link that only expands into a folder picker once clicked, so it does not compete visually with "type a name to start a new project." The feature is entirely unimplemented: the create UI today is a plain `Field.Set`/`Input`/`Button` block that sits above and outside the `{#each}` loop (`+page.svelte:143-158`, `179-191`), and there is zero backend support anywhere for pointing a sandbox's workspace at an existing directory — `create_sandbox` (`src-tauri/src/lib.rs:69-81`) takes only a `name`, and `PodmanCliBackend::create` (`src-tauri/src/backends/mod.rs:318-352`) always derives the workspace path as `workspace_root().join(name)` (`workspace_path`, `mod.rs:77-80`) and unconditionally runs `std::fs::create_dir_all` on it. Relevant files: `src/routes/projects/+page.svelte`, `src/routes/projects/SandboxItem.svelte`, `src-tauri/src/backends/mod.rs`, `src-tauri/src/backends/types.rs`, `src-tauri/src/lib.rs`, `src-tauri/capabilities/default.json`, `src-tauri/Cargo.toml`, `package.json`.

## Current State

`src/routes/projects/+page.svelte:15-16` holds `projectName` and `projects` as page-level `$state`. The create form (`+page.svelte:143-158`) is a `Field.Set > Field.Group > Field.Field` wrapping an `Input` bound to `projectName` and a `Button` calling `createProject()` (`+page.svelte:59-70`), which trims the name, calls `invoke("create_sandbox", { name })` through the shared `createActionRunner()` busy/error/message wrapper (`action`, `+page.svelte:31`), then clears the input and calls `loadProjects()`. This form sits in the page markup *outside* the `{#if podmanUnavailable}...{:else if projects.length > 0}` conditional (`+page.svelte:166-191`), so today it renders even when the sandbox list is empty; the `<ul class="mt-6 space-y-2">` with the `{#each projects as project (project.id)}` loop over `<SandboxItem>` (`+page.svelte:180-189`) only renders in the `projects.length > 0` branch and is entirely absent when there are zero sandboxes.

`SandboxItem.svelte:30-43` takes `{ project: Project; deployment: Deployment | undefined; hosts: string[]; currentImageVersion: number | undefined; onChanged: () => void }` as props and roots its markup at `<li class="flex flex-col gap-2 rounded-lg border p-3 text-sm">` (`SandboxItem.svelte:192`). Any new create-item component needs to render as a matching `<li>` to sit visually consistent as the last entry of the same `<ul>`.

No dialog, modal, or separate route for creation exists anywhere in the repo. shadcn-svelte's `dialog` and `command` primitives are installed under `src/lib/components/ui/` (confirmed via `docs/features/responsive-panel/01_ideas.md`) but unused by any route — `AGENTS.md`'s "Currently available components" list predates their addition and is stale on this point.

Backend: `create_sandbox` (`src-tauri/src/lib.rs:69-81`) calls `store.ensure_base_image()`, `store.create(&name)`, then `runtime.init(&sandbox.workspace_path)`. The `SandboxBackend::create` trait method (`src-tauri/src/backends/types.rs:125`) is `async fn create(&self, name: &str) -> Result<Sandbox, BackendError>` — no path parameter exists at any layer. Inside `PodmanCliBackend::create` (`mod.rs:318-352`): `validate_name(name)` (`mod.rs:63-72`) rejects anything but ASCII alphanumerics plus `_`/`.`/`-` after the first character — this doubles as the path-safety gate, since `workspace_path` (`mod.rs:77-80`) joins `name` directly onto `workspace_root()` (`mod.rs:53-59`, `<Documents>/sandbox-mio` unless `SANDBOX_WORKSPACE_ROOT` is set). `create` then unconditionally does `std::fs::create_dir_all(&workspace)` (`mod.rs:325-328`, deliberately, per its comment, "so an unwritable path fails here, not silently via podman's auto-creation") before bind-mounting `workspace:/root/work` into the container.

No native directory-picker plumbing exists. `src-tauri/Cargo.toml` has no `tauri-plugin-dialog` or `tauri-plugin-fs` dependency (only `tauri-plugin-opener`, `tauri-plugin-shell`, `tauri-plugin-devtools`), `package.json` has no `@tauri-apps/plugin-dialog`, and `src-tauri/capabilities/default.json`'s `permissions` array has no `dialog:*` entries — only `core:default`, `opener:default`, `core:webview:allow-create-webview-window`, `core:window:allow-set-focus`, and a scoped `shell:allow-execute` for the bundled Mutagen sidecar. The `/projects` route renders inside the `main-global` webview (`src-tauri/src/workspace/mod.rs:29`, `GLOBAL_LABEL`), which is already listed in `capabilities/default.json`'s `webviews` array, so a new `dialog:allow-open` permission would need to cover that same webview label.

## Proposed Model

### `CreateSandboxItem.svelte`, a new list-item component

A new file, e.g. `src/routes/projects/CreateSandboxItem.svelte`, extracted from the current inline form (`+page.svelte:143-158`) and the `createProject`/`action` logic (`+page.svelte:31, 59-70`). It roots its markup at an `<li>` matching `SandboxItem.svelte:192`'s classes (`flex flex-col gap-2 rounded-lg border p-3 text-sm`) so it reads as one more row in the list rather than a visually distinct form. `+page.svelte` renders it as the last child of the same `<ul>` that maps `projects` to `<SandboxItem>` (`+page.svelte:180-189`), after the `{#each}` block closes. Collapsed state shows the same two controls as today: a name `Input` and a `Create` `Button`. The action-runner pattern (`createActionRunner`, `StatusRow`) moves into this component unchanged, since `SandboxItem.svelte` already follows the identical per-item action/status convention (`SandboxItem.svelte:54`, `StatusRow` import).

Because the component must now render even with zero existing sandboxes (the user's request that it be "part of the list" implies the list always has at least this one row), `+page.svelte`'s conditional structure (`+page.svelte:166-191`) needs to change so the `<ul>` renders whenever Podman is available, regardless of `projects.length`, with `{#each}` simply producing zero `<SandboxItem>` rows when the list is empty and `<CreateSandboxItem>` always rendering as the final row.

### The name input stays the primary, inviting affordance; the existing-directory option is a discreet click-to-reveal link

The current wide `Input` + `Create` `Button` (`+page.svelte:148-155`) is preserved as-is in `CreateSandboxItem` — its width and prominence are what make the row read as "type a name to start a new project," and that invitation is deliberately not diluted by a second prominent control next to it. The existing-directory path is instead a small, low-visual-weight text link beneath or beside the name row (e.g. "or use an existing folder…", styled like a `Button variant="link"` or plain muted text), matching the discreetness the user asked for rather than an "Advanced" toggle framing (a toggle/`Switch` reads as a settings-like binary option, which overstates what is really a one-time alternate path picker for this one row).

Clicking that link swaps the row's content in place: the name `Input` is replaced (not supplemented) by a "Choose folder…" trigger that opens the OS-native directory picker via `@tauri-apps/plugin-dialog`'s `open({ directory: true })`. Once a directory is picked, the row shows the chosen path plus a name `Input` pre-filled from the directory's basename (still editable, see Technology Choices) and the same `Create` `Button`. A small "back"/"x" affordance next to the picked-path display returns the row to its original wide-name-input state, discarding the picked path. Both the freshly-typed-name path and the picked-directory path terminate in the same `Create` `Button` calling the same `createProject()`-equivalent handler, just with `existing_path` set or unset depending on which mode is active. Only one control is visible at a time within the row, so the wide input stays the uncluttered default state and the folder option only costs a single click's worth of visual space until it's actually used.

### Backend: optional existing-path argument threaded through `create_sandbox`

`create_sandbox` (`lib.rs:69-81`) gains an optional parameter, e.g. `existing_path: Option<String>`, forwarded into `store.create(&name, existing_path.as_deref())`. The `SandboxBackend::create` trait signature (`types.rs:125`) becomes `async fn create(&self, name: &str, existing_path: Option<&str>) -> Result<Sandbox, BackendError>`, implemented by both `PodmanCliBackend::create` (`mod.rs:318-352`) and `MockBackend`'s equivalent. Inside `PodmanCliBackend::create`, the workspace-path branch becomes: when `existing_path` is `Some(p)`, validate `p` exists and is a directory (new `BackendError` variants, e.g. `PathNotFound`/`PathNotADirectory`, added alongside `InvalidName`/`WorkspaceCreate`/`DocumentsDirNotFound` in `types.rs`), skip `workspace_root()`/`workspace_path()`/`create_dir_all` entirely, and bind-mount `p` directly; when `existing_path` is `None`, behavior is unchanged from today (derive under `workspace_root()`, create the directory). `validate_name` continues to gate only the podman container `name` argument — it no longer doubles as a path-safety check when an explicit `existing_path` is supplied, since the path is not built by joining `name` onto anything in that branch.

### Native directory-picker plumbing (new dependency)

Add `tauri-plugin-dialog` to `src-tauri/Cargo.toml` and register it in the Tauri builder (`lib.rs`, alongside the existing `.plugin(tauri_plugin_opener::init())`-style calls). Add `@tauri-apps/plugin-dialog` to `package.json` for the frontend `open()` call. Add a `dialog:allow-open` permission (or a narrower dialog scope if the plugin supports one) to `src-tauri/capabilities/default.json`'s `permissions` array, applying to the `main-global` webview label the `/projects` route already runs in.

## Technology Choices with Tradeoffs

### List-item component embedded in the shared `<ul>`, not a modal or a separate "add" button

Chosen: extract the create form into `CreateSandboxItem.svelte` and render it as the last `<li>` inside the same `<ul>` that renders `SandboxItem` rows.

Alternatives evaluated:
- **A modal/dialog triggered by a small "+ Add" button at the bottom of the list** — rejected. The user's request is specifically that creation be part of the list, at the bottom, not an overlay; a modal would also duplicate the `Dialog` primitive setup this codebase hasn't adopted anywhere yet, and the current inline-form UX (no navigation, no overlay) already works, so this only needs to move, not change interaction model.
- **Leave the form where it is, only reorder it below the `<ul>` visually** — rejected. It would look adjacent but stay outside the semantic `<ul>`/`<li>` structure, so it would not read or behave as a peer list row (no consistent hover/border styling inherited "for free" from `<li>` peers, no natural fit if the list ever gets keyboard navigation or virtualization later).

### Directory selection via `tauri-plugin-dialog`'s native picker, not a freeform text path input

Chosen: `@tauri-apps/plugin-dialog`'s `open({ directory: true })`, the standard Tauri mechanism for OS-native folder pickers.

Alternatives evaluated:
- **A plain text `Input` where the user types or pastes an absolute path** — rejected. Error-prone (typos, wrong slash direction on Windows, no autocomplete), and still requires the exact same backend-side existence/directory validation as the native picker, so it saves no backend complexity while costing UX quality.
- **A custom in-app directory browser built on `tauri-plugin-fs`'s `readDir`** — rejected. Reimplements OS-native folder browsing (icons, recent locations, network drives) that the native dialog already provides for free; no reason to build this when `tauri-plugin-dialog` exists and the app has no other in-app file-browsing surface to justify the investment.

### Name stays a separate, editable field — not forced equal to the picked directory's basename

Chosen: the name input pre-fills from the picked directory's basename when a directory is chosen, but remains user-editable and is what actually flows through `validate_name` as the podman `--name`.

Alternatives evaluated:
- **Force `name` to always equal the picked directory's basename** — rejected. Directory basenames can contain characters `validate_name` disallows for a podman container name (spaces, unicode, a leading `.`, e.g. an existing `.dotfiles` project folder), and two different picked directories could share a basename (e.g. two different `backend/` folders on disk), which would collide as sandbox names with no way for the user to disambiguate.

### Single `create_sandbox` command gains an optional path argument, rather than a new `import_sandbox` command

Chosen: extend `create_sandbox`/`SandboxBackend::create` with an optional `existing_path` parameter.

Alternatives evaluated:
- **A separate `import_sandbox` command** — rejected. The two flows are identical except for how the workspace directory is sourced: both call `ensure_base_image()`, `store.create(...)`, and `runtime.init(...)` (`lib.rs:69-81`). A second command would duplicate that three-step wiring at the one call site that currently expresses it as "the explicit create step" (per the comment at `lib.rs:75-76`), and the frontend would need to pick between two near-identical commands depending on which flow the user chose in `CreateSandboxItem`, doubling the surface for no behavioral gain.

## Validation

Not yet spiked; this is fully greenfield (no directory-picker plugin, no existing-path backend support). Two risks are worth clearing with a small manual spike before committing to `02_dev.md`:
- Whether `tauri-plugin-dialog`'s `open({ directory: true })` resolves correctly when called from the `main-global` webview specifically (as opposed to the app's `main` window), given the app's multi-webview capability scoping in `capabilities/default.json`.
- Whether `podman create --volume <existing-non-empty-dir>:/root/work` and the subsequent `runtime.init(&sandbox.workspace_path)` (`lib.rs:79`) behave correctly against a directory that already contains project files (e.g. an existing `node_modules`, a `.git`, or a `mise.toml`), rather than the always-empty directory `create_dir_all` produces today.

## Open Questions

- **Empty-list conditional restructuring**: `+page.svelte:166-191`'s `{#if podmanUnavailable}...{:else if projects.length > 0}` branch currently omits the `<ul>` entirely when `projects.length === 0`. Does the new structure become `{:else}` (always render the `<ul>`, `{#each}` yields zero `SandboxItem`s, `CreateSandboxItem` always renders), or does an empty state need its own distinct copy/layout in addition to the create row?
- **Name vs. directory-basename prefill**: is the name field auto-filled from the picked directory's basename and then left editable (current lean, see Technology Choices), auto-filled and read-only, or never auto-filled (always a fresh required field even after picking a folder)?
- **Name collision handling**: if the typed/derived name collides with an existing sandbox, does the feature rely on the existing failure path (podman's `create --name` erroring, surfaced as `BackendError::CommandFailed` through `AppError`), or does `CreateSandboxItem` need a client-side pre-check against the already-loaded `projects` list to disable Create / show an inline error before the round trip?
- **Re-registering an already-tracked workspace directory**: should the picker block or warn when the chosen directory is itself already inside `workspace_root()` (i.e., it's an existing sandbox's own workspace, or a subdirectory of one)? Bind-mounting the same host path into a second container risks a Mutagen sync race or duplicate-container confusion; this needs a decision before `02_dev.md` designs the validation step.
- **Scope of the click-to-reveal link**: this document scopes it strictly to the existing-directory picker. `create_sandbox` today has no template/runtime/base-image-variant choice at all — should the reveal-on-click affordance be designed now with room to grow into those later (e.g. becoming a small options panel rather than jumping straight to the folder picker), or is that explicitly out of scope and deferred to a separate feature?
- **Single command vs. two-command split, final call**: Technology Choices leans toward one `create_sandbox` command with an optional `existing_path`, but this should be confirmed once the validation-error shape (new `BackendError` variants) is designed in `02_dev.md`, since a sufficiently different error surface between the two paths could tip the balance back toward separate commands.

## Common Gotchas

| Gotcha | Cause | Fix |
|---|---|---|
| Create row disappears when the sandbox list is empty | `+page.svelte:179` only renders the `<ul>` in the `projects.length > 0` branch; a naive port of the existing form into the list would inherit that gate | Restructure the conditional so the `<ul>` (and `CreateSandboxItem`) renders whenever Podman is available, independent of `projects.length` |
| Picked directory's name silently overwrites a user's intended sandbox name, or collides with an existing sandbox | Forcing `name = basename(existing_path)` removes the user's ability to disambiguate two same-named folders or work around characters `validate_name` disallows | Keep name pre-filled but editable, and run it through the same `validate_name` gate as manual creation regardless of path source |
| `validate_name`'s path-safety comment (`mod.rs:61-62`) becomes stale/misleading | That comment says `validate_name` doubles as the path-safety gate for `workspace_path`, which is only true on the auto-create branch; the `existing_path` branch bypasses `workspace_path` entirely | Update the comment when implementing to scope the path-safety claim to the auto-create branch only |
| Podman create fails or `runtime.init` misbehaves against a pre-populated directory | `create_dir_all`'s current always-empty-directory assumption doesn't hold once `existing_path` points at a real project with existing files (`.git`, `node_modules`, `mise.toml`) | Validate this with the spike described in Validation before assuming the bind-mount and mise init "just work" against arbitrary existing content |
| `dialog:allow-open` permission missing or scoped to the wrong webview | `/projects` renders in the `main-global` webview (`workspace/mod.rs:29`), not the `main` window; capabilities are scoped per webview label in `capabilities/default.json` | Add the webview label the route actually runs in to the permission's scope, and verify with a manual `open()` call from that route, not just from `main` |

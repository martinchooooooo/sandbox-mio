# Sandbox List Create-Item — E2E Test Plan

This document is the test plan for the feature built per `docs/features/sandbox-list-create/02_dev.md`: `CreateSandboxItem.svelte` as the always-present last row of the sandbox `<ul>`, and its click-to-reveal existing-directory picker backed by `create_sandbox`'s new `existing_path: Option<String>` parameter (Phase A) and `tauri-plugin-dialog` (Phase B). No spike has been run against the built application yet — none of `02_dev.md`'s four phases are implemented. This plan's De-Risking section below identifies one Windows-specific risk in Phase A (`std::fs::canonicalize`'s `\\?\` UNC prefix) that must be cleared by hand before the spec is trustworthy, in addition to the risks `01_ideas.md`/`02_dev.md` already flagged as unspiked (native dialog resolution from `main-global`, bind-mounting a pre-populated directory).

## Goal

The test must prove, through the running application, that a sandbox created from an **existing, pre-populated directory** ends up as a real, working container whose workspace is that exact directory — not a copy, not a fresh empty one. Concretely:

1. **`create_sandbox`'s `existing_path` branch runs the real backend path.** Calling it with a real directory must reach `PodmanCliBackend::create`'s `existing_path: Some(p)` branch (`src-tauri/src/backends/mod.rs`, per `02_dev.md` Phase A), canonicalize `p`, skip `workspace_root()`/`create_dir_all` entirely, and bind-mount `p` directly as `/root/work`. A test that only asserts the row appears in the UI would miss whether the *directory itself* (not a new one under `SANDBOX_WORKSPACE_ROOT`) was actually mounted.
2. **The pre-existing directory's content survives into the container.** A marker file written into the fixture directory before creation must be readable inside the container afterward (`podman exec <name> cat <marker>`), proving the bind-mount source was the real existing directory and not a wiped/re-created one — this is the entire point of the feature (users sandboxing an existing project, not starting from empty).
3. **No new directory is created under `SANDBOX_WORKSPACE_ROOT` for this sandbox.** Proves the `create_dir_all` codepath was genuinely skipped, not just that the container happens to work — a stray auto-created (and orphaned) directory under the workspace root would be a real bug the "happy path" alone would not surface.
4. **`runtime.init` (mise) succeeds against a directory that already has files in it**, not just an empty one — the `01_ideas.md` Validation section flagged this as unproven; the spec is the proof, not just a manual check.

A weaker test — e.g. one that creates the fixture directory *empty* — would pass even if the backend silently ignored `existing_path` and fell back to its normal empty-`create_dir_all` behavior; only asserting the marker file's presence inside the running container closes that gap.

## Existing Test Styles

- **App-driven WebdriverIO specs** (`e2e/test/specs/{standard,light,heavy}/*.spec.ts`) launch the compiled Tauri binary via `tauri-driver`, drive the real UI through page objects (`e2e/test/pageobjects/`), and read ground truth from `podman --connection` and the laptop filesystem. This feature's test belongs here.
- **Direct-`invoke` bridging within a WebDriver spec** — not a separate style, but an established technique used *inside* app-driven specs for UI surfaces `tauri-driver` cannot click into: `e2e/lib/workspace.ts:39-48` and `e2e/test/specs/standard/opencode-agent.spec.ts:19-27` both define a local `invoke<T>(cmd, args)` helper that calls `window.__TAURI_INTERNALS__.invoke(cmd, args)` via `browser.execute()`, reaching the real command handler through the real IPC bridge (not a stub — every existing use is a genuine pass-through call, never an override of `invoke` itself). `e2e/lib/workspace.ts:1-6`'s comment states the rationale directly: some surfaces are "separate native surfaces a WebDriver session attached to the app webview never sees, so specs cannot click into them." A native OS directory-picker dialog (opened by `tauri-plugin-dialog`'s `open({ directory: true })`) is exactly this category — grep across the whole `e2e/` tree found zero precedent, and no configuration in `e2e/wdio.conf.ts`, for driving a native OS file/folder dialog, and there is no Tauri or WebdriverIO capability in this project's stack that can do so. **Clicking the real "Choose folder…" button in automation would spawn a real, blocking Windows Explorer window that never closes — this must never happen in the spec.** The spec therefore drives the UI up to (and including) the click-to-reveal toggle, then swaps to the `invoke<T>()` bridge in place of the native-dialog click, mirroring `opencode-agent.spec.ts:17-18`'s documented rationale for the same technique ("the command bridge is the only way to drive `provision_opencode` in isolation from the install flow").
- **Standalone POCs** (`e2e/` root scripts) exercise a transport in isolation without launching the app. Not used for this feature.

## Chosen Approach

**Standard tier.** Add `e2e/test/specs/standard/sandbox-existing-folder.spec.ts`. Topology is local-only: one `LOCAL_CONNECTION` Podman machine (`mio-tests`), no remote host — the feature is entirely local-workspace-sourcing, with no deploy/remote-sync interaction. This is the tier that proves the actual value of the feature (a real bind-mount of a real pre-populated directory, real `mise` init against it), matching `e2e/AGENTS.md`'s "write the happy/common-path spec against the real backend first" rule; the `MockBackend`'s `create` (per `02_dev.md` Phase A) does no filesystem validation at all, so it cannot exercise canonicalization, the `PathAlreadyTracked`/`PathNotFound`/`PathNotADirectory` checks, or the actual bind-mount — a `light` spec against the mock would only prove the frontend called `invoke` with the right arguments, not that the feature works.

**Paired light spec**, per `e2e/AGENTS.md` rule 4: add `e2e/test/specs/light/sandbox-create-row-ui.spec.ts` for two UI/store-logic edge cases that are awkward or slow to provoke against real infra:
- The create row renders (and the click-to-reveal toggle works) even when the sandbox list is empty — exercising the `{:else}` restructuring in `+page.svelte` resolved in `02_dev.md`'s Resolved Decisions. The mock backend starts with zero sandboxes deterministically; provoking a genuinely empty list against the real backend would require destroying every other sandbox on the test machine first, which is slow and racy against parallel spec runs.
- The client-side name-collision pre-check (also in Resolved Decisions) shows an inline error without a round trip when the typed name matches an already-loaded project. This is UI/store logic (`projects.some(p => p.name === name)`), not backend behavior, and the mock backend's `list_sandboxes` is fast and deterministic for seeding a known collision.

The already-tracked-path backend guard (`PathAlreadyTracked`, `02_dev.md` Phase D) is deliberately **not** covered by either spec — see Sequencing.

## Harness Changes

No changes to `e2e/wdio.conf.ts` `onPrepare`/`beforeSession` are required: the standard spec uses the same `mio-tests` machine and debug-binary build every other standard spec already relies on, and the light spec uses the existing `MIO_MOCK_BACKEND=1` light-suite wiring (`e2e/AGENTS.md`'s "Mocked tier design" section) unchanged.

The standard spec's own setup/teardown:
- `before`: create a fixture directory under `path.join(os.homedir(), ".sandbox-mio-e2e-existing", "existing-${Date.now()}")` (siblings `SANDBOX_WORKSPACE_ROOT`'s `.sandbox-mio-e2e` convention, `e2e/wdio.conf.ts:18-24`, and stays under the user profile the podman machine already auto-mounts) via `fs.mkdirSync(dir, { recursive: true })`, then write a marker file (`fs.writeFileSync(path.join(dir, "marker.txt"), "e2e-existing-dir-marker")`) with known, greppable content.
- `after`: `podman(LOCAL_CONNECTION, ["rm", "-f", projectName], { check: false })` (matching `runtime-management.spec.ts`'s cleanup pattern), then `fs.rmSync(fixtureDir, { recursive: true, force: true })`.

### Page object additions (`e2e/test/pageobjects/projects.page.ts`)

The current `nameInput`/`createButton` getters (`projects.page.ts:11-17`) are page-global `$(...)` lookups, not scoped to a row — after Phase C moves the form into `CreateSandboxItem.svelte`'s `<li>`, these selectors keep resolving correctly by accident (only one such input/button exists on the page), but the plan adds an explicit `createRow` getter and scopes new members to it, and asks Phase C to add a `data-create-row` attribute to the component's root `<li>` (matching the existing `data-specs`/`data-specs-ready` convention in `src/routes/models/+page.svelte:230,249` for stable, non-text-dependent test hooks) so `createRow` does not depend on the row containing no other text a future locale/copy change might alter.

```ts
// The always-present create row, last <li> in the sandbox list (docs/features/sandbox-list-create).
get createRow(): Element {
    return $("li[data-create-row]");
}

get nameInput(): Element {
    return this.createRow.$("input[placeholder='my-project']");
}

get createButton(): Element {
    return this.createRow.$("button=Create");
}

// The discreet link that reveals the folder picker (initial "name" mode → "folder" mode).
get useExistingFolderLink(): Element {
    return this.createRow.$("button*=existing folder");
}

// Visible only in "folder" mode; clicking it in real automation would spawn a real, blocking OS
// dialog (see 03_e2e.md's Existing Test Styles) — specs assert its presence/absence to confirm
// mode-toggle wiring, but never click it.
get chooseFolderButton(): Element {
    return this.createRow.$("button*=Choose folder");
}

// Resets "folder" mode back to "name" mode, discarding any picked path.
get backToNameButton(): Element {
    return this.createRow.$("[aria-label='Back']");
}

async useExistingFolderMode(): Promise<void> {
    await (await this.useExistingFolderLink).click();
}
```

## Spec Scenario

### `e2e/test/specs/standard/sandbox-existing-folder.spec.ts`

```
describe("Sandbox from an existing folder", function () {
    this.timeout(180000);
    projectName = `e2e-existing-${Date.now()}`;
    fixtureDir = path.join(os.homedir(), ".sandbox-mio-e2e-existing", `existing-${Date.now()}`);
    row = ProjectsPage.row(projectName);
```

1. **Prepare the fixture.** `fs.mkdirSync(fixtureDir, { recursive: true }); fs.writeFileSync(path.join(fixtureDir, "marker.txt"), "e2e-existing-dir-marker")`. This is the "existing project the user already has on disk" the feature targets.
2. **Open the projects page and reveal the folder-picker mode.** `await ProjectsPage.open(); await ProjectsPage.ensurePodmanReady(); await ProjectsPage.useExistingFolderMode()`. Assert `await ProjectsPage.chooseFolderButton.isDisplayed()` and `await ProjectsPage.nameInput.isDisplayed() === false` (or the input has been replaced) — proves the click-to-reveal toggle actually swapped the row into "folder" mode (Phase C wiring), without touching the native dialog.
3. **Bypass the native dialog and drive the real backend path directly.** `await invoke("create_sandbox", { name: projectName, existingPath: fixtureDir })` using the local `invoke<T>()` bridge (per Existing Test Styles). This is the one step that cannot go through a real button click; it exercises exactly what clicking "Choose folder…", picking `fixtureDir` in the OS dialog, then clicking the row's `Create` button would have called, per `02_dev.md`'s `CreateSandboxItem` handler design.
4. **Assert the row appears.** `await row.waitForDisplayed(timeout)` — the existing `ProjectRow` component object needs no changes; the row it resolves (`li*=${projectName}`, `project-row.component.ts:20`) is the *other* kind of `<li>` in the same list (a `SandboxItem`, not the create row), and is unaffected by this feature.
5. **Assert the marker file is present inside the container.** `podmanOk(LOCAL_CONNECTION, ["exec", projectName, "cat", "/root/work/marker.txt"])` returns `"e2e-existing-dir-marker"`. This is the core proof (Goal #2): the bind-mount source was the real, pre-populated `fixtureDir`, not a fresh empty directory.
6. **Assert no directory was auto-created under the workspace root.** `fs.existsSync(path.join(process.env.SANDBOX_WORKSPACE_ROOT!, projectName)) === false`. Proves Goal #3 — the `create_dir_all` branch was skipped, not just harmlessly redundant.
7. **Assert the returned `workspace_path` is the fixture directory.** Read back via `invoke<Project[]>("list_sandboxes")`, find the entry by name, assert its `workspace_path` matches `fixtureDir` (allowing for the forward-slash normalization `workspace_path()`/the new `existing_path` branch already apply, per `02_dev.md` Phase A).
8. **Start the sandbox and confirm mise ran.** `await row.start(); await row.waitForRunning();` then `podmanOk(LOCAL_CONNECTION, ["exec", projectName, "mise", "--version"])` succeeds. Proves Goal #4 — `runtime.init` completed against a non-empty pre-existing directory, not just that the container exists.
9. **Cleanup**: `after` — `podman(LOCAL_CONNECTION, ["rm", "-f", projectName], { check: false }); fs.rmSync(fixtureDir, { recursive: true, force: true })`.

### `e2e/test/specs/light/sandbox-create-row-ui.spec.ts`

Runs against `MIO_MOCK_BACKEND=1`, no podman. Two independent `it` blocks:

1. **Empty list still shows the create row.** With a freshly launched mock-backend app (no sandboxes created yet in this session), assert `ProjectsPage.createRow` is displayed and `ProjectsPage.useExistingFolderLink` is displayed — proves the `{:else}` restructuring (`02_dev.md` Resolved Decisions) renders the `<ul>`/create row independent of `projects.length`.
2. **Typed name collides with an existing project, no round trip.** Create one mock sandbox by name via the UI (fast against the mock), then in the create row's "name" mode type the same name again and click `Create`. Assert an inline error appears (`row`'s equivalent `StatusRow` error text) without waiting on any podman-shaped delay, and assert (via a short `browser.waitUntil` with a tight, e.g. 2s, timeout) that a second sandbox with that name never gets created — proves the client-side pre-check (Resolved Decisions) fires before `create_sandbox` is even called, distinguishable from the backend-side collision path (which the standard-tier `project-start-stop.spec.ts`-style specs already implicitly rely on *not* needing to hit, since names there are always unique per run).

## De-Risking Spike Results

Not yet spiked; nothing in `02_dev.md` is implemented. Three risks, in the order they block the spec:

**Risk 1 — Windows `std::fs::canonicalize`'s `\\?\` UNC prefix may break the podman `-v` bind-mount (feature-fix concern, blocks Spec step 5).** `02_dev.md` Phase A's `resolve_workspace` helper canonicalizes the picked path before using it as the bind-mount source. On Windows, `std::fs::canonicalize` returns an extended-length path prefixed `\\?\` (e.g. `\\?\C:\Users\...`), which `workspace_path()`'s existing `.replace('\\', "/")` convention (`backends/mod.rs:77-80`) was never designed to handle and which `podman -v` / the machine's Windows-path-to-VM-path translation may reject or mis-translate. `dunce` is already present in `Cargo.lock` (a transitive dependency, not a direct one) and is the standard fix (`dunce::canonicalize` normalizes without the `\\?\` prefix on Windows, falling back to plain `canonicalize` elsewhere) — if this risk clears as real, Phase A should add `dunce` as a direct dependency and use `dunce::canonicalize` instead of `std::fs::canonicalize`. To clear: after Phase A lands, run the standard spec's steps 3-5 by hand once (`create_sandbox` with a real Windows path, then `podman exec ... cat marker.txt`) before trusting the automated spec; if it fails with a "no such file or directory" inside the container despite the host-side file existing, this is the cause.

**Risk 2 — native dialog resolution from `main-global` webview (already flagged in `01_ideas.md` Validation, unspiked, feature-fix or test-scope concern).** This risk only affects the actual "Choose folder…" click, which the spec deliberately never automates (see Existing Test Styles). It remains a manual-only check: after Phase B lands, click the real button in the running app once and confirm the native picker opens and resolves. If it fails, the fix is scoped entirely inside `capabilities/default.json`'s webview-label permission grant (per `02_dev.md` Phase B / Common Gotchas) and does not affect the automated spec's validity, since the spec bypasses the click by design.

**Risk 3 — `chooseFolderButton*=Choose folder` and `useExistingFolderLink*=existing folder` text selectors may not match the actual rendered copy (test concern).** `02_dev.md` Phase C names the link/button text loosely ("or use an existing folder…", "Choose folder…") without finalizing exact copy or `messages/en.json` keys (i18n is deferred per the project's `feature-implement` convention until the UI is approved). To clear: after Phase C lands and the UI is approved (including its final `messages/en.json` strings), inspect the rendered button/link text and update the page-object selectors in this document and in `projects.page.ts` to match exactly, before the spec is written.

## Sequencing

1. Implement `02_dev.md` Phase A (backend `existing_path` support), including the `dunce`/canonicalization fix if Risk 1 clears as real.
2. Clear Risk 1 by hand: call `create_sandbox` with a real existing directory (e.g. via the Rust test harness or a manual `invoke` from devtools) and confirm the bind-mount and `mise` init succeed against it, before trusting step 5/8 of the standard spec.
3. Implement `02_dev.md` Phase B (dialog plugin plumbing) and Phase C (`CreateSandboxItem.svelte` + list restructuring), including the `data-create-row` attribute this plan adds to Phase C's scope.
4. Clear Risk 3 by hand: confirm the final rendered link/button text and update selectors.
5. Add the `projects.page.ts` page-object members from Harness Changes.
6. Write and run `e2e/test/specs/standard/sandbox-existing-folder.spec.ts`.
7. Implement `02_dev.md` Phase D (name-collision and already-tracked-path guards) only if the light spec's collision scenario (or a future spec) needs it — the standard spec above does not depend on Phase D.
8. Write and run `e2e/test/specs/light/sandbox-create-row-ui.spec.ts`.
9. Clear Risk 2 by hand once, informally, after Phase B — no automated coverage will ever exist for the literal native-dialog click.

`PathAlreadyTracked` (Phase D) is intentionally left without e2e coverage in this plan: exercising it meaningfully requires two real sandboxes and a real canonicalized-path comparison the mock backend cannot perform, making it expensive for a rejection-path assertion; a Rust-level unit test on `resolve_workspace`/`PodmanCliBackend::create` is the better-leverage place to prove it, out of scope for this document.

## Environment Notes

A future session implementing these specs needs:
- `mio-tests` Podman machine running and the mise base image staged (standard spec) — handled by `onPrepare` in `e2e/wdio.conf.ts`; no `REMOTE_CONNECTION` needed.
- `SANDBOX_WORKSPACE_ROOT` set by `wdio.conf.ts` (`e2e/wdio.conf.ts:24`) — the standard spec's step 6 reads this directly to assert no stray directory was created.
- Write access to `path.join(os.homedir(), ".sandbox-mio-e2e-existing")` for the fixture directory — a new sibling of the existing `.sandbox-mio-e2e` convention, under the user profile the podman machine already auto-mounts (no new machine-mount configuration needed).
- The compiled debug Tauri binary including Phases A, B, and C (the light spec additionally needs only Phase C, since it runs against the mock backend and never reaches Phase A's real bind-mount code).
- Risk 1 and Risk 3 cleared by hand before each respective spec is authored (see Sequencing); Risk 2 is permanently manual-only.

## Common Gotchas

| Gotcha | Cause | Fix |
|---|---|---|
| Standard spec step 5 fails with "no such file or directory" inside the container despite the host file existing | `std::fs::canonicalize`'s `\\?\` UNC prefix on Windows was passed straight through to `podman -v`, which does not understand it (Risk 1) | Switch Phase A's canonicalization to `dunce::canonicalize` (already a transitive `Cargo.lock` dependency; add it directly) instead of `std::fs::canonicalize` |
| The spec hangs indefinitely with no timeout/error | Something clicked the real "Choose folder…" button, spawning a real native OS Explorer window that `tauri-driver` cannot see or dismiss | Audit the spec for any `chooseFolderButton.click()` call — the button must only ever be asserted for visibility, never clicked; use the `invoke<T>("create_sandbox", ...)` bridge instead |
| `useExistingFolderLink`/`chooseFolderButton` selectors never match | Phase C's final rendered copy or `messages/en.json` keys differ from this document's placeholder text ("or use an existing folder…", "Choose folder…") | Inspect the actual rendered button text after Phase C lands and update both this document's selectors and `projects.page.ts` (Risk 3) |
| Step 6's workspace-root check is flaky/fails intermittently | A previous failed test run left a stray directory under `SANDBOX_WORKSPACE_ROOT/<same-name>` from an unrelated run using a colliding name pattern | Keep `projectName` timestamp-uniqued (`e2e-existing-${Date.now()}`), matching every other spec's convention, so cross-run collisions cannot happen |
| Fixture directory cleanup leaves files behind on a failed run | `after` only runs if `before`/the test body did not throw before registration, or `fs.rmSync` itself fails on a locked file (e.g. podman still holds the bind-mount open) | Ensure `podman rm -f` (which unmounts) runs strictly before `fs.rmSync` in the `after` hook, matching the ordering already specified in Harness Changes |
| Light spec's collision scenario is flaky | The inline client-side error and the mock backend's own (near-instant) response race, and a naive fixed `browser.pause` either over- or under-waits | Use `browser.waitUntil` polling the error element's text, not a fixed pause, matching the polling pattern `package-autocomplete.spec.ts` (`docs/features/package-autocomplete/03_e2e.md`) already establishes for this codebase |

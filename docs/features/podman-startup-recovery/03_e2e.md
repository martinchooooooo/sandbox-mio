# Podman Startup Recovery E2E Test Plan

This document is the test plan for the Podman startup recovery feature described in `docs/features/podman-startup-recovery/02_dev.md`. The test proves that when `podman-machine-default` is stopped, the app shows a recovery screen, and clicking "Start Podman" restarts the machine and loads the projects page normally. No spike has been run for the spec itself; the failure sequence that produced the underlying recovery logic was already captured in `01_ideas.md` Validation (2026-06-29).

## Goal

The test must exercise the real `check_podman_ready` and `start_podman_machine` Tauri commands, the `activity::open`/`progress`/`succeed`/`fail` helpers in `src-tauri/src/activity/mod.rs`, and the `podman machine start` + `podman machine ssh` (socket activation via `setsid`) subprocess chain. A weaker test — one that mocks the Podman CLI, stubs the Tauri commands, or never actually stops the machine — would not prove that the `setsid` socket-activation script survives the SSH channel close, that `poll_ready` reaches a live socket, or that the frontend correctly gates the project list behind a successful probe.

The test also proves that sandbox operations (which target `mio-tests` via `PODMAN_CONNECTION`) are unaffected: after the recovery screen clears, creating a project must succeed on `mio-tests`.

## Existing Test Styles

All app-driven tests are WebdriverIO specs in `e2e/test/specs/*.ts`, exercised through the Tauri driver (`tauri-driver`) which controls a real debug build of `sandbox-mio`. Page state is inspected through WebdriverIO element queries (no DOM snapshots); CLI state is verified with `spawnSync("podman", ...)` calls via `e2e/lib/podman-connection.ts`. The existing spec pattern uses:

- `before`/`after` hooks for per-suite setup and teardown (`agent-setup.spec.ts`, `deploy-remote.spec.ts`)
- `assert` from `node:assert` for plain-value assertions with diagnostic messages
- `browser.waitUntil` for async convergence with a `timeoutMsg`
- `spawnSync("podman", ...)` for out-of-band CLI verification without going through the app

The new spec belongs in the default suite (`e2e/test/specs/podman-startup-recovery.spec.ts`) — not in `heavy/` — because it does not download large artefacts. It does take 30–60 seconds (machine stop + start cycle), so it sets a suite-level `this.timeout(120000)`.

## Chosen Approach

The spec targets `podman-machine-default` directly: it stops the machine in `before`, navigates to `/projects` to trigger `onMount` → `check_podman_ready`, exercises the recovery UI, and verifies that the projects page loads after `start_podman_machine` succeeds. The sandbox operations that follow continue to use `mio-tests` (the `PODMAN_CONNECTION` the harness sets in `beforeSession`), which is left untouched throughout.

This topology (two distinct machines: `mio-tests` for sandboxes and `podman-machine-default` for the startup probe) is exactly the production topology the feature is designed for. It also ensures the `wsl --shutdown` guard is exercised: because `mio-tests` is running during the test, `check_other_machines_running()` returns `true` and the shutdown step is skipped. The guard cannot be tested in a run where `mio-tests` is active; that path is excluded from the spec and documented under Environment Notes.

## Harness Changes

### `e2e/wdio.conf.ts`

No changes to `onPrepare` are needed. `onPrepare` already provisions only `mio-tests` and `mio-tests-remote`; it does not touch `podman-machine-default`. The spec's own `before` hook handles stopping the machine.

Add a guard to `onPrepare` after the existing `provisionMachine` calls that checks whether `podman-machine-default` exists and is initialized. If the machine has never been initialized (not listed in `podman machine list`), the guard should print a diagnostic and abort so the spec fails with a clear message rather than timing out:

```ts
// Guard: podman-startup-recovery.spec.ts needs podman-machine-default to be initialized.
const defaultMachineRaw = spawnSync(
  "podman", ["machine", "list", "--format", "json"],
  { encoding: "utf8", shell: true }
);
const defaultMachines: Array<{ Name: string }> = JSON.parse(defaultMachineRaw.stdout || "[]");
if (!defaultMachines.some((m) => m.Name === "podman-machine-default")) {
  console.warn(
    "[e2e] podman-machine-default is not initialized. " +
    "podman-startup-recovery.spec.ts will skip its before() step and fail on navigation. " +
    "Run `podman machine init && podman machine start` once to initialize it."
  );
}
```

This is a warning, not an `process.exit(1)` abort, so the rest of the suite still runs on machines where `podman-machine-default` does not exist (e.g., a CI environment that only provisions `mio-tests`).

## Spec Scenario

**File**: `e2e/test/specs/podman-startup-recovery.spec.ts`

```ts
import assert from "node:assert";
import { spawnSync } from "child_process";
import ProjectsPage from "../pageobjects/projects.page.js";

describe("Podman startup recovery", function () {
  this.timeout(120000);

  before(() => {
    const stop = spawnSync("podman", ["machine", "stop", "podman-machine-default"], {
      encoding: "utf8", shell: true,
    });
    // A non-zero exit means the machine was already stopped or does not exist — treat as OK.
    if (stop.status !== 0) {
      console.warn(
        `[e2e] podman machine stop podman-machine-default exited ${stop.status}: ${stop.stderr.trim()}. ` +
        "Proceeding — the machine may already be stopped."
      );
    }
  });

  after(() => {
    // The spec's recovery flow should have left the machine running. If not, best-effort restart
    // so subsequent manual runs are not affected.
    spawnSync("podman", ["machine", "start", "podman-machine-default"], {
      encoding: "utf8", shell: true,
    });
  });

  // steps 1–6 below
});
```

**Step 1 — Navigate to a known non-projects route to force a fresh `onMount`.**

```ts
it("navigates home so the projects onMount fires fresh on the next step", async () => {
  const origin = new URL(await browser.getUrl()).origin;
  await browser.url(`${origin}/`);
  const homeHeading = $("h1");
  await homeHeading.waitForDisplayed({ timeout: 5000 });
});
```

This step is required because the app may already be on `/projects` from a prior spec, and `onMount` only fires on route entry, not on revisiting the same route.

**Step 2 — Navigate to `/projects` and assert the recovery screen appears.**

```ts
it("shows the 'Start Podman' screen when the machine is stopped", async () => {
  await ProjectsPage.open();
  const startButton = $("button=Start Podman");
  await startButton.waitForDisplayed({ timeout: 15000,
    timeoutMsg: "Expected 'Start Podman' button but it did not appear. " +
      "check_podman_ready may have returned Ok (machine may still be running) or the button label may have changed."
  });
  const explanation = $("p=Podman machine is not running");
  await explanation.waitForDisplayed({ timeout: 5000,
    timeoutMsg: "Explanation text 'Podman machine is not running' not visible alongside the Start Podman button."
  });
});
```

This assertion proves `check_podman_ready` detected the stopped machine and the frontend rendered the recovery screen.

**Step 3 — Click "Start Podman" and assert the button enters its loading state.**

```ts
it("clicking Start Podman enters a loading state", async () => {
  const startButton = $("button=Start Podman");
  await startButton.click();
  // The button acquires aria-busy="true" while the action runner is in flight.
  await browser.waitUntil(
    async () => {
      const busy = await startButton.getAttribute("aria-busy");
      const disabled = await startButton.getAttribute("disabled");
      return busy === "true" || disabled !== null;
    },
    { timeout: 5000, interval: 200,
      timeoutMsg: "Button did not enter a loading/disabled state after click." }
  );
});
```

**Step 4 — Wait for the activity center to show the `podman-startup` task.**

```ts
it("activity center shows a running 'Starting Podman machine' task", async () => {
  // The activity center bell badge appears when a task is running. Open the panel.
  const bell = $("[aria-label='Activity']");
  await bell.waitForDisplayed({ timeout: 10000,
    timeoutMsg: "Activity center bell not found. ActivityCenter.svelte may not be mounted in the layout."
  });
  await bell.click();
  const taskLabel = $("*=Starting Podman machine");
  await taskLabel.waitForDisplayed({ timeout: 10000,
    timeoutMsg: "Task label 'Starting Podman machine' not visible in the activity panel."
  });
});
```

This proves `start_podman_machine` called `activity::open` and the task reached the frontend store.

**Step 5 — Wait for recovery and assert the projects page loads normally.**

```ts
it("projects page loads after recovery completes", async () => {
  // The 'Start Podman' screen is replaced by the normal sandbox list once recovery succeeds.
  const createButton = $("button=Create");
  await createButton.waitForDisplayed({ timeout: 90000,
    timeoutMsg: "Create button (normal projects page) did not appear after Start Podman completed. " +
      "`start_podman_machine` may have failed — check the activity center panel for an error."
  });
  // Confirm the recovery screen is gone.
  const startButton = $("button=Start Podman");
  await expect(startButton).not.toBeDisplayed();
});
```

The 90-second timeout covers `podman machine start` (up to 30 s) + socket activation (up to 7 s) + polling (up to 4 × 0.5 s) + activity center event delivery.

**Step 6 — Verify `podman-machine-default` is now reachable via the CLI.**

```ts
it("podman-machine-default is reachable after recovery", async () => {
  const info = spawnSync(
    "podman", ["--connection", "podman-machine-default", "info", "--format", "json"],
    { encoding: "utf8", shell: false }
  );
  assert(
    info.status === 0,
    `podman --connection podman-machine-default info failed (exit ${info.status}): ${info.stderr.trim()}. ` +
      "The socket may not have been activated — check activate_podman_socket and poll_ready in backends/mod.rs."
  );
});
```

This is the decisive CLI assertion. It proves `activate_podman_socket` launched `podman system service` with `setsid` and that `poll_ready` reached the live socket — not just that the machine reported `Running: true` in `podman machine list`.

**Step 7 — Create a sandbox to prove sandbox operations are unaffected.**

```ts
it("can create a sandbox on mio-tests after Podman recovery", async () => {
  const name = `e2e-recovery-${Date.now()}`;
  const row = await ProjectsPage.createProject(name, { timeout: 600000 });
  await row.waitForDisplayed(10000);
  // Cleanup
  const { podman } = await import("../../lib/podman-connection.js");
  const { LOCAL_CONNECTION } = await import("../../lib/podman-connection.js");
  podman(LOCAL_CONNECTION, ["rm", "-f", name], { check: false });
});
```

This proves that the startup probe (which targets `podman-machine-default`) does not interfere with sandbox operations on `mio-tests`.

## De-risking Spike Results

No spec spike has been run. The underlying recovery mechanics (stop machine → activate socket via `setsid` → verify via `podman info`) were validated manually on 2026-06-29 (see `01_ideas.md` Validation). The spec is safe to write once Phases A–F of `02_dev.md` are implemented, because all primitives are proven.

One risk not yet cleared: whether `podman machine stop podman-machine-default` leaves the WSL instance in a state where `check_podman_ready` correctly identifies it as stopped via `podman machine list --format json` (field `Running: false`). The manual session confirmed the stopped state showed no "Currently running" marker in `podman machine ls`, but the JSON field name was not verified. The `machine_is_running()` helper in Phase C of `02_dev.md` must parse `Running` from the JSON output. Run `podman machine stop podman-machine-default && podman machine list --format json` and confirm the field is `"Running": false` on this machine before finalising Phase C.

## Environment Notes

The following must be true before the spec is run:

- `podman-machine-default` must be **initialized** (`podman machine init` run at least once). The spec's `before` hook stops it but does not init it. The harness guard in `wdio.conf.ts` warns but does not abort if the machine is absent.
- `mio-tests` must be provisioned and running (handled by existing `onPrepare` in `wdio.conf.ts`).
- The `wsl --shutdown` path is **not exercised** when `mio-tests` is running. This is by design — `check_other_machines_running()` correctly skips the shutdown. The `wsl --shutdown` code path can only be exercised manually, after stopping all other machines.
- After `before` stops `podman-machine-default`, the machine's socket (`/run/user/1000/podman/podman.sock`) is also gone. The spec therefore exercises both the "machine stopped" detection (via `podman machine list`) and the socket activation path on recovery.
- If the spec fails between Steps 2 and 5 (machine stopped but recovery did not complete), the `after` hook attempts `podman machine start podman-machine-default`. If that also fails, `podman-machine-default` is left stopped. Subsequent runs of the spec can still proceed because the `before` hook treats a non-zero exit from `podman machine stop` as a no-op.

## Common Gotchas

| Gotcha | Cause | Fix |
|---|---|---|
| "Start Podman" button never appears; projects page loads normally | `podman-machine-default` was not stopped before the spec navigated to `/projects` (machine was already running), so `check_podman_ready` returned `Ok` | Confirm the `before` hook ran and `podman machine stop` exited; add a guard assertion after stop that verifies `podman machine list` shows `Running: false` for the machine |
| `check_podman_ready` throws `Backend` instead of `PodmanUnavailable` | `podman_global` cannot spawn the `podman` executable (not in PATH), which returns `BackendError::CommandFailed` rather than `AppError::PodmanUnavailable` | Ensure the `podman` binary is in PATH for the `tauri-driver` process; the `beforeSession` env inherits from `process.env` which should include the PATH configured in `onPrepare` |
| Step 5 times out even though the machine started | `check_podman_ready` was called again after `start_podman_machine` returned `Ok` and found the socket missing (race between socket bind and poll) | Verify `poll_ready` in `backends/mod.rs` is running up to 4 attempts with 500 ms sleep; add a log line in `activate_podman_socket` to confirm the setsid script ran |
| Step 6 fails (`podman info` exits non-zero) even though Step 5 passed | The frontend `check_podman_ready` probe used an internal `verify_host` that happened to succeed on a stale connection, but the socket died after the poll | Confirm `activate_podman_socket` uses `setsid` (not plain `&`); without `setsid` the service dies when the SSH channel closes, leaving the socket briefly reachable during polling but dead afterward |
| Step 4 (activity panel) times out because the bell badge never appears | The activity center feature is not yet built (layout does not mount `ActivityCenter.svelte`) | Implement the activity center feature through its Phase C before running this spec, or skip Step 4 and come back to it after the activity center lands |
| `before` hook fails because `podman machine stop` exits non-zero | The machine does not exist or was already stopped; the hook treats this as acceptable | The hook logs a warning and continues; if the machine truly does not exist, the `onPrepare` guard will have warned and Step 2 will fail with a clear `timeoutMsg` |
| Recovery screen does not disappear after `start_podman_machine` succeeds | The frontend did not call `check_podman_ready` again after success, or `loadAll()` was not called | Check Phase F of `02_dev.md`: `startPodman()` must set `podmanUnavailable = false` and call `loadAll()` on success |
| `wsl --shutdown` kills `mio-tests` during the spec | `check_other_machines_running()` returned `false` because `mio-tests` was briefly stopped or the machine list parse failed, so the shutdown ran | Ensure `check_other_machines_running()` is conservative (returns `true` on parse error) as specified in Phase C of `02_dev.md` |

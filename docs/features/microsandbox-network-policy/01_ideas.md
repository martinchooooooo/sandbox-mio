# Microsandbox Network Policy: Native Egress Policy, Host-Held Secrets, and a Chained Traffic Proxy

This document covers securing a microsandbox-provider sandbox's outbound traffic with microsandbox's own host-side network stack (default-deny egress rules, strict hostname matching, host-held secrets) and chaining a mitmproxy sidecar microsandbox VM behind microsandbox's outbound SOCKS5 proxy option so `TrafficPanel` works for microsandbox sandboxes. Nothing of this feature is implemented. Today `MsbProvider::create_instance` (`src-tauri/src/provider/msb.rs`) passes no network or secret flags at all, and every proxy operation is refused for microsandbox (`docs/features/network-proxy/02_dev.md`, Resolved Decision 9). The design depends on microsandbox 0.7.12, which the development host now has installed (upgraded from 0.6.6 on 2026-11-01); four spikes ran against it (Validation). The remaining 0.6 → 0.7 code upgrade is this feature's first phase. The former open questions were resolved by the user on 2026-11-02 (Resolved Decisions). NVIDIA OpenShell was evaluated as an alternative and as a complement and is deferred (`docs/features/microsandbox-network-policy/04_improvements.md`). Relevant files: `src-tauri/src/provider/msb.rs`, `src-tauri/src/provider/types.rs`, `src-tauri/src/proxy/mod.rs`, `src-tauri/src/proxy/flowlog.rs`, `src-tauri/src/proxy/rules.rs`, `src-tauri/src/services/sandbox.rs`, `src/routes/projects/CreateSandboxItem.svelte`, `src/routes/projects/ProxyPanel.svelte`.

## Current State

**Microsandbox sandboxes reach the network unmediated by this app.** `MsbProvider::create_instance` (`src-tauri/src/provider/msb.rs`) builds `msb create <image> --name <name> --mount-named <volume>` plus labels, and rejects any `InstanceSpec` with a `network` attachment or a non-empty `env` (`src-tauri/src/provider/types.rs`). Microsandbox's built-in default is deny-by-default egress with an implicit `allow@public` rule, so private ranges, loopback, link-local and the cloud metadata endpoint are already blocked, but the app sets no allowlist, no secrets and no TLS interception.

**The host runs `msb` 0.7.12.** The upgrade used `msb self update`, which on Windows must be run from a copy of `msb.exe` because the running executable cannot overwrite itself. Spike A replayed every `msb` call `MsbProvider` makes and found no break in argv or output parsing. The one behavioural change is that `msb create` now validates the image workdir in the guest: the base image's `/root/work` must exist, so a create without the workspace volume mount fails (`docs/features/microsandbox-network-policy/spike/01_egress-baseline.md`).

**The proxy feature family is Podman-only.** `network-proxy` (implemented: `src-tauri/src/proxy/mod.rs` `create_proxy`, `src-tauri/resources/mitm_addon.py`) and `proxy-traffic-viewer` (implemented: `src-tauri/resources/mitm_flowlog_addon.py`, `src-tauri/src/proxy/flowlog.rs`, `TrafficPanel.svelte`) run a mitmproxy container on a private DNS-disabled Podman bridge and steer the sandbox into it with `HTTP_PROXY`/`HTTPS_PROXY` environment variables. `MsbProvider` has no sidecar support: `create_sidecar`, `pull_image`, `create_network` and `remove_network` in `src-tauri/src/provider/msb.rs` all return `ProviderError::CommandFailed`. `CreateSandboxItem.svelte` disables the proxy toggle when the provider is `microsandbox`.

**The planned proxy features assume the Podman sidecar.** `proxy-network-policy`, `proxy-credential-secrets`, `proxy-non-http-capture`, `proxy-toggle-management` and `proxy-remote-deploy` (each `docs/features/<name>/02_dev.md`, all phases `Remaining`) extend the mitmproxy sidecar. For a microsandbox sandbox, microsandbox's host-side stack covers most of what `proxy-network-policy`'s static half and `proxy-credential-secrets` plan, and removes the bypass that `proxy-non-http-capture` exists to count.

**The workspace and terminal transports do not use guest egress.** The workspace is a `--kind disk` volume synced by Mutagen over `msb ssh serve --stdio` (`docs/features/microsandbox-provider/02_dev.md`, Phase H), and terminals reach the guest the same way. Both run over microsandbox's agent channel, not the guest's network, so a default-deny egress policy does not affect them. The local-LLM reverse forward (`forward_create_reverse` in `src-tauri/src/sync/mod.rs`) listens inside the guest and is unverified under a restrictive policy (Validation).

## Microsandbox 0.7.12 Capabilities This Feature Uses

Read from the microsandbox repository at tag `v0.7.12` (2026-10-31) and corrected against the spikes: `docs/changelog/`, `docs/networking/overview.mdx`, `docs/networking/outbound-proxy.mdx`, `docs/networking/tls.mdx`, `docs/sandboxes/secrets.mdx`, `docs/security/network.mdx`, `docs/cli/sandbox-commands.mdx`.

- **Egress rules:** `--net-default-egress deny` plus repeatable `--net-rule` tokens (`<action>[:<direction>]@<target>[:<proto>[:<ports>]]`) targeting IPs/CIDRs, domains, `*.domain` suffixes (at least two labels) and groups (`public`, `private`, `multicast`, `host`, `dns`). Domain rules bind to the IPs the sandbox's own DNS answers returned. `msb inspect <name> --format json` exposes the effective policy at `active_config.network.policy`, usable for a "show effective policy" panel.
- **Strict hostname mode:** `--net-strict[=true|false]` defaults to true, so every sandbox is already strict. Strict denies a hostname-allowed HTTPS connection whose authority cannot be inspected, so deny-egress without `--tls-intercept` cannot make any HTTPS call (`SSL_ERROR_SYSCALL`). A mismatched `Host` header does not bypass a hostname allow.
- **Host-held secrets:** `--secret ENV[:OPTIONS]@HOST[,HOST...]`, where `ENV` is the name of a host environment variable read from the `msb` process's environment at every start. The guest gets a variable of the same name holding the literal placeholder `$MSB_<ENV>`. Options: `no-headers`, `headers=[FIELD,...]` or `headers=*` (headers are substituted by default), `query`, `body`, `passthrough=HOST`. `--secret` turns TLS interception on implicitly. A placeholder sent to a non-bound host is blocked in every position; to the bound host in an unlisted position it is passed literally. Plain HTTP is always blocked. `inspect` stores only a source reference, never the value.
- **Violation actions:** `--secret-violation-action` selects `block`, `block-and-log` (the default) or `block-and-terminate`. `block-and-log` writes a `secret violation` line to `~/.microsandbox/sandboxes/<name>/logs/runtime.log`; `block` writes nothing; `block-and-terminate` also stops the VM.
- **Readable denials:** denied HTTP and intercepted HTTPS requests get a JSON `403` (`network_policy_denied` or `secret_policy_denied`) with `code`, `message` and `domain`, with `network_deny_message` and `secret_deny_message` overrides. Denied plain HTTPS without interception gets no readable body, only a failed connect.
- **Outbound proxy:** `--proxy socks5://IP:PORT` or `http://IP:PORT` (CONNECT) tunnels guest TCP through a host-reachable proxy after the policy check. Authentication flags: `--socks5-username` with `--socks5-password-env`, or `--http-connect-username` with `--http-connect-password-env`. DNS never traverses the proxy and SOCKS5 mitmproxy cannot carry UDP.
- **Upstream CA trust:** `--tls-upstream-ca-cert` / `--tls-upstream-ca-cert-for` let microsandbox's interception layer trust a downstream intercepting proxy's CA.
- **Live changes:** `msb modify` (alias `msb mod`) has no network-rule flag. `msb modify --secret` is live only for value rotation and host-list changes, and every call must repeat `@HOST[,HOST...]` with the value in its environment. Adding a secret or changing options needs `--restart` or `--next-start`. `--secret-rm` is live but leaves the guest variable and placeholder behind. Changing egress rules means recreating the sandbox.

## Policy File (`.mio/net-policy.json`)

A workspace file, the provider-neutral rule format that `proxy-network-policy` also adopts for Podman (Resolved Decision 6), read and written through `src-tauri/src/mio_files.rs`, mirroring `.mio/ports.json` and `.mio/proxy-rules.json`. The file holds an egress mode (`open`, meaning microsandbox's default `allow@public`, or `allowlist`), a list of allow entries (domain or suffix, optional protocol and port), a strict-hostname flag, and secret bindings that carry a secret id, allowed hosts and a substitution location only, never a value. Values stay in `<app_data_root>/proxy/secrets.json` (`proxy::load_secrets` in `src-tauri/src/proxy/mod.rs`), because the workspace is visible inside the guest. A new `src-tauri/src/provider/msb_policy.rs` translates the file into `msb create` argv. The generated rules must not include `allow@dns`: domain-allow rules resolve exactly the allowed names through the gateway, while `allow@dns` lets denied names resolve and opens a DNS exfiltration channel. The starter allowlist (Resolved Decision 4) is used only when the user switches a sandbox to allowlist mode; the default is permissive (Resolved Decision 3). It needs `nodejs.org` (Node downloads) and `mise-versions.jdx.dev` (otherwise every `mise use` warns of a 403), besides the npm registry, GitHub and the agent API.

## `InstanceSpec` Gains a Provider-Neutral Egress Policy

`InstanceSpec` (`src-tauri/src/provider/types.rs`) gains an `egress: Option<EgressPolicy>` field describing allow entries, strictness, secret bindings and an optional outbound proxy URL. `MsbProvider::create_instance` renders `EgressPolicy` into `--net-default-egress`, `--net-rule`, `--net-strict`, `--tls-intercept`, `--secret` and `--proxy`. `PodmanProvider::create_instance` (`src-tauri/src/provider/mod.rs`) rejects a `Some` `egress` until `proxy-network-policy` gives Podman an enforcement path, the same way `MsbProvider` rejects a `network` attachment today. `ProviderCapabilities` (`src-tauri/src/provider/types.rs`) gains an `egress_policy: bool` flag so the frontend hides the policy controls instead of failing at invoke time.

## Secret Values Reach `msb` Through the Child Process Environment

Microsandbox reads a secret's value from the environment of the `msb` process that starts the sandbox, at every start, and a start without it fails closed. Every start-capable `msb` call therefore needs the values: `create`, `start`, `restart`, `exec` on a stopped sandbox (an implicit ephemeral start) and `modify --restart`. `MsbProvider::run` and the start path (`MsbProvider::start` in `src-tauri/src/provider/msb.rs`) set each bound secret's value as an environment variable on the spawned `msb` `Command` only, resolved from `proxy::load_secrets` at call time, for all of those calls. The app's own process environment never carries the value, and no value is written to argv or `msb` config files. One leak path remains: an echo or debug endpoint on an allowed secret-bound host reflects the real value into guest stdout, which microsandbox records in `~/.microsandbox/sandboxes/<name>/logs/exec.log`. Echo and debug hosts must stay off the allowlist of secret-bound sandboxes, and `exec.log` is sensitive. Violations default to `block-and-log`, and the UI should surface `runtime.log` violation lines; `block-and-terminate` is an opt-in hard-stop mode.

## Chained mitmproxy for Visibility

When traffic viewing is on (a separate opt-in, Resolved Decision 5), the app runs mitmproxy as a per-sandbox sidecar microsandbox VM and passes `--proxy socks5://127.0.0.1:<hostport>` with SOCKS5 authentication to the agent's `msb create`. The sidecar uses the same image tag as the Podman path (`MITMPROXY_IMAGE_DEFAULT` in `src-tauri/src/proxy/mod.rs`), pulled once with `msb pull` (about 8 s, 98 MiB). The existing `mitm_flowlog_addon.py` and `proxy::flowlog::watch_flows` (`src-tauri/src/proxy/flowlog.rs`) keep producing `flows.ndjson` and `proxy://flows-changed` events unchanged, so `TrafficPanel.svelte` needs no change beyond being shown for microsandbox. Enforcement stays in microsandbox; mitmproxy observes. Spike C confirmed the layering and spike D the sidecar form (Validation). `mitm_addon.py`'s header injection is not mounted for a microsandbox sandbox, because microsandbox owns secrets (Technology Choices).

**Sidecar shape (spike D).**

- **Launch.** `msb create` accepts no command, so the sidecar gets a `--script start=<mitmdump command>` and `--init /.msb/scripts/start`, which hands PID 1 to the script. mitmdump runs `--mode socks5` with `--proxyauth`, the flow-log addon and a `confdir` under `/home/mitmproxy/.mitmproxy`, and starts on every create and every start.
- **Port.** The SOCKS port is published with `-p 127.0.0.1:<hostport>:<guestport>`. Spike D saw only a `127.0.0.1` listener on the host. The host port is allocated app-side per sandbox. A default agent cannot reach the port through `host.microsandbox.internal`.
- **Mounts.** `--mount-dir` for the addons directory (read-only), a flows directory (read-write; `flowlog.rs` tails `flows.ndjson` live, including the addon's truncate-and-rewrite) and the confdir (read-write). The CA `mitmproxy-ca-cert.pem` lands in the host confdir at first start, so `wait_for_ca` carries over. Recreating the sidecar on the same confdir keeps the CA; recreating on a fresh certs dir changes it and breaks every agent chained to it.
- **Egress.** The sidecar keeps microsandbox's default egress (`allow@public`). It runs no agent code, so it may hold more permission than the agent sandbox. A deny default breaks its DNS and the chain.
- **Agent flags.** `--tls-intercept` (required, or HTTPS fails `curl (60)` with no rows), `--proxy`, `--socks5-username`, `--socks5-password-env`, and `--tls-upstream-ca-cert <confdir>/mitmproxy-ca-cert.pem`. Works under permissive and deny-egress agents.
- **Lifecycle.** Stop the sidecar with `msb stop -f`; a graceful stop hangs in `draining` with `--init`. msb reports `running` about 3 s before mitmdump listens, so the app needs a readiness probe (TCP connect plus SOCKS authentication, budget about 5 s). A stopped sidecar makes the agent fail closed (about 8 s connect timeout) and the chain recovers when the sidecar returns, without touching the agent. Idle footprint is about 115 MiB RSS.
- **Password exposure.** The `--proxyauth` password sits in the script body and is visible in `msb inspect`. Proposed mitigation, untested (Validation gap): pass `--proxyauth @<htpasswd file>` with the file in the read-only addons mount or in the confdir, so the script body carries only a path.

**`MsbProvider` work.** `MsbProvider` implements `create_sidecar` and `pull_image` (`src-tauri/src/provider/msb.rs`); `create_network` and `remove_network` stay unsupported because the chain goes through host loopback and needs no user network or fixed IP. `SidecarSpec` (`src-tauri/src/provider/types.rs`) gains a published-port list (bind address, host port, guest port; Podman maps it to `-p` too), force-stop semantics for `stop`/`remove` of an `--init` sidecar, and a readiness probe. Its existing `command` maps onto `--script`/`--init` through a shell-join and quoting layer. Spike D mapping: `name` to `--name`, `image` to the positional fully qualified reference, `mounts` to `--mount-dir ...[:ro]`, `labels` to `--label`, `network` ignored.

**Constraints inherited from spike C.**

- **Silent fail-closed.** A wrong SOCKS password, a stopped listener and a missing or wrong `--tls-upstream-ca-cert` all fail closed, differ only by curl error code in the guest, and log nothing host-side. The app needs its own health check.
- **Viewer coverage.** The traffic viewer covers TCP/HTTPS only. DNS is answered by the microsandbox gateway and SOCKS5 mitmproxy has no UDP.
- **IP destinations.** microsandbox SOCKS-connects by IP, so the flow log keys on `request.pretty_host` (the shipped addon does).
- **`secretInjected` is wrong.** `mitm_flowlog_addon.py` derives `secretInjected` from `rules.json`, so it is always false for microsandbox. It needs a different derivation, such as marking rows whose host carries a `--secret` binding.
- **Secret exposure.** mitmproxy sees the real substituted value in `Authorization`, because substitution happens before the upstream leg. The flowlog addon logs no header values, so the exposure is limited to code in the sidecar (other addons, `flow_detail` verbosity, saved flow files).

## Frontend

`CreateSandboxItem.svelte` stops forcing the proxy toggle off for microsandbox and adds an egress mode choice when `ProviderCapabilities.egress_policy` is true. `ProxyPanel.svelte` shows the policy file's allow entries and secret bindings for a microsandbox sandbox, labels egress-rule edits as requiring a recreate, and keeps the existing secret-entry surface. Agent-facing denial text is set through `network_deny_message` so a blocked agent tells the user which host to add.

## Technology Choices with Tradeoffs

### Enforcement layer: microsandbox's host-side stack (chosen) vs. a mitmproxy policy addon vs. NVIDIA OpenShell vs. both tools layered

Chosen: microsandbox enforces egress and secrets natively, because every guest packet already terminates in microsandbox's host-side stack, so nothing in the guest can bypass enforcement, and no extra infrastructure is needed.

- **A mitmproxy policy addon** (`proxy-network-policy`'s `mitm_policy_addon.py` design) — rejected as the enforcement layer for microsandbox: mitmproxy only sees what reaches it, and microsandbox already provides private-range blocking, DNS-pinned domain rules and strict hostnames that the addon would re-implement. The addon remains the right place for request-level rules later (`04_improvements.md`).
- **NVIDIA OpenShell** — rejected for now: its gateway and Podman driver would run inside the podman machine's WSL distro, which OpenShell marks experimental on Windows. Its Podman driver needs a `systemd --user` Podman socket the podman machine lacks (`docs/features/network-proxy/02_dev.md`, Spike Results). It also needs Landlock ABI 3 and seccomp user-notification in the WSL kernel, and processes started by `podman exec` get no egress at all, which breaks the exec transport. Its unique value over this design is per-binary rules, live policy reload, an agent-proposal approval workflow and a policy prover (`04_improvements.md`).
- **OpenShell layered inside each microsandbox VM** — rejected for now: it adds a gateway, a supervisor and a nested container per sandbox. It needs two policy languages kept in sync. Only one layer can own secrets and TLS interception. Podman-in-microVM plus Landlock in microsandbox's bundled 6.12 kernel are unverified. Recorded as the fallback if per-binary rules become a requirement (`04_improvements.md`).

### Who owns secret injection: microsandbox `--secret` (chosen) vs. the mitmproxy `mitm_addon.py` header injector

Chosen: microsandbox `--secret`, because microsandbox checks the destination against DNS, TLS and HTTP-authority identity before substituting. It can restrict substitution to one header, and it fails closed with a configurable violation action.

- **`mitm_addon.py` injection** — rejected for microsandbox: the addon injects a header the agent never set, by host-string match only, and cannot detect a placeholder being sent to the wrong host. Keeping `mitm_addon.py` as well would put two injectors on one request.

The cost of the chosen option is that agents must send the `$MSB_<NAME>` placeholder (typically through an environment variable such as an API-key variable) rather than nothing. Agents authenticated by the whole-home credential bundles (`src-tauri/src/credentials/mod.rs`) still hold real tokens in the guest; neither option fixes that.

### TLS layering with the chained proxy: microsandbox intercepts, mitmproxy re-intercepts with upstream trust (chosen, validated) vs. mitmproxy-only interception vs. no TLS interception

Chosen, confirmed end to end by spike C: microsandbox `--tls-intercept` stays on, so secret injection and strict hostnames work. mitmproxy intercepts the re-encrypted upstream leg, and microsandbox trusts mitmproxy's per-sandbox CA through `--tls-upstream-ca-cert`. The guest trusts only microsandbox's CA, configured by microsandbox's `msb-trust.sh` helper.

- **mitmproxy-only interception** (inject the mitmproxy CA with `proxy::inject_ca`, microsandbox interception off) — rejected: microsandbox secret injection requires microsandbox interception, and `--net-strict` would deny every hostname-allowed HTTPS connection.
- **No interception in mitmproxy** (SOCKS pass-through) — rejected: `flows.ndjson` would record only host and port for HTTPS, losing method, path and status, which are the traffic viewer's whole value.

The chosen option exposes real secret values to mitmproxy in flight, because microsandbox substitutes before the upstream leg. `mitm_flowlog_addon.py` records no header values (`docs/features/proxy-traffic-viewer/02_dev.md`), and mitmproxy runs host-side, so the value never enters the guest.

### Mitmproxy placement: a sidecar microsandbox VM (chosen) vs. Windows-native `mitmdump` vs. the existing Podman bridge

Chosen (Resolved Decision 2, validated by spike D): mitmproxy runs in its own microsandbox VM, chained from the agent through a SOCKS5 port published to host loopback. It needs no extra host install beyond `msb`, uses the same image as the Podman path, and keeps a stable CA through a per-sandbox confdir.

- **Windows-native `mitmdump`** (spike C's recommendation) — rejected: it needs a shipped Windows binary or a pinned `uv` environment bundled through `build.rs` (size, antivirus behaviour and start time unmeasured), a host process lifecycle outside the VM tooling, and a different build than the Podman path's image.
- **The existing Podman sidecar** — rejected: the rootless bridge is unreachable from the Windows host (`docs/features/network-proxy/02_dev.md`, Spike Results), and microsandbox dials the proxy from the host; publishing to `127.0.0.1` would also couple microsandbox to a running podman machine.

Any `127.0.0.1` listener is reachable by every local process, which is why SOCKS5 authentication is mandatory. Any fixed host port is host-global state that cannot be isolated per worktree, so the port is allocated app-side per sandbox, as the `NetworkError::PortAllocation` path (`src-tauri/src/network/types.rs`) does.

### Policy changes: recreate the sandbox (chosen) vs. wait for live network-rule modification upstream

Chosen: an egress-rule change recreates the microsandbox sandbox around its preserved workspace volume, reusing the recreate primitive planned by `docs/features/proxy-toggle-management/02_dev.md` (Phase B, `SandboxBackend::recreate`). Secret value rotation and host-list changes apply live through `msb modify --secret`; adding a secret or changing its options needs `msb modify --restart`. Recreate must remove the old sandbox before creating the new one, because a `--kind disk` volume admits only one attached sandbox (a second `msb create` fails `already attached with an incompatible disk mode`). Waiting for upstream live rule changes was rejected because no microsandbox issue or changelog entry signals one is planned.

### Rule file: one shared `.mio/net-policy.json` (chosen) vs. reusing `proxy-network-policy`'s `.mio/proxy-policy.json`

Chosen (Resolved Decision 6): a new file, because microsandbox's rule vocabulary (CIDRs, groups, protocol and port, suffix rules with DNS pinning) is wider than the exact host-string allow/deny list `proxy-network-policy` Resolved Decision 5 settled. Reusing the narrower file would cap microsandbox at that vocabulary. The new file is the shared provider-neutral format: `proxy-network-policy` adopts it for Podman instead of `.mio/proxy-policy.json`, so its `02_dev.md` needs a follow-up edit (not made here).

## Resolved Decisions

The user resolved the former Open Questions on 2026-11-02. `02_dev.md` carries them forward.

1. **Upgrade sequencing: this feature's first phase.** The msb 0.6 → 0.7 code upgrade ships now as phase one, with a minimum-version check. The host already runs 0.7.12 and spike A found no argv or output break. Remaining items: `create` validates the image workdir, a `kind=disk` volume attaches to one sandbox, and the install path (`msb self update` from a copy of `msb.exe`) and setup flow need a check.
2. **Mitmproxy host placement: a sidecar microsandbox VM, not Windows-native.** Design under Chained mitmproxy for Visibility and Technology Choices. Reason: no bundled host binary, same image as the Podman path, and the sidecar runs no agent, so it can keep default egress that the agent sandbox may lack. Windows-native `mitmdump` is the rejected alternative.
3. **Default egress mode: permissive.** New microsandbox sandboxes use microsandbox's `allow@public` default; the allowlist is opt-in. Reason: a deny default breaks tool installs and agent flows unless the user tunes a list.
4. **Starter allowlist source: static base list plus a per-agent field.** A static base list (mise and `mise-versions.jdx.dev`, npm, PyPI, GitHub including `*.githubusercontent.com`, `nodejs.org`) lives in the shared policy module (`src-tauri/src/provider/msb_policy.rs`); each agent in the catalogue (`src/lib/agents/`) gains a descriptor field carrying its API hosts. Applied only when the user switches to allowlist mode. The user was unsure; this was the assistant's default choice.
5. **Traffic viewing: a separate opt-in from egress policy.** Reason: the extra sidecar VM costs about 115 MiB RSS, and mitmproxy sees substituted secret values in flight.
6. **Rule format: one shared provider-neutral `.mio/net-policy.json`.** `proxy-network-policy` adopts it for Podman. Follow-up, not done here: `docs/features/proxy-network-policy/02_dev.md` must reference the shared format instead of `.mio/proxy-policy.json`.

## Common Gotchas

| Gotcha | Cause | Fix |
|---|---|---|
| `microsandbox does not support a network attachment or environment variables` from `create_sandbox` | `MsbProvider::create_instance` (`src-tauri/src/provider/msb.rs`) rejects any `InstanceSpec` with `network` or `env`, which the Podman proxy path sets | Carry microsandbox policy in `InstanceSpec.egress`, never in `network`/`env`; the Podman `ProxyAttachment` path stays Podman-only |
| A secret placeholder `$MSB_<NAME>` reaches the upstream unsubstituted, or `msb start`/`exec`/`restart` fails `host environment variable X is not set` | The value is read from the starting `msb` process's environment at every start, including the implicit start in `exec` on a stopped sandbox and `modify --restart` | Set every bound secret's value on the spawned `msb` `Command` for each start-capable call in `src-tauri/src/provider/msb.rs`, never in argv or `--env` |
| A real secret value appears inside the guest | The value was written into `.mio/net-policy.json` or passed as a plain `--env`, both visible to guest code | Keep values in `<app_data_root>/proxy/secrets.json` and bind them only with `--secret`; `.mio/net-policy.json` carries secret ids only |
| Every hostname-allowed HTTPS request is denied after enabling strict mode | `--net-strict` denies HTTPS whose authority microsandbox cannot inspect, which happens when `--tls-intercept` is off or the host matches a `--tls-bypass` pattern | Enable `--tls-intercept` alongside `--net-strict`, or drop strictness for hosts that must bypass interception |
| Editing egress rules in `ProxyPanel.svelte` has no effect on a running microsandbox sandbox | `msb modify` has no network-rule flag in microsandbox 0.7.12; rules are fixed at `msb create` | Apply egress-rule changes through the recreate primitive (`SandboxBackend::recreate`, `docs/features/proxy-toggle-management/02_dev.md`); `msb modify --secret` is live only for value rotation and host-list changes, and adding a secret or changing options needs `--restart` |
| `--proxy socks5://…` connections fail although mitmproxy is running in its Podman sidecar | The `mio-proxy-<sandbox>` bridge is unreachable from the Windows host, and microsandbox dials the proxy from the host | Use the microsandbox sidecar VM with a port published to `127.0.0.1` (Resolved Decision 2) |
| HTTPS rows in `TrafficPanel.svelte` show host only, or upstream TLS fails with an unknown-issuer error | mitmproxy is not intercepting the upstream leg, or microsandbox does not trust mitmproxy's CA | Run mitmproxy with interception on and pass `<confdir>/mitmproxy-ca-cert.pem` to `msb create --tls-upstream-ca-cert` |
| A local process unrelated to the sandbox can route traffic through the chained proxy | A `127.0.0.1` SOCKS5 listener accepts every local process | Require SOCKS5 username/password authentication, with the password supplied to `msb` through a host environment variable |
| Two worktrees' microsandbox sandboxes collide on the chained proxy port | A fixed host port is host-global and cannot be isolated per worktree | Allocate the proxy listener port app-side per sandbox, as `NetworkError::PortAllocation` (`src-tauri/src/network/types.rs`) already does |
| Every HTTPS call fails `SSL_ERROR_SYSCALL` under deny-egress although the host is allowed | `--net-strict` defaults to true and the authority cannot be inspected without interception | Always pass `--tls-intercept` with deny-egress (`src-tauri/src/provider/msb_policy.rs`), or accept `--net-strict=false` and no readable denial |
| Denied hostnames still resolve in DNS | `--net-rule allow@dns` opens resolver access for every name, a DNS exfiltration channel | Never generate `allow@dns`; domain-allow rules resolve exactly the allowed names |
| `msb create` fails `already attached with an incompatible disk mode` during recreate | A `--kind disk` volume admits one attached sandbox | `msb rm` the old sandbox before creating the new one in `SandboxBackend::recreate` |
| `msb create` fails `could not validate workdir in guest "/root/work"` | microsandbox 0.7 checks the image workdir and the base image expects the workspace mount | Mount the workspace volume at `/root/work`, or pass `--workdir` in tests without a volume |
| `msb self update` fails to overwrite `msb.exe` on Windows | The running executable cannot replace itself | Run `msb self update` from a copy of `msb.exe` |
| Guest sees `curl: (56) Connection reset` or `(52) Empty reply` on every HTTPS call with the chained proxy, and `runtime.log` is empty | Wrong SOCKS password, stopped listener, or missing `--tls-upstream-ca-cert` all fail closed and silent | Health-check the listener (TCP connect plus SOCKS authentication) before and during the sandbox's life; pass the listener's `confdir/mitmproxy-ca-cert.pem` |
| `secretInjected` is always false in `TrafficPanel.svelte` rows for a microsandbox sandbox | `src-tauri/resources/mitm_flowlog_addon.py` derives it from `rules.json`, not from microsandbox substitution | Derive it from the sandbox's `--secret` host bindings |
| Flow rows or mitmproxy logs show IP addresses instead of names | microsandbox resolves the name and SOCKS-connects by IP | Key on `request.pretty_host` in `src-tauri/resources/mitm_flowlog_addon.py`, not the server connection address |
| mitmproxy can see the real secret value | Substitution happens before the upstream leg | Keep header-logging addons, high `flow_detail` and flow-file saving off |
| The real secret value appears in `~/.microsandbox/sandboxes/<name>/logs/exec.log` | An echo or debug host on the allowlist reflected it into guest stdout | Keep echo and debug hosts off the allowlist of secret-bound sandboxes; treat `exec.log` as sensitive |
| The chained SOCKS listener is reachable beyond loopback | The published-port bind address was omitted | Publish with `-p 127.0.0.1:<hostport>:<guestport>` and always `--proxyauth` |
| Traffic viewer shows nothing for DNS or UDP traffic | DNS is answered by the microsandbox gateway and SOCKS5 mitmproxy has no UDP | Document the viewer as TCP/HTTPS only |
| After `msb modify --secret-rm` the placeholder still travels upstream | Removal clears the injection rule, not the guest variable | Recreate the sandbox to remove the placeholder variable |
| `msb` paths or `--workdir /root` are mangled when run from Git Bash | MSYS rewrites path-like arguments | `export MSYS_NO_PATHCONV=1` and pass `cygpath -m` paths |
| `msb create IMAGE ... -- mitmdump ...` fails `unexpected argument` | `create` takes no command and `--entrypoint` is not auto-run | Register `--script start=<command>` and pass `--init /.msb/scripts/start` |
| Sidecar addon never fires and `flows.ndjson` stays empty, no error | Addons were delivered with `--copy-dir`, which gives files mtime 1970 | Deliver addons with `--mount-dir <dir>:<dest>:ro` |
| `msb stop <sidecar>` hangs in `draining` | mitmdump runs under `--init`, so graceful shutdown never completes | Use `msb stop -f` for sidecars in the `MsbProvider` stop/remove path |
| Agent chain breaks after the sidecar is recreated | The sidecar was recreated on a fresh confdir, so the CA changed and the agent's `--tls-upstream-ca-cert` no longer matches | Always recreate on the same per-sandbox confdir; deleting it requires recreating the agent |
| Chain fails with `Failed to connect ... after 8056 ms`, or the sidecar logs `Name or service not known` | The sidecar is stopped, or was created with `--net-default-egress deny`, which breaks its DNS | Start the sidecar; leave default egress on it |
| Sidecar shows `running` in `msb ls` but the agent gets `(7)` connect errors | msb reports running about 3 s before mitmdump listens | Probe the published port (TCP connect plus SOCKS authentication) before marking the viewer ready |
| HTTPS from the chained agent fails `curl (60)` and no rows appear | The agent was created without `--tls-intercept`, so mitmproxy terminates TLS with a CA the guest does not trust | Always pass `--tls-intercept` with `--proxy` |
| The sidecar SOCKS password is visible in `msb inspect` | The `--proxyauth user:pass` value sits in the `--script` body | Use `--proxyauth @<htpasswd file>` in a mounted file (untested) and treat the password as loopback-only |

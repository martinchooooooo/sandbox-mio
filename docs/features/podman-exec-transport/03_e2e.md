# Podman Exec Transport: E2E Test Plan

This is the test plan for `docs/features/podman-exec-transport/02_dev.md`. The feature ships two
permanently-coexisting reachability models gated by `Sandbox::supports_exec_transport()`
(`src-tauri/src/backends/types.rs`): the new **exec-transport** model (an SSH session tunneled
through `podman exec` for `BASE_IMAGE_VERSION >= EXEC_TRANSPORT_MIN_IMAGE_VERSION` sandboxes) and the
pre-existing **publish+relay** model (`--publish` + relay-pool `socat`) for older sandboxes. The
regression surface is therefore split: the `standard` tier proves the exec-transport model on every
run, while the publish+relay model has no automated fixture and is proven by the manual spike
recorded below plus the `standard` specs that predate this feature.

## Goal

Prove two things the implementation must not regress:

1. **Exec-transport reachability works end to end for an exec-capable sandbox.** After `create`/
   `deploy` drop all `--publish` flags and instead bake a per-sandbox key into
   `/etc/ssh/authorized_keys.container` and write a `Proxied` SSH alias, a real Mutagen forward
   dialing that alias must reach the container's own loopback service (zellij, paseo, or a
   user-exposed port) — the exec pipe carrying the SSH handshake *is* the transport, so
   `PassthroughPortTransport` returns the container port unchanged and the forward lands directly in
   the container netns.
2. **The publish+relay model still works for a `!exec_capable` sandbox.** Since the
   `imageOutdated` banner is dismissible (`02_dev.md` Resolved Decision 1), a sandbox on a
   pre-feature image can run indefinitely, so `PodmanPortTransport`'s `podman port` lookup and the
   relay-pool `socat` bridge must keep working alongside the new path.

## Chosen Approach

**Standard tier for the exec-transport model, reusing rewritten and existing specs; a manual spike
for the publish+relay model.**

- `e2e/test/specs/standard/agent-web.spec.ts` — its first two tests were rewritten for the new model
  (`02_dev.md` Phase F): they assert the container publishes *nothing*, that `create` wrote a
  `Proxied` alias carrying all four load-bearing keywords (`ProxyCommand`, `User`, `IdentityFile`,
  `UserKnownHostsFile`), and that the started container holds both halves of the handshake
  (`/etc/ssh/authorized_keys.container` with the sandbox's public key, `/etc/ssh/sshd_config.container`
  from the image). The remaining tests drive `prepare_agent_web` and confirm the paseo daemon is
  reachable through the exec-transport forward.
- `e2e/test/specs/standard/embedded-workspace.spec.ts` — drives `prepare_terminal_webview` →
  `RuntimeManager::prepare_terminal` and asserts `zellij web --status` reports `online` behind the
  resolved port, exercising the `PassthroughPortTransport` selection for `exec_capable` sandboxes.
- `e2e/test/specs/standard/expose-port.spec.ts` — drives `NetworkManager::expose_port`'s
  exec-capable branch (no relay slot, no `socat`; `forward_create` dials the container loopback
  directly) end to end, dialing the resulting Windows-host loopback port with a raw socket to confirm
  the byte round trip.

No `light` spec is added: the mock tier never opens a terminal/agent-web pane or exposes a port
(`network/mock.rs` doc comment), and the feature adds no new UI/store gating logic — only the
`imageOutdated` banner's existing dismissibility, already covered. Per `e2e/AGENTS.md` Decision rule
4, the `standard` specs are the source of truth here.

The **publish+relay model is not covered by any `standard` spec**, because every `standard` run
creates only exec-capable (current `BASE_IMAGE_VERSION`) sandboxes, so nothing constructs a
`!exec_capable` sandbox. Closing this properly needs a fixture that pins an old image version and
exercises both models in one run; it is recorded as deferred in `04_improvements.md` and stood in for
by the manual spike below.

**Prerequisite:** a real `mio-tests` Podman machine (`e2e/AGENTS.md`), plus the driver/Edge version
match the tier already needs. No new provisioning, host port, or app-data path — the per-sandbox key
lives under `app_data_root(app)/ssh-keys/<name>/`, already worktree-isolated via `MIO_APP_DATA_DIR`.

## Spec Scenario

Run the three specs via `./build e2e` (`standard`), fastest-to-fail first:

1. **`agent-web.spec.ts`** — the alias/handshake assertions fail fast if `create` still publishes
   ports, omits a `Proxied` keyword, or fails to install the authorized key; the later tests fail if
   the paseo forward can't reach the container over the exec transport.
2. **`embedded-workspace.spec.ts`** — fails if `prepare_terminal` selects the wrong `PortTransport`
   for an `exec_capable` sandbox, or the exec-tunneled forward can't reach zellij on the container
   loopback.
3. **`expose-port.spec.ts`** — fails if `expose_port`'s `exec_capable` branch is mis-wired (e.g.
   still allocating a relay slot, or dialing the connection instead of the container loopback).

## De-Risking Spike Results

A three-part spike was run on 2026-08-10 against the real `mio-tests` machine, standing in for the
two `standard`-tier coverage gaps this feature leaves (the publish+relay model, and abnormal-exit
`sshd` teardown). All spike containers were removed and the managed SSH config restored afterward.

1. **Exec-transport handshake and forward, pass.** A base-6 container created with the exec-capable
   argv (`--network pasta`, no `--publish`) accepted a full pubkey SSH handshake through
   `ProxyCommand … podman exec -i <name> /usr/local/bin/mio-sshd` (returning `uid=0(root)`). Driving
   the bundled Mutagen sidecar through the app's exact `forward_create`/`forward_terminate` calls
   against the container's `Proxied` alias, over five open→verify→close cycles, every forward reached
   zellij (HTTP 200), and the in-container `sshd` count dropped to zero after each `forward
   terminate` — no running-`sshd` accumulation, defunct count bounded at ~1.
2. **Publish+relay model, pass.** A container created with the `!exec_capable` argv (`--network
   pasta:--host-lo-to-ns-lo`, the zellij/paseo publishes, the eight relay-pool publishes) served
   zellij over the publish path: `podman port <name> 8082/tcp` (the `PodmanPortTransport` lookup)
   resolved the host-loopback port and a curl to it returned HTTP 200. `expose_port`'s relay branch
   also verified: a pool-slot `socat` relay reached the target through the slot's published port
   (HTTP 200) and was torn down by `pkill -f TCP-LISTEN:<slot>` (the `is_relayed` branch).
3. **Abnormal-exit teardown, one finding.** An **abrupt** `kill -9` of a raw `ssh` client running a
   bare `-N` forwarding session does *not* tear down the in-container `sshd`, because `podman exec`
   does not propagate the client's death and `sshd_config.container` sets no `ClientAliveInterval`.
   This does not affect the app's normal path (Mutagen closes gracefully — see finding 1) but refines
   Phase A's too-strong "SIGKILL cleanly kills it" claim; recorded with a mitigation in
   `04_improvements.md`.

## Common Gotchas

| Gotcha | Cause | Fix |
|---|---|---|
| `agent-web.spec.ts`'s alias assertion fails because `sshAliasBlock` reads another run's block | `sshAliasBlock` (`e2e/lib/ssh.ts`) reads the host-global managed config, shared across concurrent runs | Key the assertion on a run-unique alias — `useSandboxWorkspace`'s timestamped project name already gives one |
| A spec `podman exec`'s an in-container absolute path and the path comes back rewritten to `C:/Program Files/Git/...` | MSYS/Git-Bash path conversion rewrites POSIX arguments before `podman exec` sees them | Set `MSYS_NO_PATHCONV=1` (and `MSYS2_ARG_CONV_EXCL=*` for inline strings) for the call, exactly as `crate::sync::command` does for the Mutagen sidecar |
| The exec-transport forward fails with `unable to receive server magic number: EOF` / `Connection closed by UNKNOWN port 65535` | `mio-sshd`'s `mkdir -p /run/sshd` step is missing, or the `ProxyCommand` references `sshd` by an MSYS-manglable absolute path — neither error names the real cause | Run `podman exec <sandbox> /usr/sbin/sshd -t -f /etc/ssh/sshd_config.container` (expect only the `/run/sshd` complaint, which `mio-sshd` creates at launch); confirm the `Proxied` command execs `/usr/local/bin/mio-sshd` |
| A `standard` run passes but nothing proved the publish+relay path | Every `standard` run creates only current-`BASE_IMAGE_VERSION` (exec-capable) sandboxes, so no `!exec_capable` sandbox is ever constructed | Run the manual publish+relay spike (De-Risking Spike Results 2) or build the pinned-old-image fixture recorded in `04_improvements.md` |
| pubkey auth silently fails with only a container log line | The authorized-keys file arrives via `podman cp` from a Windows temp file at mode `0666`, which sshd rejects as too open | `sshd_config.container` sets `StrictModes no` (baked at image build); if pubkey auth regresses, confirm that line survived a Containerfile edit |

# Responsive Panel Build Plan

This document is the build plan for `docs/features/responsive-panel/01_ideas.md`: making the global panel's content react correctly to its real 380px/full-window widths, and moving Terminal/Packages/Agents management out of each project row into a per-sandbox workspace dashboard pane. It continues `01_ideas.md` and resolves every one of its six Open Questions below. **Status: no code has landed yet; every phase in this document is Remaining.** It builds on the already-implemented embedded-windows system (`docs/features/embedded-windows/02_dev.md`, Phases A-E) without modifying that system's core geometry/lifecycle primitives (`workspace_layout`, `run_on_main`, `apply_layout`), only extending the registry and switcher with a second pane kind.

## The concrete model

Two independent tracks, buildable and shippable separately:

**Track 1 — width responsiveness (no Rust changes).** `src/routes/projects/+page.svelte` and `src/routes/projects/SandboxItem.svelte` gain a CSS breakpoint at 420px (`max-width: 420px`, chosen with margin above the real 380px `GLOBAL_EXPANDED_W` panel width) that drops the fixed `max-w-2xl` column and switches the action row to icon-only buttons. This track needs no IPC or Svelte state: `main-global`'s document viewport already equals its real `set_bounds` width (`01_ideas.md`, "The global panel's document viewport equals its real rendered width"), so a plain CSS media query fires correctly with zero plumbing.

**Track 2 — workspace-as-hub (Rust + Svelte).** `AppKind` (`src-tauri/src/workspace/types.rs`) gains a second variant, `Dashboard`, alongside the existing `Terminal`. `open_workspace` creates both a `Terminal` pane and a `Dashboard` pane together the first time a sandbox's workspace is opened (eager creation, Resolved Decision 2). The `Dashboard` pane is an internal SvelteKit route (`WebviewUrl::App`, new file `src/routes/workspace/dashboard/+page.svelte`) hosting `PackageManager.svelte` and `AgentManager.svelte` — moved out of `SandboxItem.svelte` — as two stacked sections. The switcher (`src/routes/workspace/switcher/+page.svelte`) renders two tabs per open sandbox, "Terminal" and "Manage" (Resolved Decision 6), and a new `switch_pane` command switches between a sandbox's own two panes without disturbing which sandbox is in front. A new `src/lib/workspace/state.svelte.ts` store centralizes the `workspace://state` subscription so both the projects list (which sandboxes have an open workspace) and the switcher (which panes exist, which is active) read the same data instead of `+layout.svelte`'s existing `hasTabs`/`collapsed`-only mirror.

## Resolved Decisions

Each Open Question from `01_ideas.md` is restated with its resolution.

1. **`switch_app`/`active_app` model for two panes per sandbox.** Resolved: keep `active_app: Option<String>` meaning exactly what it means today — the label of the one pane currently shown in the content rect — and add a new field, `sandbox_last_pane: HashMap<String, String>` (sandbox name → pane label), to `WorkspaceState` (`src-tauri/src/workspace/types.rs`). Cross-sandbox switching keeps calling `switch_app(app, sandbox)`, which now looks up `sandbox_last_pane[sandbox]` (defaulting to that sandbox's `Terminal` pane if unset) instead of assuming one pane per sandbox. A new command, `switch_pane(app, sandbox, kind)`, switches between a sandbox's own Terminal/Dashboard panes without changing which sandbox is in front, and updates `sandbox_last_pane[sandbox]` on every switch (both cross-sandbox and in-sandbox) so returning to a sandbox restores whichever pane the user had open.
2. **Eager versus lazy dashboard pane creation.** Resolved: **eager** — `open_workspace` creates the `Dashboard` pane in the same call that creates the `Terminal` pane, so both tabs exist from the moment a sandbox's workspace is first opened. Chosen over lazy creation because it makes Resolved Decision 3 (below) a single, predictable extra click ("Open workspace") rather than a second hidden trigger.
3. **Workspace-open as a prerequisite for package/agent management.** Resolved: **accepted as an intentional behavior change.** A sandbox's Packages/Agents management is only reachable after "Open workspace" has been clicked once (which, per Resolved Decision 2, creates both panes together). This is a one-click cost against every already-listed sandbox, and is judged acceptable because it is the same click the terminal already required for terminal access.
4. **CSS breakpoint coupling to `GLOBAL_EXPANDED_W`.** Resolved: **accept manual sync**, not a shared runtime value. The CSS breakpoint (420px, Track 1) is a literal in `SandboxItem.svelte`/`+page.svelte`, with a comment cross-referencing `GLOBAL_EXPANDED_W` (`src-tauri/src/workspace/mod.rs:32`); `GLOBAL_EXPANDED_W`'s doc comment gets a matching cross-reference back. No shared constant file or runtime CSS custom property is introduced — rejected as more machinery than a single well-commented pixel value justifies at this scale (two files, one number).
5. **Whether `GLOBAL_EXPANDED_W` should grow.** Resolved: **stays at 380** for this build. Track 2's row narrowing (Terminal/Packages/Agents buttons removed once a workspace is open) is expected to leave enough room at 380px for the remaining buttons in icon-only form; revisit only if Phase B's manual check (Phase B exit criterion below) shows real cramping.
6. **User-facing label for the dashboard pane's switcher tab.** Resolved: **"Manage"** (i18n key `workspace_manage_tab`, alongside the existing `workspace_expand`/`workspace_collapse` keys in `messages/en.json` and its sibling locale files).

## Implemented: Phase A — width responsiveness (Track 1, no Rust changes)

- **`src/routes/projects/+page.svelte`** — the fixed `<div class="max-w-2xl mx-auto">` now also carries `max-[420px]:max-w-none max-[420px]:mx-0`, removing the column constraint below 420px.
- **`src/routes/projects/SandboxItem.svelte`** — the action row's buttons each render a `HugeiconsIcon` (`@hugeicons/core-free-icons`: `Folder01Icon`, `DashboardSquare01Icon`, `TerminalIcon`, `CloudUploadIcon`, `CloudDownloadIcon`, `PlayIcon`, `StopIcon`, `Delete02Icon`) plus a label `<span class="max-[420px]:hidden">`, and every button carries a `title`.
- **Manual check (Phase A exit criterion) — not run this session.** No live app instance (Podman/sandbox) was available to drive `pnpm tauri build --debug --no-bundle`; `pnpm run check` (svelte-check) passes with zero new errors, but the devtools confirmation that the 420px breakpoint fires at the panel's real 380px width is still outstanding. Run it before relying further on this track.

## Implemented: Phase B — per-sandbox workspace-open state and row narrowing

- **`src/lib/workspace/state.svelte.ts`** (new) — a Svelte-5-runes store wrapping `workspace_state`/`workspace://state`. Exposes `workspaceApps()`, `isCollapsed()`, `hasTabs()`, `activeAppLabel()`, `isSandboxOpen(name)`, and `ensureWorkspaceState()` (idempotent hydrate + subscribe, mirroring `src/lib/activity/activity.svelte.ts`'s pattern). `src/routes/+layout.svelte` now derives `collapsed`/`hasTabs` from this store instead of its own private listener.
- **`src/routes/projects/SandboxItem.svelte`** — derives `workspaceOpen = isSandboxOpen(project.name)`. When true: the standalone `openTerminal()` button is hidden, and `openWorkspace()` calls `switch_app` directly instead of `open_workspace` (Resolved Decision 1). The inline `PackageManager`/`AgentManager` renders and imports are removed unconditionally (moved to Phase D's dashboard route).

## Implemented: Phase C — `AppKind::Dashboard` and eager pane creation

- **`src-tauri/src/workspace/types.rs`** — extend `AppKind` with a `Dashboard` variant alongside the existing `Terminal`. `AppPane` is unchanged in shape (`label`, `sandbox`, `forward_name`, `kind`, `url`) but a `Dashboard` pane's `forward_name` is unused (empty string or `Option`, since it has no Mutagen forward — see Phase C capability note below) and its `url` holds the internal route path instead of a loopback URL.
- **`src-tauri/src/workspace/types.rs`** — add `sandbox_last_pane: HashMap<String, String>` to `WorkspaceState` (Resolved Decision 1), defaulting empty.
- **`src-tauri/src/workspace/mod.rs`** — add `embed_dashboard(app, name) -> Result<(), WorkspaceError>`, mirroring `embed_terminal` (`src-tauri/src/workspace/mod.rs:130-188`) but adding a child webview with `WebviewUrl::App(format!("workspace/dashboard?sandbox={name}"))` instead of `WebviewUrl::External`, and no `initialization_script`. It does not call `sync::forward_create` (no loopback bridge needed, per `01_ideas.md`'s "Dashboard pane transport" choice).
- **`open_workspace` command** (`src-tauri/src/lib.rs`, beside `open_terminal`) — after embedding the terminal pane (existing behavior), also call `embed_dashboard` for the same sandbox in the same invocation, so both panes exist together (Resolved Decision 2). The switch-or-embed guard already present (per `mod.rs:127-129`'s comment, "Caller guarantees no pane exists for `name`") extends to check both pane kinds before creating either.
- **`embed_dashboard` must only ever be called from an `async` Tauri command.** Confirmed by the de-risking spike (`03_e2e.md`, run 2026-07-02): a synchronous (non-`async`) command calling `add_child` through `run_on_main` deadlocks the entire app, because a sync command appears to execute directly on the main thread already, so `run_on_main`'s blocking wait for its own posted closure never resolves. `open_workspace` (`src-tauri/src/lib.rs:226`) is already `async fn`, so this is satisfied as planned, but any future code path that calls `embed_dashboard` must not do so from a sync command wrapper.
- **`capabilities/default.json`** (or a new `capabilities/workspace-dashboard.json` following the `agent-auth.json` precedent) — add the new `workspace-*-dashboard` webview label to the capability set that already covers `main-global`/`main-switcher`, since the dashboard route calls `invoke` (`install_agent`, etc.) the same way `main-global` does.
- **`src-tauri/src/workspace/mod.rs` doc comments** — cross-reference `GLOBAL_EXPANDED_W`'s doc comment (line 31) with the Track 1 CSS breakpoint's file/line (Resolved Decision 4).

## Implemented: Phase D — dashboard route

- **`src/routes/workspace/dashboard/+page.svelte`** (new) — reads `sandbox` from the query string, looks up `workspace_path` via `list_sandboxes` (the query string only carries the sandbox name), and renders `PackageManager.svelte` and `AgentManager.svelte` (moved here, unchanged internally, from `SandboxItem.svelte`) as two stacked sections with its own `StatusRow`/`ActionRunner` — no longer sharing the projects-row's action state. Uses the full pane width (no 380px constraint), so neither component needs the icon-only/overflow treatment Phase A gives the projects-list row.
- **i18n deferred**: no strings were added to `messages/*.json` this pass, per the feature-implement skill's hard-code-English-first convention; the switcher's new "Terminal"/"Manage" tab labels (Phase E) carry `TODO(i18n)` markers instead of `workspace_manage_tab`. The i18n pass (including that key) happens after user sign-off on behavior and wording.

## Implemented: Phase E — two-tab switcher and `switch_pane`

- **`src-tauri/src/workspace/mod.rs`** — added `switch_pane(app, sandbox, kind: AppKind) -> Result<(), WorkspaceError>`, resolving the target pane by `(sandbox, kind)`. Both `switch_app` and `switch_pane` now share an `activate_pane` helper that does the show/hide/`sandbox_last_pane` bookkeeping; `switch_app` consults `sandbox_last_pane[sandbox]`, defaulting to that sandbox's `Terminal` pane if unset (Resolved Decision 1).
- **Registered `switch_pane`** in the `generate_handler!` list beside `switch_app` (`src-tauri/src/lib.rs`); `AppKind` gained `Deserialize` so it can be a command argument.
- **`src/routes/workspace/switcher/+page.svelte`** — renders, per open sandbox, one tab per pane (Terminal/Manage) grouped from `workspace_state()`'s `apps` list. Clicking a tab calls `switch_pane(sandbox, kind)`; the active tab is derived from `active_app` matching that sandbox's pane label. (Reads `workspace_state()`/`workspace://state` directly rather than through `src/lib/workspace/state.svelte.ts`, since that store is scoped to the global panel's document and `main-switcher` is a separate webview document — consistent with Phase B's "exactly one subscription per document" goal, just one document, not one process-wide.)

## Lifecycle and cross-cutting concerns

- **Teardown.** `close_app` (`src-tauri/src/workspace/mod.rs:251-273`) already removes a sandbox's pane(s), terminates its forward, and re-layouts; it is extended to iterate both of a sandbox's panes (Terminal and Dashboard) instead of assuming one, closing each webview but only calling `sync::forward_terminate`/`ForwardPortMap` cleanup for the `Terminal` pane (the `Dashboard` pane has no forward, per Phase C).
- **`sandbox_last_pane` cleanup.** When `close_app` removes a sandbox's panes entirely, its `sandbox_last_pane` entry is also removed, so a later `open_workspace` for the same sandbox starts fresh (defaults to `Terminal`) rather than reading a stale label.
- **State derivation for the global panel.** `+layout.svelte` and the projects list both read through the single `src/lib/workspace/state.svelte.ts` store (Phase B) rather than each maintaining an ad hoc `workspace://state` listener. The switcher (`main-switcher`) is a separate webview document, so it keeps its own listener rather than sharing that store across a webview boundary — one subscription per document remains the invariant, just not one subscription for the whole app.
- **DPI and units.** Unchanged from `embedded-windows/02_dev.md` — the `Dashboard` pane's `add_child` call uses the same `LogicalPosition`/`LogicalSize` discipline as every other child webview; no new DPI concern is introduced.

## Common Gotchas

| Gotcha | Cause | Fix |
|---|---|---|
| The 420px CSS breakpoint never fires even though the panel is visibly narrow | The rule was written against `SandboxItem.svelte` inside a component that isn't re-rendered in the `main-global` document, or the selector targets the wrong element | Verify in devtools that `main-global`'s document viewport itself is 380px (Phase A exit criterion) before assuming the CSS is wrong |
| `open_workspace` errors "pane already exists" when only a `Dashboard` pane (no `Terminal`) is present, or vice versa | The switch-or-embed guard (Phase C) was extended to check only one pane kind instead of both | Check both `AppKind::Terminal` and `AppKind::Dashboard` for the sandbox before embedding either in `open_workspace` |
| Switching sandboxes always reopens the Terminal tab even after the user was last on "Manage" | `switch_app` does not consult `sandbox_last_pane` (Phase E) | Update `switch_app` to look up `sandbox_last_pane[sandbox]` before falling back to the `Terminal` pane default |
| The dashboard pane's `invoke("install_agent", …)` is silently denied | `workspace-*-dashboard` is a new webview label with no capability entry (Phase C) | Add the label to `capabilities/default.json` or a new `capabilities/workspace-dashboard.json`, following `capabilities/agent-auth.json` |
| Closing a sandbox's workspace leaves its Mutagen forward alive | `close_app` iterates only the pane it knew about pre-Phase-C and skips the second pane's forward cleanup | Extend `close_app` to iterate every `AppPane` for the sandbox, calling `sync::forward_terminate` only for `Terminal`-kind panes (Lifecycle) |
| A sandbox's `sandbox_last_pane` entry points at a pane label that no longer exists | The pane was closed without clearing the sandbox's `sandbox_last_pane` entry | Clear `sandbox_last_pane[sandbox]` in `close_app` whenever all of that sandbox's panes are removed (Lifecycle) |
| The projects list and the switcher disagree about which sandboxes have an open workspace | Each maintains its own `workspace://state` listener instead of sharing one store | Route both through `src/lib/workspace/state.svelte.ts` (Phase B) instead of duplicating the subscription |
| The whole app hangs (no crash, no error) the moment a Dashboard pane is embedded | `embed_dashboard` was called from a synchronous (non-`async`) Tauri command; `add_child` via `run_on_main` deadlocks in that case (confirmed by spike, `03_e2e.md`, 2026-07-02) | Only call `embed_dashboard` from an `async fn` command, exactly as `open_workspace` already does; never add a sync command wrapper around it |

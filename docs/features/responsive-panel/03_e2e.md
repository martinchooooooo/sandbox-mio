# Responsive Panel E2E Plan

This document is the test plan for `docs/features/responsive-panel/02_dev.md` (Phases A-E, all currently Remaining). No e2e spike has been run for this feature yet; one is recommended before Phase C-E work starts (see De-risking spike below) because it exercises a WebDriver technique the repo has never used. **Note on prior art**: `docs/features/embedded-windows/03_e2e.md` describes the *pre-redesign* per-sandbox-container-window model (`GLOBAL_EXPANDED_W = 260`, a `workspace_state(name)` taking a sandbox-name parameter) and was never updated after the 2026-07-02 redesign noted in `embedded-windows/02_dev.md` line 5; the actually-shipped spec, `e2e/test/specs/standard/embedded-workspace.spec.ts`, matches the current single-main-window model and is the ground truth this document builds on, not `embedded-windows/03_e2e.md`.

## Goal

Prove three real code paths, all through the actual running app (`pnpm tauri build --debug --no-bundle`, driven by `tauri-driver`/WebdriverIO), not by asserting on Rust unit-test coverage alone:

1. **`open_workspace` eagerly creates two distinct `AppPane`s per sandbox** (`AppKind::Terminal` and `AppKind::Dashboard`, `02_dev.md` Phase C) and **`switch_pane` genuinely shows/hides the correct native child webview** (`02_dev.md` Phase E) — verified by reading `workspace_state()` back through `window.__TAURI_INTERNALS__.invoke`, the technique `e2e/lib/workspace.ts` already establishes.
2. **The Dashboard pane's package/agent controls, now rendered inside the `workspace-<name>-dashboard` child webview instead of inline in the projects list, still perform real installs** — a real `podman exec`/mise-manifest-visible package install and a real agent install, matching what `e2e/test/specs/standard/package-autocomplete.spec.ts` and `e2e/test/specs/standard/agent-setup.spec.ts` already prove today against the old inline location. A test that only checks `workspace_state()`'s JSON shape (pane count, `kind` values) would miss whether the install buttons are still wired to real `invoke` calls after the Svelte markup moved — that is the actual regression risk a UI relocation carries, and reading Rust-side registry state alone cannot catch it.
3. **The projects-list row genuinely renders its narrow-width form** (icon-only buttons, no inline Package/Agent controls) once a sandbox's workspace is open, at the real 380px `GLOBAL_EXPANDED_W` width `workspace_layout` applies (`src-tauri/src/workspace/mod.rs:44`) — not a simulated/resized browser window, since `main-global`'s real width only ever comes from `set_bounds`, driven by embedding a pane.

## Existing test styles

Two styles exist in the repo:

- **App-driven WebdriverIO specs against the real backend** (`e2e/test/specs/standard/**`). `embedded-workspace.spec.ts` is the closest prior art: it never drives DOM inside `main-global`, `main-switcher`, or a terminal pane directly — those are separate native child webviews a WebDriver session attached to the app webview cannot see or click into (`e2e/lib/workspace.ts:1-6`) — so it reads back state exclusively via `workspace_state()`/`set_panel_collapsed()`/`switch_app()` wrappers over `window.__TAURI_INTERNALS__.invoke` (`e2e/lib/workspace.ts:38-61`), and verifies real external effects (`podman exec … zellij web --status`, `mutagen forward list`, an HTTP fetch to the forwarded loopback URL) directly in the spec body. `agent-setup.spec.ts` and `package-autocomplete.spec.ts` are the second most relevant pair: they *do* drive real DOM — clicking install buttons, typing into the package-name input — via `ProjectRow` page-object getters (`e2e/test/pageobjects/project-row.component.ts:59,108,115,174,181,189,212,216,239-240,250,291,340-341`) scoped to the project's `<li>` inside `main-global` (the one webview the global `before` hook in `e2e/wdio.conf.ts:210-217` pins the session to at start).
- **Light specs driving the mock backend directly** (`e2e/test/specs/light/**`), inlining `browser.execute()` + `window.__TAURI_INTERNALS__.invoke(...)` calls with no shared helper (`e2e/AGENTS.md`, "Writing a light spec").

This feature's tests span both styles across two tracks: Track 1 (width responsiveness) extends the existing registry-read-back style in `embedded-workspace.spec.ts`; Track 2 (Dashboard pane) needs a **new** technique — driving real DOM inside a second internal `WebviewUrl::App` child webview — that no existing spec has done (every prior spec either reads back via `invoke` only, or drives DOM inside the one webview the global `before` hook already selects).

## Chosen approach

**Tier: `standard` is primary**, per `e2e/AGENTS.md` rule 1 — both tracks prove real backend behavior (real geometry from a real embedded pane; real package/agent installs) and neither downloads a large asset or loads a model, so `heavy` does not apply.

1. **Extend `e2e/test/specs/standard/embedded-workspace.spec.ts`.** After `rowA.openWorkspace()` (the existing "opening the workspace embeds the terminal as the active pane" test), add assertions that `workspace_state()` now returns **two** panes for `nameA` — one `kind: "terminal"`, one `kind: "dashboard"` — and that a new `switch_pane(nameA, "dashboard")` call moves `active_app` to the dashboard pane's label while leaving `sandbox_last_pane[nameA]` reflecting the switch (`02_dev.md` Resolved Decision 1), without disturbing sandbox B's own last-active pane once the second-sandbox test runs. This reuses the existing describe block's sandbox lifecycle (create/start/destroy) rather than standing up a parallel one.
2. **Migrate `agent-setup.spec.ts` and `package-autocomplete.spec.ts` in place**, not fork them. Their real-install assertions (mise-manifest reads, `waitForAgentStatus`, `waitForPackage`) stay unchanged; only their navigation changes: each spec's setup now calls `row.openWorkspace()` then a new `switchToDashboard(sandbox)` helper (Harness changes below) before locating the install controls, because those controls no longer render inline in the project `<li>` once `02_dev.md` Phase B/D land (Resolved Decision 3 makes workspace-open a prerequisite for package/agent management — there is no inline fallback to fall back to). Migrating in place, rather than writing a fresh `workspace-dashboard.spec.ts`, is chosen because the whole point of the relocation is that these controls behave identically once moved; re-running the same real-effect assertions through the new navigation path is the most direct proof of that continuity, and avoids maintaining two specs that assert the same install behavior from two entry points.
3. **New light spec, `e2e/test/specs/light/workspace-panel-ui.spec.ts`.** Covers UI/gating logic only, against the mock backend (`MIO_MOCK_BACKEND=1`): the "Manage" tab appears in the switcher once a mocked sandbox's workspace opens, clicking it flips `active_app` to the dashboard pane, and the projects-list row's icon-only/no-inline-controls state is present once a mocked sandbox's workspace is open. Chosen over relying on the `standard` specs alone per `e2e/AGENTS.md` rule 4 ("a real spec paired with a light one... the light spec covers a gating-logic edge case or gives a fast debug loop") — the tab-presence/gating logic is pure UI/store logic once the mocked pane exists, and `open_workspace`'s pane-creation logic runs identically under the mock (its I/O goes through the already-mocked `SandboxBackend`/`RuntimeManager`/`SyncEngine` traits), so this spec is fast and deterministic without weakening the real-install proof, which stays in the migrated `standard` specs.

Track 1 (width responsiveness) needs no dedicated new spec: because it is pure CSS with no Tauri command of its own, its only real assertion point is "does `main-global`'s DOM look different once its real width is 380px," which is naturally checked inside the same `embedded-workspace.spec.ts` test that already puts the panel at that width (`state.rects.global.width === GLOBAL_EXPANDED_W`, line 109 today) — add a DOM check there (e.g. the action row's icon-only marker class present, `max-w-2xl` no longer applied) rather than writing a separate spec.

## Harness changes

- **`e2e/lib/workspace.ts`** — extend `export type AppKind = "terminal";` (line 8) to `"terminal" | "dashboard"`. Add `export async function switchPane(sandbox: string, kind: AppKind): Promise<void>` wrapping the new `switch_pane` command (mirroring `switchApp`, lines 59-61). `paneFor` (lines 63-65) currently returns the *first* `AppPane` matching a sandbox via `.find()` — with two panes per sandbox this becomes ambiguous, so add `panesFor(state, sandbox): AppPane[]` (returns all) and change `paneFor` to take an explicit `kind` parameter (`paneFor(state, sandbox, kind)`) so every existing call site in `embedded-workspace.spec.ts` is updated to specify which pane it means.
- **New page object, `e2e/test/pageobjects/workspace-dashboard.page.ts`.** Exposes `switchToDashboard(sandbox: string): Promise<void>`: enumerates `browser.getWindowHandles()`, switches into each, and matches the handle whose `window.location.pathname` is `/workspace/dashboard` and whose query string contains `sandbox=<name>` (mirroring the technique `e2e/wdio.conf.ts:210-217`'s global `before` hook already uses to find `main-global`). Also exposes `switchToAppWebview(): Promise<void>` to switch back to `main-global` afterward — necessary because the global `before` hook only runs once per WebDriver session, not per test, so any spec that switches into the Dashboard webview must switch back itself before the next test assumes it is in `main-global`.
- **`e2e/test/pageobjects/project-row.component.ts`** — the package/agent getters (`packageInput`, `addAgentButton`, `agentInstallButton`, etc., lines 59, 108, 174, 181, 189, 212, 216, 239-240, 250, 291, 340-341) are scoped today to the project's `<li>` inside `main-global`. Either move these getters to `workspace-dashboard.page.ts` scoped to that webview's own document root, or give `ProjectRow` a root-element parameter so the same getters work against either document. Moving them is the more direct fix, since after the relocation these controls have nothing to do with the projects-list row's own DOM.
- **`agent-setup.spec.ts` / `package-autocomplete.spec.ts`** — setup steps gain `await row.openWorkspace(); await workspaceDashboard.switchToDashboard(name);` before the existing install-driving steps, and an `afterEach` gains `await workspaceDashboard.switchToAppWebview().catch(() => {});` so later tests in the same file (or later spec files in the same session) are not left attached to the Dashboard webview.
- **Two more specs needed the same migration, not anticipated when this document was written**: `opencode-agent.spec.ts` and `runtime-management.spec.ts` also called the package/agent getters that moved off `ProjectRow` (`typecheck` in `e2e/` caught both as compile errors after the getters moved — `pnpm run typecheck` in `e2e/` is the fast way to enumerate every call site a `ProjectRow` API change breaks). Migrated identically: open the workspace, switch to the dashboard webview, drive the same controls through `workspace-dashboard.page.ts`, switch back before any subsequent `ProjectRow`/`ProjectsPage` step.
- **No `e2e/wdio.conf.ts` provisioning changes.** The same `mio-tests` real Podman connection already provisioned by `onPrepare` covers every migrated spec.

## Spec scenario

**`embedded-workspace.spec.ts` (extended, standard):**

1. Create and start sandbox A (existing step).
2. Open A's workspace (`row.openWorkspace()`, existing step) — assert `workspace_state()` returns exactly two panes for A, `kind: "terminal"` and `kind: "dashboard"` (new assertion), and the terminal pane keeps today's assertions (loopback URL, active-on-embed).
3. Assert the Dashboard pane's `url` field holds the internal route path (e.g. contains `/workspace/dashboard`), not a loopback address, distinguishing it from the terminal pane's transport (new assertion, proves `02_dev.md` Phase C's "no forward for Dashboard" choice).
4. Call the new `switchPane(nameA, "dashboard")`; assert `active_app` now equals the dashboard pane's label and `sandbox_last_pane[nameA]` (surfaced through `workspace_state()`) reflects it (new assertion, proves Resolved Decision 1).
5. Assert the panel's real DOM (in `main-global`, the webview the session is already attached to) shows the icon-only action row and no inline Package/Agent controls for sandbox A now that its workspace is open (new assertion, proves Track 1 + Resolved Decision 3 together, at the real 380px width already asserted by the existing `state.rects.global.width === GLOBAL_EXPANDED_W` check).
6. Existing collapse/expand, second-sandbox-coexistence, `switch_app`, and teardown steps continue unchanged, with `paneFor` calls updated to pass an explicit `kind` (Harness changes).

**`agent-setup.spec.ts` / `package-autocomplete.spec.ts` (migrated, standard):**

1. Create and start a sandbox (existing step, unchanged).
2. Open its workspace and switch into the Dashboard webview (`row.openWorkspace()`, `workspaceDashboard.switchToDashboard(name)` — new steps replacing direct access to the inline row).
3. Drive the install controls exactly as today (type a package name, select a suggestion, click install; open the agent picker, click install) — same assertions against real `podman exec`/mise-manifest state (existing steps, unchanged bodies).
4. Switch back to the app webview (`workspaceDashboard.switchToAppWebview()`, new step) before the spec's `after` teardown destroys the sandbox through `ProjectsPage`/`ProjectRow`, which operate on `main-global`.

**`workspace-panel-ui.spec.ts` (light) — NOT IMPLEMENTED, blocked.** Investigating this spec during
implementation found that `open_workspace` cannot run under `MIO_MOCK_BACKEND=1` at all today, for
reasons unrelated to this feature's own `embed_dashboard` (which genuinely has no I/O to mock, as
this document originally predicted): `open_workspace`'s shared `prepare_terminal_webview` helper
(`src-tauri/src/lib.rs`) unconditionally calls `crate::backends::ensure_connection_alias`, which
shells out to real `podman system connection` info regardless of `MIO_MOCK_BACKEND`, and
`sync::forward_create` (`src-tauri/src/sync/mod.rs`), which always invokes the real Mutagen
sidecar. Neither is gated by `mock_backend_enabled()` (`src-tauri/src/backends/mod.rs:95`) the way
`SandboxBackend`/`RuntimeManager`/`SyncEngine` are — confirmed by grepping every existing
`test/specs/light/**` spec, none of which calls `open_terminal`/`open_workspace`. So this was never
actually exercisable under the light tier, for the pre-existing Terminal pane alone, before this
feature added Dashboard. Making it mockable (gating both calls behind `mock_backend_enabled()`) is
backend infrastructure work orthogonal to `responsive-panel`, not something to slip in silently
inside an "implement e2e tests" pass — it is left as follow-up, tracked here rather than shipped as
a spec that would hang or fail in CI. The two-pane eager-creation and `switch_pane` behavior this
spec would have covered as a fast/mocked edge case are proven instead by the real coverage added to
`embedded-workspace.spec.ts` above (`standard` tier, `03_e2e.md` Goal 1) — no coverage gap, just no
`light`-tier duplicate.

## De-risking spike

**Run 2026-07-02.** Method: a temporary `#[tauri::command] spike_add_webview` was added beside `open_workspace` in `src-tauri/src/lib.rs`, backed by a temporary `workspace::spike_add_webview` in `src-tauri/src/workspace/mod.rs` that calls `Window::add_child` to attach a third child webview (`"main-spike"`) to the running main window on demand — mirroring `embed_terminal_on_main`'s shape but callable at any time after startup, not only from `open_workspace`. A temporary spec, `e2e/test/specs/light/spike-webview.spec.ts`, drove it via `MIO_MOCK_BACKEND=1` (`pnpm exec wdio run wdio.conf.ts --suite light --spec ./test/specs/light/spike-webview.spec.ts`, no podman needed). All temporary code was reverted after the run (`git status` confirms the working tree carries none of it); this section is the evidence trail.

Cleared risks:

- **A child webview added after the WebDriver session already started does appear as a new `browser.getWindowHandles()` entry**, and is fully driveable — this was the original question. With the app already running (2 handles: `main-global`, `main-switcher`), calling `spike_add_webview` (adding a third child with `WebviewUrl::App("workspace/switcher".into())`, the same internal-route shape a `Dashboard` pane would use) grew the handle count to 3; `browser.switchToWindow()` into the new handle and reading `window.location.pathname` correctly returned `/workspace/switcher`; switching back to the original handle left the session functioning normally (confirmed by reading `pathname` again and getting `/`). Log evidence: `[spike] handles after add: 3 [...]`, `[spike] new webview pathname: /workspace/switcher`, `[spike] back on original webview, pathname: /`. This clears the blocker `02_dev.md`'s Phase C/D design depends on: `AppKind::Dashboard` as a genuine separate child webview, not a `main-global`-hosted route swap, is viable.
- **The same result holds for an external URL child** (`http://127.0.0.1:59999/`, unreachable but loopback — no DNS/proxy needed), confirming the finding is about "webview added post-session-start" in general, not specific to internal routes.

Blocker found (feature bug, not a test concern) — **`add_child` deadlocks the whole app when called from a synchronous (non-`async`) Tauri command, even when routed through the module's `run_on_main` helper.** First attempt made `spike_add_webview` (Rust) a plain `fn`, exactly like the existing `switch_app`/`set_panel_collapsed` commands (`src-tauri/src/lib.rs`, both non-`async`). Every call hung indefinitely: diagnostic `eprintln!`s showed execution reaching `spike_add_webview_on_main: got main window, calling add_child` and then never returning — no `add_child returned Ok`, no `run_on_main returned`, and the WebDriver session's `execute/sync` call eventually failed with the verbatim error `WebDriverError: script timeout` (`e2e` log). This reproduced identically for both an internal route and a real external URL (`https://example.com/`, and the loopback URL above), ruling out URL kind as the cause. Changing only the command's signature to `async fn spike_add_webview(...)` (matching `open_workspace`'s shape, with an unchanged body) fixed it: `add_child` returned `Ok` and the whole spec passed in 151-185ms. Root cause: a synchronous Tauri command appears to execute directly on the main/event-loop thread in this Tauri version; `run_on_main`'s blocking `rx.recv()` then deadlocks against its own posted closure, which can never run because the thread executing `rx.recv()` **is** the main thread and is not returning to pump its message queue. `add_child` specifically needs to pump messages to complete WebView2's async controller creation, so it hangs; simpler calls like `set_bounds`/`hide`/`show` (used by `switch_app`/`set_panel_collapsed`, both already-shipped sync commands) apparently do not need this pumping and so do not exhibit the same deadlock — this was not independently re-verified against the real sync commands in this spike, so treat it as a strong hypothesis, not a confirmed fact about `switch_app`/`set_panel_collapsed`.

This blocker does **not** currently affect shipped code: `embed_terminal` (which also calls `add_child` via `run_on_main`) is only ever invoked from `open_workspace`, which is already `async fn` (`src-tauri/src/lib.rs:226`). But it is a landmine for `02_dev.md`'s Phase C: **`embed_dashboard` must only ever be called from an `async` Tauri command** (it already is, per Phase C's plan to call it from `open_workspace`), and this constraint should be stated explicitly in `02_dev.md` rather than left implicit, since a future refactor that exposes `embed_dashboard` behind a new sync command (e.g., a hypothetical "open dashboard only" shortcut) would silently deadlock the whole app the first time a user clicked it. Not a blocker to writing the Phase C/D test specs as planned above, since `open_workspace` embedding both panes together (Resolved Decision 2) is already the only call site.

## Sequencing

1. Land `02_dev.md` Phase A (CSS width responsiveness) first — no new WebDriver technique needed, since the only new assertion (Track 1's DOM check) runs inside `main-global`, the webview every existing spec already drives. Extend `embedded-workspace.spec.ts`'s step 5 as soon as Phase A lands.
2. Run the de-risking spike above **before** starting Phase C (`AppKind::Dashboard`). Its result gates whether Phase C-E build a second native child webview (as `02_dev.md` currently specifies) or a `main-global`-hosted route swap instead — resolve this before writing any Track 2 spec bodies against a design that might change.
3. Implement Phase C (Rust `AppKind::Dashboard`, `embed_dashboard`) and Phase D (the dashboard route) together; extend `e2e/lib/workspace.ts` (Harness changes) in the same change, since the `AppKind` union and `paneFor` signature change together.
4. Migrate `agent-setup.spec.ts`/`package-autocomplete.spec.ts` **in the same change as `02_dev.md` Phase B's inline-UI removal**, not after — Phase B deletes `PackageManager`/`AgentManager` from `SandboxItem.svelte`, which breaks both specs' current selectors immediately; landing the removal without the spec migration leaves a red window with no coverage of package/agent installs at all.
5. Implement Phase E (`switch_pane`, two-tab switcher); extend `embedded-workspace.spec.ts`'s steps 2-4 (two-pane assertions, `switchPane`) once it lands.
6. ~~Add the light spec, `workspace-panel-ui.spec.ts`, last~~ — **not done**: turned out `open_workspace` does not support running under the mock backend at all (see "Chosen approach" above), so this was blocked rather than merely low-priority. Tracked as backend follow-up, not shipped.

## Environment notes

- The real Podman connection (`mio-tests`, `LOCAL_CONNECTION` in `e2e/lib/podman-connection.ts`) is already provisioned by `e2e/wdio.conf.ts`'s `onPrepare`; no new machine or connection is needed for either migrated `standard` spec.
- `SANDBOX_WORKSPACE_ROOT`/`WORKSPACE_ROOT` env (used by `waitForToken` in `embedded-workspace.spec.ts:23,29`) is unchanged and still needed for the terminal pane's token-file check; the Dashboard pane writes no equivalent token file (it has no Mutagen forward per `02_dev.md` Phase C), so no new file-existence polling is needed for it.
- No new ports/sidecars: the Dashboard pane is an internal route with no loopback forward, so it adds no new `ForwardPortMap` entry and no new `mutagen forward list` target to poll.
- The light spec needs only `--suite light` (sets `MIO_MOCK_BACKEND=1` automatically per `e2e/wdio.conf.ts:190`); no manual env setup.

## Common Gotchas

| Gotcha | Cause | Fix |
|---|---|---|
| A migrated `agent-setup.spec.ts`/`package-autocomplete.spec.ts` step can't find the install button | The spec is still attached to `main-global`; the controls now live in the `workspace-<name>-dashboard` webview | Call `workspaceDashboard.switchToDashboard(name)` before locating install controls, and confirm the page object actually switched windows (log the handle) |
| A later test in the same spec file (or a later spec file in the same run) fails to find ordinary projects-list elements | A prior test switched into the Dashboard webview and never switched back; the global `before` hook (`e2e/wdio.conf.ts:210-217`) only runs once per session, not per test | Call `workspaceDashboard.switchToAppWebview()` in an `afterEach`/`after` for any spec that switches into the Dashboard webview |
| `paneFor(state, sandbox)` returns the wrong pane (or a type error after the harness change) | Two panes now exist per sandbox; the old single-pane `.find()` semantics (`e2e/lib/workspace.ts:63-65`) are ambiguous | Use the updated `paneFor(state, sandbox, kind)` signature or `panesFor(state, sandbox)` for the full list (Harness changes) |
| `browser.switchToWindow()` never finds the Dashboard webview's handle | `tauri-driver`/WebView2's WebDriver bridge may only enumerate handles present when the session started, not ones added by a later `add_child` call | Run the de-risking spike before relying on this; if confirmed, `02_dev.md`'s Track 2 must route Dashboard content through `main-global` instead of a new native child webview |
| The install proof (`podman exec`, mise-manifest read) still passes even though the install button's `onclick` silently stopped calling `invoke` | Assertions were written against `workspace_state()` shape only, not against a real install actually landing on disk/in the container | Keep the migrated specs' real-effect assertions (mise manifest, `podman exec`) exactly as they are today; do not replace them with registry-shape checks alone (Goal, point 2) |
| The new light spec's tab-click assertion is flaky/never observes the mocked pane | `open_workspace`'s eager Dashboard creation under `MIO_MOCK_BACKEND=1` was assumed without checking that `embed_dashboard` has no real-I/O step that silently no-ops under the mock | Confirm in Phase C that `embed_dashboard` (unlike `embed_terminal`) has no `sync::forward_create` call to mock in the first place — it should succeed identically under mock and real backends since it does no I/O |

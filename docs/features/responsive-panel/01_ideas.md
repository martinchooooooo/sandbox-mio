# Responsive Panel Ideas

This document is the ideation for two related global-panel problems in the embedded multi-webview workspace built by `docs/features/embedded-windows/` (01/02/03; Phases A-E implemented, Phase F deferred): first, the panel's content — the projects list and each project's action row — is authored assuming the panel fills the whole window and looks wrong once Rust shrinks it to `GLOBAL_EXPANDED_W` (380 logical px) or `GLOBAL_RAIL_W` (48 logical px); second, Terminal, Packages, and Agents are three separately-triggered surfaces stacked inside every project's row rather than organised as the "hub" a workspace is meant to be once a sandbox is open. Nothing described here is built yet. The relevant files are `src-tauri/src/workspace/mod.rs` and `src-tauri/src/workspace/types.rs` (the Rust-owned registry and geometry), `src/routes/+layout.svelte` (the global-panel chrome mirroring `workspace://state`), `src/routes/projects/+page.svelte` and `src/routes/projects/SandboxItem.svelte` (the projects list and per-project action row), `src/routes/projects/PackageManager.svelte` and `src/routes/projects/AgentManager.svelte` (the package/agent management UI currently embedded inline in each row), and `src/routes/workspace/switcher/+page.svelte` (the tab bar for the sandbox's embedded panes).

## Current State

`workspace_layout` (`src-tauri/src/workspace/mod.rs:44`) computes three rectangles from the container window's logical size, the collapse flag, and whether any app is embedded: with no embedded app the global panel (`main-global`) is full-bleed (its width equals the whole window, roughly 1024 logical px at the default size set in `create_main_window`, `src-tauri/src/workspace/mod.rs:80`); once a sandbox's terminal is embedded, the panel shrinks to `GLOBAL_EXPANDED_W` = 380 (`src-tauri/src/workspace/mod.rs:32`), or to `GLOBAL_RAIL_W` = 48 (`src-tauri/src/workspace/mod.rs:35`) when collapsed. `src/routes/+layout.svelte` mirrors this via the `workspace://state` event (lines 32-64): when `collapsed && hasTabs` it renders only the expand button (the thin-rail state, lines 70-76) and suppresses everything else — so the projects list and `SandboxItem.svelte` never actually render at 48px, only at 380px (once a workspace is open) or at full window width (before one is). This narrows the real responsiveness problem to a single width, 380px, not the rail width.

Neither `src/routes/projects/+page.svelte` nor `SandboxItem.svelte` accounts for that 380px case today. `+page.svelte` wraps the list in `<div class="max-w-2xl mx-auto">` (line 141), a fixed ~672px column sized for the pre-workspace full-width window. `SandboxItem.svelte`'s action row (lines 186-236) is a single `flex` row of up to seven labeled buttons — folder, sync switch, workspace, terminal, undeploy/deploy, destroy, plus (via `PackageManager.svelte` and `AgentManager.svelte` embedded at lines 275 and 277) a package-install control and an agent list, each with their own inline flex rows. None of this has a width guard beyond the name span's `min-w-0`/`truncate` (lines 172, 181), so at 380px the row overflows or wraps awkwardly — this is the "too wide" symptom.

Terminal, Packages, and Agents are reached from three different places inside one project's row today: `openTerminal()`/`openWorkspace()` (`SandboxItem.svelte:130`, `:141`) invoke `open_terminal`/`open_workspace`; `PackageManager.svelte` and `AgentManager.svelte` render inline, always visible, regardless of whether a workspace is open for that sandbox. The workspace registry (`WorkspaceState`, `src-tauri/src/workspace/types.rs`) already tracks `apps: Vec<AppPane>` with a `sandbox` field per pane (`src-tauri/src/workspace/mod.rs:169-175`) and exposes a `workspace_state` read command (`src-tauri/src/workspace/mod.rs` module doc, line 9) — the primitive needed to know, per project row, whether *that* sandbox currently has an open pane already exists but is not consumed by the projects list; only `+layout.svelte` reads it today, and only for the global `hasTabs`/`collapsed` flags, not per-sandbox.

`AppKind` (`src-tauri/src/workspace/types.rs`) has exactly one variant, `Terminal`, per the deferred Phase F note in `docs/features/embedded-windows/02_dev.md` (Resolved Decision 6, "OpenCode and pi remain terminal agents... a dedicated OpenCode app webview... is Phase F"). No non-terminal internal-route pane exists yet in the switcher.

## Proposed Model

### The global panel's document viewport equals its real rendered width

`main-global` is a native child webview (`src-tauri/src/workspace/mod.rs:88-96`), which means it is its own top-level document with its own CSS viewport — not a flexbox child sharing the OS window's viewport the way a pane would be in a single-webview app. Its viewport width is exactly whatever `set_bounds` last applied: 380px, 48px (never rendered per Current State), or the full window width. This is the seam the width-responsiveness half of this feature hangs off: ordinary CSS/Tailwind viewport media queries (`@media (max-width: …)`, Tailwind's `max-[…]:` arbitrary variant) evaluated inside `main-global`'s document correctly and automatically reflect the panel's real on-screen width, with no IPC round-trip or Svelte state needed to know "am I narrow." Add a breakpoint just above 380px (so the 380px case matches) to `src/routes/projects/+page.svelte` (drop `max-w-2xl` to a fluid width) and to `SandboxItem.svelte`'s action row (switch labeled buttons to icon-only with `title` tooltips, which several buttons already carry, e.g. `SandboxItem.svelte:187`).

### Per-sandbox "workspace open" state narrows each row's action set

Extend the existing `workspace://state` mirroring beyond `+layout.svelte`'s global `hasTabs` boolean into a shared reactive store (new seam, e.g. `src/lib/workspace/state.svelte.ts`) exposing the full `apps: AppPane[]` list from `workspace_state`/`workspace://state`, keyed by `sandbox`. `src/routes/projects/+page.svelte` and `SandboxItem.svelte` subscribe to it to know, per row, whether *that* project's workspace is currently open. When open, the row collapses its action cluster to the existing `openWorkspace()` button (`SandboxItem.svelte:141`) — repurposed to focus/switch to that sandbox's tab via the existing `switch_app` primitive (`src-tauri/src/workspace/mod.rs:191`) rather than only embedding a fresh terminal — plus Destroy; the `openTerminal()` standalone-window button, the inline `PackageManager`, and the inline `AgentManager` are removed from the row once a workspace is open for that sandbox, because that tooling now lives in the workspace dashboard pane (next section). When no workspace is open yet, the row keeps its current button set (Folder, Start/Stop or Sync, Deploy/Undeploy, Destroy) plus the single "Open workspace" entry point, but package/agent management is no longer inline — see Open Questions for the resulting behavior change.

This directly reduces the button count that has to fit in 380px (the same width problem the previous section solves at the CSS layer), so the two proposed changes compound rather than duplicate effort.

### A workspace dashboard pane hosts Packages and Agents as sections

A second `AppPane`/`AppKind` variant — `AppKind::Dashboard` (extending `src-tauri/src/workspace/types.rs`) — is an internal SvelteKit route (`WebviewUrl::App`, following the pattern `main-switcher` already uses at `src-tauri/src/workspace/mod.rs:98-106`, not an external loopback URL) added as a sibling content pane alongside a sandbox's terminal pane. Its route (new file, e.g. `src/routes/workspace/dashboard/+page.svelte`) reads the sandbox name from a query param and renders `PackageManager.svelte` and `AgentManager.svelte` — moved out of `SandboxItem.svelte` — as two sections of one pane (stacked or with a small in-pane sub-nav), not as separate switcher tabs. This is the "sections within a single workspace dashboard pane" model: a sandbox's switcher gains at most two tabs (Terminal, Dashboard/"Manage"), not one tab per management concern, so the 40px-tall switcher bar (`SWITCHER_H`, `src-tauri/src/workspace/mod.rs:37`) does not grow per feature. Because `AppKind::Dashboard` is an internal route rather than an external process, it needs no `sync::forward_create` loopback bridge — package/agent management is already pure Tauri IPC (`invoke("install_agent", …)` etc.) — only a capability entry extending the existing internal-route pattern (`main-global`/`main-switcher` are covered by `capabilities/default.json`; a `workspace-*-dashboard` label would need the same coverage or an entry mirroring `capabilities/agent-auth.json`).

### Switching between two panes per sandbox needs a second level of tab state

`switch_app` (`src-tauri/src/workspace/mod.rs:191-217`) and the registry's `active_app: Option<String>` (`src-tauri/src/workspace/types.rs`) currently model exactly one active pane *across the whole registry* — "bring sandbox `name`'s pane to the front" (doc comment, `mod.rs:190`) assumes one pane per sandbox, so switching sandboxes is switching panes. Adding a second pane per sandbox (Terminal and Dashboard) breaks that assumption: the model needs to distinguish "which sandbox is in front" from "which of that sandbox's panes is in front," which `switch_app`'s current `(app, name) -> ()` signature cannot express. This is named as an open question below rather than resolved here, because it changes a seam (`switch_app`'s signature and the registry's single `active_app` field) shared with the already-implemented Terminal-only path.

## Technology Choices With Tradeoffs

### Width responsiveness: CSS viewport media queries in the panel's own document

Chosen because `main-global` is a genuinely separate native document (see Proposed Model) whose viewport width already equals its real rendered width, so a plain `@media (max-width: …)` breakpoint (or Tailwind's `max-[420px]:` arbitrary variant) reacts correctly with zero IPC or Svelte-state plumbing. Alternatives evaluated:

- **Thread panel width/narrowness through Svelte state fed by `workspace://state`.** Rejected as unnecessary for this specific problem: the information CSS already has for free (real viewport width) would be re-derived from `hasTabs`/`collapsed` booleans and pushed through a store, adding an IPC-event dependency to a purely visual layout decision. (Per-sandbox "is my workspace open" state is still needed for the *button-set* changes in the next choice below — that is a different, non-visual decision CSS cannot make, so that plumbing is proposed anyway, just not for width alone.)
- **CSS container queries (`@container`).** Rejected as redundant: container queries exist to make an element responsive to an *ancestor's* size when the document viewport itself doesn't reflect that size (e.g., a card in a shared-viewport flex layout). Here the document viewport *is* the panel's real size because of the multi-webview architecture, so a container query would answer the same question a media query already answers, at the cost of an extra wrapping element and a feature JSDOM/Tailwind support matrix has to accommodate.

### Packages/Agents placement: sections in one dashboard pane, not per-concern switcher tabs

Chosen (per explicit product direction) because it keeps the switcher bar (`SWITCHER_H` = 40px) to at most two tabs per sandbox regardless of how many management concerns the dashboard grows to hold. Alternatives evaluated:

- **A separate switcher tab per concern (Terminal, Packages, Agents, …).** Rejected: three-plus tabs per sandbox crowds a 40px-tall bar and gives each concern its own tab-management chrome (open/close/focus) for tooling that is not a live external process the way Zellij is — Packages and Agents are IPC-driven forms, not sessions that benefit from independent pane lifecycle.
- **Leave Packages/Agents inline in the projects list permanently (status quo).** Rejected: this is the current behavior and is exactly what causes the 380px overflow this document also fixes; it does not deliver "the workspace becomes a hub for any work done inside a sandbox," which was the second half of the request driving this feature.

### Dashboard pane transport: internal SvelteKit route, not an external process

Chosen because package/agent management is already pure Tauri IPC (`invoke("install_agent", …)`, etc. inside `PackageManager.svelte`/`AgentManager.svelte`) with no container-served HTTP surface to forward, so an internal `WebviewUrl::App` route (the same shape `main-switcher` already uses) needs no `sync::forward_create` loopback bridge and no `ForwardPortMap` bookkeeping. The alternative — **wrapping Packages/Agents as a container-served HTTP surface** to reuse the exact external-URL pattern the terminal uses — was not seriously considered: it would require inventing an HTTP server for functionality that is IPC-native today, solely to make two pane-creation code paths look more alike.

### Compact action row: icon-only buttons, not an overflow dropdown menu

Chosen because, combined with the per-sandbox action-set narrowing above, 380px is generous for the remaining 3-5 buttons per row once labels are dropped for icons with `title` tooltips (several already carry a `title`, e.g. `SandboxItem.svelte:187`), so no new component dependency is needed. Alternative evaluated:

- **A shadcn-svelte `dropdown-menu` overflow ("more actions") menu.** Rejected for now: `src/lib/components/ui/` has no `dropdown-menu` primitive yet (only `button`, `field`, `input`, `label`, `separator`, `sonner`, `switch`, `dialog`, `command`, `textarea` exist), so adopting it is a new dependency for a row that, once Packages/Agents move out (this document's other proposal), no longer has enough buttons to need an overflow mechanism. Revisit only if a future row grows past what icon-only buttons fit at 380px.

## Validation

No spike has been run for this feature; it is pure design at this stage. It reuses, without re-validating, the geometry and pane-lifecycle primitives the `docs/features/embedded-windows/` spike (2026-07-01) already proved — `set_bounds` on child webviews, `Webview::hide`/`show` for pane switching, and an internal `WebviewUrl::App` child rendering a live SvelteKit route — so no new native-API risk is introduced by the Proposed Model above. The one genuinely new claim in this document — that a child webview's CSS viewport equals its `set_bounds` width, so ordinary media queries work unmodified — follows directly from the spike's confirmed DPI-scaling finding (`01_ideas.md` Validation: "a 600×700 logical child became 1200×1400 physical") but has not itself been exercised with an actual `@media` breakpoint in the running app; a short manual check (open a sandbox's workspace, inspect `main-global`'s rendered width in devtools at 380px, confirm a test breakpoint fires) is cheap and worth doing early in `02_dev.md` before relying on it further.

## Open Questions

- **`switch_app`/`active_app` model for two panes per sandbox.** The registry's `active_app: Option<String>` and `switch_app(app, name)` (`src-tauri/src/workspace/mod.rs:191-217`) assume one pane per sandbox is "the" pane to bring forward. Introducing `AppKind::Dashboard` alongside `AppKind::Terminal` needs either a `(sandbox, pane_kind)` parameter on `switch_app`, or a two-level active-state model (active sandbox, plus active pane within that sandbox). Undecided; `02_dev.md` must resolve this against the already-implemented single-pane-per-sandbox switching Terminal uses today, without regressing it.
- **Eager versus lazy dashboard pane creation.** Whether `open_workspace` always creates both the terminal pane and the dashboard pane together (dashboard always reachable once any workspace is open), or the dashboard pane is created lazily the first time its tab is clicked, is undecided. Affects whether Packages/Agents install actions are always one click away or require an extra pane-open step.
- **Whether opening a workspace becomes a prerequisite for managing packages/agents.** Today `PackageManager.svelte`/`AgentManager.svelte` are reachable inline for any listed sandbox regardless of whether its terminal/workspace has ever been opened. Moving them into the dashboard pane means a user must open a workspace before installing a package or agent, which is a behavior narrowing, not a pure move. Whether that's acceptable, or whether the dashboard pane should be independently reachable (i.e., `open_workspace` variant that opens only the dashboard, without a terminal), is undecided.
- **CSS breakpoint coupling to `GLOBAL_EXPANDED_W`.** The proposed media-query breakpoint is a hand-picked pixel value tracking the Rust constant `GLOBAL_EXPANDED_W` = 380 (`src-tauri/src/workspace/mod.rs:32`). If that constant changes without the CSS being updated, the two can drift silently (a panel that's actually 340px wide still assumes it has "380px" layout room, or vice versa). Whether to accept manual sync (with a code comment cross-referencing the Rust constant) or find a way to share the value (e.g., emit it as part of `workspace://state` and consume it as a CSS custom property) is undecided.
- **Whether `GLOBAL_EXPANDED_W` itself should grow.** Once Terminal/Packages/Agents buttons move out of each row (reducing button count) and the remaining buttons go icon-only, 380px may now be more width than the row needs, or still not enough once real content is prototyped. Left to `02_dev.md` to reconsider empirically rather than guessed here.
- **User-facing label for the dashboard pane's switcher tab.** "Manage," "Dashboard," "Tools," or something else — a naming choice, deferred to `02_dev.md`/product judgement.

## Common Gotchas

| Gotcha | Cause | Fix |
|---|---|---|
| A `SandboxItem.svelte` narrow-width fix is written but never visibly triggers | The rail-collapsed state (`GLOBAL_RAIL_W` = 48px) never renders the projects list at all — `+layout.svelte` shows only the expand button when `collapsed && hasTabs` (`src/routes/+layout.svelte:70-76`) | Target the breakpoint at the 380px expanded-with-tabs case only; there is no 48px case to design for in the projects list |
| A CSS breakpoint written against the *window's* viewport doesn't fire correctly for the global panel | Confusing `main-global`'s own document viewport (its real rendered width, per `set_bounds`) with the OS window's overall size | Write the media query assuming the panel's own document is the viewport — it already is, because `main-global` is a separate native child webview, not a flex child of the main window's DOM |
| The dashboard pane's `invoke` calls are denied | A new `workspace-*-dashboard` webview label is not covered by any capability (`capabilities/default.json` is scoped to the existing labels only) | Add a capability entry scoped to the new label, following `src-tauri/capabilities/agent-auth.json` or extending `default.json`'s webview list the way `main-global`/`main-switcher` are covered |
| Switching to the dashboard pane hides/breaks the terminal's live session, or vice versa | `switch_app` (`src-tauri/src/workspace/mod.rs:191-217`) and `active_app` assume one pane per sandbox; naively reusing them for two panes conflates "active sandbox" with "active pane within a sandbox" | Resolve the two-level active-state model (Open Questions) before wiring the dashboard tab's click handler to any existing switch primitive |
| Package/agent install actions disappear for a sandbox that never opened a terminal | Moving `PackageManager.svelte`/`AgentManager.svelte` into the dashboard pane makes opening a workspace a prerequisite, where today they are inline and always reachable | Decide eager-vs-lazy dashboard creation and whether a dashboard-only open path is needed (Open Questions) before removing the inline components |
| The 380px CSS breakpoint silently stops matching reality after a later change | `GLOBAL_EXPANDED_W` (`src-tauri/src/workspace/mod.rs:32`) and the CSS breakpoint are two independently-edited numbers with no shared source | Cross-reference the Rust constant in a comment next to the CSS breakpoint, or resolve the sharing mechanism in Open Questions before either number changes again |

# Workspace App Tabs Ideas

This document is the ideation for reshaping the embedded workspace's tab model once a sandbox is open: instead of `open_workspace` eagerly landing the user on a Terminal pane with Terminal / Manage / Agents all pre-shown, opening a sandbox should land on the **Manage** tab (a home/launcher surface listing the apps installed in that sandbox), and each app — Terminal, Agents, and any future app — is opened on demand as its own tab and can be individually closed while the others stay open. The switcher chrome is also restyled into a two-level grouping per sandbox (sandbox name on top, one tab per app below), with the Manage tab shown as a home icon (to be renamed `SandboxHome` later). Nothing described here is built yet. The feature builds directly on the panes/switcher machinery from `docs/features/responsive-panel/` (Phases A-D implemented) and `docs/features/agent-web-ui/` (the `AgentWeb`/Paseo pane). The relevant files are `src-tauri/src/workspace/mod.rs` and `src-tauri/src/workspace/types.rs` (Rust-owned registry, pane lifecycle, geometry), `src-tauri/src/lib.rs` (the `open_workspace`, `open_agent_web`, `switch_pane`, `close_workspace` commands), `src/routes/workspace/switcher/+page.svelte` (the tab bar), `src/routes/workspace/dashboard/+page.svelte` (the Manage pane's content), `src/lib/workspace/state.svelte.ts` (the shared `workspace://state` store), and `src/routes/projects/AgentManager.svelte` (today's "Open Agents UI" entry point).

## Current State

`open_workspace` (`src-tauri/src/lib.rs:405`) eagerly embeds **two** panes when a sandbox is first opened: `embed_terminal` (`src-tauri/src/workspace/mod.rs:126`) creates the Zellij Terminal pane and makes it the active tab, then `embed_dashboard` (`src-tauri/src/workspace/mod.rs:230`) creates the Manage pane hidden behind it. The Terminal embed is the slow half of opening a workspace: `prepare_terminal_webview` (`src-tauri/src/lib.rs`) resolves the Podman connection, idempotently starts `zellij web`, mints a login token, and allocates a Mutagen loopback forward before the pane exists. So opening a sandbox today always pays the Zellij-start cost and always lands on Terminal, even for a user who only wants to install a package.

The Agents (`AppKind::AgentWeb`, Paseo) pane is already **lazy**: `open_agent_web` (`src-tauri/src/lib.rs:344`) embeds it the first time its entry point is used and switches to it if it already exists (`src-tauri/src/workspace/mod.rs:135`, `embed_agent_web`). Its only entry point today is the "Open Agents UI" button inside `AgentManager.svelte` (`src/routes/projects/AgentManager.svelte:170`, `openAgentsUi`), which is rendered only when at least one agent is installed (`installedAgents.length > 0`, `src/routes/projects/AgentManager.svelte:248`). This is the existing precedent for "an app you can open only if it's installed" — the pattern this feature generalises to a launcher.

The switcher (`src/routes/workspace/switcher/+page.svelte`) renders a single flat horizontal row. It groups panes by sandbox (`bySandbox`, `switcher/+page.svelte:20`) and, per group, renders one button per pane labelled `"{sandbox} — {paneTitle(kind)}"` (`switcher/+page.svelte:93`), an inline "open Agents" button when no AgentWeb pane exists yet (`switcher/+page.svelte:96`), and a single `×` that calls `close_workspace` for the **whole** sandbox (`switcher/+page.svelte:104`, `close()`). There is no per-tab close and no sandbox-name/tab two-level structure. The bar is `SWITCHER_H` = 40 logical px tall (`src-tauri/src/workspace/mod.rs:33`), sized for one row of buttons.

Pane lifecycle in the registry (`WorkspaceState`, `src-tauri/src/workspace/types.rs:70`) tracks `apps: Vec<AppPane>`, one `active_app: Option<String>` label across the whole registry, and `sandbox_last_pane: HashMap<String,String>` mapping each sandbox to its last-focused pane. `switch_app` (`src-tauri/src/workspace/mod.rs:286`) brings a sandbox's last-active pane forward, **defaulting to its Terminal pane** when none is recorded (`switch_app_on_main`, `src-tauri/src/workspace/mod.rs:302-308`, the `p.kind == AppKind::Terminal` fallback). `close_app` (`src-tauri/src/workspace/mod.rs:404`, exposed as `close_workspace`) removes **every** pane belonging to a sandbox — there is no primitive that closes exactly one pane and leaves its siblings open. `AppKind` (`src-tauri/src/workspace/types.rs:21`) has three unit variants (`Terminal`, `Dashboard`, `AgentWeb`) and derives `Copy`.

The Manage pane's content is the internal route `src/routes/workspace/dashboard/+page.svelte`, which renders `StatusRow`, `PackageManager`, `AgentManager`, and `PortsManager` stacked for the sandbox named in its query string. It is where "what is installed in this sandbox" is already computed: `AgentManager.svelte` derives `installedAgents` from `list_packages` against the static `AGENTS` catalogue (`src/routes/projects/AgentManager.svelte:35`), and `PortsManager.svelte` reads user-exposed forwards from `src/lib/network/state.svelte.ts` (`openForwardsFor(...).filter(exposed)`, `src/routes/projects/PortsManager.svelte:26`). Icons in this codebase come from `@hugeicons/svelte` (e.g. `DashboardSquare01Icon` in `src/routes/projects/SandboxItem.svelte:13`), not inline SVG or lucide.

## Proposed Model

### Opening a sandbox lands on the Manage tab, and Terminal becomes a launchable app

Change `open_workspace` (`src-tauri/src/lib.rs:405`) to embed **only** the Manage pane (`embed_dashboard`) and make it the active tab, dropping the eager `embed_terminal` call. Terminal moves from "always embedded first" to "an app the user launches from the Manage tab," reached by a new command that mirrors `open_agent_web`'s lazy shape (`src-tauri/src/lib.rs:344`): embed-or-switch on `AppKind::Terminal`, running `prepare_terminal_webview` only on first launch. This is the seam that also removes the Zellij-start cost from the open path — a user who opens a sandbox to install a package never starts Zellij. `embed_dashboard` currently embeds the Manage pane **hidden** (`src-tauri/src/workspace/mod.rs:230`, doc comment "this never becomes the active pane on creation"); with no Terminal embedded first, that pane must instead become active on creation, which is a behavioural change to `embed_dashboard` or a new "embed and activate the dashboard" path.

### The Manage tab is an app launcher scoped to what the sandbox has installed

`src/routes/workspace/dashboard/+page.svelte` gains a launcher section listing the apps openable in this sandbox, each a button that opens (or switches to) that app's tab. Availability is per-app and already computable on this page: **Terminal** is always available; **Agents** is available when `installedAgents.length > 0` (the exact predicate `AgentManager.svelte` already computes, `src/routes/projects/AgentManager.svelte:35`); future apps hang off the same "installed → launchable" idea. This generalises the single "Open Agents UI" button (`AgentManager.svelte:170`) into a uniform launcher, so "Open Agents UI" is subsumed rather than kept as a separate control. The launcher reads which apps are **already open** (so it can show "switch to" vs "open") from the shared `workspace://state` store (`src/lib/workspace/state.svelte.ts`, `workspaceApps()`), which already exposes `apps: AppPane[]` keyed by `sandbox`.

### The switcher is a two-level grouping per sandbox: name row over app-tab row

Restyle `src/routes/workspace/switcher/+page.svelte` so each sandbox group (`bySandbox`, `switcher/+page.svelte:20`) renders two stacked rows: the sandbox name on top, and below it one tab per pane. The Manage/Home tab is rendered as a home icon (a `@hugeicons/svelte` home glyph, matching the icon convention in `SandboxItem.svelte`) and is always present. Terminal and Agents tabs appear only once their panes exist. This two-level layout is taller than today's single button row, so `SWITCHER_H` (`src-tauri/src/workspace/mod.rs:33`, currently 40) almost certainly has to grow — a geometry constant flowing through `workspace_layout` (`src-tauri/src/workspace/mod.rs:40`), so it must be changed in Rust, not only in CSS, or the two-row content is clipped.

### Each app tab closes individually, leaving the Manage tab and siblings open

Introduce a per-pane close distinct from the existing whole-sandbox `close_workspace`. A new `close_pane(name, kind)` command backed by a new `workspace::close_pane` closes exactly one pane: remove its `AppPane` from the registry, close its webview, tear down only that pane's Mutagen forward (Terminal/AgentWeb have one; Dashboard has none — the same per-kind mapping `close_app` already applies at `src-tauri/src/workspace/mod.rs:436-443`), re-activate the Manage tab (or a sibling), and re-layout without returning the global panel to full-bleed (the sandbox still has its Manage pane). This is a strict subset of `close_app`'s existing body split into "close one pane" vs "close all panes for the sandbox," so `close_workspace` stays as the close-the-whole-sandbox path (used by undeploy/destroy and the main-window Destroyed teardown, `src-tauri/src/workspace/mod.rs:113`). The switcher's per-tab `×` calls `close_pane`; closing the sandbox entirely remains a separate affordance.

### The active-pane default shifts from Terminal to Manage

Because Terminal is no longer embedded first, the `switch_app` fallback that defaults a sandbox to its Terminal pane (`switch_app_on_main`, `src-tauri/src/workspace/mod.rs:302-308`) must default to the Manage/Dashboard pane instead — that is now the always-present pane every open sandbox has. `sandbox_last_pane` (`src-tauri/src/workspace/types.rs:76`) still records the user's last-focused pane per sandbox, so re-focusing a sandbox restores whatever tab they left on; only the *no-record* default changes from Terminal to Dashboard.

## Technology Choices With Tradeoffs

### Manage pane doubles as the launcher, rather than a new dedicated launcher pane/AppKind

Chosen because the Manage pane (`AppKind::Dashboard`) is already the always-present internal-route pane for every open sandbox and already computes "what is installed" (`installedAgents` in `AgentManager.svelte`, exposed ports in `PortsManager.svelte`). Adding launch buttons to it is additive and needs no new pane lifecycle. Alternatives evaluated:

- **A separate `AppKind::Launcher` pane distinct from Manage.** Rejected: it would duplicate the always-present-internal-route role Dashboard already fills and add a fourth `AppKind` variant plus its own embed/close paths, for a surface that is conceptually the same "home for this sandbox" the request itself says the Manage tab already is ("we can rename it to SandboxHome later").
- **Keep the per-agent "Open Agents UI" button and add Terminal next to it ad hoc.** Rejected: that leaves two inconsistent launch idioms (one button living inside `AgentManager`, one elsewhere) instead of one launcher listing all apps uniformly, and does not scale to a third app.

### Terminal becomes lazy by reusing `open_agent_web`'s embed-or-switch shape, not a new mechanism

Chosen because `open_agent_web` (`src-tauri/src/lib.rs:344`) already proves the exact "embed on first launch, switch if it exists" pattern for an on-demand pane, and Terminal's construction (`prepare_terminal_webview` + `embed_terminal`) already runs on-demand today — only its *call site* (eager, inside `open_workspace`) changes. Alternative evaluated:

- **Keep embedding Terminal eagerly but start it hidden behind Manage.** Rejected: it still pays the full Zellij-start + forward-allocation cost on every workspace open (the slow half of `open_workspace`), defeating the "land on Manage cheaply" goal, and it contradicts "start off with the manage tab" by keeping a Terminal tab present before the user asked for one.

### Per-tab close as a new `close_pane`, not a parameter on `close_workspace`

Chosen because `close_workspace`/`close_app` is depended on as the *whole-sandbox* teardown by undeploy, destroy, and the main-window Destroyed handler (`src-tauri/src/workspace/mod.rs:113`, `478`), so overloading its contract with a "close just one" mode risks a caller closing one pane when it meant to close all. A separate command keeps each contract single-purpose. Alternative evaluated:

- **Add an optional `kind` parameter to `close_workspace` (absent = close all).** Rejected: the two operations differ in their post-conditions (one leaves the sandbox open on Manage and keeps the global panel narrow; the other returns the panel to full-bleed and drops `sandbox_last_pane`), so a single command would branch heavily and is easy to mis-call from the several existing whole-sandbox call sites.

### Home/tab icons from `@hugeicons/svelte`, not inline SVG

Chosen because `@hugeicons/svelte` is already this repo's icon library (`SandboxItem.svelte:10-18`), so a home glyph (e.g. a `Home*Icon`) for the Manage tab is consistent with existing chrome and needs no new dependency. Inline SVG paths were rejected as an inconsistent one-off against the established `HugeiconsIcon` usage.

## Validation

Every native primitive this feature relies on is already proven by earlier features and is reused without re-validation: on-demand pane embedding and switching (`embed_terminal`/`embed_agent_web`/`switch_pane`, proven by `docs/features/embedded-windows/` 2026-07-01 and `docs/features/agent-web-ui/` 2026-07-02), the internal-route Manage pane rendering a live SvelteKit route (`embed_dashboard`, `docs/features/responsive-panel/` Phase C-D), and per-pane forward teardown (`close_app`'s existing per-kind `network.close_forward` loop, `src-tauri/src/workspace/mod.rs:436-443`). One geometry claim is not yet validated: that a two-level switcher needs `SWITCHER_H` to grow. It is trivially checkable by rendering the new switcher markup at the current 40px and observing clipping, but that requires the two-row markup to exist, so it is a build-time check in `02_dev.md`, not a pre-implementation spike.

### Spike: does a closed-and-reopened Terminal tab keep the Zellij session? (2026-07-04, cleared — with a required design change)

Run by hand against a throwaway container (`localhost/sandbox-mio/base:4`, `podman-machine-default`) built with the app's exact terminal flags (`--tty --network pasta:--host-lo-to-ns-lo --publish 127.0.0.1::8082`). The container was removed after the spike. The question was Open Question "Cost of re-launching a closed Terminal": whether closing the Terminal tab (host webview + Mutagen forward torn down) and reopening it preserves the user's shell state. Findings:

- **The Zellij web daemon and existing sessions survive a tab close.** Closing a Terminal tab issues no Zellij stop command (`close_app` only closes the host webview and tears down the host-side Mutagen forward), so the in-container `zellij web` daemon stays up (`zellij web --status` still reported `Web server online` minutes later) and a manually created session (`main`) stayed listed and alive throughout. On reopen, `prepare_terminal`'s idempotent `--status` check (`src-tauri/src/runtime/mod.rs:217-225`) finds it online and skips the restart, as designed.
- **BLOCKER for state persistence: the app's root URL spawns a brand-new session on every open.** The app points the terminal webview at `http://127.0.0.1:<port>/` (root, `prepare_terminal_webview`, `src-tauri/src/lib.rs:137`). The served SPA derives its session from the URL path — `const sessionName = location.pathname.split("/").pop();` (`assets/index.js:21`) — so root yields an **empty** session name, and `initWebSockets` then connects to `/ws/terminal` with no name (`assets/websockets.js`, the `sessionName === "" ? ".../ws/terminal" : ".../ws/terminal/${sessionName}"` branch). A stdlib-WebSocket probe driving the real auth flow (`POST /command/login` → `POST /session` → `web_client_id` → `/ws/terminal`) confirmed that each no-name connection **creates a new randomly-named session**: connect #1 created `erudite-duck`, connect #2 created `awesome-apricot`, each showing the fresh "Hi from Zellij!" welcome screen. So closing and reopening a Terminal tab today would show an empty shell, and the previous session would persist only as an accumulating orphan.
- **The fix is to pin a stable session name in the URL path.** Connecting to the named path `/ws/terminal/main` attached to the existing `main` session with **no** new session created (21 bytes received, no welcome screen). Because the SPA reads the name straight off `location.pathname`, the app only needs to navigate the terminal webview to `http://127.0.0.1:<port>/<stable-session-name>` (e.g. the sandbox name) instead of `/` for close-and-reopen to reattach to the same live session. This is a small change to the URL built in `prepare_terminal_webview` (`src-tauri/src/lib.rs:137`), not a new mechanism — and it also fixes the pre-existing session-orphaning that already affects every terminal reopen today.

This spike resolves the "Cost of re-launching a closed Terminal" open question: the session survives, but only if `02_dev.md` adopts the stable-session-name URL; the default root URL loses state.

## Open Questions

- **Which apps are launchable, and where each app's availability predicate lives.** Terminal (always) and Agents (when `installedAgents.length > 0`) are clear, but whether **user-exposed ports** (`PortsManager.svelte`, `src/lib/network/state.svelte.ts`) also become openable app tabs — versus staying as external-browser links as they are today — is undecided, as is whether the launcher's app list is a hardcoded set in the Dashboard route or a small catalogue (mirroring `src/lib/agents/catalogue.ts`) that a future app registers into. `02_dev.md` must name the source of truth for "the set of apps and each one's installed-predicate."
- **Whether the Manage/Home tab is closable, and what closing it means.** The request says Manage "will also be shown" (always present). If the Home tab has no `×`, closing the whole sandbox needs a separate affordance (a group-level control on the sandbox-name row?). If the Home tab *is* closable, closing it presumably closes the sandbox (falls back to `close_workspace`). Undecided; affects the switcher's two-level layout and whether `close_pane` ever targets `AppKind::Dashboard`.
- **What happens when the last non-Home app tab is closed.** `close_pane` on the final Terminal/Agents pane should leave the sandbox open on its Manage tab (global panel stays narrow), which differs from `close_workspace` returning the panel to full-bleed. `02_dev.md` must confirm the sandbox does *not* auto-close when only Manage remains.
- **Cost of re-launching a closed Terminal. Resolved 2026-07-04 (see Validation spike).** The Zellij web daemon and any existing sessions survive a tab close (nothing stops them), so reopening re-runs `prepare_terminal_webview` cheaply (idempotent `--status` skips the restart). But shell state persists across close/reopen **only if** the terminal webview URL pins a stable session name in its path (`http://127.0.0.1:<port>/<session>`), because the served SPA reads its session from `location.pathname` and the current root URL (`/`) spawns a new random session on every open. `02_dev.md` must set a stable session-name path (e.g. the sandbox name) in `prepare_terminal_webview` (`src-tauri/src/lib.rs:137`); the remaining sub-question is what that stable name should be (sandbox name? a per-sandbox fixed literal?) and whether the same fix should be applied to the standalone `open_terminal` window path.
- **New `SWITCHER_H` value for the two-level bar.** The two-row grouping needs more than 40 logical px; the exact value is a layout constant to pick empirically in `02_dev.md` (see Validation), not guessed here. It flows through `workspace_layout` and the `content`/`switcher` rects, so it must be changed in `src-tauri/src/workspace/mod.rs`, not only in the switcher's CSS.
- **Multiple instances of the same app kind.** Pane labels are `workspace-{name}-{suffix}` where `suffix` is the `AppKind` (`src-tauri/src/workspace/mod.rs:170-175`), so exactly one pane per (sandbox, kind) is representable today. If exposed-port apps become tabs, several would share `AppKind` and collide on that label scheme — whether the launcher is restricted to one-per-kind apps (Terminal, Agents) or the label/registry model must gain a per-instance discriminator is undecided.
- **Grouping layout when several sandboxes are open at once.** The two-level block (name over tabs) is described per sandbox; how multiple sandboxes' blocks sit in the horizontal switcher bar (side by side, each with its own name row) and whether that fits at narrow content widths is a layout question deferred to `02_dev.md`.

| Opening a sandbox still starts Zellij and lands on Terminal | `open_workspace` (`src-tauri/src/lib.rs:405`) still calls `embed_terminal` before `embed_dashboard` | Drop the eager `embed_terminal` call so only the Manage pane is embedded and activated; make Terminal a launcher-triggered lazy embed like `open_agent_web` |

# Remote Sync Implementation Plan

This document is the build plan for in-app file synchronisation between a remote sandbox workspace and the user's laptop, driven by a bundled Mutagen sidecar with a "sync with remote" UI toggle. The plan continues the Phase 2 design in `docs/remote-workspace-sync.md` and records which design questions are now resolved. Mutagen sidecar bundling is already implemented; the remaining work is the sync wrapper, the SSH transport, the workspace resolver, and the UI. Background design rationale lives in the auto-memory `workspace-sync-design`.

## Resolved Decisions

The Phase 2 "Open Questions" in `docs/remote-workspace-sync.md` are resolved as follows. Mutagen is bundled as a Tauri sidecar (a vendored binary), not a required external install. The "sync with remote" toggle maps to Mutagen `sync pause` and `sync resume`, not session teardown; full teardown is a separate future feature. SSH transport configuration is supplied to Mutagen through an app-managed OpenSSH config file pulled into the user config with an `Include` directive, not by rewriting the user's own `~/.ssh/config` blocks in place.

## Already Implemented: Sidecar Bundling

Mutagen v0.18.1 is bundled as a Tauri sidecar. `bundle.externalBin` in `src-tauri/tauri.conf.json` declares the `binaries/mutagen` sidecar, and Tauri resolves the platform binary `mutagen-<target-triple>` at build time. The `tauri-plugin-shell` plugin is registered in `run` in `src-tauri/src/lib.rs` and scoped in `src-tauri/capabilities/default.json` with a `shell:allow-execute` entry naming the `binaries/mutagen` sidecar. The `command` function in `src-tauri/src/sync/mod.rs` builds a sidecar invocation with `MUTAGEN_DATA_DIRECTORY` pinned to an app-private directory under the Tauri app data directory, isolating the app's Mutagen daemon and sessions from a Mutagen the user installed separately. The `version` function in `src-tauri/src/sync/mod.rs` and the `mutagen_version` command in `src-tauri/src/lib.rs` are a runtime smoke test that the sidecar resolves and runs. The binary is gitignored (`/src-tauri/binaries/mutagen-*` in `.gitignore`) and staged reproducibly by `fetch_mutagen` in the root task runner `build.rs`, run as part of `build dev --setup`, which downloads the pinned Mutagen release and copies it to the triple-suffixed sidecar name. `fetch_mutagen` is Windows-only for now and uses `todo!()` for other platforms, matching `setup_e2e` in `build.rs`.

The runtime smoke test (invoking `mutagen_version` from the running application) is not yet performed and is the first validation step of the remaining work.

## Implementation Status

Phases A through C of the remaining work are implemented; phases D (sandbox lifecycle integration) and E (UI) are not. The sync engine wrapper, the SSH transport writer, and the workspace resolver seam land in this session as the Rust core, with no frontend and no sync-session lifecycle wiring.

Implemented in this session: the `SyncEngine` trait, `MutagenCli` implementation, and `SyncStatus` enum in `src-tauri/src/sync/types.rs`, with the implementation and the `status_from_session` status collapser in `src-tauri/src/sync/mod.rs`; the `default_sync_engine` constructor registered as Tauri managed state in `run` in `src-tauri/src/lib.rs`; the `sync_status`, `enable_sync`, and `disable_sync` commands in `src-tauri/src/lib.rs`; a best-effort Mutagen `daemon stop` on `RunEvent::Exit` in `run`; the OpenSSH config writer (`write_alias`, `remove_alias`, `ensure_include`) in `src-tauri/src/ssh/mod.rs` with `SshAlias` in `src-tauri/src/ssh/types.rs`; the `resolve_workspace` resolver returning a `WorkspacePlan` (`bind_mount_source`, `laptop_dir`, `strategy`) plus `WorkspacePlan`, `SyncStrategy`, and `ConnectionInfo` types in `src-tauri/src/backends/types.rs`; remote workspace creation over SSH (`remote_mkdir`) and live connection lookup (`remote_connection_info`, `parse_connection_entry`) in `src-tauri/src/backends/mod.rs`; the `is_remote` field on the `Sandbox` struct; and the `destroy` method on the `SandboxBackend` trait with its `destroy_sandbox` command.

On every remote sandbox creation, `create` in `src-tauri/src/backends/mod.rs` runs `remote_mkdir` and then writes the host's OpenSSH alias with `write_alias`, but it does not yet create a Mutagen sync session — session creation is phase D. The `SyncEngine` trait methods `create`, `terminate`, and `flush` are present but carry `#[allow(dead_code)]` because no caller exists until phase D wires them.

## Remaining Work: Phase D (Sandbox Lifecycle Integration)

Phase D wires the sync session into the sandbox lifecycle. On remote sandbox creation, `create` in `src-tauri/src/backends/mod.rs` must call `SyncEngine::create` with the session name set to the sandbox name, alpha set to the `WorkspacePlan` `laptop_dir`, and beta set to `<connection-alias>:<bind_mount_source>` where the connection alias equals the OpenSSH `Host` alias `write_alias` already registered (the Podman connection name). Sandbox destruction must call `SyncEngine::terminate`, and the destroy guard must call `SyncEngine::status` (and `flush` before reading) to warn when the remote workspace holds unsynced changes before `destroy` removes the container. Creating the Mutagen session requires the `SyncEngine` in backend code; because the engine is Tauri state holding an `AppHandle` and the backend is a separate `Arc<dyn SandboxBackend>`, phase D must decide whether the lifecycle commands in `src-tauri/src/lib.rs` orchestrate both states or whether the backend gains a reference to the engine.

## Remaining Work: Phase E (UI)

Phase E adds the frontend. The `Project` interface in `src/routes/projects/+page.svelte` must gain an `is_remote` field to match the extended `Sandbox` struct. The "sync with remote" toggle (shadcn-svelte `switch`, added with `pnpm dlx shadcn-svelte@latest add switch`) calls `enable_sync` and `disable_sync` and renders only when `is_remote` is true. The sync-status dot reads `sync_status` (by polling or by a status channel) and maps the four `SyncStatus` values to colours. A destroy control wired to the existing `destroy_sandbox` command is also absent from the UI.

## Sync Engine Wrapper

A `SyncEngine` trait and a `MutagenCli` implementation are added under `src-tauri/src/sync/`, parallel to the `SandboxBackend` trait and `PodmanCliBackend` implementation in `src-tauri/src/backends/types.rs`. The `MutagenCli` implementation drives the sidecar through the existing `command` helper in `src-tauri/src/sync/mod.rs`. The `SyncEngine` trait exposes session create, pause, resume, terminate, flush, and status operations, each routed through a single Mutagen subcommand. Mutagen structured status is read with `sync list --template='{{json .}}'`, parsed into a status value per session (watching, scanning, staging, reconciling, conflicts, errors). The wrapper is registered as Tauri managed state in `run` in `src-tauri/src/lib.rs` alongside the existing sandbox backend, and new Tauri commands (sync status, enable sync, disable sync) delegate to the wrapper the way the existing sandbox commands delegate to `SandboxBackend`.

## SSH Transport Configuration

Mutagen scp-style beta URLs (`alias:path`) carry neither a port nor an identity file, so each remote host needs an OpenSSH `Host` alias supplying the port and the Podman identity key. The app writes those aliases to a dedicated file at `~/.ssh/sandbox-mio/config` and adds a single `Include sandbox-mio/config` line to the top of `~/.ssh/config` once. The app owns the dedicated file completely and rewrites it freely; the user's `~/.ssh/config` is modified only by the one-time idempotent `Include` insertion. The OpenSSH client follows the `Include` directive and Mutagen uses the system OpenSSH client, so Mutagen reads the app-managed aliases without any Mutagen-specific flag. The marker-delimited block writer and stripper in `writeSshAlias` and `removeSshAlias` (`e2e/lib/mutagen.js`) are the reference implementation to port to Rust for the dedicated file. Each `Host` block is keyed to a Podman host (connection), not to an individual sandbox, because many sandboxes on one remote host share one SSH endpoint. The block's host, port, user, and identity are read live from `podman system connection list` when a session is created, never cached, because a Podman machine's SSH port is assigned dynamically at boot. Writes to `~/.ssh/config` for the one-time `Include` insertion are guarded by an in-process mutex and performed with an atomic temp-file rename to avoid corrupting the user's personal configuration.

## Workspace Resolver Seam

The `resolve_workspace` resolver in `src-tauri/src/backends/mod.rs` returns a `WorkspacePlan` with three values per sandbox: the bind-mount source path on the Podman host, the laptop directory path, and the sync strategy. For a local connection the two paths are equal and the sync strategy is the no-op `SyncStrategy::Local`, preserving the Phase 1 behaviour where the bind-mount source and the laptop directory are the same directory. For a remote connection the bind-mount source resolves inside the remote host filesystem (`/root/work/<name>` for the `root` user, `/home/<user>/work/<name>` otherwise) and the remote workspace directory is created over the connection with `mkdir -p` through the registered SSH identity (`remote_mkdir`), not with the laptop-side `std::fs::create_dir_all` that `create` in `src-tauri/src/backends/mod.rs` uses for local sandboxes. Routing remote logic through the resolver keeps the shape of `create` in `src-tauri/src/backends/mod.rs` unchanged.

Local versus remote is decided by the `IsMachine` field of the connection's entry in `podman system connection list`, not by comparing the connection name to `podman-machine-default`. A Podman machine (`IsMachine` true) is a VM on the laptop that auto-mounts the user profile, so a laptop path bind-mounts straight into it and needs no sync — this is the local case, and it covers `podman-machine-default` and any machine the test harness uses (the e2e harness in `e2e/wdio.conf.js` runs the app against the `mio-tests` machine). Only a non-machine connection (a real server registered via `provision_host` in `src-tauri/src/backends/mod.rs`) is treated as remote. The name-equality rule the earlier plan text implied was rejected because it would misclassify the `mio-tests` machine as remote and break the local bind-mount behaviour the `workspace-mount.spec.js` e2e test asserts. The classification is performed by `parse_connection_entry` in `src-tauri/src/backends/mod.rs` (the pure, unit-tested core of `remote_connection_info`).

The `IsMachine` rule has a consequence for testing remote behaviour end-to-end: the two-Podman-machine validation topology in `docs/remote-workspace-sync.md` uses a second machine as the remote stand-in, but that stand-in is `IsMachine` true and so classifies as local under the resolver. An app-driven remote-path e2e test therefore needs a connection with `IsMachine` false (a `podman system connection add` entry pointing at an SSH endpoint, not a `podman machine init` machine), even if that endpoint is a loopback port on a local machine's socket.

## Sandbox Lifecycle Integration

A Mutagen sync session is created when a remote sandbox is created and terminated when the remote sandbox is destroyed, following `docs/remote-workspace-sync.md`. The "sync with remote" toggle calls Mutagen `sync pause` and `sync resume` rather than terminate and create, so toggling preserves the session and its conflict state and is near-instant. Destroying a remote sandbox checks Mutagen sync status before removing the container and warns the user when the remote workspace holds unsynced changes, because the remote workspace directory holds the only copy of unsynced work. The remote workspace directory persists across container stop and destroy; the OpenSSH alias block in `~/.ssh/sandbox-mio/config` persists as long as the Podman host is registered.

## Sandbox Struct and Remoteness

The `Sandbox` struct in `src-tauri/src/backends/types.rs` is extended so the frontend can tell a remote sandbox from a local one and render sync state. The frontend needs to know whether a sandbox is remote (the resolver returned unequal paths and a live sync strategy) and the current sync status value. Local sandboxes report no sync strategy, so the frontend hides the sync controls for local sandboxes rather than offering a toggle that does nothing.

## UI Toggle and Status

The "sync with remote" toggle and a sync-status indicator are added to each sandbox list item in `src/routes/projects/+page.svelte`, beside the existing container-status dot. The toggle uses the shadcn-svelte `switch` component, which is not yet present in `src/lib/components/ui/`; per `AGENTS.md`, the component is added with `pnpm dlx shadcn-svelte@latest add switch` before building any custom alternative. The sync-status indicator reuses the coloured-dot idiom already used for container state in `src/routes/projects/+page.svelte`, with values syncing, up to date, conflict, and error. Sync status is delivered to the frontend either by polling the sync-status command on an interval or by pushing status through the channel pattern already used for container events in `startListening` in `src/routes/projects/+page.svelte`.

## Daemon Lifecycle

The Mutagen daemon auto-starts on the first sync session command, so no explicit daemon start is wired. Because `MUTAGEN_DATA_DIRECTORY` isolates the app's daemon, a best-effort `daemon stop` on application exit is added when the sync wrapper lands, so the app does not orphan its private daemon. Stopping the app-private daemon never affects a Mutagen the user installed separately.

## Common Gotchas

| Gotcha | Cause | Fix |
|---|---|---|
| Tauri build fails because the Mutagen sidecar binary is absent | The Mutagen binary is gitignored (`/src-tauri/binaries/mutagen-*` in `.gitignore`) and not committed | Run `build dev --setup` once after clone and in CI before `pnpm tauri build`; `fetch_mutagen` in `build.rs` stages the sidecar |
| Mutagen sidecar fetch hits `todo!()` on a non-Windows platform | `fetch_mutagen` in `build.rs` is implemented for Windows only | Add the non-Windows download and target-triple mapping to `fetch_mutagen` in `build.rs` |
| App's Mutagen sessions collide with a user-installed Mutagen | A shared default Mutagen data directory means one daemon serves both | Keep `MUTAGEN_DATA_DIRECTORY` pinned to the app-private directory set by `command` in `src-tauri/src/sync/mod.rs` |
| Mutagen sync session cannot connect to a non-standard SSH port | A Mutagen scp-style `alias:path` URL cannot carry a port or identity file | Write an OpenSSH `Host` alias to `~/.ssh/sandbox-mio/config` and pull it in with a one-time `Include sandbox-mio/config` line in `~/.ssh/config` |
| Mutagen sync stops working after a Podman machine restart | A Podman machine's SSH port is assigned dynamically at boot, so a cached port points at the wrong port after a restart | Read host, port, user, and identity live from `podman system connection list` when creating a session, never cached |
| User's `~/.ssh/config` is corrupted by sync setup | Concurrent or non-atomic rewrites of the shared user config file | Touch `~/.ssh/config` only for the one-time `Include` insertion, guarded by an in-process mutex and written with an atomic temp-file rename; keep churny writes in the app-owned `~/.ssh/sandbox-mio/config` |
| Sync toggle loses conflict state and re-scans on every flip | The toggle terminates and recreates the Mutagen session instead of pausing it | Map the toggle to Mutagen `sync pause` and `sync resume`; reserve `sync terminate` for sandbox destruction |
| Remote workspace work lost after destroying a sandbox | The remote sandbox was destroyed while the remote workspace held unsynced changes | Check Mutagen sync status before destroy and warn on unsynced changes; never delete the remote workspace directory on container stop or destroy |
| Local sandboxes show a sync toggle that does nothing | The frontend rendered sync controls for a sandbox whose resolver returned equal paths and a no-op strategy | Render sync controls in `src/routes/projects/+page.svelte` only when the `Sandbox` struct reports a remote sync strategy |
| Adding a custom `switch` element instead of the shared component | The shadcn-svelte `switch` component is not yet in `src/lib/components/ui/` | Add the component with `pnpm dlx shadcn-svelte@latest add switch` before building any custom toggle, per `AGENTS.md` |
| App leaves a Mutagen daemon running after exit | The app-private daemon auto-started on first session command and was never stopped | A best-effort Mutagen `daemon stop` runs on `RunEvent::Exit` in `run` in `src-tauri/src/lib.rs` |
| The `mio-tests` machine is treated as remote and `workspace-mount.spec.js` breaks | Local-versus-remote was decided by connection name equality instead of the `IsMachine` field | Decide remoteness from the `IsMachine` field of `podman system connection list` in `parse_connection_entry` (`src-tauri/src/backends/mod.rs`); Podman machines are local, only non-machine connections are remote |
| Remote sandbox files never reach the laptop even though the workspace and SSH alias exist | `create` in `src-tauri/src/backends/mod.rs` runs `remote_mkdir` and `write_alias` but does not yet create a Mutagen sync session — session creation is phase D | Wire `SyncEngine::create` into remote sandbox creation in phase D with session name = sandbox name, alpha = `WorkspacePlan` `laptop_dir`, beta = `<connection-alias>:<bind_mount_source>` |
| An app-driven remote-sync e2e test classifies its stand-in host as local and exercises no sync | The two-machine validation stand-in is a Podman machine (`IsMachine` true), which the resolver treats as local | Register a non-machine connection (`podman system connection add` against an SSH endpoint, `IsMachine` false) for any app-driven remote-path e2e test |
| `SyncEngine` methods `create`, `terminate`, and `flush` appear dead | The methods are present but unwired until phase D, marked `#[allow(dead_code)]` in `src-tauri/src/sync/types.rs` | Wire them in phase D (session create on remote create, terminate on destroy, flush before the destroy-guard status read) and remove the `#[allow(dead_code)]` attributes |
